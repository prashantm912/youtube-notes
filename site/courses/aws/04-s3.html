Module: S3 Object Storage

S3 looks like a hard disk in the console and behaves nothing like one. Almost every expensive S3 mistake — the runaway bill, the leaked bucket, the "renamed" folder that cost a million requests — starts with someone treating an object store as a filesystem.

Knowledge Library → Courses → Cloud AWS → S3 Object Storage

What this module covers

Amazon S3 is the default place data lands on AWS: application uploads, database backups, build artefacts, data-lake parquet, static front-ends, logs from every other service. It is cheap, effectively unlimited, and callable from anywhere with a signed HTTPS request — which is exactly why it is also the service most often left open to the internet by accident.

The first half of this module is the storage model: what a bucket and an object actually are, why the keyspace is flat, how big an object can be and when you must use multipart upload, what eleven nines of durability does and does not promise, and how to pick a storage class and let lifecycle rules move data down the cost curve on their own. The second half is access — encryption, the four overlapping permission layers, presigned URLs, static hosting and event notifications. That second half is where the breaches happen, so it is where interviewers dig.

Topics

Buckets and objects: an object store is not a filesystem

A bucket is a container with a name that must be globally unique across every AWS account on the planet — not unique to your account, unique to S3 — and that name has to be DNS-compatible: lowercase, 3 to 63 characters, no underscores, no uppercase, no IP-address shapes. A bucket is created in exactly one region and its data stays in that region unless you deliberately replicate it, which is the answer to most data-residency questions. An object is four things bundled together: a key (a UTF-8 string up to 1024 bytes), the value (the bytes themselves), metadata (system metadata like content type and storage class, plus your own x-amz-meta-* headers), and — if the bucket is versioned — a version id.

The part that trips people up is that the keyspace is flat. There are no directories. invoices/2026/07/inv-9001.pdf is one key containing slash characters, not a file three levels deep. The console draws folders by asking S3 to list with / as a delimiter and rendering the common prefixes; nothing hierarchical exists on the server. Three consequences follow immediately, and they are all interview material: there is no atomic rename (a "rename" is a server-side copy followed by a delete, so renaming a million-object prefix is two million billable requests), there is no partial in-place update (changing one byte means rewriting the whole object), and a listing returns at most 1000 keys per request in lexicographic order, so anything that walks a large bucket must paginate.

Object size, multipart upload and request throughput

A single object can hold up to 5 TB, but a single PUT can carry only 5 GB. Anything larger must go through multipart upload, and AWS recommends switching to it above roughly 100 MB anyway. Multipart splits the object into parts (minimum 5 MB each except the last, maximum 10,000 parts), uploads them independently and in parallel, and reassembles them when you send the complete request. The wins are throughput on a fat pipe, a retry that only re-sends one failed part instead of the whole file, and the ability to start uploading before the final size is known. The AWS SDKs' transfer-manager classes do all of this for you — you rarely hand-roll the three API calls.

Multipart has one classic operational trap: parts from an upload that was never completed or aborted stay in the bucket, are billed as storage, and do not show up in a normal object listing. Buckets have quietly accumulated terabytes this way. Every production bucket should carry a lifecycle rule that aborts incomplete multipart uploads after a few days. On throughput, S3 scales to at least 3,500 write and 5,500 read requests per second per partitioned prefix, and it partitions automatically as load grows — so spreading hot data across several prefixes still helps, while the old advice about random hash prefixes has not been necessary for years. For large reads, byte-range fetches let you pull an object in parallel chunks.

{
  "Rules": [{
    "ID": "abort-orphaned-multipart-parts",
    "Status": "Enabled",
    "Filter": { "Prefix": "" },
    "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
  }]
}

Durability, availability, and the consistency question interviewers still ask

S3 Standard is designed for 99.999999999% durability — eleven nines — by redundantly storing every object across a minimum of three Availability Zones in the region. The number is a statement about hardware and media failure: if you stored ten million objects you would expect, on average, to lose one of them once every ten thousand years. Availability is a different and much smaller number (S3 Standard is designed for 99.99% availability with a 99.9% SLA), and it varies by storage class — One Zone-IA lives in a single AZ, so an AZ loss can destroy the data outright, which is the whole reason it is cheaper.

The point worth carrying into a design review: durability is not backup. Eleven nines protects you from disks dying. It does nothing about a DELETE issued by a buggy deploy script, an overwrite that replaces good data with garbage, ransomware with valid credentials, or an account compromise — all of those replicate perfectly across all three AZs at machine speed. Real protection is versioning plus lifecycle-managed noncurrent versions, MFA delete or Object Lock on the buckets that matter, and replication into a different account so that a compromise of one account cannot reach the copy.

On consistency: since December 2020 S3 provides strong read-after-write consistency for all GET, PUT and LIST operations — including overwrites and deletes — at no extra cost and with no performance penalty. Before that, new-object PUTs were read-after-write consistent but overwrites and deletes were only eventually consistent, which is why a generation of data pipelines carried retry loops and "S3 guard" metadata layers. Interviewers who learned S3 before 2021 still ask the eventual-consistency question, so answer it in two moves: describe the old model, then state what changed and when. Note the remaining caveat — bucket-level configuration changes (policies, ACLs, replication settings) are still eventually consistent, so a policy edit may take a moment to take effect everywhere.

Storage classes: a cost-versus-access-pattern decision

Every storage class trades a lower per-GB storage price against some combination of retrieval charges, retrieval latency, a minimum billable object size and a minimum storage duration. S3 Standard has no retrieval fee and no minimums — the default for hot, frequently read data. Standard-IA and One Zone-IA cut the storage price roughly in half but add a per-GB retrieval charge, bill a minimum of 128 KB per object and a minimum of 30 days; One Zone-IA is cheaper again because it lives in one AZ only, so use it exclusively for data you can regenerate. Intelligent-Tiering charges a small per-object monitoring fee and then moves objects between access tiers automatically with no retrieval charges — the right default whenever the access pattern is unknown, seasonal or changing, which in practice is most application data.

The Glacier family is archive storage and the differentiator is retrieval time. Glacier Instant Retrieval gives millisecond access with a 90-day minimum duration — archive pricing for data you occasionally need immediately. Glacier Flexible Retrieval (the old Glacier) is cheaper but you must restore first: expedited in minutes, standard in a few hours, bulk in up to half a day. Glacier Deep Archive is the cheapest storage AWS sells, with a 180-day minimum and restores measured in hours to a couple of days — compliance archives and tape replacement. Two costs catch people out: deleting an object before its minimum duration is billed as if you had kept it for the full period, and every restore from Glacier is a paid request in addition to the per-GB retrieval charge.

Lifecycle policies: moving and expiring data without a cron job

A lifecycle configuration is a set of rules attached to a bucket, each scoped by a filter (prefix, object tag, object size, or the whole bucket) and carrying two kinds of action. Transition actions move objects to a cheaper storage class after N days; expiration actions delete them. On a versioned bucket you get the same pair for noncurrent versions, plus the two housekeeping actions every bucket should have: abort incomplete multipart uploads, and remove expired object delete markers. A typical rule chain reads like a retention policy written in JSON: Standard for a month, Standard-IA for a quarter, Glacier Flexible for a year, gone after seven.

Two operational facts matter. First, lifecycle is asynchronous and batched — S3 evaluates rules at least once a day, so a transition happens on or after the day you specified, not at a precise moment; billing changes when the transition actually completes. Second, transitions are not free: each object transitioned costs a request, so moving ten million 20 KB log files to Glacier can cost more in requests than it ever saves in storage. That is exactly why the object-size filter exists — transition the large objects, leave the small ones in Standard or hand the whole problem to Intelligent-Tiering.

{
  "Rules": [{
    "ID": "invoice-archive-ladder",
    "Status": "Enabled",
    "Filter": { "And": { "Prefix": "invoices/", "ObjectSizeGreaterThan": 131072 } },
    "Transitions": [
      { "Days": 30,  "StorageClass": "STANDARD_IA" },
      { "Days": 90,  "StorageClass": "GLACIER" },
      { "Days": 365, "StorageClass": "DEEP_ARCHIVE" }
    ],
    "Expiration": { "Days": 2555 },
    "NoncurrentVersionExpiration": { "NoncurrentDays": 30 }
  }]
}

Versioning, delete markers and MFA delete

Versioning is a bucket-level switch, and it is one-way in an important sense: once enabled it can be suspended but never returned to the unversioned state, and objects written while it was on keep their versions. With versioning on, every PUT to an existing key creates a new version with a fresh version id and keeps the old one — which is the protection against a bad overwrite, and also the reason a versioned bucket with no lifecycle rules grows without limit while you keep paying for versions nobody can see in the console's default view.

Deletes are where the model gets interesting. A DELETE without a version id does not delete anything: it inserts a delete marker that becomes the current version, so a GET returns 404 and a normal LIST omits the key, but every prior version is intact. Delete the delete marker and the object is back — this is the single most useful S3 recovery trick to know. A DELETE with a version id permanently destroys that specific version and is the only way to actually free the storage. Lifecycle handles the cleanup at scale via NoncurrentVersionExpiration and ExpiredObjectDeleteMarker. For the buckets that really matter, MFA delete requires an MFA code from the account root user before any version can be permanently deleted or the versioning state changed; it can only be configured through the CLI or API, never the console, which is exactly why it is rare in the wild — and why Object Lock, with its per-object WORM retention and legal holds, is the more practical compliance control today.

Encryption at rest and in transit

Since January 2023 every new object is encrypted at rest by default with SSE-S3 (AES-256, keys entirely managed by AWS) at no additional cost — so "is my data encrypted?" now has a boring default answer, and the real question is which key you want to control. SSE-KMS encrypts with an AWS KMS key you can audit, rotate and restrict with its own key policy, giving you a second, independent gate: a principal needs both S3 permissions and kms:Decrypt on the key to read an object. The cost is real, though — every PUT triggers a GenerateDataKey call and every GET a Decrypt call, which are billed and count against your KMS request quota, so a high-throughput bucket can genuinely throttle on KMS. S3 Bucket Keys exist precisely for this: a short-lived bucket-level key cuts KMS request traffic by up to 99%, and you should switch it on for any busy SSE-KMS bucket. SSE-C puts you in charge: you send the encryption key on every request, S3 uses it and throws it away, and if you lose it the data is gone.

Encryption in transit is separate and is not on by default in the sense people assume — S3 accepts plain HTTP. The fix is a bucket policy that denies every request where the aws:SecureTransport condition key is false, which is a control auditors ask for by name. A second policy commonly paired with it denies any PutObject whose s3:x-amz-server-side-encryption header is not the algorithm you mandate, so a misconfigured client cannot quietly write objects under the wrong key.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyUnencryptedTransport",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": ["arn:aws:s3:::acme-invoices", "arn:aws:s3:::acme-invoices/*"],
    "Condition": { "Bool": { "aws:SecureTransport": "false" } }
  }]
}

Bucket policies, IAM policies and the legacy of ACLs

Access to an S3 object is decided by several policy types evaluated together, and knowing which one to reach for is the practical skill. IAM identity policies attach to a user or role and say what that principal may do — this is the right tool for your own applications, because the permission travels with the workload's role and you manage it in one place. Bucket policies are resource-based: they attach to the bucket, name a Principal, and are the only way to grant access to another AWS account directly or to make something genuinely public. They are also where account-wide guardrails live, because a Deny in a bucket policy cannot be argued with by any identity policy. The evaluation rule to state in an interview is simple: an explicit Deny anywhere always wins; otherwise, for same-account access, an Allow in either the identity policy or the bucket policy is enough.

ACLs are the original 2006 mechanism — per-bucket and per-object grants to canonical user ids or predefined groups such as AllUsers. They are legacy and AWS says so plainly. Since April 2023 new buckets are created with Object Ownership set to bucket owner enforced, which disables ACLs entirely and makes the bucket owner the owner of every object written to it, including cross-account uploads. This also fixed a genuinely nasty old failure mode where another account uploaded an object you could not read in your own bucket. The recommendation is unambiguous: leave ACLs disabled, use IAM policies for your own principals, use bucket policies for cross-account grants and for deny-based guardrails, and treat any requirement for ACLs as a legacy migration to plan out rather than a design choice.

Block Public Access and Object Ownership: the guardrail that ends the headlines

Every "millions of records exposed in an unsecured S3 bucket" story comes down to the same thing: someone granted public read through an ACL or a bucket policy, usually to make one file work, and nobody noticed. S3 Block Public Access is the account-level and bucket-level guardrail that makes that impossible regardless of what the policies say. It has four independent settings — block new public ACLs, ignore existing public ACLs, block new public bucket policies, and restrict public access granted by any policy — and since April 2023 all four are enabled by default on new buckets, alongside ACLs being disabled.

Two habits follow. Turn Block Public Access on at the account level, so it applies to every bucket including ones created later by a rushed engineer or a half-reviewed Terraform module; a per-bucket setting is one careless terraform apply from being switched off. And when someone genuinely needs to serve files to the public, do not reach for the block-public-access toggle — that is what CloudFront with Origin Access Control is for, covered below. Back the guardrail with IAM Access Analyzer for S3, which continuously reports buckets reachable from outside your account or organization, and with the S3 security best-practices checklist as your review script.

Presigned URLs: letting the browser talk to S3 directly

A presigned URL is an ordinary S3 URL carrying a Signature Version 4 signature in its query string, generated by your backend using its own credentials. Anyone holding the URL can perform that one operation — usually a single GET or a single PUT of one specific key — until the expiry you set, with no AWS credentials of their own. It is the standard answer to "how does a browser or mobile app upload a 200 MB video?": your API authenticates the user, generates a presigned PUT URL, and returns it; the client uploads straight to S3. Nothing large ever flows through your application servers, which removes the bandwidth cost, the request-timeout problems and the temp-disk pressure in one move.

Interview-grade details worth having ready. The URL inherits the permissions of the principal that signed it, so sign with a narrowly scoped role, never with broad admin credentials. Maximum lifetime is 7 days when signed with IAM user credentials, but only as long as the session when signed with temporary STS credentials (an instance profile or Lambda role) — the URL dies with the session, whatever expiry you asked for, which is a very common production surprise. A presigned URL is a bearer token: anyone who obtains it has that access, so keep expiries short and treat the URLs as secrets in logs. For uploads with server-side constraints — a maximum file size, a required content type, a fixed key prefix — use a presigned POST policy instead of a presigned PUT, because a plain presigned PUT cannot cap the size of what gets uploaded.

Static website hosting, and why CloudFront with OAC is the production answer

S3 can serve a static site directly: switch on website hosting, nominate an index document and an error document, and the bucket gets a website endpoint that resolves relative paths and directory-style URLs. It is the cheapest possible way to publish a built React or Angular bundle. But the website endpoint has hard limits that make it wrong for anything customer-facing: it speaks HTTP only, so no HTTPS and therefore no custom-domain TLS, it requires the bucket contents to be genuinely public (fighting your Block Public Access guardrail), it serves from one region so users far away pay the latency, and it gives you no caching layer, no access logs at the edge and no WAF.

The production pattern is CloudFront in front of a completely private bucket, using Origin Access Control. OAC is a CloudFront-signed identity that the bucket policy trusts; the bucket stays fully blocked to the public, only CloudFront can read it, and you get TLS with an ACM certificate on your own domain, edge caching, compression, HTTP/2 and HTTP/3, WAF integration and CloudFront Functions for things like SPA routing rewrites. Note the pairing detail: with OAC you use the bucket's REST endpoint as the origin, not the website endpoint, so index-document resolution for sub-paths is handled by CloudFront's default root object and a small function rather than by S3. OAC replaces the older Origin Access Identity, which still works but is no longer what you should build.

Event notifications: S3 as an event source for Lambda, SQS, SNS and EventBridge

S3 can publish an event whenever something happens to an object — created, removed, restored from Glacier, replicated, tagged, or transitioned by lifecycle — and deliver it to Lambda, an SQS queue, an SNS topic, or EventBridge. This turns the bucket into the front door of an asynchronous pipeline: an upload lands, a Lambda generates a thumbnail or extracts text, a message goes to a queue for a batch worker. Notifications can be filtered by key prefix and suffix, which is how you route uploads/ to one function and reports/*.csv to another. Delivery is typically within seconds but is not guaranteed to be ordered or exactly once, so consumers must be idempotent — a fact that turns into a follow-up question surprisingly often.

Two choices to be able to defend. Pick SQS over direct Lambda when the processing is slow, spiky or needs a retry/dead-letter story you control — the queue absorbs the burst and decouples the producer from your concurrency limits. Pick EventBridge when you need more than the native integration gives you: richer content-based filtering on any part of the event, more than one consumer per event without fan-out plumbing, cross-account and cross-region routing, archive and replay, and a schema registry. EventBridge covers all S3 API-level activity rather than the fixed notification event list, at the cost of an extra hop and per-event pricing. The classic gotcha to mention unprompted: a Lambda that writes its output back into the same bucket and prefix that triggered it will re-trigger itself — filter by prefix or write to a different bucket.

Beyond one bucket: replication, Object Lock and Requester Pays

Replication copies objects automatically from a source bucket to one or more destinations. Cross-Region Replication (CRR) serves disaster recovery, latency for a distant user base, and data-residency obligations; Same-Region Replication (SRR) serves log aggregation and, most usefully, copying into a separate account so a compromise or a rogue delete in the source cannot reach the copy. Versioning must be enabled on both ends, replication is asynchronous by default (S3 Replication Time Control adds a 15-minute SLA at extra cost), and — the detail interviewers probe — enabling replication does not backfill: only objects written after the rule exists are replicated, and existing data needs S3 Batch Replication. Delete markers replicate only if you opt in, and version-specific deletes never replicate, which is deliberate protection against a delete propagating to your DR copy.

Object Lock gives write-once-read-many retention — governance mode (privileged users can override) or compliance mode (nobody, including the root user, can delete until the retention expires), plus indefinite legal holds. It must be enabled at bucket creation and requires versioning, and it is the practical control for regulatory retention and for ransomware-resistant backups. Requester Pays flips the billing for downloads and requests onto the caller, who must send x-amz-request-payer and cannot be anonymous — the standard arrangement for publishing large open datasets without funding the whole internet's egress.

Interview questions

S3 shows up in almost every AWS round in India — service companies favour the storage-class and lifecycle questions because they map to certification syllabi, while product companies push on presigned uploads, the access-control layers and how you would actually protect data from a bad delete:

Beginner What is S3, and how is a bucket different from an object?

S3 is object storage reached over an HTTPS API. A bucket is the container: its name is globally unique across all AWS accounts, must be DNS-compatible, and is tied to a single region where the data lives. An object is what you store — a key (up to 1024 UTF-8 bytes), the value, metadata (system plus your own x-amz-meta-* headers), and a version id when versioning is on. There is no filesystem underneath; the keyspace is flat.

Beginner Are there folders in S3?

No. logs/2026/app.log is a single key that happens to contain slashes. The console renders folders by listing with / as a delimiter and grouping the common prefixes. Because of that there is no atomic rename (rename means server-side copy plus delete, billed per object), no in-place partial edit, and listing is lexicographic and paginated at 1000 keys per request.

Beginner What are the maximum object size and the maximum single-PUT size?

An object can be up to 5 TB. A single PUT can carry at most 5 GB, so anything larger requires multipart upload, and AWS recommends multipart above roughly 100 MB regardless. Parts are at least 5 MB each (except the last) and there can be at most 10,000 of them.

Beginner Name the S3 storage classes and say when you would use each.

Standard for hot data with no retrieval fee; Intelligent-Tiering when the access pattern is unknown or changing (small monitoring fee, no retrieval charges); Standard-IA for infrequent but immediately needed data across three AZs; One Zone-IA for the same but only for reproducible data, since a single AZ loss destroys it; Glacier Instant Retrieval for archives you occasionally need in milliseconds; Glacier Flexible Retrieval for archives where a wait of minutes to hours is acceptable; Glacier Deep Archive for compliance data restored in hours to days at the lowest price.

Beginner What does versioning do, and what happens when you delete a versioned object?

Versioning keeps every write of a key rather than overwriting. A delete without a version id does not remove anything — it adds a delete marker as the new current version, so GET returns 404 and normal listings skip the key, while all prior versions survive. Removing the delete marker restores the object. Only a delete that names a specific version id destroys data and reclaims the storage.

Intermediate How would you let a browser upload a large file directly to S3 without proxying it through your backend?

Generate a presigned URL. The backend authenticates the user, then uses its own IAM role to sign a URL for one operation on one key with a short expiry, and returns it; the browser PUTs straight to S3. For files above a few hundred megabytes, presign each part of a multipart upload. Points to raise: the URL carries the signer's permissions so sign with a narrow role; a URL signed with temporary STS credentials expires with the session no matter what expiry you requested; the URL is a bearer token, so keep it short-lived and out of logs; use a presigned POST policy rather than a presigned PUT when you need to enforce a maximum file size or content type; and configure CORS on the bucket for browser uploads.

Intermediate A bucket costs far more than expected but the object count looks small. What do you check?

Old noncurrent versions on a versioned bucket that has no NoncurrentVersionExpiration rule; orphaned incomplete multipart upload parts, which are billed but never appear in a listing; millions of tiny objects in IA or Glacier classes, each billed at the 128 KB minimum and each having cost a transition request; early deletions inside the 30/90/180-day minimum durations, billed for the full period anyway; and request or data-transfer charges rather than storage. Use S3 Storage Lens and Storage Class Analysis to see which it is, then fix with lifecycle rules or Intelligent-Tiering.

Intermediate Bucket policy, IAM policy or ACL — which do you use, and how are they evaluated?

IAM identity policies for your own principals, because permission travels with the role. Bucket policies for cross-account grants and for account-wide deny guardrails, because they attach to the resource and can name a Principal. ACLs are legacy and disabled by default on new buckets via Object Ownership set to bucket owner enforced — do not design with them. Evaluation: an explicit Deny anywhere always wins; otherwise, within one account, an Allow in either the identity policy or the bucket policy suffices. Block Public Access overrides both when it comes to public access.

Intermediate SSE-S3 vs SSE-KMS vs SSE-C — and what is the catch with SSE-KMS?

SSE-S3 uses AES-256 keys AWS manages entirely, is free and has been the default for new objects since January 2023. SSE-KMS uses a KMS key you can audit, rotate and gate with its own key policy, so a reader needs both S3 permissions and kms:Decrypt — the catch is that every PUT and GET makes a KMS API call, which costs money and consumes KMS request quota, so a high-traffic bucket can throttle; S3 Bucket Keys cut that traffic by up to 99%. SSE-C means you supply the key on every request and S3 never stores it — maximum control, and total data loss if you lose the key.

Intermediate Is S3 eventually consistent?

Not since December 2020. S3 provides strong read-after-write consistency for all GET, PUT and LIST operations, including overwrites and deletes, at no extra cost and with no performance penalty. Before that, new-object PUTs were read-after-write consistent but overwrites and deletes were eventually consistent, which is why older data pipelines carried retry loops and external metadata layers. The remaining caveat is that bucket-level configuration changes such as policies and ACLs are still eventually consistent.

Intermediate How do you serve a static Angular or React build to users worldwide, securely?

Put the build in a private bucket with Block Public Access on, and front it with CloudFront using Origin Access Control so only CloudFront can read the bucket. That gives HTTPS on a custom domain via ACM, edge caching and compression, HTTP/2 and HTTP/3, WAF, and access logs. S3 static website hosting on its own is HTTP-only, needs a public bucket, and serves from one region — fine for an internal demo, wrong for production. Use the bucket's REST endpoint as the CloudFront origin with OAC, and handle SPA route rewrites with a CloudFront Function.

Pro S3 gives eleven nines of durability, so why do you still need backups?

Because durability only covers hardware and media failure. A delete issued by a buggy deploy, an overwrite with corrupt data, ransomware holding valid credentials, or a compromised account all replicate perfectly across the three Availability Zones at machine speed — the storage layer is doing exactly its job. Real protection is versioning with lifecycle-managed noncurrent versions, MFA delete or Object Lock in compliance mode on the buckets that matter, and replication into a separate AWS account so that compromising one account cannot reach the copy.

Pro Design the storage and lifecycle policy for an application that writes 500 GB of transaction logs a day, queried heavily for a week, occasionally for a quarter, and retained seven years for audit.

Write to S3 Standard, partitioned by date prefix. Lifecycle: transition to Standard-IA at 30 days, Glacier Flexible Retrieval at 90, Deep Archive at 365, expire at 2555 days. Add an object-size filter so files below about 128 KB are not transitioned — the per-object transition request would cost more than the storage saved — and compact small log files into larger objects before they land. Enable versioning with NoncurrentVersionExpiration plus an abort rule for incomplete multipart uploads, turn on default SSE-KMS with a Bucket Key, and add Object Lock in compliance mode if the seven years is a regulatory requirement. Validate the plan against Storage Class Analysis before rolling it out, and remember the audit restore from Deep Archive takes hours, so document the retrieval runbook.

Pro Your bucket has Block Public Access enabled but a bucket policy granting s3:GetObject to Principal: "*". What happens, and why is that the right design?

The requests are denied. Block Public Access is evaluated as an account and bucket-level guardrail ahead of the policy, so a policy granting public access is simply ignored. That is deliberate defence in depth: policy edits happen constantly under deadline pressure, while the guardrail is a separate, rarely-touched control that an over-broad policy cannot defeat. Set it at the account level so it also covers buckets created later by automation, and when you genuinely need public delivery use CloudFront with OAC rather than turning the guardrail off.

Pro An S3-triggered Lambda writes its output back to the same bucket and the bill explodes. Diagnose it, and say how you would redesign the pipeline.

The Lambda's own write raises another ObjectCreated event that re-invokes it — an infinite recursion billed per invocation and per request. Immediate fix: write output to a different bucket, or filter the notification by a prefix or suffix the output cannot match. Redesign: put SQS between S3 and the worker so bursts are absorbed and you own the retry and dead-letter behaviour, make the consumer idempotent because S3 notifications are neither ordered nor guaranteed exactly once, and move to EventBridge if you need several consumers, cross-account routing, richer filtering or replay. AWS also has a recursive-invocation detector that will trip on this pattern.

Pro You enable cross-region replication on a bucket holding 40 TB and nothing appears in the destination. What is wrong?

Replication only applies to objects written after the rule was created — it does not backfill. Existing data needs S3 Batch Replication. While you are there, check the other usual causes: versioning must be enabled on both source and destination, the replication IAM role needs read on the source and replicate permissions on the destination, objects encrypted with SSE-KMS need the rule configured to replicate them and the role needs access to both keys, and delete markers replicate only if you opt in (version-specific deletes never replicate, by design, so a targeted delete cannot propagate to your DR copy).
