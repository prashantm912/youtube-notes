Module: EC2 and Compute

EC2 is the oldest service AWS still sells and the one everything else is built on. Containers, serverless and managed databases are all abstractions over a virtual machine on a hypervisor — learn the machine and the abstractions stop being magic.

Knowledge Library → Courses → Cloud AWS track → EC2 and Compute

What this module covers

Elastic Compute Cloud rents you a virtual machine by the second: you choose a hardware profile, a disk image, a network position and a payment model, and a few seconds later something boots. Every one of those four choices has a cost consequence and a failure mode, and this module walks all four — instance families and sizing, AMIs and bootstrapping, EBS and instance store, and the security-group firewall that decides who can reach the thing.

The second half is about money, because EC2 is where cloud bills are won and lost. On-demand, reserved instances, savings plans, spot and dedicated hosts are not five names for the same product — they are five different bets about how confident you are in your future usage. The module closes on right-sizing, which is the unglamorous truth that most overspend is not a clever architecture problem but an m5.2xlarge somebody launched for a load test in 2023 and never revisited.

Topics

Instance families and what the instance name actually encodes

An instance type name such as m7g.2xlarge is four pieces of information, not a product code. The first letter is the family — t burstable, m general purpose (a balanced ratio of roughly 4 GiB of memory per vCPU), c compute-optimized (about 2 GiB per vCPU, for CPU-bound work), r memory-optimized (about 8 GiB per vCPU, for caches, in-memory analytics and hungry JVMs), plus g/p for GPU, i and d for storage-dense, and x/u for extreme memory. The digit is the generation, and newer generations are almost always both faster and cheaper per unit of work, so an m5 still running in production is usually money left on the table.

After the digit come additional-capability letters that trip people up in interviews: g means AWS Graviton (ARM), a means AMD EPYC, i means Intel, d means local NVMe instance storage attached, n means extra network bandwidth, e extra storage or memory, and flex marks the newer discounted general-purpose variants. Finally the size — large, xlarge, 2xlarge and upward — scales vCPU, memory and network and EBS bandwidth roughly linearly, which is why an undersized instance often shows up as a network or disk bottleneck rather than a CPU one. Sizing therefore means picking the family from the memory-to-CPU shape of your workload first, then the size from the resource you actually run out of.

Burstable T instances and the CPU credit story behind "it mysteriously got slow"

T-family instances (t3, t3a, t4g) are cheap because they do not give you a whole CPU. They give you a baseline percentage of a vCPU — 20% for a t3.medium, 40% for a t3.xlarge and so on — and while you run below that baseline you accrue CPU credits. When you burst above it you spend credits, one credit buying one vCPU-minute at full speed. Credits accrue at a fixed hourly rate, cap out after 24 hours' worth, and are lost when the instance stops.

This is the mechanism behind the single most common "the server was fine for three weeks and then got slow" incident on AWS. In standard mode, once the credit balance hits zero, the instance is throttled hard to its baseline and stays there — CPU utilisation flatlines at 20% while the application crawls, and nothing in the application logs explains it. The tell is the CPUCreditBalance CloudWatch metric going to zero. Fixes, in order of preference: move to a non-burstable m or c instance if the load is genuinely sustained; or enable unlimited mode, which lets the instance burst past a zero balance and bills the surplus as a surcharge — convenient, but a silent burstable instance running permanently in unlimited mode can quietly cost more than the fixed-price instance you should have bought. T instances are right for genuinely spiky, mostly idle workloads: dev boxes, low-traffic internal tools, bastion hosts. They are wrong for anything with a steady CPU floor.

Graviton: ARM is now the default answer, not the adventurous one

Graviton is AWS's own ARM-based silicon, and the g suffix (m7g, c8g, r8g, t4g) marks the instances that run it. AWS quotes roughly 20% lower price for comparable specifications and a further performance uplift on top, which is why Graviton has moved from "worth an experiment" to "the type you should reach for first, and justify not using". For managed runtimes the migration is close to free: JVM, Python, Node.js, Go, .NET and PHP workloads mostly need a rebuild and a redeploy, and ClickHouse publicly reported a 25% end-user performance improvement moving its cloud service across.

The friction is entirely in the parts of your stack that are not portable: native libraries compiled for x86, container base images built for a single architecture, JNI dependencies, commercial agents that ship x86-only binaries, and CI runners that can only build one architecture. The practical route is to build multi-architecture container images, run one Graviton node alongside your x86 nodes, and compare latency and cost with real traffic before committing. Compute Optimizer will even tell you which of your existing workloads look safe to move.

AMIs: what is in the image, and whether to bake it or configure at boot

An Amazon Machine Image is the template an instance boots from: a root volume snapshot (operating system, packages, your application if you put it there), launch permissions saying who may use it, and a block device mapping describing the volumes to attach. AMIs are regional — an image built in ap-south-1 must be copied before it can launch in us-east-1 — and they are versioned by you, not by AWS, so treat the AMI id as a build artefact and record which one is running.

The real decision is bake versus bootstrap. A baked AMI has everything pre-installed, so instances boot in seconds, launch identically every time, and do not depend on a package repository being up during a scaling event at three in the morning — but you now own an image pipeline and a patching cadence. Bootstrapping configures a stock AMI at boot with user data or a configuration-management agent: nothing to build, but slower launches and a real risk that today's apt-get install pulls a different version than last week's. The mature answer is usually a golden AMI built by EC2 Image Builder or Packer on a schedule, carrying the OS, agents and runtime, with only environment-specific configuration applied at boot. When you must choose only one for an auto-scaling group, bake — scaling out is exactly when you cannot afford a five-minute boot or a flaky download.

User data: bootstrap scripts and the caveat everybody hits once

User data is a blob you attach at launch that cloud-init executes on the instance the first time it boots — a shell script beginning #!/bin/bash, or a cloud-config YAML document. It is the standard way to install an agent, pull a configuration file, register with a service discovery system or start your application, and it is what makes an auto-scaling group's launch template self-sufficient. It runs as root, with no terminal attached, and its output lands in the cloud-init logs on the instance rather than anywhere you can see from the console.

Two caveats do most of the damage. First, by default user data runs only on the first boot — reboot or stop-start the instance and your script does not run again, so anything you assumed it would repair on restart quietly stops being repaired. Write it as though it will run exactly once, and use a systemd unit or a configuration-management agent for anything that must hold true on every boot. (You can force re-execution per boot with the cloud-init scripts-user directive, but that then demands the script be genuinely idempotent — creating users, appending to files and cloning repositories all misbehave on a second run.) Second, user data is not a secret store: it is readable by anything on the instance through the metadata service, and by anyone with ec2:DescribeInstanceAttribute in the account. Put a Secrets Manager or Parameter Store reference in user data and let the instance's IAM role fetch the actual value.

#!/bin/bash
set -euxo pipefail
dnf install -y nginx amazon-cloudwatch-agent
# no secrets here - fetch them with the instance role instead
DB_PASS=$(aws secretsmanager get-secret-value --secret-id prod/app/db --query SecretString --output text)
systemctl enable --now nginx        # survives reboots; user data itself does not re-run

Getting in: key pairs, SSH, and why Session Manager is the better answer

A key pair is an asymmetric pair where AWS keeps the public half and hands you the private half exactly once. At launch the public key is written into ~/.ssh/authorized_keys for the default user, and you SSH in with the .pem file you downloaded. If you lose it, AWS cannot recover it — you detach the root volume, attach it to another instance, and edit the authorized keys file by hand. Key pairs are also a rotation problem: one file shared across a team, copied onto laptops, with no audit trail of who used it and no way to revoke one person's access without re-keying every instance.

Systems Manager Session Manager is the modern answer and it is strictly better on every axis that matters. The SSM Agent on the instance makes an outbound connection to the Systems Manager service, so the instance needs no inbound port 22 rule, no public IP address, and no bastion host — a private-subnet instance is reachable through a VPC endpoint with the security group's inbound rules completely empty. Access is granted by IAM policy rather than by possession of a file, so it is revocable per person in seconds, and every session can be logged to CloudWatch Logs or S3 with the full keystroke record. Port forwarding and SCP-equivalent transfers work through it too. The requirements are modest: the agent installed (it is preinstalled on Amazon Linux and recent Ubuntu images) and an instance profile granting AmazonSSMManagedInstanceCore. EC2 Instance Connect is a useful middle ground for browser-based SSH that pushes a one-time key valid for sixty seconds, but Session Manager is the one to name in an interview when asked how to reach a private instance without a bastion.

The instance metadata service and why IMDSv2 is non-negotiable

Every instance can query a link-local address, 169.254.169.254, to learn about itself: instance id, instance type, availability zone, attached network interfaces, the user data it was launched with — and, critically, the temporary credentials of its instance profile role. This is the mechanism behind module 02's instance profiles: the AWS SDKs walk a credential chain that ends at this endpoint, which is why code on an EC2 instance needs no access keys on disk.

That convenience is also the attack surface. Under IMDSv1 a plain HTTP GET returned credentials, so any server-side request forgery bug — an image-resize endpoint that fetches a user-supplied URL, a misconfigured reverse proxy, an open web application firewall — could be pointed at the metadata address and walk away with the instance's role credentials. IMDSv2 closes it with session orientation: you first send a PUT to obtain a token, then present that token as a header on every request. SSRF flaws typically cannot issue a PUT or set arbitrary headers, the token response carries an IP time-to-live of 1 so it cannot be routed off the instance, and the service refuses to issue tokens to callers carrying an X-Forwarded-For header, which shuts down the open-proxy case. IMDSv2 is now the default on new instances, but the setting you actually want is HttpTokens=required, which disables v1 outright — enforce it in your launch templates, and pair it with a hop limit of 1 so a container on the host cannot reach it. Combine that with a narrowly scoped instance role and the blast radius of an SSRF bug drops from "account compromise" to "an error in a log".

# IMDSv2: obtain a session token first, then use it as a header
TOKEN=$(curl -sX PUT "http://169.254.169.254/latest/api/token" \
        -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
     http://169.254.169.254/latest/meta-data/instance-id

# enforce it at launch - v1 refused entirely, and no extra network hop
aws ec2 modify-instance-metadata-options --instance-id i-0abc \
    --http-tokens required --http-put-response-hop-limit 1

EBS volume types: gp3 as the sensible default, and why it beats gp2

Elastic Block Store is network-attached block storage that behaves like a disk: one volume attaches to one instance in one availability zone (multi-attach exists for io1/io2 but is a specialist tool), survives instance termination if you ask it to, and can be resized and even re-typed while running through Elastic Volumes. The type you pick determines both performance and a surprisingly large share of your storage bill.

gp3 is the default you should reach for. It ships 3,000 IOPS and 125 MiB/s baseline at every size and lets you provision more IOPS and throughput independently of capacity, at roughly 20% lower cost per GiB than gp2. That independence is the whole story: with gp2, performance was welded to size at 3 IOPS per GiB, so the only way to get 6,000 IOPS was to buy a 2 TiB volume you did not need — the classic "provision for performance, pay for capacity" tax. Migrating gp2 to gp3 is an online volume modification and is close to free money. Above gp3's ceiling, io2 (and io2 Block Express) offers provisioned IOPS with far higher durability for demanding single-instance databases; io1 is its older sibling. For sequential, throughput-hungry, cost-sensitive work — log processing, data warehouse scans, big-data nodes — the HDD types st1 and sc1 are far cheaper per GiB but are throughput-optimised and terrible at small random reads, so never put a transactional database or a boot volume on them.

Snapshots, encryption, and instance store as the disk that dies with the instance

EBS snapshots are incremental, block-level backups stored in S3 behind the scenes: the first snapshot copies every used block, each later one copies only changed blocks, and deleting an intermediate snapshot never breaks the ones after it because AWS re-points the references. A volume restored from a snapshot is available immediately and lazily hydrates its blocks in the background, which is why the first read of a cold restored volume feels slow — Fast Snapshot Restore exists to remove that penalty when it matters. Snapshots are also how you move a volume across availability zones and regions, and Data Lifecycle Manager schedules and expires them so nobody has to remember.

Encryption at rest is a KMS-backed, per-volume flag, and the honest advice is to turn on account-level default encryption in every region and stop thinking about it: encryption covers the volume, its snapshots, and volumes restored from those snapshots, with negligible performance impact. Note the asymmetry that trips people up — you cannot encrypt an existing unencrypted volume in place; you snapshot it, copy the snapshot with encryption enabled, and restore. Finally, instance store is a completely different animal: physically attached NVMe on the host, the fastest storage EC2 offers, included in the price of d-suffixed instance types — and ephemeral. Stop the instance or lose the host and the data is gone, permanently, with no snapshot facility at all. Use it for scratch space, local caches, temporary shuffle data and replicated cluster nodes that can rebuild from peers. Never use it as the only copy of anything you would miss.

Security groups: stateful, allow-only firewalls attached to the interface

A security group is a virtual firewall attached to an elastic network interface, not to a subnet — two instances in the same subnet can have completely different exposure. Two properties define its behaviour and both are standard interview material. First, allow rules only: there is no such thing as a deny rule in a security group. Everything not explicitly allowed is denied, and when an interface carries several security groups the effective permission is the union of all their allow rules, so adding a group can only ever widen access. Second, stateful: if an inbound request is allowed, the response is automatically allowed out regardless of outbound rules, and vice versa. You therefore never write rules for ephemeral return ports — a fact that becomes conspicuous the first time you configure a network ACL, which is stateless and does need them (module 05 covers NACLs in full).

The idiom that separates production configurations from tutorials is referencing security groups instead of CIDR blocks. Allow the web tier's security group as the source on the application tier's port 8080 rule, and the application tier's group as the source on the database's port 5432 rule. The rule then follows instances as they are replaced by an auto-scaling group, needs no IP bookkeeping, and documents the intended call graph in the configuration itself. Reserve CIDR sources for genuine external ranges such as an office VPN. Two more habits worth carrying: the default outbound rule allows all egress, and locking it down is a real (if less common) control against exfiltration and against a compromised host phoning home; and 0.0.0.0/0 on port 22 or 3389 is the single most frequently flagged finding in any AWS security review — with Session Manager available there is rarely a defensible reason for it.

Paying for compute: on-demand, reserved instances and savings plans

On-demand is the list price, billed per second with no commitment. It is the correct choice for genuinely unpredictable load, for anything short-lived, and for the first few months of a new workload while you find out what its baseline actually is — the mistake is not using on-demand, it is still being on 100% on-demand two years later.

Once a steady baseline exists, you buy it cheaper by committing. Reserved instances commit you to a specific instance family, region and term (one or three years, with no-upfront, partial-upfront or all-upfront payment) for up to around 72% off; standard RIs are cheapest and least flexible, convertible RIs cost more and let you exchange for a different family. Savings plans are the newer and now-preferred mechanism: instead of reserving instances you commit to a dollar amount of compute spend per hour, and AWS applies the discount automatically to whatever matches. Compute savings plans are the flexible tier — any region, any instance family, and they cover Fargate and Lambda too — at up to roughly 66%; EC2 Instance savings plans lock you to one family in one region for a deeper discount closer to RI rates. The commitment is the whole tradeoff: it is a bet, you pay for the committed amount whether or not you use it, and a three-year all-upfront commitment on a workload you are about to containerise is a genuinely expensive mistake. The pragmatic pattern most teams land on is to commit to a conservative fraction of the observed floor — say 60 to 70% of steady-state usage — on one-year terms, and let on-demand absorb the peaks and the uncertainty.

Spot instances and dedicated hosts: the two ends of the spectrum

Spot sells you AWS's spare capacity at up to about 90% off on-demand, with one condition: AWS can take it back. When capacity is needed elsewhere your instance receives an interruption notice through the metadata service and an EventBridge event, and two minutes later it is stopped, hibernated or terminated according to the behaviour you configured. Two minutes is enough to drain a load balancer target, checkpoint a job, finish the in-flight request and hand work back to a queue — but only if you wrote that handler. Spot is therefore excellent for batch processing, CI runners, data pipelines, rendering, machine-learning training with checkpoints and stateless web tiers behind a load balancer, and unsuitable for stateful singletons, long non-restartable jobs and anything where a two-minute eviction means data loss.

The single most important spot practice is diversification. Capacity is allocated per pool, where a pool is one instance type in one availability zone, so a fleet that will only accept c5.2xlarge in one zone is fragile by construction. Accept a dozen compatible types across every zone, use attribute-based instance type selection to express requirements rather than names, and choose the price-capacity-optimized allocation strategy so EC2 draws from the pools least likely to be reclaimed. A mixed-instances auto-scaling group with an on-demand base plus a spot percentage on top gives you a guaranteed floor and cheap elasticity above it. At the opposite end of the spectrum sit dedicated hosts: a whole physical server allocated to you, with visibility of sockets and physical cores. The reason is almost always licensing — Oracle, SQL Server, Windows Server and similar per-socket or per-core BYOL agreements that require you to prove which physical hardware they run on — plus the occasional hard compliance requirement for physical isolation. (Dedicated instances are the lighter variant: hardware isolation without the socket-level visibility that licensing audits need.)

Right-sizing, Compute Optimizer, and the oversized instance nobody revisited

Right-sizing is matching instance type and size to measured utilisation, and it is where the money actually is. The typical enterprise AWS bill is not inflated by an exotic architectural error; it is inflated by instances chosen once, by guesswork, under deadline pressure, and never looked at again — averaging under 10% CPU with memory to spare, running twenty-four hours a day for a workload used during Indian business hours. Nobody revisits them because nothing breaks. The pattern to internalise is that buying a savings plan for an oversized fleet locks in the waste for a year: right-size first, commit second.

AWS Compute Optimizer does the analysis for you. It reads CloudWatch history, classifies each instance as under-provisioned, over-provisioned or optimised, and recommends specific alternative types with projected performance risk and estimated savings — including cross-family and Graviton moves you would not have considered. Give it the memory metric from the CloudWatch agent, because without it the recommendations are CPU- and network-blind on exactly the workloads (JVMs, databases, caches) where memory is the binding constraint. Around it, the rest of the discipline is unglamorous and effective: tag everything so cost allocation reports can attribute spend to a team, schedule non-production instances to stop outside working hours (a straight 60 to 70% saving on dev and staging), delete unattached EBS volumes and stale snapshots, set AWS Budgets alerts so a runaway is caught in days rather than at the month-end invoice, and make right-sizing a recurring calendar item rather than a heroic annual cleanup.

Interview questions

EC2 is the most reliably asked AWS topic in Indian service-company and product-company rounds alike — spot versus reserved and security-group statefulness come up almost every time, and the follow-ups sort candidates who have run production from candidates who have watched a course:

Beginner What do the letters and numbers in an instance type like m7g.2xlarge mean?

Family, generation, capability suffix, size. m is general purpose (roughly 4 GiB memory per vCPU); 7 is the generation, newer generally being faster and cheaper per unit of work; g means AWS Graviton (ARM) — a would be AMD, i Intel, d local NVMe, n extra network; 2xlarge is the size, which scales vCPU, memory, network and EBS bandwidth together. Other families: t burstable, c compute-optimized, r memory-optimized, g/p GPU, i/d storage-dense.

Beginner What is an AMI and what does it contain?

An Amazon Machine Image is the template an instance boots from: a snapshot of the root volume (OS, packages, optionally your application), launch permissions controlling who can use it, and a block device mapping describing which volumes to attach at launch. AMIs are region-scoped and must be copied to be used in another region. You can use an AWS-provided or Marketplace AMI, or create your own from a configured instance.

Beginner What is user data, and when does it run?

A script or cloud-config document supplied at launch that cloud-init executes as root on the instance. By default it runs only on the first boot — not on subsequent reboots or stop-starts — so anything that must be true on every boot belongs in a systemd unit rather than in user data. It is also not a secret store: it is readable through the metadata service and via ec2:DescribeInstanceAttribute, so put a Secrets Manager reference there and let the instance role fetch the value.

Beginner Difference between EBS and instance store?

EBS is network-attached, persistent, independently snapshot-able and survives instance stop and termination if configured to; it can be detached and reattached, and resized while running. Instance store is physically attached NVMe on the host — much faster and included in the instance price, but ephemeral: stopping the instance or losing the host destroys the data, and there is no snapshot facility. Use instance store for scratch, cache and shuffle data; use EBS for anything you need to keep.

Beginner Why choose gp3 over gp2?

gp3 gives 3,000 IOPS and 125 MiB/s baseline at any volume size and lets you provision IOPS and throughput independently of capacity, at around 20% lower cost per GiB. gp2 tied performance to size at 3 IOPS per GiB, so the only way to get more IOPS was to over-provision capacity you did not need. Migrating is an online volume modification with no detach or reboot, which makes it one of the easiest cost wins available.

Intermediate Security groups are stateful — what does that mean in practice, and how do they differ from NACLs?

Stateful means the return traffic for an allowed connection is permitted automatically: allow inbound on port 443 and the response goes back out without any matching outbound rule, and vice versa. So you never write ephemeral-port rules. Security groups also support allow rules only — everything else is implicitly denied — and attach to an elastic network interface, with multiple groups combining as a union. NACLs are the opposite on all three counts: stateless (you must allow both directions explicitly, including the ephemeral return range), they support both allow and deny rules, and they attach to a subnet and are evaluated in rule-number order.

Intermediate Your t3.medium ran fine for weeks and then became very slow with no code change. Diagnose it.

Almost certainly CPU credit exhaustion. T instances get a baseline share of a vCPU (20% for a t3.medium) and accrue credits while below it; sustained load above baseline drains the balance and, in standard mode, throttles the instance to baseline indefinitely. Check the CPUCreditBalance CloudWatch metric — a slow decline to zero confirms it. Fix by moving to a non-burstable m or c instance if the load is genuinely sustained, or switch to unlimited mode and accept the surcharge, watching that the surcharge does not exceed the fixed-price instance you should have bought.

Intermediate Compare on-demand, reserved instances, savings plans and spot. When do you use each?

On-demand: list price, no commitment, per-second billing — unpredictable or short-lived workloads and new services whose baseline you do not yet know. Reserved instances: one- or three-year commitment to a specific family and region for up to about 72% off; standard is cheapest, convertible allows exchange. Savings plans: commit to a dollar-per-hour of compute spend instead of specific instances — Compute savings plans are region- and family-flexible and cover Fargate and Lambda at up to about 66%, EC2 Instance savings plans lock to one family for a deeper discount. Spot: spare capacity at up to about 90% off, reclaimable with a two-minute notice — batch, CI, rendering, stateless fleets. Typical production mix: savings plans for the steady baseline, on-demand for the variable middle, spot for interruptible bulk.

Intermediate How do you reach an instance in a private subnet without a bastion host?

Systems Manager Session Manager. The SSM Agent makes an outbound connection to the Systems Manager service (over a NAT gateway or, better, VPC interface endpoints), so the instance needs no public IP, no inbound port 22 rule and no bastion at all. Requirements are the agent plus an instance profile with AmazonSSMManagedInstanceCore. It is also better operationally: access is granted by IAM policy so it is revocable per person, and sessions can be logged to CloudWatch Logs or S3 for audit. It supports port forwarding for database tunnels too.

Intermediate What is IMDSv2 and what attack does it prevent?

Version 2 of the instance metadata service, which is session-oriented: you send a PUT to get a token and then pass that token as a header on each request. It defends against server-side request forgery. Under v1 a plain GET to 169.254.169.254 returned the instance role's temporary credentials, so any SSRF bug, open reverse proxy or misconfigured WAF could exfiltrate them. Most SSRF flaws cannot issue a PUT or set arbitrary headers; additionally the token response has an IP time-to-live of 1 so it cannot leave the instance, and the service refuses tokens to callers sending X-Forwarded-For. Enforce HttpTokens=required in launch templates and set the hop limit to 1.

Intermediate A colleague says "we should just bake everything into AMIs". When is bootstrapping with user data the better answer?

Bootstrapping wins when the thing being configured is environment-specific or changes faster than you want to rebuild images: config files, secrets fetched at boot, service registration, per-environment endpoints. Baking wins on launch speed and determinism, which matters most for auto-scaling groups — you do not want a scale-out event depending on a package mirror at three in the morning. The usual production answer is both: a golden AMI built by Image Builder or Packer with the OS, agents and runtime, plus a small user data script for environment configuration only.

Pro Design a cost-optimised architecture for a workload with a steady baseline and a large nightly batch job.

Split the workload by predictability. Cover the steady baseline with a Compute savings plan sized to roughly 60 to 70% of the observed floor on a one-year term — conservative enough to survive a migration, flexible enough to follow you to Fargate. Let on-demand absorb the daytime variability above that. Run the nightly batch entirely on spot in a mixed-instances auto-scaling group or AWS Batch, diversified across at least a dozen instance types and every availability zone with the price-capacity-optimized allocation strategy, with checkpointing so a two-minute interruption costs minutes rather than the whole run. Right-size before committing, prefer Graviton throughout, and schedule dev and staging to stop overnight.

Pro Your spot fleet keeps getting interrupted and cannot maintain capacity. What is wrong and how do you fix it?

Almost always insufficient diversification. Spot capacity is allocated per pool — one instance type in one availability zone — so a fleet restricted to a single type in a single zone competes for one shrinking pool. Fix it by accepting many compatible instance types across all zones (or using attribute-based instance type selection to express vCPU and memory requirements rather than names), switching the allocation strategy to price-capacity-optimized, and running a mixed-instances group with an on-demand base so there is a guaranteed floor. Then handle the interruption notice properly: catch the EventBridge event or poll the metadata endpoint, deregister from the target group, checkpoint, and requeue in-flight work. Also verify you are not bidding on a maximum price below the current spot price.

Pro How would you build EC2 access with no long-lived credentials and no open SSH port, and how do you audit it?

No key pair at all on launch. Attach an instance profile with AmazonSSMManagedInstanceCore and reach instances through Session Manager over VPC interface endpoints, so nothing traverses the internet and the security group has zero inbound rules. Applications get AWS permissions from the instance role via IMDSv2 with HttpTokens=required and a hop limit of 1; application secrets come from Secrets Manager or Parameter Store at runtime, never from user data or disk. Auditing: session logs to CloudWatch Logs or S3 with keystroke logging, CloudTrail for every StartSession and every API call the role makes, IAM Access Analyzer and Config rules to catch drift such as an instance with IMDSv1 enabled or a group with 0.0.0.0/0 on port 22.

Pro Your monthly EC2 bill grew 40% with no new features shipped. How do you investigate?

Start with Cost Explorer grouped by usage type, then by instance type, then by tag, to locate where the growth sits — new instances, a family change, a region, or a discount that expired. Check whether a reserved instance or savings plan term ended and left the fleet on on-demand rates. Then look for the classic leaks: unattached EBS volumes and orphaned snapshots, non-production instances running around the clock, a load test fleet never terminated, and data transfer charges (cross-AZ and NAT gateway traffic often hide inside a compute line item). Feed Compute Optimizer with memory metrics and act on the over-provisioned list. Then prevent recurrence: cost allocation tags enforced by policy, AWS Budgets with anomaly alerts, and right-sizing scheduled as recurring work rather than an annual heroic cleanup.

Pro When is a dedicated host genuinely required, and how does it differ from a dedicated instance?

Almost always licensing. Per-socket, per-core or per-VM BYOL agreements — Oracle, SQL Server, Windows Server, some commercial middleware — require you to demonstrate which physical hardware the software runs on, and a dedicated host gives you exactly that: a whole physical server with visible sockets and physical cores, plus host affinity so an instance restarts on the same box. Some strict compliance regimes also mandate physical isolation. A dedicated instance also runs on single-tenant hardware but exposes no socket or core visibility and offers no affinity control, so it satisfies isolation requirements but not licensing audits. Both cost substantially more than shared tenancy, so neither is a default.
