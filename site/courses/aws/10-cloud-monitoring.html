Module: Monitoring and Cost in the Cloud

Two questions every on-call engineer eventually has to answer about a live AWS account: what is it doing right now, and why does it cost that much. Both are answered with services you already have switched on.

Knowledge Library → Courses → Cloud AWS → Monitoring and Cost in the Cloud

What this module covers

The moment you launch anything on AWS, CloudWatch starts collecting metrics about it — free, with nothing installed. That default telemetry is genuinely useful and also genuinely incomplete, and knowing exactly where the line falls (which metrics exist, at what interval, and which ones require an agent you have to install yourself) is the difference between an account you can operate and one you merely hope is fine. This module walks that line: metrics, logs, alarms and dashboards, then tracing with the AWS Distro for OpenTelemetry, then the cost side, which is an engineering responsibility rather than a finance one.

Scope note: this is the AWS-native view of observability. This course carries a full Observability track elsewhere — Micrometer, Prometheus, Grafana, an OpenTelemetry deep dive, SLIs and error budgets, structured logging strategy — and everything vendor-neutral belongs there. Here we stay on the AWS side: which managed service does what, what it charges for, and what a Spring Boot service running on ECS or EC2 needs to do to show up in it.

Topics

CloudWatch metrics: namespaces, dimensions and the monitoring interval

A CloudWatch metric is a time-ordered series of data points identified by three things: a namespace (a container such as AWS/EC2, AWS/ApplicationELB or your own MyCompany/Orders), a metric name, and a set of dimensions — name/value pairs such as InstanceId=i-0abc or LoadBalancer=app/prod/xyz. Dimensions are part of the metric's identity, not filters applied afterwards: CPUUtilization with InstanceId and CPUUtilization with AutoScalingGroupName are two different metrics that are billed and queried separately. That single fact explains most confusion about why a graph does not show what someone expected.

The second thing to internalise is the interval. Most AWS services publish at basic monitoring resolution — one data point every five minutes, at no charge. Detailed monitoring drops that to one minute and costs money per metric; high-resolution custom metrics can go to one second. Five-minute granularity is fine for a capacity trend and useless for an incident, because an outage that lasts four minutes may never produce a single anomalous data point. Decide the interval per workload, not per account, and remember that alarm evaluation periods can never be finer than the underlying metric.

Statistics and percentiles — and the metrics EC2 does not send you

CloudWatch never stores raw observations for you to aggregate later; it stores a statistic set per period, and you choose how to read it. Average is the default and the most misleading: an average latency of 180 milliseconds tells you nothing about the one request in a hundred that took eight seconds. Prefer p90, p99 and Maximum for latency, Sum for counts such as errors or requests, and SampleCount when you need to know whether the average is based on three data points or three million. Percentile statistics need enough samples to be meaningful, which is another reason detailed monitoring matters on latency-sensitive services.

Now the gotcha that catches almost everybody: an EC2 instance does not report memory usage or disk usage to CloudWatch by default. The hypervisor can see CPU, network and EBS I/O from outside the guest, so those are free. Memory utilisation and filesystem free space live inside the operating system, so nothing outside can observe them — you must install the CloudWatch agent on the instance, give its role the CloudWatchAgentServerPolicy permissions, and configure which counters to publish. Those become custom metrics, so they are billed, and teams routinely discover this at the worst possible moment: during an incident, looking for a memory graph that was never being collected.

// /opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json (excerpt)
{
  "metrics": {
    "namespace": "MyCompany/EC2",
    "append_dimensions": { "InstanceId": "${aws:InstanceId}" },
    "metrics_collected": {
      "mem":  { "measurement": ["mem_used_percent"], "metrics_collection_interval": 60 },
      "disk": { "measurement": ["used_percent"], "resources": ["/"] }
    }
  }
}

Custom metrics and the embedded metric format

Business-level numbers — orders placed, payments declined, queue depth in your own domain terms — are not something AWS can infer, so you publish them. The direct route is the PutMetricData API, but calling it once per event is both slow (a synchronous HTTPS call on your request path) and expensive (custom metrics are priced per metric per month, and every distinct dimension combination is a separate metric). Batch aggressively, keep cardinality low, and never put a user id, request id or full URL in a dimension unless you enjoy surprising bills.

The better pattern on Lambda, ECS and anything already shipping logs is the embedded metric format (EMF): you write a specially structured JSON log line containing both your metric values and arbitrary context, CloudWatch Logs ingests it as an ordinary log event, and CloudWatch extracts the metrics from it asynchronously. You get metrics without a blocking API call, the high-cardinality context stays queryable in Logs Insights rather than exploding your metric count, and the log line and the metric are guaranteed to agree because they are the same record.

{
  "_aws": {
    "Timestamp": 1774000000000,
    "CloudWatchMetrics": [{
      "Namespace": "MyCompany/Orders",
      "Dimensions": [["Service","Region"]],
      "Metrics": [{ "Name": "OrderValue", "Unit": "None" }]
    }]
  },
  "Service": "order-api", "Region": "ap-south-1",
  "OrderValue": 2499,
  "orderId": "ORD-91823", "customerTier": "gold"
}

CloudWatch Logs: log groups, streams, the unified agent and retention

The hierarchy is two levels. A log group is the unit of configuration and usually maps to one application or resource (/aws/lambda/checkout, /ecs/order-api); retention, encryption, subscription filters, metric filters and access policy are all set on the group. A log stream inside it is the sequence of events from one source — one container, one instance, one Lambda execution environment. Getting logs there is either automatic (Lambda, and ECS via the awslogs log driver) or a matter of installing the same unified CloudWatch agent used for metrics and pointing it at your log files.

Then set retention, because this is where AWS quietly bills you forever. A newly created log group's retention is "Never expire" by default. Storage is charged per GB per month indefinitely, ingestion is charged per GB on the way in, and a chatty debug logger in a busy service produces an astonishing amount of both. Choose a deliberate retention per group (two weeks for application debug, a year or more for audit trails), export what you truly need to keep to S3 or the Infrequent Access log class, and turn the volume down at the source rather than paying to store noise nobody will ever read.

Turning logs into signal: metric filters and subscription filters

A metric filter watches a log group for a pattern and increments a CloudWatch metric whenever it matches. This is how a log line becomes something you can alarm on: count occurrences of ERROR, of a specific exception class, of failed logins, of an OutOfMemoryError, and you now have a numeric series that alarms and dashboards understand. Filters apply only to events ingested after the filter is created — they are not retroactive — and the filter pattern syntax has separate forms for plain text and for JSON-structured events, which is one more argument for logging JSON.

A subscription filter is the streaming exit door: matching events are delivered in near real time to Kinesis Data Streams, Firehose, Lambda or OpenSearch. That is the standard route out of CloudWatch Logs to somewhere else — a central security account, a data lake in S3, or a third-party platform such as Datadog, Splunk or Elastic — and it is the answer to the common interview question "how would you centralise logs from fifty AWS accounts?" Metric filter for alarming, subscription filter for forwarding.

Logs Insights: actually finding things

Scrolling a log stream in the console stops working at about the tenth screenful. CloudWatch Logs Insights is the query engine over the same data: a small piped language (fields, filter, parse, stats, sort, limit) that runs across one or many log groups over a chosen time range, with automatically discovered fields for JSON events and parse for unstructured lines. It is the tool you reach for during an incident and the tool that makes JSON logging pay for itself, because filter level = "ERROR" and service = "checkout" only works if those are real fields.

Two operational notes. Queries are billed per GB of log data scanned, so always narrow the time range and the log groups first — an unbounded query over a month of production logs is a real invoice line, not a rounding error. And save the queries your team runs repeatedly (top error signatures, slowest endpoints, one customer's full request trail) so the next person on call does not have to reinvent them at three in the morning.

fields @timestamp, @message, level, service, latencyMs
| filter level = "ERROR" and service = "order-api"
| parse @message /orderId=(?<orderId>[A-Z0-9-]+)/
| stats count() as errors, avg(latencyMs) as avgLatency by bin(5m), orderId
| sort errors desc
| limit 20

Alarms: thresholds, evaluation, missing data and noise control

An alarm watches one metric (or one metric-math expression) against a threshold and holds one of three states: OK, ALARM, and INSUFFICIENT_DATA — the third meaning the metric has not reported enough points to judge. Two settings decide how twitchy it is: the evaluation periods (how many periods to look back over) and datapoints to alarm (how many of those must breach). "3 out of 5 periods" is the classic M-of-N configuration that ignores a single spike but catches a sustained problem, and it is a far better answer in an interview than raising the threshold until the pager stops.

Missing data is its own decision, and the default missing treatment means gaps neither cause nor clear an alarm. Choose notBreaching for a metric that is legitimately absent when idle (a queue with no messages), and breaching when absence itself is the emergency (a heartbeat that stopped because the process died). For noise, composite alarms combine child alarms with AND/OR/NOT so that one root cause pages once instead of forty times; anomaly detection builds a model of a metric's normal band and alarms on deviation from it, which is what you want for a strongly seasonal metric where no fixed threshold is right at both 3am and 3pm. Alarm actions publish to SNS (email, chat, PagerDuty, Lambda), trigger Auto Scaling policies, or stop and recover EC2 instances.

resource "aws_cloudwatch_metric_alarm" "api_5xx" {
  alarm_name          = "order-api-5xx-sustained"
  namespace           = "AWS/ApplicationELB"
  metric_name         = "HTTPCode_Target_5XX_Count"
  dimensions          = { LoadBalancer = aws_lb.app.arn_suffix }
  statistic           = "Sum"
  period              = 60
  evaluation_periods  = 5     # look back over five periods
  datapoints_to_alarm = 3     # alarm only if three of them breach
  threshold           = 10
  comparison_operator = "GreaterThanThreshold"
  treat_missing_data  = "notBreaching"
  alarm_actions       = [aws_sns_topic.oncall.arn]
}

Dashboards and widgets

A dashboard is a saved arrangement of widgets — line and stacked-area graphs, single-value numbers, gauges, alarm-status panels, log tables driven by a Logs Insights query, and free text for runbook links. Dashboards are global rather than regional, can pull metrics from several regions and (with the right roles) several accounts, and are defined by a JSON document, which means you should create them in CloudFormation or Terraform alongside the infrastructure they watch rather than clicking them together and losing them.

Keep them purposeful. One service dashboard that answers "is this healthy?" in ten seconds — request rate, error rate, latency percentiles, saturation, and the alarms that matter — beats a wall of forty graphs nobody reads. The first three of those are the classic RED metrics, and putting them in the same order on every service's dashboard makes an unfamiliar service legible to whoever is on call. Note that the first few dashboards are free and additional ones are billed per dashboard per month.

Tracing on AWS: teach ADOT, not the X-Ray SDK

Be explicit about this, because a lot of older material is misleading: the AWS X-Ray SDKs and the X-Ray daemon are on an end-of-support timeline, and OpenTelemetry is the instrumentation standard AWS itself now points you at. AWS has published a maintenance-mode and end-of-support schedule for the X-Ray SDKs and daemon plus explicit migration guides. X-Ray is not going away — it remains the backend and the console — but the code in your service should emit OpenTelemetry, not X-Ray-specific calls.

The vehicle is the AWS Distro for OpenTelemetry (ADOT): AWS's supported, security-patched build of the upstream OpenTelemetry components, with AWS-specific bits (X-Ray trace-id propagation, resource detectors for EC2/ECS/EKS/Lambda, an X-Ray exporter and a CloudWatch EMF exporter) already included. The payoff is vendor neutrality: the same instrumentation in your Java code can export to X-Ray today and to Grafana Tempo, Jaeger, Datadog or Honeycomb tomorrow by changing collector configuration rather than application code. That is why the OpenTelemetry deep dive lives in its own track — here the point is simply which distribution AWS supports and why it is the default choice.

Instrumenting a Java service: the ADOT agent, the collector, and exporters

For a Spring Boot service the fastest honest answer is zero-code instrumentation: download the ADOT Java auto-instrumentation agent JAR, attach it with -javaagent, and it will byte-code-instrument the frameworks it recognises — Spring MVC and WebFlux, servlet containers, JDBC, the AWS SDK, Apache HttpClient, Kafka clients — producing spans for inbound requests and outbound calls with no source changes. Add manual spans later, only where a business operation needs its own boundary; auto-instrumentation gets you most of a trace on day one.

The agent does not talk to X-Ray directly. It exports OTLP to a collector — the ADOT Collector, run as a sidecar container in your ECS task, a DaemonSet on EKS, or a service on EC2 — and the collector does the batching, sampling, resource enrichment and fan-out to backends. That indirection is the whole architectural point: your application knows only OTLP, and the choice of destination (the X-Ray exporter, the CloudWatch EMF exporter, or an OTLP endpoint at a third party) is collector configuration. Give the task or instance role permission for xray:PutTraceSegments and xray:PutTelemetryRecords, and remember that sampling is a cost control as well as a performance one — full-fidelity tracing of every request in a high-traffic service is rarely worth what it charges.

# Zero-code instrumentation of a Spring Boot service with the ADOT Java agent
java -javaagent:/opt/aws-opentelemetry-agent.jar \
     -Dotel.service.name=order-api \
     -Dotel.exporter.otlp.endpoint=http://localhost:4317 \
     -Dotel.propagators=tracecontext,baggage,xray \
     -Dotel.traces.sampler=parentbased_traceidratio \
     -Dotel.traces.sampler.arg=0.1 \
     -jar order-api.jar

Application Signals, SLOs, and the X-Ray service map

CloudWatch Application Signals is the layer above raw traces: once a service is instrumented with OpenTelemetry it automatically derives the application-level golden signals — request volume, availability (error rate), latency percentiles, and fault versus error breakdown — per service and per operation, with no dashboards to build. It also discovers dependencies, so you see which downstream service or database is dragging an endpoint down without correlating anything by hand.

On top of that it lets you declare service level objectives against those signals: "99.5% of POST /orders requests succeed in under 400 milliseconds over a rolling 28 days", with the remaining error budget tracked and burn visible. That is the AWS-native way to state a reliability target; the general theory of SLIs, SLOs and error budgets is covered properly in the Observability track. The X-Ray trace map (formerly the service map) remains the visualisation for an individual request path — nodes for each service, edges annotated with latency and error rate, and a click through to the actual traces behind any node, which is how you answer "where did those eight seconds go?" in one screen.

Cost as an engineering responsibility: Cost Explorer, Budgets and Anomaly Detection

Cost is a non-functional requirement like latency, and the tools live in the same console you already use. Cost Explorer is the analysis surface: daily or monthly spend broken down by service, account, region, usage type, instance type or tag, with filters and up to twelve months of history plus a forecast. It is where you answer "what changed?" after a bill jumps, and the single most useful first move is grouping by usage type rather than by service — "EC2" tells you nothing, NatGateway-Bytes or DataTransfer-Regional-Bytes tells you everything.

AWS Budgets is the guardrail: define a monthly cost or usage budget, per account or per tag or per service, and get alerted at thresholds of both actual and forecast spend — forecast alerts are the ones that reach you while there is still time to act. Cost Anomaly Detection is the machine-learning complement that needs no threshold at all; it learns each service's normal spend pattern and raises an alert when something deviates, which is how you catch a runaway Lambda loop or a forgotten load test on day two instead of at the end of the month. Every team account should have at least one budget and anomaly monitor from the day it is opened.

Cost allocation tags, the CUR, and the line items that surprise teams

An untagged account cannot answer "which team spent this", and no tool can rescue it after the fact. Cost allocation tags are ordinary resource tags that you explicitly activate in the billing console, after which they become grouping dimensions in Cost Explorer and columns in the billing data. Agree a small mandatory set early — owner, environment, application, cost-centre — enforce them with tag policies or a Service Control Policy and with your Terraform or CloudFormation defaults, and accept that activation is not retroactive: costs incurred before a tag existed stay unattributed forever. Below that sits the Cost and Usage Report, the most granular billing data AWS produces (hourly, per resource, per line item), delivered to S3 for querying in Athena or QuickSight when Cost Explorer's granularity runs out.

Finally, the line items that repeatedly ambush teams, because none of them are the compute you were thinking about. NAT gateway data processing is charged per GB on top of the hourly rate, so private-subnet traffic to S3 or ECR through a NAT gateway can cost more than the instances — VPC endpoints exist precisely to bypass this. Cross-AZ traffic is charged in both directions, so a chatty service talking to a database in another availability zone pays per gigabyte for the privilege. CloudWatch Logs ingestion and never-expiring retention is the observability bill nobody budgeted for. And idle resources bill happily forever: load balancers with no targets, unattached EBS volumes, unassociated Elastic IPs, old snapshots and stopped instances still holding storage. Sweeping those four categories is the highest-return afternoon of work available in most AWS accounts.

Interview questions

Monitoring and cost questions are a staple of Indian product and service-company rounds — service companies probe operational awareness and billing discipline, product companies push on tracing and alarm design:

Beginner What is CloudWatch, and what does it collect without any setup?

The AWS-native monitoring and observability service. With nothing installed it collects metrics that AWS can see from outside your resources — EC2 CPU, network and EBS I/O; ALB request counts, target response time and HTTP status codes; RDS connections and read/write latency; Lambda invocations, errors, duration and throttles — plus logs from services that ship them automatically, such as Lambda and ECS with the awslogs driver.

Beginner Why is memory utilisation not available for an EC2 instance by default?

Because CloudWatch collects EC2 metrics from the hypervisor, outside the guest operating system. CPU, network and disk I/O are visible from there; memory usage and filesystem free space are internal OS state that nothing outside can observe. You install the CloudWatch agent inside the instance, grant its role CloudWatchAgentServerPolicy, and configure which counters to publish — they arrive as custom metrics, which are billed.

Beginner Explain namespace and dimension with an example.

A namespace is a container for metrics — AWS/EC2, AWS/Lambda, or your own MyCompany/Orders. Dimensions are name/value pairs that identify a specific series inside it, such as InstanceId=i-0abc or FunctionName=checkout. Dimensions are part of the metric's identity, so the same metric name with different dimension sets is different metrics, priced and queried separately.

Beginner What are the three states of a CloudWatch alarm?

OK (the metric is within the threshold), ALARM (it has breached according to the evaluation configuration), and INSUFFICIENT_DATA (there is not enough data to decide — the metric has not reported, or the alarm is newly created). Actions can be attached to transitions into any of the three, and treating INSUFFICIENT_DATA as harmless is a common mistake when the metric's absence is itself the outage.

Beginner What is the default retention on a new CloudWatch log group, and why does it matter?

Never expire. Logs are billed for ingestion per GB and then for storage per GB every month, forever, so a debug-heavy service quietly accumulates a permanent bill. Set an explicit retention on every log group (weeks for application debug, longer only for audit), export anything you must keep to S3 or the Infrequent Access log class, and reduce log volume at the source.

Intermediate Standard versus detailed monitoring — what changes, and when do you pay for detailed?

Basic monitoring publishes one data point every five minutes and is free; detailed monitoring publishes every minute and is charged per metric. Five-minute granularity cannot see a four-minute outage and delays every alarm by up to five minutes, so enable detailed monitoring on user-facing and autoscaled workloads where reaction time matters, and leave batch or dev workloads on basic. Alarm periods can never be finer than the metric's resolution.

Intermediate A metric filter and a subscription filter both watch a log group. What is the difference?

A metric filter turns matching log events into a CloudWatch metric you can alarm and graph on — counting ERROR lines or a specific exception. A subscription filter streams matching events in near real time to Kinesis Data Streams, Firehose, Lambda or OpenSearch, which is the standard route for centralising logs across accounts or forwarding to a third-party platform. Metric filter for alarming; subscription filter for forwarding. Neither is retroactive.

Intermediate Why prefer p99 over Average for latency alarms?

Average hides the tail. A 180-millisecond mean is compatible with one request in a hundred taking eight seconds, and that one percent is a real set of users, often the ones with the most data. Percentiles measure the experience at the bad end, which is what an SLO is written against. Use Sum for counts, Maximum or high percentiles for latency, and check SampleCount so you know the statistic is based on enough observations to mean anything.

Intermediate Your alarm pages on every brief spike. How do you fix it without weakening the alert?

Tune evaluation rather than the threshold: set evaluation periods to five and datapoints-to-alarm to three so a sustained problem fires but a single blip does not. Choose the right missing-data treatment. Alarm on a rate or percentage instead of a raw count so it scales with traffic. Use a composite alarm so one root cause produces one page instead of forty child alarms, and use anomaly detection for metrics with a strong daily or weekly shape where no fixed number is correct at all hours.

Intermediate What is the embedded metric format and why would you use it over PutMetricData?

EMF is a JSON log line carrying both metric values and arbitrary context; CloudWatch Logs ingests it and extracts the metrics asynchronously. You avoid a synchronous PutMetricData call on the request path, you keep high-cardinality fields (order id, customer tier) queryable in Logs Insights instead of exploding your custom-metric count, and the log record and the metric can never disagree because they are the same record. It is the default pattern on Lambda and containers.

Intermediate How would you find, in production, the ten slowest requests to one endpoint in the last hour?

CloudWatch Logs Insights over that service's log group: filter on the endpoint, sort by the latency field descending, limit ten — assuming structured JSON logs so latency is a real field, otherwise parse it out of the message first. Narrow the time range before running it, because queries are billed by data scanned. Then pivot to the X-Ray trace map or Application Signals to see which downstream call consumed the time.

Pro Would you instrument a new Java service with the X-Ray SDK or with ADOT? Justify it.

ADOT. AWS has published a maintenance-mode and end-of-support timeline for the X-Ray SDKs and daemon and provides migration guides to OpenTelemetry, so new X-Ray SDK code is legacy on arrival. ADOT is AWS's supported build of upstream OpenTelemetry with X-Ray propagation, AWS resource detectors and exporters included; the Java auto-instrumentation agent needs no source changes, and because the app speaks only OTLP the backend choice (X-Ray, Tempo, Datadog, Honeycomb) becomes collector configuration rather than a rewrite.

Pro What does the ADOT Collector do that the agent in the application cannot?

It decouples producing telemetry from shipping it. The collector batches and compresses, applies tail or probabilistic sampling centrally, enriches spans with resource attributes the app does not know, redacts sensitive fields, and fans out to several backends at once — all without redeploying the service. It also absorbs backend outages and back-pressure at the edge of your cluster instead of inside your request path. Run it as an ECS sidecar, an EKS DaemonSet or an EC2 service.

Pro What is CloudWatch Application Signals, and how does it relate to X-Ray?

Application Signals sits on OpenTelemetry instrumentation and automatically derives application-level golden signals per service and per operation — request volume, availability, latency percentiles, fault versus error — plus discovered dependencies, and lets you declare SLOs against them with error-budget tracking. X-Ray holds the individual traces and renders the trace map. Application Signals answers "is this service meeting its objective?"; X-Ray answers "where did this one request spend its time?"

Pro Finance asks which team caused a 40% bill increase. The account has no tags. What can you actually do?

For the past, very little by team — cost allocation tags are not retroactive, so spend incurred before activation stays unattributed. You can still isolate the cause structurally: Cost Explorer grouped by usage type and by linked account, and the Cost and Usage Report in Athena for hourly per-resource detail, which usually identifies the resource even when it cannot identify the owner. Then fix it forward: agree a mandatory tag set, activate those tags in billing, enforce them through Terraform defaults and tag policies or an SCP, and add per-account budgets and anomaly monitors so the next jump is caught in days.

Pro Name the AWS charges that most often surprise teams, and how you would reduce each.

NAT gateway data processing — route S3, ECR, DynamoDB and SSM traffic through VPC endpoints instead. Cross-AZ data transfer, charged in both directions — keep chatty services and their databases zone-aligned where the availability design allows. CloudWatch Logs ingestion plus never-expiring retention — set retention, cut log volume, use the Infrequent Access class.
