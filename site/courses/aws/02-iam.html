Module: IAM and Identity

Every API call in AWS is authorised by IAM before anything else happens, which makes it the one service you cannot route around. Reading a policy document fluently — and predicting what it will decide — is a genuine interview differentiator.

Knowledge Library → Courses → Cloud AWS → IAM and Identity

What this module covers

IAM is the gate in front of every other AWS service. An EC2 instance reading from S3, a Lambda writing to DynamoDB, a CI pipeline pushing an image to ECR, an engineer opening the console — each one is an authenticated principal making a request that IAM allows or denies. Get IAM wrong and either nothing works or everything is exposed, and the second failure mode is the one that ends up in a post-incident review.

The module has two halves. The first is the language: the principals (users, groups, roles), the difference between identity-based and resource-based policies, the JSON elements of a policy document, ARNs and conditions, and the evaluation logic that turns a pile of attached policies into a single allow-or-deny answer. The second is roles in anger — instance profiles, task and execution roles, STS assume-role, cross-account trust, external IDs, OIDC federation for keyless CI, and IAM Identity Center as the modern replacement for IAM users. The thread running through both halves: temporary credentials good, long-lived access keys bad.

Topics

The principals: root, users, groups and roles

Four things can hold permissions, and only three of them are principals. The root user owns the account, cannot be restricted by IAM policy, and should be locked behind hardware MFA and never used for day-to-day work. An IAM user is a named long-lived identity with an optional console password and optional access keys — a real principal, and the one you should reach for least often. A group is not a principal at all: it is a container that policies attach to so that member users inherit them. Nothing can "log in as" a group, nothing can assume a group, and a group cannot be named in a policy's Principal element — a favourite trick question.

A role is an identity with permissions but no permanent credentials. Something assumes it — an EC2 instance, a Lambda function, a user from another account, a federated employee, a GitHub Actions job — and receives a short-lived credential set from STS that expires on its own. That expiry is the whole point: a leaked role credential is a problem for an hour, a leaked access key is a problem until somebody notices. In a well-run account the answer to "how does this thing get permissions?" is almost always a role.

Identity-based versus resource-based policies

An identity-based policy hangs off a user, group or role and answers "what may this principal do?" It has no Principal element, because the principal is whoever the policy is attached to. A resource-based policy hangs off the resource itself — an S3 bucket policy, an SQS queue policy, an SNS topic policy, a KMS key policy, a Lambda function policy, a role's own trust policy — and answers "who may touch me?" It requires a Principal element, and it is the only way to grant access to a principal in another account without that account's cooperation being enough on its own.

Knowing which one to use is a design question that comes up constantly. Within one account you normally grant through identity-based policies because they are easier to audit per principal; you reach for a resource-based policy when the resource must be shared across accounts, when you want the permission to travel with the resource, or when the service has no other mechanism (a KMS key policy is mandatory — an identity policy alone cannot grant use of a key). Two other types exist and matter later: permissions boundaries and service control policies, which restrict rather than grant, and ACLs, which are a legacy S3 mechanism you should generally leave disabled.

Anatomy of a policy document

A policy is a JSON document with a Version (always the literal 2012-10-17 — it is a language version, not a date you invent) and a Statement array. Each statement carries an optional Sid label, an Effect of Allow or Deny, an Action list of service-prefixed operations such as s3:GetObject, a Resource list of ARNs, an optional Principal (resource-based policies only), and an optional Condition block. Statements are independent: they are evaluated together, never in written order, so "the last statement wins" is wrong.

Two inverted elements exist and are worth understanding precisely because they are so often misused. NotAction means "every action except these", and NotResource means "every resource except these". With Effect: Allow they are dangerously broad — Allow plus NotAction: iam:* grants every action in AWS other than IAM, including services that do not exist yet. They are safe and idiomatic with Effect: Deny, which is how region-restriction and service-restriction guardrails are usually written.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadOneBucket",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::acme-reports",
        "arn:aws:s3:::acme-reports/*"
      ]
    }
  ]
}

ARNs, wildcards and the Condition block

Resources are named by ARN, and the shape is arn:partition:service:region:account-id:resource — with the region and account fields left empty for globally-namespaced services, which is why an S3 bucket ARN has the memorable triple colon (arn:aws:s3:::bucket-name). The bucket and the objects inside it are different resources: bucket-level actions such as s3:ListBucket need the bucket ARN, object-level actions such as s3:GetObject need bucket/*. Getting that pair wrong is the single most common reason a "correct-looking" S3 policy denies. Wildcards are allowed in both actions and ARNs (s3:Get*, arn:aws:s3:::acme-*), and "Resource": "*" means every resource the action applies to.

Condition is where a blunt policy becomes a precise one. Each condition is an operator, a key and a value: string operators (StringEquals, StringLike, StringNotEquals), numeric and date operators, Bool, IpAddress, ArnLike, and the ...IfExists suffix plus Null for keys that may be absent. The global keys you should be able to name without looking them up: aws:PrincipalArn, aws:PrincipalOrgID, aws:SourceIp, aws:SourceVpce, aws:RequestedRegion, aws:MultiFactorAuthPresent, aws:SecureTransport, and the tag keys aws:RequestTag, aws:ResourceTag and aws:PrincipalTag. The tag keys are the foundation of attribute-based access control, where one policy scales to hundreds of teams because it compares the principal's tags to the resource's tags instead of listing ARNs.

{
  "Effect": "Deny",
  "Action": "s3:*",
  "Resource": "*",
  "Condition": {
    "Bool": { "aws:SecureTransport": "false" }
  }
}

Evaluation logic: how every single request is decided

This is the algorithm interviewers actually test. For a request, IAM gathers every policy that applies — identity-based, resource-based, permissions boundary, service control policy, session policy — and resolves them in a fixed order that has nothing to do with the order they were written. Step one: is there an explicit Deny anywhere? If yes, the request is denied, full stop, and no Allow anywhere can rescue it. Step two: is there an explicit Allow that survives every applicable restriction? If yes, allow. Step three: otherwise implicit deny — everything is denied by default, so a permission that is simply not mentioned is not granted.

Say it in that order in an interview and add the two refinements that show experience. First, an explicit deny is absolute: it beats an administrator's AdministratorAccess, it beats a resource policy, it beats everything, which is why a deny with an ...IfExists condition is the standard guardrail shape. Second, cross-account requests are evaluated twice — the calling account must allow the call and the resource's account must allow it, so both sides have to say yes independently. (One narrow exception is worth knowing: for a few services, a resource-based policy naming an IAM user in another account can suffice on the trusting side; roles always need both.) When a policy behaves in a way you cannot explain, the IAM policy simulator replays the decision and shows you which statement produced it.

Narrowing the grant: permissions boundaries, SCPs and session policies

Three mechanisms exist purely to restrict, and the rule for all three is identical: they define the maximum, never the grant. Effective permissions are the intersection of what an identity policy allows and what every applicable restriction permits — a boundary or SCP can never expand what an identity policy gives, and attaching one alone grants nothing at all. Candidates who describe an SCP as "giving permissions to accounts" have not used one.

A permissions boundary is a managed policy attached to a user or role that caps what that principal can ever do. Its classic use is safe delegation: give a team lead the ability to create roles, but require every role they create to carry a boundary, so they cannot mint themselves an administrator. A service control policy is attached to an AWS Organizations organizational unit or account and caps every principal in it, including the account's own administrators — this is where "no resources outside ap-south-1" and "nobody may disable CloudTrail" are enforced. Note that an SCP does not apply to the management account's root user, and does not apply to service-linked roles. A session policy is passed inline at AssumeRole time and narrows that one session — useful when a broker hands out downscoped credentials per tenant.

Managed versus inline policies, and least privilege as an actual process

A managed policy is a standalone object with an ARN that can be attached to many identities and carries versions you can roll back — AWS-managed ones such as ReadOnlyAccess are convenient and deliberately broad, customer-managed ones are what you should be writing. An inline policy is embedded in a single identity and is deleted with it, which makes it right for a strict one-to-one relationship you never want accidentally reused, and wrong for anything you would want to audit across the estate. Default to customer-managed; use inline sparingly and deliberately. Remember the quotas exist — a limited number of managed policies attach per identity, and inline policies are bounded by document size, which is why sprawling per-user policies eventually break.

Least privilege is a process, not a first draft. Nobody writes a minimal policy correctly on attempt one, and pretending otherwise produces either a blocked team or a permanent "Action": "*". The honest workflow: start from a broad but bounded grant in a non-production account, let the workload run, then tighten. IAM Access Analyzer generates a policy from the principal's actual CloudTrail activity, validates the policy you wrote against a large set of correctness and security checks, and reports external access findings where a resource is shared outside your account or organization. Access Advisor's last-accessed data tells you which granted services were never touched. Tighten on evidence, review on a schedule, and treat unused permissions as debt.

Roles for compute: instance profiles, task roles and execution roles

The rule for anything running inside AWS is: never embed an access key. An EC2 instance gets credentials through an instance profile — a container that holds exactly one role and is attached to the instance. Code using any AWS SDK finds those credentials automatically through the default provider chain, which queries the Instance Metadata Service; the SDK also refreshes them before they expire, so your application never handles a key at all. Always use IMDSv2 (session-token based), because the older IMDSv1 is what makes a server-side request forgery bug in your web app into a credential theft.

Containers and functions follow the same shape with different names. On ECS, the task role is what your application code uses to call AWS, while the task execution role is what the ECS agent uses to pull the image from ECR and write logs to CloudWatch — two different roles for two different actors, and conflating them is a common interview slip. On Lambda, the execution role covers both: it is what the function's code assumes, and it must include logging permissions or you will get a function that runs and produces no logs. On EKS, the equivalent is IAM Roles for Service Accounts, which maps a Kubernetes service account to an IAM role through OIDC.

STS and AssumeRole: how temporary credentials actually work

Every role assumption goes through the Security Token Service. You call sts:AssumeRole with a role ARN and a session name; STS checks the role's trust policy (a resource-based policy on the role, whose Principal says who is allowed to assume it) and, if you pass, returns three things: an access key id, a secret access key and a session token. All three must be sent on subsequent calls — code that copies only the first two and then gets an InvalidClientTokenId is a rite of passage. Sessions last from fifteen minutes up to the role's maximum session duration, and they cannot be revoked by simply deleting them, which is why short durations matter and why the emergency lever is a deny policy conditioned on aws:TokenIssueTime.

Two elements always confuse newcomers, so be precise about them. The trust policy answers who may assume this role; the permissions policy answers what the role may do once assumed. Both are needed and they are separate documents. On the caller's side you also need an identity policy granting sts:AssumeRole on that role's ARN — so a working assume-role always has two halves in two places. Also know the family: AssumeRoleWithWebIdentity for OIDC federation, AssumeRoleWithSAML for enterprise SAML, GetSessionToken for MFA-gated long-term credentials, and the RoleSessionName you pass, which lands in CloudTrail and is the difference between an auditable trail and an anonymous one.

// Trust policy ON the role — who is allowed to assume it
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
    "Action": "sts:AssumeRole",
    "Condition": { "StringEquals": { "sts:ExternalId": "acme-tenant-42" } }
  }]
}

Cross-account access and the external ID

The canonical multi-account setup: account A holds your engineers, accounts B and C hold dev and prod workloads. You do not create users in B and C. You create a role in each, give it a trust policy naming account A, and give the engineers in A permission to call sts:AssumeRole on those role ARNs. Console users get the switch-role experience; CLI users get a named profile with role_arn and source_profile and the SDK does the assumption transparently. Add "Bool": {"aws:MultiFactorAuthPresent": "true"} to the production role's trust policy and MFA becomes mandatory for touching prod, enforced by IAM rather than by policy documents in a wiki.

When the other account belongs to a third party — a monitoring vendor, a FinOps tool, an audit partner — add an external ID. The problem it solves is the confused deputy: the vendor holds assume-role rights into many customers' accounts, so if an attacker can guess or learn your role ARN and persuade the vendor's platform to use it, the vendor becomes an unwitting proxy into your account. The external ID is a unique, customer-specific string that the vendor must pass and that your trust policy requires with sts:ExternalId, so credentials issued for one customer cannot be pointed at another. If a vendor asks you for an IAM user's access keys instead of offering a role with an external ID, that is a real security signal about the vendor.

Web identity federation and OIDC: the keyless CI pipeline

The most useful modern application of federation is deleting the access keys from your CI system. Instead of storing an AWS_ACCESS_KEY_ID secret in GitHub Actions — a long-lived credential visible to every workflow, rotated by nobody — you register GitHub's OIDC provider as an identity provider in your account and create a role whose trust policy accepts tokens from it. The runner requests a short-lived OIDC token, exchanges it via AssumeRoleWithWebIdentity, and gets credentials that expire when the job ends. Nothing durable is ever stored.

The detail that matters is the trust policy condition. Validate the audience (token.actions.githubusercontent.com:aud) and constrain the subject (...:sub) to your specific repository and ideally a specific branch or environment — repo:acme/payments:ref:refs/heads/main. A trust policy that matches on repo:*, or omits the subject condition entirely, lets any repository on GitHub assume your role, which is a total account compromise dressed up as a best practice. The same pattern covers GitLab, Bitbucket, EKS service accounts and mobile apps signed in through Cognito.

IAM Identity Center, and the finding auditors look for

In any organisation with more than one account, IAM users for humans are the wrong answer. AWS IAM Identity Center — the service formerly called AWS SSO — connects to your existing directory (Entra ID, Okta, Google Workspace, or its own built-in store) and hands out console and CLI access to many accounts through permission sets, which are effectively role templates provisioned into each account you assign them to. Access is by federated session, so nothing long-lived is issued; joiners and leavers are handled where they are already handled, in the identity provider; and the CLI works through aws sso login rather than a credentials file full of secrets. IAM users then remain only for the genuine edge cases — a legacy system that cannot federate, and even those should be justified in writing.

Which brings the module to its one-line summary. Long-lived IAM access keys are the finding auditors look for, and for good reason: they leak into git history, CI logs, Docker images, laptop backups and support tickets, they usually carry more permission than anyone remembers granting, and they work until a human notices. Prefer a role every time. Where a key genuinely must exist, scope it hard, rotate it on a schedule, alarm on its use from unexpected regions or IPs, and use the credential report and Access Advisor to find the ones nobody has touched in ninety days — then delete them.

Interview questions

IAM is asked in almost every AWS round in India, from service-company screening to product-company system design — and the evaluation order plus the user-versus-role distinction come up so reliably that not knowing them is disqualifying:

Beginner What is the difference between an IAM user and an IAM role?

A user is a permanent identity with long-lived credentials — a console password and/or access keys — that belongs to one person or system. A role is an identity with permissions but no permanent credentials; it is assumed by a trusted principal (an EC2 instance, a Lambda function, another account, a federated identity) and STS issues temporary credentials that expire on their own. Roles are the default for workloads and for humans in a multi-account setup; users are for the shrinking set of cases that cannot federate.

Beginner Can an IAM group be used as a principal, or assume a role?

No. A group is only a container for attaching policies to a set of users — it has no ARN you can put in a Principal element and it cannot assume a role. If you want group-like behaviour for a role, you grant the group's users permission to assume that role.

Beginner Name the elements of an IAM policy statement.

Version at the document level (always 2012-10-17), then per statement: Sid (optional label), Effect (Allow or Deny), Action or NotAction, Resource or NotResource, Principal or NotPrincipal (resource-based policies only), and Condition. Statements are evaluated together, not in written order.

Beginner What is the structure of an ARN, and why does an S3 bucket ARN have three colons together?

arn:partition:service:region:account-id:resource. S3 bucket names are globally unique, so the region and account-id fields are empty, producing arn:aws:s3:::my-bucket. Remember that the bucket and its objects are separate resources: s3:ListBucket needs the bucket ARN, s3:GetObject needs bucket/*.

Intermediate Explain IAM policy evaluation order.

All applicable policies are collected — identity-based, resource-based, permissions boundary, SCP, session policy — then: (1) an explicit Deny anywhere denies the request immediately and nothing can override it; (2) otherwise an explicit Allow that survives every applicable restriction allows it; (3) otherwise implicit deny, because everything is denied by default. Written order within a policy is irrelevant. For cross-account calls the decision must pass in both accounts.

Intermediate Identity-based versus resource-based policy — when do you use each?

Identity-based policies attach to a user, group or role and have no Principal; use them for normal in-account grants because they are easy to audit per principal. Resource-based policies attach to the resource (S3 bucket, SQS queue, SNS topic, KMS key, Lambda function, role trust policy), require a Principal, and are how you share a resource across accounts or make the permission travel with the resource. KMS key policies are mandatory — an identity policy alone cannot grant key usage.

Intermediate Managed versus inline policies — which would you default to?

Customer-managed. A managed policy is a standalone versioned object with an ARN, reusable across identities and rollback-able; AWS-managed ones are convenient but deliberately broad. An inline policy is embedded in one identity and dies with it, which suits a strict one-to-one relationship you never want reused, but it cannot be audited or reused across the estate and it hits document-size limits. Default managed, use inline deliberately.

Intermediate How does an EC2 instance get AWS credentials without any access key on disk?

Through an instance profile: a container holding one IAM role, attached to the instance. The AWS SDK's default credential provider chain queries the Instance Metadata Service, receives temporary credentials from STS and refreshes them automatically before expiry. Enforce IMDSv2 (session-token based) so a server-side request forgery bug in the application cannot be turned into credential theft.

Intermediate ECS task role versus task execution role?

The task role is assumed by your application code inside the container to call AWS services. The task execution role is used by the ECS agent itself to pull the image from ECR, fetch secrets and write logs to CloudWatch. Different actors, different permissions — a container that cannot start usually has an execution-role problem, while a container that starts and then gets access-denied usually has a task-role problem.

Intermediate What does an AssumeRole call return, and what breaks if you ignore part of it?

An access key id, a secret access key and a session token, plus an expiry. All three must be sent on subsequent requests; using only the first two produces InvalidClientTokenId. The session lasts from fifteen minutes up to the role's maximum session duration, and the RoleSessionName you supply appears in CloudTrail, which is what makes shared-role activity attributable to a person.

Pro A role has AdministratorAccess but the call is denied. Give three explanations.

(1) An explicit Deny somewhere — an SCP on the account's organizational unit, a resource-based policy on the target, or a deny statement in another attached policy. (2) A permissions boundary or session policy that caps the role below administrator, since effective permissions are an intersection. (3) A cross-account call where the resource's account has not granted access, or the resource is encrypted with a KMS key whose key policy does not permit this principal. Diagnose with CloudTrail's error detail and the IAM policy simulator.

Pro What is a permissions boundary, and how is it different from an SCP?

Both cap rather than grant, and effective permissions are the intersection. A permissions boundary is a managed policy attached to a single IAM user or role, typically so a delegated admin can create roles without being able to escalate beyond the boundary. An SCP is attached to an AWS Organizations OU or account and caps every principal inside it, including that account's own administrators — the account-wide guardrail for region restrictions, mandatory encryption or protecting CloudTrail. Neither grants anything on its own; SCPs do not apply to the management account's root user or to service-linked roles.

Pro Why does a third-party SaaS vendor ask for an external ID, and what attack does it prevent?

The confused deputy. The vendor holds assume-role rights into many customer accounts; if an attacker learns or guesses your role ARN and gets the vendor's platform to use it, the vendor becomes an unwitting proxy into your account. The external ID is a unique per-customer secret that the vendor must pass and your trust policy requires via the sts:ExternalId condition, so a session issued for one customer cannot be aimed at another. A vendor asking for IAM user access keys instead is a red flag.

Pro How would you give a GitHub Actions pipeline deploy access with no stored AWS keys, and what is the mistake people make?

Register GitHub's OIDC provider as an IAM identity provider, create a deploy role trusting it, and have the workflow call AssumeRoleWithWebIdentity to get job-scoped temporary credentials. The mistake is a loose trust policy: you must validate the audience claim and constrain the subject claim to your exact repository and branch or environment, for example repo:acme/payments:ref:refs/heads/main. A wildcard subject lets any repository on GitHub assume your role.

Pro You inherit an account with fifty IAM users holding access keys. What is your remediation plan?

Inventory first with the IAM credential report and Access Advisor to see which keys and permissions are actually used. Stand up IAM Identity Center against the corporate directory and move humans to permission sets; move workloads to instance profiles, task roles, execution roles or OIDC federation. Deactivate keys before deleting them so breakage is reversible, then delete. Enforce the end state with an SCP or boundary denying iam:CreateAccessKey, add IAM Access Analyzer for external-access findings, and alarm on root and on access-key use from unexpected regions.

Pro Your policy grants s3:GetObject on arn:aws:s3:::reports but reads still fail. Why?

Object actions need the object ARN, not the bucket ARN — you need arn:aws:s3:::reports/* (and the bare bucket ARN as well if you also need s3:ListBucket). If that is already correct, check the other usual suspects: a bucket policy or Block Public Access setting denying, a KMS key policy that does not allow this principal to decrypt an SSE-KMS object, an SCP restricting the region, or a VPC endpoint policy in the request path.
