Module: RabbitMQ in Production

A RabbitMQ cluster that works on a laptop and a RabbitMQ cluster that survives a bad Friday differ by about a dozen settings. This module is those settings — acknowledgements, prefetch, expiry, dead-lettering, and the replicated queue types that keep data alive when a node dies.

Knowledge Library → Courses → Messaging and Event-Driven Systems → RabbitMQ in Production

What this module covers

The previous module gave you the AMQP model: exchanges, bindings, routing keys, queues. That model is broker-side vocabulary. This module is the operational half — the consumer-side and queue-side configuration that decides whether messages are lost on a consumer crash, whether one greedy worker starves the rest of the pool, what happens to a message nobody can process, and whether a queue survives losing the node it lives on.

Everything here is against RabbitMQ 4.x, where the landscape changed materially: classic queue mirroring was removed outright, quorum queues became the default answer for durable replicated work, and streams gave RabbitMQ a Kafka-shaped append-only log of its own. The module closes on Spring AMQP, since that is how most JVM teams actually touch any of it.

Topics

Consumer acknowledgements: manual ack, autoack, and the at-most-once trap

A consumer subscribes with basic.consume, and the single most consequential flag on that call is no-ack. Set it, and you are in automatic acknowledgement mode: the broker considers a message delivered the moment it has written it to the socket, forgets it, and moves on. If your process crashes, the TCP connection drops mid-flight, or your handler throws after the bytes arrived, the message is simply gone. Autoack is therefore at-most-once delivery, and it is the correct choice only for data you are genuinely happy to lose — metrics samples, cache-warming hints, log lines. For anything with business meaning, use manual acknowledgement and ack after the work is done and committed, which gives you at-least-once and obliges the consumer to be idempotent.

In manual mode you have three verbs. basic.ack confirms a delivery tag (with a multiple flag to confirm everything up to that tag in one round trip). basic.reject discards one message, with a requeue flag deciding whether it goes back on the queue or gets dead-lettered. basic.nack is RabbitMQ's extension that does the same thing but supports multiple. The rule that trips people up: requeue=true on a message that fails deterministically produces an infinite hot loop — the message returns to the queue head, is redelivered instantly, fails again, forever, pinning a CPU. Use requeue=false plus a dead-letter exchange for anything that is not a transient fault, and read the redelivered flag on the delivery, which tells you the broker has handed this message out before (it is a hint, not a reliable counter). Finally, remember that unacknowledged messages accumulate: the broker keeps every unacked delivery pending until you ack, reject, or drop the channel, so a consumer that forgets to ack quietly grows the broker's memory footprint until the delivery-acknowledgement timeout (30 minutes by default) closes the channel and requeues everything.

channel.basicConsume(queue, false, (tag, delivery) -> {   // false = manual ack
    try {
        handle(delivery.getBody());                       // do the work first
        channel.basicAck(delivery.getEnvelope().getDeliveryTag(), false);
    } catch (TransientException e) {
        channel.basicNack(delivery.getEnvelope().getDeliveryTag(), false, true);  // requeue
    } catch (PoisonException e) {
        channel.basicNack(delivery.getEnvelope().getDeliveryTag(), false, false); // to the DLX
    }
}, tag -> {});

Prefetch (basic.qos): the one setting that decides your load balancing

By default a channel has no prefetch limit, and RabbitMQ will push messages to a consumer as fast as the socket accepts them. With ten thousand messages queued and three workers, the first worker to connect can end up buffering nearly all of them client-side while the other two sit idle — round-robin dispatch happens at delivery time, not at processing time, so the broker considers its work fairly distributed while your throughput is that of a single worker. Worse, those buffered messages are unacked: if that worker dies, all of them are requeued at once. basic.qos(prefetchCount) fixes this by capping how many unacknowledged deliveries a consumer may hold. Set it to 1 and you get strict fair dispatch — nobody gets a second message until the first is acked.

Two details worth knowing precisely. First, prefetch only exists in manual-ack mode; in autoack mode there is no such thing as an unacknowledged message, so the limit is ignored and you are back to unbounded push. Second, the global flag: RabbitMQ interprets global=false (the usual case) as per-consumer and global=true as shared across the whole channel — and quorum queues reject the channel-wide form outright, so per-consumer prefetch is the portable choice. For sizing, the honest answer is that it is a latency-versus-fairness dial: long, uneven processing times want a small prefetch (1 to about 10) so no worker hoards; short, uniform tasks at high message rates want a larger one (in the low hundreds) so the consumer is never idle waiting for a network round trip. Start from round-trip time divided by processing time, then measure — an over-large prefetch shows up as idle consumers next to a busy one, and an over-small one shows up as consumers blocked on the network.

channel.basicQos(20);              // per-consumer: at most 20 unacked deliveries
// channel.basicQos(0, 20, true);  // channel-wide form: rejected by quorum queues

// Spring Boot equivalent
// spring.rabbitmq.listener.simple.prefetch=20
// spring.rabbitmq.listener.simple.acknowledge-mode=auto   # container acks after the listener returns

TTL, queue length limits and overflow behaviour

Messages that nobody consumes are not free — they occupy memory and disk, and a queue that grows without bound eventually triggers flow control and stalls your publishers. RabbitMQ gives you two independent brakes. Time to live expires messages by age: x-message-ttl as a queue argument or policy applies to everything in the queue, while the per-message expiration property (a string of milliseconds) sets it per publish. A separate x-expires argument deletes an entire queue that has gone unused for a period — useful for per-session or per-request reply queues that would otherwise leak. Note the classic-queue subtlety with per-message TTL: expiry is evaluated at the head of the queue, so a long-lived message sitting in front of a short-lived one delays the latter's expiry.

Length limits bound the queue instead: x-max-length in messages, x-max-length-bytes in payload bytes. What happens when the limit is hit is decided by x-overflow, and choosing it is a real design decision. drop-head (the default) throws away the oldest messages, which is right for telemetry where fresh data supersedes stale data. reject-publish refuses new publishes and negatively acknowledges them to the publisher, which is right when losing data silently is unacceptable and you would rather push back on the producer. reject-publish-dlx does the same but dead-letters the rejected message so you keep it. Set these as policies rather than client-side queue arguments where you can — policies can be changed on a running system, whereas an argument baked into a queue declaration requires deleting and recreating the queue.

rabbitmqctl set_policy work-limits "^work\." \
  '{"message-ttl":600000,"max-length":100000,"overflow":"reject-publish-dlx","dead-letter-exchange":"dlx"}' \
  --apply-to queues

Dead-letter exchanges: where failed messages actually go

A dead-letter exchange is an ordinary exchange that the broker republishes to when a message can no longer stay in its queue. Exactly four things cause dead-lettering: the consumer rejects it with basic.reject or basic.nack and requeue=false; its TTL expires; the queue is over its length limit and the overflow policy drops or rejects it; or, on a quorum queue, the delivery limit is exceeded. Configure it with the x-dead-letter-exchange argument (plus an optional x-dead-letter-routing-key to override the original routing key), and RabbitMQ stamps an x-death header on the message recording the reason, the originating queue and exchange, and a count — which is your forensic trail and, historically, the way people implemented a redelivery counter on classic queues.

The classic delayed-retry trick falls straight out of these two features: declare a "wait" queue with no consumers, give it an x-message-ttl and an x-dead-letter-exchange that points back at the work exchange. Reject a failed message into the wait queue; it sits there until the TTL fires, gets dead-lettered back to the work queue, and is retried. Chain several wait queues with increasing TTLs and you have exponential backoff without a scheduler. Two warnings: because expiry is head-of-line on classic queues, mixing different per-message TTLs in one wait queue does not give you independent timers — use one wait queue per delay tier. And know that dead-lettering is at-most-once by default, so a broker failure at the wrong moment can lose the dead-lettered copy; quorum queues offer dead-letter-strategy: at-least-once (requiring overflow: reject-publish) when that matters. Module 08 develops the full retry and parking-lot strategy; this is the mechanism it is built on.

// work queue: failures go to the retry exchange
Map<String, Object> work = Map.of("x-dead-letter-exchange", "retry.ex");

// wait queue: no consumers, expires after 10s, dead-letters BACK to the work exchange
Map<String, Object> wait = Map.of(
    "x-message-ttl", 10000,
    "x-dead-letter-exchange", "work.ex",
    "x-dead-letter-routing-key", "orders");

Priority queues, and an honest note on what they cost

Declare a classic queue with x-max-priority (an integer, 1 to 255) and publishers can set a priority message property; higher priorities are delivered first. It is genuinely useful for a work queue that mixes interactive requests with bulk backfill. But be honest about the limits, because interviewers probe here. Each priority level costs resources on the broker — the practical advice from the RabbitMQ community is to use no more than about five levels, and never 255 "just in case". Priority is only meaningful when a backlog exists: an empty queue delivers whatever arrives, and messages already pushed into a consumer's prefetch buffer are never reordered, so a large prefetch quietly defeats prioritisation. Combine priorities with a length limit and drop-head and you can lose your most important message, because drop-head discards from the head of the queue.

Quorum queues changed the picture in RabbitMQ 4.x: they always support priorities and ignore x-max-priority entirely, but the implementation is deliberately coarser than the classic one — messages are sorted into a normal and a high band with a fixed delivery ratio that favours high priority while still guaranteeing normal messages make progress, so there is no starvation. If you need genuinely fine-grained scheduling, the standard advice remains the same as it has always been: use separate queues per class of work and separate consumer pools, which gives you independent capacity control as well as ordering.

Quorum queues: the default for anything durable

A quorum queue is a durable, replicated FIFO queue implemented with the Raft consensus algorithm. Every queue has a leader and followers on other cluster nodes; a publish is confirmed once a majority of replicas has written it, and if the leader's node dies a new leader is elected from the remaining replicas with no data loss for confirmed messages. Say the next part plainly, because it is the single most-asked RabbitMQ-4 interview fact: classic queue mirroring was removed in RabbitMQ 4.0. It was deprecated back in the 3.9 era and the HA policies that configured it no longer do anything. Quorum queues (and streams) are the only replicated options now, and new durable workloads should declare x-queue-type: quorum — or better, set the virtual host's default queue type so nobody has to remember.

Quorum queues also solve poison-message handling properly. Classic queues had no server-side redelivery counter, so teams hand-rolled one from the x-death header. Quorum queues track deliveries per message and enforce delivery-limit: exceed it and the message is dropped or, far better, dead-lettered. Since RabbitMQ 4.0 that limit defaults to 20, which is a behaviour change worth knowing — an endlessly requeued message that used to loop forever now eventually leaves the queue. What they do not support: non-durable (transient) queues, exclusive queues, server-named queues, and channel-wide (global) QoS prefetch, which returns a channel error. They also cost more than a classic queue — every message is replicated and written to disk on a majority of nodes — so a queue that is genuinely disposable is still a legitimate use for a classic queue. And ignore any tutorial that tells you to set x-queue-mode=lazy: that setting has been a no-op since RabbitMQ 3.12, when classic queues moved to a single version-2 storage implementation that always keeps messages on disk.

// Spring AMQP: declare a quorum queue with a delivery limit and a DLX
@Bean
Queue orders() {
    return QueueBuilder.durable("orders")
            .quorum()                            // x-queue-type = quorum
            .deliveryLimit(5)                    // poison messages leave after 5 tries
            .deadLetterExchange("orders.dlx")
            .build();
}

RabbitMQ Streams and super streams

A stream is a replicated, append-only log inside RabbitMQ — the same shape as a Kafka topic partition, and added for the same reasons. Consumption is non-destructive: reading does not remove data, many independent consumers can read the same stream, and each tracks its own offset. You attach at an offset (first, last, next, an absolute offset, or a timestamp) and replay history — something a queue can never do, because a queue delivers a message once and forgets it. Retention is size- or age-based (max-length-bytes, max-age) rather than consumption-based, which is the mental switch to make: you keep a window of time, not a backlog of unprocessed work.

Streams are reachable two ways. Over ordinary AMQP 0-9-1 they look like a queue with an x-stream-offset consumer argument, which requires manual acks and a prefetch limit — convenient, since your existing client works unchanged. The dedicated stream protocol (a separate plugin and port) is far faster and is what the stream-specific clients use, and it is the one to reach for at high throughput. Super streams are the partitioning layer on top: a logical stream composed of several individual streams, with publishing routed by a key so related messages land on the same partition, and single-active-consumer semantics per partition so ordering holds while the group scales horizontally. If you have found yourself wanting Kafka's consumer groups and replay without running Kafka, this is the feature to read about — but be clear-eyed that RabbitMQ's queues and streams answer different questions, and most systems end up using both.

Clustering, replica sizing, and migrating off mirrored queues

A RabbitMQ cluster is a set of nodes sharing users, virtual hosts, exchanges, bindings and policies. Client connections can land on any node and the broker routes internally, but a queue's data lives on specific nodes — that is the distinction to keep straight. Classic queues live on exactly one node; quorum queues and streams replicate across an explicitly chosen replica set. Size that replica set with an odd number of nodes, normally three (tolerates one failure) or five (tolerates two), because Raft needs a strict majority to elect a leader and to confirm a write. Two replicas are worse than useless: losing either one loses the majority. Cluster sizes should likewise be odd, and a partition-handling strategy such as pause_minority keeps a split cluster from accepting divergent writes on both sides.

The migration question comes up constantly for teams still on 3.x. Queue type is fixed at declaration, so you cannot convert a mirrored classic queue into a quorum queue in place — you declare a new quorum queue, move consumers, drain and repoint publishers, then delete the old one. Plan the incompatibilities before you start: transient and exclusive queues, server-named queues, global QoS, and any code depending on classic-queue-only behaviour all need changes. Watch memory and disk too, since replication multiplies both. The official migration guide and the RabbitMQ team's own retrospectives are the right reading, not blog posts written before 4.0 landed.

Spring AMQP: RabbitTemplate, @RabbitListener and AmqpAdmin

Spring AMQP is the JVM abstraction over the RabbitMQ Java client, and Spring Boot's spring-boot-starter-amqp auto-configures a ConnectionFactory, a RabbitTemplate and a listener container factory from spring.rabbitmq.* properties. RabbitTemplate is the publishing side: convertAndSend(exchange, routingKey, payload) for fire-and-forget, convertSendAndReceive for request-reply over a temporary reply queue, plus ConfirmCallback and ReturnsCallback hooks for publisher confirms and returned (unroutable) messages — set mandatory if you want to hear about messages that matched no binding rather than losing them silently.

On the consuming side, @RabbitListener(queues = "orders") registers a method with a listener container; the container's acknowledgeMode (AUTO means the container acks after your method returns normally and rejects when it throws — not the broker's autoack), prefetchCount and concurrency are where the settings from earlier in this module actually get applied. Topology is declarative: define Queue, Exchange and Binding beans and RabbitAdmin (the AmqpAdmin implementation) declares them on the broker at startup and re-declares them after a connection is re-established. That auto-declaration is a convenience in development and a hazard in production, where mismatched arguments between your bean and an existing queue cause a channel-level error — many teams manage topology with policies and definitions files and keep declarations out of the application entirely.

@RabbitListener(queues = "orders", concurrency = "3-10")
public void onOrder(OrderEvent event) {          // converted by the message converter
    orderService.process(event);                 // throw -> container rejects, DLX takes it
}

@Bean Binding binding(Queue orders, TopicExchange work) {
    return BindingBuilder.bind(orders).to(work).with("order.created");
}

Message converters, retries and RepublishMessageRecoverer

By default Spring AMQP's SimpleMessageConverter handles strings and byte arrays and falls back to Java serialization for other objects — which you should not ship, both for the security exposure and because it couples producer and consumer to the same classes. Register a JSON converter instead (JacksonJsonMessageConverter in Spring AMQP 4.x, Jackson2JsonMessageConverter in the 3.x line) on both the template and the listener container factory, and it will set the content_type and type headers so the consumer can deserialize into a target class. Be deliberate about the type mapping: shipping fully-qualified class names in headers makes a producer refactor break every consumer, so map types explicitly for anything crossing team boundaries.

For failure handling, Spring's stateless retry interceptor wraps the listener and retries in-process with backoff — cheap for a transient database blip, but note that the message stays unacked and the consumer thread is blocked while it waits, so keep the total budget short. When retries are exhausted a MessageRecoverer decides the message's fate. The default merely logs and acks, which silently swallows the message. RejectAndDontRequeueRecoverer rejects without requeue so the broker's DLX takes over. RepublishMessageRecoverer is usually the best of the three: it publishes the failed message to an exchange and routing key you choose, adding headers with the exception message, the stack trace, and the original exchange and routing key — so your parking-lot queue contains not just the payload but the reason it failed, which is exactly what you want at three in the morning.

@Bean
RetryOperationsInterceptor retryInterceptor(RabbitTemplate template) {
    return RetryInterceptorBuilder.stateless()
            .maxAttempts(4)
            .backOffOptions(500, 2.0, 8000)     // initial, multiplier, max
            .recoverer(new RepublishMessageRecoverer(template, "parking.ex", "orders.failed"))
            .build();
}
// spring.rabbitmq.listener.simple.retry.enabled=true is the properties-only equivalent

Interview questions

RabbitMQ operations is a favourite of Indian product and service-company rounds — prefetch, acknowledgement modes and dead-letter exchanges come up in almost every round that mentions RabbitMQ on the JD, and the quorum-queue questions separate candidates who have worked on 4.x from candidates who learned RabbitMQ five years ago:

Beginner What is the difference between automatic and manual acknowledgement?

With automatic acknowledgement (the no-ack flag on basic.consume) the broker considers a message delivered as soon as it writes it to the socket and immediately forgets it — a consumer crash loses the message, so this is at-most-once delivery. With manual acknowledgement the broker keeps the message until the consumer sends basic.ack, and requeues it if the channel or connection drops — at-least-once delivery, which obliges the consumer to be idempotent. Ack after the work is committed, never before.

Beginner What does prefetch (basic.qos) do, and what happens if you never set it?

It caps how many unacknowledged messages the broker will push to a consumer at once. With no limit the broker pushes as fast as the socket accepts, so the first consumer to connect can buffer the entire backlog client-side while other consumers sit idle — round-robin dispatch is done at delivery time, so the broker thinks it is balancing while your effective throughput is that of one worker. A small prefetch restores fair dispatch; it also bounds how many messages are requeued if that consumer dies.

Beginner What is a dead-letter exchange, and what causes a message to be dead-lettered?

An ordinary exchange named in a queue's x-dead-letter-exchange argument, to which the broker republishes messages that can no longer stay in the queue. Four causes: rejection with basic.reject or basic.nack with requeue=false; TTL expiry; the queue exceeding its length limit under a dropping or rejecting overflow policy; and, on quorum queues, exceeding the delivery limit. The republished message carries an x-death header recording the reason, source queue and count.

Beginner How do you set a TTL on messages, and what is the difference between the two ways?

Queue-level via the x-message-ttl argument or a policy — it applies uniformly to everything in the queue. Message-level via the expiration property on the publish, expressed as a string of milliseconds. There is also x-expires, which deletes an unused queue rather than expiring messages. Prefer policies for queue-level TTL so you can change it without recreating the queue.

Intermediate A message keeps failing and your consumer nacks it with requeue=true. What happens?

An infinite hot loop: the message goes back to the head of the queue, is redelivered almost immediately, fails again, and repeats — burning CPU and blocking the rest of the queue. Requeue only for genuinely transient faults. For deterministic failures use requeue=false with a dead-letter exchange, and on quorum queues set a delivery-limit so the broker enforces a bound even if the consumer misbehaves.

Intermediate How would you implement delayed retry with backoff using only core RabbitMQ features?

Use a TTL queue whose dead-letter exchange points back at the work exchange. Reject the failed message into a consumer-less "wait" queue that has an x-message-ttl; when the TTL fires the broker dead-letters it back to the work queue and it is retried. Chain wait queues with increasing TTLs for exponential backoff. Use one wait queue per delay tier rather than per-message TTLs in a single queue, because classic-queue expiry is evaluated at the head — a long-lived message in front delays the ones behind it.

Intermediate How do you size prefetch, and what is the interaction with acknowledgement mode?

Prefetch only has meaning in manual-ack mode; in autoack mode there are no unacknowledged messages, so the limit is ignored and delivery is unbounded again. Sizing is a fairness-versus-latency dial: long or highly variable processing times want a small prefetch (1 to about 10) so no consumer hoards work; short uniform tasks at high rates want a larger one (low hundreds) so consumers are not idle on network round trips. Start near round-trip-time divided by processing time and then measure — idle consumers next to one busy consumer means it is too large.

Intermediate What are the overflow behaviours on a length-limited queue, and when would you pick each?

drop-head (default) discards the oldest messages — right for telemetry and live metrics where new data supersedes old. reject-publish refuses new publishes and nacks the publisher — right when data loss is unacceptable and you want backpressure on producers. reject-publish-dlx rejects but dead-letters the message so it is retained for inspection or replay. Note the trap: combining drop-head with a priority queue can discard your highest-priority messages, since they sit at the head.

Intermediate What are quorum queues and why should new durable queues use them?

Durable replicated FIFO queues built on Raft: a leader plus followers, with publishes confirmed once a majority of replicas has persisted the message, and automatic leader election on node failure without losing confirmed data. They are the recommended default because classic queue mirroring was removed in RabbitMQ 4.0 — HA policies no longer replicate anything — so quorum queues and streams are the only replicated options left. They also add server-side poison-message handling via delivery-limit.

Intermediate Compare a RabbitMQ stream with a queue. When would you choose a stream?

A queue delivers each message to one consumer and deletes it on ack; a stream is a replicated append-only log where consumption is non-destructive, many consumers read independently, and each tracks an offset. Streams let you attach at an offset or a timestamp and replay history, and retain by size or age rather than by consumption. Choose a stream for fan-out to many independent readers, for replay and reprocessing, and for very high throughput ingestion; choose a queue for competing-consumer work distribution where a message should be handled once and then gone.

Pro What do quorum queues not support, and when is a classic queue still the right choice?

They cannot be non-durable (transient), exclusive, or server-named, and they reject channel-wide (global) QoS prefetch with a channel error. They also cost more — every message is replicated and written to disk on a majority of nodes — so replication multiplies memory, disk and network. A classic queue remains reasonable for genuinely disposable data, for short-lived per-connection reply queues (which need exclusivity anyway), and for very high-churn temporary topology. Also: x-queue-mode=lazy is not a tuning option any more, it has been a no-op since 3.12.

Pro How many nodes should a quorum queue be replicated across, and why must it be odd?

Three for most workloads (tolerates one failure), five where you must survive two. Raft requires a strict majority to elect a leader and to confirm a write, so an odd count maximises fault tolerance per node: with three, quorum is two; adding a fourth still needs three, giving no extra tolerance for extra cost. Two replicas are actively harmful — losing either loses the majority and the queue becomes unavailable. Pair this with an odd cluster size and a partition-handling strategy such as pause_minority so a split cluster does not accept divergent writes on both sides.

Pro You inherit a 3.x cluster using mirrored classic queues. Plan the migration.

Queue type is fixed at declaration, so there is no in-place conversion: declare parallel quorum queues, bind them, move consumers over, repoint publishers, drain the old queues, then delete them and remove the HA policies. Audit incompatibilities first — transient, exclusive and server-named queues, global QoS, and any logic relying on the x-death header as a homemade delivery counter (use delivery-limit instead, and remember the new default of 20 changes behaviour for endlessly requeued messages). Capacity-plan for replication multiplying disk and memory, and follow the official migration guide rather than pre-4.0 blog posts.

Pro In Spring AMQP, what is the difference between the container's AUTO acknowledge mode and RabbitMQ's autoack?

They sound identical and are opposites in effect. RabbitMQ's autoack (no-ack=true) is broker-side: delivery is considered complete when written to the socket, giving at-most-once. Spring's AcknowledgeMode.AUTO uses manual acknowledgement on the wire and has the container ack after your listener returns normally, or reject when it throws — that is at-least-once with the container doing the bookkeeping. AcknowledgeMode.NONE is the one that maps to the broker's autoack; MANUAL hands you the channel and delivery tag to ack yourself.

Pro Retries are exhausted for a message in a Spring AMQP listener. What are the recovery options and which do you pick?

The default MessageRecoverer logs a warning and acks — it silently destroys the message, so avoid it. RejectAndDontRequeueRecoverer rejects without requeue and lets the queue's dead-letter exchange take over. RepublishMessageRecoverer publishes to an exchange and routing key you choose while adding headers containing the exception message, stack trace and original exchange and routing key — usually the best choice, because the parking-lot queue then holds the failure reason alongside the payload. Keep in-process retry budgets short, since the message stays unacked and the consumer thread is blocked throughout.

Pro A priority queue is not prioritising in production. Give the likely causes.

Most often prefetch: messages already pushed into consumers' buffers are never reordered, so a large prefetch drains the backlog into clients where priority no longer applies — drop it to a small value. Second, priority only matters when a backlog exists; on a queue that is keeping up, whatever arrives is delivered. Third, publishers may not be setting the priority property at all, or are setting values above the declared x-max-priority. And on a quorum queue, x-max-priority is ignored entirely — priorities are always on but coarser, banding messages rather than honouring a fine-grained scale.
