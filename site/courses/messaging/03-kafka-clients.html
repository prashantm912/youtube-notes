Module: Kafka Producers and Consumers

The broker is not where Kafka correctness is decided — the clients are. A dozen configuration properties on the producer and the consumer decide whether your pipeline loses messages, duplicates them, reorders them, or quietly stops making progress.

Knowledge Library → Courses → Messaging and Event-Driven Systems → Kafka Producers and Consumers

What this module covers

Module 02 explained what the cluster does with your data. This module is about the two libraries you actually write code against, and it is where almost every real Kafka incident originates. A producer that ships with acks=1 loses records on a leader failover. A producer with retries but without idempotence can silently reorder a partition. A consumer with auto-commit enabled can acknowledge records it never processed. None of these fail loudly in a dev environment; all of them fail in production under load.

We work through the producer send path — acks, idempotence, the record accumulator, batching, compression and partitioning — and then the consumer side: consumer groups, the group coordinator, rebalancing (including the broker-driven KIP-848 protocol that is the default in Apache Kafka 4.x), the two timeouts that get consumers evicted, and the offset commit strategies that decide whether you get at-least-once or at-most-once delivery. Configuration names and defaults throughout are those of Apache Kafka 4.x.

Topics

The producer send path: acks, retries and delivery.timeout.ms

producer.send() does not talk to a broker. It serialises the record, asks the partitioner for a partition, and appends the bytes to a per-partition batch in an in-memory record accumulator bounded by buffer.memory; a background I/O thread drains full or expired batches to the partition leaders. The call returns a Future immediately, which is why fire-and-forget producer code appears to work perfectly right up to the moment you check whether anything arrived. If the accumulator fills because the brokers cannot keep up, send() blocks for max.block.ms and then throws — back-pressure surfacing as an exception on a method most people believe is asynchronous.

acks is the durability dial. acks=0 means the producer never waits for a reply: highest throughput, and records vanish without a trace if the leader is down. acks=1 waits for the leader's local write only, so a leader crash before the followers replicate loses the acknowledged record. acks=all (the default since Kafka 3.0, alongside idempotence) waits for every in-sync replica, and only combined with a broker-side min.insync.replicas=2 does it actually guarantee anything — with min.insync.replicas=1, acks=all degrades to acks=1 the moment followers fall out of the ISR. Retry behaviour is governed by delivery.timeout.ms (default two minutes), the total budget covering batching, all retries and all in-flight time; retries defaults to Integer.MAX_VALUE and the timeout, not the count, is what ends the attempt.

acks=all                       # default in 4.x; needs min.insync.replicas=2 on the topic
retries=2147483647             # bounded by the delivery timeout, not by this count
delivery.timeout.ms=120000     # total budget: batching + retries + in-flight
request.timeout.ms=30000       # per network round trip
max.block.ms=60000             # how long send() may block when the accumulator is full

The idempotent producer: producer ids, sequence numbers and in-flight ordering

Retries create duplicates. The producer sends a batch, the broker writes it, the acknowledgement is lost on the way back, the producer retries, and the same record is appended twice. The idempotent producer fixes this at the protocol level: on initialisation the client is issued a producer id (PID), and every batch carries that PID, the partition, and a monotonically increasing sequence number. The partition leader remembers the last sequence number it accepted per PID, so a replayed batch is recognised and dropped with a duplicate acknowledgement, and a batch that arrives with a gap is rejected outright as out-of-sequence. enable.idempotence=true has been the default since Kafka 3.0 and it costs essentially nothing.

The subtler benefit is ordering. With max.in.flight.requests.per.connection greater than one, several batches for the same partition are on the wire at once; if batch 1 fails and is retried while batch 2 has already been written, the partition ends up with the records in the wrong order — a silent reordering that no error message ever tells you about. Before idempotence, the only safe fix was max.in.flight.requests.per.connection=1, which throttles throughput badly. With idempotence on, the broker uses the sequence numbers to enforce order and to refuse out-of-order batches, so up to five in-flight requests per connection remain both ordered and duplicate-free. Note the scope carefully for interviews: this guarantees exactly-once writes for one producer session to one partition. Cross-partition atomicity and read-process-write atomicity need transactions, which module 04 covers.

enable.idempotence=true                     # default since 3.0
max.in.flight.requests.per.connection=5     # safe up to 5 WHEN idempotence is on
# without idempotence, anything above 1 can reorder a partition after a retry

Batching, linger.ms and compression: the throughput-versus-latency dial

Kafka's throughput comes from amortising per-request overhead across many records, and the two knobs that control it are batch.size (bytes per partition batch, default 16 KB) and linger.ms (how long the accumulator waits for more records before sending, default 0 in older releases and a small non-zero value in recent ones). With linger.ms=0 the sender ships whatever is buffered as soon as it is free, so batches stay small under light load and the producer makes many tiny requests. Raising linger.ms to 5–20 trades a few milliseconds of added latency for dramatically larger batches, better compression ratios and lower broker CPU. This is a genuine tradeoff, not a free win: state which side you are optimising before you touch either value.

Compression is configured with compression.type and — this is the part interviewers probe — it happens on the producer, per batch, not per record. The compressed batch is stored compressed on the broker and shipped compressed to consumers, so one setting reduces network transfer, disk footprint and page-cache pressure simultaneously, and the broker normally does not recompress (it will if the topic's compression.type differs from the producer's, which costs real CPU — keep them aligned). Codec choice is a CPU-versus-ratio decision: lz4 and snappy are fast with modest ratios, zstd compresses considerably harder for more CPU and is usually the best default on modern hardware, and gzip is the slow legacy option. Because compression is per batch, bigger batches compress better — which is why linger.ms and compression.type are tuned together.

batch.size=65536          # bytes per partition batch; larger = better compression
linger.ms=10              # wait briefly to fill batches; the latency you pay
compression.type=zstd     # lz4 / snappy = cheap CPU; zstd = best ratio
buffer.memory=33554432    # total accumulator size before send() blocks

Partitioning: key hashing, the sticky partitioner and custom partitioners

Kafka orders records within a partition and nowhere else, so the partitioner is the component that decides what your ordering guarantee actually means. If a record has a key, the default partitioner takes murmur2(keyBytes) % numPartitions, which means every record with the same key lands on the same partition and is therefore consumed in the order it was produced. That is how you get per-entity ordering — key by orderId, accountId or customerId and every event for that entity is a totally ordered stream, while different entities are processed in parallel. Two consequences to have ready: this hash is computed over the partition count, so adding partitions to a live topic re-maps keys and breaks ordering for existing keys, and a hot key (one huge tenant) puts all of its traffic on one partition regardless of how many you have.

For records with no key, older clients round-robined every record, which scattered a burst across all partitions and produced many small batches. The sticky partitioner instead fills one partition's batch, sends it, then picks a new partition — same uniform distribution over time, far fewer and larger requests, measurably lower latency and CPU. Modern clients go further with a built-in uniform sticky strategy that also prefers partitions whose brokers are keeping up. When neither keyed nor sticky behaviour fits, implement org.apache.kafka.clients.producer.Partitioner and set partitioner.class — legitimate reasons include routing a whale tenant to dedicated partitions, or pinning records to a partition whose consumer holds the relevant local state. You can also override per record by passing an explicit partition number to send().

// keyed: same key -> same partition -> ordered per key
producer.send(new ProducerRecord<>("orders", order.customerId(), payload));

// no key: sticky partitioner batches to one partition, then rotates
producer.send(new ProducerRecord<>("clickstream", payload));

// explicit override beats any partitioner
producer.send(new ProducerRecord<>("orders", 3, order.customerId(), payload));

Consumer groups, the group coordinator and the partition-per-consumer rule

A consumer group is identified by group.id, and its members divide the partitions of the subscribed topics between them: each partition is assigned to exactly one member of the group at a time. That single rule explains most consumer-scaling questions. Scaling out a group beyond the partition count does nothing — a topic with six partitions and ten consumers in one group leaves four consumers permanently idle, so partition count is the hard ceiling on consumer parallelism, chosen at topic-design time. Two different groups reading the same topic each get a full copy of the stream, which is how Kafka does pub/sub without duplicating storage.

Each group is managed by a group coordinator, a broker chosen by hashing the group.id onto a partition of the internal __consumer_offsets topic; that broker owns the group's membership, its committed offsets and its rebalance state. Members find the coordinator with FindCoordinator, join, and then heartbeat to it for the rest of their lives. Because partition count caps parallelism and cannot be reduced, the usual advice is to over-provision partitions modestly at design time rather than plan to add them later: adding partitions changes key-to-partition mapping and therefore breaks per-key ordering for keys already in flight.

Rebalancing: eager, cooperative-sticky and static membership

Whenever membership or subscription changes — a consumer joins, leaves, crashes, or the topic gains partitions — the group must reassign partitions. The classic protocol is eager: every member revokes all its partitions, rejoins, and waits for the leader (one elected consumer) to compute a new assignment and distribute it through SyncGroup. For the duration, the entire group processes nothing. That is the stop-the-world rebalance, and its cost scales with group size, so a rolling restart of a fifty-pod deployment can trigger fifty consecutive full pauses. The built-in eager assignors are RangeAssignor (per topic, partitions dealt in contiguous ranges — skews load when partition counts are not multiples of the member count) and RoundRobinAssignor (even, but reshuffles everything on every change).

The first real fix was incremental cooperative rebalancing (KIP-429): with partition.assignment.strategy=CooperativeStickyAssignor, members keep the partitions they are not losing and only the partitions that actually move are revoked, across two lightweight rounds. Throughput dips instead of stopping. Migrating an existing group to it requires the documented two-rolling-restart procedure, which is a favourite senior-level follow-up. The second fix targets a different cause: static group membership (KIP-345). Give each consumer a stable group.instance.id and the coordinator remembers its identity across a restart, holding its assignment for up to session.timeout.ms instead of rebalancing. On Kubernetes, where pods restart routinely, static membership plus a StatefulSet-derived instance id eliminates the majority of pointless rebalances.

partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
group.instance.id=orders-worker-3   # static membership: survives a restart, no rebalance

KIP-848: the new consumer group protocol in Kafka 4.x

KIP-848 replaces the whole join/sync dance rather than optimising it. In the old protocol the assignment logic lived in a client — the elected group leader — and every membership change forced a global synchronisation barrier that all members had to pass through together. In the new protocol the broker-side group coordinator computes the assignment and drives reconciliation, and members do nothing but send a ConsumerGroupHeartbeat carrying their current state and receive their target state in the reply. There is no group leader, no JoinGroup/SyncGroup round trip, and no global barrier: each member converges to its new assignment independently and asynchronously, so members whose partitions did not move simply keep processing.

Practical consequences worth knowing: rebalances become incremental by construction rather than by choosing the right assignor; session.timeout.ms and heartbeat.interval.ms move to the broker side as group configuration, so consumer-side tuning of those values goes away; and groups scale to far larger member counts than the old protocol tolerated. The protocol is generally available and enabled on the broker by default in Apache Kafka 4.x, with clients opting in via group.protocol=consumer (the legacy behaviour remains available as group.protocol=classic). Because the two protocols can coexist in one group during migration, the sane rollout is to upgrade brokers first, then flip clients group by group.

group.protocol=consumer   # new KIP-848 protocol (broker-driven, incremental)
# group.protocol=classic  # legacy JoinGroup/SyncGroup protocol, still supported
group.id=orders-service

Poll-loop liveness: max.poll.interval.ms versus session.timeout.ms

Two independent timeouts decide whether the coordinator considers a consumer alive, and confusing them causes the single most common Kafka support ticket. session.timeout.ms (default 45 seconds) is about the heartbeat thread: a background thread sends a heartbeat every heartbeat.interval.ms (keep it around a third of the session timeout), and if the coordinator hears nothing for a full session timeout it declares the member dead. That detects crashed processes, network partitions and long stop-the-world garbage collections. max.poll.interval.ms (default 5 minutes) is about the application thread: it is the maximum gap allowed between successive calls to poll(), and it exists precisely because the heartbeat thread keeps beating happily while your business logic is stuck.

Hence the classic bug: a consumer fetches 500 records, each taking a second to process, exceeds the poll interval, and is evicted from the group mid-batch. The group rebalances, another member picks up the same partition, the evicted consumer finally calls poll() and its commit fails with a CommitFailedException — so the batch is reprocessed, the new owner also runs slowly, and the group thrashes in a rebalance loop while lag climbs. The fixes, in order of preference: reduce max.poll.records so a batch fits comfortably inside the interval; move genuinely slow work off the poll thread onto a worker pool (pausing the partitions so you do not simply move the problem); and only then raise max.poll.interval.ms, accepting that a truly hung consumer now takes that much longer to detect.

max.poll.records=100          # cap the batch so processing fits inside the interval
max.poll.interval.ms=300000   # app-thread liveness: max gap between poll() calls
session.timeout.ms=45000      # heartbeat-thread liveness (broker-side in KIP-848)
heartbeat.interval.ms=15000   # roughly one third of the session timeout

Offset commits: auto-commit, sync versus async, and committing after processing

A consumer's position is not broker state pushed at it; it is an offset the consumer itself commits to the __consumer_offsets topic, and the committed value is where a new owner of the partition resumes. Because of that, the commit point relative to your processing is the whole delivery guarantee. Commit after processing and a crash replays the last batch — at-least-once, duplicates possible, which is what almost every system should choose and then make its handlers idempotent. Commit before processing and a crash skips those records — at-most-once, data loss, correct only for genuinely disposable telemetry.

enable.auto.commit=true (the default) commits the offsets returned by the previous poll() on a timer, during a later poll() call — meaning it can commit records that are still in your processing loop. If the process dies after that commit, those records are lost; if it dies just before, they are redelivered. Auto-commit therefore gives you neither guarantee reliably, which is why production consumers usually set it to false and commit explicitly. commitSync() blocks, retries retriable errors, and surfaces failures — use it at safe points and in the finally block on shutdown. commitAsync() does not block and does not retry (a retry could overwrite a newer offset with an older one), so the standard idiom is async commits in the hot loop for throughput plus one final synchronous commit on close. When you need precision, pass an explicit map of partition to offset — remembering that the offset you commit is the next record to read, so it is the last processed offset plus one — and use a ConsumerRebalanceListener to commit in onPartitionsRevoked before losing a partition.

props.put("enable.auto.commit", "false");
try {
    while (running) {
        var records = consumer.poll(Duration.ofMillis(500));
        for (var record : records) handle(record);   // process FIRST
        consumer.commitAsync();                      // then commit: at-least-once
    }
} finally {
    consumer.commitSync();                           // blocking commit on shutdown
    consumer.close();
}

Interview questions

Client configuration is the most heavily mined Kafka topic in Indian product and service-company rounds — consumer-group rebalancing and offset commits come up in almost every interview that mentions Kafka at all:

Beginner What do acks=0, acks=1 and acks=all mean?

They set how much acknowledgement the producer waits for. acks=0: no wait at all, fastest, records lost silently if the broker is down. acks=1: the leader has written it locally, so a leader crash before replication loses the record. acks=all: every in-sync replica has it — the durable option and the default in recent Kafka. Add that acks=all only guarantees durability with min.insync.replicas set to at least 2 on the topic.

Beginner What is a consumer group, and what happens if you run more consumers than partitions?

A consumer group is a set of consumers sharing a group.id that divide the topic's partitions among themselves, each partition owned by exactly one member. Extra consumers beyond the partition count sit idle — partition count is the hard ceiling on parallelism within a group. Different groups reading the same topic each receive the full stream independently.

Beginner How does Kafka decide which partition a record goes to?

If you pass an explicit partition, that wins. Otherwise, with a key, the default partitioner hashes the key (murmur2) modulo the partition count, so equal keys always go to the same partition. With no key, the sticky partitioner fills one partition's batch, sends it, and rotates to another — uniform over time but with far bigger batches than round-robin per record.

Beginner Where are consumer offsets stored, and what does a committed offset actually mean?

In the internal compacted topic __consumer_offsets, keyed by group, topic and partition, managed by the group coordinator. The committed value is the offset of the next record to read — last processed offset plus one — and it is the position a new owner of that partition resumes from after a rebalance or restart.

Intermediate What does enable.idempotence actually prevent, and how?

Duplicate writes caused by producer retries. The producer gets a producer id at start-up and stamps every batch with that id plus a per-partition monotonic sequence number. The partition leader tracks the highest sequence it has accepted per producer id, so a replayed batch is recognised and dropped, and a batch with a gap is rejected. It is per producer session and per partition — cross-partition atomicity needs transactions.

Intermediate How can retries reorder messages, and what stops it?

With max.in.flight.requests.per.connection above 1, batch 2 can be written while batch 1 is being retried, so the partition ends up out of order — silently. Historically the only fix was setting in-flight requests to 1, which hurts throughput. With idempotence enabled the broker enforces sequence-number ordering and rejects out-of-order batches, so up to 5 in-flight requests stay both ordered and duplicate-free.

Intermediate Explain batch.size and linger.ms, and the tradeoff between them.

batch.size is the byte cap on a per-partition batch; linger.ms is how long the accumulator waits for more records before sending an unfilled batch. Raising linger.ms adds a few milliseconds of latency but yields larger batches, fewer requests, better compression ratios and lower broker CPU — the throughput-versus-latency dial. Low-latency services keep it near zero; high-volume pipelines raise it deliberately.

Intermediate Where does compression happen in Kafka, and which codec would you pick?

On the producer, per batch, via compression.type. The batch stays compressed on the broker's disk and is delivered compressed to consumers, so one setting cuts network, disk and page-cache pressure at once; the broker only recompresses if the topic codec differs from the producer's, so keep them aligned. lz4 and snappy are the cheap-CPU choices, zstd gives the best ratio for more CPU and is the usual modern default, gzip is legacy. Bigger batches compress better, so tune it with linger.ms.

Intermediate Why is auto-commit risky, and what do you do instead?

enable.auto.commit=true commits the previous poll's offsets on a timer during a later poll(), with no knowledge of whether you finished processing. Crash after that commit and the in-flight records are lost; crash before and they are redelivered — so it guarantees neither at-most-once nor at-least-once cleanly. Production consumers set it false, process first, then commit — commitAsync() in the loop for throughput and a commitSync() in finally on shutdown.

Intermediate commitSync versus commitAsync — when do you use each?

commitSync() blocks until the broker responds, retries retriable errors, and throws on failure — correct at checkpoints and mandatory in the shutdown path. commitAsync() returns immediately and deliberately does not retry, because a retried stale commit could overwrite a newer offset and cause reprocessing. The standard idiom is async in the hot loop plus one final sync commit on close or on partition revoke.

Pro Your consumers keep getting kicked out of the group and lag keeps growing. Diagnose it.

Almost certainly max.poll.interval.ms exceeded, not a heartbeat problem: the background heartbeat thread is fine while the application thread is stuck processing a large batch, so the coordinator evicts the member for not polling. The partition moves, the evicted consumer's commit fails with CommitFailedException, the batch is reprocessed by the new owner, and the group thrashes. Fix by lowering max.poll.records, moving slow work to a worker pool with the partitions paused, and only as a last resort raising max.poll.interval.ms — which lengthens genuine failure detection.

Pro Difference between max.poll.interval.ms and session.timeout.ms?

session.timeout.ms (default 45s) is heartbeat-thread liveness: no heartbeat for that long and the coordinator declares the member dead — it catches crashes, network partitions and long garbage-collection pauses. max.poll.interval.ms (default 5 minutes) is application-thread liveness: the maximum gap between poll() calls, which catches a consumer that is alive but not making progress. Under KIP-848 the session timeout becomes broker-side group configuration rather than a client property.

Pro What is a stop-the-world rebalance, and how does cooperative-sticky assignment help?

In the eager protocol every member revokes all its partitions, rejoins, and waits for the leader's new assignment through SyncGroup; the whole group processes nothing for the duration, and the cost grows with group size, so a rolling restart triggers one pause per pod. CooperativeStickyAssignor (KIP-429) revokes only the partitions that actually change hands, in two light rounds, so unaffected members keep consuming — throughput dips rather than stopping. Migrating a live group to it needs the documented two-rolling-restart upgrade path.

Pro Your pods restart constantly on Kubernetes and every restart rebalances the group. What would you change?

Enable static group membership (KIP-345): give each consumer a stable group.instance.id — derived from the StatefulSet ordinal, not randomly generated — so the coordinator recognises the returning member and holds its assignment instead of rebalancing, as long as it returns within the session timeout. Combine with cooperative-sticky assignment, or move the group to the KIP-848 protocol where reconciliation is incremental by design.

Pro What changes with the KIP-848 consumer group protocol, and why does it matter?

Assignment moves from an elected client leader to the broker-side group coordinator, and the JoinGroup/SyncGroup barrier is replaced by a ConsumerGroupHeartbeat exchange that reconciles each member's assignment independently and asynchronously. There is no global synchronisation point, so members whose partitions did not move never pause, rebalances are incremental without picking a special assignor, groups scale to far more members, and heartbeat/session tuning becomes broker-side group configuration. It is enabled by default on Kafka 4.x brokers; clients opt in with group.protocol=consumer, and classic remains for the legacy path during migration.

Pro You need strict ordering per customer but also high throughput. How do you design it?

Key by customerId so all events for one customer hash to one partition and are consumed in order, and get parallelism across customers by having many partitions and many consumers. Enable idempotence so retries cannot reorder within a partition. Size partitions for peak parallelism up front, because adding partitions later re-maps keys and breaks ordering for existing ones, and watch for hot keys — one whale customer can saturate a single partition no matter how many you have, which is when a custom partitioner routing that tenant to dedicated partitions earns its keep.
