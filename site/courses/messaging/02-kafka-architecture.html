Module: Kafka Architecture

Kafka is not a queue with extra features. It is a distributed, replicated, append-only commit log that consumers read at their own pace — and once that single idea lands, almost every other behaviour stops being surprising.

Knowledge Library → Courses → Messaging and Event-Driven Systems → Kafka Architecture

What this module covers

Most confusion about Kafka comes from importing expectations built on message brokers. In a broker, a message is delivered and gone; in Kafka a record is written to a file, stays there until a retention policy deletes it, and any number of independent consumers can read it — repeatedly, from wherever they choose. The broker holds the data; the consumer holds the position.

This module works outward from that storage model. First the log itself: topics, partitions, offsets, segments and retention, and why ordering is guaranteed per partition and nowhere else. Then the cluster: brokers, partition leaders and followers, the in-sync replica set, and how acks and min.insync.replicas together define your durability contract. Then KRaft, the controller quorum that replaced ZooKeeper outright in Kafka 4.0. Finally the honest comparison — where log semantics beat queue semantics, where they do not, and how KIP-932 share groups have changed the old answer. Apache Kafka 4.x is current throughout.

Topics

The commit log: topics, partitions, offsets, and why ordering is per partition

A topic is a name; a partition is the actual storage unit. Each partition is an ordered, immutable sequence of records that is only ever appended to, and every record in it gets a monotonically increasing integer — its offset — which is nothing more than its position in that file. There is no global sequence number across a topic, no per-record delete, no in-place update. Reading is a sequential scan from an offset you nominate, which is why Kafka's throughput is bounded by disk and network rather than by broker bookkeeping.

Two consequences interviewers push on constantly. First, ordering is guaranteed within a partition only. A topic with six partitions is six independent logs on possibly six different machines; records that must be processed in order have to land in the same partition, which is what the message key is for — the default partitioner hashes the key, so all events for one orderId or customerId share a partition and therefore an order. Second, partitions are the unit of parallelism: within a classic consumer group a partition is assigned to exactly one consumer, so partition count sets the ceiling on how many consumers can work in parallel. Partition count can be increased later but never decreased, and increasing it re-maps the key hash, so existing keys move to different partitions and their historical ordering relationship breaks.

# A topic is a logical name over N independent ordered logs
$ kafka-topics.sh --bootstrap-server localhost:9092 \
    --create --topic orders --partitions 6 --replication-factor 3

# key -> partition is a hash, so one customer's events stay in one log
# orders-0 : [0][1][2][3] ...   append-only, offsets are positions
# orders-1 : [0][1][2] ...      no ordering relationship with orders-0

Segments and retention: Kafka forgets by clock and by size, not by consumption

A partition is not one enormous file. On disk it is a directory of segments: an active segment being appended to, plus closed segments, each with index files mapping offsets and timestamps to byte positions so a seek is a lookup rather than a scan. A segment rolls when it reaches segment.bytes (1 GiB by default) or when segment.ms elapses (7 days by default). Retention and cleanup then operate a whole segment at a time, which is why the active segment is never deleted and why very small retention windows behave oddly if your segments are large.

The behaviour that most surprises broker veterans: a record is not deleted when it is consumed. Deletion is driven by retention.ms (7 days by default) or retention.bytes, entirely independently of whether anybody read it — a hundred consumer groups can read the same bytes, and a group can rewind and read them again tomorrow. That is what makes replay, reprocessing after a bug fix, and bootstrapping a brand-new consumer from the start of history routine operations rather than recovery projects. The alternative policy, cleanup.policy=compact, keeps the latest record per key forever instead of deleting by age, turning the topic into a durable changelog you can rebuild state from; delete and compact can be combined on one topic.

# Time/size retention: nothing here mentions consumers
retention.ms=604800000        # keep 7 days of history
retention.bytes=-1            # no size cap on the partition
segment.bytes=1073741824      # roll a new segment every 1 GiB
segment.ms=604800000          # ...or every 7 days, whichever comes first
cleanup.policy=delete         # 'compact' keeps the latest value per key instead

Brokers and the cluster: leaders, followers and who is allowed to serve a read

A broker is one Kafka server process holding some subset of the cluster's partitions on its own disks. Partitions are spread across brokers so that a topic's traffic and storage are shared, and each partition has exactly one leader replica plus zero or more follower replicas on other brokers. All producer writes and, by default, all consumer reads go through the leader; followers do nothing but continuously fetch from the leader to stay caught up. They are not a read pool — the optional follower-fetching feature exists for cross-rack locality, but the mental model to carry into an interview is "leader serves, followers replicate".

Leadership is per partition, not per broker, so a healthy cluster has leadership spread evenly and every broker doing real work. When a broker dies, the controller elects new leaders for every partition it led from among the surviving in-sync replicas, and clients discover the change through metadata refresh — which is why producers and consumers only need bootstrap.servers to find one live broker, not a full list. Rebalancing leadership back after a broker returns (preferred leader election) matters operationally, because a cluster where one broker leads most partitions is a cluster with a hot node.

$ kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders
Topic: orders  PartitionCount: 6  ReplicationFactor: 3
  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3   # fully replicated
  Partition: 1  Leader: 2  Replicas: 2,3,1  Isr: 2,3     # broker 1 lagging
  Partition: 2  Leader: 3  Replicas: 3,1,2  Isr: 3,1,2

Replication, ISR, acks and min.insync.replicas: the durability contract

The replication factor says how many copies of each partition exist. The in-sync replica set (ISR) says how many of them are currently caught up — a follower stays in the ISR while it keeps fetching within replica.lag.time.max.ms, and is ejected when it falls behind or its broker dies. A record is committed, and therefore visible to consumers, only once every member of the current ISR has it. That is the crucial subtlety: the ISR shrinks and grows dynamically, so "replicated" always means "replicated to whoever is in sync right now", not "replicated three times".

Durability is then the product of two settings that only make sense together. The producer's acks chooses what it waits for: 0 is fire-and-forget (fastest, loses data on any hiccup), 1 waits for the leader's local write only (a leader crash before replication loses the record), and all/-1 waits for every in-sync replica. The topic's min.insync.replicas then sets the floor — with acks=all, if the ISR has fewer members than that floor the broker rejects the write with NotEnoughReplicas rather than silently accepting a poorly replicated record. Its default is 1, which is why the standard production recipe is stated explicitly: replication factor 3, min.insync.replicas=2, acks=all — survives one broker loss with no data loss and no write outage, and fails fast rather than lying when two brokers are gone.

The escape hatch is unclean.leader.election.enable. Left at its default of false, a partition whose entire ISR is unavailable simply stops serving until an in-sync replica returns: you choose consistency over availability. Set it to true and Kafka will promote an out-of-sync replica, restoring availability at the cost of silently discarding whatever records the old leader had that the new one never received. Kafka 4.x adds Eligible Leader Replicas, which tracks replicas known to hold all committed data so recovery has more safe candidates before that trade-off is forced.

# Topic side: floor on how replicated a write must be
replication.factor=3
min.insync.replicas=2               # default is 1 -- set this deliberately
unclean.leader.election.enable=false # prefer unavailable over silently lossy

# Producer side: what the client waits for
acks=all                            # every in-sync replica, not "all 3 replicas"
enable.idempotence=true             # no duplicates from producer retries
retries=2147483647
max.in.flight.requests.per.connection=5   # safe ordering when idempotence is on

KRaft: the controller quorum that replaced ZooKeeper — and its removal in Kafka 4.0

Something has to hold cluster metadata: which topics exist, how many partitions they have, where every replica lives, which broker leads what. For a decade that job belonged to an external ZooKeeper ensemble, with a single elected Kafka controller reading from it and pushing updates to brokers. It worked, but it meant a second distributed system to install, secure, monitor and upgrade; controller failover required reloading all metadata from ZooKeeper, so recovery time grew with cluster size; and partition counts hit a practical ceiling in the tens of thousands.

KRaft (KIP-500) removes that dependency by storing metadata in Kafka itself. A quorum of controller nodes runs a Raft implementation over an internal metadata topic, so the metadata log is replicated by the same mechanism as everything else. Brokers no longer query an external store — they follow the metadata log and keep a local cached copy, so a controller failover is a leader election on a log the followers already have, and it completes in a fraction of the old time. The result is fewer moving parts, faster metadata propagation, a much higher partition ceiling (millions rather than tens of thousands), and one security and configuration model instead of two.

Know the timeline, because interviewers date candidates by it: KRaft arrived as a preview in Kafka 2.8, became production-ready in 3.3, ZooKeeper mode was deprecated in 3.5, 3.9 was the last release that could run ZooKeeper or bridge a migration, and Kafka 4.0 (March 2025) removed ZooKeeper mode entirely — KRaft is now the only mode. Operationally, nodes take a process.roles of broker, controller or both (combined mode is for development; production separates them), the cluster is formatted once with a generated cluster id, and every node is told the controller quorum's voter list. Upgrading a pre-4.0 cluster means migrating to KRaft on 3.9 first; there is no direct ZooKeeper-to-4.x jump.

# Dedicated controller node (production separates roles)
process.roles=controller
node.id=1
controller.quorum.voters=1@ctrl-1:9093,2@ctrl-2:9093,3@ctrl-3:9093
controller.listener.names=CONTROLLER

# Broker node in the same cluster
process.roles=broker
node.id=101
controller.quorum.voters=1@ctrl-1:9093,2@ctrl-2:9093,3@ctrl-3:9093

# One-time format; no ZooKeeper connect string exists any more in 4.x
$ kafka-storage.sh format --cluster-id "$(kafka-storage.sh random-uuid)" \
    --config config/server.properties

Log semantics vs queue semantics: when Kafka is the right tool

In a classic queue broker the message is the unit of state. It is enqueued, dispatched to one consumer, acknowledged, and deleted; the broker tracks per-message delivery, redelivery and dead-lettering, and the queue is a work list that drains. In Kafka the log is the unit of state. A record is written once, read by any number of independent consumer groups, and deleted only by retention policy; the broker tracks almost nothing per consumer beyond a committed offset. Replay is not a feature bolted on — it is just seeking backwards in a file that was never erased.

That difference decides the tool. Kafka wins when you need high sustained throughput on a few topics, durable history you can re-read, multiple unrelated consumers of the same stream, strict per-key ordering, stream processing and joins over the data, or an audit trail of what happened. A queue broker wins when the work items are independent tasks with wildly varying durations, when you want many more workers than you have partitions, when you need per-message acknowledgement, per-message TTL, priorities or delayed delivery, or when flexible routing topologies (fanout, headers, per-consumer filtering) are the point. Be honest about the costs too: Kafka's parallelism is capped by partition count, one slow record blocks its partition behind it (head-of-line blocking), and it has historically had no notion of acknowledging one message out of order.

Share groups (KIP-932): queue semantics inside the log

KIP-932 adds a second consumption model alongside the classic consumer group. A share group lets many consumers read the same partition cooperatively rather than dividing partitions exclusively between them, so the number of workers is no longer capped by the partition count — the single most quoted reason to reach for RabbitMQ instead of Kafka. Records are acquired individually under a time-limited lock, moving through Available, Acquired, Acknowledged and Archived states with a delivery count attached, and each one is acknowledged, released or rejected on its own. Delivery is at-least-once and ordering is explicitly not preserved, because that is exactly the trade a work queue wants.

The consumer API is a distinct KafkaShareConsumer, and a group is created with group.type=share; share-group state lives in an internal topic on the brokers, so nothing about the topic's own storage changes — the same topic can be read by a classic consumer group and a share group at once, one for the ordered stream and one for the work queue. Get the release history right: early access in Kafka 4.0, preview in 4.1, and completed in Kafka 4.2 (February 2026), which is when it became usable in earnest. This genuinely updates the old "use a queue broker for work queues" advice — if you already run Kafka, a share group may now remove the need for a second broker rather than merely approximate it. It does not make the older advice worthless: routing topologies, priorities, delayed delivery and per-message TTL are still AMQP's home ground.

// Queue-like consumption: more consumers than partitions is fine,
// and each record is acknowledged on its own.
var consumer = new KafkaShareConsumer<String, String>(props);
consumer.subscribe(List.of("tasks"));

for (var record : consumer.poll(Duration.ofSeconds(5))) {
    try {
        handler.process(record.value());
        consumer.acknowledge(record, AcknowledgeType.ACCEPT);
    } catch (TransientFailure e) {
        consumer.acknowledge(record, AcknowledgeType.RELEASE); // redeliver
    } catch (PoisonRecord e) {
        consumer.acknowledge(record, AcknowledgeType.REJECT);  // never again
    }
}
consumer.commitSync();

Interview questions

Kafka architecture is the highest-yield messaging round in Indian product and service-company interviews. Partition-and-ordering and ISR-and-acks come up in almost every one; the later questions are where senior candidates are separated:

Beginner What is a topic, a partition and an offset?

A topic is a named category of records. It is physically split into partitions, each an ordered, immutable, append-only log stored on a broker's disk. An offset is a record's position within one partition — a monotonically increasing integer, unique per partition, not across the topic. Consumers read by advancing an offset; producers only ever append.

Beginner Does Kafka guarantee message ordering?

Only within a single partition. Across partitions there is no ordering guarantee at all, because they are independent logs on possibly different brokers. To get ordering for a business entity, give related records the same key — the default partitioner hashes the key so all of that customer's or order's events land in one partition and are consumed in sequence.

Beginner What is a broker, and what does the replication factor mean?

A broker is one Kafka server holding a subset of the cluster's partitions on its own disks. Replication factor is how many copies of each partition exist across different brokers — factor 3 means one leader and two followers. Producers write to the leader and followers replicate from it; if the leader's broker fails, one of the in-sync followers is elected leader.

Beginner Is a message deleted after it is consumed?

No. Kafka deletes by retention policy — retention.ms (7 days by default) or retention.bytes — regardless of who has read what. Consumption only advances an offset. That is why many independent consumer groups can read the same records, and why replaying history after a bug fix is trivial. With cleanup.policy=compact, Kafka instead keeps the latest record per key indefinitely.

Intermediate What is the ISR, and when does a replica leave it?

The in-sync replica set is the subset of a partition's replicas — including the leader — that are currently caught up with the leader. A follower drops out when it has not fetched up to the leader's log end within replica.lag.time.max.ms, or when its broker dies, and rejoins once it catches up. A record counts as committed, and becomes visible to consumers, only after every current ISR member has it.

Intermediate Explain acks=0, acks=1 and acks=all.

acks=0: the producer does not wait at all — highest throughput, records lost on any failure. acks=1: waits for the leader's local write only, so a leader crash before followers replicate loses the record. acks=all (or -1): waits until every in-sync replica has it. Note that "all" means all replicas currently in the ISR, not all configured replicas, which is exactly why it must be paired with min.insync.replicas.

Intermediate Why is acks=all alone not enough for durability?

Because the ISR can shrink. If two of three replicas fall behind, the ISR is just the leader, and acks=all is satisfied by that one copy — a leader crash then loses the record. Setting min.insync.replicas=2 makes the broker reject the write with NotEnoughReplicas instead. The standard production recipe is replication factor 3, min.insync.replicas=2, acks=all: survives one broker loss with no data loss and no write outage.

Intermediate What is unclean leader election and would you enable it?

It allows an out-of-sync replica to become leader when the whole ISR is unavailable. That restores availability but silently discards any records the old leader had which the new one never received. The default is false — the partition simply stops serving until an in-sync replica returns. Leave it false for anything financial or transactional; consider true only for streams where a gap is preferable to an outage, such as raw telemetry.

Intermediate Why can't you decrease the partition count, and what breaks when you increase it?

Decreasing would mean deleting or merging append-only logs and destroying their offsets, so Kafka simply does not support it. Increasing is allowed but changes the key-to-partition hash: new records for an existing key can be routed to a different partition from the one holding its history, so per-key ordering across the change is broken and any partition-local state is invalidated. Size partitions up front, or key by something you can re-partition safely.

Intermediate What replaced ZooKeeper, and in which release did ZooKeeper disappear?

KRaft (KIP-500) — a quorum of controller nodes running Raft over an internal metadata topic inside Kafka itself. KRaft was production-ready in 3.3, ZooKeeper mode was deprecated in 3.5, and 3.9 was the last release supporting it or a migration bridge. Kafka 4.0 (March 2025) removed ZooKeeper mode entirely, so 4.x runs KRaft only. Upgrading an old cluster means migrating to KRaft on 3.9 first.

Pro What does KRaft actually improve, beyond removing a dependency?

Metadata becomes a replicated log that brokers follow and cache locally, rather than external state a new controller must reload. So controller failover is a log leader election measured in a fraction of the old time, metadata propagates as incremental deltas instead of full pushes, and the practical partition ceiling rises from tens of thousands to millions. Operationally it collapses two systems into one: one config model, one security model, one thing to monitor and upgrade.

Pro Kafka is described as a log, not a queue. What follows from that in practice?

Records are retained after consumption, so many independent consumer groups can read the same stream and any of them can rewind and replay. The broker stores almost no per-consumer state beyond a committed offset, which is why it scales to enormous fan-out. But it also means no per-message acknowledgement in a classic consumer group, no per-message TTL or priority, ordering only within a partition, head-of-line blocking when one record is slow, and parallelism capped by partition count.

Pro You need 200 workers on a topic with 12 partitions. What are your options in Kafka 4.x?

With a classic consumer group, 12 is the ceiling — the extra 188 consumers sit idle — so historically you would either raise the partition count or hand the work to a queue broker. Kafka 4.x offers a third answer: a share group (KIP-932), where many consumers cooperatively read the same partitions with per-record acquisition locks and individual acknowledgement, decoupling worker count from partition count. The trade is that ordering is not preserved and delivery is at-least-once, which is fine for independent work items.

Pro Do share groups make RabbitMQ redundant?

Not redundant, but they narrow the gap considerably. Share groups give Kafka per-message acknowledge, release and reject, delivery counting for automatic poison handling, and scaling past the partition count — the main historical reasons to add a queue broker beside Kafka. What AMQP still does better is flexible routing (topic, fanout and header exchanges), priorities, delayed delivery, per-message TTL and per-consumer filtering. If you already run Kafka, evaluate share groups before adding a second broker; if you need rich routing, RabbitMQ is still the better fit.

Pro How is a partition laid out on disk, and why does that matter for performance?

Each partition is a directory of segment files plus offset and timestamp indexes. Writes are sequential appends into the active segment; retention and compaction delete or rewrite whole closed segments, never individual records. Sequential I/O plus the operating system's page cache means reads of recent data usually never touch disk, and Kafka can hand bytes to the network without copying them through user space. This is why the design's throughput comes from doing less work per record, not from clever indexing.
