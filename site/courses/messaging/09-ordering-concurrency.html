Module: Ordering and Concurrency

Ordering and parallelism pull in opposite directions. Every message system lets you have both, but only along an axis you choose in advance — and most production messaging bugs live in the gap between the ordering you were promised and the ordering your consumer actually preserved.

Knowledge Library → Courses → Messaging and Event-Driven Systems → Ordering and Concurrency

What this module covers

Two forces are in permanent tension here. Strict ordering means one message is processed at a time, in sequence — which is a single-threaded system, however many machines you own. Parallelism means many messages in flight at once, which by definition means they can complete out of order. Nothing in Kafka 4.x or RabbitMQ 4.x resolves that tension; both simply give you a way to draw the boundary between the two, and the boundary is the entity key.

So this module starts by narrowing the requirement — global total ordering across a topic is almost never what the business actually needs — then covers how each broker delivers per-key ordering and what it costs. The second half is the hazards: retries that reorder, in-flight producer requests, consumer-side threading, and rebalances that redeliver. Those are where the interview questions and the production incidents both come from, so it ends with the mitigations and an honest verdict on what ordering is worth paying for.

Topics

Narrowing the requirement: per-entity ordering, not global ordering

The first thing to do when someone says "the messages must be in order" is to ask which messages. A total order across an entire topic — every event from every producer sequenced against every other — is a genuinely expensive thing to ask for: it forces a single writer, a single log and a single consumer, and it caps your whole pipeline at what one thread can process. Almost no business rule needs it. What the business needs is that all events for order 12345 are applied in sequence (created, then paid, then shipped, then delivered), while order 67890 proceeds completely independently on another thread, another machine, another rack.

That reframing is the whole design. Once ordering is scoped to an entity, the entity id becomes the unit of serialisation and everything else becomes parallel: throughput scales with the number of distinct entities, not with the number of messages. Azure's architecture catalogue names this the sequential convoy — a stream of related messages that must stay in order, interleaved freely with other convoys. Get the interviewer to agree on the convoy key first; every subsequent answer about partitions, queues and consumers falls out of it.

Kafka: the key picks the partition, the partition owns the order

Kafka's guarantee is narrow and precise: messages sent by a producer to a particular topic partition are appended to that partition's log in the order they are sent, a consumer sees records in the order they are stored in the log, and no ordering is promised between partitions at all. There is no global sequence number across a topic. Everything you build on top of Kafka ordering is an application of that one sentence.

The bridge from "order within a partition" to "order per entity" is the record key. The default partitioner hashes the key (murmur2, modulo the partition count) and routes every record with the same key to the same partition, so choosing the entity id as the key buys per-key ordering for free. No key means round-robin or sticky batching, and therefore no ordering at all. Two consequences follow immediately: the key must be genuinely stable for the lifetime of the entity (customer id, order id, account number — never a timestamp or a request id), and one partition is only ever read by one consumer within a group, so per-key order survives all the way to your handler as long as the handler itself is sequential.

// The key is the ordering contract. Same key -> same partition -> same order.
var record = new ProducerRecord<>("orders", order.id(), event);  // key = entity id
producer.send(record);

// No key = round-robin/sticky batching = no ordering guarantee whatsoever.
producer.send(new ProducerRecord<>("orders", null, event));

What per-key ordering costs: parallelism ceilings, hot partitions, and the rehash

Per-key ordering is not free, and the bill arrives in three instalments. First, the partition count is a hard ceiling on consumer parallelism: a consumer group can never usefully run more consumers than there are partitions, so a topic with six partitions gives you six concurrent processors and any extra pods sit idle. Second, keys are rarely uniform. One tenant, one merchant or one celebrity account can send a disproportionate share of traffic; because that key always hashes to the same partition, you get a hot partition whose consumer lags while the other five idle. The usual fixes are compound keys that add a bounded salt (accepting order only within the salted sub-key), a custom partitioner that spreads known-hot keys, or simply more partitions so the hash spreads further.

Third, and most commonly asked: adding partitions to an existing topic changes the modulo, so a key that used to hash to partition 2 may now hash to partition 5. Old messages do not move — Kafka never rewrites the log — so for a window of time the history of an entity is split across two partitions with no ordering relationship between them, and a consumer can process the entity's new event before its older one. Partition counts also cannot be reduced. The practical rules: over-provision partitions at topic creation rather than scaling later, and if you must add partitions to a keyed topic, do it during a quiet period after draining, or produce to a new topic and migrate consumers.

# Adding partitions rehashes keys. On a keyed topic this breaks per-key
# ordering for entities that already have messages in the log.
kafka-topics.sh --bootstrap-server broker:9092 \
  --alter --topic orders --partitions 12

# Partition counts only go up, never down.

RabbitMQ: competing consumers, consistent-hash routing and single active consumer

A RabbitMQ queue is FIFO — messages leave it in the order they entered. That guarantee survives exactly as long as there is one consumer. Attach a second consumer to the same queue and you have the competing-consumers pattern: the broker round-robins deliveries, the two consumers run at different speeds, and message two can commit before message one. Requeues make it worse, because a negatively acknowledged message returns to the queue and is redelivered after messages that were behind it. So in AMQP the question is never "is the queue ordered?" but "how do I keep one consumer per entity?"

There are two production answers. The consistent hash exchange plugin (x-consistent-hash) is RabbitMQ's partitioning: it hashes the routing key, the message id or a chosen header and routes each message to exactly one bound queue, so all events for an entity land in the same queue and each queue gets a single consumer — a hand-rolled equivalent of Kafka partitions, with the same rehash caveat when you add or remove queues. Alternatively, single active consumer (the x-single-active-consumer queue argument, available on classic and quorum queues) lets you register many consumers on one queue while the broker delivers to only one of them at a time, promoting another automatically if the active one dies. That gives ordered processing plus hot-standby failover without the client-side coordination. Streams have their own single-active-consumer mode, and superstreams extend it to partitioned streams for the same reason Kafka partitions exist.

// One consumer at a time on this queue; others stand by for failover.
channel.queueDeclare("orders.q", true, false, false,
    Map.of("x-single-active-consumer", true,
           "x-queue-type", "quorum"));

// Or partition by entity: consistent-hash exchange fans one key to one queue.
channel.exchangeDeclare("orders.x", "x-consistent-hash");
channel.queueBind("orders.q0", "orders.x", "1");   // binding weight

Producer-side hazards: retries, in-flight requests and idempotence

Here is the reordering that surprises people most, because it happens before a consumer is even involved. Suppose the producer has several requests in flight to the same partition. Batch A fails with a retriable error and is scheduled for retry; batch B, sent immediately after, succeeds on its first attempt. The retried A now lands after B, and the log — the thing that defines the order — has them the wrong way round. Nothing downstream can detect this, because from Kafka's point of view the log is simply what it is.

The knob is max.in.flight.requests.per.connection. Setting it to 1 makes reordering impossible at a real throughput cost, since the producer cannot pipeline. The modern answer is better: turn on enable.idempotence (the default in Kafka 3.0 and later, including 4.x), which stamps each batch with a producer id and sequence number so the broker rejects duplicates and refuses out-of-sequence batches, preserving order with up to five in-flight requests. Idempotence requires acks=all and pairs naturally with a bounded delivery.timeout.ms. Note what this does not cover: application-level retries where your own code catches an exception and calls send again are just a new record, and they land wherever they land.

# Ordering-safe producer (defaults in Kafka 4.x, but state them explicitly)
enable.idempotence=true
acks=all
max.in.flight.requests.per.connection=5   # safe only with idempotence on
retries=2147483647
delivery.timeout.ms=120000

# Without idempotence, the only ordering-safe value is 1.

Consumer-side hazards: threads, async handoff and rebalance redelivery

The broker can hand you a perfectly ordered stream and your application can still destroy it in three lines. The most common way is concurrency inside one consumer: a Spring Kafka listener container with a concurrency setting above one, or a handler that submits each record to a thread pool or an executor and returns immediately. The poll loop then races ahead, records from the same partition are processed simultaneously, and the ordering the partition gave you is gone — silently, because nothing throws. The same applies to any "process asynchronously after the poll" design, including reactive pipelines that subscribe without ordering operators and code that fires a CompletableFuture per record.

The second family is rebalancing and redelivery. When a consumer group rebalances — a pod restarts, a deploy rolls, a poll exceeds max.poll.interval.ms — partitions move to other consumers and anything processed but not committed is delivered again, possibly after newer records have already been handled elsewhere. At-least-once delivery therefore implies duplicates, and duplicates arriving late are functionally identical to reordering. On the RabbitMQ side, a basic.nack with requeue puts a message back behind messages that were originally after it. The mitigations are structural: keep processing sequential per partition (Kafka's own recommendation is one thread per partition, or a keyed executor that always maps a key to the same thread), keep handlers fast enough not to trip the poll interval, and commit only after the work is genuinely done.

// Destroys per-partition ordering: records race inside the pool.
for (var record : records) pool.submit(() -> handle(record));

// Preserves it: same key always lands on the same single-threaded worker.
for (var record : records) {
    int slot = Math.floorMod(record.key().hashCode(), workers.length);
    workers[slot].submit(() -> handle(record));   // each worker is single-threaded
}

Mitigations, and the honest verdict on what ordering is worth

Because perfect ordering is expensive and imperfect ordering is inevitable, the durable engineering answer is to make consumers tolerant of disorder rather than to chase a guarantee end to end. Four techniques cover most cases. Make handlers commutative where the domain allows it, so "add 10 credits" and "add 5 credits" give the same result in either order. Make them idempotent, keyed on an event id, so a redelivery is a no-op. Carry a monotonically increasing version or sequence number on the entity and drop any update whose version is not greater than the stored one — last-write-wins by version, which is exactly the discipline Kafka's own log compaction applies to keys. And model the entity as a state machine that rejects invalid transitions, so a "shipped" event arriving before "paid" is parked or replayed rather than silently applied.

The verdict worth stating out loud in a design review: ordering guarantees you do not need are throughput you are throwing away. A single partition gives you a perfect total order and a hard throughput ceiling of one consumer. Per-key ordering costs you nothing you were using and scales with your key cardinality. And where even per-key ordering is more than the domain requires, dropping it entirely — plus idempotent, version-guarded handlers — buys you unlimited parallelism. Newer options change the arithmetic rather than the tradeoff: the Confluent Parallel Consumer subdivides work below the partition into key-order or message-order units, and Kafka's share groups (queue semantics) deliberately give up ordering to remove the partition-count ceiling for work-queue style consumers.

-- Version guard: a stale or duplicated event updates nothing.
UPDATE orders
   SET status = :status, version = :event_version
 WHERE id = :order_id
   AND version < :event_version;
-- 0 rows affected = event arrived late or twice. Log it, do not fail.

Interview questions

Ordering is the highest-signal Kafka topic in Indian product and service-company rounds — the partition-key question is asked almost every time, and the follow-ups about adding partitions and about retries are what separate candidates who have operated a cluster from candidates who have read a blog post:

Beginner How do you guarantee message ordering in Kafka?

Kafka guarantees order only within a partition, never across partitions. So you guarantee ordering by making all messages that must be ordered together land in the same partition — set the record key to the entity id (order id, customer id, account number) and the default partitioner hashes it to a fixed partition. Because one partition is consumed by exactly one consumer in a group, that order survives to your handler, provided the handler processes records sequentially. Global ordering across a whole topic requires a single partition, which caps throughput at one consumer.

Beginner What happens to ordering when you add partitions to an existing topic?

It breaks for entities that already have data. Adding partitions changes the modulo in the hash, so a key that used to map to partition 2 may now map to partition 5. Existing messages are never moved — Kafka does not rewrite the log — so an entity's history is split across two partitions with no ordering relationship between them, and a consumer can see a newer event before an older one. Partition counts also cannot be reduced. Over-provision at creation; if you must scale later, do it after draining during a quiet window, or produce to a new topic and migrate consumers.

Beginner What happens if you send a Kafka message without a key?

The partitioner has nothing to hash, so records are spread across partitions by round-robin or sticky batching for throughput. You get maximum parallelism and zero ordering guarantee between those records. That is correct for independent events such as metrics or clickstream, and wrong for anything where a later event supersedes an earlier one.

Beginner Is a RabbitMQ queue ordered?

A queue is FIFO, but only with a single consumer. Attach several consumers and the broker round-robins deliveries; they process at different speeds and finish out of order — the competing-consumers pattern. Requeue on a negative acknowledgement also puts a message back behind messages that were originally after it. To keep order you need either one queue per entity, or the single-active-consumer flag.

Intermediate How many consumers can read one topic in parallel, and why?

Within one consumer group, at most one consumer per partition — so the partition count is a hard ceiling on useful parallelism. Six partitions means six working consumers; a seventh pod is assigned nothing and idles. Different consumer groups read the same topic independently, so the limit is per group. This is the direct cost of the ordering model: the unit of ordering and the unit of parallelism are the same object.

Intermediate One tenant sends most of your traffic and its partition lags. What do you do?

That is a hot partition caused by skewed key distribution — the hash always sends that key to the same place. Options, in rough order of preference: use a compound key that appends a bounded salt for the hot key only, accepting ordering within the salted sub-key; write a custom partitioner that spreads known-hot tenants across several partitions; raise the partition count so the hash spreads further (with the rehash caveat); or isolate the noisy tenant onto its own topic with its own consumers. Whichever you pick, be explicit about what ordering guarantee you just gave up.

Intermediate What does single active consumer do in RabbitMQ, and when would you use it?

With x-single-active-consumer set on the queue, many consumers can register but the broker delivers to only one of them at a time; if that consumer dies or is cancelled, the broker promotes another automatically. It gives ordered, serialised processing plus hot-standby failover without any client-side leader election. It is available on classic and quorum queues, and streams have their own equivalent. Use it when a queue represents one entity or one ordered workflow; combine it with a consistent-hash exchange when you need many such queues.

Intermediate What is the RabbitMQ equivalent of Kafka partition keys?

The consistent hash exchange plugin. Declare an exchange of type x-consistent-hash, bind several queues to it with weights, and the exchange hashes the routing key (or a message property or header) to route each message to exactly one queue. All events for one entity therefore share a queue, and one consumer per queue preserves order. The caveat mirrors Kafka's: adding or removing bound queues changes the hash ring and moves keys, so ordering is disturbed for entities in flight.

Intermediate Your Spring Kafka listener has concurrency set to five and ordering broke. Explain.

Concurrency spawns multiple listener containers, each with its own consumer, and partitions are split across them — that alone is fine, because each partition still goes to exactly one thread. Ordering breaks when concurrency exceeds the partition count in ways that cause repeated rebalances, or, far more commonly, when the handler hands work off asynchronously to an executor or a reactive pipeline so records from the same partition run concurrently. The rule is one sequential worker per partition or per key; parallelism above that must be keyed, not free.

Pro How can a producer retry reorder messages, and what config prevents it?

With more than one request in flight to a partition, batch A can fail and be queued for retry while batch B succeeds immediately, so A is appended after B and the log is permanently wrong. Setting max.in.flight.requests.per.connection=1 prevents it by disabling pipelining, at a real throughput cost. The better fix is enable.idempotence=true — the default since Kafka 3.0 and in 4.x — which stamps batches with a producer id and sequence number so the broker rejects duplicates and out-of-sequence batches, keeping order safe with up to five in-flight requests. It requires acks=all. It does not cover retries you perform yourself in application code.

Pro Message A fails and goes to a retry topic; message B for the same key succeeds. Now what?

You have reordered your own stream: B is applied before A, and if A was "address changed" and B was "order shipped", the shipment used the old address. Non-blocking retry topics buy throughput by explicitly giving up ordering. The choices are: block the partition until A succeeds (ordering preserved, head-of-line blocking, lag grows); route A to a retry topic and accept disorder, then make handlers version-guarded so a stale A is dropped; or park the whole key — stop processing that entity and send subsequent messages for it to the same parking area until A is resolved. Say which one you chose and why; interviewers are testing whether the candidate recognises that the tradeoff exists at all.

Pro Design an order-processing consumer that tolerates out-of-order and duplicate events.

Four layers. Idempotency: deduplicate on an event id, so a redelivery is a no-op. Versioning: every event carries a monotonically increasing entity version, and the write is conditional — update only where the stored version is lower — so stale events affect nothing. State machine: the entity rejects invalid transitions, so "shipped" before "paid" is parked rather than applied. Commutativity: prefer operations whose result does not depend on order, such as set-membership or additive counters. With those in place, ordering becomes an optimisation rather than a correctness requirement, which is precisely the position you want to be in during an incident.

Pro Can you process a single partition in parallel and still keep per-key order?

Yes, if you shard below the partition. Map each record's key onto a fixed set of single-threaded workers — worker index equals the key hash modulo the worker count — so the same key always runs on the same thread while different keys run concurrently. Offsets must then be committed only up to the lowest continuously completed offset, not the highest, or a crash loses records. This is what the Confluent Parallel Consumer implements as key-order or message-order processing, and it is the standard answer when the partition count is fixed but you need more throughput, especially with slow input-output-bound handlers.

Pro When would you deliberately give up ordering entirely?

When the domain does not need it and the cost is real: independent work items, notifications, metrics, thumbnail generation, anything where each message stands alone. Ordering guarantees you do not need are throughput you are throwing away — they force a serialisation point, cap consumer count at the partition count, and create hot partitions from skewed keys. Kafka's share groups (queue semantics) exist precisely for this case, letting many consumers share a partition without an ordering promise. The discipline is to make the choice explicitly and write it down, rather than inheriting a keyed topic nobody can safely repartition three years later.
