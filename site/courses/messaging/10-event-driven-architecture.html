Module: Event-Driven Architecture

Nine modules of brokers, partitions, acknowledgements and retries all lead here. This closing module is about the architecture the machinery serves — and about the fact that "we're event-driven" is a sentence that means at least four incompatible things.

Knowledge Library → Courses → Messaging and Event-Driven Systems → Event-Driven Architecture

What this module covers

Every previous module in this track was about mechanism: how a broker stores a message, how a consumer group rebalances, how a poison message ends up in a parking lot. This one is about intent. Two teams can both run Kafka, both call their system event-driven, and have built architectures with almost nothing in common — different coupling, different failure modes, different answers to "where does the truth live?".

We separate the patterns properly, then spend most of the module on the thing that actually decides whether an event system stays maintainable: event design. Names, granularity, identity, time, and schema evolution. We finish with a choreographed order flow read end to end, and an honest account of where choreography hurts and what to reach for instead — because the senior answer to "should this be an event?" is very often no.

Topics

"Event-driven" means at least four different things

Martin Fowler's central observation, first made in a 2017 GOTO talk and then written up, is that "event-driven" is a phrase people use to mean radically different architectures, and the confusion is expensive: a design review where one person means "we publish a notification on a topic" and another means "the event log is our database" produces agreement that evaporates in implementation. He separates four patterns — event notification, event-carried state transfer, event sourcing and CQRS — and the useful discipline is to name which one you mean, every time.

They are not a maturity ladder. You do not graduate from notification to event sourcing; they solve different problems, they can coexist in one estate, and picking the heaviest one because it sounds most advanced is the most common architectural mistake in this space. Two axes distinguish them: how much state travels in the event, and whether the event stream is the system of record or a derivative of it.

Event notification: the thin signal

The producer publishes a small message saying something happened — typically a type, an entity id, a timestamp and very little else — and any consumer that needs detail calls back to the producer's API to fetch it. The customer service emits CustomerAddressChanged carrying a customer id; the insurance quoting service hears it, then issues an HTTP request for the new address. The producer never learns who is listening, which is the whole appeal: you can add a fifth consumer on Monday and the producing team need not be told.

The cost is subtle and it is the reason Fowler flags this pattern as the one that quietly rots. Because the event carries almost nothing, the real behaviour lives in the callbacks, so there is no single artefact — no code, no schema, no diagram — that tells you what happens when an address changes. You have decoupled the data shape but not the runtime: if the producer is down when the consumer calls back, the consumer is stuck holding an event it cannot process. And a notification fan-out of twenty consumers each calling back immediately is a self-inflicted thundering herd against the very service that just did work.

  "type": "CustomerAddressChanged",
  "schemaVersion": 1,
  "customerId": "CUST-88213",
  "occurredAt": "2026-07-25T09:14:02.318Z"
}
// consumer must now GET /customers/CUST-88213 to learn the new address

Event-carried state transfer: shipping the state with the news

Here the event carries enough state that consumers never call back. CustomerAddressChanged ships the new address — and, in the fatter variants, the whole customer record. Consumers keep a local read-only replica of exactly the fields they care about and serve their own queries from it. The producer's availability stops being on your critical path: it can be down for an hour and the quoting service keeps quoting, because it already holds everything it needs.

You pay for that in three currencies. Duplication: the same customer data now lives in six services, and someone will eventually ask which copy is right. Staleness: local replicas are eventually consistent, so a consumer can act on an address that changed two seconds ago — usually fine for a quote, never fine for a fraud check. Contract surface: every field you put in the event is a field consumers will depend on and you must version forever, which is why "just publish the whole entity" is a trap. Publish the fields the business fact needs, not the row.

{
  "eventId": "b3a70c46-1f8c-4c1a-9c0e-6d3e21ac54f2",
  "type": "CustomerAddressChanged",
  "schemaVersion": 2,
  "customerId": "CUST-88213",
  "address": { "line1": "14 MG Road", "city": "Bengaluru", "pin": "560001", "country": "IN" },
  "previousPin": "560034",
  "occurredAt": "2026-07-25T09:14:02.318Z",
  "recordedAt": "2026-07-25T09:14:02.907Z"
}
// consumer updates its local replica; no callback, no coupling to producer uptime

Event sourcing and CQRS: when the log is the system of record

Event sourcing inverts the relationship between state and events. In the previous two patterns the database is the truth and events are announcements about it; here the append-only sequence of events is the truth, and current state is a fold over that sequence. Nothing is updated in place and nothing is deleted — a cancelled order is an OrderCancelled event appended after OrderPlaced, not a row flipped to status = 'CANCELLED'. That gives you a complete audit trail for free, the ability to ask what the state was at any past instant, and the ability to build an entirely new projection of old data by replaying history through new code.

It is also the heaviest of the four by a distance. Rebuilding state from thousands of events needs snapshots; long-lived streams mean your code must still deserialise the event schema you wrote three years ago; and a bug in an event you already published cannot be edited away, only compensated. Note carefully that Kafka retention is not an event store — a compacted or time-retained topic loses history, and event sourcing needs the full stream plus optimistic concurrency on append. CQRS is a separate idea that often travels with it: split the write model from the read model so each is shaped for its job. This track's paired Microservices module goes deep on both, including aggregates, snapshots and projection rebuilds — see CQRS and Event Sourcing.

Designing the event: past tense, granularity, identity and time

An event is a statement of fact about something that already happened, so name it in the past tense from the business vocabulary: OrderPlaced, PaymentCaptured, ShipmentDispatched. A message named CreateOrder is not an event at all — it is a command: addressed to one recipient, may be rejected, expresses intent about the future. Events are broadcast, cannot be rejected (they already happened), and may have zero consumers. Teams that blur the two end up with "events" that carry an implicit expectation that some specific consumer will act, which is choreography wearing a disguise and the source of most accidental coupling.

Granularity is the next judgement. Too fine (OrderFieldUpdated with a field name) and consumers must reassemble business meaning from fragments; too coarse (OrderChanged carrying the whole aggregate) and every consumer wakes for changes it does not care about and has to diff to find out what happened. Aim for one event per business fact. Every event should also carry: a globally unique event id so at-least-once delivery can be deduplicated by consumers, the entity id (which is usually also your partition key, per the ordering module), a schema version, a correlation or causation id for tracing, and two distinct times — occurred-at, when the fact happened in the business, and recorded-at, when the system wrote it. Those diverge during outages, backfills and replays, and reports built on the wrong one are quietly wrong.

The rule that outranks all of these: a published event is an API contract, and it has more consumers than you know about. Nobody rings you before subscribing. Treat the event schema with the same seriousness as a REST contract — review it, own it, and never assume you can enumerate who would break.

Schema evolution: additive changes and the compatibility modes

The one change you are always allowed to make is an additive one: a new optional field with a default. Removing a field, renaming it, narrowing its type or changing its meaning are all breaking, and "changing its meaning" is the killer because no tool detects it — repurposing amount from rupees to paise passes every compatibility check and corrupts every consumer. Confluent Schema Registry enforces the mechanical half of this per subject, rejecting an incompatible schema at registration rather than at 3am in a consumer.

Know the four modes and, more importantly, what each one permits you to do first. BACKWARD (the default): new consumer code can read data written with the previous schema, so you upgrade consumers first — this is the mode for most Kafka topics, where consumers lag behind producers. FORWARD: old consumer code can read data written with the new schema, so you upgrade producers first — useful when you cannot coordinate a fleet of downstream readers. FULL is both, which in practice restricts you to adding and removing optional fields with defaults. NONE disables checking, and the transitive variants (BACKWARD_TRANSITIVE and friends) check against every previous version rather than only the last, which is what you actually want on a long-lived event stream. Pair whichever you choose with tolerant readers on the consumer side: ignore unknown fields rather than failing, so an additive producer change never becomes an incident.

{
  "type": "record", "name": "OrderPlaced", "namespace": "com.acme.orders.v1",
  "fields": [
    { "name": "eventId",  "type": "string" },
    { "name": "orderId",  "type": "string" },
    { "name": "customerId", "type": "string" },
    { "name": "totalPaise", "type": "long" },
    { "name": "channel", "type": ["null", "string"], "default": null }
  ]
}
// additive + optional + default = BACKWARD compatible; consumers upgrade at leisure

Versioning strategies: upcasting, version fields and new topics

Compatibility rules buy you time; eventually you need a genuinely breaking change. Four strategies, roughly in order of how often they are the right answer. Upcasting is the workhorse for event-sourced streams: keep the old events exactly as written, and run a transformation on read that lifts a v1 payload into the v2 shape before the domain code sees it. Your domain model then only ever knows the newest version, and the upcasters accumulate in one auditable place. A version field in the envelope (schemaVersion, or a fully-qualified type name that carries the version) lets a consumer branch explicitly — verbose, but honest, and it makes the compatibility question visible in code review.

The heavier options are a new topic per major version — orders.placed.v1 and orders.placed.v2 published in parallel while consumers migrate, then v1 retired on a published date — which is the cleanest migration path for integration events between teams and the most operationally expensive; and in-place migration of stored events, which is a rewrite of history and should be treated as a last resort, since it destroys the audit property you adopted event sourcing to get. Cutting across all four: standardising the envelope (CloudEvents gives you id, source, type, time and subject as interoperable attributes) means version negotiation happens in a place every consumer already parses, and consumer-driven contract tests tell you who actually breaks before you find out in production.

Choreography case study: an order across four services

Read the happy path as a sequence of facts, with no coordinator anywhere. The order service accepts a request, writes its own row and publishes OrderPlaced. The payment service consumes it, charges the card and publishes PaymentCaptured (or PaymentFailed). The inventory service consumes PaymentCaptured, reserves stock and publishes StockReserved or StockUnavailable. The shipping service consumes StockReserved and publishes ShipmentDispatched. The order service subscribes to all of them and advances its own view of order status. Nobody calls anybody. Each service can be deployed, scaled and restarted independently, and adding a loyalty-points service on Friday requires changing nothing that exists.

Now read the unhappy path, because that is what interviews probe. There is no rollback: StockUnavailable must trigger a compensating action — the payment service refunds, the order service cancels — which is exactly the choreographed saga. Every consumer must be idempotent, since at-least-once delivery means PaymentCaptured will be redelivered and you must not ship twice; the event id is what you deduplicate on. Each service publishes its event in the same local transaction as its state change or the two drift apart, which is what the transactional outbox pattern exists to solve. And ordering only holds per partition key, so key every event in the flow by order id.

order-service      --OrderPlaced-->       payment-service
payment-service    --PaymentCaptured-->   inventory-service
inventory-service  --StockReserved-->     shipping-service
shipping-service   --ShipmentDispatched-> order-service (status: DISPATCHED)

failure branch:
inventory-service  --StockUnavailable-->  payment-service (refund)
                                       -> order-service (status: CANCELLED)

When events hurt — and what to reach for instead

The closing verdict of this track. Choreography's defining weakness is that no single place shows the business process. The order flow above exists only in the heads of the people who built it and in the union of four codebases; there is no file you can open to see it, no diagram the compiler keeps honest, and a new joiner reconstructs it by grepping for event names. Debugging follows: one customer complaint spans four services' logs, and without correlation ids propagated on every event and distributed tracing across the broker, you are reduced to timestamp archaeology. Cyclic event chains are the next hazard — service A publishes, B reacts and publishes, C reacts and republishes something A consumes — producing infinite loops that only reveal themselves under load. And accidental coupling creeps in through event shape: the moment a consumer depends on a field the producer added for its own reasons, you have a distributed monolith with worse latency and no compiler to warn you.

So the honest guidance. Do not use events when the caller genuinely needs the answer to continue — a synchronous call is simpler, traceable and consistent. Do not use events as a slow, lossy replication mechanism for CRUD screens; publishing EntityUpdated for every table write is a message bus doing a database's job with none of its guarantees. Do not use choreography for a long, branching, business-critical workflow with compensations and timeouts: that is a process, it deserves to be visible, and an orchestrated saga or a workflow engine gives you one place that owns the flow, a state machine you can query, and a timeout story. The rule of thumb worth carrying out of this track: choreograph facts, orchestrate processes — and if you cannot explain what business fact an event records, it is probably a command wearing an event's name.

Interview questions

Architecture-judgement questions dominate the final rounds at Indian product companies, and service companies increasingly ask them for senior and architect roles — the pattern below is that every question rewards naming a tradeoff rather than a technology:

Beginner What is event-driven architecture, in one paragraph?

A style in which services communicate by publishing facts about things that have happened to a broker, and other services react to those facts, instead of calling each other directly. Producers do not know their consumers. It buys temporal decoupling and independent scaling, and costs you eventual consistency, duplicate delivery and harder debugging.

Beginner What is the difference between a command and an event?

A command expresses intent about the future, is addressed to exactly one recipient, and can be rejected: CreateOrder, ReserveStock. An event is a fact about the past, is broadcast to anyone interested, cannot be rejected because it already happened, and may have zero consumers: OrderPlaced, StockReserved. Name events in the past tense; if you find yourself expecting a particular consumer to act on an "event", you have really published a command.

Beginner Name Fowler's four patterns and one sentence on each.

Event notification (a thin signal; consumers call back for detail), event-carried state transfer (the event carries the state so consumers need not call back), event sourcing (the append-only event log is the system of record), CQRS (separate models for reads and writes). They are different tools, not stages of maturity.

Beginner What fields should every event carry?

A unique event id (for consumer-side deduplication under at-least-once delivery), the event type, a schema version, the entity id that identifies the subject and usually serves as the partition key, correlation and causation ids for tracing, and both an occurred-at business time and a recorded-at system time. Then the business payload, and only the fields the fact needs.

Intermediate Event notification vs event-carried state transfer — how do you choose?

Ask what happens when the producer is down. With notification the consumer holds an event it cannot enrich, so producer availability is on your critical path; with state transfer the consumer already has what it needs and keeps working. Choose state transfer when consumers need producer data on a hot path or must survive its outage; accept in exchange data duplication, staleness and a much wider contract to version. Choose notification when consumers rarely need detail and you want the narrowest possible contract.

Intermediate Which schema changes are safe, and which quietly are not?

Safe: adding an optional field with a default. Breaking: removing or renaming a field, narrowing a type, making an optional field required, changing enum semantics. The dangerous one is redefining the meaning of an existing field — changing an amount from rupees to paise, or a status code's interpretation — because it passes every automated compatibility check and silently corrupts every consumer.

Intermediate Explain BACKWARD, FORWARD and FULL compatibility and who you upgrade first.

BACKWARD means new consumer code can read data produced with the old schema, so you upgrade consumers first — the Schema Registry default, and right for Kafka where consumers lag. FORWARD means old consumer code can read data produced with the new schema, so you upgrade producers first. FULL is both, which limits you to adding and removing optional fields with defaults. On long-lived streams prefer the transitive variants, which check against every earlier version rather than only the immediately preceding one.

Intermediate What is upcasting and when do you use it instead of a new topic?

Upcasting transforms an old event payload into the current shape on read, so stored history is never rewritten and the domain code only knows the newest version. It is the standard answer inside an event-sourced stream, where you must keep old events forever. A new topic per major version is the better answer for integration events crossing team boundaries, where you want producers publishing both shapes in parallel and a published retirement date for the old one; it costs more operationally but gives consumers a clean, independent migration.

Intermediate Why do you need occurred-at and recorded-at, not just one timestamp?

Because they diverge exactly when it matters. Occurred-at is when the fact happened in the business; recorded-at is when the system wrote it. During an outage, a backfill, an offline mobile sync or a replay, the gap can be hours or days. Analytics and SLA reporting want occurred-at; deduplication, ordering diagnostics and operational dashboards want recorded-at. Systems that keep only one end up with reports that are quietly wrong after every incident.

Pro Walk me through a choreographed order flow, then tell me where it hurts.

OrderPlaced from the order service, PaymentCaptured from payments, StockReserved from inventory, ShipmentDispatched from shipping, with the order service subscribing to all of them to advance status. Where it hurts: no single artefact describes the process, so it lives only in four codebases; one customer complaint spans four log streams and needs correlation ids plus distributed tracing to reconstruct; failure paths need compensating actions rather than rollback; cyclic event chains can form and only surface under load; and consumers gradually couple to fields the producer added for itself, giving you a distributed monolith. For a long, branching, business-critical flow, an orchestrated saga or workflow engine is usually the better trade.

Pro When would you argue against events in a design review?

When the caller needs the answer to proceed, a synchronous call is simpler and consistent. When the "events" are just CRUD writes republished as EntityUpdated, you have a message bus doing a database's job without its guarantees. When the process is long, branching and needs timeouts and compensations, orchestrate it so the flow is visible and queryable. And when the team has no schema registry, no tracing across the broker and no dead-letter discipline, adding asynchrony converts easy bugs into hard ones. Choreograph facts; orchestrate processes.

Pro Is Kafka an event store? Justify your answer.

Not on its own. Event sourcing requires the complete history of a stream plus optimistic concurrency on append — read the current version of an aggregate's stream and append only if nobody else has. Kafka gives you an ordered, durable log, but retention and compaction discard history by design, per-key streams are not first-class, and there is no conditional append on expected version. It is superb for event streaming and integration; for event sourcing use a purpose-built store (or a relational table designed as one) and stream to Kafka from it.

Pro You need to remove a field that three known consumers use, on a topic with unknown subscribers. How do you proceed?

Treat the event as a published API contract. Publish a v2 schema or topic alongside v1 with the field removed, keep dual-publishing, and announce a retirement date. Instrument consumption of v1 so you learn who the unknown subscribers are before you break them, and pair that with consumer-driven contract tests for the consumers you do know. Only after v1 consumption reaches zero for a full business cycle do you retire it. Never remove a field in place on a live topic on the strength of "I checked and only three teams use it".

Pro Your consumer must be idempotent. How do you actually implement that in this flow?

Deduplicate on the event id, not on payload equality. Persist processed event ids in the same transaction as the business state change — a unique constraint on the event id in a processed-events table is the simplest correct implementation, since the insert fails on a duplicate and the whole transaction rolls back harmlessly. Alternatively make the effect naturally idempotent with a conditional update guarded by a version or state check ("dispatch only if status is RESERVED"). Pair it with the transactional outbox on the publish side so state change and publication cannot diverge, and keep the dedup window at least as long as your maximum redelivery and replay horizon.

Pro How do you make the business process observable when it spans four services?

Propagate a correlation id created at the edge through every event envelope, plus a causation id naming the event that caused this one, so the graph can be reconstructed. Use distributed tracing that spans the broker (context propagated in message headers) so one trace covers producer, broker and consumer hops. Publish a per-stage state on the aggregate that owns the flow, so there is one queryable answer to "where is this order?". Alert on dead-letter arrival rate and consumer lag per topic, and consider a process-manager or workflow engine when the flow is important enough that someone must be able to see it.
