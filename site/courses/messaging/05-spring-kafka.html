Module: Spring for Apache Kafka

Modules 02 to 04 taught you the broker and the raw client. This one is about the layer you will actually type at work — where a consumer loop becomes an annotated method, and where the interesting bugs move from the protocol into the framework's error handling.

Knowledge Library → Courses → Messaging and Event-Driven Systems → Spring for Apache Kafka

What this module covers

Spring for Apache Kafka does not replace the Apache client — it wraps it. Everything you learned about acks, idempotent producers, consumer groups, partition assignment and rebalancing is still exactly true underneath; the framework supplies a KafkaTemplate for sending, a listener container that owns the poll loop for you, and message conversion so your code deals in domain objects instead of byte arrays. Knowing which knob is a Spring knob and which is a plain client property is half of using it well.

The module walks the producer side (template, keys, async results, transactions), the consumer side (@KafkaListener, container factories, concurrency, acknowledgement modes, serialization), and then the half that interviewers actually probe: what happens when a record cannot be processed. Blocking retry, dead-letter topics, non-blocking retry topics, and finally how to test any of it. Targets Spring Boot 3.x/4.x with the current Spring for Apache Kafka release against a Kafka 4.x broker.

Topics

Auto-configuration: what spring.kafka actually builds for you

Adding the spring-kafka dependency to a Boot application gives you a ProducerFactory, a ConsumerFactory, a KafkaTemplate, a ConcurrentKafkaListenerContainerFactory and a KafkaAdmin, all configured from the spring.kafka.* namespace. Boot maps the well-known settings to typed properties (spring.kafka.producer.acks, spring.kafka.consumer.auto-offset-reset, spring.kafka.consumer.group-id) and gives you an escape hatch — spring.kafka.producer.properties.* and spring.kafka.consumer.properties.* — for any raw client property Boot has not modelled. Anything you can set on a KafkaProducer you can still set here.

Why this matters in an interview: the framework changes the ergonomics, not the semantics. If a candidate says "Spring Kafka guarantees delivery", they have misunderstood the layering — durability still comes from acks=all, min.insync.replicas and the replication factor on the broker, exactly as in module 03. Also note that the ProducerFactory is shared and its producers are thread-safe and pooled, while each listener container creates its own consumers, because a Kafka consumer is emphatically not thread-safe.

spring:
  kafka:
    bootstrap-servers: broker-a.internal,broker-b.internal
    producer:
      acks: all
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
      properties:
        enable.idempotence: true      # raw client property, passed straight through
    consumer:
      group-id: order-projector
      auto-offset-reset: earliest
      enable-auto-commit: false       # let the container own offset commits

Producing: KafkaTemplate, keys, and the async result nobody checks

KafkaTemplate.send(...) is the Spring face of Producer.send() and it is asynchronous in exactly the same way: it serialises the record, drops it into the accumulator batch for its partition and returns immediately. Since Spring for Apache Kafka 3.0 it returns a CompletableFuture<SendResult<K, V>> rather than the old Spring ListenableFuture — a migration detail worth knowing because a lot of blog code you will find online still uses the removed type. Ignoring that future is the single most common Spring Kafka bug: a broker rejection, a serialization failure or a TimeoutException after delivery.timeout.ms then vanishes silently and the application believes it published something it never did.

The key argument is the other thing to get right. The key decides the partition through the default partitioner, so it decides ordering: same key, same partition, same order. Send with a null key and records are spread across partitions and any per-entity ordering you assumed is gone. Pick the key from the aggregate whose order matters — order id, customer id, account number — not from something incidental. If you need the send to be synchronous for a specific call site, join the future explicitly with a timeout rather than blocking forever.

// key = orderId, so all events for one order land on one partition, in order
kafkaTemplate.send("orders", order.id(), event)
    .whenComplete((result, ex) -> {
        if (ex != null) {
            log.error("publish failed for order {}", order.id(), ex);   // never swallow this
        } else {
            var meta = result.getRecordMetadata();
            log.debug("published to {}-{} at offset {}",
                      meta.topic(), meta.partition(), meta.offset());
        }
    });

Transactions: KafkaTransactionManager and executeInTransaction

Set spring.kafka.producer.transaction-id-prefix and Boot configures a transactional ProducerFactory plus a KafkaTransactionManager, which is an ordinary Spring PlatformTransactionManager. From then on @Transactional works over Kafka sends: every KafkaTemplate operation inside the transactional scope joins the same producer transaction and commits or aborts together. Give the listener container that transaction manager and it goes further — it opens a transaction before invoking your listener and calls sendOffsetsToTransaction() before committing, so the consumed offset and the produced records commit atomically. That read-process-write atomicity is what "exactly once" actually means in Kafka, and it only holds when downstream consumers set isolation.level=read_committed.

Two details that separate the confident answer from the vague one. First, executeInTransaction(...) exists for the case where you want a local producer transaction without joining any ambient Spring transaction — useful when a listener already runs inside a database transaction and you deliberately do not want the send enlisted in it. Second, chaining a database transaction manager with the Kafka one gives you a best-effort two-phase commit, not a real one: the window where the database has committed and the Kafka commit then fails still exists, so the consumer must remain idempotent. If a candidate claims Spring gives true distributed transactions across a database and Kafka, that is the follow-up question.

@Transactional                        // KafkaTransactionManager is the tx manager
public void reprice(PriceChange change) {
    kafkaTemplate.send("prices", change.sku(), change);
    kafkaTemplate.send("audit",  change.sku(), Audit.of(change));
    // both records become visible to read_committed consumers together, or neither does
}

// local producer transaction, deliberately NOT joining an outer transaction
kafkaTemplate.executeInTransaction(t -> t.send("prices", sku, change));

@KafkaListener, the listener container, and what concurrency really means

An annotated method replaces the poll loop, but the loop is still there — it lives in a MessageListenerContainer built by the ConcurrentKafkaListenerContainerFactory. The container polls, hands each record to your method, tracks offsets and commits them according to the configured acknowledgement mode, and it also owns rebalance handling and the lifecycle (you can start, stop and inspect any container by id through the KafkaListenerEndpointRegistry, which is how you build a pause/resume switch or a dynamically managed listener).

The concurrency setting is the classic trick question. It does not create threads that share partitions — it creates that many child containers, each with its own KafkaConsumer, all in the same consumer group. The group protocol therefore bounds them: with concurrency 10 on a topic with 3 partitions, 3 consumers get one partition each and 7 sit permanently idle. Concurrency is capped by partition count, always, and the only way to raise consumption parallelism beyond that is to add partitions. Note also that concurrency is per application instance, so 4 pods at concurrency 3 is 12 consumers competing for the partitions of that group.

@KafkaListener(id = "orderProjector", topics = "orders",
               groupId = "order-projector", concurrency = "3")
public void onOrder(OrderEvent event) { projector.apply(event); }

// 3 child containers => 3 consumers in the group.
// Topic has 3+ partitions -> all three work. Topic has 1 partition -> two idle forever.

Parameter binding, batch listeners and acknowledgement modes

The listener method signature is flexible and you should exploit it. Take the deserialised body with @Payload, individual headers with @Header(KafkaHeaders.RECEIVED_KEY) or @Header(KafkaHeaders.RECEIVED_PARTITION), the whole envelope as a ConsumerRecord<K, V> when you need offsets and timestamps, or an Acknowledgment when you commit manually. Set batch: true on the factory and the same method takes a List<T> — one call per poll instead of one call per record, which is a large throughput win when your processing is a bulk database write, at the cost of coarser error granularity.

Acknowledgement mode is where correctness lives. BATCH (the default) commits the offsets of the whole poll after the batch is processed. RECORD commits after each record — safest, slowest. MANUAL queues your ack() and commits it at the end of the batch; MANUAL_IMMEDIATE commits it right away, which is what people usually mean when they say "manual commit". Whatever you choose, remember the guarantee is at-least-once: the process can die after handling a record and before the commit lands, so the record is redelivered. Idempotent handlers are not optional, they are the design.

@KafkaListener(topics = "orders", containerFactory = "manualAckFactory")
public void onOrder(@Payload OrderEvent event,
                    @Header(KafkaHeaders.RECEIVED_KEY) String key,
                    ConsumerRecord<String, OrderEvent> record,
                    Acknowledgment ack) {
    projector.apply(event);           // must be idempotent: redelivery is normal
    ack.acknowledge();                // AckMode.MANUAL_IMMEDIATE commits here and now
}

Serialization: JSON, type headers, trusted packages and the poison pill

Spring's JsonSerializer and JsonDeserializer convert domain objects with Jackson. By default the serializer writes the fully qualified class name into a type header and the deserializer reads it back — convenient inside one codebase, brittle across teams, because renaming or moving a class breaks every consumer. The fix is JsonSerializer.TYPE_MAPPINGS on the producer, which publishes a stable logical name (order:com.acme.orders.OrderEvent) instead of a package path, so producer and consumer can hold the class in different packages. Alternatively, turn type headers off entirely and pin the target type on the consumer with JsonDeserializer.VALUE_DEFAULT_TYPE or a typed JsonDeserializer<>(OrderEvent.class).

Trusted packages is the security control on the same mechanism: because the type header arrives from the network, an unrestricted deserializer would instantiate whatever class a publisher names, so Spring refuses anything outside spring.json.trusted.packages. Setting it to * to make an error go away is a real finding in a code review. The related failure is the poison pill — one record that cannot be deserialised at all. Deserialization happens inside the poll, before your listener and before any error handler, so an unguarded consumer throws, never advances the offset, and re-reads the same bad record forever. Wrapping the delegates in ErrorHandlingDeserializer is what turns that infinite loop into a normal failed record the error handler can route to a dead-letter topic.

spring.kafka.consumer.key-deserializer=org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
spring.kafka.consumer.value-deserializer=org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
spring.kafka.consumer.properties.spring.deserializer.key.delegate.class=org.apache.kafka.common.serialization.StringDeserializer
spring.kafka.consumer.properties.spring.deserializer.value.delegate.class=org.springframework.kafka.support.serializer.JsonDeserializer
spring.kafka.consumer.properties.spring.json.trusted.packages=com.acme.orders.events
# producer side: publish a stable logical type name, not a package path
spring.kafka.producer.properties.spring.json.type.mapping=order:com.acme.orders.events.OrderEvent

DefaultErrorHandler, backoff, and the dead-letter topic

When a listener throws, the container hands the failure to an error handler. The default is DefaultErrorHandler, which retries the failed record in place using a BackOff — FixedBackOff for a flat interval, ExponentialBackOffWithMaxRetries for a growing one — and, once attempts are exhausted, passes the record to a recoverer. The standard recoverer is DeadLetterPublishingRecoverer, which republishes the record to a dead-letter topic. By convention that topic is the original name plus a .DLT suffix, and the recoverer copies the original key, value and headers and adds diagnostic headers — original topic, partition, offset, timestamp, exception class and stack trace — so the DLT record is self-describing when someone has to triage it at two in the morning. Also configure the classification: addNotRetryableExceptions for deterministic failures such as validation errors, because retrying a record that will never parse is pure waste.

The thing to say out loud in an interview is why this is called blocking retry. The container retries on the same consumer thread, on the same partition, and it does not poll meanwhile — so every other record queued behind that one on that partition waits for the whole backoff sequence. A ten-second exponential backoff on one bad record stalls an entire partition for ten seconds, and if the total pause exceeds max.poll.interval.ms the broker declares the consumer dead and triggers a rebalance, which is a far worse outcome than the original error. Blocking retry is therefore correct only for short, genuinely transient faults; anything longer needs the non-blocking approach below.

@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    // exhausted attempts -> republish to "<topic>.DLT" on the same partition number
    var recoverer = new DeadLetterPublishingRecoverer(template);
    var handler = new DefaultErrorHandler(recoverer, new FixedBackOff(500L, 2L));
    handler.addNotRetryableExceptions(ValidationException.class);  // deterministic: straight to DLT
    return handler;
}

@RetryableTopic: non-blocking retry with separate delay topics

@RetryableTopic inverts the problem. Instead of holding the partition while it retries, the framework immediately forwards the failed record to a dedicated retry topic and commits the original offset, so the main partition keeps flowing. Each retry topic has its own listener and its own delay, and after the configured attempts the record lands in the DLT. Spring provides two topic strategies: a separate topic per attempt (topic-retry-0, topic-retry-1, …) which is the default, or a single retry topic reused for every attempt. Because the delay is implemented by pausing the retry topic's consumer until the record's timestamp plus the backoff has elapsed, the delays are approximate rather than exact — the reference documentation has a whole section on that precision tradeoff.

The cost of non-blocking retry is the one to name unprompted: you have given up ordering. A record that fails and is retried five seconds later is now processed after records that came behind it on the same key, so if your consumer maintains per-key state you have introduced a correctness bug in exchange for throughput. Use non-blocking retry for independent, order-insensitive work — sending an email, calling an external API, updating a cache — and stay with short blocking retry, or a parking-lot topic replayed in order, where per-key ordering is part of the contract. Module 08 covers the replay and parking-lot side of that decision.

@RetryableTopic(
    attempts = "4",
    backoff = @Backoff(delay = 1000, multiplier = 2.0),   // roughly 1s, 2s, 4s
    exclude = { ValidationException.class },              // deterministic -> straight to DLT
    dltStrategy = DltStrategy.FAIL_ON_ERROR)
@KafkaListener(topics = "orders", groupId = "order-notifier")
public void notify(OrderEvent event) { mailer.send(event); }

@DltHandler
public void onDlt(OrderEvent event,
                  @Header(KafkaHeaders.ORIGINAL_TOPIC) String origin) {
    parkingLot.record(event, origin);   // alert on this: a DLT nobody watches is a data-loss bug
}

Testing the listener: @EmbeddedKafka and EmbeddedKafkaBroker

@EmbeddedKafka starts an in-process broker for the test context and publishes its address into the environment, so spring.kafka.bootstrap-servers can be wired straight to it. You declare the partition count and the topics to create up front, inject the EmbeddedKafkaBroker when you need to build a raw consumer for assertions, and get a fast, dependency-free test that runs anywhere — including on a build agent with no Docker daemon.

Two practical warnings. Kafka consumption is asynchronous, so a test that publishes and then asserts immediately is flaky by construction: use a CountDownLatch in the listener, or Awaitility, rather than sleeping. And starting a broker per test class is slow, so keep the embedded broker on a shared, cached test context — changing broker properties between classes silently forks the context and multiplies your build time. The embedded broker is also not identical to a production broker; where behaviour under real replication, real transactions or a specific broker version matters, reach for a container instead.

Testcontainers: a real broker in the test, for higher fidelity

Testcontainers runs an actual Kafka image in Docker for the duration of the test. You test against the same broker build you deploy against, so KRaft behaviour, transaction semantics, compaction, real replication and version-specific quirks all show up in CI rather than in production. Spring Boot 3.1 and later make the wiring almost invisible: annotate the container bean with @ServiceConnection and Boot derives spring.kafka.bootstrap-servers from it automatically, with no @DynamicPropertySource block to maintain.

The tradeoff is startup cost and a hard dependency on a container runtime, so the sensible split is to use both: embedded Kafka for the fast, numerous listener and serialization tests, and Testcontainers for a smaller set of end-to-end tests covering the paths where broker fidelity genuinely matters. Reuse matters as much as choice — a singleton container, or Testcontainers reuse, keeps a suite that would otherwise spend minutes on container startup down to seconds.

@SpringBootTest
@Testcontainers
class OrderListenerIT {

    @Container
    @ServiceConnection                       // Boot derives bootstrap-servers from the container
    static KafkaContainer kafka = new KafkaContainer(
            DockerImageName.parse("apache/kafka-native"));

    @Test void projectsOrder() { /* publish, then await the projection */ }
}

Interview questions

Spring Kafka is the most commonly probed messaging topic in Indian product and service-company rounds, because almost every Java team runs it — the concurrency question and the retry/DLT question come up in nearly every interview:

Beginner What does KafkaTemplate do, and is send() synchronous?

It is Spring's wrapper over the Apache KafkaProducer: it serialises the record, resolves the topic and partition, and hands it to the producer's batching accumulator. send() is asynchronous and returns a CompletableFuture<SendResult> (it returned Spring's ListenableFuture before version 3.0). To make it synchronous you join the future with a timeout — but always handle the failure case, because ignoring the future silently drops publish errors.

Beginner How do you consume messages in Spring Boot, and what runs the poll loop?

Annotate a method with @KafkaListener(topics = "...", groupId = "..."). A MessageListenerContainer created by the ConcurrentKafkaListenerContainerFactory owns the KafkaConsumer, runs the poll loop, deserialises and converts each record, invokes your method and commits offsets according to the acknowledgement mode. You never write the while-poll loop yourself.

Beginner What is the role of the message key when sending with KafkaTemplate?

The key feeds the partitioner, so it determines which partition the record lands on — same key, same partition, therefore ordering guaranteed per key. A null key spreads records across partitions and gives you no per-entity ordering. Choose the key from the aggregate whose order matters, such as order id or customer id.

Beginner What is a dead-letter topic in Spring Kafka and how is it named?

The topic a record is republished to after retries are exhausted, so the main flow can move on without losing the record. DeadLetterPublishingRecoverer does the republishing, and the default destination is the original topic name plus a .DLT suffix. It copies the key, value and headers and adds diagnostics — original topic, partition, offset, timestamp, exception class and stack trace.

Intermediate You set concurrency to 10 but only 3 consumers do any work. Why?

Concurrency creates that many child containers, each with its own consumer in the same group — it does not multiplex threads over one consumer. Kafka assigns at most one consumer per partition within a group, so with 3 partitions only 3 consumers get an assignment and the other 7 idle. Concurrency is bounded by partition count; to increase parallelism you must add partitions. It is also per application instance, so replicas multiply the consumer count in the group.

Intermediate Explain the AckMode options and when you would use MANUAL_IMMEDIATE.

BATCH (default) commits the offsets of the whole poll after the batch is handled. RECORD commits after each record — narrowest redelivery window, most commit traffic. MANUAL queues your ack() and commits at the end of the batch. MANUAL_IMMEDIATE commits as soon as you call ack(), which is what you want when a record represents an expensive, non-repeatable side effect and you want its offset durable the moment it succeeds. All modes are still at-least-once, so handlers must be idempotent.

Intermediate A single malformed JSON record makes your consumer loop forever. Diagnose and fix it.

That is the poison pill. Deserialization runs inside the poll, before the listener and before any error handler, so the exception escapes the container, the offset is never advanced, and the same record is re-read indefinitely. Fix it by configuring ErrorHandlingDeserializer as the key and value deserializer with the real deserializers as delegates — the failure is then converted into a normal failed record that DefaultErrorHandler can route to the dead-letter topic.

Intermediate What are trusted packages, and why is setting them to a wildcard a bad idea?

JsonDeserializer reads a type header supplied by the producer and instantiates that class. Since the header comes from the network, spring.json.trusted.packages restricts which packages may be deserialised. Setting it to * means any publisher on the topic can name any class on your classpath, which is a deserialization-attack surface. Restrict it to your event packages, and prefer stable logical type mappings over fully qualified class names so refactoring does not break consumers.

Intermediate How would you test a @KafkaListener without a running Kafka cluster?

@EmbeddedKafka starts an in-process broker for the test context and exposes its address, with topics and partition counts declared on the annotation; inject EmbeddedKafkaBroker and use KafkaTestUtils to build a consumer for assertions. Because consumption is asynchronous, synchronise with a CountDownLatch or Awaitility rather than sleeping. For higher fidelity use Testcontainers with a real Kafka image, ideally with @ServiceConnection so Boot wires the bootstrap servers automatically.

Pro Blocking retry versus non-blocking retry topics — explain the tradeoff and pick one for a payment consumer.

DefaultErrorHandler retries in place on the consumer thread: ordering is preserved, but the partition is stalled for the whole backoff and, if the pause exceeds max.poll.interval.ms, the consumer is evicted and the group rebalances. @RetryableTopic forwards the record to a delay topic and commits the original offset, so the partition keeps flowing — at the cost of losing ordering, since the retried record is processed after later records for the same key. For a payment consumer where per-account ordering and correctness dominate, use short blocking retry plus a dead-letter topic (or a parking lot replayed in order); use non-blocking retry for order-insensitive side effects such as notifications.

Pro How do you get exactly-once semantics for a read-process-write flow in Spring Kafka?

Set spring.kafka.producer.transaction-id-prefix so Boot creates a transactional producer factory and a KafkaTransactionManager, then give that manager to the listener container. The container opens a transaction before the listener, any KafkaTemplate sends inside it join that transaction, and the container calls sendOffsetsToTransaction() so the consumed offset commits atomically with the produced records. Downstream consumers must set isolation.level=read_committed or they will see aborted records. This is exactly-once only within Kafka — a database write in the same listener is not covered.

Pro Your listener writes to a database and publishes an event. How do you keep the two consistent?

You cannot get a true two-phase commit across a database and Kafka; chaining ChainedTransactionManager-style managers only narrows the window, it does not close it. The robust answer is the transactional outbox: write the domain change and an outbox row in one local database transaction, then have a relay (a poller or change-data-capture such as Debezium) publish the outbox rows to Kafka. That gives at-least-once publication with no lost events, and consumers deduplicate on the event id. Alternatively invert the flow — consume the event first and derive the database write — so Kafka is the single source of truth.

Pro Records are piling up in the DLT and nobody noticed for a week. What was missing?

Operational treatment of the DLT as a first-class queue. It needs a consumer or a @DltHandler that persists and classifies the record, a metric on DLT arrival rate with an alert on any non-zero rate, dashboards showing original topic and exception class, and a documented, tested replay path back to the main topic once the defect is fixed. Also review the retry classification — deterministic errors such as validation failures should go straight to the DLT via addNotRetryableExceptions or the exclude attribute rather than burning attempts first. An unwatched DLT is silent data loss.

Pro Your consumer group rebalances every few minutes under load and throughput collapses. How do you debug it in a Spring Kafka application?

The usual cause is that processing one poll's worth of records takes longer than max.poll.interval.ms, so the broker considers the member dead and revokes its partitions. Confirm it from the rebalance log lines the container emits, then fix the cause rather than the symptom: lower max.poll.records so each poll is smaller, move slow work off the listener thread, or raise the interval deliberately. Check that a blocking error handler's total backoff is not itself exceeding the interval, and make sure the group is on the cooperative-sticky assignor so a rebalance does not stop the world. Longer term, more partitions plus matching concurrency reduces per-consumer load.
