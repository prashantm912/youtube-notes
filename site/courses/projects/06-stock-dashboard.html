Capstone: Stock Market Dashboard

The real-time capstone. Every earlier project answered a request; this one holds a connection open and pushes. Get the transport decision, the fan-out backplane and the conflation policy right and you have the project that gets you asked about architecture instead of CRUD.

Knowledge Library → Courses → Real-World Projects → Stock Market Dashboard

What this capstone covers

This is a brief, not a tutorial: a buildable specification for a live market dashboard — a per-user watchlist whose prices tick in front of your eyes, an intraday chart that grows a point at a time instead of refetching, threshold alerts, a top-movers panel and historical candles over selectable ranges. You write the code; this page fixes the scope, the architecture, the contract and the order of work.

Three decisions carry the whole project and every one of them is an interview conversation. Which transport pushes prices to the browser — and why the obvious answer (WebSocket, because real-time) is usually the wrong one. How the fan-out survives a second instance, which is where a Redis backplane and sticky routing enter. And what you drop, because a feed can produce far more ticks per second than a browser can render, and choosing what to discard is a correctness decision, not a performance tweak.

The brief

Feature outline: the MVP you must finish, and the stretch goals you may not

Scope this ruthlessly. The MVP is six features and it is already a substantial build: a watchlist per user (add, remove, reorder, persisted server-side); live price ticks streamed to the browser for exactly the symbols in that watchlist; an intraday chart that appends the newest point without refetching the series; price-movement alerts that fire when a symbol crosses a user-set threshold; a market-overview panel showing top gainers and losers; and historical candles over selectable ranges (one day, five days, one month, one year) with a matching candle interval.

The stretch goals exist to be left undone until the MVP is demoable end to end: a paper-trading portfolio with live position valuation and unrealised profit and loss; multi-symbol comparison on one normalised chart; alert delivery by email or web push rather than only in-app; and a session replay that pumps a recorded trading day back through the same stream at adjustable speed. Replay is the most valuable of the four for your own sanity — it turns "wait for the market to move" into a repeatable test.

A word on the chart. Do not build one. Candlestick and line charts with live append are a solved problem, and a purpose-built financial charting library will absorb thousands of bars plus several updates per second without dropping frames, which a general-purpose chart component wrapped in a component template will not.

Where the market data comes from — and why you must not redistribute it

Read this before you write a line. Real-time exchange data is licensed. NSE, BSE, NYSE and Nasdaq feeds are sold under agreements that restrict redistribution, display and storage, and the commercial vendors who resell them pass those restrictions on to you. Free-tier APIs handle this by giving you data that is delayed (commonly by fifteen minutes) and by rate-limiting you hard — a handful of calls per minute is typical. A learning project that scrapes a live feed and republishes it on a public URL is a licensing violation, not a clever hack.

So build against a simulated feed and treat that as the primary implementation, not a stopgap. A generator that walks each symbol's price by a small random step around its last value — a random walk with a drift term and occasional volatility spikes — produces ticks that are entirely plausible for the purpose of exercising a streaming architecture, and it has three properties a real feed does not: it runs at three in the morning, it runs at whatever rate you tell it to (crank it to ten thousand ticks a second to test backpressure), and it is deterministic if you seed it. Add a free-tier delayed API as a second implementation once the pipeline works, so you have proven the seam.

The seam is the point. Define one interface — something like MarketDataFeed with a method to subscribe to symbols and a callback or reactive stream of ticks — and put every provider behind it: SimulatedFeed, FinnhubFeed, ReplayFeed. Nothing above that interface knows where a price came from. That single decision is what lets you swap providers when a free tier changes its terms, and it is the first thing an interviewer will probe when you say "I used a mock feed".

The transport decision: long polling vs server-sent events vs WebSocket

Long polling. The client issues a normal request; the server holds it open until it has something to say or a timeout expires; the client immediately reissues. It works through every proxy, every corporate firewall and every ancient load balancer, needs no new server-side machinery, and is trivially debuggable with the network tab. It is also wasteful: full request and response headers on every cycle, a fresh handler invocation per message batch, and a permanent gap between "server has news" and "client has reconnected". Correct answer for a page that updates every thirty seconds. Wrong answer for a price feed.

Server-sent events. One long-lived HTTP response with content type text/event-stream, over which the server writes newline-delimited events forever. It is one-way, server to client — which is exactly the shape of a price feed. It is plain HTTP, so it inherits compression, authentication cookies and bearer headers, HTTP/2 multiplexing, proxy traversal and your existing observability. The browser's EventSource reconnects automatically when the connection drops, and it replays from the last event id you sent, which is a feature you would otherwise have to build. Its one real constraint: over HTTP/1.1 browsers cap concurrent connections per origin at roughly six, and each open stream burns one — so a user with your dashboard open in four tabs starts starving their own page. Over HTTP/2 the streams are multiplexed on one connection and the limit effectively disappears, which is a good reason to terminate TLS with HTTP/2 enabled.

WebSocket. A protocol upgrade to a full-duplex frame-oriented connection. Frames carry a few bytes of overhead instead of a header block, so at very high message rates it is measurably cheaper, and the client can push too. The costs are real and are what candidates forget: it is a stateful connection outside normal HTTP semantics, so your load balancer needs upgrade support and often sticky routing, your authentication has to happen at or after handshake because browsers cannot set headers on the handshake, your proxies and idle timeouts need configuring, and there is no built-in reconnect — you write the backoff loop, the resubscribe and the gap-fill yourself.

The recommendation for this project: use SSE. The data flows one way, the payloads are small JSON objects, automatic reconnection is free, and everything you already know about HTTP still applies. Adopt WebSocket only when the client genuinely needs to push on the same connection — an order entry panel, a collaborative annotation layer, a chat sidebar — because that is the requirement bidirectionality is worth its operational tax for. Build the SSE version first even if you plan to add WebSocket later; if your feed sits behind an interface and your events are well-shaped, swapping the delivery layer is a day's work.

Implementing the stream on Spring: SseEmitter, Flux and the wire format

On Spring MVC the primitive is SseEmitter: a controller method returns one, the request thread is released, and you hand the emitter to a registry keyed by user or by symbol. A background publisher calls send() on the emitters that care. Register onCompletion, onTimeout and onError callbacks that remove the emitter from the registry — forget this and you leak an emitter per disconnect, which is the single most common bug in SSE code. Set spring.mvc.async.request-timeout deliberately (or pass a timeout to the constructor); the container default will close your stream out from under you. On WebFlux the same endpoint is a method returning Flux<ServerSentEvent<Tick>> and the framework handles the plumbing, which is why the reactive stack is a genuinely good fit here.

Use the wire format properly rather than shipping bare data lines. event: names the event type so the client can attach separate handlers for snapshot, tick, alert and heartbeat. id: lets the browser send Last-Event-ID on reconnect so you can decide what to replay. retry: tells the browser how long to wait before reconnecting. And send a periodic comment line or a heartbeat event roughly every twenty seconds — it keeps intermediary proxies from reaping an idle connection, and it gives the client something to time out against when the feed dies silently.

When WebSocket earns its keep: STOMP with Spring's messaging support

Raw WebSocket gives you a byte pipe and nothing else — no addressing, no subscription model, no acknowledgement. STOMP is a tiny frame-based text protocol that adds exactly those, and Spring's messaging support turns it into something that feels like the rest of the framework: @EnableWebSocketMessageBroker, a simple in-memory broker on destination prefixes such as /topic, @MessageMapping methods that look like controllers, @SendTo for broadcast and SimpMessagingTemplate.convertAndSendToUser for per-user delivery. This is the Java-idiomatic path, and if your dashboard grows a bidirectional feature it is the one to take.

Two production notes that separate a demo from a design. First, the in-memory simple broker keeps subscriptions in the JVM heap, so it does not survive a second instance — Spring's answer is the STOMP broker relay, which delegates to a real message broker (RabbitMQ or ActiveMQ speaking STOMP) so every instance shares one destination space. Second, browsers cannot attach an Authorization header to a WebSocket handshake, so authentication is either a cookie carried on the upgrade request, a short-lived ticket in the query string exchanged for a session, or a CONNECT frame carrying the token — pick one deliberately and say which in your README. SockJS remains the fallback shim when a network genuinely blocks upgrades.

Architecture sketch, and scaling the fan-out past one instance

Here is the shape. A feed adapter ingests ticks, a processor conflates and enriches them, Redis carries the fan-out, and each API instance pushes to the browsers it happens to be holding. Draw this on the whiteboard in the interview; it is the whole answer to "walk me through your architecture".

  simulated / vendor feed

            v
  +---------------------+        writes latest price  +-----------+
  |  ingest + conflate  |------------------------------>|   Redis   |
  |  (one leader pod)   |  PUBLISH ticks.<SYMBOL>      |  cache +  |
  +---------------------+------------------------------>|  pub/sub  |
                                                        |  ZSET     |
        +----------------+          +----------------+  +-----------+
        |  api-instance-1 |          | api-instance-2 |       ^  |
        |  SUBSCRIBE      |<---------+----------------+-------+  |

        +--------+--------+          +--------+-------+
                 | SSE                        | SSE
            browsers A..                 browsers B..

  writes (watchlists, alerts, candles) -> PostgreSQL, not Redis

One instance holding every connection is fine — genuinely fine, for far longer than people expect; a well-tuned JVM will hold tens of thousands of idle SSE connections. It stops being fine the moment you deploy a second replica, because a tick that arrives on instance 1 has no way to reach the browsers attached to instance 2. That gap is what a backplane closes: the ingest path does one PUBLISH to a Redis channel, every instance holds a SUBSCRIBE, and each one forwards to its own local emitters. The fan-out cost stays O(subscribers per instance) and the publisher stays ignorant of topology. Note that Redis pub/sub is fire-and-forget — a message published while an instance is restarting is simply gone — which for prices is acceptable, because the next tick supersedes it.

Two operational consequences. Routing: SSE is plain HTTP, so any instance can serve any reconnect and you need no stickiness — one more reason it is the easier default. WebSocket sessions are stateful, so you either configure sticky routing (cookie or IP hash at the load balancer) or move subscription state into the shared broker; nginx additionally needs the upgrade headers set explicitly on the proxy pass and a raised read timeout, or it will cut your connections at sixty seconds. Capacity: budget per connection, not per request — a socket, its kernel buffers, the emitter object and the per-user subscription set. Measure it under load rather than guessing, watch file-descriptor limits (ulimit -n is the first thing that bites), and export a gauge of open connections per instance so you can see the imbalance a rolling deploy creates.

Backpressure, throttling and conflation — the part everyone skips

A liquid symbol can print hundreds of trades a second. A browser renders sixty frames a second at best, and a human reads maybe two price changes a second. If you forward every tick you are not being accurate, you are being rude: the client's event loop saturates, the chart drops frames, memory climbs, and on a slow mobile link the socket's write buffer grows until something dies. Push systems fail on the write side, and the failure is silent until it is catastrophic.

Fix it on the server, not the client — by the time bytes are on the wire you have already paid for them. Three tools, in order of importance. Conflation: keep a per-symbol "latest tick" slot and flush it on a timer, so a symbol that ticked four hundred times in a second is sent once with its current price. Throttling: cap the flush interval per connection, and consider adapting it — a client that is falling behind gets a slower interval rather than a growing queue. Batching: send one frame containing every changed symbol in this interval instead of one frame per symbol; for a twenty-symbol watchlist that is a twentyfold reduction in framing and parse overhead.

Now the distinction that makes this an architecture answer rather than an optimisation. Conflation is correct for prices and wrong for trades. A price is a state: the newest value completely supersedes the previous one, so dropping intermediate values loses nothing the user could act on. A trade, an order fill, an alert firing or a ledger entry is an event: each one is independently meaningful, and dropping one is data loss. So the tick channel conflates freely, and the alert and order channels must not — they need a durable path with at-least-once delivery and client-side de-duplication on an event id. When you drop, drop visibly: expose a "ticks conflated" counter and, if a client is so far behind that you must disconnect it, disconnect it and let it resynchronise from a fresh snapshot rather than serving it stale prices.

Redis in this project: latest price, top movers, TTL discipline and Streams

Redis does four distinct jobs here and you should be able to name each. Pub/sub is the backplane described above. Latest-price cache: a hash per symbol holding price, previous close, change and timestamp, written by the ingest path and read by the REST snapshot endpoint — so a browser that connects mid-session gets the current state immediately instead of waiting for the next tick. Top movers: a sorted set keyed by percentage change, updated as ticks arrive; the panel is then a single range query for the highest and lowest scores, which is the same shape as a leaderboard and is the answer interviewers are listening for when they ask why you used a ZSET. Short-horizon aggregates: the in-progress candle for the current minute, incremented in place until the minute rolls over and the completed candle is written to PostgreSQL.

Be disciplined about keys and expiry. Namespace everything (px:{symbol}, movers:nse, candle:{symbol}:1m:{bucket}) so you can reason about, and scan for, one concern at a time. Put a TTL on everything derived — an intraday cache entry that outlives the trading day is a bug that shows a stale price with total confidence — and never put a TTL on the source of truth, which lives in PostgreSQL. Remember Redis is single-threaded per shard: a pattern subscription across thousands of channels, or a KEYS scan in a request path, blocks every other client.

Finally, know the alternative you did not pick. Redis Streams is an append-only log with consumer groups, offsets and explicit acknowledgement — durable, replayable, and the right tool for the alert and order channels where losing a message matters, or for a replay feature that must reproduce a day exactly. Pub/sub is fire-and-forget and is the right tool for prices. Choosing pub/sub for ticks and Streams for events, and being able to justify the split, is a strong senior signal.

Data model and API contract

Split storage by lifetime, not by convenience. PostgreSQL owns everything a user created or that must survive a restart: users, watchlists, alert definitions, alert firing history, and completed historical candles. Redis owns everything derived and re-computable: the latest price per symbol, the top-movers ranking, the in-progress candle. Individual ticks are owned by nobody — they are transient by design, and storing every tick is how a learning project turns into a hundred-gigabyte table nobody queries.

The Angular client: consuming the stream without leaking it

Wrap the transport in an observable and never let a component touch EventSource directly. A service exposes prices$; internally it creates the EventSource on subscribe, pushes parsed events through a subject, and tears the connection down in the teardown function. Getting the teardown right is the entire game: a component that opens a stream and does not close it leaves a live HTTP connection per route change, and because SSE reconnects automatically the leak compounds — five navigations, five open streams, and you have hit the browser's per-origin cap on your own.

Use takeUntilDestroyed() from Angular's RxJS interop for every subscription in a component; it wires the unsubscribe to the injection context's DestroyRef so there is no manual ngOnDestroy to forget. Prefer toSignal() where the template just reads the value, which removes the subscription question altogether. And put the reconnect policy in the service, not in each caller: EventSource retries on its own, but a server returning 500 or an authentication failure needs your own backoff — an exponential delay with jitter, capped, so a restarting backend does not get a synchronised stampede from every open tab the instant it comes back.

Then surface the truth. Track the timestamp of the last received event; if more than a couple of heartbeat intervals pass with nothing, flip a stale signal and grey the prices with a visible "reconnecting" badge. A dashboard that silently shows a frozen price is worse than one that admits it lost the feed — that is a correctness statement, not a design preference, and saying it out loud in an interview lands well.

Keeping the UI smooth: change detection, signals and long lists

A high-frequency stream is the fastest way to discover what Angular's change detection actually costs. Under zone-based detection every callback that resolves inside the zone schedules a check of the component tree — so a thousand ticks a second means a thousand tree traversals a second, and your chart animation dies while the profiler shows the framework, not your code, burning the frame budget.

Three defences, in order. Signals with OnPush: write ticks into signals and mark components OnPush so only the components that read a changed signal are re-rendered — the chart component stops re-rendering because a row three panels away moved. Escape the zone for the hot path: run raw tick processing inside NgZone.runOutsideAngular (or adopt zoneless change detection, where the question disappears) and re-enter only to publish the conflated result the UI actually shows. Imperative canvas drawing — the chart's own update call — never needs a change-detection cycle at all. Virtualise the list: a five-hundred-symbol watchlist should render the visible twenty rows, so use the CDK's virtual scroll viewport, and give every row a stable track expression on the symbol so the framework updates rows instead of destroying and rebuilding them.

Prove it rather than assuming it. Record a profile with the feed at a realistic rate, look at where frames are being spent, then re-record after each change. "I profiled it and change detection was X percent of frame time, so I moved the tick path out of the zone" is a far stronger interview sentence than "I used OnPush".

Build phases: nine steps, each independently runnable and demoable

The rule for every phase below: at the end of it you can start the app, show a person something working, and commit. No phase depends on a later phase to be demonstrable. If a phase is taking more than a few evenings, cut its scope rather than merging it into the next one.

  1. Simulated tick generator behind an interface. Define MarketDataFeed; implement a seeded random-walk generator over a hardcoded symbol list, with a configurable ticks-per-second knob. Demo: a scheduled log line showing plausible prices moving. No web layer yet — and you now have a load generator for phase 8.
  2. REST endpoints for symbols and historical candles. PostgreSQL schema, Flyway or Liquibase migration, seed data, and the candle range/interval query with its composite index. Demo: curl or an HTTP client returning a day of one-minute candles for a symbol.
  3. SSE endpoint streaming ticks for a symbol set. An emitter registry, the snapshot-then-tick sequence, heartbeats, and completion callbacks that actually deregister. Demo: a browser tab on the raw endpoint, events scrolling past. This is the first genuinely new thing you have built.
  4. Angular watchlist consuming the stream. The stream service, takeUntilDestroyed, a signal-backed row list, add and remove against the watchlist API. Demo: prices ticking in a real table; navigate away and back and prove in the network tab that exactly one stream is open.
  5. The live chart with conflated updates. Load history over REST, then append from the stream — never refetch the series on a tick. Server-side conflation lands here: one flush interval, latest price per symbol. Demo: a candlestick chart whose last candle grows in place.
  6. Redis pub/sub backplane and a second instance. Move ingest out of the API path, publish per symbol, subscribe on every instance, add the latest-price cache and the movers ZSET. Demo: two instances behind a load balancer; both browsers see the same tick at the same time. This is the phase worth screen-recording for your portfolio.
  7. Alerts with threshold evaluation. Rule CRUD, evaluation on the conflated stream, cooldown so a price sitting on the threshold does not fire forty times, an append-only firing log, and a separate non-conflated alert stream. Demo: set a threshold just above the current price, watch it fire once.
  8. Reconnect, backpressure and the stale indicator. Backoff with jitter, resume behaviour on Last-Event-ID, adaptive throttling for slow clients, a "ticks conflated" and "open connections" metric, and the stale badge. Demo: kill the backend mid-session; the UI greys out, then recovers on its own. Then run the generator at ten thousand ticks a second and show the UI still smooth.
  9. One stretch goal, finished properly. Pick one — paper portfolio, multi-symbol comparison, email or push delivery, or session replay — and take it to the same standard as the MVP. One polished feature beats four half-built ones on a CV, every time.

Interview questions

An interviewer sees this project on your CV and will not ask you about CRUD. These are the questions that follow — the ones Indian product and service companies use to find out whether you designed the thing or followed a tutorial:

Beginner Walk me through what happens between a price changing and a user seeing it.

The feed adapter receives a tick and hands it to the processor, which updates the latest-price hash in Redis, updates the movers sorted set, and publishes to the symbol's Redis channel. Every API instance is subscribed; each one looks up which of its own open SSE connections care about that symbol, and writes a conflated batch on the next flush interval. The browser's EventSource fires a message event, the stream service parses it into a signal update, and the OnPush row and the chart's imperative update call redraw. Roughly five hops, and I can point at where each one is in the code.

Beginner Where did your market data come from?

A simulated feed — a seeded random walk per symbol with a drift term and volatility spikes — behind a MarketDataFeed interface, with a free-tier delayed API as a second implementation of that same interface. That is deliberate, not a shortcut: real-time exchange data is licensed and cannot be redistributed, free tiers are delayed and heavily rate-limited, and a simulator runs at any hour, at any rate I choose, and reproducibly. Because everything above the interface is provider-agnostic, swapping in a paid feed is one class.

Beginner Why does the dashboard call a REST endpoint at all if it has a live stream?

Because a stream only tells you about changes from the moment you connect. A user opening the page at a quiet moment would stare at empty rows until something moved. So the page loads a snapshot over REST — served from the Redis latest-price cache — paints immediately, and the stream then applies deltas on top. The same snapshot-then-delta pattern also covers reconnection. Historical candles are REST for the same reason: they are a bounded query, not a subscription.

Intermediate You chose SSE over WebSocket. Defend that.

The data flows one way. SSE is exactly that shape, and being plain HTTP it keeps everything I already have: bearer tokens and cookies, compression, HTTP/2 multiplexing, proxy traversal, the same logging and tracing, the same load balancer with no stickiness needed because any instance can serve a reconnect. EventSource also reconnects automatically and resumes from Last-Event-ID, which with WebSocket I would write myself. WebSocket buys bidirectionality and lower per-frame overhead, and I did not need bidirectionality — if I added order entry or a chat panel I would move to STOMP over WebSocket, and I structured the event model so that swap is a delivery-layer change.

Intermediate What is the downside of SSE that you had to work around?

Over HTTP/1.1 browsers limit concurrent connections per origin to about six, and every open stream consumes one — so a user with several tabs open starves their own page, and any other request queues behind the streams. The fix is HTTP/2 at the edge, where the streams multiplex over a single connection. Secondly, intermediaries buffer or reap idle responses, so I send heartbeats and set the header that disables proxy buffering. Thirdly, SSE is text-only, so a binary protocol would need encoding — irrelevant for small JSON ticks.

Intermediate How did you scale to more than one instance?

One instance holding all the connections works until you deploy a replica, and then a tick arriving on instance 1 cannot reach browsers attached to instance 2. I introduced a Redis pub/sub backplane: ingest publishes once per symbol channel, every instance subscribes, and each forwards to its own local emitter registry. The publisher stays ignorant of topology and fan-out cost stays proportional to connections per instance. Because SSE is stateless HTTP I needed no sticky sessions; had I used WebSocket I would have needed sticky routing or a shared STOMP broker relay, because subscription state lives with the socket.

Intermediate Redis pub/sub is fire-and-forget. Is that not a problem?

For prices, no — a message lost while an instance restarts is immediately superseded by the next tick, and the client resynchronises from a snapshot on reconnect anyway. For anything event-shaped it would be a problem, so alerts do not go over pub/sub; they use Redis Streams with a consumer group, offsets and explicit acknowledgement, plus a firing log in PostgreSQL and de-duplication on the event id at the client. Choosing fire-and-forget for state and a durable log for events is the actual design decision, and I can state the rule that separates them.

Intermediate Why a sorted set for top movers instead of a query?

Because the ranking changes on every tick and is read constantly. A SQL ORDER BY over a live price table would be a full scan on a table under continuous write. A Redis sorted set keyed on percentage change is updated in logarithmic time as ticks arrive, and the panel becomes two range queries — highest scores and lowest scores — in constant-ish time. It is the leaderboard pattern. The tradeoff is that it is derived state that has to be rebuilt after a Redis flush, which the ingest path does from the previous close within one interval.

Pro How did you handle backpressure?

Server side, because once bytes are on the wire the cost is already paid. Three layers: conflation — a per-symbol latest-value slot flushed on a timer, so four hundred ticks in a second become one message; throttling — a per-connection flush interval that lengthens for a client that is falling behind rather than letting its write buffer grow; and batching — one frame carrying every changed symbol in the interval instead of one frame per symbol. I also instrumented it: counters for ticks received versus ticks sent, and per-connection queue depth. A client too far behind gets disconnected and resynchronises from a fresh snapshot, because serving it a growing backlog of stale prices is worse than a brief reconnect.

Pro You conflate ticks. When would conflation be a bug?

Whenever the messages are events rather than state. A price is state — the newest value fully supersedes the previous one, so dropping intermediates loses nothing actionable. A trade, an order fill, an alert firing or a ledger entry is an event: each is independently meaningful and dropping one is data loss, and it also breaks any downstream that computes volume or sequence. So in my design the tick channel conflates and the alert and order channels never do; they get a durable path with at-least-once delivery and client-side de-duplication. Getting that split wrong is how a dashboard quietly loses a fill.

Pro How does the Angular client avoid change-detection thrash at a thousand ticks a second?

Three things, in order of impact. Ticks land in signals and every component is OnPush, so only components reading a changed signal re-render — a moving row no longer forces a chart re-check. The raw tick path runs inside runOutsideAngular (zoneless removes the question entirely), re-entering only to publish the conflated result; the chart's own canvas update never needs a change-detection cycle. And the symbol list uses the CDK virtual scroll viewport with a stable track on the symbol, so five hundred symbols render twenty rows and update rather than rebuild them. I verified each with a profile at a realistic tick rate rather than assuming.

Pro A user's connection drops for thirty seconds. What does the UI show, and what happens on reconnect?

The client tracks the last-event timestamp; once it exceeds a couple of heartbeat intervals a stale signal flips, prices grey out and a reconnecting badge appears — a frozen price shown confidently is worse than an admitted outage. EventSource retries on its own using the interval I send in the retry field; for errors it does not handle I use exponential backoff with jitter so a restarting backend is not stampeded by every open tab at once. On reconnect the browser sends Last-Event-ID; the server replies with a fresh snapshot rather than replaying the intervening ticks, because for state the current value is strictly better than a backlog. Alerts are the exception and do replay from the durable log.

Pro How many concurrent users could one instance hold, and how would you find out?

I would not quote a number without measuring, because it depends on payload size, flush interval and heap sizing. The method: a load generator opening N streams while the simulator runs at a fixed rate, then watch open connections, heap after GC, CPU, and the per-connection queue depth, and find the knee. The limits that bite first are file descriptors, then heap held by emitter and subscription objects, then the write path once flush work exceeds the interval. Rough expectation is tens of thousands of mostly-idle SSE connections per well-tuned JVM. I export open connections and conflation counters per instance, so the imbalance a rolling deploy creates is visible rather than inferred.

Pro If you had to add order placement tomorrow, what changes?

That is the requirement that finally justifies WebSocket, because the client now publishes on the same connection — I would add STOMP over WebSocket with Spring's messaging support, keep the price feed on SSE initially, and move it later only if measurement justified it. The bigger changes are not transport: orders are events, so they need a durable path with idempotency keys so a retried submit cannot double-fill, an acknowledgement the client can reconcile against, and strict no-conflation. Operationally I would need sticky routing or a STOMP broker relay for shared subscription state, and handshake-time authentication since browsers cannot set headers on the upgrade.
