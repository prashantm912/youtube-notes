Capstone 10: Cloud Enterprise Deployment

The graduation project. You already have a system that works on your laptop — capstone 08 built the e-commerce application, capstone 09 pulled it apart into services. This brief takes that estate and runs it properly in the cloud: defined in code, deployed by a pipeline nobody can bypass, observed well enough to argue with, and then deliberately broken to find out whether any of it is true.

Knowledge Library → Courses → Real-World Projects → Cloud Enterprise Deployment

What this capstone covers

This is a brief, not a tutorial. It specifies a target architecture, an infrastructure inventory, a pipeline design and ten delivery phases — each of which leaves you with something that runs. It does not hand you the YAML. Producing the YAML, and understanding why each line is there, is the exercise.

Two things separate this capstone from every previous one. First, everything is defined as code: no click-ops in a console, no manual kubectl apply against production, no cloud key stored in a repository. Second, the deliverable is not the deployment — it is the write-up of the disaster-recovery drill at the end, in which you break the system you just built and record honestly what failed. A backup you have never restored is not a backup, and a runbook you have never rehearsed is fiction.

You do not need to spend money to do this. The section on the two paths is explicit about what the AWS route costs per month and what a local cluster on your own machine teaches for nothing — which is most of it.

The brief

The target architecture

The shape is the standard cloud-native web estate, and it is worth committing to memory because you will meet it in almost every product company. A browser reaches a CDN for the Angular build and an ingress or Gateway API listener for the APIs. Behind the ingress sits a Kubernetes cluster running the services from capstone 09 — gateway, catalog, cart, order, payment, inventory, notification — each a Deployment with probes, resource requests and limits, and a horizontal autoscaler. Behind the services sit managed stateful things you deliberately do not run yourself: a Postgres instance per service boundary, a Kafka cluster, a Redis cache, an object store. Secrets come from a manager, never from a checked-in file. Every arrow in the diagram is defined in Terraform, and every pod in it arrives via the pipeline.

The single most important property of this architecture is that it is reproducible. If someone deletes the whole cluster, you should be able to recreate it from the repository and a database backup. That property is exactly what the drill at the end tests, and it is what turns a demo into something you can talk about in an interview.

Two paths, and the cost reality

Be honest with yourself about the bill before you start. A realistic AWS build of this architecture — an EKS control plane, two or three small managed nodes, an RDS Postgres instance with multi-AZ, a small MSK or self-hosted Kafka, an ElastiCache node, a NAT gateway, an application load balancer, CloudFront and S3 — lands somewhere around $250 to $450 per month if you leave it running, and the NAT gateway plus the EKS control plane are a fixed floor of roughly $100 before you deploy a single pod. Left on by accident for a month, that is a genuinely painful amount of money for a learner. Run the numbers in the pricing calculator first, set a billing alarm, and destroy the stack with terraform destroy the moment a session ends.

The cost-conscious path is not a lesser path. Run the whole thing on a local Kubernetes cluster — kind or k3d, both of which create a multi-node cluster inside Docker in under a minute — and you learn manifests, probes, resource limits, HPA behaviour, ingress, cert-manager, Helm, Kustomize, Argo CD, Prometheus, Grafana, Loki, OpenTelemetry, the pipeline, and the whole disaster-recovery drill for nothing. What you do not learn locally is IAM, VPC networking, managed-service failover semantics and real cloud billing. The pragmatic compromise most learners should make: build phases 1 through 3 and 7 locally, then spend one focused weekend standing up the AWS foundation with Terraform to see phases 4 through 6 for real, and destroy it on Sunday night. That costs a few dollars, not a few hundred.

The infrastructure inventory

Write the inventory down before you write any code, because it is the list Terraform has to produce and the list the DR drill has to restore. For the cloud path: a VPC with public and private subnets across at least two availability zones; an EKS cluster with a managed node group; an RDS Postgres instance with multi-AZ enabled and automated backups plus point-in-time recovery; a Kafka cluster — managed MSK if you can afford it, the Strimzi operator inside your own cluster if you cannot; an ElastiCache Redis node for sessions and the cart; an S3 bucket plus a CloudFront distribution for the Angular build; a certificate from ACM or cert-manager; a secrets manager holding database credentials, JWT signing keys and third-party API keys; a Route 53 hosted zone; and an ECR registry for images.

Two decisions in this list are the ones interviewers probe. First, why managed Postgres rather than a Postgres pod: because failover, backups, patching and point-in-time recovery are exactly the operational work you do not want to invent, and a database on ephemeral cluster storage is a data-loss incident waiting for a node to die. Second, Kafka. Self-hosting via an operator is legitimate and cheap, and Strimzi is genuinely good, but you now own broker rebalancing, disk pressure and upgrades. Pick one deliberately and be able to defend it — "we self-hosted with Strimzi because MSK was three times our budget and our throughput was tiny" is a much better answer than "we used MSK because it is managed".

Terraform: repository layout and modules per concern

The layout matters more than the syntax. Split the infrastructure into modules by concern — network (VPC, subnets, routing, NAT), cluster (EKS, node groups, IAM roles for service accounts), data (RDS, ElastiCache, MSK, the parameter groups and subnet groups they need) and dns (Route 53 records, ACM certificates) — and keep each module ignorant of the others except through explicit input variables and outputs. The test of a good module boundary is whether you could destroy and rebuild the data layer without touching the network layer's state.

Do not write the VPC or the EKS cluster yourself. The community modules in the Terraform registry encode years of edge cases — subnet tagging that the AWS load balancer controller requires, IRSA wiring, node group lifecycle rules — and reimplementing them by hand is how learners lose a weekend to a cluster that will not schedule pods. Consume them as modules, pin the version, and read their source: it is some of the best Terraform you will find to learn from.

infra/
  modules/
    network/      main.tf variables.tf outputs.tf   # VPC, subnets, NAT, routing
    cluster/      main.tf variables.tf outputs.tf   # EKS, node groups, IRSA
    data/         main.tf variables.tf outputs.tf   # RDS, ElastiCache, MSK
    dns/          main.tf variables.tf outputs.tf   # Route 53, ACM
  envs/
    dev/          main.tf backend.tf terraform.tfvars   # its OWN state file
    staging/      main.tf backend.tf terraform.tfvars   # its OWN state file
    prod/         main.tf backend.tf terraform.tfvars   # its OWN state file

# envs/* are thin: they wire modules together and set sizes.
# Anything copy-pasted between two env directories belongs in a module.

Remote state, locking, environments, and what does not belong in Terraform

State is the part beginners get wrong and the part that ends careers. Local state in terraform.tfstate is fine for a tutorial and unacceptable for anything shared: it lives on one laptop, it contains secrets in plaintext, and two people running apply at once will corrupt it. Use a remote backend — an S3 bucket with versioning and encryption enabled — and turn on locking so a second apply blocks instead of racing. Modern Terraform supports native S3 state locking; older setups used a DynamoDB lock table, and you will still meet both in real repositories.

Give each environment its own state file, not a copy-pasted directory sharing one. Separate state is the blast-radius boundary: a botched apply against dev cannot reach prod's resources because prod's resources are not in dev's state. Then enforce the discipline: terraform plan runs on every pull request and its output is what the reviewer actually reviews; terraform apply runs only after merge, only from the pipeline, and only with a plan file the reviewer approved. Nobody applies from a laptop.

Equally important is what you keep out. Terraform owns long-lived infrastructure: networks, clusters, databases, DNS, IAM. It should not own your application Deployments. If Terraform applies your Kubernetes manifests, then every application release becomes an infrastructure change, your state file churns on every deploy, and a rollback of the app means a rollback of the infrastructure repository. Application deployment belongs to the pipeline or to a GitOps controller. The dividing line is lifecycle: things that change monthly go in Terraform, things that change several times a day do not.

Kubernetes: the runtime contract every service must satisfy

Write down a contract that every one of your services must meet before it is allowed into the cluster, and hold each service to it. A Deployment with at least two replicas. A readiness probe that returns healthy only when the service can actually serve — database pool up, Kafka producer connected — because readiness is what removes a pod from the load balancer. A liveness probe that is deliberately dumber than readiness, checking only that the process is not wedged, because a liveness probe wired to a downstream dependency will restart your entire fleet the moment that dependency wobbles. A startup probe for anything with a slow JVM warm-up, so liveness does not kill a pod that is merely booting.

Then resource requests and limits on every container. Requests are what the scheduler uses to place pods and are the number that actually matters; limits are the ceiling, and a CPU limit set too low will throttle a service that has plenty of headroom on the node. Add a HorizontalPodAutoscaler keyed on something meaningful — CPU is the default, requests-per-second or queue depth via custom metrics is better — and a PodDisruptionBudget so a node drain during a cluster upgrade cannot take your last two replicas down simultaneously. Namespaces separate environments; if dev, staging and prod share one cluster, they must not share a namespace, a quota or a network policy.

The edge: ingress or Gateway API, TLS, and externally sourced configuration

Ingress is the mature, universally supported way to get HTTP into a cluster, and for this project it is entirely sufficient: one ingress controller, host and path rules per service, TLS terminated at the edge. Gateway API is its successor and the direction the ecosystem is moving — richer routing, a cleaner separation between the platform team who owns the Gateway and the application teams who own their Routes, and no more vendor-specific annotations. Build with Ingress if you want the shortest path; build with Gateway API if you want the thing you will be asked about in two years. Either way, do not terminate TLS by hand: cert-manager issues and renews Let's Encrypt certificates automatically inside the cluster, and on AWS an ACM certificate on the load balancer does the same job with zero renewal work.

Configuration and secrets come from outside the image. ConfigMaps hold non-sensitive per-environment settings; secrets are not stored in Git, not even base64-encoded in a manifest, because base64 is encoding rather than encryption and a Kubernetes Secret in a repository is a plaintext credential in a repository. Use the External Secrets Operator to sync values from AWS Secrets Manager (or Vault) into cluster secrets at runtime, so the source of truth is the secrets manager, rotation is a manager-side operation, and your Git history stays clean. If you take one habit from this capstone into your first job, make it this one.

Packaging environments: Helm charts or Kustomize overlays

You need one definition of each service that renders differently in dev, staging and prod. Copy-pasting three near-identical manifest directories is the failure mode this section exists to prevent — they drift within a fortnight, and the drift is invisible until an outage. Helm templates the manifests and parameterises them through values.yaml, giving you one chart plus a values file per environment, versioned releases, and helm rollback. Kustomize takes the opposite approach: a plain-YAML base plus declarative overlays that patch it, with no templating language to learn and manifests that stay valid YAML you can read.

For a team of one building this capstone, Kustomize is the gentler start and is built into kubectl. For anything you intend to distribute, or where you want release history and a rollback verb, Helm wins. Choose one and be consistent — a repository that uses both for the same service is a repository nobody can reason about. Either way, put the environment differences where they belong: replica counts, resource sizes, hostnames, log levels and feature flags in the overlay or values file; everything else identical, so that "it works in staging" means something.

Push deploys or GitOps: the either/or you have to decide

There are two coherent ways to get a new image into the cluster and you must pick one, not blend them. In the push model the pipeline holds cluster credentials and runs helm upgrade or kubectl apply itself. It is simple, it is what most teams start with, it works on day one — and its weaknesses are that CI needs standing access to your cluster, and that the truth about what is running lives in whatever the last job happened to do.

In the pull or GitOps model, the pipeline's last step is a commit: it updates an image tag in a manifests repository and stops. A controller inside the cluster — Argo CD is the mature choice — watches that repository and reconciles the cluster towards it continuously. The repository becomes the single declarative source of truth, drift is detected and reverted automatically, a rollback is a git revert, the audit trail is the git log, and CI never needs cluster credentials at all. The cost is a second repository, a controller to operate, and a slightly longer path from merge to running pod.

The honest recommendation for this capstone: build phase 6 with push deploys so you understand what the pipeline is actually doing, then convert to Argo CD in phase 8 and keep both branches in your repository. Being able to explain, in an interview, why you migrated and what changed is worth more than either implementation alone.

CI/CD: build the image once, promote the same image

The rule that governs everything else in the pipeline: an artifact is built exactly once and the identical, immutable image is promoted through every environment. Tag by commit SHA, never by latest, and never rebuild for production. If staging tested image a1b2c3d and production runs a rebuild of the same branch, you have tested nothing — the base image may have moved, a transitive dependency may have published a new patch, and the artifact in production is one nobody ever ran a test against.

Design the stages explicitly and make each one a gate: compile and unit test; integration test with Testcontainers; static analysis and dependency scanning; build the container image; scan the image for vulnerable OS packages; sign it with cosign so you can verify provenance later; push to the registry; deploy to staging; run a smoke test against the deployed staging environment; then a gated production deploy that a human approves. Everything before the staging deploy runs on every pull request; everything after runs only on the main branch.

pull request:        compile -> unit -> integration -> lint/SAST -> dep-scan
                          -> build image (SHA tag) -> image scan -> sign

merge to main:       reuse image :$SHA
                          -> deploy staging (OIDC role, staging env)
                          -> smoke test against staging URL
                          -> [ manual approval gate: production environment ]
                          -> db migration job (expand-only)
                          -> deploy prod (canary 10% -> 50% -> 100%)
                          -> verify SLO burn rate -> promote or auto-rollback

never:               a long-lived cloud access key stored as a repo secret

OIDC federation, environment protection and the gated production deploy

No cloud keys. This is not a nice-to-have; a leaked long-lived AWS access key in a repository secret is one of the most common breach vectors in the industry, and the fix has been standard for years. Configure GitHub as an OIDC identity provider in AWS IAM, create a role whose trust policy is scoped to your specific repository and specific branch or environment, and let the workflow exchange a short-lived GitHub-issued token for temporary AWS credentials at runtime. The credentials expire in minutes and nothing is ever stored. Getting the trust policy's subject condition right — pinning repo:org/name:environment:production rather than a wildcard — is the part interviewers ask about, because a sloppy wildcard lets any branch in the repository assume your production role.

Layer environment protection rules on top. Declare staging and production as GitHub environments, attach required reviewers and a wait timer to production, and scope each environment's secrets and variables to itself. The result is that the production deploy job physically cannot start until a named human clicks approve, the approval is recorded against the run, and a pull request from a fork can never reach the production role. That is the difference between a pipeline and a pipeline you would let near real customers.

Rolling out and rolling back: migrations, canaries and blue-green

A rolling deploy means old and new versions of your code run against the same database at the same time, for minutes. That single fact dictates the migration rule: every schema change must be backwards compatible with the version currently running. Expand, then contract. To rename a column you add the new column, deploy code that writes both and reads the new one with a fallback, backfill, deploy code that only uses the new column, and only then — in a later release, after you are certain no rollback target needs it — drop the old one. A migration that drops or renames in the same release as the code change cannot be rolled back, because rolling the code back leaves it staring at a schema that no longer has its column.

Run migrations as an explicit pipeline step, not as an application startup hook: a Kubernetes Job that runs Flyway or Liquibase before the new pods roll, so a failed migration fails the deploy loudly instead of crash-looping ten replicas. Then choose a rollout strategy for the code itself. A canary sends a small percentage of live traffic to the new version and promotes only if the error rate and latency hold; blue-green stands up a complete parallel environment and flips traffic in one atomic switch, which makes rollback instant but doubles your compute during the cut-over. Argo Rollouts implements both as drop-in replacements for a Deployment, with automated analysis and automatic abort.

Metrics: Micrometer to Prometheus

Every Spring Boot service already has Micrometer; expose /actuator/prometheus, add a ServiceMonitor or a scrape annotation, and Prometheus collects it. What you get free is worth knowing: JVM heap and garbage collection, thread pools, HikariCP connection pool saturation, HTTP server request counts and latency histograms per endpoint and status, Kafka consumer lag, and every Resilience4j circuit breaker's state. What you must add yourself are the business counters that make an incident diagnosable — orders placed, payments authorised, payments declined, carts abandoned, inventory reservations failed.

Name them properly, because metric names are an API you will live with. Follow the Prometheus conventions: a single-word application prefix, a unit suffix, base units (seconds not milliseconds, bytes not megabytes), and _total on counters. Keep label cardinality under control — a label whose value is a user id or an order id will multiply your time series into the millions and take Prometheus down. That cardinality mistake is one of the most common real-world production incidents caused by well-meaning instrumentation.

Dashboards as code, and logs that join up with traces

Dashboards built by clicking in the Grafana UI are lost the first time the pod is rescheduled with an empty volume. Provision them instead: keep dashboard JSON in the repository, mount it through Grafana's provisioning directory, and treat a dashboard change like any other code change — reviewed in a pull request. Build four for this project: a service overview with the RED signals (rate, errors, duration) per service, a Kubernetes cluster view (node and pod resource usage, restarts, pending pods), a data-layer view (connection pool saturation, replication lag, Kafka consumer lag), and a business view (orders per minute, checkout conversion, payment decline rate). The last one is the dashboard a non-engineer will look at, and the one that tells you fastest that something is genuinely wrong.

Logs go to Loki, shipped by Alloy or Promtail as a DaemonSet. The single change that makes them useful is structured JSON output with the trace id and span id in every line — Spring Boot's Micrometer Tracing puts them in the MDC automatically once tracing is wired up. With that in place, Grafana can jump from a slow span in a trace straight to the log lines that span emitted, and from a suspicious log line to the full distributed trace of that request. Without it you are grepping across seven services by timestamp, which is exactly the experience distributed tracing exists to abolish.

Traces, SLOs and burn-rate alerts

Instrument with OpenTelemetry rather than a vendor SDK, and route everything through an OpenTelemetry Collector deployed in the cluster. The collector is the piece that makes this architecture durable: applications talk OTLP to one endpoint, the collector batches, samples, enriches with Kubernetes metadata, and exports onward — to Tempo, Jaeger, or a commercial backend — so swapping your tracing vendor is a collector config change rather than a redeploy of every service. For Java, the OpenTelemetry agent instruments Spring MVC, WebClient, JDBC and Kafka with no code changes at all, which is the fastest possible route to a useful trace.

Then define service level objectives, because "the site is slow" is not an alertable condition. Two are enough for this system: a checkout success rate objective (for example, 99.5% of checkout requests succeed over a rolling 30-day window) and a latency objective (95% of checkout requests complete within 800 milliseconds). Each objective implies an error budget, and you alert on the burn rate of that budget rather than on raw thresholds — a fast burn over a short window pages someone immediately, a slow burn over a long window opens a ticket. That two-window approach is what stops alert fatigue, and it is why on-call engineers can sleep. Route the page somewhere a human actually sees it, and test the routing before you need it.

Building it

Delivery phases

Ten phases, each ending in something that runs. Do not skip ahead: every phase depends on the previous one working, and the ordering is deliberately front-loaded with the free local steps so you spend money only once you know what you are doing.

  1. Containerise everything and run the full stack in Compose. Multi-stage Dockerfiles, a non-root user, a JRE base image, and a docker compose up that brings up every service plus Postgres, Kafka and Redis. Done when a fresh clone plus one command gives a working checkout.
  2. A local Kubernetes cluster with hand-written manifests. kind or k3d, one namespace, plain Deployments and Services, an ingress controller, probes and resource requests. Done when the same checkout works through the ingress.
  3. Helm or Kustomize with environment overlays. Collapse the copy-pasted manifests into one definition plus a dev and a staging overlay. Done when the only difference between environments is the overlay file.
  4. Terraform for the cloud foundation. Remote state with locking, the network and cluster modules, one environment. Done when terraform apply from an empty account produces a cluster you can reach with kubectl, and terraform destroy removes every trace of it.
  5. Managed data services and secrets. RDS with multi-AZ and backups, Redis, Kafka, the secrets manager, and the External Secrets Operator wiring. Done when no credential exists anywhere in the repository.
  6. The CI/CD pipeline to staging. Build once, scan, sign, push, OIDC-federated deploy, smoke test. Done when merging a pull request puts the new image in staging with no human touching a terminal.
  7. The observability stack. Prometheus, Grafana with provisioned dashboards, Loki, the OpenTelemetry Collector and Tempo. Done when you can start from a slow checkout on a dashboard and reach the exact log line, through the trace, in under a minute.
  8. Production, gated, with a progressive rollout. A production environment with required reviewers, and a canary or blue-green strategy with automated analysis. Done when a deliberately broken build is rejected by the canary and rolled back without you intervening.
  9. The disaster-recovery drill and the write-up. The graduation exercise, below.
  10. A cost-optimisation pass. Right-size everything you guessed at in phase 4 and cut the bill. Done when you can state the before and after figure and justify every remaining line.

The graduation exercise: define RTO and RPO, then run the drill

Start with the two numbers, written down and agreed before you touch anything. RTO, the recovery time objective, is how long the business can tolerate the system being down. RPO, the recovery point objective, is how much data the business can tolerate losing. For this project, propose something like a 30-minute RTO and a 5-minute RPO for the order and payment data, and then check whether your architecture can actually deliver them: automated RDS backups plus point-in-time recovery gives you an RPO in the low minutes, but a restore of a large database can take far longer than 30 minutes, which means your stated RTO may be a fiction. Discovering that mismatch on paper, before an incident, is the entire point of writing the numbers down.

Then run the drill, in this order, recording the wall-clock time and what you observed at each step:

  1. Kill a pod. Delete one running replica and watch the ReplicaSet reschedule it. Did any in-flight request fail? If yes, your readiness probe or your graceful-shutdown handling is wrong.
  2. Drain a node. Cordon and drain a worker while traffic flows. Did your PodDisruptionBudget hold, or did a service lose all replicas at once?
  3. Fail over the database. Trigger a multi-AZ failover on RDS. How long was the write outage, and did your connection pool recover on its own or did the pods need a restart?
  4. Restore a backup into a fresh environment. Not a test of the snapshot's existence — an actual restore into a new instance, followed by a row-count and checksum comparison against the source. Time it. This is the step that most often reveals the RTO was fantasy.
  5. Simulate an availability-zone loss. Remove the nodes in one AZ. Did the cluster reschedule into the surviving zone, or were all your replicas on the zone that just vanished because you never set topology spread constraints?
  6. Roll back a bad deploy. Ship a deliberately broken build to production and recover — via canary abort, helm rollback, or a git revert under Argo CD. Time from bad deploy to healthy, and note whether an in-flight database migration made rollback harder than it should have been.

The write-up is the real deliverable

When the drill is over, write it up. Not a success report — an honest one. For each of the six exercises: what you expected, what actually happened, the measured time, what broke, and what you would change. The write-up is the artifact you show people. Anyone can put "deployed microservices to Kubernetes" on a CV; almost nobody can say "our stated RTO was 30 minutes, the database restore took 47, so we moved to a warm standby replica and re-measured at 6". That sentence is a hiring signal, and it is the thing this capstone exists to give you.

Once the manual drill works, automate a small piece of it. A chaos experiment that kills a random pod on a schedule, or introduces 200 milliseconds of network latency between two services, turns resilience from something you assert into something continuously verified. Start with pod-kill — it is safe, it is fast, and it catches the single most common bug in this architecture, which is a service that cannot tolerate its own dependency restarting. And when a real incident does happen, write a blameless postmortem in the same format: the discipline of recording what happened without hunting for someone to blame is what makes a team learn from an outage instead of quietly repeating it.

The cost-optimisation pass

Phase 10 is a real engineering exercise, not an afterthought, and "how would you halve this bill" is a question senior candidates get asked constantly. Work from measurement rather than instinct: pull the actual CPU and memory usage of every pod over a week and compare it to what you requested. Most first drafts over-request by a factor of two or three, and since requests are what the scheduler reserves, over-requesting means you are paying for nodes to hold air. Right-size the requests, and the same workload fits on fewer nodes.

Then attack the big line items in order. Consolidate NAT gateways, or remove them entirely by using VPC endpoints for S3 and ECR traffic. Move non-production node groups to Spot instances, which are dramatically cheaper and perfectly appropriate for workloads that can tolerate interruption. Replace a fixed node group with Karpenter so nodes are provisioned to fit pending pods and removed when empty, instead of sitting idle overnight. Scale dev and staging to zero replicas outside working hours — for a learner, this alone is often the single largest saving. Downsize the RDS instance class and drop multi-AZ in non-production. Set S3 lifecycle rules on logs and old artifacts. Finally, attribute the remaining spend per namespace with OpenCost so you can point at which service costs what, which is the conversation that actually changes behaviour.

Closing the course

That is the tenth capstone and the last page of the curriculum. Step back and look at what the ten of them add up to. You started with an expense tracker — Boot, JPA, Angular, a login — and ended with a distributed system running on managed cloud infrastructure that you defined in code, shipped through a gated pipeline, instrumented well enough to debug from a dashboard, and then deliberately broke to find out what was actually true. In between you built an admin dashboard with signal-based state, an inventory system with real transactional concurrency and a full test pyramid, a job portal with search at scale, an HR system with workflows and audit logging, a real-time stock dashboard, a banking application where correctness was the feature, an e-commerce platform end to end, and a strangler-fig migration from that monolith to services.

What you can now legitimately claim is not a list of technologies. It is that you have made the decisions: chosen a consistency model and lived with it, picked a rollout strategy and rolled something back, sized a thread pool, named a metric, written a migration that survived a rolling deploy, and measured a recovery instead of assuming one.

Present them accordingly. On a CV, one line per project: the problem, the scale or constraint, the one decision you are proudest of, and the measured outcome. Not "built microservices with Spring Boot and Kafka" but "split a monolith into seven services using a strangler-fig migration; kept checkout available throughout; reduced deploy lead time from a weekly release to under an hour". In an interview, the tradeoffs are the story and the feature list is noise — a candidate who says "we chose eventual consistency for the inventory count and accepted occasional oversell, because the alternative was a distributed transaction on the checkout path" has already outperformed a candidate reciting a stack. Have the DR write-up and one architecture diagram ready to share; both invite exactly the questions you want to be asked. And be equally ready to say what you would do differently, because that answer is the one that signals seniority.

What to learn next, in rough order of return on effort:

  • Depth in one data store rather than breadth across five — Postgres internals (query plans, indexes, vacuum, replication) pays back on every project you will ever touch.
  • Performance work as a discipline: profiling a JVM, reading a flame graph, load-testing to find the actual bottleneck rather than the assumed one.
  • Platform and reliability engineering: service meshes, multi-region topologies, capacity planning, and running a real on-call rotation.
  • Security beyond the checklist: threat modelling your own designs, and the supply-chain end of it — SBOMs, provenance attestation, and verifying signatures at admission.
  • The part nobody teaches: writing design documents your colleagues can review, and reviewing theirs well. It is the highest-leverage skill on this list.

Interview questions

When this project is on your CV, the interviewer will not ask you what Kubernetes is — they will assume you deployed something and probe whether you understood it. These are the questions that separate a candidate who ran the commands from one who made the decisions, weighted towards Indian product and service-company rounds:

Beginner Walk me through what happens when you merge a pull request to main on this project.

CI builds and unit-tests, runs integration tests, scans dependencies, builds a container image tagged with the commit SHA, scans and signs that image, and pushes it to the registry. The workflow then assumes a short-lived AWS role via OIDC and deploys that exact image to staging, runs a smoke test against the deployed staging URL, and stops at a manual approval gate. After a reviewer approves, a migration job runs, then the same image rolls out to production as a canary. The key point is that one artifact is built once and promoted; production never rebuilds.

Beginner Why did you use Terraform instead of clicking through the AWS console?

Reproducibility and review. The console gives you infrastructure nobody can recreate and changes nobody can audit. With Terraform the whole environment is a reviewable diff, a second environment is a new state file rather than a week of clicking, drift is detectable, and teardown is one command — which for a learner also means you stop paying the moment you finish. It also makes the DR drill possible at all: recovering into a fresh environment requires the environment to be code.

Beginner What is the difference between a liveness and a readiness probe, and what goes wrong if you confuse them?

Readiness decides whether a pod receives traffic; liveness decides whether it gets restarted. Confuse them and you get a cluster-wide outage: if liveness checks a downstream dependency and that dependency has a blip, Kubernetes restarts every replica of every service that depends on it, turning a small degradation into a full outage. Liveness should check only that the process itself is alive and not deadlocked; readiness can be as strict as you like because failing it merely removes the pod from the load balancer.

Intermediate You have a rolling deploy and a schema change. How do you avoid breaking the old version?

Expand and contract. During a rolling deploy both versions run against one database, so every migration must be backwards compatible with the currently deployed code. Add the new column, deploy code that dual-writes and reads the new column with a fallback, backfill existing rows, deploy code that uses only the new column, and drop the old column in a later release once no rollback target needs it. Migrations run as an explicit pipeline job before the pods roll, not on application startup, so a failure blocks the deploy instead of crash-looping the fleet.

Intermediate How do you roll back a bad production deploy, and how fast is it?

Three layers. The canary aborts automatically if error rate or latency breaches the analysis thresholds, so most bad deploys never reach full traffic. If it gets through, it is helm rollback to the previous release, or under GitOps a git revert that Argo CD reconciles — both under a minute because the previous image is still in the registry and the previous manifest is still in history. The hard case is a deploy that already ran a destructive migration; that is why migrations are expand-only, so the code can always go back even when the schema has moved forward.

Intermediate Your pipeline deploys to AWS. Where are the AWS credentials stored?

Nowhere. GitHub is registered as an OIDC identity provider in IAM, and the workflow exchanges a short-lived GitHub-issued token for temporary AWS credentials at runtime. The IAM role's trust policy pins the subject to a specific repository and environment, so a pull request from a fork or an unrelated branch cannot assume it. The credentials last minutes and are never written down — which removes the single most common cause of cloud breaches, a long-lived access key leaked from a repository or a log.

Intermediate Why is the database managed rather than a pod in the cluster?

Because the operational work is the product. Managed Postgres gives automated backups, point-in-time recovery, a tested multi-AZ failover, patching and monitoring — all of which I would otherwise have to build and, more importantly, verify. A stateful database on cluster storage also inherits the cluster's failure modes: a node eviction or a bad upgrade becomes a data incident. The tradeoff is cost and less control over configuration, which is a fair price for not owning failover.

Intermediate Terraform or the pipeline — which one applies your Kubernetes manifests, and why?

The pipeline, or a GitOps controller — not Terraform. The dividing line is lifecycle. Terraform owns things that change monthly: networks, clusters, databases, DNS, IAM. Applications change several times a day, and putting them in Terraform means every release churns infrastructure state, every rollback becomes an infrastructure rollback, and a plan output becomes unreadable. Keeping them separate also keeps the blast radius separate: a bad app deploy cannot touch the VPC.

Pro What are your RTO and RPO, and how do you know they are real?

Stated: a 30-minute recovery time objective and a 5-minute recovery point objective for order and payment data. Known, because we measured them rather than asserted them — we restored a backup into a fresh environment and timed it end to end, then compared row counts and checksums against the source. RPO is credible because point-in-time recovery on RDS has a granularity in the low minutes. RTO was the number that failed: the restore took longer than the objective, so either the objective moves or the architecture does, and both are legitimate answers as long as the number is measured.

Pro Tell me what actually broke during your disaster-recovery drill.

This is the question the project exists to answer, and a specific answer beats a polished one. Typical genuine findings: pod deletion dropped in-flight requests because the app did not handle SIGTERM with a graceful shutdown; a node drain took a service to zero replicas because there was no PodDisruptionBudget; the connection pool did not recover after an RDS failover until pods were restarted; all replicas of one service were scheduled in the AZ that was removed because no topology spread constraint existed; and the restore took longer than the stated RTO. Each of those is a real fix, and describing the fix is what demonstrates you ran the drill instead of reading about it.

Pro Your monthly cloud bill is $400. Halve it without dropping availability.

Measure first: compare actual pod CPU and memory usage against requests over a week — most workloads over-request by two to three times, and since requests are what the scheduler reserves, right-sizing them alone consolidates nodes. Then the big line items: remove or consolidate NAT gateways using VPC endpoints for S3 and ECR; move non-production node groups to Spot; replace the fixed node group with Karpenter so nodes bin-pack and scale to zero; scale dev and staging to zero replicas outside working hours; downsize the RDS class and drop multi-AZ in non-production only; add S3 lifecycle rules on logs. Then attribute spend per namespace with OpenCost so the next conversation is evidence-based. Production availability is untouched because every change targets idle capacity and non-production.

Pro You chose Argo CD over pushing deploys from CI. Defend it — and say what it cost you.

The gains: CI no longer needs standing cluster credentials, which removes a large piece of attack surface; the manifests repository is a single declarative source of truth, so what is running is always inspectable in git; drift is detected and reconciled continuously rather than discovered during an incident; rollback is a revert, and the audit trail is the git log. The costs: a second repository and the commit-back step that keeps them in sync; a controller to operate and upgrade; a longer and less obvious path from merge to running pod, which makes first-time debugging harder; and secrets management gets more awkward because plain secrets cannot live in the manifests repository, so you need External Secrets or sealed secrets. For a solo project push deploys are entirely defensible; the GitOps case gets stronger with every additional engineer and cluster.

Pro A checkout request is slow in production. Walk me through your first five minutes.

Start at the service overview dashboard: is it rate, errors or duration, and is it one service or all of them? If latency is up on one service only, open a slow trace in Tempo and look at the span breakdown — a slow JDBC span points at the database, a slow client span points at a downstream, a large gap between spans points at thread-pool queuing or garbage collection. Jump from that span to its logs, which carry the same trace id. In parallel check the obvious infrastructure signals: connection pool saturation, Kafka consumer lag, pod restarts, CPU throttling from a too-low limit, and whether any circuit breaker has opened. Five minutes is enough because the dashboards, traces and logs are joined by trace id — if they were not, this would be twenty minutes of grep.

Pro How do you keep three environments identical, and what legitimately differs?

One definition plus per-environment overlays or values files, so there is no copy-pasted YAML to drift. Terraform uses the same modules with separate state per environment, so the shape is shared and only the sizes differ. What legitimately differs: replica counts, resource requests and limits, instance classes, hostnames, log levels, feature flags, and whether multi-AZ is on. What must not differ: the image, the schema version, the deployment mechanism, and the observability configuration. If a bug reproduces in staging but not production — or worse, the reverse — the first thing I check is which of those "must not differ" items quietly did.
