Capstone 07: Banking Application

The security and correctness flagship of the track. Nothing else you build will punish sloppiness the way a ledger does: a rounding error is a lost rupee, a retried request is a duplicated payment, and two threads reading the same balance is a hole in the bank.

What this capstone is — and what it is not

Read this first. This is a learning project, not a production banking system. Real banking runs on regulatory compliance, licensed and certified infrastructure, externally audited controls, settlement networks you cannot simulate, and a legal perimeter that has nothing to do with your code quality. Build this to learn the engineering — the ledger, the concurrency, the idempotency, the authorization model — and then leave it in your portfolio. Do not run other people's money through it.

What you are building is a retail banking core: customers with KYC-style profile data, several accounts each, balance enquiry, internal transfers, scheduled and standing instructions, a paginated statement with a running balance, beneficiary management with a cooling-off period, and an audit trail that explains every rupee that moved and every request that was refused.

The two lessons this brief exists to teach are double-entry ledger modelling and idempotency. Everything else in the feature list is scaffolding around those two. If you finish the project and can defend those two designs in an interview, the capstone has done its job.

The brief

Feature outline, ledger modelling, idempotent transfers and security architecture

The specification below is deliberately small in surface area and deep in correctness. A banking core with eight endpoints that never loses money is a far stronger portfolio piece than one with forty endpoints and a double balance field. Scope ruthlessly: the MVP is the part you must get exactly right, the stretch goals are the part you add once the invariants hold under a concurrency test.

MVP scope

Ship these, in this order of importance. Each is small; the difficulty lives in the guarantees, not the feature count.

  • Customers — profile with name, date of birth, government-ID reference (store a hash or a tokenised reference, never a raw ID number in plain text), address, contact details, and a KYC status field (PENDING, VERIFIED, REJECTED) that gates what the customer may do.
  • Accounts — many per customer, each with a type (savings, current), a currency, a status (active, frozen, closed), and a balance that is derived from the ledger, not typed in.
  • Balance enquiry — current balance plus an available balance (current minus holds), returned with the currency and the minor-unit scale, never as a bare number.
  • Internal transfers — account to account, atomic, idempotent, never permitted to drive an account negative.
  • Scheduled and standing transfers — a one-off future-dated instruction and a recurring one, executed by a scheduler that is itself idempotent (a missed run must be catch-up-able without double-posting).
  • Statement — a paginated list of ledger entries for one account with a running balance, ordered newest first, filterable by date range.
  • Beneficiaries — a payee list with a cooling-off period: a newly added beneficiary cannot receive money until a fixed delay has elapsed and the addition has been confirmed.
  • Audit trail — an append-only record of every money movement, every authorization denial, every beneficiary change and every login attempt.

Stretch goals

Add these only after phase 5 is green. Each is a genuinely different engineering problem rather than more of the same.

  • Multi-currency accounts with FX — a transfer across currencies becomes a four-entry posting (debit source, credit an FX position, debit the FX position, credit destination) so the ledger still sums to zero in every currency independently.
  • Interest accrual — a daily job that posts interest as ordinary ledger entries, with the rounding policy written down and the residual paisa accounted for rather than lost.
  • Statement export — a generated PDF for a date range, produced from the same query as the API so the two can never disagree.
  • Spending analytics — categorised aggregates over the statement, computed with window functions rather than in application memory.
  • Card-block simulation — a card entity with a block/unblock lifecycle, demonstrating that a blocked card rejects an authorisation attempt and that the rejection is audited.

Data model

Eight tables carry the whole MVP. The one that matters is ledger_entry: it is append-only, it has no UPDATE path in the application at all, and every row belongs to a posting whose entries sum to zero.

Ledger modelling: double-entry, done properly

A bank account balance is not a field you edit. It is a conclusion drawn from a list of immutable facts. Double-entry bookkeeping is the five-hundred-year-old encoding of that idea, and it survives because it makes an entire class of bug structurally impossible: every movement of money is recorded as two or more entries whose signed amounts sum to exactly zero. Money is never created or destroyed by a posting, only relocated. If a bug ever produces entries that do not sum to zero, a single SELECT finds it — which is why the invariant is worth the extra table.

Four rules make the model work, and you should be able to recite all four. One: entries are immutable and append-only — the application's database role gets INSERT and SELECT on ledger_entry and nothing else, so "fixing" a bad entry is not even physically available. Two: a correction is a new posting, not an edit; you reverse with compensating entries and keep both rows, because the audit story is "we moved it, then we moved it back", not "it never happened". Three: the balance is derived — SELECT SUM(amount_minor) FROM ledger_entry WHERE account_id = ? is the definition of truth, and the balance_minor column on account is a cache maintained in the same transaction as the entries, reconciled by a scheduled job that compares the two and screams on a mismatch. Four: a posting is the unit of atomicity — either all of its entries commit or none do.

Two ledgers are worth naming for interviews. In a single-entry design each transfer writes one row per account with no linkage; nothing forces the two sides to agree, and a partial failure silently destroys money. In a double-entry design the linkage is the point. Real systems go further and model the bank's own accounts explicitly (a cash account, a fees account, an FX position account) so that even a fee or an interest payment has a counterparty inside the ledger rather than appearing from nowhere.

-- One transfer of 250.00 INR = 25000 paisa: two entries, sum zero.
INSERT INTO posting (id, kind, transfer_id, posted_at, description)
VALUES ('p-1', 'TRANSFER', 't-1', now(), 'UPI to beneficiary');

INSERT INTO ledger_entry (posting_id, account_id, amount_minor, currency) VALUES
  ('p-1', 'acct-source', -25000, 'INR'),   -- debit
  ('p-1', 'acct-target',  25000, 'INR');   -- credit

-- The invariant, checkable at any time over the whole database:
SELECT posting_id, SUM(amount_minor) AS imbalance
FROM ledger_entry GROUP BY posting_id HAVING SUM(amount_minor) <> 0;
-- must return zero rows, forever

-- Truth vs cache: this must also return zero rows.
SELECT a.id FROM account a
JOIN (SELECT account_id, SUM(amount_minor) s FROM ledger_entry GROUP BY account_id) l
  ON l.account_id = a.id
WHERE a.balance_minor <> l.s;

Money: integer minor units, an explicit currency, and never a float

Store an amount as a BIGINT count of the currency's minor unit — paisa for INR, cents for USD — paired with an ISO-4217 currency code. Two hundred and fifty rupees is 25000 paisa and the string "INR". Never double or float: binary floating point cannot represent 0.1 exactly, so 0.1 + 0.2 is not 0.3, and the error compounds across a million rows into a real, reportable discrepancy. If you must use BigDecimal — for an interest calculation, say — construct it from a string or an integer (never from a double), pin an explicit scale, and pass an explicit RoundingMode to every division. A BigDecimal with an implicit scale is the same bug wearing a suit.

Wrap the pair in a Money value object and make it the only money type in the domain: immutable, currency-checked on every operation (adding INR to USD must throw, not coerce), with a documented allocation method for splitting an amount that does not divide evenly. Splitting 100 paisa three ways gives 34, 33, 33 — not 33.33 three times — and deciding who gets the extra paisa is a business rule you write down, not a rounding accident. Currencies also differ in scale: JPY has zero decimal places, most have two, a few have three, so hard-coding "multiply by 100" is a bug waiting for your first international customer.

public record Money(long minor, Currency currency) {
    public Money {
        Objects.requireNonNull(currency);
    }
    public Money plus(Money other) {
        if (!currency.equals(other.currency))
            throw new CurrencyMismatchException(currency, other.currency);
        return new Money(Math.addExact(minor, other.minor), currency);  // overflow throws
    }
    public boolean isNegative() { return minor < 0; }
}
// Never: double balance; Never: new BigDecimal(0.1); Never: amount / 3 without RoundingMode

Transactions, locking, and the negative-balance invariant

A transfer touches two accounts and must be all-or-nothing. That means one database transaction, opened once at the application-service boundary, containing the balance check, both ledger entries, both cached-balance updates and the transfer row. The single most common bug in student banking projects is reading the balance in one transaction and writing the debit in another: between the read and the write, a concurrent transfer spends the same money, and both requests succeed. The check and the debit must be in the same transaction, and the row must be locked for the duration.

Lock with SELECT ... FOR UPDATE (JPA's PESSIMISTIC_WRITE) on both account rows before touching anything. Two concurrent transfers between the same pair of accounts in opposite directions will deadlock if each locks its own source first — A→B locks A then B while B→A locks B then A, and the database kills one of them. The fix is consistent lock ordering: sort the two account ids and always acquire in that order, regardless of which is the source. It costs three lines and removes the deadlock class entirely. Keep the locked section short, never call a remote service inside it, and set a lock timeout so a stuck transaction fails loudly rather than hanging the pool.

On isolation: PostgreSQL's default READ COMMITTED is sufficient because you hold row locks — the lock, not the isolation level, is what serialises the two transfers. REPEATABLE READ or SERIALIZABLE buy you protection against phantoms and write skew at the cost of serialisation failures your code must catch and retry; they are the right answer when the invariant spans rows you cannot lock individually (a per-customer daily limit across many accounts, for instance). Being able to explain that trade-off — locks versus isolation level, and when each is the right tool — is a senior-level answer.

Finally, enforce the negative-balance invariant twice. In the service, so the caller gets a clean 422 with a business error code. In the database, as a CHECK (balance_minor >= 0) constraint, so that a bug, a bad migration, a manual fix or a future code path that forgot the rule fails with a constraint violation instead of quietly overdrawing an account. Belt and braces is not redundancy here; the database constraint is the one that survives your refactors.

@Transactional  // one transaction: check + debit + credit + entries, or nothing
public TransferResult transfer(TransferCommand cmd) {
    // Consistent lock ordering by id kills the A->B / B->A deadlock class.
    List<UUID> ids = Stream.of(cmd.sourceId(), cmd.targetId()).sorted().toList();
    Account first  = accounts.findByIdForUpdate(ids.get(0));   // PESSIMISTIC_WRITE
    Account second = accounts.findByIdForUpdate(ids.get(1));

    Account source = first.getId().equals(cmd.sourceId()) ? first : second;
    Account target = source == first ? second : first;

    if (source.balance().minor() < cmd.amount().minor())
        throw new InsufficientFundsException(source.getId());   // -> 422, audited

    ledger.post(Posting.transfer(source, target, cmd.amount()));  // two entries, sum 0
    source.debit(cmd.amount());   // cached balance, same transaction
    target.credit(cmd.amount());  // DB CHECK constraint is the second line of defence
    return TransferResult.posted(cmd.transferId());
}

Idempotent transfers: the retry that must not move money twice

Here is the scenario the whole design exists for. A customer taps "Send". The request reaches your server, the transfer commits, and then the response is lost — a flaky mobile network, a load-balancer timeout, a client that gave up at four seconds. The app shows an error. The customer taps "Send" again. A timeout is ambiguous: the client cannot distinguish "never arrived" from "succeeded but the answer was lost". If your API is not idempotent, the customer has now paid twice, and you will find out from a support ticket rather than from your monitoring.

The fix is an idempotency key carried end to end. The client generates it — a UUID, created once per user intent and reused across every retry of that intent (this is the part people get wrong: a key generated fresh on each retry is not a key, it is a nonce). The client sends it as an Idempotency-Key header. The server stores the key together with a fingerprint of the request (a hash of the canonical body plus the authenticated user) and, once complete, the full response status and body. Then four rules follow:

  • Replay — same key, same fingerprint, request already completed: return the stored response verbatim, with the same status code, and do not touch the ledger. The client cannot tell it was a replay, which is exactly the point.
  • Concurrent duplicate — same key arrives while the first is still in flight: return 409 Conflict and let the client poll. Do not queue behind it and do not execute; the unique constraint on the key is what makes this race safe, so insert the key row first and let the database referee.
  • Key reuse with a different body — same key, different fingerprint: reject with 422 and a distinct error code. Silently returning the first response would be worse than failing, because the client believes a payment it never authorised has succeeded.
  • Expiry — keys are kept for a bounded window (24 hours is a common choice) and then purged. A key is a deduplication device with a lifetime, not permanent storage; document the window in your API docs so clients know when a retry stops being safe.

Store the key row in the same database transaction as the ledger entries. If the key lives in Redis and the money lives in PostgreSQL, a crash between the two commits leaves you with a key that claims success and a ledger that disagrees — you have moved the race, not removed it. Redis is fine as a fast pre-check in front of the durable record; it is not fine as the record.

// Insert-first: the unique constraint, not application logic, decides the race.
try {
    keys.insertInProgress(key, userId, endpoint, fingerprint(request));
} catch (DuplicateKeyException e) {
    IdempotencyRecord existing = keys.require(key, userId);
    if (!existing.fingerprint().equals(fingerprint(request)))
        throw new IdempotencyKeyReusedException();          // 422, different body
    if (existing.isInProgress())
        throw new RequestInFlightException();               // 409, retry later
    return existing.storedResponse();                       // replay: byte-identical
}
// same @Transactional scope as the ledger write; response is persisted on commit

The transfer state machine: reverse, never delete

Give the transfer an explicit lifecycle and store it: INITIATED (accepted, key recorded, nothing posted) → POSTED (entries written, money moved) or FAILED (rejected for insufficient funds, a frozen account, a failed limit check — recorded with a reason, never silently dropped) → REVERSED (a compensating posting has undone it). Transitions are a small table you can test exhaustively, and every transition writes an audit event.

The rule that matters: you reverse, you do not delete. A reversal is a new posting with the opposite entries, linked to the original by reversal_of_transfer_id. Both survive in the statement, and the customer sees the debit and the credit — which is what every real bank statement shows, and what a regulator or an auditor requires. Deleting a row destroys the answer to "what happened here", and once you have deleted it you can never prove the system behaved correctly. The same discipline explains why the ledger has no UPDATE: an append-only history is the only history you can trust.

Security architecture

Treat this section as an integration exercise: the depth lives in the Secure Coding and Spring Security tracks, and this project is where you assemble it. The shape to build:

  • Tokens — short-lived access tokens (five to fifteen minutes) plus a refresh token with rotation and reuse detection: each refresh issues a new refresh token and invalidates the old one, and presenting an already-used refresh token revokes the whole family, because that is the signature of a stolen token. Configure the app as an OAuth2 resource server rather than hand-rolling a filter; opaque tokens with introspection are the more conservative choice for a bank because they can be revoked instantly, while JWTs trade revocability for statelessness — pick one deliberately and be able to say why.
  • Authorization — method-level rules with @PreAuthorize, but the ownership predicate belongs in the query: findByIdAndCustomerId(accountId, principal), not "load the account, then check". Filtering after loading is how insecure direct object reference bugs are born, and it leaks existence through timing and error differences. Return the same 404 for "does not exist" and "not yours".
  • Step-up for high value — a transfer above a configured threshold, or to a beneficiary added recently, requires a fresh second factor or a signed confirmation. Model it as a challenge the API issues and the client answers, and record the challenge in the audit trail.
  • Rate limiting — on login (per account and per IP, with progressive delay and lockout) and on the transfer endpoint (per user). Login limiting blunts credential stuffing; transfer limiting blunts an attacker who already has a token.
  • Audit logging — every money movement, every authorization denial, every beneficiary change, every login success and failure. Denials matter as much as successes: a burst of denials is the clearest signal you have that something is being probed. Log structurally, never log a token or a full account number, and make the audit table append-only like the ledger.
  • Secrets and transport — no credentials in application.yml and none in the repository; a vault or a cloud secret manager, injected at runtime, rotated on a schedule. TLS on every hop including service-to-database. Encrypt sensitive PII columns at rest and store identity documents as tokenised references or hashes rather than plaintext.

Suggested build phases, reference implementations and the module map

Every phase below ends in something you can run and show. That constraint is not decoration: it is what stops a capstone from becoming a half-finished schema with no demo. Commit at the end of each phase, write the test named in the phase before you move on, and resist adding features until phase 5 is green.

The ten phases

  1. Schema and skeleton. Customer, account and the ledger tables, created by versioned migrations (Flyway or Liquibase) — never by ddl-auto. Add the CHECK (balance_minor >= 0) constraint now, before any code can violate it. Demo: migrations run clean on an empty database, and an INSERT with a negative balance is rejected by PostgreSQL.
  2. Ledger service. Double-entry posting and balance derivation, with no HTTP layer yet. Demo: a test posts a balanced entry pair, derives the balance from the entries, and proves an unbalanced posting is refused. Test: the sum-to-zero invariant over a randomly generated posting set.
  3. Transfer use case. Locking with consistent id ordering, the balance check inside the transaction, the negative-balance invariant enforced in both service and database. Demo: a transfer moves money and an over-limit transfer returns a clean business error.
  4. Concurrency proof. The phase that makes the project worth talking about. Fire N parallel transfers out of one account with a real PostgreSQL container, then assert that the ledger still sums to zero, the account never went negative, and exactly the expected number succeeded. Demo: a red test on the naive implementation, green on the locked one. Keep the naive version on a branch so you can show the failure.
  5. Idempotency. Key storage, fingerprinting, replay, conflict and expiry, written in the same transaction as the ledger. Demo: the same request sent three times moves money once and returns three identical responses; a different body with the same key is rejected.
  6. Authentication and authorization. Resource-server configuration, refresh rotation, ownership pushed into the query, login rate limiting. Demo: customer A cannot see, or transfer from, customer B's account, and the denial is audited.
  7. Statements. Keyset (seek) pagination on (created_at, id) rather than OFFSET, with the running balance computed by a window function in SQL. Demo: stable pagination over a hundred thousand seeded entries, with the query plan showing an index scan.
  8. Beneficiaries with cooling-off. Pending state, an activates-at timestamp, confirmation with step-up, and a transfer to a not-yet-active beneficiary refused. Demo: the refusal, then the same transfer succeeding after the clock is advanced.
  9. Audit and observability. Append-only audit events, structured logs with a correlation id, metrics for transfer volume and failure rate, traces across the request. Demo: a dashboard panel showing transfers per minute and a trace of one transfer end to end.
  10. Angular UI. Login, account list, balance, statement with infinite scroll over the keyset cursor, and a transfer form with an idempotency key generated once per submission attempt and reused on retry. Demo: the full customer journey in a browser.

Then phase 11: one stretch goal, chosen for the engineering you want to learn rather than the screenshot. Multi-currency FX teaches you the four-entry posting; interest accrual teaches you rounding policy and residuals. Both are better interview material than a PDF exporter.

Definition of done

The capstone is finished when all of the following hold, and not before. Each one is a sentence you can say in an interview.

  • Every posting in the database sums to zero, and a test asserts it after a randomised workload.
  • The cached balance on every account equals the sum of its ledger entries, checked by a reconciliation job.
  • A parallel-transfer test against a real PostgreSQL container never overdraws an account and never loses a rupee.
  • Sending the same transfer request three times moves money exactly once and returns three identical responses.
  • No float, double or scale-less BigDecimal appears anywhere in the money path.
  • The application's database role has no UPDATE or DELETE grant on ledger_entry or audit_event.
  • Customer A receives an identical 404 whether customer B's account exists or not, and the denial is in the audit log.
  • No secret is in the repository, and the README explains where secrets actually come from.

Interview questions

An interviewer sees "banking application" on your CV and immediately knows which questions separate a CRUD project from an engineered one. These are the ones asked in Indian product and service-company rounds — the ledger and the retry questions come up almost every time:

Beginner How do you store a monetary amount, and why not a double?

As a signed integer count of the currency's minor unit — paisa, cents — in a BIGINT, paired with an ISO-4217 currency code. Binary floating point cannot represent decimal fractions like 0.1 exactly, so arithmetic drifts and the error compounds across millions of rows into a reportable discrepancy. If a calculation genuinely needs decimals, use BigDecimal constructed from a string or integer, with an explicit scale and an explicit RoundingMode on every division. Also: currencies differ in scale, so hard-coding a factor of 100 breaks on JPY.

Beginner Why did you model the ledger as double-entry instead of just updating a balance column?

Because it makes an entire class of bug structurally impossible. Every movement is two or more entries whose signed amounts sum to zero, so money cannot be created or destroyed by a posting, and a one-line query over the whole database finds any violation. It also gives a complete, immutable history: the balance is a conclusion derived from the entries rather than a field someone can overwrite. A single mutable balance column has no counterparty, no audit story, and no way to prove after the fact that it is correct.

Beginner Where is the transaction boundary in your transfer, and why there?

One transaction opened at the application-service method, containing the row locks, the balance check, both ledger entries, both cached-balance updates, the transfer row and the idempotency key record. It is there because the balance check and the debit must be atomic — if they are in separate transactions, a concurrent transfer spends the same money between them and both succeed. The boundary is not in the controller and not in the repository; putting it in either is a classic review finding.

Beginner Why is the account balance both derived from the ledger and stored in a column?

The sum over the ledger entries is the definition of truth, but summing millions of rows on every balance enquiry does not scale. So the column is a cache, updated inside the same transaction as the entries, and a scheduled reconciliation job compares the two and alerts on any mismatch. That gives fast reads plus a continuous, automated proof that the cache has not drifted — which is exactly the answer an interviewer is fishing for.

Intermediate A client times out and retries a transfer. How do you guarantee the money moves once?

An idempotency key generated by the client once per user intent and reused on every retry, sent as a header. The server inserts the key row first — the unique constraint referees the race — storing the key, the authenticated user, and a fingerprint of the request. If the key already exists and the request completed, return the stored response verbatim without touching the ledger. If it is still in flight, return 409 and let the client poll. If the fingerprint differs, reject with 422. Keys expire after a documented window. Critically, the key row is written in the same database transaction as the ledger entries.

Intermediate Why store a request fingerprint alongside the key rather than just the key?

To catch key reuse with a different payload. A buggy or malicious client can send the same key with a different amount or destination; without a fingerprint you would return the first response and the client would believe a transfer it never requested has succeeded. Comparing a hash of the canonical body plus the authenticated principal lets you reject that with a distinct error code, which is both safer and far easier to debug than a silent replay.

Intermediate How did you avoid deadlocks between two concurrent transfers?

Consistent lock ordering. A transfer from A to B and a simultaneous transfer from B to A will deadlock if each locks its own source first, because each holds what the other needs. So before locking anything I sort the two account ids and acquire the row locks in that fixed order regardless of direction. Every transaction in the system therefore takes account locks in the same global order, which makes a cycle impossible. Beyond that: keep the locked section short, never make a remote call while holding a lock, and set a lock timeout so a stuck transaction fails loudly.

Intermediate Which isolation level did you choose, and why was it sufficient?

PostgreSQL's default READ COMMITTED, because the correctness here comes from the explicit row locks, not the isolation level — SELECT ... FOR UPDATE serialises the two transfers touching the same account. I would move to REPEATABLE READ or SERIALIZABLE for an invariant that spans rows I cannot lock individually, such as a per-customer daily limit computed across many accounts, where write skew is possible. That choice costs serialisation failures the application has to catch and retry, so it is a deliberate trade, not a default.

Intermediate Where do you enforce that an account cannot go negative?

In both places. In the service, inside the locked transaction, so the caller gets a clean business error with a specific code rather than a constraint-violation stack trace. And as a database CHECK (balance_minor >= 0) constraint, so that any future code path, migration or manual fix that forgets the rule fails hard instead of quietly overdrawing. The database constraint is the one that survives refactoring, which is why it is not redundant.

Intermediate Why does your statement endpoint use a cursor instead of a page number?

Because OFFSET makes the database count and discard every skipped row, so page 5000 gets progressively slower, and because new entries arriving between requests shift the offsets and cause rows to be duplicated or skipped across pages. Keyset pagination seeks on the last row's (created_at, id) with a matching composite index, so every page costs the same and the result set is stable under concurrent inserts. It also composes naturally with the infinite scroll in the Angular client.

Pro How would you prove to an auditor that no money was lost?

Three checks, all runnable on demand. First, group every ledger entry by posting and assert the signed sum is zero — a non-empty result means a bug created or destroyed money. Second, reconcile every account's cached balance against the sum of its entries. Third, since the ledger is append-only and the application role has no UPDATE or DELETE grant, the history itself is evidence: every reversal exists alongside the original, so the trail explains each state change rather than hiding it. I would run the first two as a scheduled job with alerting, and back them with a randomised concurrency test in CI that asserts the same invariants after a parallel workload.

Pro Why reverse a transaction instead of deleting or editing the row?

Because deleting destroys the answer to "what happened here", and after a delete you can never prove the system behaved correctly. A reversal is a new posting with the opposite entries, linked to the original, so both survive on the statement — which is what a real bank statement shows and what an auditor requires. Editing is worse still: it means a mutable ledger, which means every historical balance you ever reported is unverifiable. The same reasoning is why the application's database role has insert and select on the ledger and nothing more.

Pro How did you test that concurrent transfers cannot double-spend?

An integration test against a real PostgreSQL instance in Testcontainers — an in-memory database will not reproduce real locking behaviour. Seed an account with a known balance, then fire N parallel transfers out of it from a fixed thread pool with a latch so they start together. Assert three things afterwards: exactly the expected number succeeded, the account never went negative, and every posting still sums to zero. I keep the naive unlocked implementation on a branch so the test can be shown failing, which is far more convincing in an interview than a passing test alone.

Pro JWT or opaque tokens for a banking API — defend your choice.

The trade is revocability against statelessness. A JWT is validated locally with no round trip, which scales well, but it stays valid until it expires — so revoking a compromised session means a short expiry plus a denylist, which reintroduces the state you were avoiding. Opaque tokens with introspection are revocable instantly, at the cost of a call to the authorization server on each request, usually mitigated by a short-lived cache. For money movement I lean opaque, or JWTs with a very short expiry plus refresh rotation and reuse detection: a refresh token can only be used once, and presenting a used one revokes the whole family because that is the signature of theft.

Pro Why is the ownership check inside the query rather than after loading the entity?

Loading first and checking afterwards is how insecure direct object reference bugs happen: one missed check on one code path exposes another customer's data, and the "not found" versus "forbidden" difference leaks whether an account exists. Putting the predicate in the repository method — find by id and owning customer — means the unauthorised row is never in memory, the rule cannot be forgotten on a new endpoint, and the same 404 is returned either way. Method-level annotations layer on top of that, they do not replace it.

Pro Your scheduler runs a standing instruction. How do you stop a double-posting after a missed run or a redeploy?

Derive a deterministic idempotency key from the instruction id and the scheduled run date rather than generating a random one, so a catch-up run for a missed day produces the same key as the original attempt and the second execution replays instead of posting again. Combine that with a scheduler lock so only one instance runs a given job, and store the last successfully executed run date on the instruction. That way a redeploy mid-run, a duplicate trigger and a manual catch-up are all safe by construction rather than by luck.

Pro Why did you build this as a modular monolith rather than microservices?

Because the invariant that matters — a posting sums to zero and commits atomically — is enforced by a single database transaction, and splitting the ledger across services replaces that with a distributed transaction, sagas and compensating actions. That is a real design (it is the next capstone), but it buys operational complexity to solve a scaling problem this system does not have. Keeping the money in one database and the boundaries as packages, enforced by an architecture test, preserves the option to split later without paying for it now.
