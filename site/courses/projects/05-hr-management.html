Capstone 05: HR Management System

Every company you will ever work for runs one of these, and almost every one of them is a mess — because a leave request looks like a CRUD row until the day it has to travel through five states, two approvers, one holidaying manager and an auditor who wants to know who changed the salary field last March. This capstone is about building the version that does not rot.

Knowledge Library → Courses → Real-World Projects → HR Management System

What this capstone is

An HR system for a mid-sized company — say eight hundred employees across six departments — covering employee records and the reporting hierarchy, departments, leave requests with a multi-step approval workflow, timesheets, performance review cycles, document management, and an audit trail over every sensitive change. It is deliberately the least glamorous project in this track and the most interviewable, because it forces three things that a to-do app never will: an explicit workflow, authorization that role checks alone cannot express, and a record of who did what.

This is a brief, not a tutorial. It gives you the scope, the architecture, the data model, the contract and a build order where every phase ends with something you can demonstrate. The engineering judgement — a hand-rolled state machine instead of a workflow engine, an ownership predicate pushed into the query instead of a filter after the fetch, an audit table nothing may update — is the actual deliverable. Build it in Spring Boot with PostgreSQL and an Angular front end; substitute your own stack freely, the design decisions survive the swap.

The brief

Scope: the MVP boundary and the stretch goals

The failure mode of this project is breadth. An HR suite has infinite surface — recruitment, onboarding, payroll, benefits, learning, exit — and a candidate who ships a shallow slice of all of it has demonstrated nothing. Cut hard. The MVP is employees, departments, hierarchy, leave requests with a real approval workflow, and an audit trail. Everything else is a stretch goal you attempt only once those five are genuinely finished, tested and defensible.

The scoped MVP, in the order they become useful: employee records with a manager relationship forming an organizational hierarchy; departments with a head; leave requests carrying a type, a date range, a computed working-day count and a lifecycle; a multi-step approval workflow driven by the hierarchy; and audit rows for every sensitive create, update and delete. Then the second tier, still core but buildable later: timesheets (weekly entries against projects or cost centres, submitted and approved), performance review cycles (a cycle window, self-assessment, manager assessment, calibration, publication) and document management (offer letters, ID proofs, appraisal PDFs with strict access control and virus-scanned uploads).

The stretch goals, each of which adds one distinct hard problem rather than more screens: a payroll summary export (an aggregation report with money in it, so rounding, currency scale and access control all bite at once); an org-chart visualisation (recursive traversal and a tree render that survives a thousand nodes); delegation of approval authority while a manager is away (the most interesting one — it changes who counts as the approver, without changing the workflow definition); and an employee self-service portal (the same data through a narrower lens, which is a pure authorization exercise). Pick one. Two if the first went quickly.

Architecture sketch: one deployable, four bounded slices

Build a modular monolith. There is no distributed-systems problem here worth the operational cost of microservices — the entities are densely joined, the transactions are naturally local, and splitting leave requests from employees would only convert a foreign key into a network call. What you do need is internal boundaries, so that the workflow package never reaches into JPA entities owned by the people package, and the audit module has exactly one way in.

The shape below is the whole system. Note the two rules encoded in it: nothing calls a repository directly from a controller, and every write to a sensitive entity passes through the audit interceptor. Both rules are cheap to hold on day one and impossible to retrofit on day ninety.

The data model

Three decisions dominate the schema. First, the hierarchy: model it as an adjacency list — a nullable manager_id self-reference on employee — and query ancestors and descendants with a recursive CTE. It is the simplest model, the cheapest to reorganise (a manager change is one row update), and PostgreSQL's WITH RECURSIVE handles both directions. Reach for a closure table only if you measure the recursive query as a real bottleneck; for eight hundred employees you will not.

Second, the leave request carries its state as a column plus a separate leave_transition history table — the current state answers "what now?", the history answers "how did it get here?", and an auditor will ask both. Third, audit_log is append-only and stores a before and after snapshot as JSON, keyed by entity type and id rather than by foreign key, so it can outlive the row it describes.

API contract: the endpoints that pin down the design

Write the contract before the code — the endpoint list is where the workflow design becomes visible. Notice what is not here: there is no PUT /leave-requests/{id} that lets a caller set state to whatever it likes. State changes happen through named action endpoints, each of which maps to exactly one declared transition. That single choice removes an entire class of bug, and it is the first thing a good reviewer will look for.

The three hard parts

The workflow engine: modelling the leave request lifecycle

This is the heart of the project. A leave request moves through DRAFT, SUBMITTED, MANAGER_APPROVED, HR_APPROVED, REJECTED and CANCELLED. The naive implementation — a String status column, and an if/else chain over it inside whichever service happens to be touching the row — is exactly what makes these systems unmaintainable. The rules end up scattered across five classes, nobody can answer "what can happen next?" without reading all of them, and the sixth developer to add a state forgets one branch. Six months later a request sits in MANAGER_APPROVED that was never submitted, and no one can explain how.

The alternative is an explicit state machine: the set of legal transitions declared in exactly one place, so that adding a state is a one-file change and an illegal move is impossible by construction rather than by discipline. Each transition carries a guard (a boolean precondition — does the employee have the balance? is the actor the current approver? is the date range still in the future?) and an optional entry action (send the notification, decrement the balance, write the history row). Persist two things: the current state on the aggregate, and an append-only transition history recording who moved it, from what, to what, when, and why.

How to build it: for a domain this size, hand-roll it. An enum of states, each holding the set of actions it permits, with a service that looks up the transition, evaluates the guard, applies the action and records history — roughly eighty lines, no dependency, fully unit-testable, and readable by anyone joining the team. Spring Statemachine exists and is genuinely good at hierarchical states, regions, forks and persisted machine contexts; know it by name, and note honestly that its GitHub repository is now archived, which is a real consideration before adopting it. Full BPMN engines — Camunda, Flowable — are the right tool when non-developers must draw and change processes, when you need timers, compensation and human task queues out of the box, and when a process spans systems. For one leave workflow inside one application they are overkill; say so in the interview, and then show that you can name what they buy.

public enum LeaveState {
    DRAFT, SUBMITTED, MANAGER_APPROVED, HR_APPROVED, REJECTED, CANCELLED
}

public record Transition(LeaveState from, LeaveAction action, LeaveState to,
                         Predicate<LeaveContext> guard) { }

// The single place the workflow is defined. Nothing else may change state.
private static final List<Transition> TABLE = List.of(
  new Transition(DRAFT,            SUBMIT,      SUBMITTED,        Guards::ownerAndBalanceAvailable),
  new Transition(SUBMITTED,        APPROVE,     MANAGER_APPROVED, Guards::actorIsManagerOrDelegate),
  new Transition(SUBMITTED,        REJECT,      REJECTED,         Guards::actorIsManagerOrDelegate),
  new Transition(SUBMITTED,        CANCEL,      CANCELLED,        Guards::actorIsOwner),
  new Transition(MANAGER_APPROVED, APPROVE,     HR_APPROVED,      Guards::actorIsHrAndTypeNeedsHr),
  new Transition(MANAGER_APPROVED, REJECT,      REJECTED,         Guards::actorIsHr),
  new Transition(MANAGER_APPROVED, CANCEL,      CANCELLED,        Guards::ownerBeforeStartDate),
  new Transition(HR_APPROVED,      CANCEL,      CANCELLED,        Guards::hrOnlyWithReason));

public LeaveRequest apply(LeaveRequest req, LeaveAction action, Actor actor) {
    LeaveContext ctx = new LeaveContext(req, actor);
    Transition t = TABLE.stream()
        .filter(x -> x.from() == req.getState() && x.action() == action)
        .findFirst()
        .orElseThrow(() -> new IllegalTransitionException(req.getState(), action));
    if (!t.guard().test(ctx)) throw new TransitionNotPermittedException(action);

    LeaveState previous = req.getState();
    req.setState(t.to());                       // 1. move
    history.record(req, previous, t.to(), action, actor);   // 2. remember, always
    events.publish(new LeaveStateChanged(req, previous, t.to(), actor)); // 3. react
    return req;
}

Approval chains, delegation and escalation

The state machine says what may happen. The approval chain says who may make it happen, and it is a separate concern that beginners routinely fuse into the state enum. Two designs are worth knowing. A fixed chain hard-codes the steps — manager, then HR — which is trivial to implement and fine for one leave type. A rules-driven chain computes the steps when the request is submitted, from the request's own attributes: duration above ten working days adds an HR step; unpaid or sabbatical leave adds a department-head step; a requester who is themselves a department head skips the manager step and goes straight to HR. Materialise the computed chain into approval_step rows at submission time rather than recomputing it on every read — otherwise a policy change next quarter silently rewrites the approval history of a request from last quarter, which is precisely the kind of thing auditors hate.

Then the two cases that make this an interview-worthy design. Delegation: a manager going on holiday assigns their approval authority to a peer for a date range. Model it as its own entity with a validity window and a scope, and resolve it at decision time — "may this actor act on this step?" becomes "is the actor the assigned approver, or an active delegate of the assigned approver for this scope right now?". Never rewrite approval_step.approver_id to the delegate: the record must still show who was accountable, and the transition history must record both the acting user and the person on whose behalf they acted. Escalation: a step that sits undecided past its service-level window gets escalated to the approver's own manager by a scheduled job, which writes a normal transition row with a system actor. Both features are pure additions if the chain is a first-class entity, and both are painful rewrites if approval is an if statement inside the leave service.

Authorization depth: roles are the easy half

Start with roles — EMPLOYEE, MANAGER, HR, ADMIN — because they answer the coarse question cleanly: only HR may open a review cycle, only admin may deactivate a user. Wire them with Spring Security method security (@EnableMethodSecurity, then @PreAuthorize at the service layer, not the controller — the service is the real security boundary, and a scheduled job or a message consumer reaching the same method must hit the same check).

Then confront the half that RBAC cannot express, which is the whole point of this capstone. "A manager may view their reports' records but not a peer's" is not a role, it is a relationship between the actor and the specific record. So is "an employee may view only themselves". hasRole('MANAGER') is true for every manager in the company; it says nothing about whether this manager owns this record. The fix is a permission decision that takes both the principal and the target: a PermissionService consulted from the service layer, or — the idiomatic Spring version — a custom PermissionEvaluator registered with the method security expression handler so that @PreAuthorize("hasPermission(#employeeId, 'Employee', 'READ')") compiles down to your relationship logic. Spring Security's ACL module is the heavyweight option; it is worth knowing, and usually more machinery than a manager-chain lookup deserves.

@Service
public class EmployeeService {

    // Coarse role gate AND fine-grained relationship check, both before the method runs.
    @PreAuthorize("hasAnyRole('HR','ADMIN') or hasPermission(#employeeId, 'Employee', 'READ')")
    public EmployeeView get(Long employeeId) { ... }
}

@Component
public class HrPermissionEvaluator implements PermissionEvaluator {

    @Override
    public boolean hasPermission(Authentication auth, Serializable targetId,
                                 String targetType, Object permission) {
        Long actorId = ((AppPrincipal) auth.getPrincipal()).employeeId();
        Long targetEmployeeId = (Long) targetId;
        if (actorId.equals(targetEmployeeId)) return true;            // self
        // relationship: is the target anywhere in the actor's reporting subtree?
        return hierarchy.isInReportingChainOf(targetEmployeeId, actorId);
    }
}

Two implementation details separate a working design from a correct one. First, isInReportingChainOf must be a recursive query, not a loop that fetches a manager, then their manager, then theirs — that is N round trips and it will be the slowest endpoint you own. Second, write the tests that prove the negative: a manager reading a peer's record must get a denial, and that test is more valuable than any of the happy-path tests in the project. Use Spring Security's test support to run each service method as several different principals in one test class.

Field-level sensitivity, and why you must not over-fetch then trim

Not every field on an employee record has the same access rule. Name, designation, department and work email are effectively internal-public. Salary and CTC are visible to HR and to the employee themselves — and specifically not to a peer manager, or even, in most companies, to the employee's own reporting manager. Home address, personal phone, bank details, date of birth and identity numbers each carry their own rule. Role-level checks are the wrong granularity here; the decision is per field, and sometimes per field per relationship.

The tempting shortcut is to load the full entity, serialise it, and strip the fields the caller may not see — with @PostAuthorize, a JSON view, or a mapper that nulls things out. Resist it. Every one of those trims happens after the sensitive value has already been read out of the database, copied into the heap, and very likely logged by a debug statement, an APM tracer or an exception message on the way. It is one refactor, one toString(), one new logging aspect away from a leak, and it fails open: forget to add the new column to the strip list and it ships to everyone. Push the decision earlier instead — model compensation as a separate table and a separate repository method with its own authorization, and use projections so that the query for a peer-visible view never selects the salary column at all. Then the sensitive value is not in memory to leak.

Do the same at the collection boundary. "Show me my team's leave requests" must be a query filtered by the manager's reporting subtree in SQL, not a fetch-all followed by an in-memory filter: the latter is slow, it breaks pagination (page one of a hundred rows filtered down to four), and it means the unauthorised rows were in your process anyway. Spring Security's Spring Data integration lets the principal appear directly in a query with ?#{ principal.employeeId }, which keeps the predicate where it belongs.

The audit trail: what to record, how to capture it, why it is immutable

An audit row answers six questions and it is worthless if it drops any of them: who (the authenticated actor, plus the effective role used and, for delegated actions, the person on whose behalf they acted), what (the action, in domain terms — LEAVE_APPROVED, not UPDATE), which (entity type and id, stored as loose values so the row survives the entity's deletion), before and after (the changed fields only, as a diff), when (a server-side timestamp with a time zone, never a client-supplied one) and whence (source address, correlation or request id, client type). Record reads too, for the genuinely sensitive endpoints — knowing that someone opened forty compensation records in an afternoon is the entire point of having an audit log.

Two capture mechanisms, and the tradeoff is real. JPA entity listeners or Hibernate Envers hook the persistence layer, so nothing can slip past: turn on @Audited and every change to that entity, from any code path, produces a revision. That completeness is the strength. The weakness is vocabulary — the persistence layer sees "the state column changed from SUBMITTED to MANAGER_APPROVED", not "the reporting manager approved a leave request", and it cannot record intent, the reason text, or the fact that a delegate acted. Explicit service-layer audit events have exactly the opposite profile: rich, business-meaningful, and easy to forget on the one new code path nobody remembered to instrument. The mature answer is both — Envers as the low-level safety net on entities like employee_compensation, and explicit domain events for the workflow.

A neat middle path, and a legitimate use of the reflection and annotation material from the Advanced Java track: a custom @Audited annotation on service methods, processed by a Spring AOP aspect that reads the annotation's metadata, resolves the actor from the security context, computes the field diff and writes the audit row. It keeps the audit call out of the business method while staying in business vocabulary — and it demonstrates that you understand annotations as a design tool rather than as decoration.

@Target(ElementType.METHOD) @Retention(RetentionPolicy.RUNTIME)
public @interface Audited {
    String action();
    String entityType();
    boolean captureDiff() default true;
}

@Aspect @Component
public class AuditAspect {

    @AfterReturning(pointcut = "@annotation(audited)", returning = "result")
    public void record(JoinPoint jp, Audited audited, Object result) {
        AuditEntry entry = AuditEntry.builder()
            .occurredAt(Instant.now())                      // server clock, always
            .actorUserId(SecurityUtils.currentUserId())
            .actorRole(SecurityUtils.effectiveRole())
            .action(audited.action())                       // LEAVE_APPROVED
            .entityType(audited.entityType())
            .entityId(EntityIds.of(result))
            .requestId(MDC.get("requestId"))
            .beforeValue(Redactor.redact(diff.before()))    // never store the raw secret
            .afterValue(Redactor.redact(diff.after()))
            .build();
        auditWriter.append(entry);   // append-only; no update path exists in the repository
    }
}

Finally, the two rules that get asked about most. The audit table is immutable. Insert only — no update path in the repository, no delete, and enforce it in the database as well as the code: revoke UPDATE and DELETE on audit_log from the application role, or add a trigger that raises on either. A log that the application can rewrite proves nothing, and the whole value of the table is that it is evidence. Retention and archival are a separate, deliberate process with its own privileges. The audit log must not leak the values it guards. If salary is restricted to HR, an audit row containing the old and new salary is a copy of that restricted data sitting in a table that more people can read — so redact or hash sensitive values, store field names rather than field contents where a change indicator suffices, and put the audit-read endpoint behind its own authorization. Never write passwords, tokens, full identity numbers or bank details into it at all.

Building it

Build phases: ten increments, each one demoable

Build in this order and every phase ends with something you can run and show. Do not start phase four until phase three has tests that fail when you break authorization — the whole value of this project is that its security is provable, and a state machine bolted onto an unauthorised API is a demo, not a system.

  1. Employees, departments and the hierarchy. Schema with Flyway or Liquibase, JPA entities, the self-referencing manager relationship, seed data with a realistic tree four levels deep, and a recursive CTE query for ancestors and descendants. Demo: the reporting chain of any employee, and the full subtree under any manager.
  2. The role model and method security. Users, roles, login issuing a JWT, @EnableMethodSecurity, and coarse @PreAuthorize role gates on the service layer. Demo: an employee token is refused on an HR-only endpoint.
  3. Relationship-based authorization, with the tests that prove it. The PermissionService or custom PermissionEvaluator, the recursive reporting-chain check, and a test class that asserts a manager cannot read a peer's record, cannot read a peer's reports, and cannot read anyone's compensation. Demo: run that test class. This is the phase that makes the project worth putting on a CV.
  4. The leave request state machine. States, the transition table, guards, the action endpoints, optimistic locking on the aggregate, and the append-only transition history. Demo: walk a request through the happy path, then show that an illegal transition is rejected with a clean problem-details response.
  5. The approval chain with delegation. Rules-driven step computation materialised at submission, the pending-approvals queue, delegation with a validity window resolved at decision time, and a scheduled escalation job. Demo: a manager delegates, the delegate approves, and the history shows both identities.
  6. Audit logging across sensitive entities. The @Audited annotation and aspect, Envers on compensation, the append-only table with database-level protection, redaction of sensitive values, and the HR-only audit query endpoint. Demo: change a salary, then show the audit row — and show that the application cannot update or delete it.
  7. Timesheets and review cycles. Weekly timesheets with their own small submit-and-approve lifecycle (reuse the transition machinery — if you cannot, your phase-four design was too specific), and review cycles with self-assessment, manager assessment and publication.
  8. Document management. Upload with content-type and size validation, a stored SHA-256 for integrity, opaque storage keys, streaming download behind an authorization check, and per-document visibility. Never serve a document by a guessable sequential id alone.
  9. The Angular front end. Role-driven navigation, functional route guards, an interceptor attaching the token and handling 401 or 403 uniformly, reactive forms for the leave request with date-range and balance validation, the approvals inbox, and the audit viewer for HR. Remember that hiding a menu item is user experience, not security — the server check is the security.
  10. One stretch goal. Payroll summary export, the org-chart visualisation, or the self-service portal. Finish one properly rather than starting three.

Interview questions

An interviewer sees this project on your CV and will not ask you about CRUD. They will ask how you modelled the approval workflow, how you stop a manager reading a peer's salary, and why the audit table cannot be updated — these are the questions Indian product and service companies use to separate a project you built from a project you followed:

Beginner Walk me through the states of a leave request in your system.

Draft, submitted, manager-approved, HR-approved, rejected and cancelled. Draft to submitted is the employee's action; submitted to manager-approved or rejected is the reporting manager's; manager-approved to HR-approved applies only to leave types that require it. Rejected is terminal. Cancelled can be reached by the employee before the leave starts, or by HR afterwards with a recorded reason. Every move is one declared transition with a guard, and every move writes a history row.

Beginner Why do you have separate approve and reject endpoints instead of a single update endpoint that sets the status?

Because a generic update endpoint accepts a state value from the client, which means the client decides the workflow. Action endpoints map one-to-one onto declared transitions, so the server decides: it looks up whether that action is legal from the current state, evaluates the guard, and refuses anything else. It also removes the mass-assignment risk of a state field on the request DTO, and it makes the audit action meaningful — "leave approved" rather than "row updated".

Beginner How did you model the organizational hierarchy?

An adjacency list: a nullable manager_id on the employee table that self-references. Reorganisations are a single row update, and both directions of traversal — the chain of command upward and the reporting subtree downward — come from a recursive CTE. I considered a closure table, which makes ancestor queries a single indexed lookup, but it costs extra rows on every hierarchy change and the recursive query is comfortably fast at our scale. I would revisit it if the org-chart or authorization queries showed up in profiling.

Beginner Which roles exist and what does each one gate?

Employee, manager, HR and admin. Employee is the baseline — self-service on their own records. Manager adds approval and visibility over their reporting subtree. HR gets organization-wide visibility, policy configuration, review cycles and the audit query. Admin handles user lifecycle and configuration. But roles only answer the coarse questions; the interesting rules in this system are relationship-based and roles cannot express them.

Intermediate A manager tries to open a peer's employee record. Trace exactly what stops them.

The request hits the controller, which delegates to a service method annotated @PreAuthorize("hasAnyRole('HR','ADMIN') or hasPermission(#employeeId, 'Employee', 'READ')"). The role branch fails. The permission branch calls my custom PermissionEvaluator, which resolves the caller's employee id from the principal, sees it does not equal the target, and runs a recursive query asking whether the target sits anywhere in the caller's reporting subtree. A peer is not, so it returns false, Spring Security throws before the method body executes, and no data is loaded at all. I have a test class asserting exactly this denial — it is more important than the happy-path test.

Intermediate Why is hasRole('MANAGER') not sufficient for that check?

Because it is a property of the caller alone, not of the caller and the record together. Every manager in the company satisfies it, so it grants access to every employee's record. The rule I actually need — "this manager, over this employee" — is a relationship, and relationship-based access control needs a decision function that takes the principal and the target object. That is precisely what PermissionEvaluator or a permission service gives you, and it is why role-based access control alone is not enough in any system with an ownership concept.

Intermediate You need to show a manager their team's leave requests. Why not fetch all requests and filter in Java?

Three reasons. Correctness: pagination breaks, because page one of a hundred rows might reduce to four after filtering, and total counts become meaningless. Performance: you read the whole table to return a handful of rows. Security: the unauthorised rows were loaded into your process, so any logging, tracing, serialisation bug or error message can leak them. The predicate belongs in the query — a join against the reporting subtree, or Spring Security's Spring Data integration putting the principal directly into the query expression.

Intermediate How does delegation work when a manager goes on holiday?

A delegation entity holds delegator, delegate, a validity window and a scope. At decision time the guard asks whether the actor is the assigned approver or an active delegate of that approver right now. I never rewrite the approval step's approver id to the delegate, because the record must still show who was accountable; instead the transition history stores both the acting user and the person on whose behalf they acted. Escalation is the same shape: a scheduled job promotes an undecided step to the approver's own manager and writes a normal transition row with a system actor.

Intermediate What exactly goes into an audit row, and where does the timestamp come from?

Actor (user id and the effective role, plus the on-behalf-of identity for delegated actions), action in domain vocabulary, entity type and id stored as plain values so the row outlives the entity, the before and after values of the changed fields only, a server-generated timestamp with time zone, and provenance — source address, request or correlation id, client type. The timestamp is always from the server clock, never from the client, because the client is exactly the party an audit log exists to hold accountable.

Pro Why is the audit table immutable, and how do you actually enforce that?

Because an audit log the application can rewrite proves nothing — its entire value is that it is evidence, and evidence that the accused controls is not evidence. Enforcement is layered: the repository exposes only an append operation and has no update or delete method; the application's database role has UPDATE and DELETE revoked on the audit table, so even a code path that tried would fail at the database; and a trigger can raise on either statement as a belt-and-braces measure. Retention and archival happen through a separate, privileged process on its own schedule, never through application code. If you want stronger guarantees, chain each row's hash to the previous one so tampering is detectable even by someone with database privileges.

Pro Salary is HR-only. Your audit log records salary changes. Isn't the audit log now a copy of the data it is supposed to protect?

Yes, and that is the trap. An audit trail must not leak the values it guards. I handle it three ways: the audit read endpoint has its own authorization, at least as strict as the data it describes; sensitive values are redacted or hashed, so the row records that compensation changed and by whom without reproducing the figure; and categorically secret values — passwords, tokens, full identity or bank numbers — are never written at all, only the fact that they changed. Where the actual old and new values are legally required, they live in a separately protected column or table with narrower access than the rest of the audit row.

Pro Hibernate Envers or explicit service-layer audit events — which did you choose and why?

Both, for different jobs. Envers is a completeness guarantee: hook it to an entity and no code path can change that row without producing a revision, which is what I want on compensation. Its weakness is vocabulary — it records that a column changed, not that a delegate approved a leave request on behalf of a holidaying manager, and it cannot capture intent or a reason. Explicit service-layer events are business-meaningful but only as complete as your discipline. So Envers is the safety net on sensitive entities, and a custom annotation plus an AOP aspect emits the domain-level events for the workflow, keeping the audit call out of the business method.

Pro Why a hand-rolled state machine rather than Spring Statemachine or a BPMN engine?

Because the domain has six states and one workflow, and a transition table plus guards is roughly eighty lines with no dependency, no extra persistence, and no learning curve for the next developer. Spring Statemachine earns its place when you need hierarchical or orthogonal states, forks and joins, or persisted machine contexts across nodes — and its repository is now archived, which is a real factor in an adoption decision. A BPMN engine like Camunda or Flowable earns its place when non-developers must draw and change the process, when you need timers, human task queues and compensation out of the box, or when a process spans systems. Choosing the smallest thing that makes illegal transitions impossible is the actual engineering judgement here.

Pro Two approvers open the same request and both click approve. What happens?

The leave request carries a JPA version column, so the second transaction to commit fails with an optimistic locking exception, which I translate into a 409 with a problem-details body telling the caller the request has already moved on. The state machine helps too: the second attempt is evaluated against the state the first one produced, so the transition lookup itself may already be illegal. The important part is that the history contains exactly one approval row — I never want two transition rows claiming to have made the same move, because the history is the audit evidence.

Pro Your Angular app hides the compensation menu for non-HR users. Is that a security control?

No. It is user experience. The single-page app runs on the user's machine, the bundle is public, and any caller can invoke the endpoint directly with a token. Hiding the menu just avoids showing people buttons that would fail. The security control is the server-side check at the service layer, which runs regardless of which client called, and which I test independently of the front end. Route guards and conditional navigation are built from the same role claims for consistency, but the server is authoritative and the client is a convenience.

Pro How would you extend this to a rules-driven approval chain without breaking existing requests?

The chain is already a first-class entity computed at submission time and materialised into approval_step rows, so a policy change only affects requests submitted after it — historical requests keep the chain they were actually judged under, which is what an auditor needs. To make it rules-driven I move step computation behind a policy component that takes the request attributes (duration, leave type, requester's position in the hierarchy) and returns an ordered list of steps, then version the policy and store the policy version on the request. The state machine does not change at all, because it governs what may happen, not who may make it happen — that separation is what makes the extension cheap.
