Capstone 02: Admin Dashboard

The frontend flagship of the set. The backend here is deliberately modest — a handful of read endpoints and a few writes — because everything worth learning lives on the Angular side: how you slice features, where each piece of state belongs, why the table's filters live in the address bar, and how you prove any of it works with tests.

Knowledge Library → Courses → Real-World Projects → Admin Dashboard

What this capstone is

You are building an internal admin console over the expense and inventory domain you already modelled in capstone 01 — the screen an operations team actually opens every morning. It shows what the business spent this month, lets a manager page through thousands of expense records with real filters, opens a record in a side drawer to correct it, and gives an administrator a place to grant and revoke roles. Nothing here is novel product design; that is the point. The novelty is entirely architectural.

Treat this brief as a specification, not a tutorial. It names the features, sketches the architecture, fixes the API contract, and breaks the work into phases that each end with something you can demo. It does not hand you the code. Where a decision has a defensible alternative — SignalStore or a plain service, Chart.js or ECharts, filters in the component or filters in the URL — the brief states the tradeoff and picks one, and you should be able to defend the pick in an interview.

The brief

Feature outline: the MVP you must finish, and the stretch goals you may not

Scope discipline is the first skill this capstone teaches. An admin dashboard is infinitely expandable, and half-finished dashboards are the single most common dead project on a junior CV. Fix the MVP first and treat everything else as optional. The MVP is seven things: a metrics overview page with headline totals and two charts; a paginated, sortable expense table with server-side filtering; an entity detail and edit drawer; user and role administration; an audit trail view; light and dark theming; and a settings page. That is a complete, coherent product — an operator can see the numbers, drill into a record, fix it, and see who else changed what.

The stretch list exists to be attempted only after the MVP ships and is tested: saved filter views (named, shareable query presets), CSV export, bulk actions with optimistic updates and rollback on failure, virtual scrolling for tables past a few thousand rows, and internationalisation. Each stretch goal is chosen because it forces a genuinely harder version of a decision you already made — optimistic updates make you confront where the source of truth lives, saved views make you confront URL serialisation, i18n makes you confront how much text is hard-coded in your components.

Architecture sketch: standalone components, feature folders, lazy routes

There are no NgModules in this project. Every component, directive and pipe is standalone, every route is lazy, and the folder tree is organised by feature rather than by technical kind — no top-level components/ bucket holding forty unrelated files. Each feature folder owns its routes, its smart container components, its presentational children, its data-access service and its store, and exposes exactly one public entry point. Anything two features both need moves into shared/; anything the whole app needs at boot lives in core/.

Inside a feature, keep the smart/presentational split honest: container components inject the store, read signals and hand plain data down; presentational components take inputs, emit outputs and inject nothing. That split is what makes the presentational half trivially testable and reusable, and it is the first thing an interviewer probes when you say "component library". Enforce the boundaries mechanically if you can — Sheriff lints folder-level dependency rules so a violation fails the build instead of surviving a code review.

Data model and the API contract

Keep the backend small and boring: Spring Boot, a relational schema, Spring Data paging, and a handful of DTOs. Eight tables carry the whole product. app_user and role with a join table, permission joined to roles, expense with a status enum and money stored as a scaled integer or numeric (never a float), category and vendor as lookups, and audit_event as an append-only log of actor, action, entity type, entity id, timestamp and a JSON diff. Saved views, if you build them, are one more table holding a user id, a name and a serialised query string.

The contract that actually shapes the frontend is the list endpoint. Every collection returns the same envelope — a content array plus page, size, totalElements, totalPages and sort — so one generic table adapter serves expenses, users and audit events without special-casing. Publish the contract with an OpenAPI document generated by springdoc rather than hand-writing it; you can then generate the TypeScript interfaces instead of maintaining two copies of the same shape by hand, which is the single most common source of frontend/backend drift on a project like this.

State design: what is global, what is feature-scoped, what is component-local

Make this decision explicitly and write it down, because "how did you decide what goes in the store?" is the question this project exists to answer. Three tiers. Global: the authenticated session — user identity, roles, the flat permission set, the active theme and locale. It is read by guards, interceptors, the shell and half the feature components, it is written exactly once at bootstrap, and it must survive navigation. That belongs in a root-provided SignalStore. Feature-scoped: the expenses list, its loading and error flags, the currently selected row, the pending bulk-action set. Several components inside one feature read it, nothing outside the feature cares, and it should die when you navigate away. That is a SignalStore provided on the feature's lazy route, not in root. Component-local: whether a drawer is open, which tab is active, the value of a search box before it is debounced. Plain signal() inside the component. Putting any of this in a store is over-engineering and interviewers notice.

There is a fourth tier that people forget, and it is the interesting one: URL state. Page, page size, sort column, sort direction and every active filter are not application state at all — they are navigation state, and they belong in the query string. The SignalStore then derives from the URL rather than owning a duplicate copy, which removes an entire category of bug where the table and the address bar disagree. Choose @ngrx/signals SignalStore over a hand-rolled service because you get the parts you would otherwise write badly — patchState with immutable updates, computed selectors, rxMethod for cancellable async flows, withEntities for keyed collections, and lifecycle hooks — while staying signal-native and avoiding the action/reducer/effect ceremony that classic NgRx Store imposes. Reach for classic Store only if you genuinely need time-travel debugging or a global, replayable action log.

export const ExpensesStore = signalStore(
  // provided on the feature route, NOT in root: dies with the feature
  withEntities<Expense>(),
  withState({ total: 0, loading: false, error: null as string | null,
              selected: [] as number[] }),
  withComputed(({ entities, selected }) => ({
    hasSelection: computed(() => selected().length > 0),
    pageTotal:    computed(() => entities().reduce((s, e) => s + e.amountMinor, 0)),
  })),
  withMethods((store, api = inject(ExpenseApi)) => ({
    // driven by the URL query params, not by component-held filter state
    load: rxMethod<ExpenseQuery>(pipe(
      tap(() => patchState(store, { loading: true, error: null })),
      switchMap((q) => api.list(q).pipe(
        tapResponse({
          next: (p) => patchState(store, setAllEntities(p.content),
                                  { total: p.totalElements, loading: false }),
          error: (e: Error) => patchState(store, { error: e.message, loading: false }),
        }))),
    )),
  })),
);

The server-driven table: query state belongs in the URL

This is the most instructive screen in the project, so build it deliberately. The table is server-driven: the client never holds the full dataset, it holds one page and a total count. Page index, page size, sort field, sort direction, the free-text query and every filter travel to the server as query parameters, and the server returns the paged envelope. Client-side filtering of an already-paged array is the classic mistake here — it filters twenty-five rows out of four thousand and quietly lies to the user about the totals.

The design decision worth defending: that same query state also lives in the browser's address bar. When a manager filters to pending travel expenses from March, sorted by amount, and hits page three, the URL should read /expenses?status=PENDING&category=Travel&from=2026-03-01&sort=amount,desc&page=2. Three things follow for free. The view is shareable — she can paste that link into a chat and a colleague sees exactly what she sees. It survives reload and browser back, because the router, not a component field, is holding the truth. And deep-linking from an email or a saved bookmark works without any extra plumbing. The implementation shape: the filter bar and paginator do not mutate state, they call router.navigate with merged query params; the container reads ActivatedRoute.queryParams as a signal, validates and coerces it into a typed query object (a schema validator earns its keep here, because query params are always strings and always attacker-controlled), and feeds that into the store's rxMethod. One direction of flow, no synchronisation code, and the back button behaves.

// container: the URL is the single source of truth for the query
private readonly route = inject(ActivatedRoute);
private readonly router = inject(Router);
private readonly store = inject(ExpensesStore);

readonly query = computed(() => parseExpenseQuery(this.routeParams()));
private readonly routeParams = toSignal(this.route.queryParams, { initialValue: {} });

constructor() { this.store.load(this.query); }   // rxMethod accepts a signal

// paginator / sort / filter-bar outputs all funnel through one navigation
onQueryChange(patch: Partial<ExpenseQuery>) {
  this.router.navigate([], {
    relativeTo: this.route,
    queryParams: { ...patch, page: patch.page ?? 0 },  // any filter change resets to page 0
    queryParamsHandling: 'merge',
  });
}

Detail and edit drawers with typed reactive forms

Clicking a row opens a side drawer rather than navigating to a full page — the operator keeps the list in view, which is why every real admin console works this way. Give the drawer its own route (a child route or an outlet), so the open drawer is part of the URL and is therefore also shareable and back-button-friendly; a drawer whose open state lives in a component field is one more thing that breaks on reload.

The edit form is a strictly typed reactive form. Build it with FormBuilder.nonNullable.group and let inference do the work — no FormGroup<any>, no untyped get('field') lookups scattered through the template. Typed forms turn a whole class of runtime nulls into compile errors, and the interview follow-up is always about value versus getRawValue and why disabled controls disappear from the former. Two more rules for this screen: patch, don't replace — send a PATCH with only the dirty controls so two concurrent editors do not clobber each other's untouched fields; and map server-side validation errors back onto the matching controls with setErrors instead of dumping a toast, because a field-level error is the difference between a form the user can fix and a form the user abandons.

RBAC in the UI: permissions from /me, guards, and the caveat that matters

Model permissions, not roles, in the UI. Roles are an administrative grouping that changes when the org chart changes; permissions are the stable atoms your components check. The session store loads a flat set such as expense:read, expense:approve, user:manage, audit:read — either decoded from the access token's claims or fetched from /me at bootstrap. Prefer /me when the permission set is large or changes without a re-login; prefer token claims when you want zero extra round trips and can live with staleness until the token refreshes. Say which you chose and why.

Then apply it in three places. A functional route guard per permission stops navigation into a feature the user cannot use, and the lazy route means the code is never even downloaded. A structural directive or a signal-driven @if hides the actions the user cannot perform — hide, do not disable, unless the disabled state is itself informative. And a functional HTTP interceptor attaches the token on the way out and centralises the response on the way back: a 401 clears the session and routes to login, a 403 shows a "not permitted" surface rather than a generic error toast, so the two failures stay distinguishable. Now the caveat, and put it in your README because interviewers ask it as a trap: hiding a button is user experience, not security. Anyone can open DevTools, flip a signal, or simply curl the endpoint. Every permission checked in the UI must be enforced again on the server — method-level authorization in Spring Security — and the UI check exists only so users are not shown doors they cannot open.

Charts: pick a library on purpose, and keep chart components dumb

You need three visuals on the overview page: a trend line over time, a category breakdown as a bar or donut, and a row of stat tiles with period-over-period deltas. Pick one library and commit. ngx-charts is Angular-native and declarative — components, inputs, Angular animations, no imperative canvas API — which makes it the smoothest fit and the easiest to test, at the cost of a smaller chart vocabulary. Chart.js behind a thin wrapper is the pragmatic middle: tiny, canvas-based so it stays fast at a few thousand points, enormous community, but you own the wrapper component and the lifecycle (destroy on ngOnDestroy, re-render on input change). ECharts is the heavyweight — the widest chart vocabulary and the best behaviour on very large series — and the right answer when the dashboard is genuinely analytical, but it is the largest bundle and the steepest configuration surface. For this brief, Chart.js behind a wrapper or ngx-charts is the proportionate choice; say ECharts only if you can name what you needed that the others lack.

Whatever you pick, the architectural rule is the same and it is the thing interviewers actually probe: a chart component takes data as an input and never fetches its own. The container calls the metrics endpoint, shapes the response into the chart's data structure, and passes it down; the chart component is presentational, injects nothing, and is therefore renderable in a test with a fixed array and no HTTP mock at all. A chart that calls HttpClient in its own constructor cannot be reused on a second page, cannot be storybooked, and drags a network round trip into every test that renders it.

The shell: theming, settings and accessibility

The shell is the toolbar, the collapsible sidenav, the content outlet and the theme. Light and dark are not a cosmetic afterthought on an internal tool that people stare at for eight hours — they are a feature request you will get on day two. Implement them as CSS custom properties toggled by a class or a data-theme attribute on the root element, driven by a signal in the core theme service and persisted to localStorage. Default to the operating system preference via prefers-color-scheme and let the settings page override it; that combination is what users expect and it costs one media query.

The settings page is where profile details, theme and (if you attempt i18n) locale live. Keep it deliberately thin — it is a form over the session store, not a feature with its own architecture. Spend the time you save on accessibility instead: a data table needs proper header semantics and sort announcements, a drawer needs focus trapping and an escape key, and every icon-only toolbar button needs an accessible label. Admin tools are exactly the software that gets audited for accessibility, and "it is internal" has never been an accepted answer.

Build phases: nine slices, each one runnable and demoable

Build in vertical slices, not layers. Every phase below ends with something you can run, click and show to somebody — that is the discipline that keeps a capstone alive, and it is also what lets you talk about the project as a sequence of decisions rather than a wall of code. Commit at the end of each phase with a message that names what now works; the commit history becomes the story you tell in the interview.

  1. Shell, routing, layout and theming. Standalone bootstrap, the toolbar and sidenav, five lazy feature routes with placeholder pages, the theme signal with light/dark and OS-preference default. Demo: navigate between empty features, flip the theme, reload and see it stick.
  2. Auth, interceptor, guards and the permission model. Login, token storage, the auth interceptor, the error interceptor, the session SignalStore loading /me, one functional guard per permission, and the permission directive. Demo: log in as two users with different roles and watch routes and buttons appear and disappear.
  3. The metrics overview with two charts. The summary endpoint, stat tiles with deltas, a trend chart and a breakdown chart — all fed by inputs from a container. Demo: the landing page shows real numbers and two charts that redraw when you change the date range.
  4. The server-driven data table with URL-synced query state. Paged endpoint, generic table component, filter bar, sort headers, paginator, all funnelling through router navigation. Demo: filter and sort, copy the URL into a fresh tab, land on exactly the same view; press back and it unwinds.
  5. Detail and edit drawers with typed reactive forms. A routed drawer, the detail payload, a strictly typed edit form, dirty-field PATCH, server validation mapped onto controls. Demo: open a row, edit one field, save, see the list row update.
  6. User and role administration. The users table reusing the generic table, the role assignment screen, permission sets per role. Demo: grant a role to a second account and watch that account's UI change.
  7. The audit trail view. Append-only list with actor, action, entity and diff, filterable by actor and date, reusing the same table adapter. Demo: make an edit in phase 5, then find it in the audit view.
  8. The testing pass. Vitest for pure logic and the query parsers, TestBed for containers, component harnesses for the Material table and paginator, store tests for the SignalStore, and one Playwright happy path that logs in, filters the table, opens a row, edits it and asserts the audit entry. Demo: a green pipeline and a coverage number you can justify.
  9. One stretch goal, finished properly. Pick a single item — saved views, CSV export, bulk actions with optimistic rollback, virtual scrolling, or i18n — and ship it with tests rather than starting three and finishing none.

Interview questions

An interviewer who sees "Admin Dashboard (Angular, SignalStore, RBAC)" on your CV will not ask you what a component is — they will ask why you built it this way. These are the questions that actually come, weighted toward Indian product and service-company rounds where a project walkthrough is a full round of its own:

Beginner Walk me through the architecture of this dashboard in two minutes.

Lead with the shape, not the feature list: a standalone-component Angular app with feature-based folders and one lazy route per feature; a core layer holding auth, functional interceptors and theming; a shared UI library of presentational components; smart containers that inject stores and dumb children that only take inputs; NgRx SignalStore for shared feature state, plain signals for component-local state, and the router's query params for table query state. Backend is a small Spring Boot API returning a uniform paged envelope. Then offer one decision you would happily go deeper on.

Beginner Why standalone components and lazy routes instead of NgModules?

Standalone components declare their own dependencies, so there is no indirection between a component and what it uses, and no shared "everything module" that quietly grows. Lazy routes mean a user who never opens the audit feature never downloads it — which on an admin console with six features is a real first-paint win. NgModules still work, but new Angular applications default to standalone and the ecosystem has moved with them.

Beginner What is the difference between a smart and a presentational component here, and why did you bother?

Smart containers inject services and stores, read signals, and orchestrate; presentational components inject nothing, take inputs and emit outputs. The payoff is testing and reuse: the stat tile, the chart wrapper and the data table can be rendered in a test with a fixed array and no HTTP mock, and the same table serves expenses, users and audit events. It also localises change — a change to the API shape touches containers only.

Intermediate Why NgRx SignalStore rather than a plain service with a BehaviorSubject or a signal?

Because on this project I needed things a hand-rolled service makes me rewrite badly: immutable updates via patchState, computed selectors that memoise, rxMethod for cancellable async flows so a fast-typing filter does not race, withEntities for keyed collections, and lifecycle hooks tied to where the store is provided. It stays signal-native, so there is no manual subscription management and no async pipe noise. For genuinely trivial state a service with a signal is the right answer and I used exactly that for the theme — the store earns its place only where the extra machinery is used.

Intermediate How did you decide what is global state, feature state and component state?

By lifetime and readership. Global: the session — identity, permissions, theme — read by guards, interceptors and many features, written once at bootstrap, must survive navigation, so it is a root-provided store. Feature: the expense list, its loading and error flags, the selection set — read by several components within one feature and should die on navigation away, so the store is provided on the feature's lazy route. Component: drawer open, active tab, pre-debounce input — plain signal(). Anything that fails the "more than one component reads this" test does not go in a store.

Intermediate Why did you keep the table's page, sort and filters in the URL instead of in the store?

Because it is navigation state, not application state. Putting it in the URL buys three things at once: the filtered view is shareable by copying the address bar, it survives reload and the browser back button without any restore logic, and deep links from mail or bookmarks work for free. It also removes a whole class of bug — with the URL as the single source of truth there is no synchronisation code to get wrong between the address bar, the paginator and the store. The filter bar navigates; the container derives a typed query from queryParams and feeds the store.

Intermediate Server-side or client-side filtering for the table, and what breaks if you choose wrong?

Server-side, because the client only ever holds one page. Filtering the page you already have filters twenty-five rows out of four thousand, and the total count, the pagination and any aggregate you show all become wrong — the UI confidently lies. Client-side filtering is only correct when the entire dataset is small enough to ship in one response and you have said so deliberately.

Intermediate How is RBAC enforced in this application?

In four places, three of them cosmetic and one of them real. Permissions arrive as a flat set from /me at bootstrap (or from token claims). Functional route guards block navigation per permission, so lazy feature code is never even fetched. A structural directive or signal-driven control flow hides actions the user cannot perform. An HTTP interceptor distinguishes 401 from 403 so the app logs out on one and shows a not-permitted surface on the other. The real enforcement is server-side method-level authorization — the UI checks exist so users are not shown doors they cannot open.

Intermediate Why permissions rather than roles in the component checks?

Roles change with the org chart; permissions do not. If a template says "show this if role is MANAGER", then the day finance leads also need to approve expenses you edit templates. If it says "show this if the user has expense:approve", you change one role definition in the database and every screen is correct. Roles remain the administrative grouping; the UI codes against the atoms.

Intermediate Which charting library did you choose and what was the tradeoff?

Name the choice and the losing alternatives. ngx-charts is Angular-native and declarative, easiest to test, smallest chart vocabulary. Chart.js behind a thin wrapper is small and canvas-fast with a huge community, but you own the wrapper lifecycle — destroy and re-render on input change. ECharts has the widest vocabulary and the best very-large-series behaviour at the cost of bundle size and configuration complexity. For a dashboard with a trend line, a breakdown and stat tiles, the first two are proportionate; picking ECharts without naming a capability you needed reads as over-engineering.

Intermediate How did you test the data table?

In layers. The query parser — query string to typed query object — is pure, so plain Vitest unit tests cover coercion, defaults and rubbish input. The container is a TestBed test with a stubbed store and a fake ActivatedRoute, asserting that a filter change triggers navigation with the right params and that a params change triggers a load. Rendering assertions use Angular Material component harnesses instead of CSS selectors, so a Material upgrade does not break every test. Finally one Playwright happy path drives the real thing: log in, filter, sort, page, open a row, edit, assert the audit entry.

Pro Explain optimistic updates in your bulk-approve action and how rollback works.

On submit, patch the selected rows to APPROVED in the store immediately and keep a snapshot of their previous state, so the table reacts instantly. Fire the request; on success reconcile with the server's per-id outcomes, because a bulk endpoint can partially succeed. On failure — or for the ids the server rejected — restore from the snapshot and surface a specific error rather than a generic toast. The two traps are assuming all-or-nothing semantics from an endpoint that returns per-id results, and letting a second optimistic action start before the first resolves; either serialise them or key the snapshots per operation.

Pro Your table hides the Delete button for users without expense:delete. Is that secure?

No, and it was never meant to be. Hiding a control is user experience: it stops people trying things they cannot do. The bundle is on the client, the permission set is in memory, and the endpoint is one curl away — anyone can flip a signal in DevTools or call the API directly. Authorization must be enforced on the server for every mutating endpoint, deny-by-default, and ideally checked against the same permission names the UI uses so the two never drift. The correct answer to this question is always "the server enforces it; the UI only reflects it".

Pro A filtered table URL is pasted by a user without permission to see those records. What happens?

The route guard runs first and blocks navigation if the feature permission is missing. If the feature is permitted but the rows are not — a manager scoped to one department, say — the guard cannot help, because scoping is data-level, not route-level. The server must apply the scope to the query itself and return only the rows that user may see, with the totals computed over the same restricted set. Filtering after the fact on the client, or trusting a departmentId sent from the browser, is exactly the broken-object-level-authorization failure that tops the OWASP API list.

Pro The table jitters and the whole page re-renders on every keystroke in the search box. Diagnose it.

Likely three things stacked. The search input is navigating on every keystroke, so debounce before navigating and only push a distinct value. Each navigation is producing a new query object identity even when nothing changed, so the store's rxMethod refires — compare structurally or derive with computed so the reference is stable. And the row components are re-rendering because the list is rebuilt with new object identities and there is no track expression on the loop; track by id and keep children presentational with OnPush (or run zoneless) so a parent signal change does not walk the whole tree.

Pro If you rebuilt this project today, what would you change?

A strong answer names a real regret, not a humble brag. Good candidates: generating the TypeScript models from the OpenAPI document from day one instead of hand-writing DTOs that drifted; introducing the generic table abstraction after the second table rather than designing it up front for one; putting the permission names in a single shared constant so the server and UI could not diverge; and writing the Playwright happy path in phase 4 rather than phase 8, because it would have caught the URL-state regressions immediately.
