Capstone 04: Job Portal

The search, file handling and email capstone. Everything a candidate types into a search box has to become an index-friendly query, every CV they upload is an untrusted binary from the public internet, and every alert email you promise has to arrive exactly once even when four copies of your application are running.

Knowledge Library → Courses → Real-World Projects → Job Portal

What this capstone is

This is a buildable specification, not a tutorial. It gives you the scope, an architecture sketch, a data model, an API contract and ten build phases — each phase independently runnable and demoable — then points at the documentation and reference implementations that carry the detail. You write the code.

Three things make this project worth building rather than a fourth CRUD app. First, search: a job board is a search product wearing a CRUD costume, and the honest progression from LIKE to PostgreSQL full-text search to Elasticsearch is one of the best design conversations you can have in an interview. Second, file handling: a CV upload endpoint is an attacker's favourite door, and doing it properly touches validation, storage, authorization and streaming. Third, email: transactional mail plus a scheduled digest forces you to confront asynchrony, retries, and the duplicate-send problem that appears the moment you run more than one instance.

The brief

Scope: two user types and the MVP cut

Two roles share one application. Employers register a company, post job listings, edit and close them, and review incoming applications through a small status pipeline. Candidates build a profile, upload a CV, search and filter listings, apply with one click, and track the status of everything they have applied to. An admin role exists only to moderate — do not let it grow into a third product.

The MVP is deliberately narrow: multi-criteria search (keyword, location, salary range, experience level, remote flag, posted-within), sorted and paginated results, applications with a status pipeline, saved searches with an emailed digest, and an employer dashboard showing listing performance and the application funnel. Ship those and you have a genuinely complete product. The stretch goals — full-text relevance ranking beyond a naive rank, candidate recommendations, resume parsing that pre-fills a profile, and scheduled listing expiry — are each a self-contained second act you can add without rewriting anything, which is exactly how you should scope features in real work.

What you are explicitly not building: messaging between employer and candidate, payments for premium listings, or a recruiter CRM. Each is a different product. Note the boundary in your README; interviewers respect a candidate who can say what they left out and why.

Architecture sketch

A modular monolith is the right shape. One Spring Boot application, one PostgreSQL database, packages organised by feature rather than by layer, and object storage held behind an interface so a local filesystem implementation in development can become S3 in production without touching a controller. Angular is a separate build served as static assets or from its own dev server during development.

The only two components that must sit outside the request thread are mail delivery and the digest scheduler. Everything else — search, filtering, uploads, applications — is a plain synchronous HTTP request. Resist adding a message broker, a search cluster or a second service until a build phase forces the question; the point of the exercise is to feel where the pressure actually arrives.

Data model

Nine tables carry the MVP. The shape worth arguing about is the search column: job.search_doc is a stored generated tsvector built from title, description and company name with weights, so the database maintains it on every write and you never have to remember to refresh it. That single decision is what turns the search phase from a chore into a two-line change later.

Note the deliberate denormalisations. application.applied_cv_id pins the CV version that was actually submitted, because a candidate who uploads a new CV must not retroactively change an application an employer already reviewed. job.posted_at is separate from created_at so a draft that is published later sorts by publication, not authorship. And salary is stored as two integers plus a currency, never as a string, so range filters are index-friendly.

API contract

Design the search endpoint first, because it constrains everything else. It takes filter parameters as flat query parameters (not a JSON body — search results must be linkable and cacheable), returns a page envelope with total count and facet counts, and accepts a sort parameter whose value you validate against an allow-list rather than passing to the database. Everything else is ordinary REST.

Two authorization rules cut across the whole contract and belong in your notes: an employer may only touch jobs and applications belonging to their own company, and a CV may only be fetched by its owner or by an employer who has a live application from that candidate. Both are object-level checks — the kind of broken-object-level-authorization bug that tops every API security list — so write them as explicit tests, not as comments.

Search, step one: LIKE, and exactly where it stops working

Start here, honestly, because this is what everyone writes first: WHERE lower(title) LIKE lower('%' || :q || '%'). It works on your seed data and it teaches you three lessons fast. A leading wildcard cannot use a normal B-tree index, so every query is a sequential scan of the whole table. There is no linguistic knowledge, so a search for "developers" misses "developer" and a search for "manage" matches "management" only by accident. And there is no ranking: a listing that mentions the term once in a footer scores identically to one with it in the title, so your result order is whatever the planner felt like returning.

Do not skip this step and do not leave it in. Build it in phase four, feel it, and let phase five replace it — that arc is worth more in an interview than arriving with Elasticsearch and no explanation. (If you ever do need substring matching for real — an autocomplete on company names, say — the right tool is a trigram index from pg_trgm, which makes LIKE '%foo%' indexable. That is a different problem from relevance search, and knowing the difference is the point.)

Search, step two: PostgreSQL full-text search and ts_rank

This is the step that actually matters, and for a portfolio-scale job board it is where you should stop. PostgreSQL parses text into a tsvector of normalised lexemes with positions, parses the user's input into a tsquery, and matches them with the @@ operator. Stemming means "developers" finds "developer"; stop words are dropped; setweight lets a term in the title count for more than the same term in a description. ts_rank and ts_rank_cd then turn a match into a score you can order by, and ts_headline gives you the highlighted snippet users expect under each result.

Two practical notes. Choose the input parser deliberately: plainto_tsquery for naive user input, websearch_to_tsquery when you want quoted phrases and OR/- to behave the way people expect from a search engine. And combine relevance with recency rather than sorting on rank alone — a perfect match from eight months ago is a worse result than a good match from yesterday, so a blended score, or "sort by relevance" as one option alongside "sort by date", is the honest product answer.

SELECT j.id, j.title, j.company_id,
       ts_rank(j.search_doc, q) AS relevance,
       ts_headline('english', j.description, q) AS snippet
FROM   job j, websearch_to_tsquery('english', :q) AS q
WHERE  j.status = 'PUBLISHED'
  AND  j.search_doc @@ q
  AND  (:location IS NULL OR j.location = :location)
  AND  (:minSalary IS NULL OR j.salary_max >= :minSalary)
ORDER  BY relevance DESC, j.posted_at DESC, j.id DESC
LIMIT  :size OFFSET :offset;

Indexing the search: GIN, and keeping the vector fresh

A tsvector match without an index is still a sequential scan — you have bought linguistics, not speed. The index you want is GIN (Generalized Inverted Index): it maps each lexeme to the rows containing it, which is exactly the access pattern of "find every job mentioning kubernetes". GIN is slower to update and larger on disk than GiST, and for a job board that is precisely the right trade, because listings are read thousands of times and written once.

Keeping the vector current is where implementations rot. The three options are a trigger, an application-side recompute on save, and a GENERATED ALWAYS AS ... STORED column. Prefer the generated column: PostgreSQL maintains it, it cannot drift, and it needs no Hibernate involvement beyond mapping the field as insertable = false, updatable = false. Then verify with EXPLAIN (ANALYZE, BUFFERS) that your query actually reaches a Bitmap Index Scan on the GIN index — an index nobody checks is an index that is quietly not being used.

Search, step three: when Elasticsearch earns its operational cost

Elasticsearch is a genuinely better search engine than PostgreSQL. It is also a second datastore: a cluster to size and patch, an indexing pipeline to build, a dual-write or change-data-capture path to keep in sync, a reindex procedure for every mapping change, and a whole new class of "the search index is stale" bug. For a job board with tens of thousands of listings, that cost buys you almost nothing, and an interviewer who hears "I used Elasticsearch because it is what you use for search" will ask what it cost you.

Name the thresholds instead. Reach for a dedicated engine when you need typo tolerance and fuzzy matching, per-field boosting and tunable relevance you tweak without a migration, aggregations that power facet counts across millions of documents, synonym and multi-language analysis chains, or search-as-you-type at a latency Postgres cannot hold. If you do add it, add it as a read model fed asynchronously from the database — the database stays the source of truth, and search staleness becomes a measurable lag rather than a data-loss risk. Hibernate Search is the middle path worth knowing: Lucene-grade indexing driven from your JPA entities.

Faceted filtering and the combinatorial index problem

Six independent filters give sixty-four possible filter combinations, and you cannot build a composite index for each. This is the moment to understand what an index actually buys: a composite index on (status, posted_at) serves the common "live jobs, newest first" path; the GIN index serves keyword; a range index on salary serves salary. Everything else is filtered after the driving index has cut the candidate set down, and that is fine, because the driving predicate — published status plus a keyword or a recency window — usually reduces millions of rows to hundreds before any other filter runs.

Facet counts ("Remote (412)") are the second half of the problem. Computing them by re-running the query once per facet value is the naive approach and it will be your slowest endpoint. Do it in one pass with conditional aggregation or GROUPING SETS over the filtered set, cache the counts for the unfiltered default view, and accept approximate counts for large result sets — no user has ever noticed the difference between 412 and "400+", and count(*) over a huge filtered set is often more expensive than the page of results itself.

Building the query dynamically — and the sort-column allow-list

Three routes, and you should be able to defend the one you picked. The JPA Criteria API (through Spring Data Specification) composes typed predicates and is parameterised by construction, so injection is impossible; the cost is verbosity and a query you cannot read at a glance. QueryDSL gives you the same safety with a fluent, generated, refactor-safe DSL — worth the annotation-processor setup on anything with more than a handful of filters. A hand-built native query is the most honest option for a search that already relies on tsvector and ts_rank, which the Criteria API cannot express cleanly; you append AND clauses conditionally and bind every value as a parameter.

The trap in the third route is ORDER BY. Bind parameters work for values, never for identifiers — you cannot write ORDER BY :sort — so the sort column has to be concatenated into the SQL string, and a request of ?sort=(CASE WHEN (SELECT ...) THEN ...) becomes a blind SQL injection oracle that will happily leak your password hashes one boolean at a time. The fix is an allow-list, not escaping and not a regex: map a small fixed set of client-facing sort keys to known column expressions and reject anything else with a 400. Do the same for the sort direction. This is the single most common injection hole in real search endpoints, and being able to explain it is worth more than any framework name.

// Values are bound. Identifiers are allow-listed. Never the other way round.
private static final Map<String, String> SORTABLE = Map.of(
    "relevance", "relevance DESC",
    "date",      "j.posted_at DESC",
    "salary",    "j.salary_max DESC NULLS LAST",
    "title",     "j.title ASC");

String orderBy = SORTABLE.get(request.sort());
if (orderBy == null) {
    throw new BadRequestException("Unsupported sort: " + request.sort());
}

StringBuilder sql = new StringBuilder(BASE_SELECT);
if (request.location() != null)  sql.append(" AND j.location = :location");
if (request.remoteOnly())        sql.append(" AND j.remote_flag = true");
if (request.minSalary() != null) sql.append(" AND j.salary_max >= :minSalary");
sql.append(" ORDER BY ").append(orderBy).append(", j.id DESC");   // safe: from the map

Pagination at scale: offset versus keyset

LIMIT 20 OFFSET 780 asks the database to produce eight hundred rows in sorted order and then throw seven hundred and eighty away. Cost grows linearly with the page number, so page 40 is forty times the work of page 1, and because the query re-runs against live data, a listing inserted between requests shifts every subsequent row — users see duplicates across pages and miss others entirely. Keyset (seek) pagination fixes both: instead of an offset you carry the sort key of the last row seen and ask for rows after it, which the index can jump straight to in constant time regardless of depth.

The honest caveat, and you should say it out loud in an interview: on a job board almost nobody visits page 40, so offset pagination is very likely fine and keyset costs you the ability to jump to an arbitrary page. What matters is that the choice is deliberate — that you chose offset because the depth distribution is shallow, not because you had never heard of the alternative. Two details apply either way: always include a unique tiebreaker (, j.id DESC) or your ordering is non-deterministic and pages overlap; and cap size server-side so ?size=100000 cannot become a denial of service.

-- Offset: simple, jumpable, degrades with depth
ORDER BY j.posted_at DESC, j.id DESC
LIMIT 20 OFFSET 780;

-- Keyset: constant cost at any depth, stable under concurrent inserts,
-- but only "next page" -- the client sends back the last row's sort key
WHERE (j.posted_at, j.id) < (:lastPostedAt, :lastId)
ORDER BY j.posted_at DESC, j.id DESC
LIMIT 20;

CV upload: accepting an untrusted binary from the internet

Every rule here exists because someone skipped it. Cap the size in two places — spring.servlet.multipart.max-file-size and a reverse-proxy body limit — so a hostile upload is rejected before it reaches your heap. Validate the content type by sniffing the bytes, not by trusting the filename extension or the client-supplied Content-Type header, both of which the uploader controls completely; Apache Tika reading the magic bytes is the standard answer, and you allow-list the results (PDF, DOCX) rather than block-listing the ones you fear.

Never reuse the client's filename. It arrives with path traversal sequences, null bytes, right-to-left override characters and Windows reserved names, and rendering it later is a stored-XSS vector. Generate a UUID key, store the original name as a plain database column for display, and escape it on output. Stream the upload to storage rather than calling getBytes() — a handful of concurrent multi-megabyte uploads read fully into memory is a trivially reachable out-of-memory error. Finally, record a scan_status even if your MVP sets it to SKIPPED: knowing that a real system routes uploads through a virus scanner such as ClamAV before an employer can download them is the answer an interviewer is listening for.

Storing and serving the CV: outside the web root, behind an authorization check

The file must not be reachable by URL guessing, which rules out writing it anywhere the web server will serve statically. Two acceptable designs: object storage (S3 or MinIO) with a private bucket, where downloads go through a short-lived presigned URL your application mints only after an authorization check; or a directory outside the deployment root, served by a controller that authorizes first and then streams. Either way the storage key is a UUID that reveals nothing, and the key never appears in a client-facing URL that bypasses the check.

Get the response headers right. Send Content-Disposition: attachment; filename="..." so a malicious HTML or SVG file downloads instead of executing in your origin, and X-Content-Type-Options: nosniff so the browser does not helpfully re-interpret the bytes as something executable. Stream with InputStreamResource or a presigned redirect rather than materialising the file in memory. And keep the authorization rule explicit: the owning candidate always; an employer only while an application from that candidate to one of their jobs is live — which means revoking access is a status change, not a file move.

Transactional email: templates that are not string concatenation

Four emails carry the MVP: application confirmation to the candidate, new-application notification to the employer, status-change notification to the candidate, and the saved-search digest. Build them with Thymeleaf templates rendered to HTML with a plain-text alternative part, not with string concatenation — you will want a shared layout, a footer with an unsubscribe link, and locale support, and none of that survives concatenation. Escape every user-supplied value in the template; a job title is attacker-controlled text arriving in someone's inbox.

Configure JavaMailSender through spring.mail.* and keep credentials out of the repository. In development, point it at a capture tool such as MailHog or a provider sandbox so you can see rendered output without sending real mail, and make the from-address, reply-to and a stable message identifier explicit — deliverability is a real constraint, and mail that lands in spam is mail you did not send.

Sending asynchronously, with retries and a visible failure path

An SMTP handshake takes hundreds of milliseconds on a good day and can hang for the full socket timeout on a bad one. If your POST /applications handler sends mail inline, the candidate's apply button spins for as long as your mail provider feels like taking, and a provider outage turns into an application outage. Move the send off the request thread: annotate the send method @Async with a dedicated bounded TaskExecutor (never the default unbounded one), and enable it with @EnableAsync.

Two subtleties separate a working implementation from a correct one. First, ordering: publish the mail as a Spring application event and consume it with @TransactionalEventListener(phase = AFTER_COMMIT), otherwise you will cheerfully email "your application was received" for a transaction that then rolls back. Second, failure: an async void method swallows its exception into a log line nobody reads. Give mail a small outbox table — row inserted in the same transaction as the business change, a worker picks it up, retries with exponential backoff, and moves it to a failed state after N attempts — so "did that email go?" is a query rather than a guess. That outbox is also the exact pattern you would reuse later for a message broker.

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Async("mailExecutor")                       // bounded pool, never the default
public void onApplicationSubmitted(ApplicationSubmitted event) {
    try {
        mailService.sendApplicationConfirmation(event.applicationId());
        outbox.markSent(event.outboxId());
    } catch (MailException e) {
        outbox.markForRetry(event.outboxId(), e.getMessage());   // visible failure
    }
}

Saved searches, the scheduled digest, and the duplicate-send problem

A saved search stores the criteria a candidate used, as JSONB, plus a frequency and a last_notified_at watermark. The digest job wakes on a cron schedule, re-runs each active saved search restricted to jobs posted since that watermark, and mails a batch of new matches. Two details make it behave: advance the watermark after a successful send, not before, and skip empty results — an alert email with nothing in it trains people to ignore your alerts.

Now the interesting failure. @Scheduled is per JVM. Deploy three replicas and all three fire at the same instant, and every candidate receives three identical digests; during a rolling deploy they might get four. The fix is a distributed lock: ShedLock is the standard Spring answer, storing a lock row in the same PostgreSQL database you already have, so exactly one instance runs the job and the others skip it. The alternatives worth naming are leader election (Spring Integration's LockRegistryLeaderInitiator, or Kubernetes lease objects), a Quartz cluster with a shared job store, or moving the trigger out of the application entirely into a Kubernetes CronJob that hits an internal endpoint. Whichever you pick, make the per-recipient send idempotent too — a unique constraint on saved search plus digest window means even a double-run cannot double-send.

@Scheduled(cron = "0 0 7 * * *", zone = "Asia/Kolkata")
@SchedulerLock(name = "savedSearchDigest",
               lockAtMostFor = "PT30M",     // released if the instance dies
               lockAtLeastFor = "PT5M")     // guards against clock skew re-runs
public void sendDailyDigests() {
    savedSearches.findActiveDaily()
                 .forEach(digestService::sendIfNewMatches);   // advances the watermark
}

Building it

Ten build phases, each independently runnable and demoable

Every phase ends with something you can show on screen and commit. Do not start phase five until phase four demonstrably works — the whole value of the search progression is that you felt the previous version fail. Write the tests for each phase as you go rather than as a final chapter; a phase is not done when it compiles, it is done when a test proves it.

  1. Schema, roles and authentication. Flyway or Liquibase migrations for the core tables, the two user types with role-based authorization, registration and login, and a protected endpoint that proves the role split works. Demo: an employer token opens the employer endpoint and a candidate token gets a 403.
  2. Job CRUD for employers. Create, edit, publish, close. Company scoping enforced server-side, status transitions validated, and a test that proves employer A cannot edit employer B's listing. Demo: post a job through the API, list it, close it.
  3. Candidate profile and CV upload. Profile fields, multipart upload with size and sniffed-content-type validation, generated storage key, and a download endpoint behind an authorization check. Demo: upload a PDF, try to upload a renamed executable, watch it be rejected.
  4. Basic search and filtering with pagination. The naive version: LIKE on title and description, the six filters, sorting, offset paging with a server-side size cap. Demo: search, filter, page. Then run EXPLAIN and look at the sequential scan you just created.
  5. Upgrade to full-text search with ranking. The generated tsvector column, the GIN index, websearch_to_tsquery, ts_rank, snippets, and relevance as a sort option. Demo: the same searches from phase four returning better results, plus the EXPLAIN output showing the index scan.
  6. Applications and the status pipeline. Apply (idempotent, pinning the CV version), the employer review queue, status transitions writing application_event rows, and the candidate's tracker view. Demo: the full apply-to-hire path for one candidate.
  7. Email notifications, sent asynchronously. Thymeleaf templates, JavaMailSender, an @Async bounded executor, AFTER_COMMIT event publication, and the outbox with retries. Demo: apply for a job and watch the confirmation appear in MailHog while the HTTP response returns immediately.
  8. Saved searches and the scheduled digest. Persist criteria as JSONB, the cron job, the watermark, and ShedLock. Demo: run two instances locally on different ports and show exactly one digest going out.
  9. Angular UI. Search page with filters and facet counts, listing detail, apply flow with upload, candidate tracker, employer dashboard. Reactive forms for the search panel, query parameters synced to the URL so results are shareable, and an interceptor attaching the token.
  10. One stretch goal, finished. Pick a single item — resume parsing with Tika, recommendations from profile-to-listing similarity, a scheduled expiry job that closes stale listings, or blended relevance-plus-recency ranking — and complete it properly. One finished stretch goal reads far better than four abandoned ones.

Interview questions

An interviewer who sees "Job Portal" on your CV will not ask you what Spring Boot is — they will ask why your search works the way it does. These are the questions this project attracts in Indian product and service-company rounds, from the screening call to the design round:

Beginner Walk me through what happens when a candidate types "java developer bangalore" into your search box.

The Angular search panel puts the terms and active filters into query parameters so the URL is shareable. The controller binds them to a request record, validates the page size against a cap and the sort key against an allow-list, and hands them to the search service. The service builds one SQL statement: websearch_to_tsquery over the stored tsvector column for the keyword, conditional AND clauses for location, salary, remote and recency, ranking by ts_rank blended with recency, then LIMIT and OFFSET. PostgreSQL uses the GIN index on the tsvector to find candidate rows and filters the rest. The response is a page envelope with results, snippets, total count and facet counts.

Beginner Why did you not just use LIKE with wildcards?

Three reasons. A leading wildcard cannot use a B-tree index, so every search is a full table scan. There is no stemming or stop-word handling, so "developers" misses "developer". And there is no ranking, so results come back in whatever order the planner produced — a term in the title scores the same as a term buried in the description. I built it that way first deliberately, saw all three in EXPLAIN and in the result order, and replaced it in the next phase.

Beginner How does your CV upload validate that the file is really a PDF?

By sniffing the bytes, not by trusting the extension or the client-supplied Content-Type header — both are attacker-controlled. Apache Tika reads the magic bytes and returns a detected type, which I check against an allow-list of PDF and DOCX. I also cap the size at the multipart layer and again at the reverse proxy, generate a UUID storage key instead of reusing the client's filename, and store the original name as data to be escaped on display.

Intermediate Your search endpoint takes a sort parameter. How is that not a SQL injection hole?

Because it never reaches the SQL as user input. Bind parameters only work for values, not identifiers, so a sort column has to be concatenated into the statement — which is exactly the hole. I map a small fixed set of client-facing keys ("relevance", "date", "salary", "title") to known column expressions in code; an unrecognised key gets a 400 and nothing is concatenated. Same for direction. Escaping or regex-filtering the input would be the wrong answer: allow-listing is the only approach that is safe by construction.

Intermediate Six filters means sixty-four combinations. How do you index for that?

You do not — you index the driving predicate and let the rest filter afterwards. A partial index on (status, posted_at DESC) WHERE status = 'PUBLISHED' serves the default browse; the GIN index on the tsvector serves keyword search; a range index covers salary. Whichever of those runs first typically cuts millions of rows to hundreds, and filtering the remainder in memory is cheap. Building a composite index per combination costs write throughput and disk for indexes the planner will mostly ignore.

Intermediate How do you compute facet counts without running one query per facet?

Conditional aggregation in a single pass over the filtered set — count(*) FILTER (WHERE remote_flag) and friends, or GROUPING SETS when the facets are dimensions of the same column. The unfiltered default view's counts are cached, since they change only when listings do. For very large result sets I would show approximate counts rather than pay for an exact count(*), which is often more expensive than fetching the page itself.

Intermediate Offset pagination degrades with depth. Why is it still in your project?

Because the depth distribution on a job board is shallow — almost nobody goes past page three — and offset gives users the ability to jump to an arbitrary page, which keyset cannot. I know the cost: OFFSET 780 makes the database produce and discard 780 rows, and concurrent inserts shift rows between requests so users see duplicates. If deep paging mattered, or if this were an infinite-scroll feed, I would switch to keyset with the sort key carried in the cursor. Either way I include id as a tiebreaker so ordering is deterministic, and I cap the page size server-side.

Intermediate Where is the CV stored, and how do you stop someone downloading another candidate's CV?

Never under the web root. In production it goes to a private object-storage bucket under a UUID key; downloads run through a controller that performs the authorization check and then either streams the object or issues a short-lived presigned URL. The rule is object-level: the owning candidate always, and an employer only while that candidate has a live application to one of their company's jobs. Responses carry Content-Disposition: attachment and X-Content-Type-Options: nosniff so a hostile HTML or SVG file cannot execute in my origin. I test the negative case explicitly — employer B fetching candidate X's CV must get a 403.

Intermediate Why is the confirmation email not sent inside the apply request?

Because an SMTP round trip is slow and can hang, and the user should not wait on a third party to see their application succeed. The send runs on a bounded @Async executor, triggered by a Spring application event consumed at AFTER_COMMIT so no email is ever sent for a transaction that rolls back. Failures are not swallowed into a log line: the message is written to an outbox row in the same transaction as the application, and a worker retries with backoff and marks it failed after N attempts, so "did that email go?" is a query.

Pro You run three instances. Why doesn't every candidate get three digest emails?

They would, because @Scheduled is per JVM and all three fire on the same cron tick — during a rolling deploy it could be four. I use ShedLock with a lock table in the PostgreSQL database I already run: the first instance to acquire the named lock runs the job and the others skip. lockAtMostFor releases the lock if an instance dies mid-run; lockAtLeastFor stops a fast job re-running on a second instance under clock skew. Alternatives I considered: leader election via Spring Integration or a Kubernetes lease, a clustered Quartz job store, or moving the trigger out to a Kubernetes CronJob hitting an internal endpoint. Belt and braces, the per-recipient send is idempotent on saved search plus digest window, so even a double-run cannot double-send.

Pro When would you actually move this search to Elasticsearch, and what would it cost you?

When I need something Postgres genuinely cannot do well: typo tolerance and fuzzy matching, per-field boosting tuned without a migration, facet aggregations across millions of documents, synonym and multi-language analysis chains, or search-as-you-type latency. The cost is a second stateful system — cluster sizing and patching, an indexing pipeline, a dual-write or CDC path, a reindex procedure for every mapping change, and a permanent class of staleness bugs. I would introduce it as a read model fed asynchronously, keeping Postgres as the source of truth so search lag is a measurable number rather than a data-loss risk. At this project's scale it would be cost without benefit, and Hibernate Search is the cheaper middle step if I only need Lucene-grade matching.

Pro Criteria API, QueryDSL or a native query for the search — defend your choice.

I used a native query, because the search depends on tsvector, ts_rank and ts_headline, which the Criteria API cannot express without vendor-specific escape hatches that end up uglier than the SQL. Every value is bound as a parameter and the only identifier that varies — the sort column — comes from an allow-list. For the employer dashboard's simpler dynamic filters I used Spring Data Specification, which is parameterised by construction. QueryDSL would be my choice on a codebase with many dynamic queries: same safety, far better readability, refactor-safe generated metamodel, at the cost of an annotation-processor build step.

Pro A candidate uploads a new CV after applying. What does the employer see, and why?

The employer still sees the CV that was submitted with that application. application.applied_cv_id pins the specific cv_document row, so uploading a new one creates a new version rather than mutating what an employer may already have read and made notes against. This is the same immutability argument as storing the price on an order line instead of joining to the product: the record of what happened must not change when the underlying entity does. New applications pick up the current CV.

Pro How do you keep the search-relevance ordering from being useless as the board grows?

By not ranking on ts_rank alone. Raw relevance rewards keyword density, so a stale listing that repeats a term outranks a fresh, better match — and users judge a job board on recency. I blend the score with a recency decay on posted_at, weight title matches above description matches with setweight, and expose "sort by date" as a first-class option so users can bypass the blend. Beyond that, the honest answer is that relevance tuning needs feedback data: click-through and application rate per result position, which is exactly the signal a learning-to-rank stage would consume later.
