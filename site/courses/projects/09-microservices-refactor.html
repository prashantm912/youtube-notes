Capstone 09: Microservices Refactor

You are not starting a new system. You are taking the working e-commerce monolith from capstone 08 and cutting it apart while it stays in production — one seam at a time, with a deployable build at the end of every phase. The hardest engineering here is not the services; it is the order you do things in.

Knowledge Library → Courses → Real-World Projects → Microservices Refactor

What this capstone builds

Capstone 08 left you with a modular monolith: one Spring Boot application, one PostgreSQL schema, clean package boundaries for catalog, inventory, order, payment and customer, and one deployment pipeline. This capstone decomposes it into five independently deployable services behind a Spring Cloud Gateway, with Kafka as the event backbone, a saga replacing the checkout transaction, Resilience4j guarding the remaining synchronous hops, and OpenTelemetry stitching one customer checkout back into one trace.

The brief is deliberately a migration brief, not an architecture brief. Anyone can draw five boxes. The skill this capstone teaches — and the skill an interviewer is actually probing — is sequencing the cuts so that the system is releasable at every commit, the database split happens in the safest possible order, and you can stop halfway and still have something better than what you started with.

The brief

Why this refactor is justified — and the reader who should stop here

Start by being honest: the monolith was fine. It served real traffic, it was easy to reason about, a single transaction gave you consistency for free, and one deploy shipped the whole product. Nothing about "microservices" made it worse. If your reason for this refactor is that microservices are modern, close this page and go make capstone 08 faster instead — that is the better engineering decision and, said out loud in an interview, the better answer.

Three pressures do justify it, and you should be able to state which ones apply to you. Independent scaling: catalog browsing is read-heavy and bursty (a sale, a marketing email, a bot crawl) while checkout is write-heavy and comparatively low-volume — in one process you must scale the whole JVM, and its whole connection pool, to absorb a read spike. Independent deploy cadence: catalog copy and pricing rules change several times a day, the payment integration changes twice a year and every change needs sign-off; one artifact forces the cautious code to ride the reckless code's release train. Team autonomy: past roughly three teams in one codebase, merge queues, shared migrations and cross-team regression risk cost more coordination than the architecture saves.

What you are buying it with is also concrete, and you must price it before phase 1: no more distributed transactions, so checkout becomes eventually consistent and needs compensations; joins across the seam become network calls that can fail; local debugging becomes distributed tracing; one CI pipeline becomes five; one schema migration becomes five, coordinated. Chris Richardson's dark-energy/dark-matter framing is the cleanest way to talk about this in a design round — the forces pushing services apart and the forces pulling them back together, both real at the same time.

Target architecture: five services, one gateway, one event backbone

The end state is five services, each owning its own database and its own deployment: catalog (products, categories, prices, search projection), inventory (stock levels, reservations), order (orders, order lines, order state machine), payment (authorizations, captures, refunds, gateway integration) and customer (profiles, addresses, identity mapping). Spring Cloud Gateway sits at the edge doing routing, authentication token validation, rate limiting and request-id injection, so the browser and mobile clients keep talking to one origin and never learn that the backend split. Service-to-service addressing uses Kubernetes DNS if you are already on Kubernetes and a registry (Eureka or Consul) if you are not — pick one and do not build both.

Kafka carries every fact that another service needs to know about but must not block on. Configuration is centralized (Spring Cloud Config or a Kubernetes ConfigMap/Secret pair), Resilience4j wraps the few synchronous calls that survive, and an OpenTelemetry agent on every service exports traces to a collector so one checkout renders as one trace across the gateway and all five services.

The decomposition plan: which seam to cut, and in what order

You already have the seams. Capstone 08's modules were drawn along business capabilities, and those package boundaries — not technical layers — are your service boundaries. Do not re-derive them; do audit them. For each module, list the classes outside it that reference its entities directly, and the database tables it writes that another module also writes. Those two lists are the actual cost of extracting it. A module with a long "other writers" list is not ready to leave; fix that inside the monolith first, where a refactor is a compile error rather than a production incident.

The extraction order follows from that audit, and the principle is most read-heavy and least coupled first. Catalog goes first: it is mostly reads, almost nothing writes into it from elsewhere, and its failure mode is degraded browsing rather than lost money — a perfect place to make your gateway, deployment pipeline, tracing and contract-test machinery real while the stakes are low. Inventory goes next because the order module needs a reservation API from it before order can leave. Payment follows: it is naturally isolated (it already talks to an external gateway) and it has the cleanest interface. Order goes last, because order owns the invariants — a line item must reference a real product, stock must not be oversold, an order must not exist without an authorized payment — and once order is out you have no shared transaction left to enforce them. You want the saga machinery, the outbox, the tracing and the contract tests all working before you take that step, not during it. Customer can move any time after catalog; it is small and mostly read.

1. catalog    read-heavy, low coupling, safe failure mode   -> proves the machinery
2. customer   small, mostly read, no invariants at risk     -> optional, low risk
3. inventory  needed by order; publishes reservation API    -> introduces reservations
4. payment    already isolated behind an external gateway   -> introduces async auth
5. order      owns every invariant; needs the saga first    -> the real graduation

Rule: never extract a module whose invariants you cannot yet enforce
      without a database transaction.

Splitting the database: shared tables, foreign keys and reference data

This is the part people underestimate. Extracting a Spring Boot module into its own process takes a day; giving it its own database takes a month, because the single schema is where all the hidden coupling actually lives. Three transformations do most of the work. Shared tables become owned tables: exactly one service may write a table, everyone else reads through that service's API or its events. Foreign keys across the seam become identifiers: order_line.product_id stops being a constrained reference to product.id and becomes a plain column plus, at write time, a validation call or an event-fed local copy — the database will no longer stop you inserting a line for a product that does not exist, so the order service must. Reference data gets replicated rather than joined: the order service keeps a small denormalized copy of the product name, SKU and the price at the time of purchase, fed by product.changed events, because an order confirmation must render even when catalog is down, and because the price on a two-year-old invoice must be the price that was charged, not today's price.

Do the split in the monolith first. Introduce separate schemas inside the same PostgreSQL instance, remove cross-schema foreign keys, and let the code fail its integration tests until every cross-boundary read goes through a module interface. Only then move the schema to its own instance. Splitting a schema you can still test with one transaction is an afternoon of red tests; splitting one across two live services is an outage. Expect to give up some normalization permanently: an order line that stores the purchased price is not denormalization for performance, it is a correctness requirement, and framing it that way is a strong interview answer.

catalog     OWNS  product, category, price, product_search_projection
inventory   OWNS  stock_level, reservation, reservation_line
order       OWNS  customer_order, order_line, outbox
                  + replica: product_snapshot(sku, name, price_at_purchase)
payment     OWNS  payment_intent, authorization, capture, refund, outbox
customer    OWNS  customer, address, contact_preference

Cross-seam rules
  - one writer per table; readers use API or events, never a second connection
  - order_line.product_id : identifier only, no FK, validated at write time
  - price_at_purchase     : copied at checkout, never re-read from catalog
  - no cross-service JOIN  -> API composition or a local read model instead

Contracts at the seams: what each service promises

Every seam gets two contracts, and you should write both before you write any extraction code. The synchronous contract is the REST API the service exposes: resource paths, request and response schemas, error shapes, idempotency semantics and a version. The asynchronous contract is the set of events it publishes: topic name, key, schema, and — the part people forget — the delivery guarantee (at-least-once, so consumers must be idempotent) and the ordering guarantee (per key only).

Keep the synchronous surface deliberately small. Catalog exposes product lookup and search. Inventory exposes reserve, confirm and release — never "set stock to N" from outside, because that hands your invariant to a caller. Payment exposes authorize, capture and refund, all keyed by an idempotency key the caller generates. Order exposes place, cancel and read. Customer exposes profile read and address read. Everything else that another service wants to know arrives as an event. When you are tempted to add a sixth synchronous endpoint, ask whether the caller needs an answer now or merely needs to know eventually — the second case is an event, and events do not fail your checkout when the callee is restarting.

POST /inventory/reservations        Idempotency-Key: <uuid>
  { "orderId": "...", "lines": [ { "sku": "...", "qty": 2 } ] }
  201 { "reservationId": "...", "expiresAt": "..." }
  409 { "code": "INSUFFICIENT_STOCK", "sku": "..." }

POST /inventory/reservations/{id}/confirm    -> 200 | 404 | 410 (expired)
POST /inventory/reservations/{id}/release    -> 204, safe to call twice

Events with Kafka: what each service publishes

Fix the event catalogue early, because it is harder to change than any API. Catalog publishes product.changed and product.price.changed, keyed by product id. Inventory publishes stock.reserved, stock.released and stock.level.changed, keyed by SKU. Order publishes order.placed, order.confirmed and order.cancelled, keyed by order id. Payment publishes payment.authorized, payment.failed and payment.refunded, keyed by order id. Customer publishes customer.updated. Keying by the aggregate id is what buys you per-entity ordering, since Kafka orders within a partition only — two events about the same order will never be processed out of sequence, while events about different orders are free to run in parallel.

The catalog-to-search case is where you choose between the two event styles, and it is a favourite interview question. A notification event carries only { productId, version } and the search indexer calls back to catalog for the details: small payloads, no stale data in the message, but every event becomes an HTTP call and search now fails when catalog is down — you have coupled them again through the back door. An event-carried state transfer event carries the whole product document, so the indexer needs no callback at all and keeps working through a catalog outage: bigger messages, a real risk of processing a stale version if you ignore ordering, and the consumer holds a copy of data it does not own. For search indexing, take state transfer — the whole point of the read model is availability independent of catalog, and the version field plus per-key ordering handles staleness. For something like an audit trigger where payload size matters more than availability, notification is the right call. Say which you chose and why; "it depends" without the reasoning scores nothing.

The transactional outbox, consumer idempotency and schema evolution

The moment order writes a row and publishes an event, you have a dual write, and dual writes diverge. Commit the transaction and crash before the Kafka send: the order exists and nobody was told. Send to Kafka and roll back the transaction: everyone was told about an order that does not exist. There is no arrangement of these two statements that is safe, and wrapping them in @Transactional does not help because Kafka is not in the transaction. The transactional outbox is the fix: in the same local transaction that writes the order, insert a row into an outbox table in the same database. One commit, one atomic outcome. A separate relay then reads the outbox and publishes to Kafka — either a poller that selects unpublished rows, or, better, Debezium reading the PostgreSQL write-ahead log via change data capture, which adds no query load and no polling latency. Debezium even ships an outbox event router SMT that turns outbox rows into properly keyed topic messages.

The relay guarantees at-least-once delivery, never exactly-once, so every consumer must be idempotent. Give each event a stable id in the outbox row, and have the consumer record processed ids in a processed_event table written in the same transaction as its business change; a duplicate then hits a primary key violation and is dropped. Where the business operation is naturally idempotent — setting stock to a value, upserting a product projection — lean on that instead and skip the table. Finally, register your event schemas: with a schema registry and Avro or Protobuf you get compile-time-ish enforcement that a producer cannot ship a breaking change, and backward-compatible evolution rules (add optional fields, never remove or retype a field, never reuse a field number) so a consumer written last quarter keeps working.

-- written in the SAME transaction as the order insert
CREATE TABLE outbox (
  id            uuid        PRIMARY KEY,
  aggregate_type text       NOT NULL,   -- 'order'
  aggregate_id   text       NOT NULL,   -- becomes the Kafka key
  event_type     text       NOT NULL,   -- 'order.placed'
  payload        jsonb      NOT NULL,
  created_at     timestamptz NOT NULL DEFAULT now()
);

-- consumer side: at-least-once means duplicates WILL arrive
CREATE TABLE processed_event (
  event_id   uuid PRIMARY KEY,
  handled_at timestamptz NOT NULL DEFAULT now()
);

The place-order saga: choreography versus orchestration

This is the centrepiece. In capstone 08 checkout was one method with one @Transactional annotation: reserve stock, charge the card, write the order, commit. Now those three steps live in three services with three databases and there is no distributed transaction — two-phase commit is available in theory, unavailable in practice against a third-party payment gateway, and a coordinator outage locks every participant. So checkout becomes a saga: a sequence of local transactions, each publishing an event that triggers the next, with a compensating action defined for every step that has already committed.

In the choreographed version there is no coordinator. Order writes a PENDING order and publishes order.placed; inventory consumes it, reserves stock and publishes stock.reserved; payment consumes that, authorizes and publishes payment.authorized; order consumes that and moves to CONFIRMED. Failures flow backwards through payment.failed and stock.released. It is beautifully decoupled and genuinely painful to operate: the flow exists nowhere in the code, so understanding it means reading four services and a topic list, and cyclic dependencies creep in as steps are added.

In the orchestrated version an order-saga component inside the order service owns an explicit state machine and issues commands — ReserveStock, AuthorizePayment, ConfirmStock — reacting to replies. The whole flow is one readable class, the saga's current step is a column you can query during an incident, adding a step (fraud check, loyalty points) is a local change, and the participants stay dumb. The cost is a component that knows about all three services and the discipline to keep it a coordinator rather than letting business logic leak into it.

Recommendation: orchestrate the place-order saga. It has five-plus steps, real money, compensations that must fire in a specific order, and a customer-visible state that support staff will be asked about at 11pm — every one of those argues for a flow you can read in one file and a state you can query in one table. Keep choreography for the simple fan-outs where nobody needs to coordinate anything: order.confirmed triggering the email, the analytics write and the loyalty accrual, none of which needs a reply or a compensation.

ORCHESTRATED place-order saga (state lives in order service)

  step            forward action              compensation
  ----            --------------              ------------
  1 order         create order PENDING        mark order CANCELLED
  2 inventory     reserve stock               release reservation
  3 payment       authorize payment           refund / void authorization
  4 inventory     confirm reservation         (nothing: stock is committed)
  5 order         mark order CONFIRMED        -

  failure at step 3  -> compensate 2, then 1   (release, then cancel)
  failure at step 4  -> compensate 3, then 2, then 1
  compensations run in REVERSE order and must be idempotent

Compensating actions, semantic locks and what the customer sees

A compensation is not a rollback. A rollback erases history; a compensation is a new business fact that undoes the effect of an old one, and it is visible. Releasing a reservation returns stock but the reservation happened. Refunding a payment does not un-charge the card — it puts a debit and a credit on the customer's statement, and on an Indian debit card that money may be gone for three to five working days. Cancelling an order leaves a cancelled order in the customer's history. Write each compensation deliberately: release the reservation (idempotent, safe to call twice, and it must also be triggered by a reservation expiry timer in case the saga itself dies), void or refund the authorization (void it if you have not captured, refund if you have — and always with the same idempotency key so a retry cannot double-refund), cancel the order with a reason code the support team can read.

Some steps have no compensation at all, and you must design around that instead of pretending otherwise. A dispatched shipment cannot be un-dispatched; a sent email cannot be unsent. The standard move is to order the saga so that the irreversible step is last (a pivot transaction: everything before it is compensatable, everything after it is a retriable step that must eventually succeed), and to make the truly irreversible actions consume a confirmed event rather than participate in the saga.

Then there is the semantic lock, the problem an interviewer will push you on. Between step 1 and step 5 the order exists in PENDING state. The customer refreshes and sees an order that is not really an order yet. Support sees it too. A reporting job might count it as revenue. There is no database lock protecting you here — the local transaction committed. The fix is to make the intermediate state explicit and honest at every layer: an order.status of PENDING that the UI renders as "confirming your order", an API that never returns a PENDING order as placed, reports that filter on CONFIRMED, and a timeout that moves an order stuck in PENDING to a terminal state so it cannot sit there forever. Reserved stock is the same problem seen from inventory's side: a reservation with an expiry, not a decrement.

Resilience on the synchronous calls that survive

Most cross-service traffic is now events, which fail politely — the consumer lags, the broker retains, nothing cascades. The synchronous calls that remain are the dangerous ones, and each needs four decisions: a timeout, a circuit breaker, a retry policy and a fallback. Wrap the gateway-to-service hops and the few service-to-service hops with Resilience4j, and be specific about the fallback: catalog unavailable during browsing degrades to a cached product list or an honest "temporarily unavailable" panel; customer profile unavailable degrades to the identity token's name; inventory unavailable during browsing shows the product without a stock badge rather than showing zero, because a false out-of-stock loses a sale.

Budget the timeouts across the chain rather than setting each one to a comfortable number. If the gateway gives the browser 3s, the order service cannot spend 2s on inventory and 2s on payment; the inner budgets plus retries must fit inside the outer one, or the client times out while your services are still hopefully working, which produces the worst possible outcome — the customer sees a failure and the charge goes through anyway. Retries need exponential backoff with jitter so a wobbling downstream is not finished off by a synchronized retry storm. And the payment call is the exception that proves the rule: never blindly retry an authorization. A timeout there is ambiguous — the request may have reached the gateway and the response may have been lost — so retrying can charge the customer twice. Send an idempotency key with the original request, and on timeout do not retry the charge; query the payment's status by that key and act on the answer.

Observability: one checkout is one trace

The debugging you took for granted is gone. In the monolith a failing checkout was one stack trace in one log file. Now it is five services, a broker and a gateway, and "the order failed" tells you nothing about where. Distributed tracing is not a nice-to-have on this project, it is the replacement for the stack trace, and you should not extract the order service until it works. Run the OpenTelemetry Java agent (or Micrometer Tracing on Spring Boot) on every service so a trace id is created at the gateway and propagated on every HTTP hop through W3C traceparent headers — and, crucially, on every Kafka message through record headers, so an asynchronous saga step joins the same trace rather than starting a new one. That propagation across the broker is the piece most teams miss and the detail that impresses in an interview.

Put the same correlation id into every log line (an MDC field populated from the trace context) so that one grep in your aggregated logs returns the whole checkout across five services. Then give each service its own dashboard — request rate, error rate, latency percentiles, JVM and pool health — plus the ones that are new in this architecture: consumer lag per topic and consumer group, outbox backlog depth and age, saga step durations and the count of sagas stuck in a non-terminal state. Alert on symptoms customers feel (checkout success rate, gateway error rate, p99 latency) rather than on causes; a single pod restarting is not an incident, a falling checkout success rate is.

Testing the seams: consumer-driven contracts

Independent deployability is the entire point of this refactor, and it is also the thing that breaks you. The day catalog ships a change that renames a JSON field, order's client breaks in production — and nobody's test suite caught it, because catalog's tests pass and order's tests use a mock catalog that still returns the old shape. The mock is the problem: it encodes your belief about the provider, and beliefs go stale silently.

Consumer-driven contract testing fixes that. Each consumer declares what it needs — this request produces this response shape — and that contract is verified twice. On the provider's build, generated tests replay the contract against the real controller, so catalog's pipeline goes red the moment it breaks a consumer. On the consumer's build, the same contract generates a stub the consumer tests against, so the mock can never drift from what the provider actually promises. Spring Cloud Contract does both from one Groovy or YAML file, and it covers messaging as well as HTTP: you can write a contract asserting the exact shape of order.placed and have inventory's test suite verify its consumption of it. Add these before you extract the order service — that is the phase where the contracts start earning their keep.

Testing the seams: Testcontainers and a thin end-to-end suite

The second half of the testing story is integration tests that use real infrastructure. Embedded Kafka and H2 will happily pass tests that fail in production — different SQL dialect, different rebalance behaviour, different serialization. Testcontainers starts a real PostgreSQL and a real Kafka in Docker for the duration of the test class, so your outbox relay, your consumer group configuration, your Avro serializers and your actual migrations are all exercised. Spring Boot 3's Testcontainers support and @ServiceConnection wire the container's URL and credentials into the context automatically, which removes the property-plumbing boilerplate that used to make these tests unpleasant. Each service owns tests like this for its own seam: publish an event, assert the projection updated; call the reservation API, assert the row and the emitted event.

Above that, keep the end-to-end suite deliberately thin. It is the slowest, flakiest and most expensive layer, and every scenario you add there is a scenario you should have caught in a contract or integration test. Three or four journeys are enough: a successful checkout end to end, a checkout that fails at payment and compensates correctly, a checkout that fails at reservation, and a catalog change propagating to search. Run them against a Compose or ephemeral-namespace deployment in CI, and treat a flaky end-to-end test as a bug to fix or a test to delete — never as noise to retry.

The migration: ten phases, each one shippable

This is the build plan, and the constraint that governs it is absolute: every phase ends with a system you could deploy to production and walk away from. No phase leaves a half-extracted service, a table with two writers, or a branch that must be finished before release. That is what makes this a strangler fig rather than a rewrite — the new system grows around the old one, traffic moves across seam by seam, and the monolith is removed only when nothing routes to it any more. It also means you can stop after phase 4 if priorities change and still be better off, which is the honest way to sell a migration to a product manager.

  1. Gateway in front, nothing else changes. Put Spring Cloud Gateway between clients and the monolith. All routes proxy to the one backend. Add authentication, rate limiting and request-id injection here. Point DNS at the gateway. Ship it. You now have the single place through which you will later reroute traffic, and you have proved it under production load before it matters.
  2. Kafka and the outbox, inside the monolith. Stand up Kafka (and a schema registry). Add the outbox table and a relay — poller or Debezium — and have the monolith publish its first domain events in the same transactions that already write the data. Nothing consumes them yet except a logging sink. Ship it. The riskiest infrastructure is now live and observed with no service extracted.
  3. Extract catalog as a read-only service. A new catalog service reads a replica or subscribes to catalog events; the monolith remains authoritative and still handles writes. Route only GET /products/** at the gateway to the new service, behind a flag you can flip back in seconds. Ship it. You have a second deployable, a second pipeline, and a rollback that is one route change.
  4. Flip catalog ownership. Move catalog writes to the catalog service, give it its own database, and delete the product tables from the monolith. The monolith now consumes product.changed for whatever it still needs. Ship it. This is the first true database split and the first module gone for good.
  5. Extract inventory with the reservation API. Move stock tables out, expose reserve/confirm/release with idempotency keys and reservation expiry, publish stock.reserved and stock.released. The monolith's checkout now calls inventory over HTTP inside its existing transaction — still consistent, because order and payment have not moved. Ship it.
  6. Extract payment. Move authorizations, captures and refunds to their own service and database, keyed by idempotency key, with the external gateway integration behind it. Publish payment.authorized and payment.failed. The monolith still orchestrates checkout. Ship it.
  7. Extract order and implement the saga. The big one. Order gets its own database and the orchestrated saga replaces the transaction, with PENDING state, compensations and expiry timers. Run both paths behind a percentage flag at the gateway and compare outcomes before shifting traffic. Ship it — and expect this phase to take as long as phases 1 to 6 combined.
  8. Resilience and tracing throughout. Circuit breakers, timeout budgets, retries with jitter and designed fallbacks on every synchronous hop; OpenTelemetry on every service with trace context propagated across Kafka; correlation ids in logs; per-service dashboards and symptom-based alerts. Ship it. (In practice you add these incrementally from phase 3; this phase is where you make them complete and consistent.)
  9. Contract tests everywhere. Spring Cloud Contract for every HTTP and messaging seam, wired into each service's pipeline so a provider cannot merge a breaking change. Testcontainers integration tests per service, plus the thin end-to-end suite. Ship it. Only now is "deploy any service independently" actually true rather than aspirational.
  10. Decommission the monolith path. Move customer out, remove the last gateway routes pointing at the monolith, verify with traces that nothing reaches it, keep it running and idle for a release cycle, then delete it — code, pipeline, database and all. Ship it. A migration that leaves a dormant monolith running "just in case" has not finished; it has doubled your surface area.

Interview questions

An interviewer sees "migrated a monolith to microservices" on your CV and will spend twenty minutes on exactly this. These are the questions Indian product and service companies actually ask about a project like this — and the last one is the one that separates a senior engineer from a resume:

Beginner Why did you split the monolith? Give me a reason that is not "microservices are better".

Three specific pressures: catalog reads and checkout writes needed to scale independently — a browse spike forced us to scale the whole JVM and its pool; catalog changed several times a day while payment changed twice a year and needed sign-off, so one artifact forced cautious code onto a reckless release train; and past three teams the merge and migration coordination cost more than the architecture saved. If none of those had been true, keeping the modular monolith would have been the better decision.

Beginner Which service did you extract first, and why that one?

Catalog. It was the most read-heavy and least coupled module, almost nothing else wrote into it, and its worst failure mode is degraded browsing rather than lost money. That made it the right place to prove the gateway, the pipelines, tracing and contract tests while the stakes were low. Order went last because it owns every invariant, and I did not want to remove the shared transaction until the saga machinery already existed.

Beginner What did the API gateway do for you in phase 1, before anything was extracted?

It gave clients one stable origin and gave me one place to reroute traffic later. Authentication, rate limiting and request-id injection moved there, and it went into production under real load while it was still just a proxy to the monolith — so by the time it mattered, it was already proven. Every subsequent extraction became a route change I could flip back in seconds.

Intermediate How did you split a single database with foreign keys everywhere?

Three transformations. Shared tables got exactly one writer, with everyone else reading through that service's API or its events. Foreign keys across the seam became plain identifier columns plus validation in code, so order_line.product_id no longer constrains to catalog. Reference data got replicated instead of joined — order keeps a snapshot of the SKU, name and price at purchase, fed by product.changed events, which is also a correctness requirement since an old invoice must show the price charged. I did all of it as separate schemas inside the same instance first, where a broken boundary was a red test rather than an outage.

Intermediate Your service writes a row and publishes an event. How do you stop those two diverging?

You cannot, with two separate writes — commit then crash means the order exists and nobody knows; publish then roll back means everyone knows about an order that does not exist. The fix is a transactional outbox: insert the event into an outbox table in the same local transaction as the business write, so there is one commit and one atomic outcome, then have a relay publish from the outbox to Kafka. I used Debezium reading the write-ahead log, which adds no query load and no polling latency, with its outbox event router producing correctly keyed messages.

Intermediate The outbox relay gives at-least-once delivery. How do consumers cope?

They have to be idempotent, because duplicates are guaranteed rather than possible. Each event carries a stable id from the outbox row, and the consumer inserts that id into a processed_event table in the same transaction as its business change — a duplicate hits the primary key and is dropped. Where the operation is naturally idempotent, like upserting a product projection or setting a stock level, I relied on that instead. Exactly-once at the broker is not a substitute, because the side effect usually lands outside Kafka.

Intermediate Catalog changes need to reach the search index. Notification event or event-carried state transfer?

State transfer, and here is the trade-off. A notification carrying just the product id keeps messages tiny and always fresh, but every event becomes a callback to catalog, so search now fails when catalog is down — the coupling comes back through the side door. Carrying the whole product document means the indexer needs no callback and survives a catalog outage, which is the entire reason the read model exists. The costs are bigger messages and possible staleness, handled by keying on product id for per-key ordering plus a version field the consumer checks.

Intermediate Checkout spans order, inventory and payment across three databases. Why not two-phase commit?

Because it is unavailable and undesirable here. The payment gateway is a third party with an HTTP API and no XA participation, so there is nothing to enlist. Even where XA is possible it holds locks across the network for the duration of the whole flow, and a coordinator failure leaves every participant blocked — availability collapses to the product of all participants. A saga trades atomicity for availability: local transactions, each committed independently, with compensations for the ones already done.

Pro Choreography or orchestration for the place-order saga? Defend your choice.

Orchestration. The saga has five steps, real money, compensations that must run in reverse order, and a customer-visible intermediate state support will be asked about at 11pm — so I want the flow readable in one class and the current step queryable in one column. Choreography is more decoupled and I kept it for the fan-out after order.confirmed, where email, analytics and loyalty need no coordination and no compensation. The cost of orchestration is a component that knows all three participants; the discipline is keeping business logic in the services and only sequencing in the orchestrator.

Pro Payment fails at step three. Walk me through exactly what compensates, and what the customer sees.

Compensations run in reverse: release the inventory reservation, then cancel the order with a reason code. Nothing needs refunding because the authorization never succeeded — if it had succeeded and a later step failed, I would void an uncaptured authorization or refund a captured one, always with the original idempotency key so a retry cannot double-refund. The customer sees the order move from "confirming your order" to cancelled with a payment-declined reason, and their card is untouched. A compensation is a new business fact, not a rollback: the cancelled order stays in their history, and a real refund takes three to five working days to appear.

Pro During the saga the customer refreshes and sees a PENDING order that is not really placed. What is that problem called and how did you handle it?

That is the semantic lock — the intermediate state is committed and visible, and no database lock protects it. I made it explicit and honest at every layer rather than hiding it: an order status of PENDING rendered as "confirming your order" in the UI, an API that never reports a PENDING order as placed, revenue reports filtered to CONFIRMED, and a timeout that moves a stuck PENDING order to a terminal state so it cannot sit there forever. Inventory has the same shape from its side, which is why stock is a reservation with an expiry rather than a decrement.

Pro A call to the payment service times out. Do you retry?

No — not blindly. A timeout is ambiguous: the request may have reached the gateway and the response been lost, so a retry can charge the customer twice. I send an idempotency key with the original authorization, and on timeout I query the payment's status by that key and act on the answer rather than re-sending the charge. Everywhere else — catalog lookups, inventory reads — I retry with exponential backoff and jitter, and the retry budget fits inside the enclosing timeout so the client never gives up while my services are still working.

Pro How do you stop an independently deployed catalog release from breaking the order service?

Consumer-driven contract tests. Mocks encode my belief about the provider and go stale silently, which is how a renamed JSON field reaches production green. With Spring Cloud Contract, order declares what it needs from catalog; catalog's pipeline generates tests that replay that contract against its real controller and goes red on a breaking change, while order's build gets a stub generated from the same file so its tests cannot drift. It covers messaging too, so the shape of order.placed is verified on both sides. Without this, "independently deployable" is aspirational rather than true.

Pro A checkout failed in production. Show me how you debug it now that the stack trace is gone.

One trace. The gateway starts a trace id, propagated on every HTTP hop via W3C traceparent and — the part teams miss — on every Kafka message via record headers, so the asynchronous saga steps join the same trace instead of starting new ones. I open the trace and see the whole checkout across the gateway and five services with per-hop latency and the failing span. The same correlation id is in the MDC of every log line, so one search returns every log across all services. Then the saga's own state table tells me which step it stopped on and whether compensations ran.

Pro Knowing what you know now, would you do this refactor again?

For catalog and payment, yes without hesitation — independent scaling for the read path and an independent, sign-off-gated release cadence for the payment integration were both worth the cost, and both were achievable in the first six phases. For order, honestly, I would think much harder. Extracting order cost more than phases one to six combined, turned one transaction into a saga with compensations, semantic locks and expiry timers, and every bug since that touches consistency traces back to that decision. If the team had been small enough to keep shipping in one codebase, the right answer would have been to leave order and checkout inside a modular monolith and extract only the parts with genuinely different scaling and release profiles. The lesson I took away is that the migration is worth doing incrementally precisely because it lets you stop when the remaining moves stop paying for themselves — and knowing where to stop is the actual skill.
