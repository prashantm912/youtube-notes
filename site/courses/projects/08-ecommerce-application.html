Capstone 08: E-Commerce Application

The flagship build — catalog to cart to checkout to money, in one deployable unit. It is a monolith on purpose, and a modular one on purpose: capstone 09 splits these same modules into services, so every boundary you draw here is a boundary you will later cut along.

Knowledge Library → Courses → Real-World Projects → E-Commerce Application

What you are building

A working online store: a public storefront where a visitor browses categories, filters a catalog, opens a product, picks a size and colour, fills a cart, checks out with an address and a shipping option, pays in a gateway's test mode and later tracks the order — plus an admin back office where staff manage products, variants, stock and order fulfilment. One codebase, one deployable artifact, one PostgreSQL database.

This is the largest single-deployable project in the track, and the three genuinely hard parts are not the CRUD: the product-versus-variant data model, the oversell problem at checkout, and asynchronous payment confirmation over webhooks. Everything else in the brief is scaffolding around those three. Budget your time accordingly — a beautiful product grid with a broken stock decrement is a project you cannot talk about in an interview.

Read the brief end to end before writing code. Each build phase is designed to leave you with something you can run and demo, so you always have a working store rather than eleven half-finished features.

The brief

Feature outline: the MVP, and the stretch goals that come after

Scope the MVP as the shortest path from "a stranger lands on the home page" to "money has moved and an order exists". That path is: product catalog with categories, variants and images; search with faceted filtering; product detail; cart; checkout capturing address and shipping option; payment in sandbox; order placement with inventory decrement; order history and status tracking; and an admin back office for products and orders. Nothing else is in v1. Notably out of scope: multi-currency, tax engines beyond a flat rate, shipping-carrier integrations, and anything involving a real card.

Stretch goals, in the order they add the most learning per hour: reviews and ratings (a second write-heavy aggregate and a moderation workflow), wishlists (trivially easy, good for a rest), discount codes and promotions (surprisingly hard — stacking rules, per-customer limits, and a second place where price is computed), recommendations ("customers also bought", a batch job over order lines), returns and refunds (the payment flow in reverse, including partial refunds), and multi-vendor (which forces a seller dimension through catalog, inventory, orders and payouts, and is really a different product). Pick one stretch goal. Finishing one properly beats starting four.

A scoping habit worth forming: write the MVP list on one side of a page and, beside each item, the single question an interviewer would ask about it. If you cannot think of a question, the feature is probably not earning its place in a portfolio project.

Architecture: a deliberately modular monolith

One Spring Boot application, one database, one deployment — and inside it, six modules that behave like services without being services: catalog, cart, order, inventory, payment, customer. Each module is a top-level Java package, owns its own tables, and exposes exactly one public interface (plus its events and its DTOs). Everything else in the module is package-private. Modules never read each other's tables and never join across a boundary; when catalog data is needed inside an order, it is copied into the order at placement time, not referenced live.

Communication between modules is an in-process event: order publishes OrderPlaced, and inventory and payment listen. That looks like a needless indirection in a monolith — it is not. It is the seam. In capstone 09 an in-process ApplicationEventPublisher becomes a Kafka producer and the listener becomes a consumer, and the calling code does not change. Direct method calls between modules would have to be rewritten as HTTP clients with retries, timeouts and failure handling; events would not. That is the whole argument for building the monolith this way first.

Enforce the boundary mechanically or it will rot within a fortnight. Spring Modulith detects the module structure from your package layout and fails a test when one module reaches into another's internals; ArchUnit does the same thing as plain assertions if you prefer no extra framework. Put that verification test in the build on day one, before there is anything to violate.

The API surface: pin these contracts down before you build screens

Fix the endpoint list early, because the Angular app and the back end will be written in parallel and every renamed field costs both sides. Two conventions save the most pain later. First, money is an integer in the smallest currency unit (paise, cents) plus a currency code — never a floating-point rupee amount, and never a double anywhere in the stack. Second, order creation carries an Idempotency-Key header supplied by the client so a double-tapped "Place order" button cannot create two orders.

Note what the cart endpoints do not accept: a price. The client sends a variant id and a quantity; the server resolves the price. This is not a style preference, it is the fix for the single most common vulnerability in student e-commerce projects.

Catalog and variants: product is not the thing you sell

This is where most people build themselves into a corner, so slow down. A product is the marketing entity — a name, a description, a brand, a category, a gallery. A variant (or SKU) is the sellable entity — one specific combination of options, with its own barcode, its own price and its own stock row. "Nike Air Zoom" is a product; "Nike Air Zoom, Navy, UK 9" is a variant. Price lives on the variant, never on the product, because the extra-large costs more and the limited colourway costs more still. Stock lives on the variant too, for the obvious reason.

Model the options explicitly rather than stuffing "Navy / UK 9" into a string. A product declares its option types ("Colour", "Size"); each option type has option values; a variant is a set of chosen option values, joined through a link table with a composite primary key. That structure lets the product page render a colour swatch row and a size row generically, disable combinations that do not exist, and add a third dimension (fit, material) later without a migration. Free-form attributes that are informational rather than selectable — fabric, care instructions, warranty — can go in a JSONB column, but keep anything you filter or price on in real columns with real indexes.

The catalog is read-heavy in the extreme: thousands of reads per write, and the writes come from a handful of admin users. That asymmetry is what justifies the caching and the denormalised search projection in the next topic, and it is worth stating out loud in an interview — an optimisation you can justify by access pattern reads very differently from one you added because it seemed clever.

The storefront read path: search, faceted filtering and caching

Listing pages need three things at once: a text query, a set of filters (category, brand, colour, size, price band), and the counts beside each filter option. Build it in two stages. Stage one is honest SQL — Spring Data JPA Specification composed from the query parameters, with pagination and a sort. That gets you correct results and teaches you dynamic predicate building, which is a common interview topic in its own right. Stage two is the projection: a flattened, denormalised read model of the catalog, refreshed when catalog events fire, so a listing page is one indexed query rather than a five-table join per request.

PostgreSQL's full-text search with a GIN index over a tsvector column is comfortably enough for a project of this size — reach for a search engine only when you can say what Postgres failed to do. For facet counts, a grouped aggregate over the filtered set is fine at this scale; cache the result. Speaking of which: the category tree and the product detail payload are near-immutable and read constantly, so put them behind Spring's cache abstraction backed by Redis, and be explicit about invalidation — evict on the catalog event, not on a timer you hope is short enough.

Do the N+1 pass here too. A listing that lazily loads images and variants per product will issue a hundred queries for a twenty-item page; catch it by logging SQL counts in a test rather than by noticing the page is slow in production.

Cart: guest versus authenticated, where it lives, and the price rule

Three decisions, each of which an interviewer will ask you to defend. Guest or authenticated? Force a login before the cart and you lose conversions; support both and you inherit the merge problem. Support both. A guest cart is keyed by an opaque anonymous token in an HttpOnly cookie; when that visitor logs in, the guest cart is merged into their account cart — and "merge" needs a rule you have actually chosen: sum the quantities for a variant present in both, cap at available stock, and prefer the guest cart's line when the two disagree, because it reflects what the user was doing thirty seconds ago. Merge exactly once, then delete the guest cart, or a stale token will resurrect old lines on the next login.

Where does it live? Client-side (localStorage) is free and instant but does not survive a device switch and cannot be analysed for abandoned-cart work. A database table is durable, queryable and joins to your other data, but it is a write on every quantity tweak and it accumulates dead rows. Redis with a TTL is fast, self-cleaning and ideal for guest carts that mostly get abandoned — at the cost of a second datastore and of carts that vanish silently. The defensible answer for this project: guest carts in Redis with a TTL of a few days, authenticated carts in PostgreSQL, one interface over both so the rest of the code cannot tell.

What does a cart line store? A variant id and a quantity. Not a price. Prices are re-resolved from the catalog every time the cart is read and again at checkout, and the price the client sends is ignored entirely. If the price changed while the item sat in the cart, say so in the response and let the user re-confirm. A cart that trusts a client-supplied price is a shop where anyone with the browser dev tools can buy a laptop for one rupee — it is the classic mass-assignment and business-logic flaw, and it has shipped in real stores more than once. Price is frozen exactly once, into the order line, at order creation.

Checkout and the order state machine

Checkout is a short sequence with a long tail of failure modes: collect or select a shipping address, quote shipping options for that destination, show the totals, then create the order. The rule that organises everything: the order is created before payment is attempted. Persist an order in PENDING_PAYMENT, with its lines and frozen prices and its stock reservation, and only then ask the gateway for a payment intent. The reason is reconciliation — if you create the order after the payment succeeds and your process dies in between, you have taken money with no record of what it was for, and no way to find out except by trawling the provider's dashboard. With the order first, every payment has something to attach to and a nightly job can reconcile the two sets.

Model the lifecycle as an explicit state machine rather than a pile of boolean flags. Legal transitions only, every transition appended to an order_event table with a reason and a timestamp, and the admin status endpoint validated against the same machine so staff cannot mark a cancelled order as shipped. That event log is also, for free, the "track your order" timeline the customer sees.

Two smaller decisions worth making deliberately. Totals — subtotal, shipping, tax, grand total — are stored on the order, not recomputed on read, because the tax rate will change and old orders must not. And the customer-facing order number is a separate, non-guessable value from the primary key: sequential integers in URLs let anyone enumerate your order volume, and combined with a missing ownership check they let anyone read other people's orders.

  CART  --(POST /api/orders: lines frozen, stock reserved)-->  PENDING_PAYMENT

  PENDING_PAYMENT --(webhook: payment succeeded)-->  PAID
  PENDING_PAYMENT --(webhook: payment failed)----->  CANCELLED   (release reservation)
  PENDING_PAYMENT --(reservation TTL expires)----->  CANCELLED   (release reservation)

  PAID       --(admin packs and hands to courier)-->  FULFILLED
  PAID       --(admin or customer cancels)--------->  REFUNDED   (restock, refund API)
  FULFILLED  --(return accepted, stretch goal)----->  REFUNDED

  Illegal by construction: CART to PAID, CANCELLED to anything,
  FULFILLED to CANCELLED. Every arrow writes one order_event row.

Inventory: the oversell problem and reserve-then-confirm

Two customers, one unit left, both click "Place order" in the same millisecond. Both transactions read on_hand = 1, both decide it is available, both write on_hand = 0, and you have sold stock you do not have. That is oversell, it is a lost-update race, and "wrap it in a transaction" does not fix it — under read-committed isolation both transactions read a consistent snapshot and neither notices the other. There are three real answers and you should be able to argue all three.

Optimistic concurrency puts a version column on the stock row: read it, decide, then update WHERE variant_id = ? AND version = ?; if zero rows changed, someone beat you, so re-read and retry. It is cheap, it holds no locks, and it degrades badly under genuinely high contention on one hot row — every loser retries, and during a flash sale on one SKU the retry storm can be worse than a lock. Pessimistic locking takes SELECT ... FOR UPDATE on the stock row and serialises the contenders; it is simple, always correct, and it holds a database lock for the duration of the transaction, so it must never be held across a network call to a payment gateway. Reserve-then-confirm splits the problem in time: at order creation, atomically move quantity from on_hand into reserved and write a stock_reservation row with an expires_at a few minutes out; on payment success the reservation is consumed and reserved drops; on failure or expiry a scheduled sweeper releases it back.

The recommendation for this project: reserve-then-confirm, with the reservation write itself protected by optimistic locking on the stock row. It is the only option that behaves correctly across the minutes-long gap between "order created" and "webhook arrives", which is exactly the window a pure lock cannot cover. Be honest about its failure modes: a reservation sweeper that stops running silently strangles your available stock; a TTL that is too short cancels orders whose payment was merely slow; and a webhook that arrives after expiry means you have taken money for stock you released — which is precisely why the order still exists in PENDING_PAYMENT and can be flagged for manual resolution rather than lost. Write the concurrency test before the feature: twenty threads, one unit of stock, assert exactly one order succeeds.

Payments: sandbox only, and never a raw card number

State this plainly, because it is the fastest way to fail a security screen: if a card number reaches your server, your server is in PCI DSS scope. Accepting, transmitting or storing a primary account number drags your application, your database, your logs, your backups and your entire deployment into a compliance regime built for payment processors. No portfolio project should do this, and no interviewer wants to hear that you built a card form that POSTs to your controller.

The correct architecture keeps the card outside your perimeter entirely. Either you redirect to the provider's hosted checkout page, or you embed the provider's hosted fields — an iframe served by the gateway, rendered inside your page, into which the card is typed. In both cases the card data goes from the browser to the gateway directly; your server receives only an opaque token or intent identifier. Stripe Checkout, Stripe Elements, and Razorpay's standard checkout all work this way. Build against the provider's test mode with their published test card numbers, and keep the secret key in an environment variable or a secrets manager — never in application.yml, never in the repository. The publishable or key id is the only credential the Angular app ever sees.

An India-relevant note worth having an opinion on: Razorpay is the natural choice for an INR store and supports UPI, netbanking and cards through the same integration; Stripe's documentation is the better teaching material. Either is fine for this capstone. What matters is that the flow is identical in shape — create an intent or order server-side, hand a token to the browser, let the provider collect the money, and confirm asynchronously.

Webhooks, idempotency and reconciliation

The browser telling your server "payment succeeded" is a claim from an untrusted client, and it is also unreliable — users close the tab, phones lose signal, UPI apps take their time. The authoritative confirmation is the provider's webhook: a server-to-server callback that arrives when the payment actually settles, possibly seconds later, possibly minutes. Your finalisation logic — mark the order PAID, consume the stock reservation, send the confirmation email — belongs in the webhook handler, not in the redirect handler. The redirect only updates the UI.

Four properties the handler must have. Signature verification first: the endpoint is unauthenticated and publicly reachable, so verify the provider's HMAC signature over the exact raw request body before parsing anything, and reject on mismatch. Read the body as bytes — a JSON round-trip through Jackson changes whitespace and breaks the signature. Duplicate tolerance next: providers retry until they get a 2xx, and "at least once" means you will see the same event twice. Store provider_event_id with a unique constraint and treat the constraint violation as success; that one index turns duplicate delivery into a no-op. Out-of-order tolerance third: payment.captured can arrive before payment.authorized, so drive state from the event's own type and the order's current state rather than assuming a sequence, and ignore events that would move the machine backwards. And fast acknowledgement: verify, persist the raw event, return 200, and do the work from the stored event — a slow handler earns you a retry storm on top of whatever was already slow.

Finally, reconciliation. The provider is the source of truth about money; your database is a cache of their state. Run a scheduled job that fetches payments from the provider API for a recent window and compares them against your orders, and alert on the two asymmetries: a captured payment with no PAID order (a missed or dropped webhook — you have their money and they have no order) and a PAID order with no captured payment (a bug or a manual edit). Every real payments team runs this job. Being able to say you built one puts you ahead of most candidates with an e-commerce project on the CV.

Suggested build phases

Eleven phases, each ending in something you can run, screenshot and explain. Resist the urge to build all the entities first — a vertical slice that works beats a horizontal layer that does not.

  1. Catalog schema and admin CRUD. Products, option types, option values, variants, images, categories. Flyway or Liquibase migrations from day one. Admin endpoints to create a product with its full variant matrix in one request. Demo: create a t-shirt with three colours and four sizes and see twelve variants with distinct SKUs and prices. Put the Spring Modulith or ArchUnit boundary test in the build now, while there is one module.
  2. Storefront listing, search and product detail. Public read endpoints, pagination, sorting, category filter, text search, facet counts. The Angular shell: routing, product grid, product page with a working size and colour selector that disables combinations which do not exist. Demo: browse and filter a catalog of a few hundred seeded products.
  3. Cart with guest and authenticated merge. Anonymous token cookie, cart endpoints, Redis for guest carts, PostgreSQL for account carts, and the merge on login with the rule you chose. Demo: fill a cart signed out, log in, watch it merge; then tamper with the price in the request body and watch the server ignore it.
  4. Checkout and the order state machine. Address capture, shipping options, totals, order creation with frozen prices, order-event log, admin transition validation. No payment yet — a fake "mark as paid" endpoint stands in. Demo: place an order and walk it through the lifecycle.
  5. Inventory reservation with a concurrency test. Reserve on order creation, sweeper for expiry, release on cancellation, optimistic locking on the stock row. Write the test first: N threads, one unit, exactly one winner. Demo: run the test and show the losers failing cleanly rather than overselling.
  6. Payment integration in sandbox with webhooks. Provider intent creation, hosted checkout or hosted fields in Angular, the webhook endpoint with signature verification and the unique event id, finalisation moving the order to PAID and consuming the reservation. Use the provider's CLI or dashboard to replay a webhook twice and prove the second one changes nothing. Demo: a real sandbox payment, end to end.
  7. Order history and status tracking. Customer order list and detail with the timeline built from the event log, ownership checks on every read, non-guessable order numbers. Demo: two accounts, and account B cannot fetch account A's order even with the id.
  8. Admin back office. A lazily loaded Angular area behind a role guard: product and variant management with image upload, stock adjustments, order queue with fulfilment actions, basic sales figures. Demo: fulfil an order from the admin and see the customer's timeline update.
  9. Caching and performance pass. Redis-backed caching on the category tree and product detail with event-driven eviction, the denormalised listing projection, index review against real query plans, and an N+1 hunt with SQL-count assertions. Measure before and after; a number you can quote is worth more than the optimisation itself.
  10. Test pyramid pass. Unit tests on pricing, merge rules and state transitions; slice tests on controllers and repositories; integration tests on PostgreSQL and Redis via Testcontainers; the concurrency test from phase five in CI; a webhook replay test; and one end-to-end happy path. Add the module-boundary verification test to the same run.
  11. One stretch goal, finished. Reviews, wishlists, discount codes, recommendations, returns or multi-vendor — pick the one you would most enjoy defending, and complete it including its tests and its admin surface.

Module map: which track modules this exercises

Every part of this capstone maps back to a module you have already worked through. Use it in reverse too: when a phase stalls, the linked module is where the explanation lives.

  • Application structure, web layer and configuration — Spring Boot fundamentals and auto-configuration, Spring Boot web, data access, caching, messaging and scheduling (the reservation sweeper and the reconciliation job live here).
  • Catalog and order persistence — entity mapping, relationships (product to variant to option value), Spring Data repositories, fetching and the N+1 problem (phase nine), transactions and concurrency (phase five), JPA caching.
  • Schema, indexes and isolation — normalization and design, indexing, query optimization, transactions and isolation levels (the oversell discussion), Redis (guest carts and the catalog cache).
  • Authentication, roles and ownership — authentication, authorization (the admin back office and per-order ownership checks), JWT resource server, CSRF, CORS and security headers (the webhook endpoint must be exempt from CSRF and protected by signature instead).
  • The vulnerabilities this project attracts — OWASP Top 10, authentication and authorization flaws (broken object-level authorization on order ids), input validation (quantity, coupon codes, address fields), secrets and cryptography (gateway keys and the webhook signing secret).
  • Storefront UI — signals (cart state), forms (checkout and admin product forms), HTTP and observables.
  • Routing, interceptors and front-end performance — routing fundamentals, advanced routing (guards and resolvers for the checkout steps and the lazy admin area), advanced HTTP (the auth and cart-token interceptors), performance (deferred loading on a long product grid).
  • Proving it works — Mockito basics, Spring integration testing, Testcontainers (the concurrency and webhook tests need a real database), API and contract testing.
  • The design conversation — API design, caching, database scaling (what you would do when the catalog outgrows one node), consistency and availability (the reservation window is an availability-for-consistency trade you made deliberately).

Interview questions

An interviewer sees "E-Commerce Application" on your CV and assumes it is a CRUD tutorial until you prove otherwise. These are the questions that decide which it was — weighted to Indian product and service-company rounds, where the concurrency and payments follow-ups are where the offer is won or lost:

Beginner Walk me through your schema. Why is there a product table and a variant table?

Product is the marketing entity — name, description, brand, category, images. Variant is the sellable entity — one specific combination of options, with its own SKU, its own price and its own stock row. A navy shirt in medium and the same shirt in large are two variants of one product; they can differ in price and certainly differ in stock. Option types and option values are modelled explicitly and joined to variants through a link table, so the product page can render the selectors generically and a third option can be added without a migration.

Beginner Where does price live, and why not on the product?

On the variant, as an integer in the smallest currency unit plus a currency code. Sizes and colourways are priced differently in the real world, so a price on the product cannot express what a shop needs. Integer minor units avoid floating-point rounding on money, which is a bug you cannot argue your way out of in an interview.

Beginner A guest fills a cart and then logs in. What happens?

The guest cart is keyed by an opaque token in an HttpOnly cookie and stored in Redis with a TTL. On login it is merged into the account cart with an explicit rule: sum quantities for a variant present in both, cap at available stock, prefer the guest line on conflict because it is the most recent intent. The merge runs exactly once and the guest cart is then deleted, otherwise a stale token resurrects old lines on the next login.

Intermediate Why is the price re-resolved at checkout instead of read from the cart?

Because a price sent by the client is attacker-controlled. Cart lines store only a variant id and a quantity; the server resolves the price from the catalog on every cart read and again when the order is created. If the catalog price changed while the item sat in the cart, the response says so and the user re-confirms. Trusting a client-supplied price is the classic mass-assignment flaw that lets someone buy a laptop for one rupee, and it has shipped in production stores more than once. The price is frozen exactly once, into the order line, at order creation — so historical orders remain correct when the catalog price later changes.

Intermediate Where does the cart live — database, Redis or the browser? Defend the choice.

Guest carts in Redis with a TTL, authenticated carts in PostgreSQL, behind one interface. Guest carts are mostly abandoned, so a self-expiring store avoids accumulating dead rows and a write per quantity tweak. Authenticated carts need durability, cross-device continuity and joins against customer data, so they belong in the relational store. Pure localStorage is rejected because it does not survive a device switch and gives you nothing to analyse; pure database is rejected because of the write volume and the garbage.

Intermediate Two customers buy the last unit at the same instant. How did you stop overselling?

It is a lost-update race, and a transaction alone does not fix it — under read-committed both transactions read the same snapshot. Three options: optimistic concurrency with a version column and a conditional update plus retry; pessimistic SELECT ... FOR UPDATE serialising the contenders; or reserve-then-confirm, moving quantity from on_hand into reserved with an expiring reservation. I used reserve-then-confirm with optimistic locking on the stock row, because the gap between order creation and payment confirmation is minutes long and no database lock should be held across a call to a payment gateway. I proved it with a test: twenty threads, one unit of stock, assert exactly one order succeeds.

Intermediate Why does the order exist before the payment is attempted?

So there is always something to reconcile against. The order is persisted in PENDING_PAYMENT with its frozen lines and its stock reservation, and only then is a provider intent created. If you create the order after payment succeeds and the process dies in between, you have taken money with no record of what it was for — recoverable only by trawling the provider's dashboard. Order-first also gives the webhook handler a target to attach to, gives the customer something to see if they refresh, and gives the nightly reconciliation job both sides of the comparison.

Intermediate Why is your monolith split into modules if it deploys as one artifact?

Because the boundaries are the point, not the deployment. Each module owns its tables, exposes one interface and communicates by in-process events; no module reads another's tables or joins across a boundary. That keeps the codebase navigable at size, and it means the next capstone is a migration rather than a rewrite — an in-process event publisher becomes a Kafka producer and the calling code is unchanged. I enforce it with Spring Modulith's verification test in CI, because a boundary that is only a convention is gone within a fortnight.

Pro The same payment webhook arrives three times. What happens each time?

The first time: verify the HMAC signature over the raw body, insert the event with its provider_event_id under a unique constraint, finalise the order, return 200. The second and third: the same signature check passes, the insert violates the unique constraint, and the handler treats that violation as success and returns 200 without touching the order. Providers retry until they see a 2xx, so at-least-once delivery is guaranteed and duplicates are normal rather than exceptional. The unique index is what turns a duplicate into a no-op; without it you double-decrement stock or send two confirmation emails.

Pro Your webhook signature check keeps failing even though the secret is right. Why?

Almost always because the body was parsed and re-serialised before verification. The signature is an HMAC over the exact bytes the provider sent; deserialising to a POJO and re-serialising changes key order and whitespace and invalidates it. Read the raw request body as bytes, verify against it, and only then parse. The other usual causes are a trailing newline added by a proxy, the wrong secret for the environment (test versus live secrets differ), and comparing with string equality instead of a constant-time comparison — the last one works but leaks timing.

Pro Events can arrive out of order. How does your order state machine cope?

State is driven by the event type combined with the order's current state, never by an assumed sequence. Each transition is validated against the machine, so an authorized event arriving after a captured event is recognised as a backwards move and ignored rather than applied. Every accepted transition appends to an order_event log with the provider event id and a reason, which is both the audit trail and the customer-facing tracking timeline. Illegal transitions — cancelled to paid, fulfilled to cancelled — are impossible by construction rather than by an if-statement someone will forget.

Pro Did you store card details? What would it mean if you had?

No, and deliberately. A card number touching the server puts the application, the database, the logs and the backups into PCI DSS scope, which is a compliance regime no side project should enter. The card is collected by the provider — either a redirect to their hosted checkout or their hosted fields in an iframe — so it goes from the browser to the gateway and my server only ever sees an opaque intent or token. The secret key lives in an environment variable or a secrets manager; the browser only receives the publishable key. Everything runs against the provider's test mode with their published test cards.

Pro A customer says they paid but the order shows unpaid. How do you find out what happened?

The provider is the source of truth for money; my database is a cache of their state. I run a scheduled reconciliation job over a recent window that fetches payments from the provider API and compares them with my orders, alerting on both asymmetries — a captured payment with no PAID order, meaning a webhook was dropped or my handler failed, and a PAID order with no captured payment, meaning a bug or a manual edit. For this specific customer I look up the order, find its stored payment intent id, query the provider for that intent, and either replay the webhook or finalise from the reconciliation path. Because the order was created before payment, there is always a record to attach the answer to.

Pro What breaks first when this store gets a hundred times the traffic, and what would you do?

Not the catalog — that is read-heavy, cacheable and horizontally scalable behind Redis and a read replica. It is the hot rows: a flash sale on one SKU concentrates every write on a single stock row, and optimistic retries turn into a retry storm while pessimistic locks turn into a queue. The mitigations are sharding the counter across several rows and summing, admitting a bounded number of buyers into checkout at all, or moving the decrement to a single-writer queue per SKU. Second to break is the reservation sweeper, whose failure silently strangles available stock, so it needs a metric on reservations released per run and an alert when it reaches zero unexpectedly.

Pro How would you split this into microservices, and what becomes hard?

The service boundaries are already drawn: catalog, cart, order, inventory, payment and customer, each owning its tables and already talking only through events. The mechanical part is replacing the in-process publisher with a broker and putting an HTTP or gRPC facade on each module's existing interface. What becomes hard is what the single database was hiding — placing an order and reserving stock stop being one transaction, so the flow becomes a saga with compensations, and the outbox pattern is needed so a state change and its published event cannot diverge. Read paths that used to join now need either duplication or composition, and every call gains a timeout, a retry and a failure mode. That is capstone 09.
