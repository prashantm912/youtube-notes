Capstone 01: Expense Tracker

The first thing you build end to end. It is small on purpose — one user, one list, one summary — because the point is not the feature count, it is finishing something that runs, is tested, and has no security holes you would be embarrassed to explain in an interview.

Knowledge Library → Courses → Real-World Projects → Expense Tracker

What you are building

A personal expense tracker: a person signs up, logs in, records what they spent with an amount, a date, a category and a note, then lists and filters their own spending and sees a monthly total per category. That is the whole product. It fits in roughly a dozen backend classes and half a dozen Angular components, and it can be built in evenings over two or three weeks.

This is a brief, not a tutorial. It tells you what to build, how the pieces fit, what the tables and endpoints should look like, and in what order to build them so that you always have something you can demo. It does not hand you the code — the linked documentation and reference repositories do that better, and typing it yourself is the exercise. Read the whole brief once before you open an editor; the pitfalls section in particular exists because almost every first version of this project gets those four things wrong.

The brief

Feature outline: the MVP you must finish, and the stretch goals you may not start

Scope discipline is the actual skill being taught here. The MVP is exactly this: a user can register with an email and password and log in; a logged-in user can create, edit and delete an expense carrying an amount, a spend date, a category and an optional note; they can list their expenses newest-first with paging, and filter that list by date range and by category; they can see a monthly summary that totals spending per category for a chosen month; and they can manage their own category list, with a small set of defaults seeded at registration. Nothing else. No sharing, no multi-currency, no teams, no mobile app.

Stretch goals are things you add after the MVP is deployed, tested and demoable, and you add exactly one of them: recurring expenses that materialise on a schedule; CSV export of a filtered list; a monthly budget per category with an over-budget indicator in the UI; or receipt image upload with the file stored outside the database. Each of these is a genuinely different lesson — scheduling, streaming responses, a second aggregate, and binary storage plus content-type validation — which is why you pick one and do it properly rather than half-doing four. Write the MVP list into your README on day one and treat anything not on it as a change request to yourself.

Architecture sketch: four boxes and the contracts between them

One Angular single-page app talks over HTTPS and JSON to one Spring Boot REST API, which talks JDBC to one PostgreSQL database. There is no message broker, no cache, no second service, and adding any of those to a project this size is a red flag in a code review rather than a sign of ambition. Inside the API, keep the classic three layers honest: the controller handles HTTP and shapes (request and response DTOs, status codes, validation), the service holds business rules and owns the transaction boundary, and the repository does data access. Entities never leave the service layer — the controller returns DTOs, so a column rename does not silently change your public API.

Authentication is the one place with a real design choice. A stateless JWT issued at login and sent as an Authorization: Bearer header suits an SPA and is what most interviewers expect you to have used; a plain server session with a cookie is simpler, gives you free logout, and is perfectly defensible if you can say why. Either way the security filter chain runs before your controllers and puts the authenticated user into the security context, and everything downstream reads the user from there — never from a path variable or a request body.

Data model: three tables, one foreign key that carries the whole security model

Three tables cover the MVP. app_user holds the account and the password hash. category holds a user's own category names. expense holds the money. Every one of the last two carries a user_id foreign key, and that column is not decoration — it is the security boundary. A category name is unique per user, not globally, so the unique constraint is on the pair. An expense's category must belong to the same user as the expense, which is a rule your service enforces because a plain foreign key cannot express it.

Store the amount as a whole number of minor units — paise, cents — in a BIGINT column, with a fixed currency code alongside it, and convert to BigDecimal at the edges of the system. Binary floating point cannot represent 0.10 exactly, so double accumulates error the moment you sum a month of expenses and eventually reports a total that is a fraction of a paisa off; integers cannot drift. If you prefer, NUMERIC(12,2) mapped to BigDecimal is also correct and simpler to read in the database — what is never acceptable is double, float, or PostgreSQL's locale-dependent money type. Store the spend date as a plain DATE, because "I spent this on the 3rd" has no time zone; store audit columns such as created_at as TIMESTAMPTZ, because "the row was written at this instant" absolutely does.

CREATE TABLE app_user (
  id            BIGSERIAL PRIMARY KEY,
  email         VARCHAR(255) NOT NULL UNIQUE,
  password_hash VARCHAR(100) NOT NULL,
  display_name  VARCHAR(100) NOT NULL,
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE category (
  id       BIGSERIAL PRIMARY KEY,
  user_id  BIGINT      NOT NULL REFERENCES app_user(id),
  name     VARCHAR(60) NOT NULL,
  archived BOOLEAN     NOT NULL DEFAULT false,
  CONSTRAINT uq_category_per_user UNIQUE (user_id, name)
);

CREATE TABLE expense (
  id           BIGSERIAL PRIMARY KEY,
  user_id      BIGINT      NOT NULL REFERENCES app_user(id),
  category_id  BIGINT      NOT NULL REFERENCES category(id),
  amount_minor BIGINT      NOT NULL CHECK (amount_minor > 0),  -- paise, never a double
  currency     CHAR(3)     NOT NULL DEFAULT 'INR',
  spent_on     DATE        NOT NULL,                            -- a calendar day, not an instant
  note         VARCHAR(255),
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_expense_user_date ON expense (user_id, spent_on DESC);

API contract: the endpoints, and the user that is never in them

Nine endpoints cover the MVP. Notice what is missing from every path: the user id. There is no /api/users/{userId}/expenses, because the moment a user id appears in a URL somebody will try changing it, and you will have to defend a check you should never have needed. The authenticated principal comes from the security context, the service derives the owner from it, and every repository method takes that owner as a parameter. This is the single most important line in the whole brief.

Return DTOs, not entities. Use the ordinary status codes — 201 with a Location header on create, 204 on delete, 400 for a body that fails validation, 401 when there is no valid token, 404 when the row does not exist or is not yours (never 403 for someone else's row, which confirms it exists). Paginate the list endpoint from the start with page and size parameters rather than retro-fitting it later, and shape validation errors consistently — RFC 9457 problem details is the format Spring's own error handling now produces.

The four things almost every first version gets wrong

First, ownership. If a repository method is findById(id) and the service returns whatever it finds, then user A can read, edit and delete user B's expenses simply by changing a number in the URL. That is an insecure direct object reference, and it is the most common real vulnerability in beginner full-stack projects. The fix is structural rather than a check you remember to add: make every finder take the owner — findByIdAndUserId, findAllByUserIdAndSpentOnBetween — so a query without the user does not compile into your data-access layer at all. Second, money. Never double, never float: use integer minor units or NUMERIC, and BigDecimal in Java with an explicit scale and RoundingMode — and remember BigDecimal.equals compares scale, so 2.50 does not equal 2.5, which is why compareTo is what you use in tests.

Third, dates and time zones. The day an expense belongs to is a calendar fact: model it as LocalDate mapped to DATE and it will never shift when your server moves to UTC or your user travels. Audit instants are the opposite: Instant or OffsetDateTime mapped to TIMESTAMPTZ. Mixing these up is how "expenses from 1 April" quietly starts including one from 31 March. Fourth, validation. A required field enforced only by an Angular validator is not enforced at all — anyone can post JSON straight to your API with curl. Put Jakarta Bean Validation constraints on the request DTO, annotate the controller parameter with @Valid, keep the database constraints as the last line of defence, and treat the form validators as a convenience for the user rather than a security control.

// Every finder is scoped to the owner. There is no unscoped variant to misuse.
public interface ExpenseRepository extends JpaRepository<Expense, Long> {
    Optional<Expense> findByIdAndUserId(Long id, Long userId);
    Page<Expense> findByUserIdAndSpentOnBetween(Long userId, LocalDate from, LocalDate to, Pageable page);
}

// The owner comes from the security context, never from the request.
@GetMapping("/api/expenses/{id}")
ExpenseDto get(@AuthenticationPrincipal AppUserDetails me, @PathVariable Long id) {
    return repo.findByIdAndUserId(id, me.userId())
               .map(ExpenseDto::from)
               .orElseThrow(ExpenseNotFoundException::new);   // 404, not 403
}

Suggested build phases: eight steps, each one demoable

Build in vertical slices that end in something you can show. The rule for every phase below is that at its end the application starts, does something visible, and the tests pass — so if you stop after phase 4 you still have a project worth putting on a CV, and you are never twelve hours into a rewrite with nothing running. Commit at the end of each phase with a message that says what now works.

  1. Schema and persistence. Spring Initializr with Web, Data JPA, Validation, PostgreSQL and Flyway. Write V1__initial_schema.sql, set spring.jpa.hibernate.ddl-auto=validate so Flyway is the only thing that changes the schema, map the three entities and repositories, and add a seed migration with one known user and a few categories. Demo: the app boots, the migration history table shows V1, and a repository test reads the seeded rows.
  2. CRUD API with validation and per-user scoping. Request and response DTOs, bean validation, a @RestControllerAdvice that turns your exceptions into problem details, and the five expense endpoints — all scoped to a hard-coded seeded user for now. Demo: create, list, update and delete an expense from curl or Postman.
  3. Authentication. Registration with BCrypt password hashing, login issuing a JWT (or establishing a session), a security filter chain that permits the auth endpoints and requires authentication everywhere else, and replacing the hard-coded user with the authenticated principal. Demo: a request without a token returns 401; with a token it returns only that user's data.
  4. Angular shell and the expense list. Angular CLI project, routes for login, list and edit, an auth guard on the protected routes, an HTTP interceptor that attaches the token, a typed ExpenseService, and a list component with paging. Demo: log in through the browser and see real rows from your API.
  5. Create and edit forms. Reactive forms with validators mirroring the server rules, a shared form component for create and edit, and error messages that render the server's validation response when the two disagree. Demo: add an expense in the UI and watch it appear in the list.
  6. Filtering and the monthly summary. Date-range and category filters wired to the query parameters you already defined, a /api/summary/monthly endpoint that aggregates in SQL with GROUP BY, and a chart of category totals on a dashboard route. Demo: pick a month and see where the money went.
  7. Tests and local infrastructure. Unit tests for the service rules, slice tests for the controllers, an integration test against a real PostgreSQL via Testcontainers, and a Docker Compose file that brings up the database (and optionally the API) with one command. Demo: a fresh clone runs docker compose up and then the full test suite green.
  8. One stretch goal. Pick a single item from the stretch list, write down its acceptance criteria first, and ship it with tests. Then stop and write the README: what it does, how to run it, the decisions you made and why.

Phase notes: authentication, tests and local infrastructure

On authentication, resist writing your own filter that parses tokens by hand — Spring Security's OAuth2 resource server support validates and decodes a JWT for you, and a login endpoint that signs one is a few lines. Store the password with the framework's PasswordEncoder (BCrypt by default) and never log the raw value. Decide deliberately where the browser keeps the token: localStorage is easy but readable by any script that gets injected, while an HttpOnly cookie is safer against cross-site scripting but then needs cross-site request forgery protection turned back on. Being able to explain that trade-off is worth more in an interview than the implementation itself.

On tests, aim for a shallow pyramid rather than a large number: a handful of plain unit tests over the summary and validation rules, a couple of @WebMvcTest slices asserting status codes and that an unauthenticated call is rejected, and one integration test that starts real PostgreSQL through Testcontainers, runs your Flyway migrations against it, and exercises create-then-list end to end. The migration test alone catches the mistake that bites everyone: a migration that works on an empty database but fails on one that already has rows. Docker Compose is what makes all of this repeatable — one file, one command, and a reviewer who clones your repository can run it.

Reference implementations worth reading before you start

Read code before writing it, but read it critically: many popular tutorial repositories return entities straight from controllers, keep secrets in application.properties, or skip the ownership check entirely. Treat each one as a specimen — find the layering, find where the authenticated user enters the request path, and find what you would do differently. The PetClinic family is the most instructive because the same domain is implemented several ways by the Spring team itself, so the differences between the versions are all deliberate.

The expense-tracker repositories linked here are ordinary community projects rather than exemplars, and that is exactly their value: they are the same size as what you are about to build, so you can see the whole thing in one sitting, and their weak spots (a double amount, an unscoped finder, validation only in the form) are the ones this brief has been warning you about. Reviewing someone else's project against the pitfalls list above is genuinely good practice for the code review round of an interview.

Interview questions

These are the questions an interviewer actually asks when this project is on your CV — Indian product and service-company rounds alike open with "walk me through your project" and then probe exactly these decisions:

Beginner Walk me through your expense tracker in two minutes.

Name the shape first, then one interesting decision. "An Angular SPA talks JSON to a Spring Boot REST API backed by PostgreSQL. Users register and log in, record expenses with an amount, date, category and note, filter their list by date range and category, and see a monthly total per category. Auth is a JWT issued at login; every data query is scoped to the authenticated user at the repository level; the schema is owned by Flyway migrations and tested against real Postgres with Testcontainers." Do not narrate every screen — give the architecture and invite the follow-up.

Beginner Why did you store the amount as an integer instead of a double?

Binary floating point cannot represent decimal fractions like 0.10 exactly, so sums drift: add ten ten-paise expenses in a double and the total is not exactly one rupee. Money needs exact decimal arithmetic. Storing minor units (paise) in a BIGINT makes every value an exact integer and arithmetic exact by construction; NUMERIC(12,2) mapped to BigDecimal is the equally valid alternative. In Java the type is BigDecimal with an explicit scale and RoundingMode, never double or float.

Beginner Why is the spend date a LocalDate but created_at a timestamp with time zone?

They model different things. "I spent this on 3 April" is a calendar fact with no instant attached — stored as DATE and mapped to LocalDate, it never shifts when the server's zone changes or the user travels. "This row was written at this moment" is a point on the timeline — stored as TIMESTAMPTZ and mapped to Instant or OffsetDateTime. Storing the spend date as a timestamp is how a filter for April silently starts including a 31 March expense.

Beginner How does a request get from the Angular app to the database in your project?

The component calls a typed service using HttpClient; an interceptor attaches the Authorization header. On the server the security filter chain validates the token and populates the security context, the controller binds and validates the request DTO, the service applies rules inside a transaction and derives the owner from the principal, the Spring Data repository issues the query, and the controller maps the result to a response DTO. Entities never cross the controller boundary.

Intermediate User A changes the id in the URL and sees user B's expense. Did that work in your app, and why not?

No, because there is no unscoped finder to exploit. The repository exposes findByIdAndUserId rather than findById, so the owner is part of every query, and the owner comes from the security context rather than from any request value. When the row exists but belongs to someone else the response is 404, not 403 — a 403 confirms the record exists and leaks information. This is the insecure direct object reference class of bug in OWASP's broken access control category.

Intermediate You validate in the Angular form. Why validate again on the server?

The browser is not a trust boundary. Anyone can post JSON directly to the API with curl or Postman and skip the form entirely, so client validation is a user-experience feature, not a security control. The server enforces the contract with Jakarta Bean Validation constraints on the request DTO plus @Valid on the controller argument, business rules in the service (does this category belong to this user?), and database constraints such as CHECK (amount_minor > 0) as the last line of defence.

Intermediate Why Flyway migrations rather than Hibernate's ddl-auto?

Because ddl-auto=update is not a migration tool: it never drops or renames anything, its behaviour depends on the entity classes in the running jar, and it gives you no ordered, reviewable history. Flyway makes the schema a versioned artefact — each change is a numbered SQL file, applied in order exactly once, recorded in a history table, and reviewable in a pull request. I keep ddl-auto=validate so Hibernate confirms the mapping matches the migrated schema and fails fast if they drift.

Intermediate Where did you compute the monthly summary, and why there?

In SQL, with GROUP BY category_id and a SUM over a date range, returned into a projection. Loading a month of rows into Java to add them up moves the whole result set over the network, allocates objects you throw away, and gets linearly worse as the user's history grows; the database can answer it from the (user_id, spent_on) index. The general principle is to aggregate as close to the data as possible.

Intermediate Why do your controllers return DTOs instead of entities?

Three reasons. Coupling: an entity is the database shape, so exposing it turns every column rename into a breaking API change. Security: entities carry fields you never meant to publish, such as the password hash or another user's id, and they also make mass-assignment possible on the way in. Serialisation: a lazily-loaded association serialised outside the persistence context throws, or worse, triggers extra queries. A DTO makes the contract explicit and reviewable.

Intermediate How does your JWT authentication actually work, end to end?

Login verifies the submitted password against the BCrypt hash with the framework's PasswordEncoder, then signs a token containing the subject and an expiry. The client sends it as Authorization: Bearer on every request. A filter validates the signature and expiry, builds an Authentication and puts it in the security context; the filter chain then enforces that everything except the auth endpoints requires authentication. The token is stateless, so the server keeps no session — which also means logout is client-side unless I add a deny list, and that is the main trade-off against plain sessions.

Pro Where do you store the token in the browser, and what does that choice cost you?

localStorage is simple and immune to cross-site request forgery because the browser never attaches it automatically — but any injected script can read it, so one cross-site scripting hole is a full account takeover. An HttpOnly cookie cannot be read by script, but it is sent automatically, so cross-site request forgery protection has to be enabled and the cookie marked SameSite and Secure. Neither is universally right; the honest answer is that the cookie approach is safer for a browser-only client provided you keep the CSRF defences, and that a strong content security policy matters either way.

Pro Ten thousand users, each with years of expenses. What breaks first and what would you change?

The list and summary queries break first, on rows scanned rather than on user count. I would confirm the composite index on (user_id, spent_on) is actually used with EXPLAIN, keep the list paginated, and switch from offset paging to keyset (seek) paging because deep offsets degrade badly. The monthly summary becomes a candidate for a rolled-up table or a materialised view refreshed nightly. Beyond that: connection pool sizing, a cache for the small and rarely changing category list, and only then horizontal scaling of the stateless API — which the JWT design already permits.

Pro A user deletes a category that has expenses against it. What happens, and why did you choose that?

Nothing is deleted — the category is archived with a flag, so it disappears from the picker but old expenses keep a readable label and historical summaries stay correct. A cascading delete would destroy financial history, and a plain restrict would just show the user an error they cannot act on. Soft-delete here is a data-integrity decision, not laziness: the alternative is a nullable category with an "Uncategorised" fallback, which is also defensible but loses information.

Pro What did you leave out of this project deliberately, and what would you do differently now?

A strong answer names real cuts and owns them: no multi-currency (one currency code stored so the column exists when it is needed), no refresh tokens, no rate limiting on login, no soft-delete on expenses, no audit trail. What I would change: introduce keyset pagination from the start, put the money handling behind a small value type instead of passing BigDecimal around, and add an integration test that asserts a second user genuinely cannot reach the first user's rows — the ownership rule deserves a test, not just a convention.
