Module: NgRx Foundations

NgRx is Redux wearing Angular's dependency injection and RxJS: one immutable state tree, events in, new state out, and a DevTools trace of every change in between. Get the loop and the vocabulary right here and selectors, effects and the entity adapter become detail rather than mystery.

What this module covers

Two layers. The model first: Redux's three principles as NgRx implements them — a single source of truth, state that is read-only, and changes made only by pure reducer functions — plus the unidirectional action → reducer → store → selector loop that follows from them. Then the API you actually type in an Angular v20 app: standalone provideStore() and provideState() bootstrapping, createActionGroup for declaring events, createReducer with on for folding them into state, and the state-shape rules that keep a store maintainable a year later. Depth on each lives in the linked official docs.

Topics

The Redux model in Angular terms, and standalone provideStore setup

Redux states three principles and NgRx inherits all three. Single source of truth: the whole application's state is one plain object tree held in one store. State is read-only: nothing writes to it directly — you dispatch an action, a serializable object describing something that happened. Changes are made with pure functions: reducers receive the previous state and the action and return a brand-new state object, never mutating the old one. On top of that Angular contributes dependency injection (Store is an injectable service) and RxJS contributes the plumbing (Store is simultaneously an Observable of state and an Observer of actions).

The flow is strictly one-directional and worth memorising as a sentence: a component or service dispatches an action, every reducer in the app sees it, the ones that care return new slices, the store swaps in the new state object, selectors recompute from it, and templates re-render. Because each reference changes only when its data changes, OnPush change detection works perfectly with it. Why it matters: the payoff is traceability — every state change has a named cause you can replay in Redux DevTools, time-travel through, and assert on in a unit test with no mocks. The cost is ceremony and file count, which is why NgRx's own docs push back with the SHARI checklist (state that is Shared, Hydrated, Available across routes, Retrieved via side effects, or Impacted by other sources) before you reach for a global store at all.

Setup in a modern standalone app is two functions. provideStore() goes in the root providers array and registers the store infrastructure once; convention is to leave it empty and register every slice with provideState(), either at the root or — better for lazy features — inside a route's own providers, so the slice arrives with the chunk that needs it. The StoreModule.forRoot() / StoreModule.forFeature() pair still works and is what you will meet in older codebases, but it is legacy: nothing new should be written with it.

// app.config.ts — standalone bootstrap
export const appConfig: ApplicationConfig = {
  providers: [
    provideStore(),               // root store; kept empty by convention
    provideState(booksFeature),   // an eagerly-loaded slice
    provideStoreDevtools(),       // time-travel debugging in development
  ],
};

// books.routes.ts — a lazy feature brings its own slice
export const routes: Routes = [
  {
    path: 'books',
    providers: [provideState(booksFeature)],   // replaces StoreModule.forFeature
    loadComponent: () => import('./books-page').then((m) => m.BooksPage),
  },
];

Actions, reducers and state shape: createActionGroup, createReducer/on, feature state

An action is a unique event: a type string plus optional payload. Instead of hand-writing one createAction call per event, createActionGroup declares a whole group from a source and an events dictionary — NgRx generates a camelCase creator per event ('Book Added' becomes booksPageActions.bookAdded) and stamps the type as [Source] Event. Use emptyProps() for payload-free events and props<{ … }>() for typed payloads. This is the current idiom; a bare createAction is still fine for one-off events.

The rule that separates a store you can debug from one you cannot is good action hygiene: actions describe events, not commands. Name them after what happened and where it happened — '[Books Page] Opened', '[Books API] Books loaded success', '[Books API] Books loaded failure' — never loadBooks or setBooks. One event dispatched from exactly one place; any number of reducers and effects may listen. The anti-pattern is a generic reusable action (a single setLoading fired from five components), which erases the DevTools trace, couples unrelated features and makes "why did this state change?" unanswerable. NgRx ships an ESLint rule, good-action-hygiene, that enforces the [Source] Event template for you.

Reducers are built with createReducer(initialState, …on(…)). Each on(actionCreator, handler) clause is narrowed to that action's payload type, and the handler returns a new state object — spread the old one, never mutate it. createFeature({ name, reducer }) bundles a slice's name and reducer together and generates its feature selector and one selector per top-level key, which is why feature state is now usually declared as a feature object and handed straight to provideState. On shape: keep the tree flat (one shallow slice per feature, no deep nesting), normalized (entities in a dictionary keyed by id with a separate ids array rather than nested arrays — exactly what @ngrx/entity automates), and serializable (no class instances, Dates, Maps, Sets, Observables or DOM nodes; NgRx's strictStateSerializability runtime check will fail the build in development if you try). Derived values — totals, filtered lists, view models — belong in selectors, never as extra fields in state that a reducer must remember to keep in sync.

// books.actions.ts
export const BooksPageActions = createActionGroup({
  source: 'Books Page',                       // types become '[Books Page] …'
  events: {
    'Opened': emptyProps(),
    'Book Added': props<{ bookId: string }>(),
  },
});

// books.reducer.ts — flat, normalized, serializable
export const booksFeature = createFeature({
  name: 'books',
  reducer: createReducer(
    { ids: [] as string[], entities: {} as Record<string, Book>, loading: false },
    on(BooksPageActions.opened, (state) => ({ ...state, loading: true })),
    on(BooksApiActions.booksLoadedSuccess, (state, { books }) => ({
      ...state,
      loading: false,
      ids: books.map((b) => b.id),
      entities: Object.fromEntries(books.map((b) => [b.id, b])),
    })),
  ),
});

Interview questions

NgRx is the dividing line between "knows Angular" and "has shipped a large Angular app" in Indian interviews — service companies screen on the vocabulary, product companies push on state shape and design trade-offs. These are the questions this module powers:

Beginner What is NgRx and what problem does it solve?

NgRx is a Redux-inspired, RxJS-powered global state container for Angular. It solves the problems that appear once state is shared across many components and routes: no single place to look for the current value, no record of what changed it, prop-drilling and duplicated copies drifting apart. NgRx replaces that with one immutable state tree, explicit named events, pure state transitions, and a DevTools timeline of every change.

Beginner What are the three principles of Redux?

(1) Single source of truth — the whole app's state lives in one object tree in one store. (2) State is read-only — the only way to change it is to dispatch an action describing what happened. (3) Changes are made with pure functions — reducers take the previous state plus an action and return a new state, with no mutation and no side effects.

Beginner Name the building blocks of NgRx and what each one does.

Store — the injectable state container, an Observable of state and an Observer of actions. Action — a unique event with a type and optional payload. Reducer — a pure function computing the next state from the current state plus an action. Selector — a pure, memoized function reading and deriving slices of state. Effect — listens to the action stream and handles side effects (HTTP, router, storage), usually dispatching a result action back.

Beginner How do you set up NgRx in a standalone Angular app? What replaced StoreModule.forRoot?

Add provideStore() to the providers array in app.config.ts (used by bootstrapApplication) and register each slice with provideState(feature) — at the root for eager state, or in a route's providers for a lazy feature. provideStore() replaces StoreModule.forRoot() and provideState() replaces StoreModule.forFeature(); the module APIs still work but are the legacy path.

Beginner Describe the unidirectional data flow of an NgRx app.

Component dispatches an action → the action reaches every reducer → matching on handlers return new slices → the store holds a new state object → selectors recompute → the template re-renders (and effects listening to that action fire their side effects, dispatching further actions). Data flows one way only; nothing writes back into state directly, which is what makes the flow replayable.

Intermediate What is createActionGroup and why is it preferred over many createAction calls?

It declares a whole group of related action creators from one source and an events dictionary. The source is written once instead of repeated in every type string, event names are converted to camelCase creators automatically ('Book Added' → bookAdded), and the [Source] Event type format is guaranteed. Payloads use emptyProps() or props<T>(). Less boilerplate, no typos in type strings, same runtime behaviour as createAction.

Intermediate What is "good action hygiene" and why should actions be events, not commands?

An action should be a unique event that says where it was dispatched and what occurred: '[Books Page] Opened', not 'Load Books'. Commands invert the relationship — the dispatcher starts deciding what the store should do, so one action gets reused from many places and the DevTools log stops telling you why anything happened. Events keep dispatchers dumb and listeners many: one event can drive several reducers and effects. NgRx's ESLint rule good-action-hygiene enforces the [Source] Event template.

Intermediate How does createReducer/on work, and why must a reducer be pure?

createReducer(initialState, on(actionA, handler), on(actionB, handler)) builds a function that switches on action type with full payload typing per clause. Purity — same inputs, same output, no mutation, no HTTP, no Date.now(), no randomness — is what makes state transitions replayable, time-travel debugging correct, and reducer tests trivially assertable with no mocks. Anything impure belongs in an effect.

Intermediate Root state versus feature state — how and where do you register a feature slice?

Root state is registered at bootstrap and exists for the life of the app; feature state is a named slice added later, usually alongside a lazy-loaded route. In standalone apps, keep provideStore() empty and register slices with provideState(feature) — in app.config.ts for eager slices, or in the route's own providers array so the slice loads with the chunk. A createFeature object carries the name, the reducer and its generated selectors together.

Intermediate How should you design the shape of the state tree?

Flat, normalized, serializable. Flat: one shallow slice per feature keyed by feature name, not deeply nested objects that force long spread chains in reducers. Normalized: entities in a dictionary keyed by id plus an ids array for order, so a single update touches one key instead of rebuilding a list (this is what @ngrx/entity generates for you). Serializable: plain objects and primitives only — no class instances, Dates, Maps, Sets, Observables or DOM nodes. Store the minimum; derive everything else in selectors.

Pro A developer mutates state inside a reducer. What breaks, and how do you catch it?

The object reference does not change, so OnPush components and memoized selectors see "no change" and the UI silently goes stale; DevTools time-travel becomes wrong because past states were altered in place; and reducer tests pass while the app misbehaves. Catch it with NgRx runtime checks, on by default in development — strictStateImmutability and strictActionImmutability freeze state and actions and throw on mutation — backed by the @ngrx/eslint-plugin and code review. The fix is always to return a new object via spread or an immutable helper.

Pro Should derived data such as a filtered list or a cart total live in the reducer or in a selector?

In a selector. Storing derived values duplicates the source of truth, and every reducer that touches an input then has to remember to recompute the derivative — the classic drift bug. Selectors are pure and memoized, so the computation reruns only when its inputs change and costs nothing on other dispatches. Keep state minimal and canonical; compose createSelector on top of it.

Pro Does every Angular app need NgRx? How do you argue the decision in a design round?

No — and saying so with reasons scores better than reciting the API. Use the SHARI checklist from the NgRx docs: reach for a store when state is Shared across many components, Hydrated from external storage, must be Available when re-entering routes, is Retrieved through side effects, or is Impacted by actions from elsewhere. For a form-heavy CRUD app with mostly local state, a signal-based service or NgRx SignalStore gives the same discipline for a fraction of the ceremony, and server cache state is often better handled by a data-fetching layer. Name the trade-off explicitly: traceability and testability bought with indirection and file count.
