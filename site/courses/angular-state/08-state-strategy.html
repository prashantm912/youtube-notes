Module: State Strategy and Migration

Seven modules taught you the mechanisms. This one is about judgement: deciding which slice of your application deserves which mechanism, recognising that "we need a state library" is usually a misdiagnosis of a caching problem, and moving an existing codebase between approaches without a rewrite.

Knowledge Library → Courses → Angular State Management → State Strategy and Migration

What this module covers

This is the synthesis chapter for the track. It starts by breaking "state management" into five separate problems — local component state, shared client state, server-cache state, URL state and form state — because only one or two of them ever want a store. It then spends real time on the server cache, which is where most of the pain actually lives, using Angular v20's resource() and httpResource() plus the TanStack Query Angular adapter. From there: a decision framework for when NgRx Store earns its ceremony, concrete migration paths (signal service → SignalStore → full NgRx Store, and StoreModule.forRoot → standalone providers), and a worked admin-dashboard case study that assigns a mechanism to each slice and explains why.

Topics

The taxonomy: five kinds of state wearing one name

"State management" is a single phrase covering at least five unrelated problems. Local component state — an accordion's open flag, a spinner, a hovered row — belongs in a signal() on the component and nowhere else; hoisting it into a store is pure cost. Shared client state — the signed-in user, a theme, a shopping cart, a feature-flag map — is genuinely application-wide and genuinely client-owned, and this is the only category a client store is actually designed for. Server-cache state — the product list, the order you are viewing — is not your state at all: it is a local copy of somebody else's data that goes stale the moment you fetch it. URL state — the current page, active filters, the selected tab — belongs in route and query parameters so it survives a refresh and can be pasted into Slack. Form state — draft values, dirty and touched flags, validation errors — belongs to the forms system, which already manages it far better than a reducer will.

Why it matters: almost every over-engineered Angular codebase is the result of applying one mechanism to all five categories. Push server data through a reducer and you have hand-written a cache with no invalidation policy; push filters through a store instead of the URL and you have broken the back button and shareable links; push a form draft through a store and you have reimplemented FormGroup badly. Interviewers at product companies test exactly this: they will not ask you to recite createReducer, they will describe a screen and ask where each piece of data should live. Getting the taxonomy right is what makes the rest of the decisions easy.

// Same screen, five different homes — this is the whole module in one comment.
drawerOpen   = signal(false);                    // local: component signal
user         = inject(AuthStore).user;           // shared client: one app-wide store
orders       = httpResource(() => `/api/orders?page=${this.page()}`); // server cache
page         = input.required<number>();         // URL: bound from query params
editForm     = new FormGroup({ /* ... */ });     // form: the forms system owns it

Server-cache state: the problem most "state management" actually is

Open any store in a typical enterprise Angular app and count the slices. Most of them hold rows fetched from an API, wrapped in loading, error and lastFetched fields, refreshed by an effect. That is not state management — that is a cache, written by hand, usually without a staleness policy, deduplication, or a story for what happens when two components ask for the same resource at once. The moment you recognise this, the questions change: not "which store?" but "how long is this data fresh, what invalidates it, and what do we show while we refetch?"

Angular v20 answers part of this natively. resource() models an async dependency as a signal-based unit with value, status, error and reload(), re-running whenever its reactive params change; httpResource() is the HttpClient-flavoured version that takes a URL (or request object) built from signals and gives you the response as a signal, with typed value and a request lifecycle you never subscribe to. What Angular deliberately does not give you is a shared cache: two components calling httpResource for the same URL issue two requests, and there is no cross-component invalidation or mutation lifecycle. That is where the ecosystem answer comes in — the TanStack Query Angular adapter provides the query cache, keyed by a queryKey, with staleTime and gcTime, request deduplication, background refetch and explicit invalidation after mutations. Its default behaviour is stale-while-revalidate: serve the cached value instantly, refetch in the background, swap in the fresh result. Learn that model even if you never adopt the library, because it is the vocabulary interviewers use — "stale", "invalidate", "refetch on window focus" — and once you own it, the number of slices your NgRx store actually needs collapses.

// Angular-native: reactive URL in, signal out. No subscription, no loading flag by hand.
export class OrdersComponent {
  page   = signal(1);
  orders = httpResource<Order[]>(() => `/api/orders?page=${this.page()}`);
  // orders.value() | orders.isLoading() | orders.error() | orders.reload()
}

// What it does NOT do: share one cache between components, dedupe concurrent
// requests, or invalidate after a mutation. That is the query-library's job.

When NgRx Store earns its ceremony — a decision framework

NgRx Store is not overkill because it is complicated; it is overkill when the properties it buys you are properties you do not need. What it buys: a single serialisable source of truth, a strictly auditable change log (every mutation is a named action, replayable in DevTools), memoised derived views via selectors, and a hard separation of side effects. Those properties earn their price on a large, long-lived application with many teams, complex cross-feature interactions, and a real need to reason about "how did the state get into this shape?" — think a trading terminal, a claims-processing workbench, an editor with undo. NgRx's own guidance frames this well: if your state is shared across many components, hydrated from elsewhere, retrieved repeatedly, or genuinely complex, a store helps; if it is none of those, it does not.

The practical framework, in order: (1) Can this live in a component signal? Do that. (2) Is it shared client state used by a handful of components? A signal service with a readonly public surface is enough. (3) Is it server data? Reach for httpResource/resource or a query library before any store. (4) Is it a self-contained feature's local-but-complex state — a wizard, a filterable table, a drawer? @ngrx/signals SignalStore scoped to that feature, provided at route or component level, is the modern sweet spot; it is the successor to ComponentStore and the NgRx team now points local-state work there. (5) Only when several features must coordinate, the change history matters, and the team is large enough to benefit from the convention, does global NgRx Store pay for itself. Two more honest signals: if your reducers mostly set loading: true, you are managing a cache, not state; and if a store slice has exactly one consumer, it is a signal in disguise.

Migration paths: signal service → SignalStore → NgRx Store

The good news is that these three are points on one line, not competing religions, so migration is incremental rather than a rewrite. A signal service already has the shape of a store: private writable signals, public computed readonly accessors, methods that mutate. Promoting it to a SignalStore is largely mechanical — the private signals become withState, the computed accessors become withComputed, the methods become withMethods, and async work moves into rxMethod or a plain async method. Consumers barely change, because both expose signals. Going the other way is equally cheap, which is why starting with a service costs you almost nothing.

Promoting a SignalStore to global NgRx Store is a bigger step and should be driven by a real requirement (cross-feature coordination, action-level auditability), not by aesthetics. Do it slice by slice: the two can coexist in the same application, so move one feature, keep the facade its components already call, and let the facade's implementation switch from store methods to store.dispatch and selectors. Keeping a facade in front of state is what makes this migration a one-file change per feature instead of a hundred-component change.

The other migration every legacy Angular codebase faces is module-to-standalone. NgRx ships a provide* equivalent for every module registration: StoreModule.forRoot() → provideStore(), EffectsModule.forRoot() → provideEffects(), StoreDevtoolsModule.instrument() → provideStoreDevtools(), StoreRouterConnectingModule.forRoot() → provideRouterStore(). Feature registrations move out of lazy NgModules and into the route's own providers array, which is strictly better — the slice's lifetime now matches the route's. Run the Angular standalone migration schematics first to get components and bootstrapping converted, then swap the NgRx module imports; adopt the standalone APIs wholesale per application rather than mixing both styles.

// Step 1 — signal service (start here, always)
@Injectable({ providedIn: 'root' })
export class CartService {
  private _items = signal<Item[]>([]);
  readonly items = this._items.asReadonly();
  readonly total = computed(() => this.items().reduce((s, i) => s + i.price, 0));
  add(item: Item) { this._items.update(list => [...list, item]); }
}

// Step 2 — same contract, SignalStore shape
export const CartStore = signalStore(
  { providedIn: 'root' },
  withState({ items: [] as Item[] }),
  withComputed(({ items }) => ({ total: computed(() => items().reduce((s, i) => s + i.price, 0)) })),
  withMethods((store) => ({ add: (i: Item) => patchState(store, { items: [...store.items(), i] }) })),
);

// Step 3 — module-based NgRx becomes standalone providers
bootstrapApplication(AppComponent, {
  providers: [
    provideStore({ cart: cartReducer }),   // was StoreModule.forRoot(...)
    provideEffects(CartEffects),           // was EffectsModule.forRoot([...])
    provideStoreDevtools({ maxAge: 25 }),  // was StoreDevtoolsModule.instrument(...)
  ],
});

Case study: an admin dashboard, slice by slice

Take a concrete screen — the one you will be asked to design in a system-design round. An admin dashboard shows a paginated, sortable table of users; a filter bar (search text, status, date range); a row-click that opens an edit drawer with a form; and a save that must refresh the table. A junior answer puts all of it in one NgRx feature slice with a dozen actions. Here is the slice-by-slice assignment instead.

Filters, sort and page number → the URL. They are the definition of shareable, refresh-surviving view state; put them in query params, bind them into the component with withComponentInputBinding(), and you get the back button, deep links and bookmarking for free. The table rows → server-cache state. An httpResource (or a query keyed on the filter tuple) whose URL is computed from those URL-derived signals: change a filter, the key changes, the data refetches, and stale-while-revalidate keeps the old rows on screen so the table does not flash empty. No reducer, no loading boolean, no effect. Drawer open/closed and the selected row id → local component state, a plain signal() — or the id in the URL too, if you want a deep-linkable drawer, which is usually the better call. The edit form's draft → the forms system, seeded from the selected row with a linkedSignal so switching rows resets the draft cleanly while still allowing local edits. The save → a mutation, and the only interesting design decision on the page: after a successful PUT, invalidate the users query key rather than hand-patching the row into a store, so every consumer of that data converges on the server's truth. Signed-in user and permissions → one small shared client store, because it is read everywhere and owned by the client.

Count what is left for NgRx Store on this screen: nothing. That is not an argument against NgRx — it is the argument for the taxonomy. Add a second screen that must react when this one saves, an offline queue, or an undo stack, and the calculus changes; the framework tells you when it changed instead of leaving it to taste. If the table grows into a shared, normalised collection consumed by several features, that is the moment for withEntities or the @ngrx/entity adapter and a normalised shape, not before.

Interview questions

This is the module that shows up in architecture and design rounds — Indian service companies ask it to check you will not over-engineer a delivery, product companies ask it to check you can defend a decision. Expect scenarios rather than API recall:

Beginner What are the different kinds of state in an Angular application?

Five useful categories: local component state (a toggle, a spinner), shared client state (signed-in user, theme, cart), server-cache state (a local copy of API data), URL state (page, filters, selected tab) and form state (draft values, dirty/touched, validation). They have different owners and different lifetimes, so they want different mechanisms — treating them as one problem is the root cause of most over-engineering.

Beginner Does every Angular application need NgRx?

No. Most applications are fine with component signals plus a couple of signal services, and their API data belongs in a resource or query cache rather than a store. NgRx Store earns its cost on large, long-lived apps with many teams, cross-feature coordination and a real need for an auditable change history. Saying "it depends, here is my checklist" is the answer interviewers want — not a yes or a no.

Beginner Where should a table's current filters and page number live?

In the URL as query parameters. That makes the view shareable and bookmarkable, survives a refresh, and restores the back button's meaning. Bind them into the component with withComponentInputBinding() and derive the data request from them. Putting them in a store instead is the classic mistake — you gain nothing and lose deep links.

Beginner What is server-cache state and why is it not really "your" state?

It is a local copy of data the server owns — a product list, an order. You never have the authoritative version, only a snapshot that starts going stale the instant it arrives. So the meaningful questions are about freshness and invalidation (how long is it good for, what makes it wrong, what do we show while we refetch), not about reducers. Once you frame it that way, a cache is the right tool, not a store.

Intermediate What do resource() and httpResource() give you, and what do they deliberately not give you?

They turn an async dependency into signals: value, status/isLoading, error, plus reload(), re-running automatically when the reactive params or computed URL change — so no subscription and no hand-rolled loading flags. httpResource is the HttpClient-backed variant taking a URL or request object. What they do not provide: a shared cache across components, request deduplication, cross-component invalidation, mutation lifecycles, retries or polling. Each resource fetches independently, which is exactly the gap a query library fills.

Intermediate Explain stale-while-revalidate and how you would apply it to a dashboard table.

Serve the cached value immediately, kick off a background refetch, then swap in the fresh result. The user sees data instantly instead of a spinner, and correctness catches up a moment later. On a dashboard table it means changing a filter keeps the previous rows visible while the new page loads, so the layout never collapses to an empty state. In TanStack Query this is the default, tuned with staleTime (how long a value is considered fresh) and gcTime (how long an unused cache entry is kept).

Intermediate After a successful save, would you patch the row into your store or refetch? Defend it.

Default to invalidating the query key and refetching: the server may have applied defaults, computed fields, audit stamps or concurrent changes, so hand-patching risks a UI that quietly disagrees with the database. Patch optimistically only when latency matters more than exactness, and even then follow it with an invalidation and a rollback path on failure. The bug you are avoiding is two sources of truth drifting apart.

Intermediate How do you migrate a signal service into a SignalStore?

Almost mechanically, because the shapes match. Private writable signals become withState, public computed accessors become withComputed, mutating methods become withMethods using patchState, and async work becomes rxMethod or a plain async method. Consumers barely change since both expose signals. Provide it at root, route or component level depending on the intended lifetime. The reverse migration is equally cheap, which is why starting with a plain service is a safe default.

Intermediate How do you move a StoreModule.forRoot application to standalone providers?

Every NgRx module has a provider equivalent: StoreModule.forRoot → provideStore, EffectsModule.forRoot → provideEffects, StoreDevtoolsModule.instrument → provideStoreDevtools, StoreRouterConnectingModule.forRoot → provideRouterStore. Run Angular's standalone migration schematics to convert components and bootstrapping first, then move root registrations into bootstrapApplication's providers and feature registrations into the lazy route's own providers array — which also ties the slice's lifetime to the route. Commit to the standalone APIs application-wide rather than mixing both styles.

Pro Design the state for an admin dashboard: paginated table, filter bar, edit drawer. Where does each piece live?

Filters, sort and page → query params in the URL (shareable, refresh-safe, back button works). Table rows → server cache keyed on that filter tuple via httpResource or a query, with stale-while-revalidate so the table does not flash empty. Drawer open state and selected row id → a component signal, or the URL if the drawer should be deep-linkable. Edit draft → a reactive form seeded from the selected row, reset cleanly via linkedSignal. Save → a mutation that invalidates the rows query. Signed-in user and permissions → one small shared client store. Net result: no global NgRx slice is required for this screen, and that is the point of doing the triage.

Pro Your team's NgRx store is 80% loading flags and API rows. What is the diagnosis and the remediation plan?

Diagnosis: they built a cache by hand without a caching policy — no staleness rules, no deduplication, no invalidation strategy, and effects doing work a library already does. Remediation, incrementally: pick one feature, replace its load actions/reducer/effect with a resource or a query keyed on its inputs, keep the existing facade so components do not change, delete the slice, measure. Repeat feature by feature. What legitimately stays in the store is client-owned state and anything needing an auditable change history. Do not attempt a big-bang rewrite — coexistence is supported and per-feature migration is reviewable.

Pro When would you argue AGAINST removing NgRx from a codebase that has it?

When the properties it provides are load-bearing: a replayable action log used for debugging production incidents, undo/redo, offline queueing, or many teams relying on the convention to stay coordinated. Also when the migration cost is real and the benefit is aesthetic — churn on a working system is a cost, not a win. The senior answer names the properties being bought, checks whether anything else in the system depends on them, and proposes stopping new slices from being added rather than ripping out working ones.

Pro A slice of your store has exactly one consumer. What does that tell you, and what is the general rule?

It tells you the state was hoisted for no reason — global scope with a single reader is a component signal wearing ceremony, and it costs you locality, lifetime management (the slice outlives the component) and reviewability. The general rule: state should live at the narrowest scope that all its consumers share, and be promoted only when a second consumer genuinely appears. Promotion is cheap along the service → SignalStore → Store line; demotion after a year of coupling is not.
