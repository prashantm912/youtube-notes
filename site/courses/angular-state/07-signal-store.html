Module: NgRx SignalStore

Actions, reducers and effects were the price of admission to NgRx for a decade. @ngrx/signals drops all three and rebuilds state management out of signals and composable features — and it is now the direction the library itself is heading, which is exactly why interview panels have started asking about it.

Knowledge Library → Courses → Angular State Management → NgRx SignalStore

What this module covers

Two halves. First, the store itself: signalStore(), the feature functions that build it up (withState, withComputed, withMethods, withHooks), the deep signals it hands you for nested slices, and patchState as the single write path. Second, the ecosystem and the trade-off: rxMethod for reactive side effects, withEntities from @ngrx/signals/entities, writing your own reusable features with signalStoreFeature, and a straight comparison against classic NgRx Store and the older @ngrx/component-store that SignalStore effectively supersedes. Everything here assumes a current @ngrx/signals release on Angular v20 or newer; depth lives in the linked docs.

Topics

signalStore: feature composition, deep signals and patchState

signalStore() does not take a configuration object full of reducers — it takes a list of features and returns an injectable class. withState(initial) turns every top-level property of your initial state into a signal on the store instance. withComputed(store => ({...})) adds derived signals. withMethods(store => ({...})) adds behaviour, and because its factory runs inside an injection context you can inject() services right there. withHooks({ onInit, onDestroy }) ties work to the store's lifetime, and withProps attaches plain non-signal members such as an injected service or a subject. Each feature sees everything the previous features added, and the types flow through — that composition is the whole design.

Two details decide how the store behaves in practice. Scope: passing { providedIn: 'root' } makes the store an application-wide singleton you simply inject; omitting it means you list the store in a component's providers array, which gives it the component's lifetime and a fresh instance per component — the local-state option that used to require ComponentStore. Writes: state is protected by default, so patchState(store, partial) can only be called from inside the store (typically from a method). patchState accepts either a partial object or an updater function (state) => partial for updates that depend on the current value, and it merges shallowly, so nested slices must be spread yourself. Reading nested state is the pleasant part: deep signals mean a nested object in your state is exposed as a signal whose properties are themselves signals, so store.filter.query() works without you ever declaring it.

export const BooksStore = signalStore(
  { providedIn: 'root' },                       // omit this to provide it per component
  withState({
    books: [] as Book[],
    filter: { query: '', order: 'asc' },        // nested -> deep signals
    isLoading: false,
  }),
  withComputed(({ books, filter }) => ({
    booksCount: computed(() => books().length),
    sorted: computed(() => sortBooks(books(), filter.order())),  // filter.order() is a signal
  })),
  withMethods((store) => ({
    setQuery(query: string) {
      patchState(store, (s) => ({ filter: { ...s.filter, query } }));  // updater fn
    },
  })),
  withHooks({ onInit: (store) => store.setQuery('') }),
);

rxMethod, custom features, and how SignalStore compares to Store and ComponentStore

Signals are synchronous, so asynchronous work still needs somewhere to live. rxMethod (from @ngrx/signals/rxjs-interop) is that place: you give it an RxJS pipeline and get back a function you can call with a plain value, a signal, or an observable. It manages the subscription for you and tears it down with the store's injector, which is what makes debounced search, switchMap cancellation and retry logic expressible without a single Effect class. withEntities from @ngrx/signals/entities is the SignalStore counterpart to @ngrx/entity: it adds entityMap, ids and an entities signal plus updaters such as setAllEntities, addEntity, updateEntity and removeEntity, with named collections when one store holds several lists. Repeated shapes — loading flags, pagination, a data-service wiring — become reusable signalStoreFeature functions, which is how teams keep twenty stores from containing the same twenty lines.

The honest comparison matters more than the API surface, because that is what interviewers push on. Classic NgRx Store is the global, Redux-style, event-sourced option: actions give you a replayable audit trail, DevTools time travel, and a strict separation that scales across many teams — at the cost of files and ceremony. @ngrx/component-store was the older answer to "I want a store, but only for this component": RxJS-based, with select, updater and effect, tied to a component's lifetime. SignalStore covers that same local territory with far less RxJS, and covers the global case too via providedIn: 'root' — so new code should reach for SignalStore rather than ComponentStore, while existing ComponentStore code is stable and does not need a panic migration. The one thing classic Store still gives you that a plain SignalStore does not is the action stream itself; the newer @ngrx/signals/events plugin brings an event-driven, reducer-like flow into SignalStore for teams that want it back.

// reactive side effect + entity updater, inside withMethods
loadByQuery: rxMethod<string>(
  pipe(
    debounceTime(300),
    distinctUntilChanged(),
    tap(() => patchState(store, { isLoading: true })),
    switchMap((q) => books.search(q).pipe(
      tapResponse({
        next: (list) => patchState(store, setAllEntities(list), { isLoading: false }),
        error: () => patchState(store, { isLoading: false }),
      }),
    )),
  ),
),

// a reusable custom feature, dropped into any store
export function withCallState() {
  return signalStoreFeature(
    withState<{ callState: 'init' | 'loading' | 'loaded' }>({ callState: 'init' }),
    withComputed(({ callState }) => ({
      isLoading: computed(() => callState() === 'loading'),
    })),
  );
}

Interview questions

SignalStore is the newest thing on Angular state-management question banks — Indian product companies ask it to separate people who track the ecosystem from people who learned NgRx once in 2019, and service-company panels increasingly ask it as the "what is new in Angular" question:

Beginner What is NgRx SignalStore and how does it differ from classic NgRx Store?

SignalStore is the store from the @ngrx/signals package. Instead of actions, reducers, selectors and effects, you declare a store as a composition of features — withState, withComputed, withMethods, withHooks — and state is exposed as Angular signals rather than observables. Same goals (a single source of truth, immutable updates, derived state), far less boilerplate, and no action stream unless you opt into the events plugin.

Beginner How do you create a SignalStore and make it available across the whole application?

Call signalStore({ providedIn: 'root' }, withState({...}), ...) and assign it to an exported constant. That returns an injectable class registered in the root injector, so any component or service just does private store = inject(BooksStore) — nothing to add to a providers array.

Beginner What does withState do, and how do you read a value in a template?

withState(initialState) seeds the store and turns each top-level property into a signal on the store instance. In a template you call it like any signal: {{ store.isLoading() }} — no async pipe, and it works cleanly with OnPush and zoneless change detection.

Beginner What is patchState and why not assign to the state directly?

patchState(store, partial) is the only write path. It applies an immutable shallow merge and notifies every dependent signal in one go. Direct mutation would bypass the signal graph, so nothing would recompute — and state is protected by default, so patchState is rejected from outside the store unless you pass { protectedState: false }.

Beginner withComputed vs withMethods — what goes in each?

withComputed is for derived read-only values: memoized computed() signals built from existing state, such as a filtered list or a total. withMethods is for behaviour: functions that change state via patchState or perform side effects. Rule of thumb — if it can be recalculated from state, it is a computed; if it causes something, it is a method.

Intermediate What are deep signals?

When a state slice is a nested object, SignalStore does not stop at one signal — it exposes each nested property as a signal too, created lazily and memoized. So with state { filter: { query, order } } you can read store.filter.query() directly and a component that only depends on query will not recompute when order changes. It is what makes fine-grained reactivity work without you writing a selector per field.

Intermediate providedIn root versus providing the store in a component — how do you choose?

{ providedIn: 'root' } gives one shared instance for the app's lifetime — right for authenticated user, cart, feature flags, anything several routes read. Listing the store in a component's providers array gives a fresh instance per component that is destroyed with it — right for a form's working copy, a wizard, a modal, or a list widget rendered many times. This second mode is the local-state use case that used to require ComponentStore.

Intermediate What is rxMethod and when do you need it over a plain async method?

rxMethod wraps an RxJS pipeline into a callable store method and manages the subscription against the store's injector. Use it when you need RxJS semantics that async/await cannot express: debounceTime, distinctUntilChanged, switchMap cancellation of a stale request, retries, or concurrency control. A one-shot fetch with no cancellation concern is perfectly fine as a plain async method inside withMethods. A bonus: you can call an rxMethod with a signal, and it re-runs whenever that signal changes.

Intermediate What does withEntities give you, and how does it relate to @ngrx/entity?

withEntities from @ngrx/signals/entities is the SignalStore version of the entity adapter: it stores a collection normalized as an entityMap plus an ids array, exposes a derived entities signal, and ships updaters like setAllEntities, addEntity, updateEntity and removeEntity that you pass straight into patchState. Named collections let one store hold several lists. Same normalization benefits as @ngrx/entity — O(1) lookup, no duplicate records — without reducers.

Intermediate What is withHooks for?

It attaches lifecycle behaviour to the store rather than to a component: onInit runs when the store is created (load initial data, start an rxMethod driven by a signal, restore from storage) and onDestroy when its injector is destroyed. For a component-provided store that is the component's lifetime; for a root store it is the application's. It keeps initialization inside the store instead of scattered across every consumer's ngOnInit.

Intermediate How do you write a custom feature, and why bother?

Write a function that returns signalStoreFeature(...) composing the built-in features, then drop it into any store's feature list. Classic examples are withCallState (a loading/loaded/error flag plus derived booleans), withPagination, withUndoRedo and withDataService. The payoff is that cross-cutting state stops being copy-pasted into every store, and the feature can declare the state it expects so misuse is a compile error rather than a runtime one.

Pro Does SignalStore replace ComponentStore? What would you tell a team still on it?

For new code, yes — SignalStore covers ComponentStore's local-state role with signals instead of RxJS, plus deep signals, entity support and composable features, and it also handles the global case. ComponentStore remains maintained and there is no forced migration, so the advice is: stop writing new ComponentStores, migrate opportunistically when a component is being reworked, and translate select to computed signals, updater to methods calling patchState, and effect to rxMethod — the shapes map almost one to one.

Pro patchState with an object versus an updater function — and what about nested state?

Pass an object when the new value does not depend on the old one; pass an updater (state) => partial when it does (incrementing a counter, appending to a list), because reading the signal separately and then patching can race with other updates. Either way the merge is shallow: to change one field of a nested slice you must spread it yourself, and you must never mutate the existing object — the store's runtime checks will flag it in development. Updaters compose too, which is exactly how entity helpers like addEntity are implemented.

Pro Would you replace NgRx Store with SignalStore in a large enterprise application?

Not reflexively. Classic Store earns its ceremony where you genuinely need the action stream: a replayable audit trail, DevTools time travel, many features reacting to one event, and a hard boundary between teams. SignalStore wins on ergonomics, on local and feature-scoped state, and on anything signal-first or zoneless. A realistic answer is a hybrid — keep the existing global store, build new feature and component state as SignalStores, and reach for @ngrx/signals/events if a SignalStore genuinely needs event-driven, multi-listener semantics. Migrating a working store wholesale is cost without benefit.

Pro How do you test a SignalStore, and what makes it easier than testing a reducer-plus-effect setup?

Create the store inside a TestBed.runInInjectionContext (or provide it in a testing module), call its methods, and assert on the signals by reading them — no marble diagrams, no mock action stream, and dependencies swapped with normal provider overrides. Because a SignalStore bundles state, derived state and behaviour in one unit, one test covers what previously needed a reducer test plus an effect test plus a selector test. For asynchronous flows driven by rxMethod, mock the injected service and flush with the usual fake-async tooling.
