Module: Component Communication Matrix

Before you reach for a store, answer a cheaper question: which two things actually need to talk, and how far apart are they? This opening module lays out every mechanism Angular gives you for moving data between components — and the rule for choosing the smallest one that works.

Knowledge Library → Courses → Angular State Management → Component Communication Matrix

What this module covers

State management in Angular is mostly a routing problem for data: something over here needs a value that lives over there. The whole track exists to answer that, and this module maps the options end to end — from the tightest coupling (a parent binding an input() on its own child) through signal queries and template reference variables, out to loosely coupled options like a shared injectable service or the URL itself carrying the state.

Everything here uses the current Angular (v20) signal-based APIs: input(), output(), model(), viewChild(), contentChild(), standalone components and inject(). The older decorator forms — @Input, @Output, @ViewChild — still compile and still come up in interviews, so they get named once here and then set aside. Depth on each mechanism lives in the linked official documentation; what this page adds is the comparison and the decision rule at the end.

Topics

Local wiring: inputs, outputs, signal queries and template references

The cheapest communication in Angular is the kind the template already expresses. A parent passes data down by binding to a child's input(), which returns a read-only InputSignal — the child reads it like any other signal, so computed() and effect() react to changes without an ngOnChanges hook. Data travels back up through output(), which returns an OutputEmitterRef the child calls with a payload; the parent listens with ordinary event binding. When a value is genuinely owned jointly — a form control, a toggle, an expanded/collapsed flag — model() gives you a writable signal that supports the banana-in-a-box [(value)] syntax without needing a separate valueChange output. Inputs can be marked input.required() so the compiler enforces them, and can carry a transform function to normalise incoming values.

Sometimes a parent needs the child instance rather than a value: to call focus() on an element, read a child component's public API, or measure something in the DOM. That is what the signal queries viewChild(), viewChildren(), contentChild() and contentChildren() are for. The distinction that interviewers press on: view queries look inside the component's own template, content queries look at nodes projected into it through <ng-content> by a caller. Both target either a component/directive type or a template reference variable — the #name label you attach in the template, which is also directly usable inside that same template with no TypeScript at all. Signal queries return signals rather than being filled in during a lifecycle hook, which removes the classic "undefined in ngOnInit" trap that the @ViewChild decorator had.

Why it matters: this row of the matrix costs nothing and hides nothing. Data flows along the component tree, the template documents the contract, change detection is trivially predictable, and the child stays reusable because it depends on bindings rather than on a service. Most "we need state management" complaints turn out to be a parent-child relationship that was never expressed as a binding.

@Component({
  selector: 'app-rating',
  template: `
    <button #resetBtn (click)="score.set(0)">Reset</button>
    <span>{{ label() }}: {{ score() }}</span>
  `,
})
export class RatingComponent {
  label = input.required<string>();          // parent -> child, read-only signal
  score = model(0);                          // two-way: [(score)] in the parent
  cleared = output<void>();                  // child -> parent, an event

  // view query by template reference variable, returned as a signal
  private resetBtn = viewChild<ElementRef<HTMLButtonElement>>('resetBtn');

  // content query: a directive projected in by whoever uses this component
  private badge = contentChild(BadgeDirective);
}

Going wider: shared services, router state, and choosing a mechanism

Bindings stop being the answer the moment the two participants are not on the same branch of the tree. Two sibling routes, a header and a deeply nested table, a notification toast triggered from anywhere — passing a value through six intermediate components just to relay it is the "prop drilling" smell, and it couples every component in the chain to data it does not use. The standard fix is a shared injectable: a service marked @Injectable({ providedIn: 'root' }), pulled in with inject(), holding the value in a private signal and exposing it as a read-only computed or .asReadonly() plus explicit mutation methods. Provider scope is the design lever here — providedIn: 'root' makes one instance for the app, while providing the service on a component or a route makes a fresh instance per subtree, which is how you get "shared, but only within this feature". That pattern is the subject of module 02, and it is also the honest starting point for most applications.

The other wide channel is the URL. Path parameters, query parameters and route data are application state that survives a refresh, is shareable as a link, and participates in browser history for free — which makes them the right home for identifiers, filters, sorting, pagination and tab selection. Read them from ActivatedRoute (paramMap / queryParamMap for reactive reads, snapshot for one-shot ones) or, more simply, enable withComponentInputBinding() on provideRouter and let the router bind matching keys straight into your components' input()s. Beyond those, the tree also offers a couple of narrower channels worth knowing by name: content projection with <ng-content> lets a parent hand markup rather than data to a child, and router resolve functions deliver data to a route before it activates.

So, the decision rule — take the first line that fits, and stop:

Parent renders the child?             -> input() / output() / model()
Parent needs the child instance?      -> viewChild() / contentChild()
Only used inside one template?        -> template reference variable (#ref) or @let
Should survive refresh or be linkable? -> router params / query params
Unrelated components, same feature?   -> service provided on the route or component
Unrelated components, whole app?      -> service provided in root (module 02)
Many writers, complex flows, audit trail?
                                      -> a real store (modules 03-07)

Why it matters: senior interviews rarely ask "how does @Input work" — they ask you to justify a choice. Reaching for a global store when a binding would do adds indirection, boilerplate and a second source of truth; refusing a store when eight unrelated features write the same data produces a tangle of services nobody can trace. Being able to walk this matrix out loud, from cheapest to most powerful, is the answer that reads as experience.

Interview questions

Component communication is the warm-up round in almost every Indian Angular interview — service companies screen on the mechanics, product companies push on the trade-offs. These are the questions this module powers:

Beginner What are the ways two components can share data in Angular?

Parent to child with input(); child to parent with output(); both directions with model(); parent reaching into the child instance with viewChild() / contentChild(); template reference variables within a single template; a shared injectable service for unrelated components; and the URL itself through route params, query params and route data. Content projection with <ng-content> passes markup rather than values. Name them roughly in that order — cheapest coupling first — and you have answered the follow-up before it is asked.

Beginner How does input() differ from the @Input decorator?

input() is a signal-based function called in the class body; it returns a read-only InputSignal that you call like this.title(). Because it is a signal, computed() and effect() track it automatically, so you rarely need ngOnChanges. It also gives you input.required<T>(), which the compiler enforces at the binding site. @Input is the legacy decorator that sets a plain property; it still works and is not deprecated, but new code should use input().

Beginner How do you send data from a child component back to its parent?

Declare saved = output<Order>() in the child and call this.saved.emit(order). The parent listens with normal event binding: <app-form (saved)="onSaved($event)">. output() replaces @Output with EventEmitter; it is not an observable, has no subscribe in templates, and is cleaned up automatically when the component is destroyed.

Beginner What is a template reference variable and when would you use one?

A #name label on an element, component or directive that makes it addressable elsewhere in the same template — <input #email> then {{ email.value }} or email.focus() from a button click. It is the zero-cost option when the interaction never leaves one template. If the class needs the same reference, query it with viewChild('email').

Beginner What does model() do, and when is two-way binding appropriate?

model() declares a writable signal that is also an input and an implicit output, enabling [(value)] on the parent. Use it when the value is genuinely co-owned — a custom form control, a rating widget, an expanded flag. Prefer separate input() and output() when the child should only propose a change and the parent decides whether to accept it, because that keeps a single writer.

Intermediate viewChild versus contentChild — what is the actual difference?

A view query searches the component's own template — nodes the component itself declares. A content query searches nodes that were projected into the component from outside through <ng-content>. So a tab container queries its tab children with contentChildren() because the consumer wrote them, while it queries its own internal indicator element with viewChild(). Content is resolved earlier than view, which is why the decorator era had ngAfterContentInit and ngAfterViewInit as separate hooks.

Intermediate Why are signal queries preferred over the @ViewChild decorator?

Because they remove the timing trap. @ViewChild results were populated during lifecycle hooks, so reading them in ngOnInit gave undefined and code drifted into ngAfterViewInit plus static: true juggling. viewChild() returns a signal you read whenever you want — inside a computed() or effect() it simply re-evaluates when the result appears or changes. It is also better typed: viewChild.required() removes the undefined from the type.

Intermediate What is prop drilling and how do you fix it in Angular?

Passing a value down through components that do not use it, purely to reach a descendant. It couples every intermediate component to a contract it does not care about, and every change ripples through the chain. Fixes: hoist the value into a service and inject it where it is needed; provide that service at the feature route so its lifetime matches the feature; or restructure with content projection so the owner of the data renders the consumer directly.

Intermediate When should state live in the URL rather than in a service?

Whenever the user would reasonably expect to bookmark it, share it, refresh into it, or reach it with the back button — the selected record id, filters, sort order, page number, active tab. Route params identify the resource; query params refine the view. The trade-off is that URL state is stringly typed and public, so secrets, large objects and transient UI flags do not belong there.

Intermediate How does withComponentInputBinding change how you read route parameters?

Add it to provideRouter(routes, withComponentInputBinding()) and the router binds path params, query params, matrix params and resolved data to component input()s whose names match the keys. The component then needs no ActivatedRoute injection and no subscription — the input is just a signal that updates on navigation. Fall back to ActivatedRoute when you need the parent route's params, non-matching key names, or the full URL tree.

Intermediate Two sibling components need the same data. Walk me through your options.

First ask whether their common parent can own it and pass it down as inputs with outputs coming back — often the correct and cheapest answer. If the parent is far away or the value is refresh-worthy, put it in the URL. If neither fits, create a service and provide it at the narrowest scope that contains both siblings — the shared route or the common parent component — rather than in root, so the state is created and destroyed with the feature. A global store is the last option, not the first.

Pro How do you decide between a plain service and a store like NgRx?

Count writers and cross-cutting reads. One or two writers with simple transitions: a signal-holding service is enough and far less code. Many independent writers, multi-step async flows, optimistic updates, undo, or a genuine need to replay and audit what changed: a store earns its overhead, and the action log plus DevTools become the debugging tool. Also weigh team size and turnover — the store's ceremony buys uniformity across a large team. Deciding by application size alone is the answer that reads as junior.

Pro A shared service exposes a writable signal directly. Why is that a problem, and what is the fix?

Any injector of the service can call set() or update(), so there is no single place where a transition happens and no way to reason about who changed what. Keep the writable signal private and expose readonly state = this._state.asReadonly() (or computed() projections), with named methods such as addItem() and clear() as the only mutation path. That is the store-lite discipline the next module builds on, and it is what makes a later migration to SignalStore or NgRx mechanical rather than a rewrite.

Pro Are there cases where a parent legitimately reaches into a child with viewChild instead of using bindings?

Yes, but narrowly: imperative DOM work with no declarative equivalent (focus management, scroll position, measuring, calling play() on a media element) and calling a well-defined public method on a child component such as reset() on a form wrapper. What it should not become is a channel for reading or writing the child's data — that reverses the flow, breaks the child's encapsulation, and makes it unusable anywhere the parent is not present. If you find yourself pulling values out with viewChild, the value belongs to the parent and should be passed in.
