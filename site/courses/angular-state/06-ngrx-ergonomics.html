Module: NgRx Ergonomics and Testing

Actions, reducers, selectors and effects are only half the story. What decides whether a team still likes NgRx a year in is the machinery around it — the service layer components actually talk to, the debugger that replays the whole session, and a test suite that stays fast because the store is a pure function.

What this module covers

Two practical halves. First, the ergonomics: the facade service pattern (and the honest argument against it), the low-boilerplate functional creators, wiring provideStoreDevtools to the Redux DevTools extension for time-travel debugging, and putting router state into the store with @ngrx/router-store. Second, testing: reducers and selectors are pure functions and need no TestBed at all, effects are tested with provideMockActions plus marble diagrams, and components are isolated from the real store by provideMockStore. Everything here uses the current standalone provider APIs.

Topics

Facades, functional creators, Redux DevTools and router-store

A facade is an injectable service that owns the Store so components never see it: it exposes ready-made observables or signals as fields and offers plain methods such as loadProducts() or addToCart(id) that dispatch behind the scenes. The upside is real — components stop importing action and selector files, the NgRx surface area a new joiner must learn shrinks to one class per feature, and cross-cutting logic (combining two selectors, debouncing a dispatch) gets a natural home. The honest counter-argument is equally real: it is a layer that adds no behaviour, it tempts developers to write imperative methods that return state and so quietly undo unidirectional data flow, the "we could swap NgRx out later" justification almost never gets exercised, and the "facades make components easier to test" argument lost most of its force once provideMockStore shipped. Treat it as a team convention worth arguing about, not a rule — and expect an interviewer to ask you to argue both sides.

The ergonomics that are not debatable: functional creators (createActionGroup, createFeature, and effects declared with { functional: true } so they are standalone functions instead of class members) cut most of the boilerplate NgRx was once criticised for. provideStoreDevtools connects your store to the Redux DevTools browser extension, giving an action log, a live state inspector, a diff per action, and time travel — replay the exact sequence a bug reporter produced instead of guessing. Keep logOnly on outside development so a production build cannot have its state rewritten from the extension, cap history with maxAge, and use autoPause so a chatty polling effect does not flood the timeline. Finally, provideRouterStore from @ngrx/router-store mirrors the Angular Router into the store: navigation dispatches router actions your reducers and effects can react to, getRouterSelectors() gives you selectRouteParams, selectQueryParams and selectUrl so a selector can read the current id without injecting ActivatedRoute, and time travel now moves the URL too rather than leaving the address bar out of sync.

// app.config.ts
providers: [
  provideStore(reducers),
  provideEffects(ProductEffects),
  provideRouterStore(),                       // router state lands under state.router
  provideStoreDevtools({
    maxAge: 25,
    logOnly: !isDevMode(),                    // read-only outside dev builds
    autoPause: true,
    connectInZone: true,
  }),
],

// products.facade.ts — the optional service layer
@Injectable({ providedIn: 'root' })
export class ProductsFacade {
  private store = inject(Store);
  readonly products = this.store.selectSignal(selectAllProducts);
  readonly loading  = this.store.selectSignal(selectProductsLoading);

  load()            { this.store.dispatch(ProductActions.load()); }
  select(id: string) { this.store.dispatch(ProductActions.select({ id })); }
}

// reading route state from the store instead of ActivatedRoute
const { selectRouteParams } = getRouterSelectors();
export const selectCurrentProduct = createSelector(
  selectAllProducts, selectRouteParams,
  (products, params) => products.find(p => p.id === params['id']),
);

Testing reducers, selectors, effects and store-connected components

NgRx is unusually pleasant to test because the interesting parts are pure. A reducer is a function of state and action, so a test is three lines with no TestBed, no dependency injection and no asynchrony: build a state, call the reducer with an action, assert on the returned object (and, while you are there, assert the previous state was not mutated). A selector created with createSelector exposes a projector function — calling selectX.projector(inputA, inputB) tests the projection logic directly, so you never have to hand-build a full application state object just to exercise one derived value. Reserve full-state selector tests for the composition itself, and remember memoization is stateful across tests: call release() or rebuild the selector if a stale cached result bites you.

Effects are the part that needs machinery, because an effect is a stream in and a stream out. provideMockActions(() => actions$) feeds a controllable actions stream into the effect under test; the simplest tests push a single action and assert the emitted one. For anything timing-sensitive — debounceTime, concatMap ordering, retries — use RxJS marble diagrams inside TestScheduler.run, where hot models the actions stream, cold models the API call, and expectObservable asserts both the values and when they arrive in virtual time. Finally, for components, provideMockStore({ initialState, selectors }) swaps in a fake store: overrideSelector pins whatever a selector should return (followed by store.refreshState() to push a new value mid-test), and spying on store.dispatch asserts the component fired the right action. That combination is why a facade is no longer required for testability — you can isolate a component from real reducers and effects without inventing a wrapper service.

// reducer — a pure function, no TestBed
const next = productsReducer(initialState, ProductActions.loadSuccess({ products }));
expect(next.items.length).toBe(2);
expect(next).not.toBe(initialState);           // reducers return new state

// selector — test the projection, not a hand-built state tree
expect(selectVisibleProducts.projector(allProducts, 'shoes')).toEqual([shoe]);

// effect — marble test with a controllable actions stream
TestBed.configureTestingModule({
  providers: [ProductEffects, provideMockActions(() => actions$), { provide: Api, useValue: api }],
});
testScheduler.run(({ hot, cold, expectObservable }) => {
  actions$ = hot('-a', { a: ProductActions.load() });
  api.getAll.mockReturnValue(cold('--b', { b: products }));
  expectObservable(effects.load$).toBe('---c', { c: ProductActions.loadSuccess({ products }) });
});

// component — fake store, pinned selector, dispatch spy
providers: [provideMockStore({ selectors: [{ selector: selectAllProducts, value: products }] })];
const dispatch = jest.spyOn(store, 'dispatch');
store.overrideSelector(selectAllProducts, []);
store.refreshState();

Interview questions

Tooling and testing are where Indian interviews separate "I followed an NgRx tutorial" from "I have maintained an NgRx codebase" — service-company rounds probe the DevTools setup, product-company rounds go straight at the test strategy:

Beginner What is a facade in an NgRx application?

An injectable service that wraps the Store for one feature. It exposes selected state as observables or signals and offers plain methods that dispatch actions internally, so components inject the facade instead of the store and never import action or selector files directly.

Beginner How do you enable Redux DevTools in a standalone Angular app?

Install the @ngrx/store-devtools package and the Redux DevTools browser extension, then add provideStoreDevtools({ maxAge: 25, logOnly: !isDevMode() }) to the providers array in app.config.ts, after provideStore. It replaces the older StoreDevtoolsModule.instrument() import.

Beginner What does the Redux DevTools extension actually give you?

A chronological log of every dispatched action, the full store state at each point, a diff showing exactly what that action changed, time travel to replay or step back through the sequence, and export or import of a state snapshot — which turns "it broke on my machine" into a file you can load.

Beginner How do you test a reducer?

Call it directly: const next = reducer(someState, someAction) and assert on the result. No TestBed, no injector, no async — a reducer is a pure function. Also assert the input state object was not mutated, since returning new state is the contract the whole store depends on.

Intermediate What is projector on a selector and why prefer it in tests?

Every createSelector result exposes .projector(...) — the raw projection function without the input selectors or memoization. Passing the inputs directly lets you test the derived-value logic without constructing an entire application state tree, so the test stays short and does not break when unrelated parts of the state shape change.

Intermediate What does @ngrx/router-store do, and why would you add it?

provideRouterStore() connects the Angular Router to the store: navigations dispatch router actions (request, navigation, navigated, cancel, error) that reducers and effects can react to, and the serialized router state lives under a router slice. Benefits: selectors can read route params without injecting ActivatedRoute, effects can trigger on navigation, and DevTools time travel also restores the URL instead of leaving the address bar stale.

Intermediate How do you test a component that reads from the store?

Provide provideMockStore({ initialState, selectors: [...] }) in the TestBed instead of the real store. Pin selector results with overrideSelector, push a new value mid-test with store.overrideSelector(...) followed by store.refreshState(), and assert behaviour by spying on store.dispatch. Reducers and effects never run, so the test stays focused on the component.

Intermediate How is an effect tested? What does provideMockActions do?

provideMockActions(() => actions$) supplies a stream you control in place of the real Actions stream, so you can push exactly the action the effect listens for. You stub the service the effect calls, subscribe to the effect observable, and assert the action it emits. Because the callback is re-read per test, assign actions$ inside each test before the effect subscribes.

Intermediate What is logOnly and why does it matter in production?

With logOnly: true the DevTools connection is restricted to recording — the extension can display actions and state but cannot dispatch, jump or rewrite state in the running app. Set it from !isDevMode() so development keeps full time travel while a production build is read-only. Many teams go further and skip the provider entirely in production builds.

Pro Argue against the facade pattern. When is it genuinely the wrong choice?

It adds an indirection layer that carries no behaviour of its own, so every feature costs one more file and one more hop when reading code. It invites anti-patterns — methods that dispatch and return state in one call, or that hide sequencing that belongs in an effect — which erodes unidirectional flow. Its historical selling point, testability, is now covered by provideMockStore. And the portability argument ("we can swap NgRx out") is rarely exercised, because actions and selectors leak through the facade's own types anyway. It is a reasonable convention for a large team wanting one entry point per feature; it is the wrong choice when it is adopted reflexively for a small feature or as a substitute for good selector design.

Pro An effect uses debounceTime. Why does a naive test fail, and how do marble tests fix it?

A naive test subscribes and asserts synchronously, but the debounce schedules emission on a real timer, so nothing has been emitted yet — or the test waits on wall-clock time and turns flaky and slow. TestScheduler.run replaces the scheduler with virtual time: hot models the incoming actions stream, cold models the API response, and expectObservable(effect$).toBe(diagram, values) asserts both what was emitted and at which virtual frame. The suite stays deterministic and instant regardless of the debounce interval.

Pro Selector memoization is caching stale values across tests. What is happening and how do you handle it?

A memoized selector holds its last inputs and last result on the selector object itself, which is module-level and therefore shared by every test in the file. If one test overrides it or feeds it a state object that is reference-equal to a previous one, the next test can receive the cached projection. Fixes: call selector.release() (or store.resetSelectors() when using MockStore) in an afterEach, always create new state objects rather than mutating, and prefer .projector() for pure-logic tests since it bypasses the memoized wrapper entirely.
