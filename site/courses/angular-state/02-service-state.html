Module: Shared Services as State

Before you reach for a state-management library, Angular already gives you one: a root-provided service that owns some private state and hands out a read-only view of it. Done with discipline, this "store-lite" pattern carries most applications the whole way.

Knowledge Library → Courses → Angular State Management → Shared Services as State

What this module covers

A shared service becomes a store the moment you stop letting callers write to it directly. This module covers the shape of that service — private writable state, public read-only projection, and a small set of methods that are the only way to change anything — in both flavours: the classic RxJS BehaviorSubject plus asObservable(), and the modern Angular v20 signal() plus asReadonly() and computed(). It then covers the discipline that makes it work: replacing state objects rather than mutating them, deriving instead of duplicating, and recognising the point where a plain service genuinely stops being enough.

Topics

The store-lite service: private writable state, public read-only view

An Angular service marked @Injectable({ providedIn: 'root' }) is a single instance shared by everyone who injects it — that is already the "single source of truth" that state libraries advertise. The store-lite pattern adds one rule on top: the writable handle stays private, and the public surface is read-only. With signals that means a private signal() exposed through .asReadonly(); with RxJS it means a private BehaviorSubject exposed through .asObservable(). BehaviorSubject specifically (not a plain Subject) because state must have a current value that late subscribers receive immediately — the same guarantee a signal gives for free.

Why it matters: the read-only projection is what turns a shared bag of variables into a store. Components can read the state and react to it, but the only way to change it is to call a named method on the service — addToCart(), clearFilters() — which keeps every mutation in one auditable file and makes the state machine testable without a single component. This encapsulation, not the library you pick, is the actual idea behind Redux-style architecture, and it is the answer interviewers are listening for when they ask why you would use a service instead of NgRx. Signals are the default for new code; the BehaviorSubject form remains essential for interop with existing codebases and for anything genuinely stream-shaped, where toSignal and toObservable let the two worlds meet.

@Injectable({ providedIn: 'root' })
export class CartStore {
  // modern (v20): writable stays private, consumers get a read-only signal
  private readonly _items = signal<Item[]>([]);
  readonly items = this._items.asReadonly();

  // classic RxJS equivalent, still everywhere in existing code
  private readonly itemsSubject = new BehaviorSubject<Item[]>([]);
  readonly items$ = this.itemsSubject.asObservable();

  add(item: Item): void {
    this._items.update(list => [...list, item]);   // the ONLY way in
  }
}

Immutability, derived state with computed, and when a service is enough

Angular's reactivity is reference-based. A signal notifies its dependents when set() or update() hands it a value that is not the same reference as before; OnPush components re-render when an input reference changes; memoised derivations recompute when an input reference changes. Push a row onto the array inside a signal and every one of those checks sees the identical reference and concludes nothing happened — the data changed, the screen did not. The fix is not a deep-equality option, it is a habit: never mutate, always replace. Spread the object or array, change the one field you meant to change, and hand back a fresh value (update(s => ({ ...s, loading: false }))). The same rule is why NgRx freezes state in development mode — it is enforcing a discipline you should already have.

Immutability also unlocks the second half of the pattern: derived state. Totals, filtered lists, "is the form valid" flags and view models should never be stored as separate fields that some method has to remember to keep in sync — that is the classic source of stale-UI bugs. Wrap them in computed(), which recalculates lazily, caches the result, and only tells the template to update when the value actually changed. Store the minimum irreducible state; compute everything else. In the RxJS flavour the equivalents are map and combineLatest over the exposed observable, with shareReplay if the work is expensive.

And the honest verdict: for most applications this is the finish line, not a stepping stone. A handful of feature-scoped store-lite services — one for the cart, one for the current user, one for a filter panel — gives you a single source of truth, testable state transitions, read-only consumers and derived values, with no actions, no reducers, no effects and no extra dependency. You outgrow it when several unrelated features must coordinate on the same state, when time-travel debugging or a strict audit trail of every change earns its keep, or when the team is large enough that an enforced convention beats a graceful one. Until one of those is genuinely true, adding NgRx buys ceremony rather than clarity — and being able to argue that trade-off out loud is a senior-level answer.

private readonly _state = signal({ items: [] as Item[], coupon: null as string | null });
readonly state = this._state.asReadonly();

// derived, never stored: recomputes only when items actually change
readonly total = computed(() =>
  this._state().items.reduce((sum, i) => sum + i.price * i.qty, 0));

setQty(id: string, qty: number): void {
  this._state.update(s => ({                       // new state object
    ...s,
    items: s.items.map(i => (i.id === id ? { ...i, qty } : i)),  // new array, new row
  }));
  // s.items[0].qty = qty   ← would change the data and update nothing on screen
}

Interview questions

Service-based state is the most-asked state question in Indian Angular interviews — service companies screen on BehaviorSubject, product companies push on immutability and on why you did not use NgRx:

Beginner What is a shared service used as a store, and why providedIn: 'root'?

A service that holds application state and exposes methods to change it. providedIn: 'root' registers it in the root injector, so every component that injects it receives the same instance — one source of truth for the whole app. It is also tree-shakable: if nothing injects the service, it never ships in the bundle.

Beginner Why expose asReadonly() or asObservable() instead of the writable signal or the Subject itself?

To stop consumers from writing. If a component can call .set() or .next() on your state, mutations scatter across the codebase and become impossible to trace. Exposing a read-only projection forces every change through a named service method, so the state transitions live in one file, are unit-testable on their own, and show up in one place during code review.

Beginner Subject vs BehaviorSubject — which one for shared state, and why?

BehaviorSubject. It requires an initial value and replays the current value to every new subscriber, so a component created later still gets the present state. A plain Subject emits only to subscribers already listening, so a late component sees nothing until the next change — the classic "my data is empty on first load" bug. Subject is for events, BehaviorSubject is for state.

Beginner How does a component consume signal-based state from such a service?

Inject the service and call the signal in the template: {{ cart.total() }}, or @for (item of cart.items(); track item.id). No async pipe, no subscription, no cleanup — reading a signal inside a template registers the dependency automatically and Angular marks only the affected views dirty. With the observable flavour you would use the async pipe instead.

Beginner set() vs update() on a signal?

set(value) replaces the state outright, when the new value does not depend on the old one. update(fn) derives the new value from the current one — update(n => n + 1), or a spread over the previous state object. Both must be given a new reference for objects and arrays; neither is a place to mutate what you were handed.

Intermediate Why must you replace state objects instead of mutating them?

Angular compares by reference. items().push(x) keeps the same array reference, so the signal does not notify, OnPush parents do not re-check, and computed() derivations do not recompute — the model changed and the UI silently did not. Replacing ([...items, x], { ...state, flag }) produces a new reference, which is the signal every layer of the framework is watching for. It also makes state changes debuggable, since the previous value still exists untouched.

Intermediate Why derive with computed() instead of storing the derived value in another field?

Two stored fields can disagree; a derived one cannot. computed() recalculates lazily from its dependencies, memoises the result, and propagates only when the value actually changes — so a cart total can never drift out of sync with the items. Storing total alongside items means every mutation path has to remember to update both, which is exactly the bug class the pattern exists to remove. Rule: store the minimum irreducible state, compute the rest.

Intermediate You have a legacy BehaviorSubject service and a new signal-based component. How do you bridge them?

Use the RxJS interop: toSignal(this.svc.items$, { initialValue: [] }) converts an observable into a signal (and handles unsubscription when the injection context is destroyed), while toObservable(someSignal) goes the other way for code that still needs a stream. This lets you migrate a codebase service by service rather than in one big rewrite — a very common real-project question.

Intermediate Do you need to unsubscribe or clean up in a root-provided state service?

The exposed state itself does not leak — but consumers that manually subscribe to items$ do, because a root service lives for the whole app and holds the subscription forever. Use the async pipe, takeUntilDestroyed(), or signals, all of which unsubscribe automatically. Signals sidestep the issue entirely: there is nothing to unsubscribe from. If the service itself subscribes to something long-lived, tie that to DestroyRef.

Intermediate How does OnPush change detection interact with a state service?

An OnPush component re-renders when an input reference changes, when an event fires inside it, when the async pipe emits, or when a signal it reads changes. A service that always replaces state satisfies all of those cleanly, which is why immutability plus OnPush is a safe combination — and why a service that mutates in place produces components that update in some places (default change detection) and not others (OnPush), the most confusing bug shape in this area.

Pro asReadonly() prevents set() — does it make the state immutable?

No. It is a compile-time restriction on the signal handle only; the value it returns is the same object reference the service holds, so store.items()[0].qty = 5 compiles and mutates the store's own data from the outside, silently and without notifying anyone. Defences: type the state with readonly / Readonly<T> so TypeScript rejects the write, return copies at the boundary when the data is genuinely at risk, or deep-freeze state in development builds the way NgRx's runtime checks do.

Pro When does a store-lite service stop being enough, and what do you move to?

When many unrelated features must coordinate on the same slice and the update rules no longer fit in one readable file; when you need an explicit, replayable log of every change (time-travel debugging, audit); or when team size makes an enforced convention worth more than a graceful one. The intermediate step is usually NgRx SignalStore — the same encapsulation with withState/withComputed/withMethods plus composable features — and full NgRx Store with actions, reducers and effects only when the event log itself is the requirement. Most applications never cross that line, and saying so confidently is the point of the question.

Pro When would you not use providedIn: 'root' for a state service?

When the state should die with its feature. Providing the service in a component's providers (or on a route via providers on the route config) gives each instance its own state that is destroyed with the component or the route — right for a wizard, an editable detail panel, or a reusable widget where two instances must not share a cart. It also matters under SSR: a root singleton holding user-specific state on the server can bleed between requests, so per-request or per-route scoping is the safe default for anything user-specific.
