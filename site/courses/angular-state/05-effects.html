Module: Effects and Side Effects

A reducer is a pure function, so it may never call an API, navigate the router, touch local storage or raise a toast. Everything impure is exiled to one place — effects — and the craft of NgRx is largely the craft of writing them so they never die, never double-fire, and never lie to the store.

What this module covers

Effects are the asynchronous half of NgRx: a long-lived RxJS pipeline that listens to every dispatched action, performs the impure work the reducer is forbidden to do, and feeds the result back into the store as another action. The module covers the building blocks (createEffect, the Actions stream, ofType), how effects are registered in a standalone app with provideEffects and written as functional effects with inject(), the canonical load / success / failure action triple, and then the two things interviews actually probe: where catchError must sit so the effect stream survives a failed request, and how to pick the right flattening operator for each kind of effect.

Topics

Why effects exist: createEffect, the Actions stream, ofType

NgRx reducers are pure functions of (state, action). Purity is what makes the store replayable, time-travel debuggable and trivially testable — so an HTTP call inside a reducer is not merely bad style, it breaks the model. Effects are the sanctioned escape hatch. The Actions service is an observable of every action dispatched anywhere in the app, emitted after the reducers have already run. You pipe that stream through ofType(SomeActions.something) to filter down to the actions you care about, do the impure work, and map the outcome back to a new action. createEffect wraps that pipeline and, by default, subscribes the returned observable straight back into the dispatcher.

Why it matters: this is the discipline that keeps components dumb. A component dispatches "the user asked for the product list" and stops caring; the effect owns the HTTP client, the retry policy and the error translation. It is also why NgRx interviews open with "what belongs in a reducer versus an effect?" — the answer separates people who have read the docs from people who have shipped. One rule to internalise early: ofType accepts action creators directly (not just type strings), which gives you full type inference on the action payload downstream.

@Injectable()
export class ProductEffects {
  private actions$ = inject(Actions);
  private api = inject(ProductService);

  loadProducts$ = createEffect(() =>
    this.actions$.pipe(
      ofType(ProductPageActions.opened),           // filter the action stream
      switchMap(() =>
        this.api.getAll().pipe(                    // impure work, safely nested
          map(products => ProductApiActions.loadSuccess({ products })),
          catchError(err => of(ProductApiActions.loadFailure({ error: err.message })))
        )
      )
    )
  );
}

Registering effects: provideEffects and functional effects with inject()

In a standalone application there is no EffectsModule.forRoot([]). You register root effects by adding provideEffects(...) to the providers array in app.config.ts, alongside provideStore(); feature effects go into the providers of a lazily loaded route, where they are registered the moment that route activates and stay registered for the life of the app. provideEffects accepts effect classes, whole modules of functional effects, or a mixture of both.

Functional effects drop the class entirely. Pass { functional: true } in the effect config and declare dependencies as default parameter values resolved with Angular's inject() — (actions$ = inject(Actions), api = inject(ProductService)). The payoff is testability: because the dependencies are ordinary parameters, a unit test calls the effect function with fakes and never needs TestBed. The NgRx docs recommend the parameter form over calling inject() in the body for exactly that reason, and inject() in the body must stay in a synchronous injection context anyway.

// product.effects.ts — functional effect, no class
export const loadProducts = createEffect(
  (actions$ = inject(Actions), api = inject(ProductService)) =>
    actions$.pipe(
      ofType(ProductPageActions.opened),
      exhaustMap(() => api.getAll().pipe(
        map(products => ProductApiActions.loadSuccess({ products })),
        catchError(e => of(ProductApiActions.loadFailure({ error: e.message })))
      ))
    ),
  { functional: true }
);

// app.config.ts
providers: [
  provideStore(reducers),
  provideEffects(ProductEffects, AuthEffects),   // classes
];

// lazy feature route
{ path: 'orders', providers: [provideState(ordersFeature), provideEffects(orderEffects)] }

The load triple, and optimistic versus pessimistic updates

Almost every data-fetching effect follows the same three-action shape: a command action that says something happened ([Product Page] Opened or loadProducts), and two event actions the API reports back with (loadProductsSuccess, loadProductsFailure). The reducer handles all three — set loading: true on the command, store the payload and clear the flag on success, store the message and clear the flag on failure. Keep the naming honest: actions are unique events, not reusable setters, so resist a single setProducts action fired from four places. createActionGroup gives you the whole triple with one declaration.

Writes come in two flavours and interviewers love the contrast. A pessimistic update waits for the server: dispatch saveTodo, the effect calls the API, and only saveTodoSuccess mutates the store. Correct, but the UI feels slow. An optimistic update mutates the store immediately in the reducer for saveTodo, lets the effect fire the request in the background, and dispatches a rollback action (saveTodoFailure carrying the previous value) if the server rejects it. Optimistic is the right call for cheap, high-confidence, easily reversible changes — toggling a checkbox, reordering a list, liking a post. It is the wrong call for payments, or anything where the server assigns the identity of the created record. Optimistic writes also force concatMap rather than switchMap: you must not cancel a request whose local mutation has already been applied.

export const TodoActions = createActionGroup({
  source: 'Todo API',
  events: {
    'Toggle Todo':          props<{ id: string }>(),          // optimistic: reducer flips it now
    'Toggle Todo Failure':  props<{ id: string; error: string }>(), // reducer flips it back
  },
});

export const toggleTodo = createEffect(
  (actions$ = inject(Actions), api = inject(TodoService)) =>
    actions$.pipe(
      ofType(TodoActions.toggleTodo),
      concatMap(({ id }) => api.toggle(id).pipe(     // queue writes, never cancel them
        map(() => TodoActions.toggleTodoNoop()),
        catchError(e => of(TodoActions.toggleTodoFailure({ id, error: e.message })))
      ))
    ),
  { functional: true }
);

Error handling: where catchError must sit, and dispatch: false

This is the single highest-value thing in the module. An effect is one long-lived subscription. RxJS terminates a stream on error — so if an HTTP failure is allowed to propagate to the outer action stream, that effect stops listening and the feature silently dies until the page is reloaded. The fix is placement, not the operator: catchError must live inside the inner observable, within the flattening operator's projection function, so the error is caught and converted to a failure action before it can reach the outer pipeline. A catchError chained after switchMap at the outer level compiles, passes a happy-path test, and is a production bug.

NgRx does give you a safety net: since version 8 an error escaping to the outer stream is reported to Angular's ErrorHandler and the effect is automatically resubscribed, up to a default of ten errors, after which it gives up. Treat that as a seatbelt, not a strategy — a resubscribed effect has already lost the action that triggered it. Two more essentials. First, { dispatch: false }: effects that end in a genuine terminal side effect — router navigation, a snackbar, writing to local storage, logging — must declare it, because an effect that returns something other than an action while dispatch is on will feed the action back into the stream it is subscribed to and spin an infinite loop. Second, keep each effect to a single responsibility: one action in, one action out. Fanning several unrelated actions out of one effect makes the action log unreadable and is flagged by the official ESLint rules.

// WRONG — catchError outside: one failed request kills the effect forever
actions$.pipe(
  ofType(A.load),
  switchMap(() => api.get()),
  map(r => A.loadSuccess({ r })),
  catchError(e => of(A.loadFailure({ e })))   // stream is already dead here
);

// RIGHT — catchError inside the inner observable
actions$.pipe(
  ofType(A.load),
  switchMap(() => api.get().pipe(
    map(r => A.loadSuccess({ r })),
    catchError(e => of(A.loadFailure({ e })))
  ))
);

// terminal side effect: no action comes out, so say so
export const navigateAfterSave = createEffect(
  (actions$ = inject(Actions), router = inject(Router)) =>
    actions$.pipe(ofType(A.saveSuccess), tap(() => router.navigate(['/orders']))),
  { functional: true, dispatch: false }
);

Choosing the flattening operator per effect

Every effect that performs async work nests an inner observable inside a flattening operator, and the choice is a behavioural decision, not a style preference. switchMap cancels the in-flight request when a new action arrives — correct for reads where only the latest result matters (type-ahead search, a filter change, a detail page reload), catastrophic for writes because a cancelled save looks successful to the user and never reaches the server. concatMap queues requests and runs them strictly in order — the safe default for writes and for any sequence where ordering matters. mergeMap runs everything concurrently with no ordering guarantee — right for independent, order-insensitive work such as firing analytics events or deleting several selected rows. exhaustMap ignores new actions while one is in flight — the double-click guard, and the canonical choice for a login button or a form submit.

A useful shorthand for interviews: search uses switchMap, save uses concatMap, login uses exhaustMap, and fire-and-forget uses mergeMap. Two related habits round the topic off. When an effect needs a slice of state, do not subscribe to the store inside the pipeline — use concatLatestFrom from @ngrx/operators, which reads the selector lazily only when the action actually arrives, so the selector is not evaluated on every unrelated dispatch. And when an effect legitimately needs a value the action does not carry, prefer widening the action payload at the dispatch site over reaching into the store from the effect.

// read: only the newest query matters -> cancel the rest
ofType(SearchActions.queryChanged), debounceTime(300), switchMap(...)

// write: never cancel, never reorder
ofType(CartActions.addItem),        concatMap(...)

// submit button: swallow the double-click
ofType(AuthActions.loginSubmitted), exhaustMap(...)

// independent fire-and-forget work
ofType(AnalyticsActions.tracked),   mergeMap(...)

// needs state? read it lazily, do not subscribe
ofType(OrderActions.checkout),
concatLatestFrom(() => store.select(selectCartItems)),
concatMap(([action, items]) => api.checkout(items).pipe(/* ... */))

Interview questions

Effects are where NgRx interviews get real — Indian product and service companies alike use them to separate tutorial knowledge from production experience:

Beginner What is an NgRx effect and why can't the work live in a reducer?

An effect is a long-lived RxJS pipeline that listens to the dispatched-action stream, performs impure work (HTTP, router navigation, local storage, notifications) and dispatches a new action with the result. Reducers must be pure functions of (state, action) — that purity is what makes the store predictable, replayable and time-travel debuggable. Any asynchrony or I/O inside a reducer breaks it, so it is exiled to effects.

Beginner What does the Actions service give you, and what does ofType do?

Actions is an injectable observable of every action dispatched anywhere in the app, emitted after the reducers have already processed it. ofType is a pipeable operator that filters that stream to the action types you care about. Pass action creators rather than type strings and TypeScript infers the payload type for the rest of the pipe.

Beginner How do you register effects in a standalone Angular application?

Add provideEffects(EffectsA, EffectsB) to the providers array in app.config.ts for root effects, and to the providers of a lazily loaded route for feature effects. It replaces EffectsModule.forRoot() / forFeature(). It accepts effect classes and modules of functional effects interchangeably.

Beginner Describe the three actions of a typical data-loading flow.

A command action (loadProducts, or better, an event name such as [Product Page] Opened) that the reducer uses to set loading: true; a success action carrying the payload, which stores the data and clears the flag; and a failure action carrying an error message, which stores the error and clears the flag. Only the command is dispatched by the component — the other two come out of the effect.

Intermediate When do you need dispatch: false, and what happens if you forget it?

Use it when the effect ends in a terminal side effect and produces no action — router navigation, showing a snackbar, writing to local storage, logging. If you omit it, whatever the pipeline emits is dispatched back into the action stream the effect itself is subscribed to, which re-triggers the effect and spins an infinite loop that freezes the tab.

Intermediate Where exactly must catchError go inside an effect, and why?

Inside the inner observable, within the flattening operator's projection function — switchMap(() => api.get().pipe(map(...), catchError(...))). RxJS terminates a stream on error, so if the error reaches the outer action stream the effect's subscription ends and it stops reacting to that action for the rest of the session. Catching inside converts the failure into a failure action before it can escape, and the outer stream never sees an error at all.

Intermediate switchMap vs concatMap vs mergeMap vs exhaustMap — give one effect for each.

switchMap: type-ahead search — cancel the stale request, only the newest query matters. concatMap: saving cart items — queue in order, never cancel a write. mergeMap: analytics events or bulk deletes — independent, order does not matter. exhaustMap: login or form submit — ignore repeat clicks until the current request settles. Using switchMap for a save is the classic production bug: the cancelled request never reaches the server but the UI shows success.

Intermediate What is a functional effect and what does it improve?

An effect created with createEffect(..., { functional: true }) outside any class, with dependencies supplied as default parameters resolved by inject(): (actions$ = inject(Actions), api = inject(Api)) => .... It removes the @Injectable class boilerplate and, more importantly, makes tests trivial — call the function with fakes, no TestBed and no DI container needed. NgRx recommends the parameter form over calling inject() in the body for exactly this reason.

Intermediate Optimistic vs pessimistic updates — how do the effects differ?

Pessimistic: the reducer ignores the command action and only the success action mutates state, so nothing changes until the server confirms. Optimistic: the reducer applies the change immediately on the command action, the effect fires the request in the background, and a failure action carries enough information to roll the state back. Optimistic suits cheap, reversible, high-confidence changes (toggles, reordering, likes); pessimistic is mandatory for payments and anywhere the server assigns identity. Optimistic writes must use concatMap, never switchMap — a cancelled request whose local mutation already landed leaves the client lying about server state.

Intermediate An effect needs a value from the store. What is the right way to get it?

Use concatLatestFrom(() => store.select(selector)) from @ngrx/operators. Unlike withLatestFrom, it takes a factory and evaluates the selector lazily, only once the action actually arrives — so the selector is not recomputed on every unrelated dispatch. Better still, if the value is known at dispatch time, put it in the action payload and keep the effect free of store reads.

Pro An effect stops firing after the API returns a 500 once. Diagnose it.

The catchError is chained on the outer pipe instead of inside the inner observable, so the error terminated the effect's subscription — it is no longer listening to the action stream, and every later dispatch is ignored until a reload. Move catchError inside the flattening operator's projection. Note that NgRx will report the error to Angular's ErrorHandler and automatically resubscribe the effect (up to a default of ten errors), but the triggering action is already lost, so resubscription is a seatbelt rather than a fix.

Pro Two effects each react to the other's output action and the app hangs. What went wrong and how do you prevent it structurally?

A cyclic effect chain: effect A dispatches an action that effect B listens to, and B dispatches something A listens to, so the action stream never settles. It usually comes from generic setter-style actions reused across features instead of unique past-tense events. Prevention: name actions as unique events by source ([Cart Page] Item Added), keep one effect to a single responsibility with one action in and one action out, and enable the official NgRx ESLint rules — avoid-cyclic-effects, no-multiple-actions-in-effects and no-dispatch-in-effects catch all three shapes of this bug in CI.

Pro How would you make effects easy to test, and what do the tests assert?

Prefer functional effects with injected parameters so a test constructs the effect directly with stub services and a hand-made Actions observable — no TestBed, no provideMockActions ceremony. Assert three things per effect: the happy path emits the success action with the mapped payload; the error path emits the failure action and the returned observable does not error; and the concurrency behaviour matches intent (with a marble test, that two rapid actions produce two results under concatMap but one under switchMap or exhaustMap). Non-dispatching effects are asserted on the spy for the router or notification service instead.
