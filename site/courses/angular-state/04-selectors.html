Module: Selectors and Entity State

Reducers are the write model; selectors are the read model. This module is about the query layer that sits between your store and your components — how a memoized selector avoids recomputation, how to compose one view model per screen, and how @ngrx/entity stops you hand-rolling array lookups over collections.

What this module covers

NgRx separates reading from writing in the spirit of CQRS: reducers own state transitions, selectors own the projections components actually consume. Half of this module is the selector API — createFeatureSelector, createSelector, memoization semantics, and folding many small selectors into a single view-model selector that a component reads with one store.selectSignal(...). The other half is @ngrx/entity: why collections belong in a normalized ids + entities shape, how createEntityAdapter generates the CRUD helpers your reducer calls, and how adapter.getSelectors() hands the query layer back to you for free. Everything uses current standalone NgRx, including the signals interop.

Topics

createSelector, memoization, and view-model selectors

A selector is a pure function from state to a slice of it. createFeatureSelector<T>('featureKey') grabs a whole registered feature slice without you typing state.books everywhere; createSelector(...inputs, projector) then takes one or more input selectors and a projector function that combines their results. The payoff is memoization: NgRx remembers the last arguments a selector was called with and the last value it produced. If every input result is reference-equal to the previous run, the projector is skipped entirely and the cached output is returned — which also means downstream selectors and the template see the same object reference and change detection has nothing to do.

That single sentence explains most selector bugs. Memoization compares by reference, not by deep value, so a reducer that mutates an array in place (state.items.push(x)) hands back the same reference and the selector reports "nothing changed" — the screen goes stale. Conversely, a projector that builds a fresh object or array on every call (books.map(...) inside a component, or { ...a, ...b } in an unmemoized function) breaks reference equality further downstream and defeats OnPush. The composition habit that survives code review is small, reusable selectors near the reducer plus one view-model selector per screen that assembles them, so the component subscribes once instead of juggling four streams. Read it with store.selectSignal(selector) for a Signal, or store.select(selector) when you still need an Observable to pipe; both are backed by the same memoized function, and selectSignal accepts an equality function just like computed.

// books.selectors.ts
export const selectBooksState = createFeatureSelector<BooksState>('books');

export const selectQuery   = createSelector(selectBooksState, s => s.query);
export const selectLoading = createSelector(selectBooksState, s => s.loading);

// one view model per screen — the component takes a single signal
export const selectBooksPageVm = createSelector(
  selectAllBooks, selectQuery, selectLoading,
  (books, query, loading) => ({
    books: books.filter(b => b.title.includes(query)),
    loading,
    isEmpty: !loading && books.length === 0,
  })
);

// books-page.component.ts
private readonly store = inject(Store);
readonly vm = this.store.selectSignal(selectBooksPageVm);   // Signal<BooksPageVm>

@ngrx/entity: normalized collections and the adapter

Storing a collection as a plain array forces every reducer to do work the store should not care about: find the index, splice it out, rebuild the array immutably, and repeat for add, update and remove. Normalization fixes this by keeping two things instead — ids, an ordered array of primary keys, and entities, a dictionary keyed by id. Lookup by id becomes O(1) rather than a scan, an entity exists in exactly one place so two screens cannot drift out of sync, and ordering is decoupled from storage. EntityState<T> is exactly that pair, and you extend it to add your own slice properties such as selectedId or loading.

createEntityAdapter<T>() returns a stateless helper configured with selectId (only needed when your primary key is not literally id) and an optional sortComparer — set the comparer to false when you do not need sorted output, because sorting costs on every write. The adapter gives you getInitialState() to seed the slice, a full set of immutable collection methods used inside on(...) handlers — addOne/addMany, setOne/setMany/setAll, updateOne/updateMany (which take an Update<T> of { id, changes } and therefore support partial updates), upsertOne/upsertMany, mapOne/map, and removeOne/removeMany/removeAll — and finally getSelectors(), which returns selectIds, selectEntities, selectAll and selectTotal. Compose those four with your feature selector and the whole read layer for a collection is four lines. This is the point where the two halves of the module meet: the adapter produces the base selectors, and createSelector composes them into the view models the screens want.

export interface BooksState extends EntityState<Book> { selectedId: string | null; }

export const adapter = createEntityAdapter<Book>({
  selectId: b => b.isbn,                                   // key is not called "id"
  sortComparer: (a, b) => a.title.localeCompare(b.title),  // or false, if unsorted
});

export const initialState: BooksState = adapter.getInitialState({ selectedId: null });

export const reducer = createReducer(initialState,
  on(BooksApi.loadedAll, (state, { books })  => adapter.setAll(books, state)),
  on(BooksApi.created,   (state, { book })   => adapter.addOne(book, state)),
  on(BooksApi.patched,   (state, { update }) => adapter.updateOne(update, state)), // { id, changes }
  on(BooksApi.deleted,   (state, { isbn })   => adapter.removeOne(isbn, state)),
);

// the read layer, for free
const { selectAll, selectEntities, selectTotal } = adapter.getSelectors();
export const selectAllBooks   = createSelector(selectBooksState, selectAll);
export const selectBookMap    = createSelector(selectBooksState, selectEntities);
export const selectBookCount  = createSelector(selectBooksState, selectTotal);

Interview questions

Selectors and the entity adapter are where Indian NgRx interviews get specific — service-company rounds test the API, product-company rounds test whether you understand memoization and state shape:

Beginner What is a selector in NgRx and why not just read state directly?

A selector is a pure function that projects a slice of store state. Reading state directly couples every component to the exact state shape, so a rename breaks the whole app; a selector is a single point of change, is independently unit-testable, is reusable across components, and — unlike an inline map — is memoized so the projection does not re-run on every emission.

Beginner createFeatureSelector vs createSelector?

createFeatureSelector<T>('key') returns the top-level slice registered under that feature key — it is the entry point. createSelector(...inputSelectors, projector) derives a new value from one or more existing selectors and memoizes the result. In practice you write one feature selector per feature and many createSelectors on top of it.

Beginner How do you consume a selector in a standalone component today?

Inject the store with private store = inject(Store), then either store.selectSignal(selectX) for a Signal you read as x() in the template, or store.select(selectX) for an Observable you render with the async pipe. Signals are the current default because they need no unsubscribe and compose with computed.

Beginner What is @ngrx/entity and what problem does it solve?

A small library for managing collections in a normalized shape. It supplies EntityState<T> (an ids array plus an entities dictionary), an adapter that generates immutable add/update/remove/upsert helpers for your reducer, and ready-made selectors. It removes the repetitive, error-prone array manipulation from reducers.

Beginner What does EntityState look like, and why keep both ids and entities?

{ ids: string[] | number[]; entities: { [id]: T } }. The dictionary gives O(1) lookup and a single source of truth per record; the ids array preserves order (including any sortComparer order), which a plain object cannot guarantee. selectAll simply maps ids over the dictionary to rebuild the ordered array for the view.

Intermediate How does memoization in createSelector actually work?

The selector caches its last input arguments and its last output. On each call it compares the new inputs to the cached ones with a reference check; if all match, it returns the cached output without invoking the projector. Because the returned reference is also unchanged, downstream selectors short-circuit too and OnPush components skip re-rendering. Memoized selectors also expose release() to clear that cache when needed.

Intermediate Your component does not update after a state change even though the reducer ran. What is the usual cause?

State was mutated instead of replaced — state.items.push(item) or assigning to an existing object property. The array or object reference is unchanged, so the selector's reference check says "same input" and returns the cached value. Fix it by returning new references from the reducer, and turn on NgRx runtime checks (strictStateImmutability, strictActionImmutability) in development so mutation throws instead of failing silently.

Intermediate What is a view-model selector and why is it preferred over combining several selectors in the component?

One selector that composes all the state a screen needs into a single object, consumed with one selectSignal or one async pipe. It keeps derivation logic out of the template (so it runs on state change, not on every change-detection pass), removes multi-stream coordination bugs, makes the screen's data contract explicit, and is far easier to test — you feed it a state object and assert the view model.

Intermediate Which adapter methods would you use for "replace the list from the server", "save an edited row", and "toggle one field"?

setAll(books, state) replaces the whole collection after a load. updateOne({ id, changes }, state) applies a partial update to one record — upsertOne if it may not exist yet. mapOne updates one entity via a map function when the new value depends on the current one. removeOne/removeMany (which also accepts a predicate) handle deletion.

Intermediate How do you configure selectId and sortComparer, and what do they cost?

createEntityAdapter<Book>({ selectId: b => b.isbn, sortComparer: (a, b) => a.title.localeCompare(b.title) }). selectId is only required when the key is not named id. A sortComparer keeps ids permanently ordered, which is convenient but re-sorts on every write; pass false when the API already returns the order you want or when the view sorts, since that is measurably faster for large collections.

Pro Selectors with arguments: how do you write one, and what is the memoization trap?

Either pass runtime data through props into the projector, or use a selector factory — a function returning createSelector(...). The trap is that a factory creates a brand-new memoized instance on every invocation, so calling it inside a template or on every emission gives you a cache of size one that is thrown away each time — the memoization benefit disappears and you may leak instances. Create the factory result once in a field, or prefer composing the argument into state or into a parent view-model selector.

Pro Where should filtering, sorting and pagination of a large list live — reducer, selector, or component?

Keep the raw normalized collection plus the filter criteria in state; derive the visible list in a memoized selector. The reducer should not store derived data (it goes stale and duplicates truth), and the component should not compute it inline (it re-runs on every change detection). If the derivation is genuinely expensive, split it into layered selectors so each memoizes independently, and if the dataset is large enough that the client should not hold it at all, move filtering and paging to the server and store only the current page.

Pro How do you unit-test selectors, and what makes them cheap to test?

They are pure functions, so no TestBed and no store are needed: call the selector with a handcrafted state object and assert the result. For composed selectors, use selector.projector(...inputValues) to test the projection logic in isolation without building the whole state tree — this is the standard trick and it keeps tests immune to state-shape refactors. In component tests, override values with provideMockStore({ selectors: [{ selector: selectX, value: … }] }) or store.overrideSelector, remembering to call refreshState() after changing them.
