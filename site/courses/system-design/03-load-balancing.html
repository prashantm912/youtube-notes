Module: Load Balancing

A load balancer is the component that turns N unreliable machines into one reliable-looking endpoint. Every design decision in it reduces to two questions: what can it see, and how does it decide?

Knowledge Library → Courses → System Design track → Load Balancing

What this module covers

Horizontal scaling only pays off if something in front of the fleet distributes work and notices when a machine stops being useful. That something is the load balancer, and it sits on the critical path of every request you serve — which makes its visibility (layer 4 or layer 7), its failure detection (health checks and ejection) and its selection algorithm three of the highest-leverage choices in a system design.

This module is deliberately vendor-neutral: the theory, the tradeoffs and the failure behaviour, illustrated with nginx, HAProxy and Envoy because their documentation is the clearest public specification of how these things actually work. Managed-cloud specifics live elsewhere in the course — the AWS track covers ALB and NLB configuration in Load Balancing and Scaling. Here you learn the concepts that let you evaluate any of them.

Topics

What a load balancer actually buys you (and what it cannot)

Clients want one address. Operations wants many machines: to add capacity, to survive a dead instance, to deploy without downtime. The load balancer reconciles those by publishing a single virtual endpoint and spreading requests across a pool of backends behind it, removing failed members and adding new ones without the client noticing. Everything else it does — TLS termination, routing, retries, rate limiting, header rewriting — is opportunistic, because it is already the one place every request passes through.

Be honest about its limits in an interview. A load balancer distributes load, it does not create capacity: if the fleet is saturated, perfect distribution just spreads the overload evenly, and the correct response is shedding or queueing, not a better algorithm. It also becomes a single point of failure the moment you have exactly one, so real deployments run a redundant pair sharing a virtual IP, or push the decision to DNS or anycast so no single box is on every path. And it can only balance what it is allowed to see: a long-lived connection (WebSocket, gRPC stream, database pool) is assigned once and then stays put, so a connection-level balancer in front of persistent connections will drift into imbalance no matter how good its algorithm is.

Reverse proxies, and where the balancing decision lives

A reverse proxy accepts a client connection, decides what to do with it, and opens its own connection to a backend on the client's behalf. Load balancing is one thing a reverse proxy can do; caching, compression, TLS termination, authentication and request rewriting are others. nginx, HAProxy and Envoy are the three reference implementations you should be able to name and distinguish: nginx grew from a web server into a proxy, HAProxy was purpose-built for proxying and load balancing, and Envoy was designed for dynamic environments where the backend set changes constantly and is pushed in over an API rather than written into a config file. An API gateway is the same machinery again with product concerns bolted on (keys, quotas, request transformation, developer portal) — in an interview, say that a gateway is a superset of a reverse proxy, not a different thing.

The more interesting question is where the decision is made. A middle proxy is easy to reason about and easy to operate, but it adds a network hop and concentrates every request into one tier. Client-side load balancing moves the decision into the caller's library — the client learns the backend list from service discovery and picks a member itself, which removes the hop entirely and is the normal arrangement for gRPC and for Spring Cloud LoadBalancer. Its costs are that every client language needs the logic, and that rolling out a policy change means redeploying every caller. A service mesh splits the difference: the sidecar proxy next to each pod does exactly what the client-side library would do, so the load balancing is per-caller and hop-free-ish, but the policy is configured centrally and updated without touching application code.

Layer 4 versus layer 7: what the balancer is allowed to see

A layer 4 balancer works with transport-level information only: source and destination IP addresses, ports, and the state of the TCP connection. It picks a backend when the connection is established and then forwards packets for the life of that connection without ever looking inside them. Because it never parses the payload it is fast, cheap in CPU and memory, and completely protocol-agnostic — the same box balances HTTP, MQTT, SMTP, a Postgres port or a game protocol. The price is that it is blind: it cannot route on a URL path, cannot read a header, cannot retry a failed request (it only knows connections, and the request is already gone), and cannot terminate TLS.

A layer 7 balancer terminates the client connection, parses the application protocol, and makes a per-request decision. That unlocks the features people actually want: route /api to one pool and /static to another, split traffic by header or cookie for canary releases, retry an idempotent request on a different backend when the first one fails, terminate TLS once at the edge, compress, cache, inject request ids for tracing, and multiplex many client requests over a small pool of keep-alive connections to the backends. All of that costs CPU per request and memory per buffered request, and it means the balancer must understand your protocol — an L7 proxy that speaks HTTP/1.1 and HTTP/2 does nothing useful for a binary protocol it has never heard of.

Two forwarding mechanics are worth naming. Ordinary L4 proxying is connection-oriented: the balancer keeps a connection-tracking table so every packet of a flow lands on the same backend, and both request and response traverse the balancer, which means return traffic consumes its bandwidth. Direct server return sends the client's packets through the balancer but lets the backend answer the client directly, bypassing the balancer on the response path — a large win when responses dwarf requests (video, file downloads), at the cost of fiddly network setup and no visibility into responses. Google's Maglev and Cloudflare's Unimog are production L4 balancers built on exactly these ideas, and both are excellent reading precisely because they are honest about the constraints.

# L4: forward TCP, know nothing about the payload
stream {
  upstream db { server 10.0.1.10:5432; server 10.0.1.11:5432; }
  server { listen 5432; proxy_pass db; }
}

# L7: parse HTTP, so path routing and per-request retries become possible
http {
  upstream api    { server 10.0.2.10:8080; server 10.0.2.11:8080; }
  upstream static { server 10.0.3.10:8080; }
  server {
    listen 443 ssl;                       # TLS terminated here
    location /api/   { proxy_pass http://api; }
    location /static/ { proxy_pass http://static; }
  }
}

Health checks: active, passive, and what a good check actually tests

A load balancer's second job is knowing which backends are worth sending traffic to, and this is where load balancers most often cause the outage rather than prevent it. Active checks are the balancer probing each backend on a schedule — a TCP connect, or an HTTP request to a known path, with a required status code and optionally a required body. They detect a dead backend even when no user traffic is flowing, at the cost of probe load and a detection delay bounded by the interval multiplied by the unhealthy threshold. Passive checks watch real traffic instead: nginx open source does this with max_fails and fail_timeout on each upstream server, and it costs nothing extra, but it can only learn from requests that have already failed for a user. Serious deployments run both.

Design the check itself with care, because the two obvious choices are both wrong. A check that only opens a TCP socket, or returns a static 200 OK from the web framework, will happily report health while the process cannot reach its database — a liveness check so shallow it detects almost nothing. The opposite mistake is worse: a deep check that verifies every dependency means one shared dependency wobbling marks every backend unhealthy simultaneously, and the balancer removes the entire pool for a fault that was degrading, not fatal. The usual resolution is layered checks — a shallow local check drives whether the process should be restarted, a slightly deeper check drives whether this instance should receive traffic, and dependency failures are reported as degraded rather than down. Add a fail-open rule so that when zero backends pass, the balancer sends traffic to all of them anyway: a partially working service beats a guaranteed total outage. Also give backends a graceful drain (the "lame duck" state) so a shutting-down instance fails its check and finishes in-flight requests before the process exits.

upstream api {
  server 10.0.2.10:8080 max_fails=3 fail_timeout=10s;   # passive: learn from real traffic
  server 10.0.2.11:8080 max_fails=3 fail_timeout=10s;
  server 10.0.2.12:8080 backup;                          # only used if the others are out
}
server {
  location / {
    proxy_pass http://api;
    health_check uri=/healthz interval=5s fails=3 passes=2;   # active probe (NGINX Plus)
  }
}

Outlier detection and ejection: removing the sick, not the pool

Health checks answer a binary question, but the machine that ruins your latency is rarely down — it is the one node with a failing disk, a stuck garbage collector, a noisy neighbour or a half-broken network path that still answers every probe. Outlier detection is passive statistics over live traffic: the proxy counts consecutive 5xx responses, consecutive gateway failures (connection errors and timeouts), or compares each host's success rate against the fleet mean, and temporarily ejects any host that stands out. Ejection is time-boxed with exponential extension — a first ejection lasts a base interval, and a host that misbehaves again on return is ejected for longer — so a transiently sick node heals itself back into the pool without human intervention.

The safety valve is the part people forget, and it is the part interviewers probe. Ejection must be capped: Envoy's max_ejection_percent limits what fraction of the pool may be ejected at once (the default is deliberately conservative), because a correlated fault — a bad deploy, a poisoned config, a downstream dependency failing — makes every host look like an outlier, and uncapped ejection would remove the whole fleet in seconds. The complementary guard is the panic threshold: if the healthy fraction of hosts falls below a configured percentage, the balancer stops respecting health status altogether and load balances across all hosts, on the reasoning that the health signal has probably become the unreliable component. Both mechanisms encode the same principle — degraded service beats a self-inflicted total outage — and both are what you should reach for when an interviewer asks how you would stop your own load balancer from causing an incident.

outlier_detection:                       # Envoy cluster config
  consecutive_5xx: 5                     # eject after five consecutive 5xx
  consecutive_gateway_failure: 5         # connect errors / timeouts
  interval: 10s                          # analysis sweep
  base_ejection_time: 30s                # multiplied by the ejection count
  max_ejection_percent: 10               # NEVER eject more than a tenth of the pool
  success_rate_minimum_hosts: 5          # need a fleet before comparing to its mean

common_lb_config:
  healthy_panic_threshold: { value: 50 } # below 50% healthy, ignore health and use everyone

Selection algorithms: round robin, weighted, least connections, least time

Round robin walks the backend list in order. It is stateless, trivially cheap, and correct whenever two assumptions hold: every request costs roughly the same, and every server is roughly the same size. Break either assumption and it degrades — send a mix of 5 ms cache reads and 3-second report generations round robin and the servers that drew the expensive requests fall behind while their neighbours idle. Weighted round robin patches the second assumption by giving bigger machines a larger share, which is how you run a heterogeneous fleet or shift traffic gradually during a migration; it does nothing about variable request cost.

Least connections attacks the first assumption directly. Instead of predicting cost, it observes it: whichever backend currently has the fewest in-flight connections gets the next request, so a server stuck on slow work naturally stops receiving new work. This is the sensible default for anything with variable request cost or long-lived connections, and weighted variants exist for mixed fleets. Least response time (Envoy and NGINX Plus call it least time, HAProxy has similar behaviour) goes further and ranks by a blend of active connections and observed latency, which catches the node that is answering but answering slowly. The catch with all of these is state: the balancer must maintain accurate per-backend counters, which is fine in one process and increasingly wrong when you run several independent balancer instances that each see only their own share of the traffic. Finally, hash-based selection (source IP hash, or a hash of a cookie, header or URL) is not about balance at all — it is about affinity, deliberately sending the same key to the same backend so a local cache or in-memory session keeps working.

The power of two random choices

Least connections needs global state, and global state is exactly what you lose when you scale the load balancer tier out. Worse, several balancers each independently picking "the least loaded server" all pick the same server at the same instant and stampede it — the herd behaviour that makes naive least-connections dangerous in a distributed front end. Pure random selection has the opposite problem: no coordination needed, but the imbalance between the busiest and the average server grows as the fleet grows.

The fix is a classical result from Michael Mitzenmacher's work in the 1990s and it is beautifully cheap: pick two backends at random, compare only those two, and send the request to whichever has fewer in-flight requests. Choosing between two samples rather than one collapses the expected maximum load from something that grows roughly logarithmically in the fleet size to something that grows about as fast as the logarithm of a logarithm — in practical terms, almost all of the benefit of true least-connections, with no global view and no stampede, because two balancers rarely draw the same pair. That is why it is the default or recommended algorithm in modern distributed proxies: nginx ships it as random two least_conn, HAProxy has benchmarked it against its alternatives, and Envoy and Linkerd use variants of it as their standard policy. It is a very strong answer to "how would you load balance without a central coordinator?".

upstream api {
  random two least_conn;       # sample two backends, take the less busy one
  server 10.0.2.10:8080;
  server 10.0.2.11:8080;
  server 10.0.2.12:8080;
}

Consistent hashing: affinity that survives a changing fleet

Sometimes you do not want balance, you want stability: the same cache key on the same cache node, the same user's session on the same server, the same shard key on the same database. The obvious implementation is hash(key) % N, and it is a trap. Change N — one node dies, one node is added — and nearly every key maps somewhere new: going from 4 nodes to 5 remaps around 80% of the key space. For a cache that is a mass eviction event and a thundering herd onto the origin at the worst possible moment; for a shard map it is a data migration you did not schedule.

Consistent hashing fixes the remapping. Hash the output space into a fixed ring (say, the integers modulo 2 to the power 32, wrapped into a circle), place each node at one or more positions on that ring by hashing its identity, and map each key to the first node encountered walking clockwise from the key's own hash. Now removing a node only moves the keys that sat between it and its predecessor — about 1/N of the key space — and adding a node only steals a comparable slice from its clockwise neighbour. Everything else stays exactly where it was. The refinement that makes it usable is virtual nodes: one position per node produces wildly uneven arc lengths, so each physical node is placed at a hundred or more hashed positions, which smooths the distribution and, as a bonus, lets a bigger machine claim proportionally more positions. Variants go further — Google's bounded-load version caps how much any one node may receive before overflow spills to the next, and Maglev's table-based scheme trades a little disruption for very fast lookup.

Know where it shows up, because it recurs across this whole track: memcached and Redis client-side sharding, Dynamo-style partitioning and its descendants (Cassandra, Riak), sticky routing to a stateful backend, and consistent-hash load balancing policies in Envoy and nginx (hash ... consistent). And know the failure mode: consistent hashing distributes key space evenly, not load — a single hot key still lands on exactly one node, which is why bounded loads, key splitting or a small local cache in front are the standard follow-up answers.

Naive modulo:  node = hash(key) % N        # N changes -> nearly every key moves

Ring (clockwise walk), each node placed at many virtual positions:

   0 ......... A1 ... B1 ... A2 ... C1 ... B2 ... A3 ... C2 ......... 2^32
                ^      ^
                |      key k hashes here -> walks clockwise -> lands on B1

   Remove node B  ->  only keys in B's arcs move, to the next node clockwise
   Add node D     ->  D takes one slice per virtual position, nothing else moves

Global load balancing: geo-DNS, anycast and cross-region failover

Everything above balances within one location. Across regions the problem changes, because you are now choosing which data centre a user should reach before a connection exists — and the only levers available that early are DNS and IP routing. DNS-based global balancing answers the same hostname with different addresses depending on the resolver's location or an explicit policy: geo-steering by continent or country, latency-based steering using measured round-trip times rather than raw geography (nearest on a map is not always fastest on a network), weighted steering for gradual regional migrations, and failover steering that stops handing out a region's address once its health checks fail.

Anycast takes the other route: announce the same IP prefix from many locations over BGP and let internet routing deliver each packet to the topologically closest announcement. It is how public DNS resolvers and CDN edges work, and failover is nearly instantaneous because withdrawing a route reroutes traffic without any client-side change. Its limitation is that BGP is not application-aware — routing can shift mid-session, which is a real issue for long TCP connections, and you cannot express "send 10% of traffic to the new region" the way you can with weighted DNS.

The honest caveat that earns marks in an interview: DNS-level balancing is coarse. Answers are cached by resolvers, operating systems and browsers for the length of the TTL and often longer, because plenty of clients ignore short TTLs entirely; you are steering resolvers, not users, so a single corporate or ISP resolver can represent a huge population; and DNS has no idea how loaded a backend is. Shortening the TTL to seconds increases query volume and still does not guarantee prompt failover. The workable pattern is layered: DNS or anycast chooses the region, a regional layer 4 or layer 7 balancer chooses the machine, and the fast, precise failure handling happens at that second layer rather than in DNS.

Interview questions

Load balancing is asked in almost every Indian system design round, from service-company screening to product-company design loops. L4-versus-L7 and consistent hashing are effectively guaranteed; the rest separate candidates who have operated a balancer from candidates who have only drawn one on a whiteboard:

Beginner What does a load balancer do, and why do you need one?

It presents one endpoint to clients and spreads requests across a pool of backend instances, removing failed members and admitting new ones without the client knowing. That gives you horizontal scale, tolerance of individual machine failure, and zero-downtime deploys. It does not create capacity — if the whole fleet is saturated, the answer is more capacity or load shedding, not a smarter algorithm.

Beginner Difference between a load balancer and a reverse proxy?

They overlap rather than compete. A reverse proxy is any server that accepts client connections and forwards them to backends on the client's behalf; load balancing is one of the jobs it can do, alongside TLS termination, caching, compression and authentication. Every layer 7 load balancer is a reverse proxy; a reverse proxy in front of a single backend is not load balancing anything. An API gateway is the same machinery with product concerns (keys, quotas, transformations) added.

Beginner Explain L4 versus L7 load balancing.

L4 works at the transport layer: it sees IPs, ports and TCP state, picks a backend when the connection opens, and forwards packets without inspecting them — fast, cheap, protocol-agnostic, but blind. L7 terminates the connection and parses the application protocol, so it can route on path, header or cookie, terminate TLS, retry an individual request on another backend, compress and cache — at a real CPU and memory cost per request, and only for protocols it understands. Rule of thumb: L4 for raw throughput and non-HTTP protocols, L7 when routing decisions depend on request content.

Beginner When would round robin be the wrong choice?

When requests are not uniform in cost, or servers are not uniform in capacity, or connections are long-lived. Round robin assumes each turn costs the same; mix cheap reads with expensive report generation and some backends fall behind while others idle. Weighted round robin handles heterogeneous servers; least connections or power-of-two-choices handles variable request cost.

Intermediate Active versus passive health checks — what does each miss?

Active checks probe on a schedule, so they detect a dead backend even with no user traffic, but they cost probe load and detect only after interval multiplied by the unhealthy threshold. Passive checks observe real traffic (nginx max_fails and fail_timeout), which is free and reflects what users actually experience, but it only learns from requests that already failed, and an idle backend is never evaluated. Production deployments run both.

Intermediate Your health check verifies the database connection, and one database blip takes every backend out of the pool. What went wrong?

The check was too deep for the decision it drives. A shared dependency makes the check fail on every instance simultaneously, so a degradation becomes a total outage caused by your own balancer. Fix it by layering: a shallow local check for "is this process alive", a slightly deeper one for "should this instance take traffic", and report dependency problems as degraded rather than down. Add fail-open behaviour so that when no backend passes, traffic goes to all of them anyway — and cap how much of the pool may be removed at once.

Intermediate What is outlier detection, and why is there a cap on ejection?

Outlier detection ejects hosts that look statistically worse than their peers — consecutive 5xx, consecutive gateway failures, or a success rate far below the fleet mean — for a base ejection time that extends on repeat offences. The cap (Envoy's max_ejection_percent) exists because a correlated fault such as a bad deploy or a failing dependency makes every host an outlier, and uncapped ejection would drain the entire pool in seconds. The panic threshold is the same idea from the other side: below a configured healthy fraction, the balancer ignores health status and uses every host, on the basis that the health signal is now the untrustworthy part.

Intermediate How do you keep a user pinned to one server, and what does it cost you?

Session affinity: hash the source IP, or issue and hash a sticky cookie (an L7 balancer can do the cookie; an L4 balancer only has the IP, which breaks behind carrier-grade NAT and corporate proxies where thousands of users share an address). The cost is that the fleet is no longer interchangeable — that server's failure loses those sessions, scaling out does not rebalance existing users, and deployments become disruptive. The better answer in most designs is to make the service stateless and push session state to Redis or a signed token, keeping affinity only as a cache-hit optimisation where losing it is harmless.

Intermediate Why does naive modulo hashing break when you add or remove a node?

Because the node index is a function of N. With hash(key) % N, changing N reshuffles almost the entire key space — moving from four nodes to five relocates roughly 80% of keys. For a cache that is a mass eviction plus a stampede onto the origin exactly when a node has just failed; for a shard map it is an unplanned data migration. Consistent hashing bounds the movement to roughly 1/N of keys.

Intermediate Explain consistent hashing and the role of virtual nodes.

Map the hash output onto a ring, place each node at hashed positions on that ring, and assign each key to the first node clockwise from the key's hash. Removing a node moves only the keys in its arcs to the next node clockwise; adding one takes a slice from its neighbour. Everything else is untouched. With one position per node the arcs are very uneven, so each physical node is given many virtual positions (typically 100 to 200) — that smooths distribution and lets a larger machine claim proportionally more positions. Uses: cache sharding, Dynamo-style partitioning, sticky routing, and consistent-hash policies in Envoy and nginx.

Pro Explain the power of two random choices and why it beats least connections in a distributed front end.

Pick two backends at random, compare only those two, and send the request to the less busy one. Sampling two instead of one drops the expected maximum load from roughly logarithmic in the fleet size to roughly log-log — nearly all the benefit of true least connections with no global state. It wins in a distributed front end precisely because several balancer instances cannot each maintain an accurate global view, and if they each pick "the least loaded server" they all pick the same one and stampede it. Two independent balancers rarely draw the same pair, so the herd behaviour disappears. nginx exposes it as random two least_conn; Envoy and Linkerd use variants as their default.

Pro Consistent hashing distributes keys evenly, yet one node is at 90% CPU. Explain and fix.

It distributes key space, not load. One extremely hot key — a celebrity profile, a flash-sale product — deterministically lands on one node, and by design consistent hashing keeps sending it there. Fixes: consistent hashing with bounded loads, which caps a node's share and spills overflow to the next node clockwise; splitting the hot key into several suffixed sub-keys replicated across nodes; a small local cache in front of the ring so hot reads never reach it; or replicating hot entries to several nodes and reading from any. Also verify it is genuinely a hot key and not a bad virtual-node count producing lopsided arcs.

Pro Design failover for a service running in Mumbai and Singapore. What are the limits of DNS-based balancing?

Layer it. DNS or anycast picks the region — geo or latency steering for normal traffic, health-check-driven failover steering to stop advertising a sick region — and a regional L4 or L7 balancer picks the machine, where fast and precise failure handling lives. DNS is coarse because answers are cached by resolvers, operating systems and browsers, often past the TTL, so failover is not prompt; you steer resolvers rather than users, so one ISP resolver can represent a huge population; and DNS knows nothing about backend load. Shortening the TTL raises query volume without guaranteeing timely failover. Anycast fails over faster because withdrawing a BGP route reroutes packets, but routing is not application-aware and can shift mid-session, which hurts long-lived TCP connections. Then answer the harder half: data replication lag, whether the second region is active-active or warm standby, and what your RPO and RTO actually are.

Pro Your service uses gRPC and one backend is taking almost all the traffic despite round robin. Why?

gRPC runs over HTTP/2 and multiplexes many requests onto one long-lived connection. A connection-level (L4) balancer assigns that connection once and then never revisits the decision, so all subsequent requests ride the same backend — and a client that opens one connection at startup pins itself for its lifetime. Fixes: use an L7 proxy that understands HTTP/2 and balances per request, or do client-side load balancing where the client resolves the backend list and spreads calls itself (the standard gRPC approach), or run a sidecar proxy that does the same. The same reasoning explains imbalance with WebSockets and database connection pools.
