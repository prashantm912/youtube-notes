Module: Rate Limiting

Every service has a throughput it can actually serve, and traffic does not care. Rate limiting is the policy that decides, before the work starts, whose requests get admitted — so that a scraper, a retry storm or an unexpectedly popular launch cannot take the system down for everyone.

Knowledge Library → Courses → System Design track → Rate Limiting

What this module covers

Rate limiting answers one question — may this request proceed right now? — and the interesting engineering is entirely in how you answer it cheaply, fairly and consistently across a fleet. The first half of this module covers the four algorithms every interview asks about, judged on the property that actually separates them: what each one does when a client sends a burst.

The second half covers everything that turns a working algorithm into a working system: enforcing one global limit when the limiter runs on fifty instances, the race conditions that make a naive shared counter wrong, what to key the limit on, tiered quotas and per-endpoint cost, and the response contract — 429, Retry-After, RateLimit-* — that decides whether clients back off politely or hammer you harder. It closes on the boundary between rate limiting and load shedding, which are often confused and are not the same tool.

Topics

Why rate limiting exists, and where it sits

Four separate motivations get bundled under one name, and being able to name them apart is worth marks. Abuse prevention: credential stuffing, scraping, enumeration of ids, spam sign-ups. Cost control: every request you serve costs CPU, egress, a third-party API call or an LLM token bill, and an unlimited free tier is an unlimited invoice. Fair sharing: in a multi-tenant system one noisy tenant will otherwise consume capacity that the other thousand tenants paid for. And above all overload protection: a service pushed past its saturation point does not degrade gracefully — queues grow, latency climbs, timeouts fire, clients retry, and the retries make it worse. A limit that rejects the marginal request in microseconds keeps the service inside the region where it still works.

Where the limit lives determines what it can see and what it can protect. At the edge (CDN or WAF) you stop volumetric abuse before it costs you any origin capacity, but the only signals available there are the IP and the URL. At the API gateway the authenticated principal is known, so this is where per-key quotas and plan tiers naturally sit, and where one policy covers every service behind it. Per-service (or per-endpoint) limits protect a specific scarce resource — the report generator, the search cluster, the payment provider whose contract caps you at a fixed rate — that a global gateway limit knows nothing about. Real systems use all three layers, with progressively narrower scope and progressively better information.

Fixed window counter — and the boundary burst that doubles your limit

The simplest algorithm: chop time into fixed windows (say one minute), keep one integer per client per window, increment on each request, reject when the counter exceeds the limit, and let the key expire when the window ends. One counter per active client, one atomic increment per request, no timestamps, no history. On Redis this is two commands and it is the reason fixed window is everywhere: it costs almost nothing.

Its flaw is the window boundary, and interviewers ask about it constantly. Suppose the limit is 100 requests per minute. A client sends 100 requests in the final second of one window and 100 more in the first second of the next. Both windows are individually legal — 100 each — but the server just absorbed 200 requests in a two-second span, twice the intended rate over the sliding minute that straddles the boundary. Worse, this is not an exotic adversarial case: clients that schedule work on minute boundaries produce it accidentally, and every client doing so synchronises into the same spike. Fixed window is also unfair inside a window — a client that spends its whole allowance in the first two seconds is blocked for the remaining fifty-eight while the server sits idle.

# Fixed window: one counter per client per window, expiring with the window.
# key = ratelimit:{api_key}:{floor(now / 60)}
INCR   ratelimit:acme:29384710      # returns the new count
EXPIRE ratelimit:acme:29384710 60 NX   # NX = only set a TTL if there isn't one

# Careful: INCR and EXPIRE are two round trips. If the process dies between them the
# key never expires and that client is throttled forever. Do both in one Lua script,
# or use a pipeline/transaction, so the counter and its TTL are created together.

Sliding window log and sliding window counter

The sliding window log fixes the boundary problem exactly. Store a timestamp for every accepted request in a sorted set per client; on each new request, drop entries older than the window, count what remains, and admit only if the count is under the limit. The window now genuinely slides with the clock, so no boundary exists to exploit and the answer is exact. The price is memory and CPU: you store one entry per request per client, so a client sending 10,000 requests a minute costs 10,000 timestamps — and rejected requests still cost you a trim operation. For a large public API this is the algorithm that quietly turns your rate limiter into your biggest Redis consumer.

The sliding window counter is the pragmatic middle ground and, in practice, the most commonly deployed accurate-enough option. Keep just two counters — the previous window's total and the current window's total — and weight the previous one by how much of it still overlaps the trailing window. With a limit of 100 per minute, 30 seconds into the current window, a previous count of 80 and a current count of 40, the estimate is 80 × 0.5 + 40 = 80, so the request is admitted. The estimate assumes traffic was spread evenly across the previous window, which is a small and bounded inaccuracy — Cloudflare reported the approximation misclassifying well under 1% of requests at their scale — in exchange for two integers per client instead of thousands.

// Sliding window counter: two integers per client, no per-request storage.
elapsed  = now - currentWindowStart            // seconds into the current window
overlap  = (windowSize - elapsed) / windowSize // fraction of the previous window still in view
estimate = previousWindowCount * overlap + currentWindowCount

if (estimate < limit) { currentWindowCount += 1; return ALLOW }
return DENY

Leaky bucket: a queue that drains at a constant rate

Leaky bucket inverts the framing. Instead of counting arrivals, model a bucket with a hole in the bottom: requests pour in at whatever rate clients send them, and leak out — get processed — at a fixed constant rate. If the bucket is full when a request arrives, that request is dropped. The defining property is that the output is perfectly smooth regardless of how spiky the input was, which is exactly what you want when the thing downstream is a fixed-capacity resource: a database with a known safe write rate, a third-party API with a contractual limit, an SMS gateway.

The trade-offs follow directly from that queue. Bursts are not rejected, they are delayed, so a client that sends a spike sees its later requests served with added latency — and if the bucket is deep, that latency can be large and hard to reason about. Requests can also sit in the bucket long after the caller has given up and timed out, so you end up doing work nobody is waiting for. When the bucket overflows you drop the newest arrivals even if they are the most valuable ones. NGINX's limit_req is the canonical implementation, with burst sizing the queue and nodelay switching between smoothing and immediate rejection.

Token bucket, the implementation sketch, and choosing between the four

Token bucket is the most widely deployed algorithm, and the reason is that it models real traffic honestly. A bucket holds up to capacity tokens and refills at a steady rate; each request removes a token, and a request that finds the bucket empty is rejected. Capacity and refill rate are two independent knobs: the refill rate sets the sustained throughput you are willing to serve, and the capacity sets how large a burst you will tolerate from a client that has been idle. That is precisely the behaviour real clients need — a mobile app that syncs ten resources on launch and then goes quiet is not abusive, and an algorithm that forces perfectly even spacing punishes it for no reason.

Implementations almost never run a background refill timer, because one timer per client does not scale. Instead they refill lazily: store the token count and the timestamp of the last update, and on each request compute how many tokens have accrued since. That makes the whole limiter two numbers per client, updatable in one atomic operation — which is also what makes it easy to move into Redis. It generalises nicely too: charge a heavy endpoint several tokens instead of one, and you have cost-weighted limiting for free. Spring Cloud Gateway's RequestRateLimiter exposes exactly this shape as replenishRate, burstCapacity and requestedTokens.

// Token bucket with lazy refill: two numbers per client, no timers.
allow(now, cost = 1):
    elapsed = now - lastRefill                       // seconds
    tokens  = min(capacity, tokens + elapsed * refillPerSecond)
    lastRefill = now

    if (tokens >= cost):
        tokens -= cost
        return ALLOW
    // tell the caller exactly how long until the next token is available
    return DENY(retryAfterSeconds = (cost - tokens) / refillPerSecond)

Distributed rate limiting: one limit across N instances

Every algorithm above assumes one limiter holding one piece of state. Deploy it in-process and the limit silently multiplies: ten pods each permitting 100 requests per second permit 1000 at the provider, and autoscaling makes the effective limit a function of your current replica count — which is not a limit at all. This is the single most common follow-up in a "design a distributed rate limiter" interview, and the answer is always some position on a consistency-versus-latency spectrum.

The default answer is a shared store: Redis holding the counter or bucket, keyed by client. The correctness trap is doing it as read-modify-write from the application — GET, compare, SET — because two instances can read the same value concurrently and both decide there is room, so the limit leaks under exactly the concurrency you built it for. Use atomic server-side operations (INCR is atomic and does the whole job for fixed window) or, for anything with more logic — token refill, window weighting, conditional TTLs — put the whole decision in a Lua script, which Redis executes atomically as a single unit. GitHub's own limiter is a Lua script over a sharded, replicated Redis, precisely so that read and write cannot interleave.

Two alternatives trade accuracy for throughput. Sticky routing — hashing the client key at the load balancer so a given client always lands on the same instance — makes local in-memory state correct again with zero coordination, but it re-introduces hot spots and breaks the moment instances scale or restart. Local limiting with periodic reconciliation — each instance enforces its own share and asynchronously syncs counts every few hundred milliseconds — removes the per-request network hop entirely at the cost of briefly overshooting the limit; this is how limiters at CDN scale are built, and it is the honest answer when the limiter itself must handle millions of requests per second. State the trade explicitly in an interview: exact enforcement costs a network round trip on every request, and for a limiter that is often too expensive.

-- Atomic fixed-window limiter as a Redis Lua script: count and TTL set together,
-- executed as one unit so no other client can interleave a read between them.
-- KEYS[1] = ratelimit:{client}:{window}   ARGV[1] = limit   ARGV[2] = window seconds
local count = redis.call('INCR', KEYS[1])
if count == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[2])
end
if count > tonumber(ARGV[1]) then
  return {0, redis.call('TTL', KEYS[1])}    -- denied, plus seconds until reset
end
return {1, tonumber(ARGV[1]) - count}       -- allowed, plus remaining quota

What to key on: identity, tiered quotas and cost weighting

The key you choose is the fairness policy. An API key or client id is the best key for machine traffic: it is stable, it maps to a contract, and it survives network changes. A user id is right for authenticated end-user traffic, because it follows the person across devices and networks. IP address is the only key available for unauthenticated traffic — login, sign-up, password reset — and it is genuinely useful there, but it is a poor fairness key on its own: behind corporate NAT, a university network, or carrier-grade NAT (CGNAT, which is how most mobile networks in India allocate addresses) thousands of unrelated users share one address, so a limit tuned for a person throttles a whole city. IPv6 flips the problem: a single subscriber may hold a huge address block and simply rotate. The usual compromise is a layered key — a strict per-account limit plus a looser per-IP limit as a backstop, and per-IP-prefix rather than per-address for IPv6.

Two refinements make quotas match reality. Tiering: free, paid and internal callers get different limits from the same policy engine, with the tier resolved from the authenticated principal — this is what AWS API Gateway usage plans and Stripe's per-mode limits do, and it turns the limiter into a product feature rather than only a defence. Cost weighting: not all requests are equal, so charge them unequally. A point lookup costs one token; a report export, a full-text search across a year of data, or an LLM completion costs many. GitHub's GraphQL API scores each query's cost before running it, which is the clean answer to the classic follow-up "how do you rate limit an endpoint where one request can be a thousand times more expensive than another?" — you stop counting requests and start counting work.

The client contract: 429, Retry-After and the RateLimit headers

A limiter that just drops traffic teaches clients nothing, and an uninformed client retries immediately — converting your rejection into more load than the original request. The contract is what makes rate limiting cooperative. Reject with 429 Too Many Requests (RFC 6585), never a bare connection reset and never 503, which means something different and invites different retry behaviour. Include Retry-After with the number of seconds until capacity exists — your token bucket already computes this exactly — so a well-behaved client sleeps for precisely the right interval instead of guessing.

Better still, tell clients where they stand before they hit the wall. The IETF RateLimit header fields draft standardises what vendors have shipped for years in incompatible forms: the remaining quota, the limit, and when the window resets, returned on every response rather than only on rejections. A client that can see it has 5 calls left out of 5000 can slow itself down; a client that only learns on rejection cannot. Two production details: add jitter to any client-side retry so a thousand clients told to wait 30 seconds do not all return in the same millisecond, and make sure your 429 path is genuinely cheap — if rejecting costs a database lookup, a determined caller can exhaust you with requests you are refusing.

HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit-Limit: 5000
RateLimit-Remaining: 0
RateLimit-Reset: 30
Content-Type: application/problem+json

{"type":"about:blank","title":"Too Many Requests",
 "detail":"Quota of 5000 requests per hour exhausted for key acme-prod."}

Rate limiting, load shedding, backpressure and admission control

These four are related and are routinely confused, so hold the distinction firmly. Rate limiting is a policy limit: a number you chose in advance, tied to an identity or a contract, enforced whether or not the system is currently under stress. Load shedding is a survival response: it looks at live signals — queue depth, latency, concurrency, CPU — and drops the least valuable work to stay alive, regardless of whose quota is intact. A service can be shedding load while nobody has exceeded their rate limit, and it can be rate limiting a client while running at 5% utilisation. The Amazon Builders' Library makes the key point that shedding must be paired with a fast rejection path and with prioritisation, so that health checks and high-criticality traffic survive when everything else is dropped.

Backpressure is the third idea: rather than dropping work, propagate the "slow down" signal upstream so the producer stops producing — bounded queues that block, TCP windows, reactive-stream request counts, consumer lag driving a slower fetch. It preserves work instead of discarding it, but it only functions when the producer can actually be slowed, which is why it fits internal pipelines better than public APIs where the "producer" is the internet. Admission control is the umbrella: the decision, made at entry, about which work to let in at all — with rate limits, shedding thresholds and concurrency limits as its instruments. On the client side, the counterpart to all of this is the circuit breaker, which stops a caller from sending requests it can predict will fail; see the Microservices resilience module for the state machine, retry budgets and the jitter that keeps backoff from synchronising. A complete design mentions both halves: the server limits and sheds, the client backs off and breaks the circuit.

Interview questions

Rate limiting is one of the highest-frequency system design rounds in Indian product and service companies — it is short enough to fit a 45-minute slot and deep enough to separate candidates, so the algorithm comparison and the distributed follow-up come up again and again:

Beginner What is rate limiting and why does a service need it?

A policy that caps how many requests a given client may make in a given period, enforced before the work starts. Four reasons: preventing abuse (scraping, credential stuffing, spam), controlling cost, sharing capacity fairly between tenants, and above all protecting the service from overload — past its saturation point a service degrades non-linearly, and rejecting the marginal request cheaply keeps it in the region where it still works.

Beginner Name the common rate limiting algorithms.

Fixed window counter, sliding window log, sliding window counter, leaky bucket and token bucket. Fixed window is cheapest and least accurate; sliding window log is exact but memory-hungry; sliding window counter approximates the log with two counters; leaky bucket smooths output to a constant rate by queueing; token bucket allows controlled bursts and is the usual default.

Beginner Which HTTP status code do you return, and what do you send with it?

429 Too Many Requests, defined in RFC 6585. Send Retry-After with the seconds until capacity exists, and ideally the RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset fields from the IETF draft on every response so clients can self-throttle before they get rejected. Do not use 503 — it means the server is unavailable, which is a different condition and triggers different client retry logic.

Beginner Where in the architecture would you place the rate limiter?

Usually all three layers, narrowing as you go in. At the edge or WAF to absorb volumetric abuse before it costs origin capacity, though it only knows IP and URL. At the API gateway, where the authenticated principal is known, so per-key quotas and plan tiers live there and one policy covers every service behind it. Per-service or per-endpoint for a specific scarce resource — a report generator, a third-party API with a contractual cap — that the gateway knows nothing about.

Intermediate Explain the fixed window boundary problem with a concrete example.

With a limit of 100 requests per minute, a client sends 100 in the last second of one window and 100 in the first second of the next. Each window is individually legal, but the server absorbed 200 requests in two seconds — double the intended rate over the sliding minute that straddles the boundary. It is not only adversarial: clients scheduled on minute boundaries produce it accidentally and synchronise with each other. Fix it with a sliding window log (exact) or a sliding window counter (weighted approximation).

Intermediate Token bucket versus leaky bucket — when would you pick each?

Token bucket refills tokens at a steady rate up to a capacity, so an idle client can spend a burst and then settles to the sustained rate; excess requests are rejected immediately. Leaky bucket queues arrivals and drains them at a fixed rate, so the output is perfectly smooth and bursts become latency rather than errors. Pick token bucket for public APIs, where legitimate clients are naturally bursty and fast rejection is kinder than unbounded queueing. Pick leaky bucket when a downstream requires a strictly constant feed rate — a payment provider's contracted rate, a write-limited database.

Intermediate How does the sliding window counter work, and how accurate is it?

Keep only the previous window's count and the current window's count, and weight the previous one by the fraction of it still inside the trailing window: estimate = prev × overlap + current. With a limit of 100 per minute, 30 seconds in, a previous count of 80 and a current count of 40, the estimate is 80. It assumes the previous window's traffic was evenly distributed, so it can be slightly off in either direction, but the error is bounded and small — Cloudflare reported well under 1% of requests misclassified at their scale — for two integers per client instead of one timestamp per request.

Intermediate Why is rate limiting by IP address alone a bad idea?

Because IP is not identity. Behind corporate NAT, campus networks and especially carrier-grade NAT — how most Indian mobile networks allocate addresses — thousands of unrelated users share one public IP, so a per-person limit throttles a whole population. In the other direction, IPv6 gives a single subscriber a large block to rotate through, and attackers rent proxy pools. Use IP as a backstop layer for unauthenticated endpoints (login, sign-up, OTP), key the real limit on API key or user id, and limit per IPv6 prefix rather than per address.

Intermediate How do you rate limit when one request can be far more expensive than another?

Stop counting requests and start counting work: assign each endpoint a token cost and charge that many tokens, which token bucket supports natively. A point lookup costs one, a search or export or LLM call costs many. For query languages where cost is not known from the route, score the request before executing it — GitHub's GraphQL API computes a query's point cost up front and rejects it against a points budget. Report the cost in the response headers so clients can budget too.

Pro Design a distributed rate limiter for an API served by fifty instances.

Start by naming the problem: per-instance state means the effective limit is the configured limit multiplied by the replica count, and autoscaling makes it non-deterministic. Then walk the options. Shared store — Redis holding a token bucket or window counter per key, with the whole decision in a Lua script so it is atomic; simple, exact, but a network hop on every request and Redis becomes an availability dependency, so decide the fail-open versus fail-closed policy explicitly. Sticky routing — hash the client key at the load balancer so a client always reaches the same limiter; zero coordination, but hot spots and breakage on scaling events. Local limiting with asynchronous reconciliation — each instance enforces a share and gossips counts every few hundred milliseconds; highest throughput, brief overshoot, the right answer at CDN scale. Finish with the response contract, the key design (API key with an IP backstop), tiering and the observability you would add.

Pro What race condition breaks a naive Redis-backed limiter, and how do you fix it?

Read-modify-write from the application: two instances both GET the counter, both see room, both SET, and the limit leaks under exactly the concurrency it exists to control. Similarly, INCR followed by a separate EXPIRE can leave a key with no TTL if the process dies in between, throttling that client permanently. Fix by making the whole decision atomic: use a single atomic command where one suffices (INCR), or move the entire read-compute-write into a Lua script, which Redis runs as one indivisible unit. Redis transactions or WATCH with optimistic retry also work but are clumsier for this shape.

Pro Your Redis rate limiter cluster goes down. What should the service do?

A deliberate, documented choice. Fail open — admit everything — keeps the product working but removes the protection at the moment overload is most likely, so it is only safe if a separate load-shedding layer still guards the service. Fail closed — reject everything — protects the backend but converts a limiter outage into a total outage. The usual production answer is fail open on the shared limiter while falling back to a conservative per-instance local limit, so you keep serving with a coarser guarantee, plus a circuit breaker on the Redis call so a slow store does not add its latency to every request.

Pro Distinguish rate limiting from load shedding, backpressure and admission control.

Rate limiting is a policy limit chosen in advance and tied to an identity or contract; it applies whether or not the system is stressed. Load shedding is a survival response driven by live signals — queue depth, latency, concurrency — that drops the least valuable work regardless of whose quota is intact, and needs prioritisation so critical traffic survives. Backpressure propagates a slow-down signal to the producer instead of discarding work, which preserves the work but only functions when the producer can be slowed, so it suits internal pipelines more than public APIs. Admission control is the umbrella term for deciding at entry what gets in, with all three as instruments. On the client side the counterpart is the circuit breaker plus jittered backoff.

Pro A rate limiter is deployed and abuse still gets through, while legitimate users get throttled. Diagnose.

Almost always a keying problem. Attackers rotate IPs or unauthenticated identifiers, so a limit keyed on something cheap to change is not a limit; legitimate users share NAT addresses, so the same key over-throttles them. Check whether the limit is keyed on the strongest identity available at that endpoint, whether unauthenticated endpoints have a separate, tighter policy, and whether limits are per-endpoint rather than one global number. Then check the window: a generous fixed window lets boundary bursts through. Finally check enforcement scope — a per-instance limiter behind a scaled deployment is enforcing many times the configured number.

Pro What would you monitor to know your rate limiter is set correctly?

The rejection rate broken down by key, tier and endpoint — a client sitting permanently at its ceiling is either abusive or under-provisioned, and you cannot tell without the breakdown. Track the ratio of rejected to admitted traffic over time, the distribution of per-key consumption (a long tail is healthy, a cliff is a mis-set limit), the latency and error rate of the limiter's own store, and whether rejections correlate with backend saturation — if you are shedding while the backend is idle, the limit is too tight. Alert on a sudden change in rejection rate in either direction, and always ship the limiter in observe-only mode first so you can see what it would have blocked before it blocks anything.
