Module: Database Scaling

Application servers are easy to add; the database is where the design gets expensive. This module walks the ladder of responses in the order a real team should climb it — and explains why sharding sits at the top, not the bottom.

Knowledge Library → Courses → System Design track → Database Scaling

What this module covers

In almost every system that grows, the database is the first component to become the bottleneck. Stateless web servers scale by adding a machine behind the load balancer; the database holds state, and state does not clone itself for free. Every technique in this module is a different answer to one question — how do you serve more reads, more writes, or more bytes than one machine can hold?

The module has two halves. The first is replication: keeping more than one copy of the data, which buys you read capacity and survivable failure, at the price of copies that disagree with each other for a while. The second is sharding: splitting the data so that no single machine holds all of it, which buys you write capacity and unbounded volume, at the price of losing the single-machine conveniences — joins, transactions and auto-increment ids — that you had been taking for granted.

This is vendor-neutral scaling architecture. Indexing, query plans and transaction isolation belong to the Databases track; managed-service mechanics such as RDS or Aurora belong to the Cloud track. Here we care about topology and tradeoffs.

Topics

Climb the ladder in order: what to do before you shard

There is a well-worn sequence of responses to a slow database, and it runs from cheap and reversible to expensive and permanent. First, tune the queries and the indexes — a missing index or an accidental full table scan is behind a startling share of "we need to scale the database" incidents, and the fix costs an afternoon. Second, add a cache in front of the hot read path, which removes load rather than adding capacity. Third, scale up: more RAM so the working set fits in the buffer pool, faster disks, more cores. Vertical scaling is unfashionable but it is a configuration change, and modern instances are enormous. Fourth, add read replicas if the workload is read-dominated. Fifth, split by function — move the reporting tables, the audit log, the session store off the primary. Only when all of that is exhausted do you shard.

Say this ladder out loud in an interview before you say the word "shard". Reaching for sharding first is the single most common mistake in system design rounds, because sharding is the only step on the list that is genuinely hard to undo: it changes your data model, your query layer, your operational runbooks and your migration story permanently. The right instinct is not "how do I shard this?" but "what is the cheapest rung that buys me the headroom I need for the next eighteen months?"

Leader–follower replication: synchronous, asynchronous, semi-synchronous

The default topology everywhere is leader–follower (also called primary–replica, or master–slave in older documentation). One node accepts writes and records them in an ordered log — the write-ahead log in PostgreSQL, the binary log in MySQL. Followers subscribe to that log and replay it. Because there is exactly one writer, there are no write conflicts to resolve, which is why this topology dominates: it is the arrangement that keeps a relational database recognisably relational.

The interesting choice is when the leader tells the client the write succeeded. With synchronous replication the leader waits for at least one follower to confirm the log record is durable before it acknowledges. Nothing is lost on failover — but every write now pays a network round trip, and worse, a single slow or wedged follower stalls the leader entirely, because the leader is blocked waiting for a confirmation that never comes. With asynchronous replication the leader acknowledges as soon as its own log is durable and ships records to followers in the background. Writes are fast and a dead follower cannot hurt the leader — but if the leader dies before the tail of the log has shipped, those writes are gone, permanently, and the new leader has no idea they ever existed.

Semi-synchronous is the compromise almost everyone actually runs: the leader waits for one follower (out of several) to acknowledge, then proceeds. You keep one guaranteed durable copy off-box without waiting for all of them, and implementations add a timeout that degrades the setup to asynchronous rather than freezing the leader when the last synchronous follower goes away. PostgreSQL expresses this through synchronous_standby_names and synchronous_commit; MySQL through its semisynchronous replication plugin. Know which mode your system is in before an incident, not during one.

# PostgreSQL: wait for any ONE of these standbys to confirm before ack
synchronous_standby_names = 'ANY 1 (replica_a, replica_b, replica_c)'
synchronous_commit = on          # off = async; remote_write / remote_apply = stricter

# MySQL semisynchronous: ack after one replica has the event,
# but fall back to async if none answers inside the timeout
rpl_semi_sync_source_enabled     = 1
rpl_semi_sync_source_wait_for_replica_count = 1
rpl_semi_sync_source_timeout     = 1000   # milliseconds before degrading to async

Read replicas and replication lag: read-your-writes and monotonic reads

Read replicas are the cheapest real scaling win available, because most applications read far more than they write. You point the reporting queries, the search pages and the dashboards at followers and leave the leader to handle writes. The catch has a name: replication lag. A follower is always some interval behind the leader — normally milliseconds, but seconds during a bulk import, and minutes if a long transaction or a vacuum blocks replay. Lag is not a bug to be eliminated; it is the price of asynchronous replication, and your application has to be written knowing it exists.

The user-visible symptom is famous. A user updates their profile, the write goes to the leader, the page reloads, the read lands on a replica that has not yet applied the change, and the user sees their old name. They conclude the save failed and do it again. This is the read-your-writes (read-after-write) consistency violation, and there are three standard fixes. Route reads to the leader for a short window after a write — simplest and most common; the application records "this session wrote at time T" and sends its reads to the leader for the next few seconds. Pin the session to one replica so that reads never travel backwards in time even if they are stale — that gives you monotonic reads, which prevents the even more confusing symptom where a value appears, disappears on refresh, then reappears. Or wait for the log position: capture the leader's log sequence number at write time, pass it along, and have the replica block until it has replayed at least that far. Precise, but it converts a fast read into a slow one.

Two operational notes worth having ready. Replicas do not help write throughput at all — every write still lands on the single leader and is replayed on every follower, so adding replicas actually increases total write work in the cluster. And you must monitor lag as a first-class metric with an alert, because a replica quietly falling an hour behind is indistinguishable from a healthy one until someone reads from it.

// Read-your-writes by write-window routing: the pragmatic default
onWrite(session) {
  leader.execute(stmt);
  session.leaderUntil = now() + STICKY_WINDOW;   // e.g. a few seconds
}

onRead(session) {
  if (now() < session.leaderUntil) return leader.query(stmt);   // fresh
  return replicaPool.pick(session).query(stmt);                 // sticky pick
}                                                               // = monotonic reads

Failover: promotion, split-brain and why fencing matters

A follower exists so that it can become the leader. Failover is the process: detect that the leader is gone, choose a replacement, promote it, and redirect every client and every remaining follower to the new leader. Each of those four steps has a way to go wrong, and the first is the hardest — you cannot distinguish a dead leader from a slow leader, or from a leader you have simply lost the network path to. That ambiguity is the root of everything difficult about failover.

Manual failover means a human decides, which is slower (minutes of downtime) but safe from false positives; it is a perfectly respectable choice for a system with a generous recovery-time objective. Automatic failover — Patroni over etcd or Consul for PostgreSQL, replica-set elections in MongoDB, Redis Sentinel — restores service in seconds but will occasionally promote on a false alarm, typically a network partition or a garbage-collection pause that made a healthy leader look dead. When that happens you get split-brain: two nodes both believe they are the leader, both accept writes, and the two divergent histories cannot be merged automatically. Someone ends up choosing which customers' writes to discard.

The defences are worth naming precisely. Promotion should require a quorum — a majority of nodes agreeing — so that the minority side of a partition can never elect anyone. Fencing (sometimes STONITH, "shoot the other node in the head") ensures the old leader is actively prevented from serving writes: revoke its storage lease, kill its network path, or have every write carry a monotonically increasing fencing token that the storage layer rejects if it is stale. A watchdog on the demoted node that halts it if it cannot reach the coordination store is the same idea implemented locally. And accept the fundamental tradeoff: failover always loses something. With synchronous replication you lose time (the leader stalls whenever a follower does); with asynchronous replication you lose data (the unshipped tail of the log). There is no configuration that loses neither.

Multi-leader and leaderless replication

Two other topologies exist, and you should be able to describe them and their hazards even if you never operate one. Multi-leader (multi-master) replication accepts writes at more than one node — typically one leader per data centre, so that each region gets local write latency and survives losing its link to the others. Offline-capable mobile clients are the same pattern in miniature. The cost is that concurrent writes to the same row in different regions will conflict, and something has to resolve them.

Leaderless replication, the Dynamo lineage that runs Cassandra, Riak and DynamoDB, drops the leader entirely. Clients (or a coordinator) write to several replicas at once and read from several at once, and consistency is tuned by quorum arithmetic: with N replicas, if the write quorum W plus the read quorum R exceeds N, any read set overlaps any write set and you are guaranteed to see the latest value. Divergence is repaired by read repair, hinted handoff and anti-entropy background processes.

The trap to name in an interview is last-write-wins conflict resolution. It is the default because it is simple — compare timestamps, keep the newer value — but it silently discards data, and it depends on clocks across machines being comparable, which they are not: clock skew means "newer" can be wrong, and two writes stamped in the same millisecond are decided arbitrarily. The safer alternatives are application-level merge functions, conflict-free replicated data types (CRDTs) which merge deterministically by construction, or version vectors that detect concurrency and hand both siblings back to the application to reconcile. Say plainly that last-write-wins is acceptable for a cache or a "last seen" field and unacceptable for a shopping cart or a ledger.

When to shard, and federation as the lighter alternative

Replication multiplies copies of the whole dataset; it does nothing about a dataset too large to fit on one machine, and nothing about a write rate one machine cannot absorb. Those are the two legitimate reasons to shard: write throughput beyond a single leader, and data volume beyond a single box's storage, memory or backup window. A third, quieter reason is blast radius — with data split across shards, one corrupted or overloaded shard degrades a fraction of your users rather than all of them. A fourth is regulatory: data residency rules may force a European customer's rows to live in Europe.

Sharding means splitting rows across independent database instances, each holding a disjoint subset — horizontal partitioning, taken across machines. Distinguish it clearly from two neighbours. Table partitioning inside one database (PostgreSQL declarative partitioning, MySQL PARTITION BY) splits a table into pieces managed by a single server: it makes maintenance and pruning of old data far cheaper, but it does not add a machine, so it is not sharding. Federation, also called functional or vertical partitioning, splits by feature rather than by row — users in one database, orders in another, analytics in a third. Federation is the lighter alternative and usually the better next step: each database is still a normal database with working joins and transactions inside its own domain, and the operational model is unchanged. It buys perhaps an order of magnitude, and it maps naturally onto a microservices boundary. Exhaust it before you shard.

Partitioning strategies: range, hash, directory and geo

Range partitioning assigns contiguous key ranges to shards — customer ids A to F on shard one, G to M on shard two, or January's data here and February's there. Range scans and "give me everything between these two dates" queries stay on one shard, which is its great virtue. Its great vice is hot spots: if the key is sequential — a timestamp, an auto-increment id — then every new write lands on the last shard while the others idle, and you have built a distributed system with a single-threaded write path.

Hash partitioning applies a hash to the key and takes the result modulo the shard count (or maps it onto a hash ring). Distribution is close to uniform regardless of what the key values look like, which kills the hot-spot problem at its source. The price is that ordering is destroyed: adjacent keys land on unrelated shards, so range scans become scatter-gather across every shard. A common hybrid is the composite key — hash on a partition key to spread the load, sort by a clustering key within the partition to keep range scans local — which is exactly how Cassandra and DynamoDB model data.

Directory (lookup) based partitioning keeps an explicit mapping from key to shard in a lookup service. It is the most flexible option by far: you can move one tenant to a dedicated shard, rebalance arbitrary key ranges, or run different strategies for different key spaces, all without recomputing anything. The cost is a lookup on the path of every query, and a component that is a single point of failure and a scaling problem of its own unless you replicate and cache it aggressively. Geo or entity-based partitioning shards by region or by tenant — natural for data residency, natural for a business-to-business product where each customer's data is independent — and its risk is that real tenants are wildly unequal in size.

Choosing the shard key: the decision hardest to reverse

Everything else about a sharded system can be changed later with effort. The shard key is the one choice that reaches into every query, every index and every migration script, and changing it after the fact means rewriting the data layer and moving all the data. Treat it as an architectural decision with a written rationale, not a field you pick during implementation.

Four criteria, and a good candidate satisfies all four. High cardinality — the key must have far more distinct values than you will ever have shards, otherwise you cannot subdivide further; a boolean or a status enum is disqualified immediately, and "country" is disqualified as soon as one country dominates. Even distribution — the frequency of values must be roughly uniform, since a key with high cardinality can still be skewed if a handful of values account for most of the traffic. Matches the dominant query — the key should be present in the majority of your reads, so that a typical request is routed to exactly one shard instead of broadcast to all of them; this is where you must know your actual access patterns rather than guess. Keeps related data together — rows that are read or written as a unit should land on the same shard, so a shopping cart and its items, or a tenant and all of its records, stay co-located and can still be updated in a single local transaction.

These criteria pull against each other, and the tension is the interview. Sharding an e-commerce database by user_id gives even distribution and keeps each user's orders together, but "all orders for this seller today" now touches every shard. Sharding by order_id spreads writes beautifully and makes user-scoped queries useless. There is no key that is right for all queries; you choose the one that is right for the dominant query and pay for the others with denormalisation, a secondary index shard, or an asynchronously maintained read model.

The hard parts: cross-shard queries, joins and transactions

Once the data is split, the conveniences of a single database quietly stop working. A query that does not carry the shard key cannot be routed, so the router must scatter-gather: send it to every shard, wait for all of them, merge the results. The latency of that query is the latency of the slowest shard, so tail latency now dominates, and every additional shard makes it worse. Aggregations and sorting have to be recombined by the router, and OFFSET-style pagination across shards is genuinely awkward — it forces each shard to return far more rows than the page size so the router can sort and slice, which is a strong argument for cursor or keyset pagination in any sharded system.

Joins across shards are the sharpest edge. A relational join assumes both sides are on one machine; when they are not, the options are all compromises. Co-locate the tables by sharding them on the same key so the join stays local — the preferred answer, and what Citus calls co-location. Replicate small dimension tables to every shard as reference tables, so lookups never leave the node. Denormalise, embedding what you need in the row. Or join in the application, which means N queries and no help from the query planner.

Cross-shard transactions are the same story one level up. Within a shard you keep ordinary ACID guarantees. Across shards you need either a two-phase commit coordinator — correct, but it holds locks across a network round trip and blocks if the coordinator dies mid-protocol, which is why it is rarely used at scale — or you abandon distributed atomicity for a saga: a sequence of local transactions with compensating actions, which gives you eventual consistency and an obligation to design the compensations. The senior answer is to design the shard key so that the transactions you actually need are single-shard, and to treat any cross-shard transaction requirement as a signal that the boundary is wrong.

Resharding, consistent hashing and hot partitions

Naive hash sharding uses hash(key) mod N, and the flaw shows up the day you add a shard: changing N remaps almost every key, so nearly the entire dataset must move at once. Consistent hashing fixes this by placing shards and keys on a ring; adding or removing a node only moves the keys between that node and its neighbour, so roughly 1/N of the data relocates instead of all of it. Real deployments add virtual nodes — each physical shard owns many small arcs of the ring rather than one big one — which smooths out the uneven arc sizes you get from placing a handful of nodes on a ring, and lets a bigger machine simply own more virtual nodes. A related and often simpler trick is fixed partitions: create far more logical partitions than you will ever have machines (say a thousand), assign many partitions per machine, and rebalance by moving whole partitions. The key-to-partition mapping never changes; only the partition-to-machine mapping does.

Even so, resharding a live system is a project, not a command. The workable pattern is dual-write and backfill: stand up the new topology, copy historical data in the background while streaming ongoing changes to both old and new, verify by comparing checksums, shift reads over shard by shard behind a feature flag, then cut writes over and keep the rollback path alive until you are confident. Vitess and MongoDB automate much of this — resharding workflows and a background balancer respectively — which is a real argument for adopting a sharding-aware layer rather than hand-rolling one.

Hot partitions are the failure mode that survives every good decision above, because the real world is skewed: one celebrity account, one enterprise tenant a hundred times larger than the median, one product on sale. The remedies are worth listing crisply. Key salting — append a small random or bucketed suffix to the hot key so its writes spread across several partitions, at the cost of having to read and merge all the buckets. Split the hot tenant out onto a dedicated shard, which is where directory-based routing earns its keep. Cache in front of the hot read key, which is often the whole answer for read hot spots. Add a time or random component to a monotonic key so sequential writes stop targeting the last range. Whatever you choose, you need per-shard metrics to see it: cluster averages hide a hot shard completely.

Distributed ID generation: life after auto-increment

Sharding breaks the humblest feature in your schema. An auto-increment primary key is a counter owned by one database; with several databases there is no shared counter, and two shards will happily hand out the same integer. You need identifiers that are unique without coordination — and, ideally, that behave well as index keys.

UUIDv4 is the obvious first answer: 122 random bits, collision probability negligible, generated anywhere with no coordination at all. Its problem is not correctness but storage. Random values insert at random positions in a B-tree, so every insert dirties a different page, page splits are constant, the index fragments, the buffer pool fills with pages you touched once, and write throughput on a large table degrades badly. On a clustered-index engine such as InnoDB, where the primary key determines physical row order, the effect is severe. (Mitigations exist — storing the value as binary rather than a 36-character string, or byte-reordering a time-based UUID — but they are patches on the underlying randomness.)

UUIDv7, standardised in RFC 9562 alongside v6 and v8, fixes this properly: the leading 48 bits are a Unix millisecond timestamp and the rest is random, so values are broadly time-sortable and insert at the right-hand edge of the index like a sequence, while remaining globally unique and generated client-side. ULID reached the same design earlier with a compact 26-character Crockford base32 encoding that is sortable as text. For new systems, a time-sortable identifier should be the default and UUIDv4 should need a justification.

Snowflake ids, from Twitter's 2010 design and reimplemented everywhere since, pack a 64-bit integer as roughly 41 bits of millisecond timestamp, 10 bits of machine or shard id, and 12 bits of per-millisecond sequence. They fit a BIGINT, sort by creation time, are compact in indexes, and encode which node produced them — which is why they remain popular for high-volume systems. The costs to state in an interview: you need a coordination mechanism to assign machine ids uniquely (typically ZooKeeper, etcd, or the ordinal of a Kubernetes StatefulSet pod), the epoch and bit layout are baked in at design time, and the design assumes the clock never moves backwards. It does — NTP corrections and virtual-machine migrations happen — and a backwards clock jump can produce duplicate ids, so real implementations refuse to issue ids until the clock catches up. A final, non-technical warning: sequential ids leak business information. A competitor can register two accounts a week apart and read your growth rate off the id gap, which is why public-facing identifiers are often a separate opaque value from the internal primary key.

Interview questions

Database scaling is the highest-yield System Design topic in Indian product and service-company rounds — shard key selection and replication lag come up in almost every design discussion, and "how would you generate unique ids across servers" is a standing favourite at Flipkart, Swiggy, PhonePe and the GCC design panels:

Beginner What is database replication and what does it buy you?

Keeping copies of the same data on more than one node. It buys read scalability (reads spread across followers), availability (a follower can be promoted when the leader dies), and locality (a replica near the users cuts latency). It does not buy write scalability — every write still goes through the single leader and is replayed on every follower, so replication actually increases the total write work in the cluster.

Beginner Synchronous versus asynchronous replication — what is the tradeoff?

Synchronous means the leader waits for a follower to confirm the write before acknowledging: no data loss if the leader dies, but every write pays a network round trip and one slow follower stalls the leader entirely. Asynchronous means the leader acknowledges immediately and ships in the background: fast writes and no coupling to follower health, but a failover loses whatever had not shipped yet. Semi-synchronous is the usual compromise — wait for one follower, with a timeout that degrades to asynchronous instead of freezing.

Beginner What is sharding, and how does it differ from partitioning and replication?

Sharding splits rows of a dataset across independent database instances, each holding a disjoint subset — it adds machines, so it scales writes and storage. Partitioning usually means splitting a table into pieces inside one database server, which helps maintenance and pruning but adds no capacity. Replication copies the whole dataset to more nodes, which scales reads and gives failover. Real systems use both: each shard is itself replicated.

Beginner Your database is slow. Walk me through what you try, in order.

Measure first, then climb the cheap-to-expensive ladder. Find the slow queries and fix indexes and query plans. Add a cache in front of the hot read path. Scale up the instance so the working set fits in memory. Add read replicas if the workload is read-heavy, and route reads to them. Split by function — move reporting, audit and session data off the primary. Only then shard. Volunteering "shard it" as step one is the classic red flag; sharding is the only step that is genuinely hard to reverse.

Intermediate A user updates their profile and immediately sees the old value. Diagnose and fix it.

Replication lag causing a read-your-writes violation: the write went to the leader, the subsequent read landed on a follower that had not applied it yet. Three fixes. Route reads to the leader for a short window after that session writes — simplest and most common. Pin the session to one replica so reads never go backwards, which also gives monotonic reads. Or capture the leader's log sequence number at write time and have the replica wait until it has replayed that far — precise but slower. Independently, alert on replication lag so a replica falling far behind is visible.

Intermediate Range versus hash partitioning — which do you choose and why?

Range keeps contiguous keys together, so range scans and time-window queries hit one shard; but a sequential key such as a timestamp or auto-increment id sends every new write to the last shard, creating a hot spot. Hash distributes evenly and eliminates that hot spot, but destroys ordering, so any range scan becomes a scatter-gather across all shards. Choose from the dominant query: time-series and "between these dates" workloads favour range; uniform point lookups by id favour hash. The common hybrid is a composite key — hash the partition key, sort within the partition on a clustering key.

Intermediate How would you generate unique ids across many servers, now that auto-increment is gone?

Four options with clear tradeoffs. UUIDv4 — zero coordination, but random values fragment B-tree indexes and hurt insert throughput on large tables. UUIDv7 or ULID — time-ordered prefix plus randomness, so still coordination-free but insert at the index edge like a sequence; this is the modern default. Snowflake — 64 bits of timestamp plus machine id plus sequence, compact, sortable, fits a BIGINT, but needs unique machine id assignment and is sensitive to clock skew. Ticket server or id block allocation — a central service hands out ranges that each node consumes locally; simple but the allocator is a dependency to make highly available.

Intermediate What is a hot partition and how do you deal with one?

A single shard receiving disproportionate traffic — a celebrity account, an enterprise tenant far larger than the median, a product on flash sale, or a sequential key that always targets the newest range. Remedies: salt the key with a small random or bucketed suffix so writes fan out (accepting that reads must now merge the buckets), split the hot tenant onto a dedicated shard using directory-based routing, put a cache in front of a hot read key, or add a time or random component to a monotonic key. Prerequisite: per-shard metrics, because cluster averages hide a hot shard completely.

Intermediate Why does adding read replicas not help a write-heavy workload?

Every write still lands on the one leader, and each follower must replay the entire write stream. So follower hardware has to keep up with the same write rate as the leader, and the cluster's total write work grows with each replica rather than shrinking. Replicas add read capacity and failover targets only. For write capacity you need to split writes across leaders — federation by feature, or sharding by row.

Pro How would you pick a shard key for an e-commerce orders table, and what breaks?

Judge candidates against four criteria: high cardinality, even distribution, presence in the dominant query, and co-location of related rows. Sharding by user_id gives even spread and keeps a user's orders together so their order history and cart transactions stay single-shard — but seller-scoped and analytics queries then scatter across every shard. Sharding by order_id spreads writes perfectly and makes user history useless. There is no key that serves every query, so pick for the dominant read path and pay for the rest with denormalisation, a separate read model maintained asynchronously, or a secondary index sharded on the other key. State explicitly that this is the hardest decision to reverse and deserves a written rationale.

Pro Explain split-brain during failover and how fencing prevents it.

Failure detection cannot distinguish a dead leader from a slow or partitioned one. If automatic failover promotes a new leader while the old one is actually alive, both accept writes and the two histories diverge irreconcilably — split-brain. Defences: require a quorum (majority) to promote, so the minority side of a partition can never elect anyone; fence the old leader by revoking its storage lease, cutting its network path, or a local watchdog that halts it when it loses the coordination store; and have every write carry a monotonically increasing fencing token that the storage layer rejects if it is stale. Also accept that failover always loses something — data with asynchronous replication, availability with synchronous.

Pro Why is hash-modulo-N sharding a problem, and what do you use instead?

Because N appears in the mapping. Adding or removing one shard changes N, which remaps nearly every key and forces a near-total data migration. Consistent hashing places shards and keys on a ring so that adding a node only moves the keys between it and its neighbour — roughly 1/N of the data. Virtual nodes give each physical shard many small arcs, which evens out the distribution and lets heterogeneous machines own proportionally more. The simpler alternative is fixed partitions: create far more logical partitions than machines and rebalance by moving whole partitions, leaving the key-to-partition mapping untouched forever.

Pro How do you handle transactions and joins that span shards?

First, try not to need them: choose the shard key so that transactional units are single-shard, co-locate tables that join by sharding them on the same key, and replicate small dimension tables to every shard as reference tables. When you genuinely must cross shards, the options are two-phase commit — correct but it holds locks across a network round trip and blocks if the coordinator dies, so it is rare at scale — or a saga of local transactions with compensating actions, giving eventual consistency and an explicit compensation design. For queries, expect scatter-gather with tail-latency dominated by the slowest shard, and switch to keyset or cursor pagination because offset pagination across shards forces every shard to over-fetch.

Pro Critique last-write-wins as a conflict resolution strategy.

It is the default in multi-leader and leaderless systems because it is trivial, and it silently loses data by design: of two concurrent writes, one is discarded with no notification. Worse, "last" is decided by wall-clock timestamps, and clocks across machines are skewed, so the write that is kept may genuinely be the older one; ties within the same millisecond are broken arbitrarily. It is acceptable for a cache entry or a last-seen-at field. It is unacceptable for a shopping cart, an inventory count or any ledger. The alternatives are application-level merge functions, CRDTs that merge deterministically by construction, or version vectors that detect concurrency and hand both siblings to the application to reconcile.

Pro How would you reshard a live production system with no downtime?

Dual-write and backfill, verified at every step. Stand up the new topology alongside the old. Start writing to both, then backfill historical data in the background while ongoing changes continue to stream to both. Verify equivalence by comparing row counts and checksums per key range. Shift reads across gradually behind a feature flag, one shard or one percentage at a time, watching error rates and lag. Cut writes over last, and keep the old topology in sync and the rollback path alive until you are confident. Vitess resharding workflows and the MongoDB balancer automate much of this — a strong argument for adopting a sharding-aware layer instead of hand-rolling one. Also budget for the fact that this is a multi-week project, not a maintenance window.

Pro Why do random UUID primary keys hurt write performance, and what fixes it?

A UUIDv4 is uniformly random, so consecutive inserts land at random positions in the primary key B-tree. Each insert dirties a different page, page splits become constant, the index fragments and grows, and the buffer pool fills with pages touched once — so insert throughput falls as the table grows. On a clustered-index engine like InnoDB, where the primary key dictates physical row order, the effect is worst. Fixes: use a time-ordered identifier such as UUIDv7 or ULID so inserts append at the right-hand edge like a sequence; or use a Snowflake-style BIGINT, which is both sortable and half the storage. If you are stuck with existing UUIDs, store them as 16 raw bytes rather than a 36-character string, and consider byte-reordering time-based variants so the timestamp leads.
