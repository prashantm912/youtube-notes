Module: Scaling Basics

Scaling is rarely about adding capacity. It is about removing the things that stop you adding another machine — and almost all of those things are state living somewhere it should not.

Knowledge Library → Courses → System Design track → Scaling Basics

What this module covers

Every scaling conversation starts with the same two words — up or out — and most candidates answer it as a slogan ("horizontal is better") rather than a tradeoff. This module takes both seriously: a single large instance is simpler, faster per unit of work and free of the distributed-systems tax, but it has a ceiling and it is a single point of failure; a fleet is elastic and fault tolerant, but every problem you had becomes a distributed problem.

It then gives you the vocabulary to say which kind of scaling you mean — the scale cube's X, Y and Z axes — and spends the second half on the property that makes any of it possible: statelessness, where the state actually goes when you evict it from the process, the twelve-factor app read as design guidance, and the two laws (Amdahl and the Universal Scalability Law) that explain why the tenth machine helps less than the second and the hundredth can make you slower.

Topics

Vertical scaling: the option people abandon too early

Vertical scaling means giving the same process a bigger machine — more cores, more memory, faster storage. Its virtues are all the ones you stop noticing until you lose them: no network hop between your data and your code, no partial failure, no eventual consistency, no distributed transaction, no cache coherency protocol you wrote yourself, and the ability to debug production by attaching to one process. Every line of application code stays the same. In cloud terms it is often a one-line instance-type change and a restart.

It is also badly underrated. Modern instance families go to hundreds of vCPUs and multiple terabytes of RAM; a well-indexed relational database on one large instance comfortably serves workloads that entire teams have rebuilt as distributed systems out of reflex. The honest limits are real though, and you should name them precisely: a hard ceiling (you eventually run out of instance sizes), a step-function cost curve (the top of a family is priced far above linear), downtime or at least a failover to resize, and — the one that actually decides it — the fact that one machine is one failure domain. If the box dies, the service is down. Vertical scaling buys you time and simplicity; it does not buy you availability.

Horizontal scaling and the distributed-systems tax

Horizontal scaling means running many copies of the service behind a load balancer and adding copies as demand grows. Two properties make it the default for anything user-facing: capacity becomes elastic (add replicas on a schedule or a metric, remove them at night) and the failure domain shrinks (losing one of twenty replicas costs you five percent of capacity, not the service). It also lets you buy commodity instances instead of the most expensive box in the family, and it is what autoscaling groups, Kubernetes deployments and serverless platforms are all built to do.

The bill arrives as a tax on everything else. Every request now crosses a network that can drop, duplicate, delay and reorder it. Deploys become rolling, so two versions of your code run at once and your database schema must be compatible with both. Caches multiply, so invalidation gets harder. Logs are scattered, so you need aggregation and tracing to answer a question you used to answer with one grep. Locking becomes distributed locking. Cron becomes a leader election. Test setups that worked against one process become flaky. None of this is a reason not to scale out — it is a reason to scale out deliberately, and to keep the fleet as boring as possible so the tax stays small.

The scale cube: X, Y and Z axes

"We scaled the service" is ambiguous. The scale cube, from Abbott and Fisher's The Art of Scalability and popularised for services by Chris Richardson, gives three named directions instead. X-axis is cloning: run N identical copies behind a load balancer, each able to serve any request. It is the cheapest axis and usually the first — but it scales the whole application uniformly, and every clone still talks to the same database, so it moves the bottleneck rather than removing it. Y-axis is functional decomposition: split by verb or noun, so search, checkout and recommendations become separate deployables with separate resource profiles and separate teams. This is exactly what microservice decomposition is, viewed as a scaling move. Z-axis is data partitioning: every instance runs the same code but is responsible for a subset of the data, routed by a partition key — sharding, cell-based architecture, and (in its more careful form) shuffle sharding.

The value of the vocabulary is that it forces you to say what your bottleneck is. If the CPU on the web tier is saturated, that is an X-axis problem and more replicas fix it. If one endpoint's traffic is drowning nine others that share its thread pool, that is a Y-axis problem and cloning just buys everything you did not need. If a single database is the ceiling — write throughput, working-set size, lock contention — no amount of X or Y helps and you are looking at Z. Real systems use all three at once, and being able to say "we are X-scaled behind an L7 balancer, Y-split into six services, and the ledger is Z-sharded by customer id" is a much stronger interview answer than "we scaled horizontally".

Statelessness: the property that makes cloning legal

A stateless service is one where any replica can serve any request, and where killing a replica mid-life loses nothing that mattered. It does not mean the system has no state — it means the state lives in a backing service (database, cache, object store, queue) rather than in the process's own memory or local disk. That single property is what makes the X axis work: replicas become interchangeable, so you can add them, drain them, roll them, autoscale them, move them between availability zones and let the orchestrator restart them without ceremony.

The practical value of this topic is the failure list, because in-process state does not announce itself — everything works perfectly on one replica and breaks subtly on the second. The usual suspects: in-memory HTTP sessions (a user logs in on replica A, the next request lands on replica B, they are logged out); local file caches and uploads (a file written to /tmp on one pod is invisible to the others and gone when the pod is replaced); in-memory counters, rate limiters and circuit breaker state (each replica enforces the limit independently, so ten pods permitting a hundred requests per second allow a thousand); in-memory caches (each replica has a different, independently stale view, so a cache-clear endpoint clears exactly one of them); scheduled jobs (a nightly report written as a plain @Scheduled method runs once per replica, so the invoice is emailed twenty times); WebSocket and SSE connections (a push targeted at a user only reaches them if it is published on the replica holding their socket); in-memory locks (synchronized guards one JVM, not the cluster); and ephemeral ids and sequence numbers generated per process, which start colliding the moment a second process exists.

// Breaks on replica two — all of this state is process-local
private final Map<String, Cart> carts = new ConcurrentHashMap<>();  // lost on restart
private final AtomicInteger orderSeq = new AtomicInteger();          // collides across pods

@Scheduled(cron = "0 0 2 * * *")   // runs once PER REPLICA, not once per cluster
public void emailInvoices() { ... }

// Stateless equivalent: state in a backing service, work claimed by exactly one replica
private final CartRepository carts;              // shared store
private final IdGenerator ids;                   // database sequence / Snowflake-style id
@SchedulerLock(name = "emailInvoices")           // distributed lock: one winner per run
public void emailInvoices() { ... }

Session externalization: sticky sessions, or a shared store

Sessions are the state that breaks first, so they get their own treatment. The path of least resistance is session affinity — sticky sessions — where the load balancer pins a client to the replica that first served it, using a cookie (AWS ALB's AWSALB, nginx's sticky directive) or a hash of the source address (ip_hash). It works, it needs no application change, and it is a crutch. Affinity re-couples the client to one machine, which means you lose the session on deploy, on autoscale-in, on any crash, and on a health-check blip; load skews because long-lived sessions do not rebalance when you add capacity; draining a node for maintenance now hurts users instead of being invisible; and the whole point of interchangeable replicas is gone. Treat stickiness as a temporary measure during a migration, or as an optimisation for a local cache you can afford to lose — never as the design.

The real fix is to move the session out of the process into a shared store: Redis is the usual choice (fast, has native expiry that matches session semantics, and clusters), a relational table works fine at moderate scale and gives you durability, and Spring Session makes the swap almost transparent on the JVM — you keep the HttpSession API and change where it is persisted. The costs to state honestly: a network round trip on every request that touches the session, a new dependency that is now on the critical path (a Redis outage becomes a logout storm, so plan replication and a degraded mode), and serialization concerns — keep sessions small, store an id and a few claims rather than a whole shopping cart object graph.

Going fully stateless with signed tokens — and the revocation bill

The third option removes the server-side session entirely: put the state in the client, signed so it cannot be tampered with. A JWT carrying a subject, a few claims, an expiry and a signature lets any replica authenticate a request with a signature check and no lookup at all — no shared store, no round trip, no affinity, and it scales across services and regions for free. This is Fowler's Client Session State pattern with modern cryptography, and it is why token auth dominates API and mobile back ends.

The bill is revocation, and interviewers reach for it every time. A signed token is valid until it expires because validation is offline by construction — so "log this user out everywhere", "this account was compromised", "this admin was demoted five minutes ago" have no clean answer. The mitigations all reintroduce a bit of state: short access-token lifetimes (minutes) paired with a longer refresh token that is checked against a store, a denylist of revoked token ids in Redis, or a per-user token version stamped in the claims and compared against the database. Notice that each of these puts a lookup back on some requests — which is the honest summary of the whole topic. Also mind the secondary traps: tokens are signed, not encrypted, so anything inside them is readable by the client; every claim you embed is a cache of data that can go stale; and a fat token is sent on every single request, so size matters.

The twelve-factor app, read as design guidance

The twelve-factor manifesto is usually recited as a list; it is more useful read as a set of answers to "what stops this app from being cloned?" Config in the environment (factor III) means anything that varies between deploys — credentials, endpoints, feature flags — comes from environment variables rather than a prod.properties baked into the artifact, so the identical image runs in staging and production and you never ship a build with someone's laptop database URL in it. The litmus test is blunt: could you open-source the repository right now without leaking a credential?

Backing services as attached resources (factor IV) says the database, cache, broker and mail service are all just URLs in config, with no code distinction between a local Postgres and a managed one. That is what lets you swap a failed cache cluster for a fresh one without a redeploy, and it is the same discipline that makes tests runnable against containers. Processes are stateless and share-nothing (factor VI) is the factor this whole module is about — memory and local disk are a single-transaction scratchpad, never a store — and concurrency (factor VIII) follows from it: you scale by running more processes, not by making one process cleverer with threads.

Disposability, parity and logs: the factors that make replicas cheap

Disposability (factor IX) is the operational half of statelessness: processes should start in seconds and shut down gracefully on SIGTERM. Fast startup is what makes autoscaling responsive and rollbacks quick — a service that needs ninety seconds to warm caches before it can serve cannot be scaled reactively. Graceful shutdown is what makes deploys invisible: on the signal, stop accepting new requests, finish in-flight ones inside a bounded grace period, return unacknowledged queue messages so another worker picks them up, then exit. In Kubernetes this pairs with a preStop hook and readiness probe so the endpoint is removed from the load balancer before the process starts refusing connections, which is the difference between a clean rollout and a burst of 502s. And because a replica can be killed at any moment, every job must be crash-safe — which in practice means idempotent, because "at least once" is the only delivery guarantee you get.

Dev/prod parity (factor X) keeps the gap between environments small in time, personnel and tooling — same backing service types everywhere, so an in-memory H2 in tests and Postgres in production is a parity violation waiting to produce a bug you cannot reproduce. Logs as event streams (factor XI) says the app writes unbuffered to stdout and never manages log files or rotation; the platform routes the stream to the aggregator. That is not a stylistic preference — a replica that owns a log file on local disk has state, and you lose the file when the pod dies.

Shared-nothing as the general principle

Statelessness is one instance of a broader rule that predates it: shared-nothing architecture, Michael Stonebraker's term for a design where each node has its own CPU, memory and storage and coordinates only by passing messages. Anything shared — a shared disk, a shared session store, a shared lock table, a shared sequence generator, a shared leader — is a coordination point, and coordination points are simultaneously your scaling ceiling and your correlated failure. The design question to keep asking is not "is this service stateless?" but "what do all my replicas have to agree on, and how often?" Every answer you can delete makes the fleet cheaper to grow.

Applied, this looks like: partition data so each request touches one shard rather than fanning out; prefer per-request idempotent work over cross-request coordination; make failure handling constant-work (do the same amount of work whether things are healthy or broken, so recovery does not add load exactly when you cannot afford it); and isolate blast radius into cells or bulkheads so one hot tenant cannot exhaust the shared resource everyone depends on. The counter-current is worth knowing too — deliberately stateful services (in-memory caches, stream processors with local state, databases themselves) are sometimes the right answer for latency, and modern orchestrators support them properly. The point is that stateful should be a decision you argued for, not the accident of leaving a HashMap in a field.

Why the tenth machine helps less: Amdahl and the Universal Scalability Law

Adding replicas does not add capacity linearly, and two results explain why. Amdahl's law says the speedup of a system is capped by the fraction of work that cannot be parallelised: if five percent of every request is serialised — a single write master, a global lock, a shared sequence, a leader that must approve — then no number of machines gets you past twenty times the single-machine throughput. The practical reading is that you should hunt for the serialised fraction before you buy hardware, because shrinking it from five percent to one percent raises the ceiling far more than doubling the fleet does.

The Universal Scalability Law (Neil Gunther) adds the term Amdahl leaves out: coherency, the cost of nodes keeping each other consistent. That cost grows quadratically with node count while throughput grows linearly, so the curve does not merely flatten — it peaks and then bends downward. Past a certain size, adding machines makes the system slower. Anyone who has watched a database get worse after adding connections, or a cache cluster degrade as it grew, has met retrograde scalability in person. Two takeaways for an interview: know that the model has three terms (linear work, contention, coherency), and be able to name the practical consequence — measure the curve on your own system, find the peak, and do not scale past it without removing a coordination point first.

Interview questions

Scaling basics is the opening round of almost every Indian system-design interview — service companies stay on the definitions and the session question, product companies push into the scale cube, revocation and the limits of adding machines:

Beginner Vertical vs horizontal scaling — define both and give one advantage each.

Vertical (scale up) means a bigger machine for the same process: more cores, memory, faster disk. Advantage — no code change and no distributed-systems complexity. Horizontal (scale out) means more machines behind a load balancer. Advantage — elastic capacity and fault tolerance, since losing one of many replicas is a partial capacity loss rather than an outage. Vertical has a hard ceiling and remains a single failure domain; horizontal makes every problem a distributed one.

Beginner What does it mean for a service to be stateless?

Any replica can serve any request, and killing a replica loses nothing important. The service keeps no client-specific data in its own memory or local disk between requests — state lives in a backing service such as a database, cache or object store. It does not mean the system is stateless; it means the state has been moved somewhere shared.

Beginner How do you make an existing service stateless?

Inventory the process-local state and relocate each item. Sessions move to Redis or a database (or become signed tokens). Uploaded files and local caches move to object storage or a shared cache. In-memory counters and rate limiters move to a shared counter. Scheduled jobs get a distributed lock or move to a dedicated scheduler so only one replica runs them. In-memory locks become distributed locks. Process-generated ids become database sequences or Snowflake-style ids. Then verify by running two replicas behind a load balancer with no affinity and killing one under load.

Beginner Name three things that silently break when you deploy a second replica.

Any three of: in-memory HTTP sessions (users get logged out at random), a nightly scheduled job now running once per replica (duplicate emails, double-counted reports), local file uploads or caches invisible to the other replica and lost on restart, an in-memory rate limiter now permitting N times the intended rate, an in-memory cache with a clear-cache endpoint that clears only one replica, WebSocket pushes reaching only clients connected to the publishing replica, and process-local id generators that start colliding.

Beginner What are sticky sessions and how does a load balancer implement them?

Session affinity pins a client to the replica that first served it, so in-memory session state keeps working. Implementations: a load-balancer-generated cookie (AWS ALB's AWSALB cookie), an application cookie the balancer honours, nginx's sticky directive, or a hash of the client address (ip_hash) which needs no cookie but breaks behind shared NAT or a mobile carrier.

Intermediate Why are sticky sessions considered a crutch rather than a design?

They re-couple the client to one machine and undo the property that made replicas useful. You lose sessions on every deploy, crash, autoscale-in and health-check blip; load skews because existing sessions never rebalance onto newly added replicas; draining a node for maintenance becomes user-visible; and blue-green or rolling deploys stop being invisible. Acceptable as a temporary bridge during a migration or for a purely optional local cache — not as the answer to "how do you scale this service".

Intermediate Explain the scale cube and give a real example of each axis.

X-axis: clone the whole application behind a load balancer — twenty identical API pods. Y-axis: split by function or service — extract search and checkout into their own deployables with their own scaling profiles. Z-axis: split by data — shard the ledger by customer id so each instance owns a subset of rows. X is cheapest and moves the bottleneck downstream; Y targets a specific hot capability and aligns with team boundaries; Z is what you reach for when a single database is the ceiling. Production systems combine all three.

Intermediate Sessions in Redis versus JWTs — how do you choose?

Redis-backed sessions keep state server-side: revocation is instant, the cookie is an opaque id so nothing leaks, and you can store more data — at the cost of a network round trip per request and a new critical dependency whose outage logs everyone out. JWTs validate offline with a signature check, so they scale across services and regions with zero lookups — at the cost of revocation being effectively impossible before expiry, claims going stale, and the token being readable by anyone holding it. Server-side sessions suit a single trust boundary needing immediate revocation (banking, admin consoles); tokens suit distributed APIs and mobile clients. The common middle ground is a short-lived access token plus a refresh token that is checked against a store.

Intermediate Which twelve-factor factors matter most for horizontal scaling, and why?

VI (stateless, share-nothing processes) is the enabling one. III (config in the environment) lets the identical artifact run in every environment, so replicas are truly identical. IV (backing services as attached resources) lets you swap or repoint a database or cache without a rebuild. IX (disposability — fast startup, graceful shutdown on SIGTERM) is what makes autoscaling and rolling deploys safe. VIII (concurrency via the process model) says you scale by adding processes. XI (logs as event streams to stdout) removes the last piece of local disk state.

Intermediate You have a nightly job in a service running on six pods. How do you run it exactly once?

Options in rough order of preference: move it out of the service into a platform scheduler (a Kubernetes CronJob, or a managed scheduler triggering one execution); or keep it in-process but guard it with a distributed lock backed by a shared store (ShedLock, a Redis lock with a fencing token, or a database row lock) so exactly one replica wins each run; or elect a leader and let only the leader schedule. Whichever you choose, make the job idempotent and safe to re-run, because a lock holder can die mid-job.

Pro Argue the case for vertical scaling. When would you deliberately choose it?

When the workload is coordination-heavy and the team is small. A single large instance removes the entire distributed-systems tax: no network partitions, no eventual consistency, no distributed transactions or locks, no cross-node cache coherency, one process to profile. Modern instances reach hundreds of vCPUs and terabytes of memory, so a well-indexed relational database on one box serves far more traffic than most teams assume — and engineer time saved is real money. Choose it for the primary write database, for latency-sensitive single-tenant workloads, and as the deliberate first move while product-market fit is still uncertain. Accept the limits explicitly: a hard ceiling, superlinear cost near the top of the family, resize downtime, and one failure domain — so pair it with a replica for availability even when you are not scaling out for capacity.

Pro How do you revoke a JWT, and what does each approach cost?

Strictly you cannot — offline validation is the point. Practical approaches: keep access tokens short-lived (a few minutes) and revoke at refresh time, which bounds exposure but does not eliminate it; keep a denylist of revoked token ids in Redis and check it on every request, which restores instant revocation but reintroduces the lookup and the shared dependency you were avoiding; stamp a per-user token version in the claims and compare it against the user record, which is cheaper if you were reading the user anyway; or rotate the signing key, which revokes everyone at once and is a blunt incident tool. Each buys revocation by giving back some statelessness — say that tradeoff out loud.

Pro Your service is X-scaled to forty replicas and throughput has stopped improving. How do you diagnose it?

Assume a serialised fraction or a coordination point rather than a capacity shortfall. Find the shared resource everything queues on — a single write master, a global lock, a hot partition, a shared sequence generator, a connection pool at the database, an external dependency with its own limit. Measure throughput against replica count to see whether the curve is flattening (Amdahl-style contention) or actually bending downward (coherency cost, the USL's retrograde region). If it is bending down, adding replicas is making things worse and the answer is fewer, better-behaved clients — connection pooling, batching, caching — not more machines. Then attack the serialised fraction: shard the hot data (Z axis), split the hot capability out (Y axis), or make the coordination unnecessary.

Pro What is shared-nothing architecture, and where do real systems knowingly violate it?

Each node owns its own CPU, memory and storage and coordinates only by message passing; nothing is shared, so nodes can be added without contending for a common resource. Real systems violate it deliberately where the alternative is worse: a shared session or token-denylist store, a shared metadata or config service, a leader for scheduling and cluster membership, a shared object store, and the database itself. The discipline is to keep the shared thing small, keep it off the hot path where possible, and know the blast radius when it fails — which is exactly why cell-based and bulkhead architectures partition even the shared components.

Pro A service is stateless but still cannot be safely restarted mid-request. What is missing?

Disposability. Statelessness makes replicas interchangeable, but you also need a clean shutdown path: on SIGTERM stop accepting new work, fail readiness so the load balancer removes the endpoint before connections are refused (a preStop hook plus a short delay in Kubernetes), finish in-flight requests inside a bounded grace period, negatively acknowledge or return unprocessed queue messages so another worker claims them, and flush what must be flushed. Anything still in flight past the grace period will be killed, so the work must be idempotent and re-runnable — at-least-once is the only guarantee available.
