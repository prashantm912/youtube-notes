Module: Asynchronous Architectures

The design question is not "should we use a queue" — it is which work must finish before you answer the user. The honest answer is almost always less than you think, and everything else belongs behind a queue.

Knowledge Library → Courses → System Design track → Asynchronous Architectures

What this module covers

This is the design-level view of going asynchronous: when to do it, what shape to choose, and what each shape costs you. It starts with the request-path discipline — do only what the response genuinely depends on, queue the rest — then works through queue-based load leveling and its capacity caveat, the health signals that tell you a queue is in trouble, the fan-out strategies (competing consumers, publish-subscribe, fan-out on write versus on read), and priority work. The second half covers processing models: batch versus stream, windowing and event time, scheduled work and the distributed-cron trap, and exactly-once revisited as a design target rather than a delivery guarantee.

Broker mechanics live elsewhere in this course. Partitions, consumer groups, acknowledgements, retry topics and dead-letter queues are taught in depth in the Messaging track — start with Messaging Fundamentals and Kafka Architecture. Here we stay at the level an architect argues at: what work moves off the request path, what shape the flow takes, and what breaks when load rises.

Topics

The request path: what must finish before you answer?

Every endpoint has an implicit contract about what is true by the time the response is written. The design work is making that contract explicit and then aggressively shrinking it. Take "user uploads a video": the response depends on the bytes being durably stored and a video id existing. It does not depend on the thumbnail being generated, the transcode ladder being built, the search index being updated, the recommendation model being recalculated, or the "your upload is live" email being sent. Do the first two synchronously; publish an event and let the other five happen behind it. The same test applies to checkout (charge the card and persist the order synchronously; send the confirmation email, decrement loyalty points and warm the analytics warehouse asynchronously) and to signup (create the account; queue the welcome mail, the CRM sync and the fraud score).

Shrinking the request path buys three things at once: latency (you stop paying for work the user is not waiting on), availability (the email provider being down no longer fails checkouts), and independent scaling (thumbnail workers scale on thumbnail load, not on HTTP load). It costs you one hard thing in exchange — the user's mental model and yours diverge. The response now means "accepted", not "done", so the API has to say so: return 202 Accepted with a status resource the client can poll, or push completion over a websocket. Anything that silently pretends the work is finished will eventually surface as a support ticket. Two failure modes to name in an interview: the dual write, where you commit to the database and then fail to publish the event (fixed with the transactional outbox, covered below), and the read-your-writes break, where the user reloads and cannot see the thing they just created.

                             (synchronous: bytes durable, id assigned — that is all)

  ↳ publishes VideoUploaded → thumbnail worker
                            → transcode worker
                            → search-index worker
                            → notification worker

GET  /v1/videos/vid_9f3    → 200 OK       { "state": "processing", "ready": false }

Queue-based load leveling: turning a spike into queue depth

A synchronous service facing a burst has only bad options: accept the load and fall over, or reject it with errors. Put a queue between the front door and the workers and the burst becomes something else entirely — queue depth. The producers write at whatever rate the world throws at them, the buffer absorbs it, and the consumers drain at their own steady, provisioned pace. You size the workers for the average load rather than the peak, which is often an order of magnitude cheaper, and a five-minute flash sale that would have produced a wall of HTTP 503s instead produces a queue that is a few hundred thousand messages deep and empties over the next twenty minutes.

Now the caveat that separates people who have run this in production from people who have read about it: a queue converts an availability problem into a latency problem — it does not create capacity. Load leveling only works if average consumer capacity exceeds average producer load over the window that matters. If the arrival rate exceeds the drain rate on a sustained basis, the queue does not smooth anything; it grows without bound until you hit the broker's retention limit, run out of disk, or blow past every latency expectation the business had. A queue is a shock absorber, not an engine. Bound it deliberately: set a maximum depth or an age limit, decide what happens when the bound is hit (shed, reject, spill to cold storage), and never treat "the queue is holding it" as a capacity plan. It is also worth remembering that the queue itself is now a dependency — if the broker is down, the front door is down, so the producer needs its own local durability story.

Queue depth and consumer lag: the health signals, and what to do when they rise

Two numbers tell you almost everything about an asynchronous system. Queue depth (or consumer lag, on a log-based broker like Kafka, which measures how far behind the latest offset a group is) tells you whether you are keeping up. Age of the oldest message tells you what a user is actually experiencing — depth of ten thousand means nothing on its own, but an oldest message that is forty minutes old means somebody's password reset mail is forty minutes late. Alert on the age, not just the depth; graph the arrival rate and the drain rate on the same chart so the gap is visible; and watch the trend, because a queue that is growing linearly has a deterministic time-to-disaster you can compute.

When the gap is real you have exactly three levers, and a good answer names all three in order. First, scale the consumers — this is the reflex, and it is right when the bottleneck is worker CPU and the downstream can take the extra concurrency. It fails when the real bottleneck is a shared database or a third-party API, where adding consumers just moves the queue somewhere less observable. Second, shed load — drop or downgrade work you can afford to lose (analytics events, non-critical notifications, recommendation refreshes), and consider processing newest-first so recent users get service while the old backlog is written off. Third, reject at the front door — throttle or rate-limit producers so the backlog stops growing while you recover; an honest error at the edge is better than an unbounded queue that silently degrades everyone. A fourth, underrated tactic from the Builders' Library: separate the backlogged work onto its own queue so a poisoned or slow class of message cannot starve everything else.

Work queues and competing consumers

The first fan-out shape is point-to-point: one queue, many identical workers, each message delivered to exactly one of them. This is the competing consumers pattern, and it is the workhorse of asynchronous design because it makes throughput a dial. Workers are stateless and interchangeable, so you scale by adding processes; the broker handles the distribution, so there is no coordinator to write; and a worker that dies mid-message simply has its message redelivered once the acknowledgement times out. Note the delivery model this implies — you acknowledge after the work is done, not on receipt, which is precisely why at-least-once is the default and duplicates are inevitable.

Two design consequences follow. First, competing consumers destroy ordering by construction: if two messages for the same order land on two workers, they may complete in either sequence. If you need per-entity ordering, partition by key so all messages for one key go to one consumer, and accept that you have now capped parallelism at the number of partitions and created a hot-key risk. Second, the workers must be idempotent, because redelivery is a normal event and not an error. Keep messages small — pass an identifier and let the worker fetch, or use the claim-check pattern to put a large payload in object storage and send a pointer — and give every queue a dead-letter destination so one unprocessable message cannot block the line. Ordering, acknowledgement modes and dead-letter mechanics are worked through properly in Ordering and Concurrency and DLQ and Retries.

Publish-subscribe fan-out to independent subscribers

The second shape is broadcast: the producer publishes one event to a topic and every interested subscriber gets its own copy. Where a work queue divides work among clones, publish-subscribe multiplies one fact across different consumers doing different things — OrderPlaced lands on the invoicing service, the warehouse service, the loyalty service and the analytics pipeline, none of which the order service knows about. The publisher names an event, not a recipient, which is what actually delivers the decoupling everyone claims for messaging: adding a sixth subscriber is a deployment, not a change to the publisher.

The costs are real and worth stating. Each subscriber has its own delivery state, so one slow or broken subscriber lags alone rather than blocking the others — good — but it also means failure is now per-subscriber and you need per-subscriber monitoring and dead-lettering. The event schema becomes a public contract with many consumers you may not control, so versioning is additive and breaking changes are expensive. And you lose the single-place-to-read control flow: no code says "when an order is placed, do these four things", which is the recurring complaint about choreographed event-driven systems. The design guidance is to publish domain facts ("OrderPlaced") rather than commands dressed as events ("SendInvoiceEmail"), and to be deliberate about when a request-response call is simply clearer. The event-driven style itself is treated at length in Event-Driven Architecture.

Fan-out on write versus fan-out on read

This is the fan-out decision that shows up in almost every senior interview, and it is a pure precompute-versus-compute-later trade. Fan-out on write (push) does the work at publish time: when a user posts, you write a copy of the post reference into every follower's precomputed timeline. Reads become a single sequential fetch of one list — fast, cheap, predictable, which is exactly what you want when the read-to-write ratio is a hundred to one. Fan-out on read (pull) does nothing at write time and assembles the feed at request time by fetching from everyone the reader follows and merging. Writes become trivial and there is no derived storage to keep consistent, but reads become a scatter-gather whose latency depends on how many people you follow and whose cost is paid on every refresh.

Pure fan-out on write breaks on the celebrity problem: one post by an account with fifty million followers turns a single write into fifty million writes. That burst saturates the write path, delays delivery for everyone else, and consumes storage proportional to the follower graph rather than the content. Pure fan-out on read breaks on the other end — a user following two thousand accounts pays a two-thousand-way fan-in on every pull. The production answer is the hybrid: fan out on write for ordinary accounts, and for accounts above a follower threshold skip the fan-out and merge their posts in at read time from a small, heavily cached "celebrity" set. Reads therefore do one cheap list fetch plus a merge over a handful of hot accounts. This is the shape Twitter and Instagram converged on, and it is the backbone of the news feed design in Classic Designs B. Related follow-ups worth rehearsing: what happens to a user's precomputed timeline when they follow someone new (backfill or leave a seam), and how you handle inactive users whose timelines you are paying to maintain for nobody.

post(author, item):
    if followerCount(author) < CELEBRITY_THRESHOLD:
        for f in followers(author):          # fan-out on write
            push(timeline[f], item)
    else:
        append(celebrityPosts[author], item) # skipped; merged at read

read(user):
    base    = fetch(timeline[user])                       # one sequential read
    hot     = merge(celebrityPosts[a] for a in celebritiesFollowedBy(user))
    return  rank(merge(base, hot))                        # hybrid: cheap read + small fan-in

Priority work, and the starvation you are signing up for

Not all queued work is equal: a password-reset mail and a monthly-digest mail are both "send an email", but only one of them has a user staring at an inbox. There are two ways to express that. A true priority queue keeps one queue and orders messages by a priority field, which is elegant but has real costs — priority ordering interacts badly with partitioned or log-based brokers, it complicates prefetch and batching, and support varies (RabbitMQ implements priorities per queue with caveats; Kafka has no notion of them at all). The pragmatic alternative, and the one most systems land on, is multiple queues by class: an interactive queue, a bulk queue, maybe a bulk-retry queue, with separate consumer pools sized independently. Separate pools also give you isolation — a flood of bulk work cannot consume the workers that serve interactive traffic — which a single priority queue does not.

The hazard to name before the interviewer does is starvation: if consumers always drain the high-priority queue first and high-priority work never runs dry, the low-priority tier waits forever. The standard mitigations are weighted service (consume in a fixed ratio such as nine high to one low rather than strict priority), ageing (promote a message's priority as it gets older, so nothing waits indefinitely), and dedicated capacity (reserve a minimum number of workers for the low tier). Whichever you pick, monitor the oldest-message age per class — a healthy aggregate depth routinely hides a low-priority queue that has not moved in a day. The same reasoning generalises to per-tenant fairness: one large customer's bulk job should not be able to consume the shared worker pool, which is where isolation techniques such as shuffle sharding earn their keep.

Batch versus stream processing

Batch processing runs over a bounded, complete dataset on a schedule: yesterday's orders, this month's settlements, the full product catalogue. Its virtues are underrated — throughput per rupee is excellent because you amortise setup over millions of records, the reasoning is simple because the input does not move while you read it, failures are handled by rerunning the job, and reprocessing after a bug fix is a rerun rather than an archaeology project. Its vice is latency: results are as stale as the schedule, so a nightly job means a business decision is up to a day behind. Stream processing runs continuously over an unbounded input, producing results within seconds. Its virtue is freshness; its vices are operational — the job is long-lived and must carry state across restarts, correctness now depends on how you handle out-of-order and duplicate events, and reprocessing history means replaying a log rather than rerunning a script.

Choose on requirements, not fashion. Ask what the freshness requirement actually is (fraud scoring on a card swipe needs seconds; a finance reconciliation report is fine daily), whether the computation needs the complete dataset (global ranking, deduplication across the whole corpus, and most model training want batch), how expensive correction is, and how much operational maturity the team has — a streaming job is a service you run forever, not a script you schedule. Micro-batching is the middle ground: process small batches on a short interval (a few seconds), as Spark Structured Streaming does. You get most of the freshness with batch-shaped reasoning and simpler exactly-once story, at the cost of a latency floor equal to the batch interval. Many mature systems run both over the same events — a streaming path for the fast, approximate answer and a batch path that recomputes the authoritative one — which is the practical residue of the old lambda-architecture argument.

Windows, watermarks, and event time versus processing time

An unbounded stream has no end, so any aggregation needs a window — a finite slice to compute over. The three you should be able to name are tumbling (fixed, non-overlapping: each minute), sliding or hopping (fixed length, overlapping: the last five minutes, recomputed every minute), and session (dynamic, closed by a gap of inactivity — the natural window for user behaviour). The follow-up question is always the same: when do you decide a window is finished? That is what a watermark is — the system's assertion that it believes it has seen all events up to a given event time, and may therefore emit the result. Watermarks are a heuristic, so they encode a deliberate trade between latency (emit early, risk being wrong) and completeness (wait longer, be more right).

Which brings us to the distinction behind most streaming bugs. Event time is when the thing happened in the real world; processing time is when your pipeline got around to it. They diverge constantly — a mobile client was offline in a lift for ten minutes, a partition was rebalancing, a consumer was restarted and replayed an hour of backlog. Aggregate by processing time and your "orders per minute at 8 pm" chart is really "orders our pipeline handled at 8 pm", and a replay after an incident will happily attribute yesterday's orders to today. Aggregate by event time and the numbers mean what they say, but you must now decide what to do with late-arriving data that shows up after its window has closed: drop it, hold windows open for a bounded allowed lateness and emit an updated result, or route the stragglers to a side output for correction. Make that policy explicit; a pipeline with no stated lateness policy has one anyway, and it is "silently wrong".

Scheduled work and the distributed-cron problem

Plenty of asynchronous work is not event-driven at all — it is periodic: expire abandoned carts every ten minutes, settle payouts nightly, refresh a materialised view hourly, retry the stuck records every quarter of an hour. On one box this is a cron entry or a @Scheduled annotation and it works perfectly. Then you scale to three replicas and it breaks silently and expensively, because every replica fires the job. Three copies of the settlement run, three emails to the same customer, three increments of the same counter. This is the single most common production surprise when a scheduled monolith becomes a scheduled deployment, and interviewers in India ask it constantly because everyone has been bitten by it.

The fixes, roughly in order of weight: a distributed lock that the job must acquire before running (ShedLock over your existing database or Redis is the standard Spring answer — simple, no new infrastructure, and adequate as long as you understand that a lock without fencing is best-effort under pauses); leader election, where one instance is elected via a consensus store and only the leader schedules — stronger, and the right answer once several jobs need coordinating; or a dedicated scheduler service that owns time and does no work itself, instead enqueueing a message that ordinary competing consumers pick up, which cleanly separates "decide when" from "do the work" and makes retries and observability normal. Whichever you choose, design the job to be idempotent and re-runnable anyway, make it resumable in chunks rather than one giant transaction, avoid scheduling everything on the hour boundary (a thundering herd of jobs at midnight is self-inflicted), and monitor for the job that silently stopped running — a job that never fires produces no errors at all. Locks and fencing are covered in Distributed Coordination.

@Scheduled(cron = "0 */10 * * * *")             // every ten minutes, on every replica
@SchedulerLock(name = "expireAbandonedCarts",   // ...but only one wins the lock
               lockAtLeastFor = "PT5M",         // guard against clock skew re-runs
               lockAtMostFor  = "PT9M")         // released if the holder dies
public void expireAbandonedCarts() {
    // idempotent and chunked: safe to re-run, safe to interrupt
    cartRepo.expireBatch(Instant.now().minus(Duration.ofHours(2)), 500);
}

Exactly-once revisited: at-least-once plus idempotent consumers

"Exactly-once delivery" over a network is not achievable, and saying so crisply is a strong interview signal. The reason is the ambiguity of a timeout: a producer that does not get an acknowledgement cannot distinguish "the message never arrived" from "it arrived and the ack was lost". It must choose — resend (risking a duplicate, at-least-once) or give up (risking a loss, at-most-once). There is no third option at the delivery layer. What systems like Kafka market as exactly-once is really exactly-once processing within a closed world: idempotent producers plus transactions that atomically commit output records and consumer offsets, valid as long as everything stays inside the broker. The moment your consumer charges a card or calls an external API, that guarantee stops at the boundary. The mechanics of Kafka transactions are covered in Kafka Advanced.

So the achievable design target is at-least-once delivery plus idempotent consumers, and the effect the user sees is exactly-once. Two mechanisms implement it. The explicit one is a dedup store: every message carries a stable identifier (a producer-assigned message id, or better, a business idempotency key such as the order id) and the consumer records processed keys, rejecting repeats. Record the key and the effect in the same transaction as the work, or you have simply moved the race. Dedup stores need a retention window — you cannot remember every key forever — so size it against your realistic redelivery horizon and accept that a duplicate arriving after the window slips through. The better mechanism, where you can get it, is to make the operation naturally idempotent so no bookkeeping is needed at all: set a field rather than incrementing it, upsert on a natural key rather than inserting, use a conditional update guarded by a version or expected state, and model state transitions so that applying "mark as shipped" twice is a no-op. Naturally idempotent operations survive replays, backfills and reprocessing without any dedup infrastructure; bolted-on deduplication is the fallback for when the operation genuinely cannot be reshaped. Finally, close the producer-side gap with the transactional outbox: write the event into an outbox table in the same database transaction as the state change and let a relay publish it, so you never commit a change whose event was lost.

-- Naturally idempotent: same message applied twice, same final state.
UPDATE orders SET status = 'SHIPPED', shipped_at = :ts
 WHERE id = :orderId AND status = 'PACKED';        -- conditional, not blind

INSERT INTO loyalty_points (user_id, order_id, points)
VALUES (:userId, :orderId, :points)
ON CONFLICT (user_id, order_id) DO NOTHING;        -- upsert on a natural key,
                                                   -- not points = points + n

Interview questions

Asynchronous design is where Indian product-company rounds separate candidates fast — service-company panels ask the queue and scheduler questions, product panels push on fan-out and exactly-once until you either hedge correctly or over-claim:

Beginner When would you make an operation asynchronous instead of synchronous?

When the response does not depend on it. Ask what must be true for the user's answer to be correct — persist that synchronously, queue everything else. Typical asynchronous work: confirmation emails and notifications, thumbnail and media generation, search-index updates, recommendation recalculation, analytics, third-party syncs. The gains are lower latency, higher availability (a failing email provider no longer fails checkout) and independent scaling; the cost is that "accepted" is not "done", so the API must expose status.

Beginner What is queue-based load leveling?

Putting a buffer between producers and consumers so a traffic spike becomes queue depth instead of errors or a crash. Producers write at whatever rate arrives; consumers drain at their own provisioned rate. It lets you size workers for average load rather than peak, and it protects fragile downstreams from bursts they cannot absorb.

Beginner Difference between a work queue and a publish-subscribe topic?

A work queue is point-to-point: each message goes to exactly one consumer out of a pool of interchangeable workers — it divides work, and you scale throughput by adding consumers. Publish-subscribe broadcasts: every subscriber gets its own copy and does something different with it — it multiplies one fact across independent consumers, and you add capability by adding subscribers without touching the publisher.

Beginner What is the competing consumers pattern and what does it cost you?

Multiple identical workers pulling from one queue, each message handled by whichever worker is free. It gives near-linear throughput scaling and automatic redelivery if a worker dies. The costs: ordering is lost unless you partition by key, and consumers must be idempotent because at-least-once redelivery is normal, not exceptional.

Intermediate Your queue depth has been growing steadily for two hours. Walk me through the diagnosis and the fix.

First, confirm the shape: compare arrival rate against drain rate, and look at the age of the oldest message — that is what the user feels. Growth means arrival exceeds drain, so either the arrival rate rose or per-message processing got slower (a slow downstream, a lock, a bad deploy, a poison message causing retry loops). Then apply the three levers in order. Scale consumers, if the bottleneck is worker capacity and the downstream can take more concurrency — useless or harmful if the real bottleneck is a shared database. Shed load: drop or defer non-critical classes of work, and consider newest-first processing so current users get served while the backlog is written off. Reject at the front door: throttle producers so the backlog stops growing while you recover. Also isolate the offending message class onto its own queue so it cannot starve everything else. And say the underlying truth: a queue does not add capacity, so if average load genuinely exceeds average capacity, only more capacity or less load fixes it.

Intermediate A queue converts one kind of problem into another. Which, and why does that matter?

It converts an availability problem into a latency problem — requests that would have been rejected are now accepted and answered late. That is usually a good trade, but only while average consumer capacity exceeds average producer load. Below that line the queue grows without bound until retention, disk or patience runs out; it is a shock absorber, not an engine. So bound the queue explicitly (max depth or max age), decide what happens at the bound, and never present a queue as a capacity plan.

Intermediate Explain fan-out on write versus fan-out on read, and which you would pick.

Fan-out on write precomputes: at publish time you push a copy into every recipient's materialised list, so a read is one sequential fetch — fast and cheap, ideal when reads massively outnumber writes. Fan-out on read computes at request time by fetching from every source the reader follows and merging — writes are trivial and there is no derived state, but read latency and cost scale with the number of sources. Pick on the read-to-write ratio and the fan-out distribution. In practice neither pure form survives: use the hybrid.

Intermediate What is the celebrity problem and how do you solve it?

Under fan-out on write, one post by an account with tens of millions of followers becomes tens of millions of writes — a burst that saturates the write path, delays delivery for every other user, and grows storage with the follower graph. The fix is a hybrid: keep fan-out on write for ordinary accounts, and above a follower threshold skip the fan-out entirely, storing celebrity posts once and merging them in at read time from a small, heavily cached set. Readers then pay one cheap list fetch plus a merge over a handful of accounts.

Intermediate How do you handle work of different priorities?

Either a priority field on a single queue, or — more commonly and more robustly — separate queues per class with independently sized consumer pools, which also gives isolation so bulk work cannot consume the workers serving interactive traffic. Note that priority support is uneven across brokers (RabbitMQ supports it with caveats, Kafka has no concept of it). Whichever you choose, name starvation as the hazard and give a mitigation: weighted service in a fixed ratio rather than strict priority, ageing that promotes old messages, or reserved capacity for the low tier. Monitor oldest-message age per class, not aggregate depth.

Intermediate Batch or stream — how do you decide?

Start from the freshness requirement the business actually has, not the one that sounds impressive. Batch when results can be minutes or hours old, when the computation needs the complete dataset (global ranking, corpus-wide dedup, model training), when throughput per rupee matters, or when easy reprocessing after a bug is valuable — a rerun is far simpler than a replay. Stream when a decision must be made within seconds of the event (fraud, live dashboards, alerting, personalisation) and the team can operate a permanently running stateful job. Micro-batching is the middle ground: batch-shaped reasoning with a latency floor of a few seconds.

Intermediate You run a nightly reconciliation job on three replicas of your service. What goes wrong?

All three replicas fire it — three reconciliation runs, triple side effects, possibly triple payouts. Fixes, in increasing weight: a distributed lock the job must acquire first (ShedLock backed by the existing database or Redis, understanding that a lock without fencing is best-effort under long pauses); leader election so only the elected instance schedules; or a separate scheduler service that owns time and merely enqueues a message which ordinary competing consumers execute. Regardless, make the job idempotent and chunked so a re-run or interruption is harmless, and alert on the job that stopped firing — silence produces no errors.

Pro Is exactly-once delivery possible? What do you actually build?

Not across a network. A timeout is ambiguous — the sender cannot tell a lost message from a lost acknowledgement — so it must either resend (at-least-once, duplicates possible) or not (at-most-once, loss possible). Kafka's exactly-once is exactly-once processing inside its own boundary: idempotent producers plus transactions committing output records and offsets atomically; it does not extend to a payment gateway your consumer calls. The buildable target is at-least-once delivery plus idempotent consumers, which the user experiences as exactly-once.

Pro How do you make a consumer idempotent, and why is a naturally idempotent operation better than a dedup table?

Two routes. Explicit deduplication: every message carries a stable key — ideally a business key like the order id rather than a broker-generated id — and the consumer records processed keys, writing the key and the effect in one transaction so there is no race. That needs a retention window, so duplicates arriving after it slip through, and it is extra state to operate. Natural idempotency is better: set a field instead of incrementing it, upsert on a natural key instead of inserting, guard updates with an expected current state or version, and model transitions so re-applying is a no-op. Such operations survive redelivery, replay, backfill and reprocessing with no dedup infrastructure at all — design for it first, and bolt on deduplication only where the operation genuinely cannot be reshaped.

Pro Event time versus processing time — why does the distinction cause so many bugs?

Event time is when the thing happened; processing time is when your pipeline saw it. They diverge whenever a client is offline, a partition rebalances, or a consumer restarts and replays a backlog. Aggregate by processing time and your metrics describe your pipeline rather than your business — and a replay after an incident cheerfully attributes yesterday's events to today. Aggregate by event time and the numbers are meaningful, but you must now decide the late-data policy: a watermark declares when a window is presumed complete, and stragglers arriving afterwards are dropped, folded into an updated result within an allowed-lateness bound, or routed to a side output for correction. A pipeline with no stated policy still has one, and it is "quietly wrong".

Pro You commit an order to the database and then publish OrderPlaced, but the publish fails. What is this problem and how do you fix it?

The dual-write problem: two systems, one non-atomic sequence, so a crash between them leaves the database and the event stream disagreeing — an order nobody was told about (or, if you publish first, an event for an order that never committed). Distributed transactions across a database and a broker are the wrong tool at this scale. Use the transactional outbox: write the event into an outbox table in the same local transaction as the state change, and have a relay (a poller or change-data-capture reading the log) publish it afterwards. Publication is then at-least-once, which is fine because your consumers are idempotent.

Pro Your consumers acknowledge messages on receipt and then process them. Critique that.

It converts the system to at-most-once: a worker that crashes after the ack and before finishing loses the work silently, with no redelivery and no error anywhere. Acknowledge after the work is durably complete so a crash leads to redelivery — which is precisely why duplicates are normal and consumers must be idempotent. Acking early is usually a hidden attempt to fix a throughput or visibility-timeout problem, which is better addressed by scaling consumers, chunking the work, or extending the timeout deliberately.
