Module: API Design at Scale

An API is the hardest thing in a system to change, because you do not control the clients. Databases can be migrated overnight and services rewritten in a quarter, but a published contract is held hostage by every mobile app on a phone you will never see.

Knowledge Library → Courses → System Design track → API Design at Scale

What this module covers

Every other design decision in this track is reversible under pressure. You can shard a table, swap a cache, move a service to another region — all painful, all internal. An API is different: the moment a partner integrates or an app ships to a store, your contract is frozen for as long as those clients live, and "just update the callers" stops being an option. That asymmetry is the reason API design deserves its own module rather than a paragraph inside a framework tutorial.

This module is deliberately about strategy, not syntax. The Spring Boot track owns controllers, serialization and the annotations; the Microservices track owns choosing how two of your own services talk to each other. Here we cover the decisions that outlive whichever framework you are using this year: resource and error modelling, idempotency, pagination, filtering, versioning and deprecation, and then the protocol survey — gRPC, GraphQL, webhooks and the real-time transports — with the tradeoffs that decide which one belongs in a design.

Topics

REST maturity: the Richardson model as vocabulary, not a scorecard

Leonard Richardson's maturity model describes four rungs. Level 0 is a single endpoint that tunnels every operation through POST — the "swamp of plain old XML", and the shape most legacy SOAP-over-HTTP services take. Level 1 introduces resources: many URIs, one per thing, though still with verbs hidden in the payload. Level 2 introduces HTTP verbs and status codes used as the protocol intends — GET reads and is cacheable, PUT replaces, DELETE removes, and a 404 means what the RFC says it means. Level 3 adds hypermedia controls: responses carry links telling the client what it may do next, so state transitions are discovered rather than hard-coded.

The honest note interviewers respect: almost nobody reaches level 3, and that is usually fine. Roy Fielding's thesis makes hypermedia a defining constraint of REST, so most "REST APIs" in production — including Stripe's, GitHub's and Google's — are strictly level 2 and are none the worse for it. Hypermedia earns its cost in long-lived, multi-client, evolving contracts where the server genuinely wants to move clients around without redeploying them; it is dead weight on an internal CRUD service. Treat the model as a shared vocabulary for saying "we are at level 2 and deliberately so", not as a ladder you owe someone a climb up. What you should not skip from level 2 is the discipline underneath: model nouns rather than actions (/orders/1234/refunds, not /doRefund), keep collection and item URIs consistent and plural, and never invent a verb where an HTTP method already exists.

# Level 0 — one endpoint, verb in the body
POST /api          {"op":"cancelOrder","id":1234}

# Level 1 — resources, verb still in the payload
POST /orders/1234  {"op":"cancel"}

# Level 2 — resources + HTTP semantics (where most good APIs live)
POST   /orders/1234/cancellations      201 Created
GET    /orders/1234                    200 OK, cacheable
DELETE /orders/1234/reservations/9     204 No Content

# Level 3 — the response tells the client what it may do next
GET /orders/1234
{ "status":"placed",
  "_links":{ "cancel":{"href":"/orders/1234/cancellations","method":"POST"} } }

Status codes and error bodies a machine can act on

Status codes are the only part of your contract that intermediaries — proxies, CDNs, client libraries, retry middleware — understand without reading your documentation. Getting them right is therefore not pedantry, it is interoperability. The distinctions that matter in review: 200 versus 201 with a Location header for creation; 202 when you accepted work you have not finished (the correct answer for an async command); 204 for a successful write with nothing to say; 400 for a malformed request versus 422 for a well-formed one that violates business rules; 401 (who are you?) versus 403 (I know who you are and no); 409 for a conflict such as a version clash; 429 for throttling; and the hard rule that 5xx means you failed, so a validation error returned as 500 will make every client's retry logic hammer you for nothing.

The status code alone is never enough — clients need to distinguish "card declined" from "card expired", and a human-readable sentence in a message field cannot be branched on. Standardise on a machine-readable error body, and prefer the one that already has an RFC: RFC 9457 Problem Details for HTTP APIs (which obsoletes RFC 7807) defines type, title, status, detail and instance, served as application/problem+json, with extension members for your own fields. The critical piece is type: a stable URI that identifies the error class and never changes, so clients switch on it rather than string-matching your prose. Two rules complete the design — return all validation failures at once rather than one per round trip, and put a correlation id in every error so a support ticket maps to a trace.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type":     "https://api.example.com/problems/insufficient-funds",
  "title":    "Insufficient funds",
  "status":   422,
  "detail":   "Wallet balance 240.00 is below the 999.00 charge.",
  "instance": "/payments/98f1",
  "balance":  240.00,
  "traceId":  "0af7651916cd43dd8448eb211c80319c"
}

Idempotency: which methods have it, and why POST does not

An operation is idempotent when performing it many times has the same effect on server state as performing it once. HTTP fixes this per method: GET, HEAD and OPTIONS are safe (no state change at all, therefore trivially idempotent); PUT and DELETE are idempotent by definition — writing the same representation twice leaves the same resource, and deleting twice leaves it deleted (the second call returning 404 does not break idempotency, because the state is unchanged). POST and PATCH are not idempotent: POST /orders twice means two orders, and a PATCH of {"balance": "-100"} applied twice deducts twice.

This matters because of a fact you cannot engineer away: a network timeout is ambiguous. When a client's call to POST /payments times out, it does not know whether the request never arrived, or arrived and committed while the response was lost on the way back. There are only two safe responses to that ambiguity — never retry (and leave the user staring at "did my money go?"), or make the operation idempotent so retrying is free. Every serious payment, order and inventory API in the world chooses the second. That is why the resilience patterns from the Microservices track — retry with backoff and jitter, at-least-once message delivery, a queue redelivering after a consumer crash — are all quietly dependent on idempotent write endpoints. Retry without idempotency is not resilience, it is a duplicate-charge generator.

Idempotency keys: storing the response and replaying it

The mechanism is simple to state and easy to get subtly wrong. The client generates a unique key per logical operation — a UUID, generated once and reused across every retry of that same intent — and sends it as an Idempotency-Key request header. The server, before doing any work, atomically inserts the key into a store with a unique constraint. If the insert succeeds it is the first attempt: process the request, then persist the final status code and response body against that key in the same transaction as the business write. If the insert fails because the key exists, do not process anything — look up the stored response and replay it byte for byte, so the client's retry gets the identical 201 and the identical order id it would have got the first time.

The details that separate a working implementation from a broken one. Concurrency: two retries can arrive simultaneously, so the key record needs a state machine — in-flight, completed — and a concurrent request that finds in-flight must return 409 (or 425) rather than proceed; relying on "check then insert" without a unique index or lock is a race that will duplicate payments under exactly the load where it matters. Scoping: keys must be scoped per API key or account, or one tenant can collide with — and read the response of — another. Request fingerprinting: store a hash of the request body with the key and reject a reused key carrying a different payload with 422, otherwise a client bug silently returns the wrong resource. Expiry: keys are retained for a bounded window (Stripe uses 24 hours) because storing them forever is unbounded growth; document the window, because a retry after it expires will create a second order. Failures: only cache final outcomes — replaying a cached 500 forever would make a transient fault permanent, so 5xx results should release the key for a genuine retry.

POST /v1/payments
Idempotency-Key: 3f1a9c72-8e04-4a1f-9a3d-2b7c5e6d1f80
{ "amount": 49900, "currency": "inr", "order_id": "ord_8812" }

# First call  -> 201 Created  { "id": "pay_77Kd", "status": "captured" }
# Any retry with the same key and the same body
#              -> 201 Created  { "id": "pay_77Kd", ... }   replayed, no second charge
# Same key, DIFFERENT body     -> 422 Unprocessable Content (fingerprint mismatch)
# Same key, still processing   -> 409 Conflict (request in flight)

Pagination: offset versus cursor, and why the default is wrong

Offset pagination — ?page=3&size=20, compiled to LIMIT 20 OFFSET 40 — is the default in every framework and is wrong for most real datasets, for two independent reasons. It is unstable. The offset is computed against the table as it exists at the moment of each request, so if rows are inserted at the head of the ordering between page 1 and page 2, every item shifts down and the reader sees a record twice; a deletion makes a record vanish unseen. On a feed sorted by newest-first with concurrent writes, duplicates and skips are not an edge case, they are the normal outcome. It is slow at depth. The database cannot jump to row 100,000 — it must scan and discard the first 100,000, so cost grows linearly with the offset and page 5,000 is thousands of times more expensive than page 1. This is the classic production incident where an integration partner "just downloads everything by paging" and takes the database down.

Cursor (keyset) pagination fixes both. Instead of "skip 40 rows", it says "give me rows after this exact position": WHERE (created_at, id) < (:last_created_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20. The tuple comparison is answered directly from the index, so page 5,000 costs the same as page 1, and because the cursor names a row rather than a count, concurrent inserts cannot shift the window. Note the tiebreaker column: sorting on a non-unique key alone will skip or repeat rows at page boundaries, so always append a unique id to both the sort and the cursor. The cost is real — you cannot jump to page 50, you cannot show "page 7 of 412" without a separate (often approximate) count, and the cursor should be opaque (base64 the tuple) so clients do not build on its internals and you can change the sort later.

The recommendation: make cursor pagination the default for anything that grows or is sorted by time — feeds, event logs, transaction histories, sync and export endpoints. Keep offset only where a human is browsing a small, mostly-static, numbered result set and genuinely wants to click "page 5". Whichever you choose, make the page size a server-enforced part of the contract: a default, a hard maximum, and a clamped rather than rejected over-large request.

-- Offset: unstable under concurrent inserts, and scans 100k rows to discard them
SELECT id, created_at FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100000;

-- Keyset: index seek straight to the cursor position, constant cost at any depth
SELECT id, created_at FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)   -- unique tiebreaker matters
ORDER BY created_at DESC, id DESC
LIMIT 20;

Filtering, sorting, sparse fieldsets — and the over-fetching problem

Once a collection endpoint exists, clients will want subsets of it, and if you do not design the convention they will invent one per endpoint. Settle three things once and apply them everywhere. Filtering: either simple field equality in the query string (?status=shipped&region=south), which is easy to cache and easy to validate but cannot express ranges or disjunction, or a small documented expression language in a single filter parameter (Google's AIP-160 style, ?filter=status="shipped" AND total>5000), which is far more expressive and correspondingly more work to parse safely. Pick one and never accept raw SQL fragments from a client. Sorting: one parameter, a documented allow-list of sortable fields (each of which needs an index), and a stable syntax such as ?sort=-created_at,id. Sparse fieldsets: ?fields=id,total,status lets a client that needs three columns avoid pulling forty.

That last one exists because of over-fetching: a REST resource has one fixed representation, so the mobile list screen that needs a name and a thumbnail receives the entire user object with addresses and preferences, wasting bandwidth on exactly the connections least able to afford it. Its twin is under-fetching, better known as the client-side N+1: the list endpoint returns 50 orders, each carrying a customer id, so the client fires 50 more requests to render customer names. The usual REST answers are an expand/include parameter for controlled embedding, and purpose-built composite endpoints for the two or three screens that matter — the backend-for-frontend pattern. These are pragmatic, but they multiply endpoints and they are the exact itch GraphQL was invented to scratch, which is where the second half of this module begins.

Versioning strategy, expand-contract, and how to retire an endpoint

Four mechanisms, and you should be able to argue all four. URI path (/v1/orders): ugly to purists because the same entity now has two URIs, but overwhelmingly the most common in practice — visible in logs, trivially routable at the gateway, testable from a browser, and instantly understood by every consumer. Query parameter (/orders?version=1): easy to add and easy to default, but easy to lose in a copy-paste and it pollutes cache keys. Custom header (X-API-Version: 1): keeps URIs clean, but is invisible in a browser, awkward in curl and easy for intermediaries to strip. Media-type negotiation (Accept: application/vnd.acme.order.v2+json): the most correct answer by HTTP's own design and the one Fielding endorses, and the least used, because tooling support is thin and most client developers have never done it. Recommendation: major version in the URI path, one number only (v1, never v1.2.3), a small number of live versions, and every version pinned to a documented lifetime.

The better move, though, is to version as rarely as possible. Most changes are additive, and additive changes need no version at all if you have agreed tolerant reader semantics up front: clients must ignore unknown fields, must not depend on field order, and must treat unrecognised enum values as a documented fallback rather than crashing. With that contract, adding a field or a new optional parameter is a non-event. For the changes that genuinely break, use expand-contract (parallel change): expand by adding the new field or endpoint alongside the old, writing to both; migrate consumers while both work, using per-client telemetry to see who is still on the old path; contract by removing the old one only once that telemetry reads zero. Deprecation itself is a design artefact, not an email: announce a date, return the Deprecation and Sunset headers (RFC 8594) with a Link to the migration guide, monitor usage per consumer, and — if you can — run brownouts, short deliberate outages of the old path, so integrators discover the deadline while there is still time to act rather than on the day it disappears.

GET /v1/orders/1234
HTTP/1.1 200 OK
Deprecation: Sun, 01 Feb 2026 00 00 00 GMT
Sunset: Wed, 01 Jul 2026 00 00 00 GMT
Link: <https://developer.example.com/guides/v2-migration>; rel="deprecation"; type="text/html"
Warning: 299 - "v1 of this endpoint is deprecated; migrate to /v2/orders"

Limits are part of the contract: rate limits, page caps and payload size

An API without published limits has an implicit limit anyway — the point at which it falls over — and clients will find it. Make the limits explicit and machine-readable so a well-behaved client can be well-behaved. Return 429 when a caller exceeds its quota, always with Retry-After so the client waits the right amount instead of guessing, and advertise remaining budget on every response through the emerging RateLimit header fields (the IETF draft standardises the limit, remaining and reset triplet that GitHub, Twitter and others each invented separately). Distinguish 429 (slow down, you may retry) from 403 (you are not entitled to this at all) — conflating them makes clients retry something that will never succeed.

The same logic applies to every other bound. Cap and document maximum page size, maximum request body size, maximum array lengths in a batch endpoint, and maximum query depth or cost for GraphQL. Publish quotas per plan or per tenant rather than one global number, so a single noisy integrator cannot consume the capacity of everyone else — the fairness argument from the Rate Limiting module applies directly here, and this is the point where that mechanism becomes visible in your public contract. Two designs earn goodwill: return a 429 that names which limit was hit, and offer a sandbox or a higher burst allowance so integrators discover their limits during development rather than during their launch.

gRPC: strong contracts, HTTP/2 and streaming for service-to-service

gRPC is a contract-first RPC framework: you write a .proto file describing services and messages, and the compiler generates client stubs and server skeletons in a dozen languages. Two properties make it the default for internal, high-volume, low-latency paths. First, Protocol Buffers — a compact binary encoding with field numbers rather than names on the wire, so payloads are several times smaller than JSON and parsing costs far less CPU; the numbering also gives you clean evolution rules (add fields freely, never reuse a retired field number, reserve what you remove). Second, HTTP/2 — one long-lived multiplexed connection carries many concurrent calls without head-of-line blocking at the request level, with header compression and full-duplex framing. On top of that sit four call types: unary, server streaming, client streaming and bidirectional streaming, plus deadlines, cancellation propagation and pluggable interceptors as first-class parts of the model rather than bolt-ons.

The tradeoffs are equally clear. It is awkward from browsers: browser JavaScript cannot control HTTP/2 frames, so the web story requires gRPC-Web plus a proxy (Envoy or a language-specific translator) and, until recently, no client streaming. The binary payload is not human-readable, so debugging needs tooling — you cannot curl an endpoint and read the answer, and generic HTTP caching, browser dev-tools and many API gateways understand nothing of what is inside. The build gains a code-generation step, and the whole estate needs a schema registry and review discipline or the contracts drift. The design rule that survives interviews: gRPC inside, REST or GraphQL at the edge — internal service-to-service calls where both ends are yours and performance matters, HTTP/JSON where third parties, browsers and long-lived public contracts live.

syntax = "proto3";
package orders.v1;

service OrderService {
  rpc GetOrder    (GetOrderRequest) returns (Order);              // unary
  rpc WatchOrders (WatchRequest)    returns (stream OrderEvent);  // server streaming
}

message Order {
  string id     = 1;   // field NUMBERS are the wire contract, not the names
  int64  amount = 2;
  reserved 3;          // retired field: never reuse the number
  string currency = 4; // additive change — old clients simply ignore it
}

GraphQL: the client writes the query, and the costs that follow

GraphQL inverts who decides the response shape. The server publishes a typed schema of everything available; the client sends a query naming exactly the fields it wants, across as many related entities as it likes, and gets back one response with precisely that shape. Over-fetching disappears because nobody asks for fields they will not render; under-fetching disappears because one round trip can traverse orders to customers to addresses. For a product with several very different clients — an Android app, an iOS app, a web console and a partner integration — each evolving at its own pace, that is a genuine and large win, and it removes the endless proliferation of near-duplicate REST endpoints and backend-for-frontend layers.

The costs are equally structural, and interviews probe them. Caching is harder: queries are typically POSTed to a single /graphql URL, so HTTP caching, CDNs and browser caches — the free, enormously effective layer REST gets by default — no longer apply, and you must replace them with persisted queries plus per-field client and server caches. Resolvers reintroduce N+1: a query for 50 orders each with a customer will naively execute 1 query for orders and 50 for customers, because each resolver runs independently; the standard fix is a dataloader that batches and de-duplicates the per-field loads within a single request tick, and no serious GraphQL service runs without it. A malicious or careless query can be a denial of service: deeply nested or recursive selections can ask for a combinatorial amount of work in a single small request, so a public GraphQL endpoint needs depth limiting, complexity/cost analysis with a per-caller budget, pagination enforced on every list field, and normally an allow-list of persisted queries. Add to that harder rate limiting (requests are not equal in cost, so you meter cost, not calls) and coarser observability, since every call is one POST /graphql in the access log until you instrument operation names.

Webhooks: server-to-server push, and the delivery contract behind it

A webhook inverts the direction of a normal API call: instead of the integrator polling you every minute for "has this payment settled yet?", you POST the event to a URL they registered. It is the standard mechanism for third-party notification — payment gateways, CI systems, messaging providers — and it removes an enormous amount of wasted polling traffic. But it makes you an HTTP client calling an endpoint you do not operate, which imports every distributed-systems problem in this course into your outbound path.

Design it as a delivery system, not a fire-and-forget call. Guarantees: webhooks are at-least-once, not exactly-once — a receiver may be slow, respond after you time out, or fail after processing — so every event carries a stable event_id and receivers must deduplicate on it. Ordering is not guaranteed either: include a sequence number or timestamp and tell receivers to handle out-of-order arrival. Retry: exponential backoff with jitter over hours or days, a bounded attempt count, then a dead-letter queue plus a UI where the integrator can inspect and replay failures; disable or throttle endpoints that fail persistently so one dead consumer does not consume your delivery workers. Signing: HMAC the raw request body with a shared secret and send it in a signature header so the receiver can verify authenticity — this is essential, because the endpoint is public and anyone can post to it. Replay protection: include the timestamp inside the signed payload, reject anything outside a small tolerance window, and require constant-time comparison of the signature. Receiver etiquette to document: respond 2xx immediately and process asynchronously, because doing work before responding turns your timeout into their retry storm. The Standard Webhooks specification encodes most of this if you would rather adopt than invent.

Real-time transports: long polling, server-sent events, WebSocket

Short polling is the baseline — ask every few seconds — and it is wasteful in exact proportion to how fresh you want the data: most responses are empty, and latency is bounded below by the interval. Long polling improves on it by having the server hold the request open until there is something to say (or a timeout fires), then the client immediately re-requests. It is plain HTTP, works through every proxy ever built, and needs no special client support, but it costs one held connection and one server-side wait per client, and every message pays the cost of tearing down and re-establishing a request.

Server-sent events is the underrated middle option: a single long-lived HTTP response streaming text/event-stream frames, one-way from server to client, consumed by the browser's built-in EventSource. Because it is ordinary HTTP it passes through proxies, gateways and existing auth unchanged, and the standard gives you automatic reconnection with a Last-Event-ID header for free — resumability without you writing any of it. Its limits: one direction only (client-to-server still needs normal requests), text frames rather than binary, and a per-domain connection cap on HTTP/1.1 that HTTP/2 multiplexing removes. WebSocket is the full-duplex option: an HTTP request is upgraded to a persistent bidirectional socket over which either side sends text or binary frames with almost no per-message overhead. That power costs you a stateful, non-HTTP protocol — separate authentication and authorization design, no HTTP caching or standard status codes, extra work in load balancers and gateways, and you must implement your own heartbeats, reconnection and message-resumption logic.

The decision rule: if updates flow only server-to-client — live scores, order status, notifications, a progress bar, streaming tokens from a model — use SSE; if both sides send messages frequently and latency matters — chat, collaborative editing, multiplayer, trading — use WebSocket; if you must traverse hostile infrastructure or support an ancient client, fall back to long polling. Do not reach for WebSocket by default: teams routinely pay its operational cost for a feed that only ever flows one way.

At scale, the problem changes shape. Persistent connections make your servers stateful, and that breaks the assumptions of the Scaling Basics module. Each connection consumes a file descriptor and memory for its lifetime, so capacity is measured in concurrent connections, not requests per second, and a million users means a connection-management tier sized independently from your business logic. Load balancers must be configured for long-lived connections (generous idle timeouts, connection-aware rather than request-aware balancing), and a deploy that restarts a node disconnects every client on it — which then all reconnect at once, so reconnection needs jittered backoff or your own rollout becomes a thundering herd. Because a message for user X must reach whichever node holds X's socket, you need either sticky routing plus a registry of connection-to-node, or a pub/sub backplane (Redis, Kafka, NATS) that fans every message out to all nodes. Scaling out is therefore not "add a pod": it is a design decision made at the same time you choose the transport.

# Server-sent events: one long-lived HTTP response, plain text frames
GET /orders/1234/events            Accept: text/event-stream
HTTP/1.1 200 OK                    Content-Type: text/event-stream

id: 42
event: status
data: {"status":"packed"}
          <- browser EventSource reconnects automatically and
             resends Last-Event-ID: 42 so nothing is missed

# WebSocket: an upgrade handshake, then a bidirectional frame stream
GET /chat  HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
HTTP/1.1 101 Switching Protocols   # no more HTTP semantics after this line

Choosing between the styles in a design round

Interviewers rarely ask "what is GraphQL?" — they ask you to choose, and then defend it. A defensible order of reasoning: start from the consumer (browser, mobile app, partner integration, or your own service), then the direction and frequency of data flow (request-response, one-way push, or genuinely bidirectional), then the coupling you can afford (a public contract you can never break, versus an internal one you can redeploy on both sides in an afternoon). That usually lands you on: REST over HTTP/JSON for public and browser-facing APIs, gRPC for internal service-to-service hot paths, GraphQL where many heterogeneous clients need different slices of a rich graph, webhooks for third-party event notification, and SSE or WebSocket for live updates according to the direction rule above.

Two closing points worth making out loud in an interview. First, these are not exclusive — a healthy estate runs REST at the edge, gRPC inside, a webhook fleet for partners and an SSE endpoint for live status, all in the same product, chosen per boundary rather than per company. Second, whichever you pick, the design work in the first half of this module does not go away: idempotency, pagination, error taxonomy, limits and a deprecation policy are needed just as much in a gRPC or GraphQL contract as in a REST one — the protocol changes the syntax of the answer, not the questions.

Interview questions

API design is one of the few system design topics that appears in both the design round and the backend round, so Indian product and service companies ask it at every level — from "what does PUT versus PATCH mean" in a screening call to idempotency-key concurrency in a senior loop:

Beginner Which HTTP methods are idempotent, and which are safe?

Safe (no state change): GET, HEAD, OPTIONS — and anything safe is automatically idempotent. Idempotent but not safe: PUT and DELETE. Not idempotent: POST and PATCH. PUT is idempotent because sending the same representation twice leaves the resource in the same state; DELETE is idempotent because the resource is gone either way (the second call returning 404 does not break it — idempotency is about server state, not the response code). POST creates a new resource each time, and a PATCH such as "decrement by 100" applies twice.

Beginner PUT vs PATCH vs POST — when do you use each?

POST creates a subordinate resource (or triggers a process) and is not idempotent; the server assigns the identifier and returns 201 with a Location header. PUT replaces the resource at a known URI in full — send every field, because omitted fields are removed — and is idempotent. PATCH applies a partial modification, and whether it is idempotent depends on the patch: setting a field is, incrementing one is not. Use PUT when the client owns the identifier and sends the whole object, PATCH for partial updates, POST for creation and for operations that do not map to a resource replacement.

Beginner Explain the Richardson maturity model. What level are most real APIs at?

Level 0: one endpoint, one verb, operation named in the payload. Level 1: many resource URIs. Level 2: correct use of HTTP verbs and status codes. Level 3: hypermedia controls (HATEOAS) — responses carry links describing available transitions. Most production APIs, including Stripe's and GitHub's, are level 2, and deliberately so: hypermedia pays off mainly for long-lived contracts with many independent clients you want to steer without redeploying them. Fielding's definition makes level 3 the only "true" REST, which is worth knowing but not worth arguing about in a design round.

Beginner A client sends a well-formed request that violates a business rule. Which status code?

422 Unprocessable Content — the syntax parsed fine, the semantics failed. Reserve 400 for genuinely malformed requests (bad JSON, missing required parameter, wrong type). Do not return 500 for validation failures: 5xx tells every retry layer in the chain that the problem is yours and transient, so they will retry a request that can never succeed. And do not return 200 with an error field in the body — intermediaries and generated clients cannot see it.

Intermediate Design an idempotency key mechanism for POST /payments. Walk through the storage and the concurrent case.

The client generates a UUID per logical payment attempt and sends it as Idempotency-Key, reusing it on every retry. The server inserts the key into a table with a unique constraint before doing any work, scoped by API key or account so tenants cannot collide. If the insert wins, mark it in-flight, process the payment, then persist the final status code and response body against the key in the same transaction as the business write, and mark it completed. If the insert loses because the key exists: completed means replay the stored response verbatim (same 201, same payment id, no second charge); in-flight means a concurrent duplicate is being processed, so return 409 rather than proceeding. Also store a hash of the request body and return 422 if the same key arrives with different content, expire keys after a documented window such as 24 hours, and release the key on 5xx so a genuinely failed attempt can be retried rather than replaying a cached failure forever.

Intermediate Offset vs cursor pagination — which would you choose for a social feed and why?

Cursor (keyset). Offset pagination has two fatal properties on a feed: it is unstable, because new posts inserted between requests shift every row down so page 2 repeats items from page 1 (and deletions skip items); and it degrades linearly, because LIMIT 20 OFFSET 100000 makes the database scan and discard 100,000 rows. Keyset pagination asks for "rows after this position" using an indexed tuple comparison on (sort_key, unique_id), so cost is constant at any depth and concurrent inserts cannot shift the window. The tradeoffs to state: no jumping to page 50, no cheap total count, and the cursor should be opaque so clients cannot depend on its structure. Offset stays acceptable for small, static, numbered admin tables.

Intermediate Why do you need a unique tiebreaker column in a cursor?

Because the sort key is usually not unique. If ten orders share the same created_at value and your cursor says "created_at less than X", the page boundary falls in the middle of that group and you will either skip rows or return them twice, depending on the comparison. Sorting and cursoring on the tuple (created_at, id) with a strict tuple comparison makes the ordering total, so every row has exactly one position and the boundary is unambiguous. The index must cover the same tuple in the same order, or you lose the seek and go back to scanning.

Intermediate How would you version a public API, and how do you avoid versioning most of the time?

Major version in the URI path (/v1/orders) — least elegant, most practical: visible in logs, routable at the gateway, understood by everyone. Alternatives are a query parameter (easy to lose, pollutes cache keys), a custom header (clean URIs, invisible in a browser, strippable by proxies), and media-type negotiation via Accept (most correct per HTTP, poorest tooling). Avoid versioning by making additive changes non-breaking: publish tolerant-reader rules (ignore unknown fields, do not depend on order, handle unknown enum values), so adding a field needs no new version. For real breaking changes use expand-contract — add the new shape alongside the old, migrate consumers while both work, and remove the old only when per-client telemetry shows zero use.

Intermediate WebSocket or SSE for a live order-tracking screen? Justify it.

SSE. The data flows one way — the server pushes status changes and the client sends nothing back over that channel — and SSE is plain HTTP, so it passes through existing proxies, gateways, auth and TLS termination unchanged, and gives automatic reconnection with Last-Event-ID resumption for free. WebSocket would add a stateful non-HTTP protocol, its own auth design, load-balancer configuration, and hand-written heartbeat and reconnect logic, for capability the feature does not use. Choose WebSocket when both directions carry frequent messages — chat, collaborative editing, multiplayer, trading. Choose long polling only when infrastructure or an old client forces it.

Intermediate When would you pick gRPC over REST, and what do you give up?

Pick gRPC for internal service-to-service calls where both ends are yours, volume is high and latency matters: Protobuf's binary encoding is compact and cheap to parse, HTTP/2 multiplexes many concurrent calls over one connection, the generated stubs give a strongly typed contract in every language, and streaming plus deadlines and cancellation are built in. You give up browser friendliness (gRPC-Web needs a proxy), human readability and easy debugging, standard HTTP caching and gateway/tooling support, and you take on a code-generation step and schema governance. The usual architecture is gRPC inside, REST or GraphQL at the edge.

Pro GraphQL solves over-fetching. What does it cost you, and how do you run it safely in public?

Three costs. Caching: queries POST to one URL, so HTTP/CDN/browser caching stops working and must be replaced with persisted queries and per-field caches. Resolver N+1: each field resolves independently, so 50 orders each needing a customer becomes 51 queries unless a dataloader batches and de-duplicates loads within the request. Denial of service: a small deeply nested or recursive query can request combinatorial work, so a public endpoint needs depth limits, query cost analysis with a per-caller budget, mandatory pagination on list fields, timeouts, and ideally an allow-list of persisted operations. Add cost-based rather than call-based rate limiting, and instrument operation names or your access logs are one undifferentiated POST /graphql.

Pro Design the delivery guarantees for a webhook system. What do you promise consumers?

Promise at-least-once delivery, not exactly-once, and not ordering. Every event carries a stable event_id and a sequence number or timestamp so receivers can deduplicate and detect out-of-order arrival. Retry with exponential backoff and jitter over hours, bounded attempts, then a dead-letter store with a self-service replay UI; throttle or auto-disable endpoints that fail persistently so one dead consumer cannot starve the delivery workers. Sign the raw body with an HMAC over a shared secret, include the timestamp inside the signed payload, reject anything outside a tolerance window, and require constant-time signature comparison — the endpoint is public, so authenticity and replay protection are not optional. Document that receivers should return 2xx immediately and process asynchronously, since doing work before responding turns your timeout into their duplicate delivery.

Pro You must remove a field from a public API used by a mobile app you cannot force-update. What is your plan?

Accept that the old clients never change, and use expand-contract. Expand: add the replacement field or endpoint alongside the old one and dual-write, so both are correct simultaneously. Announce deprecation with a date, and return Deprecation and Sunset headers (RFC 8594) plus a Link to the migration guide on every response from the old path. Instrument usage per API key and per app version so it is clear exactly who is still calling it, and contact those consumers directly rather than relying on a blog post. Consider scheduled brownouts — short deliberate failures of the old path — so integrators discover the deadline while they still have time. Contract only when telemetry reads zero, or when the remaining traffic is from app versions you have formally end-of-lifed; if a long tail cannot migrate, pin them to a frozen major version behind the gateway instead of breaking them.

Pro Your service holds a million WebSocket connections. What breaks first, and how do you scale it?

Capacity stops being requests per second and becomes concurrent connections: file descriptors, per-connection memory and kernel socket buffers, so you size and scale a connection tier separately from business logic. Load balancers need long idle timeouts and connection-aware balancing, since a request-level round robin means nothing when one connection lives for hours. Routing breaks next: a message for user X must reach the exact node holding X's socket, so you need either sticky routing plus a connection registry, or a pub/sub backplane (Redis, Kafka, NATS) fanning every message to all nodes and letting each drop what it does not own. Deploys are the third problem — restarting a node disconnects everyone on it and they all reconnect at once, so reconnection must use jittered backoff and rollouts must drain gradually. If the traffic is really one-way, SSE removes most of this by staying inside plain HTTP.

Pro A partner's retry logic is duplicating orders through your API. Diagnose it and design the fix on both sides.

The cause is almost always an ambiguous timeout on a non-idempotent POST: the request committed, the response was lost, and their retry created a second order. Server side, add an idempotency key contract as described above, and additionally enforce a business-level uniqueness constraint — a unique index on (customer, external_order_ref) or on a client-supplied request id — so even a client that ignores the header cannot double-book. Return the existing resource with the original status code rather than an error, so a duplicate looks like success. Client side, they must generate the key once per intent and hold it across retries — generating a fresh UUID inside the retry loop is the single most common bug and defeats the whole mechanism. Then reconcile: deduplicate the existing damage on the natural key, and add an alert on duplicate-key rates so the next occurrence is detected by you rather than by the customer.
