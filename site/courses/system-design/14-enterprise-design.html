Module: Enterprise Application Design

The previous thirteen modules were about systems at scale. This one is about the codebase you will actually open tomorrow morning — how to shape it so it survives five years of change — and about the other half of the job nobody teaches: explaining a design out loud, under time pressure, to someone who is judging you.

Knowledge Library → Courses → System Design track → Enterprise Application Design

What this module covers

Everything so far has been about the shape of a system: how it shards, caches, queues, replicates and degrades. Almost none of that decides whether your team can still ship features in year three. That is decided by the internal architecture of each service — where the dependencies point, which code is allowed to know about which other code, and whether those rules are written down or merely remembered.

So this closing module works at two altitudes. First, the application-level styles you will be asked to defend: layered, hexagonal, onion and clean, and vertical slice — compared honestly, including what they cost. Then the modular monolith as the sane default for most teams, with the tooling that makes its boundaries real rather than aspirational. Then the two artefacts that keep a design legible to other humans: architecture decision records and C4 diagrams. Finally, the design interview itself, taught as a repeatable procedure with a time budget, a list of behaviours that score and lose points, and a compact mock walkthrough that applies the whole track.

Topics

Layered architecture: the familiar default, and where its dependency direction hurts

Classic n-tier splits an application horizontally: a presentation layer holding controllers and DTOs, a service or business layer holding orchestration, and a data access layer holding repositories and the persistence model. Each layer may call only the layer beneath it. It is the shape almost every Spring codebase starts in, every developer recognises it in ten seconds, and for a genuinely CRUD-shaped service it is completely fine — you should not apologise for it.

The problem is the direction of the arrows. Every layer ends up pointing down toward the database, so the domain layer imports repository interfaces, entity annotations and driver types, and the business rules quietly become a thin coating on the persistence model. Two symptoms follow. Domain tests need a database (or a mountain of mocks) because the domain cannot be instantiated without infrastructure. And a change of infrastructure — swap the ORM, move a table to a different store, put a queue in front of a write — ripples upward through code that had no business caring. Fowler's point is worth internalising: layering is a fine first split, but it is a technical split, and a large system usually needs a domain split above it.

Hexagonal architecture: ports and adapters

Alistair Cockburn's formulation inverts the picture. Put the application at the centre. It defines ports — interfaces expressed entirely in its own vocabulary, with no framework or driver types in the signatures. Everything outside is an adapter that implements or drives a port: an HTTP controller, a CLI, a scheduled job and a message listener are all driving adapters on the left; a JPA repository, an S3 client, an SMTP sender and a payment gateway are all driven adapters on the right. The intent of the hexagon shape is only "there are several sides, not two" — it is not six of anything.

The payoff is symmetry and testability. The database is not privileged; it is just another adapter, exactly like the web framework. Your domain compiles and runs with no Spring on the classpath, so the interesting tests are plain unit tests with in-memory fakes for the driven ports, and the slow integration tests shrink to "does this one adapter honour its port's contract?". The discipline that makes it work is unglamorous: the port interfaces live with the domain, not with the adapter that implements them, and no framework annotation or persistence type ever crosses into the centre.

// domain package — a driven port, owned by the domain, no framework types
public interface PricingRules { Money priceFor(Sku sku, Quantity qty); }
public interface OrderRepository { Optional<Order> byId(OrderId id); void save(Order o); }

// domain package — a driving port: the use case the outside world may invoke
public interface PlaceOrder { OrderId handle(PlaceOrderCommand cmd); }

// adapter package — infrastructure implements the port; the arrow points inward
@Repository
class JpaOrderRepository implements OrderRepository { /* JPA lives only here */ }

Onion and clean architecture: one idea, three drawings — and its honest cost

Jeffrey Palermo's onion architecture and Robert Martin's clean architecture are not rivals to hexagonal; they are the same rule redrawn with more rings and more naming. Clean architecture's concentric circles run entities, use cases, interface adapters, frameworks and drivers, governed by one Dependency Rule: source code dependencies point only inward. Nothing in an inner circle may name anything in an outer circle. Where an inner circle needs to call outward, you invert it — the inner circle declares the interface, the outer circle implements it. That is dependency inversion doing all the work, and it is the single idea shared by hexagonal, onion and clean. If you learn one sentence from this section, learn that one; interviewers reward the candidate who says "these are three drawings of the same rule" over the one who recites three diagrams.

Now the honest caution, because the internet rarely gives it. This style buys you replaceability and fast tests, and it charges indirection: extra interfaces, mapping between domain models and persistence models and API models, more files per feature, and a longer path from a stack trace to the line that matters. On a service whose "business logic" is validate-then-save, that is a poor trade — you get ceremony and no protection. Apply it where the domain is genuinely rich or genuinely long-lived, keep it thin where it is not, and be able to say which parts of your system deserve it. "We used clean architecture everywhere" is a weaker answer than "we used it in the two modules with real rules and kept the rest a plain layered CRUD service."

Vertical slice architecture: the reaction against organising by layer

Jimmy Bogard's vertical slice architecture starts from an observation about how change actually arrives. Nobody files a ticket that says "modify the repository layer". They ask for a feature, and a feature cuts through every layer at once — so if your folders are controller/, service/, repository/, then every change touches four directories and each of those directories is coupled to a dozen unrelated features. Slice the other way: one folder per use case, containing that use case's request, handler, validation and persistence access, and let the slice choose its own internals. Coupling within a slice is fine and expected; coupling between slices is the thing you police.

The liberating consequence is that abstraction becomes a per-slice decision rather than a project-wide edict. A complex "place order" slice can hold a rich domain model behind ports; a "get order summary" slice can be a single hand-written query straight to the read model, with no repository interface and no mapping ceremony, and both can live in the same codebase without anyone feeling guilty. The risk is the mirror image: without review discipline you get duplicated rules smeared across slices and no single place where an invariant is enforced. In practice teams combine the two — vertical slices for organisation, a shared domain core for the rules that must not be duplicated.

The modular monolith: the default recommendation for most teams

After thirteen modules of distributed systems, the most useful thing this track can tell you is that you probably should not start distributed. A modular monolith is one deployable artefact containing several modules, each of which owns its own data, exposes a small published interface, and is forbidden from reaching into another module's internals or tables. You get the properties people actually buy microservices for — clear ownership, independent reasoning, the ability to extract a module later — without network calls, distributed transactions, per-service pipelines or a tracing bill for a five-engineer team.

Frame the tradeoff the way a senior engineer would. Microservices buy independent deployment and independent scaling, and they cost you eventual consistency, partial failure, operational surface and a much harder debugging story. If your real constraint is "we cannot find the code that owns this rule", that is a modularity problem, and modularity is free inside a single process. Split later, along boundaries you have already proved by keeping them clean — which is exactly why Fowler's advice is to earn the split rather than to assume it. Shopify's much-cited migration went the same direction: not monolith to microservices, but messy monolith to modular monolith.

Making boundaries real: Spring Modulith, ArchUnit, Java modules and package-private discipline

A boundary that exists only in a wiki diagram is not a boundary. Someone under deadline will autocomplete an import across it, review will not catch it, and eighteen months later the "modules" are a single ball of mud with optimistic package names. The fix is to make the rule executable, so that violating it fails the build rather than disappointing an architect.

The JVM gives you four escalating levels. Package-private by default is the cheapest and most underrated: put each module in its own package, make only the published interface public, and the compiler enforces the rest for free. Spring Modulith formalises that convention — top-level packages under the application package are modules, nested packages are internals, and ApplicationModules.of(App.class).verify() is a JUnit test that fails on illegal dependencies and cycles; it also publishes module documentation and encourages event-based communication between modules instead of direct calls. ArchUnit expresses arbitrary rules as ordinary unit tests — "nothing in ..domain.. may depend on ..infrastructure..", "no cycles between slices", "controllers may not touch repositories" — which is the direct way to enforce hexagonal or clean dependency direction. The Java Platform Module System is the strongest option, enforcing exports at compile and run time, at the cost of real migration effort.

// Spring Modulith: the whole structural check is one test
@Test void modulesRespectTheirBoundaries() {
    ApplicationModules.of(ShopApplication.class).verify();   // fails on illegal deps + cycles
}

// ArchUnit: the hexagonal rule, enforced by the build
@ArchTest static final ArchRule domainIsPure = noClasses()
        .that().resideInAPackage("..domain..")
        .should().dependOnClassesThat()
        .resideInAnyPackage("..infrastructure..", "..web..", "jakarta.persistence..");

Architecture Decision Records: capturing the why before it evaporates

Code records what you decided. It never records why, and the why is what evaporates. Two years on, a new joiner sees an odd choice — a synchronous call where a queue seems obvious, a denormalised table, a home-grown scheduler — and has exactly two options: ask someone who has probably left, or rip it out and rediscover the constraint the hard way. An architecture decision record is a short markdown file, numbered and immutable, that preserves the reasoning. Michael Nygard's original template has four parts: context (the forces in play — load, deadlines, team skills, existing contracts), decision (what we will do, in active voice), status (proposed, accepted, deprecated, or superseded by ADR-0042), and consequences (what becomes easier and what becomes harder — both, honestly).

Three habits make ADRs stick. Keep them in the repository, next to the code, in the same pull request as the change — a decision log in a wiki nobody opens is a decision log nobody reads. Never edit an accepted record: supersede it with a new one, so the history of your thinking survives. And write one only for decisions that are expensive to reverse — the datastore, the consistency model, the auth scheme, the module boundaries — not for every library choice, or the signal drowns. Thoughtworks put lightweight ADRs on the "adopt" ring of its Technology Radar for exactly this reason, and being able to describe them fluently is an easy differentiator in an architect-level round.

=== ADR-0007: Use outbox table for order events ===
Status: Accepted (supersedes ADR-0004)
Context: Orders must publish an event on commit. Dual-writing to Postgres and
  Kafka loses events on partial failure; XA is not available on managed Kafka.
Decision: Write events to an outbox table in the same transaction; a relay
  polls the table and publishes, with at-least-once delivery downstream.
Consequences: Atomicity solved; consumers must be idempotent; adds a relay
  to operate, and event publication is now asynchronous by a small delay.

C4: drawing systems at the level your audience needs

Most architecture diagrams fail for one reason: they mix altitudes. A single picture shows a load balancer next to a Java class next to an org chart, with arrows whose meaning changes halfway across the page. Simon Brown's C4 model fixes this by defining four nested levels and insisting each diagram stays on one. Context — one box for your whole system, surrounded by the people and external systems it talks to; readable by anyone, including a product manager. Container — the separately deployable or runnable things inside it: the web app, the API, the database, the message broker, the mobile client, with technology and protocol on each arrow. This is the level most engineering conversations actually want. Component — the major building blocks inside one container. Code — a class diagram, which you should almost never draw by hand because the IDE generates it better.

The practical rules matter more than the notation. Draw the level that matches your audience and stop; a container diagram plus a short paragraph beats a wall of boxes. Give every diagram a title, a legend and unambiguous arrow labels — "sends order confirmation email using SMTP" rather than a bare line. Notation is deliberately not prescribed: any consistent shapes work, as long as the levels are honest. In an interview, saying "let me draw the container level first, then zoom into the ingestion path" is itself a signal that the candidate knows how to structure a design conversation.

Diagrams as code: Structurizr, PlantUML and Mermaid

Diagrams drawn in a drawing tool rot, because updating them is a chore nobody owns and the source file lives on someone's laptop. Diagrams as code fixes the incentive: the model is a text file in the repository, it is reviewed in pull requests, it diffs, and it renders in continuous integration. Structurizr is Simon Brown's own take and the most C4-native — you describe the model once (people, systems, containers, components, relationships) in the Structurizr DSL and generate every view from it, so a renamed container updates all four levels rather than three diagrams going stale.

The lighter options are worth knowing because they are already in your toolchain. C4-PlantUML gives you C4 shapes and styling in PlantUML, which almost every wiki and IDE can render. Mermaid ships C4 syntax and renders natively inside GitHub markdown, so a diagram can live in the README with zero build step — the fastest way to get a team to start drawing at all. The choice matters less than the rule: keep the diagram in the same repository as the code it describes, so a change that invalidates it shows up in the same review.

workspace {
  model {
    customer = person "Customer"
    shop = softwareSystem "Shop" {
      api  = container "Order API"   "Spring Boot"
      db   = container "Order Store" "PostgreSQL" "Database"
      api -> db "reads from and writes to" "JDBC"
    }
    customer -> api "places orders using" "HTTPS/JSON"
  }
  views { systemContext shop { include * } container shop { include * } }
}

The system design interview method: a repeatable procedure with a time budget

The design round is not a knowledge test; it is a simulation of a design meeting, and it is scored on how you run the meeting. Treat it as a procedure you have rehearsed, with a clock. For a forty-five minute round, a workable budget is roughly: five minutes clarifying, five minutes on scope and estimates, ten to twelve minutes on the high-level design, fifteen minutes going deep where the interviewer probes, and the last five to seven minutes on bottlenecks, tradeoffs and what changes at ten times the load. Say the plan out loud at the start — "I'll spend a few minutes on requirements, sketch a first cut, then we can go deep wherever you like" — because it immediately shows you have done this before.

Each phase has a job. Clarify: who are the users, what are the core flows, read-heavy or write-heavy, how fresh must data be, is this global or one region, mobile or web, do we own authentication? Scope: write the functional requirements as a short list and get explicit agreement, then state the non-functional ones as numbers — availability target, tail-latency target, consistency expectation, retention. Estimate: daily active users to requests per second, average payload to storage per year, working set to cache size, and read-to-write ratio; round aggressively and say your assumptions aloud, because the interviewer is checking your method, not your arithmetic. High-level design: clients, edge and gateway, the two or three services, the datastores, the queues, drawn in one pass with the happy path traced end to end. Deep dive: follow the interviewer — the schema and partition key, the caching and invalidation strategy, the idempotency of the write path, the fan-out approach, the failure behaviour. Wrap up: name the bottleneck you would hit first, the tradeoff you are least happy with, and what you would change at ten times the scale.

Behaviours that score, and behaviours that lose points

What scores: stating assumptions out loud ("I'm assuming reads outnumber writes by a wide margin — is that right?"), so a wrong premise gets corrected in ten seconds instead of derailing twenty minutes. Driving the conversation — proposing the next step rather than waiting to be prompted; the interviewer is imagining you leading a design review. Naming tradeoffs instead of pretending a design is free: every choice you make should come with the sentence "which costs us…". Admitting what you do not know, then reasoning from principles anyway — "I have not run Cassandra in production, but this access pattern is a wide-row lookup by partition key, so here's how I would model it" beats confident invention every time. And quantifying: one honest number beats a paragraph of adjectives.

What loses points: jumping straight to a solution before requirements exist, which reads as someone who builds the wrong thing quickly. Silent thinking — a candidate who stares at the board for ninety seconds has given the interviewer nothing to score; narrate the search, including the options you reject. Over-engineering for scale nobody asked for: proposing Kafka, a service mesh, multi-region active-active and a data lake for a system with a few thousand users is a red flag about judgement, not a display of knowledge. Name-dropping without justification — saying "we'll use Redis" is worth nothing; saying "we'll cache the hot key set in Redis because the read-to-write ratio is extreme and we can tolerate a short staleness window" is worth everything. And ignoring the interviewer's steer: when they ask about the write path, they are telling you where the marks are.

A compact mock walkthrough, and what to actually practise

Take "design a ticket booking system for a cinema chain" — a favourite in Indian product and service-company rounds because it hides a concurrency problem inside an innocent CRUD description. Clarify: how many cities and screens, do seats have fixed numbering, is there a hold period before payment, must we prevent double-booking absolutely or is compensation acceptable, do we own payments? Scope: browse shows, view seat map, hold seats, pay, confirm, cancel; explicitly out of scope for now are recommendations, loyalty and dynamic pricing. Estimate: state a daily booking volume, convert to average and peak writes per second — noting that peak is what matters, since a blockbuster release opens at one moment nationwide — and size the seat-map reads, which dwarf the writes. High-level: clients, CDN for static seat maps, gateway, a catalogue service reading from a replica, a booking service owning the seat inventory in a strongly consistent store, a payment adapter, and a queue for confirmations and notifications. Deep dive where the real question lives: the seat hold. Take a row lock or a conditional update on the seat rows inside one transaction, write a hold with a short expiry, make the booking request idempotent on a client-generated key, and reconcile expired holds with a sweeper. Say plainly that you would not use a cache as the source of truth for seat state. Wrap up: the first bottleneck is write contention on a single popular show, so partition by show identifier; the tradeoff you dislike is the hold expiry window, which trades a little inventory utilisation for a much simpler failure story; at ten times the load you would shard by city and region, move notifications fully asynchronous, and pre-materialise seat maps.

The verdict for this track: do not read more designs — rehearse them. Pick six or seven classic problems from modules twelve and thirteen, and do each one out loud on a whiteboard against a timer, alone if you have to, until the procedure is automatic and you stop needing to remember what comes next. Keep a one-page cheat sheet of the numbers you use constantly: latency figures, rough throughput of a single database node, the read-to-write ratios you assume. Then, separately, practise the other half of this module on your day job — write one honest ADR for a decision your team made recently, and draw the container diagram for the service you own. If you can talk about your own system at the container level, name the module boundaries in it, and point to the record explaining a decision you disagree with, you are already doing the thing that senior design rounds are trying to detect.

Interview questions

Architecture and design-process questions from Indian product and service-company rounds — the ones that decide whether you are pitched as a senior engineer or an architect:

Beginner What is layered (n-tier) architecture, and what is its main weakness?

A horizontal split into presentation, business/service and data access layers, each calling only the layer below. It is familiar and perfectly adequate for CRUD-shaped services. Its weakness is the dependency direction: everything ultimately points at the database, so the domain imports persistence and framework types, domain tests need infrastructure, and swapping a datastore ripples upward through code that should not have cared.

Beginner What are ports and adapters in hexagonal architecture?

A port is an interface the application itself defines, in its own vocabulary, with no framework or driver types in the signature. An adapter is outside code that either drives a port (HTTP controller, CLI, scheduler, message listener) or implements one (JPA repository, S3 client, SMTP sender). The database and the web framework are both just adapters — neither is privileged.

Beginner What goes into an architecture decision record?

Nygard's four sections: context (the forces — load, deadlines, skills, existing contracts), decision (what we will do, in active voice), status (proposed, accepted, deprecated, superseded by a later record), and consequences (what gets easier and what gets harder). Keep it in the repository next to the code, number it, and never edit an accepted one — supersede it instead.

Beginner Name the four levels of the C4 model and who each one is for.

Context (the whole system plus its users and external systems — readable by anyone, including non-engineers), Container (the separately deployable/runnable pieces: web app, API, database, broker — the level most engineering conversations want), Component (major building blocks inside one container), and Code (a class diagram, best generated rather than drawn). Draw the level your audience needs, and do not mix levels in one picture.

Beginner How would you structure the first five minutes of a system design round?

State the plan, then clarify: who the users are, the two or three core flows, read-heavy or write-heavy, freshness and consistency expectations, scale and geography, what is explicitly out of scope, and what we own versus integrate with. End the phase by reading back a short agreed list of functional requirements plus numeric non-functional targets before drawing anything.

Intermediate Hexagonal versus layered — when is each the right call?

Layered when the service is genuinely CRUD-shaped, the team is small and the lifetime is short: you get a shape everyone recognises with no indirection tax. Hexagonal when the domain has real rules worth protecting, when infrastructure is likely to change, or when fast dependency-free domain tests matter. The deciding question is not "which is better" but "does this codebase have enough domain logic to be worth isolating?" — if the answer is no, hexagonal buys ceremony and nothing else.

Intermediate Hexagonal, onion and clean architecture — what is actually different between them?

Almost nothing structurally. All three enforce the same rule: source dependencies point inward toward the domain, and any outward call is inverted via an interface the inner layer owns. Hexagonal frames it as ports and adapters with no privileged side; onion draws concentric rings around a domain model; clean adds named rings (entities, use cases, interface adapters, frameworks) and states the Dependency Rule explicitly. Saying "three drawings of dependency inversion" scores better than reciting three diagrams.

Intermediate When would you NOT use microservices?

When the team is small enough to coordinate a single deploy; when the domain boundaries are not yet understood, so you would freeze the wrong lines into network calls; when the workload does not need independent scaling; when strong transactional consistency across the operations matters and you would be trading it for sagas; and when you lack the operational maturity — pipelines, tracing, on-call — to run many services. Microservices buy independent deployment and scaling and charge eventual consistency, partial failure and operational surface. If the real complaint is "we cannot find the code that owns this rule", that is modularity, and modularity is free inside one process.

Intermediate What is a modular monolith, and how do you stop it from decaying into a big ball of mud?

One deployable containing modules that each own their data, expose a small published interface, and never reach into another module's internals or tables. It decays when the boundaries are only documented. Make them executable: package-private by default with one public interface per module; Spring Modulith's ApplicationModules.of(App.class).verify() as a JUnit test; ArchUnit rules for dependency direction and cycles; the Java Platform Module System where you can afford the migration. If a violation does not fail the build, it will happen.

Intermediate What is vertical slice architecture, and what is its risk?

Organise by feature rather than by technical layer: one folder per use case containing its request, handler, validation and data access, because change arrives as features, not as layers. It lets each slice pick its own level of abstraction — a rich model where the rules are complex, a direct query where they are not. The risk is duplicated business rules smeared across slices with no single place to enforce an invariant, so most teams pair slices with a shared domain core for the rules that must not diverge.

Intermediate How do you do a back-of-envelope estimate in an interview, and what if you get the arithmetic wrong?

Work in a fixed order and say every assumption aloud: daily active users to daily requests, daily requests to average requests per second, average to peak with a stated multiplier, payload size to storage per year, read-to-write ratio to cache and replica sizing. Round hard to keep the maths mental. Arithmetic slips are cheap — an interviewer will correct a number and move on — but an unstated assumption or a missing peak factor is expensive, because it means you cannot size anything.

Pro Your team has an ADR you disagree with. What do you do?

Read the context section first — most disagreements are with a decision made under constraints that no longer apply, and that is exactly what the record is for. If the constraints have changed, write a new ADR that supersedes it, citing what changed and what the new consequences are; do not edit the accepted record, because the history of the reasoning is the asset. If the constraints still hold, the disagreement is a preference and the decision stands. Escalating without engaging the recorded context is the answer that loses points.

Pro How would you extract a module out of a modular monolith into its own service?

Start from a module whose boundary is already clean — one published interface, its own tables, no foreign keys crossing in. Route all callers through that interface, then move communication to events where you can so callers stop expecting synchronous answers. Split the schema, backfill and dual-write behind a flag, then move the module out and replace the in-process call with a remote one. Expect the properties that were free in-process to become work: transactions become sagas or an outbox, an exception becomes a timeout, and you now need retries, idempotency and tracing across the hop. If the boundary is not already clean, fix it inside the monolith first — extracting a leaky module just distributes the leak.

Pro You are twenty minutes into a design round and the interviewer says the requirements have changed — traffic is now ten times higher. How do you respond?

Do not redraw from scratch. Name what breaks first and why: usually a single write-hot partition, a synchronous fan-out, or a cache that no longer holds the working set. Then apply one change at a time and state its cost — partition by a different key (loses cross-key transactions), add read replicas (adds replication lag and stale reads), move fan-out to a queue (adds eventual consistency and a backlog to monitor), precompute (adds staleness and a rebuild path). Finish with what you would measure to confirm the bottleneck moved rather than multiplied. The interviewer is testing whether you reason from a bottleneck or reach for a bigger technology.

Pro Critique this: "we applied clean architecture across all forty of our services."

It signals a policy rather than a judgement. Clean architecture buys replaceability and infrastructure-free tests, and charges indirection: extra interfaces, three models per concept with mapping between them, more files per feature, and a longer path from a stack trace to the offending line. On services whose logic is validate-then-save, that cost buys nothing. The mature answer is selective application — the style in the few modules with genuinely rich domains, plain layered code elsewhere — plus an ArchUnit rule so that where the discipline exists it is actually enforced.

Pro An interviewer asks you to design something you have never built. How do you handle it?

Say so once, briefly, and then reason from primitives rather than from products. Reduce the unfamiliar problem to the shapes you do know: is this a fan-out on write or on read, a hot-key problem, a uniqueness constraint under concurrency, a stream with ordering requirements? Design against those, state the assumptions you are making about the unfamiliar part, and mark them as things you would verify with a benchmark or a spike. Candidates are rarely rejected for not having used a specific technology; they are rejected for inventing confident details that turn out to be wrong.
