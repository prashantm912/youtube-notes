Module: CQRS and Event Sourcing

Two patterns that get named in the same breath and are not the same thing. You can do CQRS without event sourcing — and most of the time you should.

Knowledge Library → Courses → Microservices track → CQRS and Event Sourcing

What this module covers

CQRS splits the model you write through from the model you read through. Event sourcing changes what you store: the sequence of things that happened, rather than the current state. They compose well, which is why they are constantly conflated — but each has its own cost curve and its own reasons to say no.

This module orients you on both, in that order, and finishes with an honest verdict: which bounded contexts earn these patterns, which do not, and what the tooling landscape actually offers.

Topics

CQRS: separating the command model from the query model

Command Query Responsibility Segregation takes the single model that normally serves an application — one set of entities used for both writing and reading — and splits it in two. The write model accepts commands, enforces invariants, and is usually normalized and small, because its job is deciding whether a change is legal. The read model answers queries, is denormalized, and is shaped for the screen that consumes it: an order-summary view with customer name, line-item count and status already flattened, no joins at request time.

Why bother? Because reads and writes genuinely have different requirements once a system has scale. Reads outnumber writes by orders of magnitude in most business systems, they tolerate slightly stale data, and they want wide, join-free, cacheable shapes. Writes are rare, must be correct, and want a tight consistency boundary. Forcing both through one ORM-mapped entity graph means every query pays for the write model's normalization and every write pays for the read model's indexes. Splitting lets you scale, index and even store each side independently — the read side can be Elasticsearch or a materialized Postgres view while the write side stays a small transactional table.

The read side is kept current by projections: handlers that consume domain events emitted by the write side and update materialized views. That is where the famous consistency lag comes from — the write commits, the event is published, the projection catches up milliseconds (or seconds) later, and a user who writes then immediately reads may not see their own change. That is a product decision to design around, not a bug to fix: show optimistic UI, read your own writes from the write side, or accept the lag where it does not matter.

Fowler's caution is the part candidates skip. CQRS adds significant complexity: two models, a synchronization mechanism, duplicated data, and a whole class of new failure modes. It belongs to a bounded context with a specific pressure — a heavily-read reporting surface, a domain with genuinely complex invariants — not to a whole system by default. Applying it everywhere is how teams end up maintaining twice the code for a CRUD screen.

// write side: enforce the invariant, emit what happened
public void handle(PlaceOrder cmd) {
    Order order = Order.place(cmd);        // invariants live here
    repository.save(order);
    events.publish(new OrderPlaced(order.id(), order.total()));
}

// read side: a projection keeps a flat view current
@EventHandler
public void on(OrderPlaced e) {
    summaryView.upsert(e.orderId(), e.total(), "PLACED");
}

Event sourcing: the event log as the source of truth

Event sourcing answers a different question: what do you persist? Instead of storing current state and overwriting it on every change, you append an immutable, ordered sequence of state-changing events — AccountOpened, MoneyDeposited, MoneyWithdrawn — to an event store. Current state is not stored at all; it is derived by replaying the events for an aggregate from the beginning and folding them into an in-memory object. The log is the truth; everything else is a cache of it.

Replay from the beginning gets expensive once an aggregate has thousands of events, so event-sourced systems take snapshots: a periodic serialized state at sequence number N, so loading means "read snapshot at N, then replay only events after N". Snapshots are strictly an optimization — you can always delete them and rebuild from the log, which is exactly the property that makes the pattern valuable.

The benefits are real and hard to get any other way. You have a complete audit log for free, because the log is the data — invaluable in regulated domains where "who changed this and when" is a legal question, not a debugging one. You get time travel: replay to any point to reconstruct the state the system was in when a decision was made. You can build a brand-new read model months later by replaying history through a new projection — retroactive analytics on data you never thought to record, because you recorded the events, not just their aggregate effect. And bugs in a projection are fixable by deleting the view and rebuilding it.

The costs are equally real and get underestimated. Event schemas are forever: an event written in 2021 must still be deserializable in 2031, so you need upcasting/versioning discipline from day one. Ad-hoc queries are painful — you cannot write "all customers in Pune with balance over X" against a log, which is precisely why event sourcing pushes you toward CQRS for the read side. Deletion is genuinely hard: GDPR's right to erasure collides head-on with an immutable append-only store, and the workarounds (crypto-shredding, keeping personal data outside the log) must be designed in, not bolted on. And every developer joining the team has to learn a new mental model before they can be productive — the ramp-up cost is a permanent tax on hiring.

// state is a fold over the event log, not a row
Account account = new Account();
for (Event e : eventStore.readStream(accountId, fromSequence)) {
    account.apply(e);   // AccountOpened, MoneyDeposited, MoneyWithdrawn ...
}
// snapshot bounds the replay cost
if (account.version() % 100 == 0) snapshotStore.save(account);

Is it worth it? The verdict and the tooling

Separate the two decisions. CQRS on its own is cheap enough to be worth reaching for whenever a bounded context has a read surface that fights its write surface — a dashboard, a search page, a reporting API. You keep a normal database, keep a normal transaction, and add a projection. That is the common, sane, usually-right call, and it is what most teams mean when they say "we did CQRS".

Event sourcing is a much bigger commitment and needs a stronger reason. It earns its cost in two situations. First, regulated or audit-heavy domains — banking, payments, insurance, trading, healthcare — where a tamper-evident history of every change is a requirement you would otherwise have to build anyway. Second, genuinely event-shaped domains, where the business already thinks in terms of things that happened: shipment tracking, order lifecycles, ledgers, workflow engines. If your domain is "user edits their profile", event sourcing is dressing up a CRUD app in a costume. InfoQ's write-ups of production experience are blunt about this: a whole system built on event sourcing is an anti-pattern, and the worst day-two problems come from teams adopting it before they understood the domain.

On tooling: Axon Framework is the mature JVM option — command bus, aggregates, event store, snapshots and projection support in one opinionated package, with Axon Server as the backing store. EventStoreDB (now shipped as Kurrent) is a purpose-built event store with streams, subscriptions and built-in projections. And Kafka is a durable log that people constantly reach for here — with an important caveat: Kafka alone is not an event store. It has no per-aggregate optimistic concurrency check, retention and compaction can drop history, and reading a single aggregate's stream is awkward. Kafka is excellent for propagating events between services; use a real event store for the write-side source of truth.

Interview questions

What actually gets asked in Indian product and service company rounds — architect screens, system design rounds, and the "you wrote CQRS on your resume" follow-ups:

Beginner What does CQRS stand for and what does it actually separate?

Command Query Responsibility Segregation. It separates the model that handles commands (state changes, invariants, normalized) from the model that handles queries (reads, denormalized, shaped for the consumer). Two models, often two stores, instead of one shared entity graph.

Beginner Is CQRS the same as event sourcing?

No — and this is the classic trap question. They are independent patterns. CQRS is about splitting read and write models; event sourcing is about what you store (a log of events instead of current state). You can do CQRS with a plain relational database and no events in sight, and that is usually the right call. Event sourcing tends to pull CQRS along with it, because you cannot query a log efficiently — which is why people see them together and assume they are one thing.

Beginner What is a projection or read model?

A denormalized view built and kept current by consuming events from the write side, shaped for a specific query or screen so reads need no joins. It is a derived artifact — you can delete it and rebuild it by replaying the events.

Beginner What is an event store and how is it different from a normal table?

An append-only, immutable, ordered log of state-changing events, usually grouped into per-aggregate streams. A normal table stores current state and overwrites it; an event store never overwrites — current state is derived by replaying the stream.

Intermediate Why do reads and writes deserve different models at all?

Different requirements. Reads are far more frequent, tolerate staleness, and want wide, join-free, cacheable shapes with heavy indexing. Writes are rarer, must be correct, and want a small normalized model with a tight consistency boundary. One shared model makes each side pay the other's cost, and neither can be scaled or indexed independently.

Intermediate Your user updates a record and immediately does not see the change. What happened and how do you handle it?

Projection lag — the write committed, the event has not been consumed into the read model yet. Options: optimistic UI that renders the expected result; read-your-own-writes by serving that one request from the write model; return the new version and have the client poll or wait for it; or accept the lag where the domain does not care. It is a product decision, not a defect to eliminate.

Intermediate What are snapshots and why are they needed?

Replaying an aggregate from event one gets slow once the stream is long. A snapshot is the serialized aggregate state at sequence number N, so loading becomes "read snapshot, replay only events after N". Purely an optimization — snapshots are disposable and can always be regenerated from the log.

Intermediate Name three genuine downsides of event sourcing.

Event schema versioning forever (a 2021 event must deserialize in 2031, so you need upcasters from day one); no easy ad-hoc queries against a log, which forces you into CQRS for reads; and a steep learning curve — every new joiner must absorb a different mental model before being productive. Add operational cost: replay time, snapshot management, and eventual consistency everywhere.

Intermediate Can you use Kafka as your event store?

Not as the write-side source of truth, on its own. Kafka has no per-aggregate optimistic concurrency check, retention and compaction can discard history you needed, and reading one aggregate's stream is awkward when a topic holds many. Kafka is excellent as the transport that propagates events to consumers and projections; pair it with a real event store (EventStoreDB/Kurrent, Axon Server, or an outbox-backed relational store) for the log of record.

Pro How do you satisfy GDPR's right to erasure in an event-sourced system?

You cannot simply delete from an append-only log without breaking replay. The practical approaches: crypto-shredding — encrypt each subject's personal data with a per-subject key and destroy the key, leaving the events structurally intact but unreadable; or keep personal data out of the log entirely, storing only a reference to a mutable, deletable side store. Both must be designed in before go-live; retrofitting them is a rewrite.

Pro How do you evolve event schemas over years without breaking replay?

Treat events as a permanent published contract. Only add optional fields; never rename or repurpose an existing one. Version the event type explicitly and use upcasters that transform old versions into the current shape on read. For a genuinely breaking change, introduce a new event type and keep handling the old one. Some teams do a one-off migration by replaying the entire log through a transformer into a new store, but that is a heavy, carefully-rehearsed operation.

Pro Fowler warns CQRS adds significant complexity. Where do you apply it, and where would you refuse?

Apply it inside a single bounded context that has a real read/write tension — a reporting or search surface fighting a transactional model, or a domain with complex invariants. Refuse it as a system-wide default: for straightforward CRUD it doubles the code, duplicates the data, and introduces eventual consistency for no return. "We use CQRS in the order context" is a good answer; "our architecture is CQRS" is a warning sign.

Pro Give a concrete verdict: which domains justify event sourcing and which do not?

Justified: regulated and audit-heavy domains — banking, payments, insurance, trading, healthcare — where a tamper-evident change history is a compliance requirement you would build anyway; and genuinely event-shaped domains where the business already thinks in events (ledgers, shipment tracking, order lifecycles, workflow engines). Not justified: profile management, catalogue admin, settings screens, most internal tooling — anything whose natural description is "the user edits a record". If you cannot name a stakeholder who asks "what was the state on 3 March and who changed it", you are paying for time travel nobody wants.

Pro How does an event-sourced write side avoid the dual-write problem when publishing to other services?

It largely dissolves it: appending the event is the state change, so there is no separate "save row then publish message" pair to keep atomic. Downstream propagation becomes a subscription that reads the store's own log and forwards events, tracking its position so it can resume. With a non-event-sourced store you achieve the same guarantee with the transactional outbox pattern — write state and outbox row in one transaction, relay them afterwards.
