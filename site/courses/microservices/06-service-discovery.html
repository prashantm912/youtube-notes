Module: Service Discovery

Autoscaling and rolling deploys mean the instance you called a minute ago may no longer exist. This module covers the machinery that answers "where is order-service right now?" — and when your platform already answers it for you.

Knowledge Library → Courses → Microservices track → Service Discovery

What this module covers

In a monolith, calling another module is a method call. In a distributed system it is a network call to an address that changes — containers get scheduled onto new nodes, autoscalers add and remove replicas, and blue-green deploys swap whole fleets. Hardcoded hostnames and hand-maintained config files stop working roughly the day you scale past one instance per service.

Service discovery is the answer: a registry that holds the current network locations of healthy instances, a way for instances to get into it, a way for them to fall out of it when they die, and a lookup path for callers. You will meet the two lookup patterns (client-side and server-side), the two registration patterns (self and third-party), the consistency tradeoff every registry makes, and three concrete implementations — Netflix Eureka, HashiCorp Consul, and Kubernetes Services.

Topics

Instances come and go: the service registry

A service registry is a database of service instances: for each logical service name (order-service) it holds a list of live instances with host, port, and metadata such as zone, version, or secure/insecure scheme. It is the single source of truth for "where is this service" and it must be highly available, because every request path depends on it. Registries typically run as a small cluster of their own and replicate between members.

Instances get into the registry one of two ways. With self-registration the instance itself calls the registry on startup, renews its entry, and de-registers on shutdown — simple, no extra moving parts, but it couples application code to the registry (this is what a Spring Boot app with the Eureka client does). With third-party registration a separate registrar watches the deployment platform and writes entries on the instance's behalf; the service stays ignorant of discovery entirely. Kubernetes is the mainstream third-party registrar: the control plane registers Pod IPs into Endpoints/EndpointSlices as readiness changes, and no application code is involved.

Client-side vs server-side discovery

With client-side discovery the caller queries the registry, receives the full list of healthy instances, caches it locally, and picks one itself — so the load-balancing decision lives inside your application. Spring Cloud LoadBalancer is the standard implementation on the JVM: you inject a @LoadBalanced RestClient/WebClient or use OpenFeign, write the logical service name in the URL, and the client resolves and balances. No extra network hop, full control over the algorithm (round-robin, zone-preference, weighted), but every language you deploy needs its own discovery-aware client library.

With server-side discovery the caller just requests one stable address, and a router — a load balancer, gateway, or the platform's own proxy — does the registry lookup and forwards the request. Callers stay dumb and polyglot-friendly, and the routing tier becomes the place to add TLS termination, retries or rate limiting; the cost is an extra hop and a component you must keep highly available. AWS ELB/ALB, an NGINX tier, Kubernetes Services, and service-mesh sidecars are all server-side discovery.

// Client-side discovery: the host is a SERVICE NAME, not a machine
@Bean @LoadBalanced
RestClient.Builder loadBalanced() { return RestClient.builder(); }

String body = restClient.get()
    .uri("http://order-service/api/orders/{id}", id)   // resolved via the registry
    .retrieve().body(String.class);

Heartbeats, leases and the CAP tradeoff every registry makes

A registry entry is a lease, not a permanent record. The instance renews it on a heartbeat (Eureka's default is a renewal every 30 seconds with a 90-second expiry); miss enough renewals and the entry is evicted. This is how the registry notices a crashed process — but it is also why discovery data is always slightly stale: between the moment an instance dies and the moment its lease expires, callers will still be handed a dead address. That is why discovery must be paired with the resilience patterns in the next modules — timeouts, retries against a different instance, and circuit breakers. Consul takes a different route: it runs explicit health checks (HTTP, TCP, script, TTL) and pulls failing instances out of the healthy set rather than waiting for a lease to expire.

Under a network partition a registry must choose. Eureka favours availability: peers replicate best-effort, any node answers reads from its own cache, and self-preservation mode deliberately stops evicting instances when renewals drop sharply — on the theory that a network glitch is more likely than every instance dying at once. You get answers during a partition, possibly stale ones. Consul favours consistency: servers elect a leader via Raft and commit registrations through the log, so a minority partition cannot accept writes at all. For a service registry, "available but occasionally wrong" is usually the better trade — a stale address plus a retry beats no address at all — which is exactly the argument to make when an interviewer asks why Eureka chose AP.

Netflix Eureka with Spring Cloud

Eureka is the registry most Indian enterprise teams meet first, because Spring Cloud Netflix made it two annotations away. A standalone server is a Spring Boot app with @EnableEurekaServer and spring-cloud-starter-netflix-eureka-server; for production you run two or more peers that replicate to each other. Every other service adds spring-cloud-starter-netflix-eureka-client, sets spring.application.name (that name becomes the registry key) and points eureka.client.service-url.defaultZone at the server. Registration, renewal and de-registration then happen automatically, and Spring Cloud LoadBalancer consumes the resulting instance list.

Two things to say out loud in an interview. First, Eureka's client-side cache means a newly started instance can take a couple of refresh cycles to become visible to callers — the "why is it so slow to register" section of the reference docs exists for a reason, and shortening the intervals in a demo is a known trick. Second, Spring Cloud Netflix is in maintenance mode: Ribbon, Hystrix, Zuul and Archaius were removed years ago, and Eureka is the only component still carried forward. It is fine on existing systems and still worth learning, but nobody should start a greenfield Kubernetes project with it.

spring:
  application:
    name: order-service      # the id other services will look up
eureka:
  client:
    service-url:
      defaultZone: http://eureka-1/eureka/,http://eureka-2/eureka/
  instance:
    prefer-ip-address: true

HashiCorp Consul: health checks, KV and a DNS interface

Consul is the polyglot answer. An agent runs on every node; services register with the local agent (via config file, HTTP API, or the Spring Cloud Consul starter) and declare health checks that the agent executes locally, reporting status up to the servers. Consul does three jobs at once: service discovery, distributed health checking, and a hierarchical key/value store that doubles as a configuration backend — which is why the next module on centralized configuration can reuse the same cluster.

Its most useful property for mixed estates is that discovery is exposed over plain DNS as well as HTTP: a lookup of order-service.service.consul returns the addresses of only the passing instances, so a legacy Python job, an NGINX config, or a shell script can discover services with no library at all. On the Spring side, spring-cloud-starter-consul-discovery implements the same DiscoveryClient interface as Eureka, so switching registries is a dependency and a properties change rather than a code change — a good example of why coding against Spring Cloud's abstraction pays off.

Kubernetes-native discovery: Services, kube-proxy and cluster DNS

On Kubernetes the platform is the registry, and it is a third-party registrar you get for free. A Service is a stable name and virtual IP in front of a set of Pods selected by labels; the control plane keeps the backing EndpointSlices in sync as Pods pass and fail their readiness probes. CoreDNS publishes an A record for every Service at <service>.<namespace>.svc.cluster.local (and short forms resolve inside the same namespace), so calling another service is literally http://order-service:8080/api/orders — an ordinary HTTP client with no discovery library. kube-proxy programs iptables or IPVS rules on each node so traffic to the ClusterIP is spread across the ready Pods. That is textbook server-side discovery, implemented by the platform.

Consequences worth knowing: because the ClusterIP is virtual, load balancing happens per connection, which is why long-lived HTTP/2 and gRPC connections pin to one Pod unless you use a headless Service (clusterIP: None, DNS returns every Pod IP) or a mesh. Readiness probes, not heartbeats, are the liveness signal here — a Pod that fails readiness is removed from the endpoints without dying. And if you do want the Spring programming model, spring-cloud-kubernetes implements DiscoveryClient on top of the Kubernetes API so @LoadBalanced clients and Spring Cloud Gateway routes keep working unchanged.

# inside any Pod in the cluster
curl http://order-service.orders.svc.cluster.local/api/orders/42
kubectl get endpointslices -l kubernetes.io/service-name=order-service

The honest verdict: do you still need a registry?

If everything you run lives in one Kubernetes cluster, running Eureka on top of it is duplicated machinery: you would have two sources of truth, two failure modes, and application code doing work the platform already does. Use Services and cluster DNS, and spend the saved effort on readiness probes and resilience. The reasonable exception is an existing Spring Cloud estate mid-migration, where keeping Eureka lets you move services into the cluster one at a time without rewriting clients.

A dedicated registry still earns its place when discovery has to span boundaries the platform does not cover: virtual machines and bare metal alongside containers, multiple clusters or multiple clouds, or non-Kubernetes schedulers — that is Consul's core use case, and its DNS interface is what makes a mixed estate workable. Beyond that, a service mesh subsumes discovery entirely into the data plane, which is the direction most large deployments end up taking. The answer interviewers reward is not "always Eureka" or "always Kubernetes" but the ability to name the deployment topology first and then pick.

Interview questions

Service discovery is a standard microservices round in Indian product and service companies — screening questions on Eureka setup, senior rounds on staleness, CAP and whether you need a registry at all:

Beginner Why do microservices need service discovery at all?

Instance addresses are dynamic: containers are rescheduled onto new nodes, autoscalers add and remove replicas, and deploys replace whole fleets. Hardcoded hostnames or hand-edited property files go stale immediately. A registry keeps the current list of healthy instances per logical service name so callers ask "who is order-service" instead of "what is 10.0.4.17".

Beginner What is a service registry and what does it store?

A highly available database of service instances. Per logical service name it holds each instance's host, port, scheme, status, and metadata such as zone or version. Callers or routers query it; instances (or a registrar) keep it current. Because every request depends on it, it is normally run as a replicated cluster.

Beginner Explain client-side and server-side discovery in one line each.

Client-side: the caller queries the registry, gets the instance list, and load-balances itself (Spring Cloud LoadBalancer, Eureka client). Server-side: the caller hits one stable address and a router or proxy does the lookup and forwards (Kubernetes Service, ALB, gateway). Client-side saves a hop; server-side keeps clients dumb and polyglot.

Beginner How do you set up a Eureka server and register a client in Spring Boot?

Server: a Spring Boot app with spring-cloud-starter-netflix-eureka-server and @EnableEurekaServer; in production run two or more peers pointing at each other. Client: add spring-cloud-starter-netflix-eureka-client, set spring.application.name (the registry key) and eureka.client.service-url.defaultZone. Registration and renewal are automatic.

Beginner Self-registration vs third-party registration?

Self-registration: the instance registers, heartbeats and de-registers itself — simple, but application code is coupled to the registry (the Eureka client model). Third-party registration: a separate registrar or the platform watches deployments and writes entries on the instance's behalf — the service stays discovery-agnostic. Kubernetes registering Pod IPs into EndpointSlices is the mainstream example.

Intermediate How does a registry decide an instance is dead?

Two mechanisms. Lease plus heartbeat: the instance renews periodically (Eureka defaults to renewal every 30 seconds, expiry after 90) and the entry is evicted when renewals stop. Or active health checking: Consul agents run HTTP/TCP/script/TTL checks and drop failing instances from the healthy set. Kubernetes uses readiness probes — a failing Pod is removed from endpoints without being killed.

Intermediate A service was killed one second ago but callers still get its address. Why, and what do you do about it?

Discovery data is eventually consistent: the lease has not expired yet, and clients cache the instance list on top of that. You cannot eliminate the window, only shrink it (shorter leases and refresh intervals, graceful shutdown that de-registers first, and readiness gates during deploys) and survive it — connect and read timeouts, retry the request against a different instance, and a circuit breaker so a bad instance is not hammered.

Intermediate Eureka vs Consul — how do you choose?

Eureka is JVM-centric, AP by design, dead simple to run for a Spring Cloud estate, and in maintenance mode. Consul is polyglot, CP via Raft, does active health checking, ships a KV store for configuration, and exposes discovery over DNS so non-JVM workloads and VMs participate. Rule of thumb: existing Spring-only system on VMs, Eureka is fine; mixed languages, VMs plus containers, or multi-datacenter, choose Consul.

Intermediate How does Kubernetes do service discovery without any registry code in the application?

A Service gives a stable name and ClusterIP over label-selected Pods; the control plane keeps EndpointSlices in sync with readiness. CoreDNS publishes <service>.<namespace>.svc.cluster.local, and kube-proxy programs iptables or IPVS rules so ClusterIP traffic is distributed across ready Pods. The app just makes an ordinary HTTP call to the service name — server-side discovery provided by the platform.

Pro Registries are distributed systems too — where does Eureka sit on CAP, and why?

Eureka chooses AP. Peers replicate best-effort, any node serves reads from its own cache, and self-preservation stops evicting instances when the renewal rate drops sharply, assuming a network problem rather than mass death. So during a partition you get answers, possibly stale ones. Consul chooses CP: Raft requires a quorum, so a minority partition refuses writes. For discovery, AP is usually right — a stale address plus a retry beats no address — but stale entries must be assumed, not wished away.

Pro Your gRPC calls all land on one Pod despite the Service having ten replicas. Explain.

A ClusterIP balances per connection, not per request. gRPC and HTTP/2 multiplex many requests over one long-lived connection, so after the initial pick every request goes to the same Pod. Fixes: a headless Service (clusterIP: None) so DNS returns all Pod IPs and a client-side balancer distributes, a proxy that speaks HTTP/2 request-level balancing, or a service mesh sidecar. Same reasoning applies to any pooled long-lived connection.

Pro You are migrating a Spring Cloud system onto Kubernetes. Do you keep Eureka?

Not as the destination. Inside one cluster, Services plus cluster DNS already give registration, health-based membership and load balancing, so Eureka would be a second source of truth and a second failure mode. Keep it only during migration so services outside the cluster stay reachable, or swap to spring-cloud-kubernetes so the same DiscoveryClient and @LoadBalanced code runs against the Kubernetes API. A dedicated registry stays justified when discovery must span VMs, multiple clusters, or clouds — that is Consul's territory.
