Module: API Gateway and BFF

Split a system into twenty services and you have just handed every client twenty addresses, twenty auth handshakes and a dozen round trips per screen. The gateway is the front door that hides all of it — and the piece most likely to become the thing that takes production down.

Knowledge Library → Courses → Microservices → API Gateway and BFF

What this module covers

An API gateway is the single entry point that sits between clients and your services: it routes requests, terminates TLS, validates tokens once, enforces rate limits, handles CORS, reshapes requests and responses, and occasionally fans one call out to several services and composes the reply. This module covers those edge responsibilities and their costs, then implements them concretely with Spring Cloud Gateway — the route model (id, uri, predicates, filters), built-in and custom filters, and configuration in YAML or the Java DSL.

It closes with Backend for Frontend: rather than one gateway trying to satisfy a web app, an Android app and a partner API at the same time, give each client type its own thin gateway shaped for its screens. Versions assumed: Spring Boot 3.x/4.x with the current Spring Cloud Gateway.

Topics

Why an edge exists: the client's problem

Without a gateway, every client must know the network address of every service, discover them when they move, speak whatever protocol each one chose, and repeat the same cross-cutting work — token validation, retries, CORS preflight handling — in every codebase, including a mobile app you cannot hot-fix. A single mobile screen showing an order, its items, the customer and a loyalty balance becomes four requests over a high-latency link. The gateway collapses that coupling: clients see one host and one API surface, while services stay free to move, split and merge behind it.

The core job is routing: match an incoming request (by path, host, method or header) and forward it to the right upstream, usually through a load balancer or service registry rather than a hard-coded host. Everything else at the edge is layered on top of that match-and-forward step. Getting this mental model right matters because interviewers routinely ask you to distinguish a gateway from a plain reverse proxy — the difference is that a gateway is API-aware and owns policy, not just TCP forwarding.

Cross-cutting work the edge absorbs — and what it costs

Once every request passes through one place, that place is the cheapest place to do work that would otherwise be duplicated. The usual list: TLS termination (certificates managed once, plaintext or mTLS inward); authentication and token translation — validate the JWT or opaque token once at the edge, then pass a trusted identity inward as headers or a relayed token, so downstream services do authorization, not authentication; rate limiting and throttling per client, key or tenant; CORS, so browsers preflight against the gateway instead of every service; request and response transformation (strip a path prefix, rewrite a URI, add or remove headers, reshape a legacy payload); and response aggregation, where one client call fans out to several services and returns a composed document.

All of that is real value, and all of it is a trap if you overdo it. A gateway every request crosses is a single point of failure — it needs redundancy, health checks and its own circuit breakers and timeouts, or one slow upstream drags the whole edge down. It is also a magnet for business logic: a discount rule "just for now" in a filter becomes an undeployable shared component every team must queue behind, which is exactly the coupling microservices were meant to remove. The rule that reads well in an interview: the gateway owns protocol and policy; domain decisions stay in services.

Spring Cloud Gateway: the route model

Spring Cloud Gateway expresses the edge as a list of routes. A route has an id, a destination uri (a real host, or lb://service-name to resolve through the load balancer and registry), a set of predicates that decide whether the request matches, and a set of filters that modify the exchange on the way through. The handler mapping walks the routes in order, and the first route whose predicates all pass wins — so ordering matters, and a broad Path=/** route placed early will swallow everything after it.

The common predicate factories are Path, Host, Method, Header, Query, Cookie, RemoteAddr and the time-based After/Before/Between; they compose with logical AND and can be combined in the Java DSL with and(), or() and negate(). Note the property prefix changed as the project split its servers: Spring Cloud Gateway 4.x used spring.cloud.gateway.routes, while the current 5.x reference documents spring.cloud.gateway.server.webflux.routes. Check the version your Spring Boot release train pulls in before copying a snippet.

spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
          - id: orders
            uri: lb://order-service      # resolved via the registry
            predicates:
            - Path=/api/orders/**
            - Method=GET,POST
            filters:
            - StripPrefix=1              # /api/orders/9 -> /orders/9

Filters: built-in, global and custom

A GatewayFilter applies to the route that declares it; a GlobalFilter applies to every route. Both run as a chain with a pre phase (before the request is proxied) and a post phase (after the response comes back), ordered by an Order value — routing, load balancing and metrics are themselves global filters, which is why the framework's own behaviour is inspectable and overridable. Useful built-ins to know by name: StripPrefix and RewritePath for URL shaping, AddRequestHeader / AddResponseHeader / RemoveRequestHeader, SetStatus, Retry, CircuitBreaker (delegating to Resilience4j with a fallback URI), and RequestRateLimiter, whose default implementation is a Redis token bucket driven by a KeyResolver.

When nothing built in fits, implement GlobalFilter as a bean, or extend AbstractGatewayFilterFactory for a route-scoped filter with configuration properties. Typical custom filters: injecting a correlation id, mapping a validated JWT into internal identity headers, or logging structured request metadata. Keep them non-blocking — the reactive gateway runs on a small Netty event loop, and one blocking call inside a filter can stall traffic for every route.

filters:
- name: RequestRateLimiter
  args:
    redis-rate-limiter.replenishRate: 10   # sustained requests per second
    redis-rate-limiter.burstCapacity: 20   # bucket size
    key-resolver: "#{@ipKeyResolver}"      # bean deciding the limit key
- name: CircuitBreaker
  args:
    name: ordersCb
    fallbackUri: forward:/fallback/orders

Configuration style: YAML, the Java DSL, and the servlet variant

Routes can be declared in YAML or built with the fluent RouteLocatorBuilder API. YAML wins for simple, mostly static routing and can be refreshed from a config server; the Java DSL wins when routes are conditional, generated from a list, or need predicates and filters that read awkwardly as strings. They coexist — many teams keep the bulk in YAML and add a small RouteLocator bean for the awkward cases. CORS is configured once globally rather than per route, and the discovery-client route locator can even publish a route per registered service automatically (convenient in demos, usually too loose for production).

One deployment detail worth stating in an interview: the reactive server built on Spring WebFlux and Netty is the mainline — it will not run in a traditional servlet container or as a WAR. A servlet-based server (Spring Cloud Gateway Server MVC) also exists for teams standardised on blocking Spring MVC, with its own handler and filter functions rather than the reactive filter factories, and a Proxy Exchange option for hand-rolled forwarding inside a controller.

@Bean
RouteLocator routes(RouteLocatorBuilder builder) {
    return builder.routes()
        .route("orders", r -> r.path("/api/orders/**")
            .and().header("X-Api-Version", "v2")
            .filters(f -> f.stripPrefix(1)
                           .addRequestHeader("X-Edge", "gateway"))
            .uri("lb://order-service"))
        .build();
}

Backend for Frontend: one gateway per client type

A single general-purpose gateway serving a desktop web app, a mobile app and a partner API ends up serving none of them well: every client's needs push changes into one shared component, payloads grow to be a superset of everyone's requirements, and release cadence is set by the slowest consumer. Backend for Frontend — named at SoundCloud and popularised by Sam Newman — flips the ownership: each client experience gets its own thin edge service, owned by the team that owns that client, exposing exactly the endpoints and payload shapes that client's screens need.

A mobile BFF might collapse four upstream calls into one lean response with small images; the web BFF returns richer documents; the partner BFF exposes a stable, versioned, rate-limited contract and nothing else. BFFs stay thin — aggregate, reshape, adapt protocols, hold client-specific session or token handling (an increasingly common pattern is the BFF holding the OAuth2 tokens so a browser app keeps only a cookie) — and hold no domain logic. The trade-off to name unprompted: duplicated aggregation code across BFFs and more services to run, accepted in exchange for team autonomy. Guard against BFF proliferation by grouping per client type, not per screen.

Interview questions

Gateway questions dominate microservices rounds at Indian product and service companies — expect the pattern first, then Spring Cloud Gateway specifics, then a design trade-off:

Beginner What is an API gateway and why do microservices need one?

A single entry point between clients and services. It routes requests to the right service and centralises cross-cutting concerns — TLS termination, authentication, rate limiting, CORS, logging. Without it every client must know every service address and repeat that work itself, and services cannot move or split freely.

Beginner How is a gateway different from a load balancer or a plain reverse proxy?

A load balancer distributes traffic across instances of one service; a reverse proxy forwards by host or path with no understanding of your API. A gateway is API-aware: it matches on path, method, headers or query, applies per-route policy such as auth and rate limits, can transform payloads and aggregate several upstream calls. Gateways typically use a load balancer or registry underneath.

Beginner Name the main responsibilities you would put at the edge.

Routing, TLS termination, authentication and token validation, rate limiting and throttling, CORS handling, request/response transformation, response aggregation, plus observability — correlation ids, access logs, metrics. Authorization on domain rules and any business logic stay in the services.

Beginner What are predicates and filters in Spring Cloud Gateway?

A route is id + uri + predicates + filters. Predicates decide whether a request matches the route (Path, Host, Method, Header, Query, Cookie, RemoteAddr, time-based After/Before/Between) and are ANDed together. Filters modify the exchange as it passes — pre phase before proxying, post phase on the response.

Beginner Which built-in filters do you use most often?

StripPrefix and RewritePath for reshaping the upstream URL, AddRequestHeader / AddResponseHeader / RemoveRequestHeader, SetStatus, Retry, CircuitBreaker with a fallback URI, and RequestRateLimiter. TokenRelay when the gateway forwards an OAuth2 access token inward.

Intermediate How does authentication work when the gateway is in front? Do services trust it blindly?

The gateway validates the token once — signature, expiry, issuer, audience — and passes identity inward, either by relaying the token or by adding trusted headers such as user id, tenant and roles. Downstream services then do authorization, not authentication. They must not trust those headers from anywhere else: enforce it with network policy or mTLS so nothing can reach a service except through the edge. Many teams still re-verify the JWT in each service — cheap, and it removes the blind-trust assumption entirely.

Intermediate How do you implement rate limiting in Spring Cloud Gateway?

The RequestRateLimiter filter with the Redis-backed token bucket: set replenishRate (sustained requests per second), burstCapacity (bucket size) and optionally requestedTokens, and supply a KeyResolver bean that decides the limit key — user id, API key, tenant or client IP. Redis makes the counter shared, so the limit holds across gateway instances; an in-memory limiter would let N replicas allow N times the quota.

Intermediate GatewayFilter vs GlobalFilter — when do you write each?

A GatewayFilter is attached to specific routes, usually via a factory extending AbstractGatewayFilterFactory so it can take configuration. A GlobalFilter runs for every route and needs no declaration — right for correlation ids, access logging or uniform security headers. Both participate in the same ordered chain; the framework's routing and load-balancing steps are themselves global filters.

Intermediate Route ordering bit you in production. What happened, and how do you debug routing?

Routes are evaluated in order and the first full predicate match wins, so a broad Path=/** or catch-all route declared early shadows every specific route after it. Debug with the gateway actuator endpoint to list resolved routes, enable trace logging for the handler mapping and filter chain, and prefer specific paths with explicit ordering over catch-alls.

Intermediate What is the BFF pattern and when would you choose it over one shared gateway?

Backend for Frontend gives each client type — web, mobile, partner API — its own thin edge service owned by that client's team, exposing exactly the endpoints and payload shapes it needs. Choose it when client needs have visibly diverged (mobile wants fewer, leaner calls; web wants richer documents) or when one shared gateway has become a release bottleneck between teams. One gateway is fine while clients want essentially the same API.

Pro The gateway is a single point of failure. How do you keep it from taking the system down?

Run several stateless replicas behind a load balancer or Kubernetes Service across zones, with readiness and liveness probes and autoscaling. Protect it from upstreams: per-route connect and response timeouts, circuit breakers with fallback URIs, bulkheads or concurrency limits so one slow service cannot exhaust the event loop, and retries only on idempotent methods. Keep filters non-blocking, keep state (rate-limit counters, sessions) in Redis rather than in the instance, and give the edge its own dashboards and alerts on latency and error rate.

Pro Why is business logic in the gateway considered an anti-pattern, and where do you draw the line?

Logic in the edge belongs to no service team but blocks all of them: every change queues behind one shared deploy, tests need the whole edge, and the coupling microservices were meant to remove comes back concentrated in one component. The line: the gateway owns protocol and policy — routing, auth, limits, headers, shaping, aggregation of existing responses. Anything that decides a domain outcome (pricing, eligibility, workflow state) belongs to a service. If aggregation logic starts making decisions, promote it to a BFF or a composition service you can own and deploy independently.

Pro With a service mesh and Kubernetes Ingress already in place, do you still need an API gateway?

They solve different axes. Ingress does L7 entry and TLS; a mesh handles service-to-service concerns — mTLS, retries, traffic splitting, telemetry — transparently as a sidecar, mostly east-west. A gateway is north-south and API-aware: client authentication, quotas per consumer, payload shaping, aggregation, API versioning and keys. Common production shape is Ingress or a cloud load balancer in front, a gateway or BFF for client-facing API policy, and a mesh for inter-service traffic. If your clients need none of the API-level policy, the gateway is redundant — say so, that honesty scores.

Pro Spring Cloud Gateway is reactive. What does that constrain, and what is the servlet alternative?

The mainline server is built on Spring WebFlux, Project Reactor and Netty: it will not run in a traditional servlet container or as a WAR, and any blocking call inside a filter — a JDBC lookup, a synchronous HTTP client — occupies an event-loop thread and degrades every route, not just that one. Offload such work or move it to a service. For teams standardised on blocking Spring MVC there is a servlet-based Spring Cloud Gateway Server MVC with handler and filter functions instead of the reactive filter factories, plus a Proxy Exchange option for controller-level forwarding.
