Module: Inter-Service Communication

Inside a monolith a call is a method invocation that cannot fail on its own. Across services it is a network call that can be slow, fail, or quietly succeed twice — and choosing how services talk is the decision that most shapes how the system behaves under load.

Knowledge Library → Courses → Microservices track → Inter-Service Communication

What this module covers

Two decisions live here. First, the communication style: REST over HTTP, gRPC over HTTP/2, or asynchronous messaging through a broker — each with a different failure model, and each honestly better than the others at something. Second, the contract and the client: how the caller knows what the callee accepts, how OpenAPI turns that into a machine-readable artefact, and which Java client you actually write in Spring Boot 3.x and 4.x — Spring Cloud OpenFeign, the modern RestClient, or a declarative HTTP interface.

Everything downstream in this track — the gateway, resilience, sagas, tracing, contract testing — assumes you have picked a style deliberately. Pick it by accident and every later module becomes damage control.

Topics

Three styles: REST, gRPC and asynchronous messaging

REST/JSON over HTTP is the default because it is ubiquitous and human-debuggable: any browser, curl, proxy or log aggregator understands it, and a junior engineer can reproduce a bug from a request line. The cost is verbosity — text on the wire, reflective serialisation, no schema the compiler enforces — and a contract that lives in documentation rather than in code.

gRPC trades that readability for speed and type safety. Protobuf messages are binary and compact, the .proto file is the contract, stubs are generated for both sides, and HTTP/2 multiplexing plus first-class streaming make it excellent for chatty internal service-to-service traffic. The cost is tooling: you cannot eyeball a payload, browser support needs a proxy layer, and every team must adopt the build plugin.

Asynchronous messaging is a different shape entirely. The caller publishes an event or command to a broker and returns immediately; the consumer processes it whenever it is healthy. This buys temporal decoupling — the downstream service can be down for ten minutes and nothing is lost — at the price of eventual consistency, at-least-once delivery (so duplicates), and debugging that spans a broker rather than a stack trace.

The decision rule that survives interviews: if the caller genuinely needs the answer to continue, use a synchronous call — REST at the edge and for cross-team or public APIs, gRPC for high-volume internal hops where both sides are yours. If the caller only needs the work to eventually happen, publish an event. Most "we need it synchronously" requirements dissolve under one question: what does the user actually see if this step finishes two seconds later?

service Inventory {
  rpc GetItem (ItemRequest) returns (Item);        // unary
  rpc WatchStock (ItemRequest) returns (stream Item); // server streaming
}
message ItemRequest { string sku = 1; }

The synchronous call-chain trap

Here is the failure mode that turns a tidy diagram into a production incident. Service A calls B, which calls C, which calls D. Each hop is fast in isolation, so nobody worries. Then D slows from 20 ms to 2 seconds. C's threads block waiting on D; C's pool fills; B's calls to C start timing out; A's request path stalls. One slow leaf has stalled the whole tree, and the alert fires on A — the service that is not broken. Availability multiplies too: four hops at 99.9% each give roughly 99.6% for the chain, and you have spent your error budget on arithmetic.

Two mitigations are mandatory for any synchronous hop and are covered later in this track: aggressive, explicit timeouts, and a circuit breaker so a sick dependency fails fast instead of consuming your threads (see Resilience with Resilience4j). But the structural answer is usually to stop making the call at all. If service A only needs to tell B something — order placed, user registered, payment captured — publish an event and let B consume it at its own pace. The request path shortens to one hop, B's downtime becomes broker backlog rather than user-visible errors, and new consumers attach later without A changing a line.

What you accept in exchange is eventual consistency and duplicate delivery. Brokers guarantee at-least-once, not exactly-once, so consumers must be idempotent — the same message processed twice must not charge the card twice. That discipline, plus the outbox pattern for publishing reliably alongside a database write, is the subject of the Messaging track and of Distributed Data Patterns later in this one.

The contract: OpenAPI and generated clients

Once two teams own two services, the interface between them needs to be an artefact, not a conversation. OpenAPI is that artefact for HTTP APIs: a machine-readable description of paths, parameters, request and response schemas, status codes and auth, versioned in a repository and reviewable in a pull request. It gives you rendered documentation for free, request validation, mock servers before the provider exists, and — the part that changes daily work — code generation.

Two directions are worth knowing. Code-first: annotate the Spring controllers, let springdoc-openapi produce the specification at build or runtime, publish it. Fast, and the spec cannot drift from the implementation, but the API is designed by whoever wrote the controller. Contract-first: write or negotiate the YAML first, then generate server interfaces and typed client stubs with OpenAPI Generator for every consumer language. Slower to start, far better across team boundaries — and it makes a breaking change visible as a diff rather than as a 4xx in someone else's logs. A generated client also removes a whole class of bug: nobody hand-types a URL path or misspells a field name.

Whichever direction you pick, treat the spec as versioned and additive. Adding an optional field is safe; removing one, renaming one, or tightening a validation rule is a breaking change that needs a version bump and a migration window. Module 12 of this track takes that further with consumer-driven contract testing.

Java clients: OpenFeign, RestClient and declarative HTTP interfaces

Spring Cloud OpenFeign is the long-standing answer in Spring microservices: declare a Java interface, annotate it with @FeignClient and Spring MVC annotations, and Spring generates the implementation. Because the client resolves a service name, it composes with service discovery and client-side load balancing, and it plugs into Resilience4j for circuit breaking and fallbacks. It remains synchronous and thread-per-request, which is exactly right for most business services.

On the Spring Framework side the picture has consolidated. RestTemplate is in maintenance mode — still supported, no new features, not the choice for new code. RestClient is the modern synchronous client with a fluent API and the same underlying infrastructure. WebClient is the reactive, non-blocking option, correct when you are already in a reactive stack or fanning out many calls concurrently. And on top of any of them sit declarative HTTP interfaces: annotate an interface with @HttpExchange / @GetExchange, build a proxy with HttpServiceProxyFactory, and you get Feign-style ergonomics from Spring Framework itself with no extra dependency.

The pragmatic rule for a Spring Boot 3.x or 4.x service: use OpenFeign if you are already on Spring Cloud and want discovery and load balancing wired in for free; use HTTP interfaces over RestClient for a plain typed client with fewer moving parts; use WebClient when reactive or genuinely concurrent. Whichever you pick, always set connect and read timeouts explicitly — the defaults on the underlying HTTP client are far too generous for a service mesh, and an unbounded read timeout is how the call-chain trap above starts.

// Spring Cloud OpenFeign — resolves "inventory" through discovery
@FeignClient(name = "inventory")
public interface InventoryClient {
    @GetMapping("/api/items/{sku}")
    ItemDto find(@PathVariable String sku);
}
// Spring Framework declarative HTTP interface over RestClient
public interface InventoryApi {
    @GetExchange("/api/items/{sku}")
    ItemDto find(@PathVariable String sku);
}

RestClient client = RestClient.create("https://inventory.internal");
InventoryApi api = HttpServiceProxyFactory
        .builderFor(RestClientAdapter.create(client)).build()
        .createClient(InventoryApi.class);

Interview questions

What Indian product and service companies actually ask about service-to-service calls — from screening rounds to architecture discussions:

Beginner What are the main styles of inter-service communication?

Synchronous request/response — REST over HTTP or gRPC over HTTP/2, where the caller blocks for an answer — and asynchronous messaging through a broker such as Kafka or RabbitMQ, where the caller publishes and moves on. A further axis is one-to-one (a command to one service) versus one-to-many (an event many services consume).

Beginner REST or gRPC — how do you choose?

REST for public and cross-team APIs, anything a browser or third party touches, and anywhere human debuggability matters. gRPC for high-volume internal hops between services you own, where the compact binary payload, generated stubs and native streaming pay for the extra tooling. Many systems use both: REST at the edge, gRPC inside.

Beginner What is @FeignClient and what does Spring do with it?

It marks a Java interface as a declarative HTTP client. With @EnableFeignClients, Spring Cloud scans for those interfaces and generates a proxy implementation that translates each annotated method into an HTTP call — resolving the service name through discovery and load balancing when Spring Cloud is on the classpath. You write the interface, not the HTTP plumbing.

Beginner Synchronous versus asynchronous — what actually differs for the caller?

Synchronous: the caller holds a thread until the response arrives, needs the callee to be up right now, and gets read-your-writes consistency. Asynchronous: the caller returns as soon as the broker accepts the message, tolerates the consumer being down, and accepts that the effect happens later — eventual consistency.

Intermediate Describe the synchronous call-chain problem.

A request that traverses A to B to C to D couples all four in latency and availability. One slow service saturates its callers' thread pools, and the stall propagates upward — the alert fires on the healthy front-end service. Availability multiplies: four hops at 99.9% each give about 99.6%. Mitigate with explicit timeouts and circuit breakers; fix structurally by replacing hops with events where the caller does not need the answer.

Intermediate Why is Protobuf faster than JSON, and what do you give up?

Fields are encoded by numeric tag with a compiled schema, so there are no field names on the wire, no text parsing and no reflection — smaller payloads and cheaper serialisation. You give up human readability (you cannot read a payload from a log or replay it with curl), you take on a build-time code generation step, and browsers need a proxy such as gRPC-Web.

Intermediate RestTemplate, RestClient, WebClient, Feign — which do you use in a new Spring Boot service?

RestTemplate is in maintenance mode: keep it in legacy code, do not choose it for new work. RestClient is the modern synchronous fluent client. WebClient is the reactive, non-blocking option — right for reactive stacks and high-concurrency fan-out. OpenFeign or a Spring HTTP interface sits above these and gives a declarative, typed interface; pick Feign when you want Spring Cloud discovery and load balancing wired in.

Intermediate What is a declarative HTTP interface in Spring Framework?

An interface whose methods are annotated with @HttpExchange or its shortcuts (@GetExchange, @PostExchange). HttpServiceProxyFactory, backed by a RestClientAdapter or WebClientAdapter, builds a proxy that performs the calls. It gives Feign-style ergonomics with no Spring Cloud dependency — the framework's own answer to declarative clients.

Intermediate How does OpenAPI help two teams that own two services?

It turns the interface into a versioned, reviewable artefact instead of a conversation. From one YAML file both sides get rendered documentation, request validation, mock servers, and generated server interfaces and typed clients. Breaking changes surface as a diff in a pull request rather than as a 4xx in the consumer's logs.

Intermediate Code-first or contract-first — which and why?

Code-first (annotate controllers, let springdoc emit the spec) is faster and never drifts from the implementation — good inside one team. Contract-first (write the YAML, generate both sides with OpenAPI Generator) is better across team or company boundaries because the API is designed and agreed before either side is built, and consumers can start against a mock immediately.

Intermediate A Feign call to a downstream service starts failing. What is your handling strategy?

Set connect and read timeouts explicitly so the failure is fast and bounded. Wrap the call in a Resilience4j circuit breaker with a fallback that degrades gracefully — cached data, a partial response, or a clear error — rather than propagating a stack trace. Retry only idempotent operations, with backoff and jitter. Use an ErrorDecoder to map downstream status codes onto meaningful domain exceptions, and make sure the failure is visible in traces and metrics.

Pro Messaging brokers give at-least-once delivery. What does that force on you?

Consumers must be idempotent, because the same message will eventually arrive twice — after a redelivery, a rebalance, or a retry. Standard techniques: a business or message id recorded in a processed-messages table inside the same transaction as the effect, natural idempotency (set a state rather than increment), or a unique constraint that makes the duplicate a no-op. Pair it with the transactional outbox pattern so publishing and the database write cannot diverge, and a dead-letter queue for messages that will never succeed.

Pro How do you evolve an inter-service API without breaking consumers?

Be additive: new optional fields and new endpoints are safe; removals, renames and tightened validation are not. Tolerant readers — consumers that ignore unknown fields — make evolution possible. For anything breaking, version the endpoint or media type, run both versions during a migration window, and instrument the old one so you can see when the last consumer leaves. In Protobuf, never reuse or renumber a field tag; mark removed ones reserved. Consumer-driven contract tests turn all of this from a promise into a build failure.

Pro Your architect wants every call synchronous "so the data is always correct". How do you argue?

Show that synchronous chains do not give correctness, only the appearance of it: a partial failure mid-chain leaves the system inconsistent anyway, with no record of what to compensate. Then price the coupling — multiplied unavailability, thread-pool exhaustion, latency that is the sum of every hop. Ask what the user genuinely sees if a step lands a second later; for confirmation emails, analytics, search indexing and inventory sync the answer is nothing. Keep synchronous calls where the caller needs the answer to render a response, and make the rest events with idempotent consumers.
