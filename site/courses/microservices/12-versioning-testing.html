Module: Versioning, Contracts and Testing

Independent deployability is the entire promise of microservices — and it dies the instant two services have to be released together. This closing module is about keeping that promise: evolving APIs without breaking callers, proving compatibility in CI instead of production, and the platform machinery that makes a dozen services survivable.

Knowledge Library → Courses → Microservices track → Versioning, Contracts and Testing

What this module covers

Every earlier module in this track bought you something — a bounded context, a database per service, an asynchronous edge, a circuit breaker, a trace id. All of it exists to let one team ship one service on a Tuesday afternoon without a release train, a coordination meeting, or a rollback plan involving four other squads. The moment a change to service A forces service B to redeploy on the same day, you have paid the full operational price of distribution and received a distributed monolith in exchange.

The first half of this module is about that contract discipline: which API changes are safe, how to version when a breaking change is unavoidable, how to retire an old version honestly, and how consumer-driven contract testing (Pact, Spring Cloud Contract) turns "I think nobody uses that field" into a build failure. The second half is the platform synthesis the track has been building toward: the microservice chassis and service template, deployment topologies, a service mesh survey, and a testing strategy that ends in production rather than pretending production does not exist.

Topics

Independent deployability, and what actually counts as a breaking change

The test for whether you have microservices or a distributed monolith is simple: can you deploy any one service to production, right now, without deploying any other? If the answer is no, the cause is almost always an API change that consumers cannot absorb on their own schedule. So the working rule for evolving a service API is additive only. Adding a new optional field, a new endpoint, or a new enum value that old clients can ignore is safe. Removing a field, renaming it, narrowing its type, tightening validation, making an optional request field required, or changing the meaning of an existing value is breaking — even when your own tests pass, because your tests are written by you and the breakage lands on somebody else.

The counterpart rule lives on the consumer side: be a tolerant reader. Deserialize only the fields you actually need, ignore everything you do not recognise instead of failing on unknown properties, and never assume element ordering or the absence of extra data. A strict consumer converts a provider's safe additive change into an outage, which then teaches the provider that no change is safe and freezes the API forever. Postel's advice — be conservative in what you send, liberal in what you accept — is the operational rule that makes independent deployment possible at all. Codify the shape in an OpenAPI document so "the contract" is a reviewable artefact rather than tribal memory.

// v1 response the provider ships today
{ "orderId": "A-1042", "status": "SHIPPED", "total": 2499 }

// SAFE: new optional field added. A tolerant reader ignores it.
{ "orderId": "A-1042", "status": "SHIPPED", "total": 2499, "carrier": "BlueDart" }

// BREAKING: renamed, retyped, and a new enum value old clients cannot map
{ "id": "A-1042", "status": "OUT_FOR_DELIVERY", "total": { "amount": 2499, "currency": "INR" } }

Versioning strategies: URI path, header, and media type

Sometimes a breaking change is genuinely unavoidable and you must run two shapes of the API at once. Three mechanisms are standard. URI path versioning (/api/v1/orders) is explicit, trivially cacheable, browsable in a browser bar and greppable in logs; purists dislike it because the URI is supposed to identify the resource, not a representation of it. Header versioning (a custom X-API-Version or the newer API-Version header) keeps URIs clean but is invisible in a browser and easy to lose at a proxy or CDN unless you add it to the cache key. Media type versioning (Accept: application/vnd.acme.order.v2+json) is the most REST-correct — content negotiation is exactly what Accept is for — and the most awkward for ordinary clients and for anyone debugging with a browser.

The honest recommendation: version at the URI path for public and partner APIs, because discoverability and support-desk debuggability beat theoretical purity, and keep the version at the coarsest sensible granularity — one version per service API, not per endpoint and never per field. Bump the major version rarely; most changes should be additive and require no bump at all. Spring Framework 7 / Spring Boot 4 finally made this first-class with built-in API versioning: a version attribute on @RequestMapping plus a configurable resolver (path segment, request header, query parameter or media type), so you declare the strategy once instead of hand-rolling it with URL prefixes and interceptors.

GET /api/v2/orders/A-1042            # 1. URI path  — explicit, cacheable, greppable
GET /api/orders/A-1042
API-Version: 2                       # 2. header    — clean URIs, invisible in a browser
GET /api/orders/A-1042
Accept: application/vnd.acme.order.v2+json   # 3. media type — pure content negotiation

Deprecation, Sunset headers, and the expand–contract migration

Publishing v2 is the easy half; retiring v1 is where teams fail, and an API you can never delete is a permanent tax on every future change. Deprecation should be a machine-readable, dated announcement rather than an email nobody read. Two standards-track headers exist for exactly this: Deprecation (RFC 9745) states that the endpoint is deprecated and when it became so, and Sunset (RFC 8594) gives the HTTP-date after which the resource is expected to stop responding, usually accompanied by a Link header pointing at the migration guide and the successor version. Emit them from the moment v2 ships, log every call still arriving on the deprecated version tagged by consumer, and let that per-consumer call count — not a calendar guess — decide when it is actually safe to delete.

For the change itself, use expand–contract (also called parallel change), which is the single most useful migration pattern in this module and applies equally to REST payloads, event schemas and database columns. Expand: add the new field, endpoint or column alongside the old one and write to both, so the service now satisfies old and new consumers simultaneously. Migrate: move consumers over one at a time, at their own pace, with no coordinated release. Contract: once telemetry proves nobody reads the old shape, delete it. Each of the three steps is independently deployable and independently revertible, which is precisely why it works — a big-bang cutover requires every team to move on one date, which is the coordinated release you built microservices to avoid.

HTTP/1.1 200 OK
Deprecation: @1761955200                     # RFC 9745 — deprecated since this instant
Sunset: Sat, 31 Jan 2026 00:00:00 GMT        # RFC 8594 — expected to stop responding
Link: <https://api.acme.com/docs/migrating-to-v2>; rel="deprecation"
Link: <https://api.acme.com/api/v2/orders>; rel="successor-version"

Consumer-driven contracts: catching breakage in CI instead of production

Integration tests that spin up every service are slow, flaky and impossible to run per-commit; mocks are fast but drift from reality the moment the provider changes, so they will happily let you ship a green build against an API that no longer exists. Consumer-driven contract testing solves both. The consumer writes a test against a local mock of the provider, and the framework records the request/response pairs that test relied on into a machine-readable pact. That pact is then replayed against the real provider in the provider's own build: the provider's pipeline sets up the declared state, receives the recorded request, and asserts its actual response satisfies what the consumer expects. Neither build ever needs both services running at once, yet a breaking change fails a pipeline within minutes.

The word "consumer-driven" is the important part. The contract encodes only what consumers genuinely use, so it is simultaneously a compatibility test and an accurate map of which fields you are allowed to delete — the answer to "does anyone still read customerName?" becomes a query against the contracts rather than a guess. Two rules keep it healthy: match on types and matchers, not exact literal values, or every harmless data change turns red; and keep contracts to structural expectations rather than business assertions — a contract test proves the two sides can talk, it does not prove the provider's discount calculation is right. Pact is the polyglot, HTTP-and-messaging standard here, with a mature JVM implementation and JUnit 5 support.

// Consumer side (Pact JUnit 5): declare what THIS consumer actually needs
@Pact(consumer = "shipping-service", provider = "order-service")
public RequestResponsePact orderExists(PactDslWithProvider builder) {
    return builder
        .given("an order A-1042 exists")            // provider state, set up in provider build
        .uponReceiving("a request for that order")
        .path("/api/v2/orders/A-1042").method("GET")
        .willRespondWith().status(200)
        .body(new PactDslJsonBody()
            .stringType("orderId", "A-1042")        // match on TYPE, never on the literal
            .stringMatcher("status", "SHIPPED|DELIVERED", "SHIPPED"))
        .toPact();
}

The Pact Broker and the can-i-deploy gate

Contract files sitting in a Git repository are a half-finished implementation. The Pact Broker is the missing piece: consumers publish their pacts to it tagged with a version and a branch, providers pull the pacts of every consumer that matters and publish verification results back, and the broker maintains the resulting compatibility matrix — which consumer version is proven to work with which provider version, in which environment. It also draws the live dependency graph of your estate, which is frequently the only accurate one anybody has.

The payoff is the can-i-deploy check, and it is what turns contract testing from a nice test into a genuine release gate. Before a deployment step runs, the pipeline asks the broker whether this exact version of this service is verified compatible with everything currently running in the target environment; if a consumer's expectation has not been verified against this build, the deploy stops. Add a broker webhook so that publishing a new pact automatically triggers the provider's verification build, record deployments with record-deployment so the broker knows what is actually live, and use pending pacts and WIP pacts so a brand-new consumer expectation cannot break the provider's main build before the provider has had a chance to implement it.

# Provider build: verify every consumer contract, publish the results
./gradlew pactVerify -Ppact.verifier.publishResults=true

# Release gate: refuse to deploy unless the broker says this version is compatible
pact-broker can-i-deploy \
  --pacticipant order-service --version "$GIT_SHA" \
  --to-environment production --retry-while-unknown 6

pact-broker record-deployment \
  --pacticipant order-service --version "$GIT_SHA" --environment production

Spring Cloud Contract: provider-first contracts and generated stubs

Spring Cloud Contract attacks the same problem from the other end and is the more natural fit for an all-JVM, all-Spring estate. Contracts are written as Groovy DSL, YAML or Java files that live with the provider (agreed with consumers in a pull request, or kept in a shared contracts repository). At provider build time the plugin generates JUnit tests from those contracts and runs them against the real controller — so the provider physically cannot merge a change that violates a contract — and then packages the same contracts as a stub JAR published to your artifact repository.

Consumers then pull that stub JAR and run @AutoConfigureStubRunner, which boots a WireMock server serving exactly the provider's agreed responses on a real HTTP port. The consumer's integration test therefore runs against a mock that is generated from the provider's verified contract rather than hand-written and stale — that is the whole trick, and it is why stub-runner tests do not drift. Spring Cloud Contract also covers messaging contracts for Kafka and RabbitMQ, which Pact supports too but which most teams forget to test at all. Rough guidance: choose Pact when consumers are polyglot (a React app, a Node service, a Python job) or when consumers must genuinely drive the contract; choose Spring Cloud Contract when everything is Spring Boot and you want contracts and stubs to fall out of the normal Maven/Gradle build.

// provider: src/test/resources/contracts/shouldReturnOrder.groovy
Contract.make {
    request  { method 'GET'; url '/api/v2/orders/A-1042' }
    response {
        status 200
        headers { contentType(applicationJson()) }
        body(orderId: 'A-1042', status: 'SHIPPED', total: 2499)
        bodyMatchers { jsonPath('$.total', byType()) }   // type, not literal
    }
}
// consumer test: WireMock is fed from the provider's published stub JAR
@AutoConfigureStubRunner(ids = "com.acme:order-service:+:stubs:8090",
                         stubsMode = StubRunnerProperties.StubsMode.REMOTE)

The microservice chassis and the service template

Twelve services means twelve chances to wire up logging, metrics, tracing, health checks, configuration, security, resilience defaults and graceful shutdown — and twelve slightly different answers, which is how you end up unable to correlate a trace across your own estate. The microservice chassis pattern says the cross-cutting concerns belong in a framework layer that every service inherits rather than in each service's own code. On the JVM this is largely Spring Boot plus a thin in-house starter: an acme-service-starter dependency that auto-configures the log format with trace ids, the Micrometer registry and OpenTelemetry exporter, the actuator endpoints and their security, the standard error response body, the default Resilience4j configuration and the shared HTTP client conventions.

The service template is the chassis's delivery mechanism: one blessed, generated starting point — a Spring Initializr configuration, a Backstage software template, a Cookiecutter or a maintained example repository — that produces a new service already carrying the chassis, a working pipeline, a Dockerfile, a Helm chart and a passing test. The subtle failure mode is worth naming in interviews: a chassis is a shared library, so a chassis upgrade is a coordinated upgrade across every service, which is the exact coupling you were trying to escape. Keep the chassis thin and strictly non-business, version it so services can adopt at their own pace, and accept that some concerns (mTLS, retries, traffic shifting) are better pushed out of the library and into the platform — which is the argument for a service mesh.

<!-- every service inherits the same cross-cutting behaviour, versioned independently -->
<dependency>
  <groupId>com.acme.platform</groupId>
  <artifactId>acme-service-starter</artifactId>   <!-- logging + tracing + actuator + -->
  <version>4.2.0</version>                          <!-- error format + resilience defaults -->
</dependency>

Deployment topologies: host, VM, container, serverless

Four topologies, in roughly the order the industry walked through them. Multiple services per host is the cheapest and the worst: services share a machine, a JVM tuning profile and a fate, so one memory leak takes down five services and resource isolation is wishful thinking. Service per VM gives real isolation and independent scaling at the cost of minutes-long boot times and heavy per-instance overhead — sensible when a machine image is your unit of deployment, expensive when you have fifty services. Service per container is today's default: seconds to start, an immutable image that is identical from a developer laptop to production, kernel-level resource limits, and an orchestrator (Kubernetes almost everywhere) handling placement, restarts, rolling updates and service discovery. Serverless removes the server abstraction altogether — you deploy a function, pay per invocation and scale to zero — at the price of cold starts, execution-time limits, constrained runtimes and much heavier vendor coupling.

The interview-worthy point is that the topology decides what your other patterns look like. On Kubernetes, service discovery is a DNS name and a Service object rather than a Eureka client; configuration is ConfigMaps and Secrets; health checks become liveness, readiness and startup probes, and getting readiness wrong is why a rolling update drops traffic. Serverless makes stateful patterns awkward — an in-process circuit breaker or rate limiter is meaningless when each invocation may be a fresh sandbox — so those concerns move to the gateway or the mesh. Choose deliberately, and prefer the boring answer: for a typical Indian product team running a dozen JVM services, service-per-container on managed Kubernetes is the correct default, with serverless reserved for spiky, stateless, event-driven edges.

Service mesh survey: Istio, Linkerd, sidecar and ambient

A service mesh moves service-to-service networking out of your application and into the platform. Classically it does this with a sidecar: a proxy container injected next to every service pod, intercepting all inbound and outbound traffic, so mTLS, retries, timeouts, load balancing, traffic splitting and golden-signal telemetry are configured declaratively by the platform team and apply uniformly to Java, Go, Node and Python services alike. The control plane distributes policy and certificates; the data plane (the proxies) enforces it. The appeal is obvious once your chassis library is the thing blocking a fleet-wide TLS rotation.

Istio is the feature-complete option — Envoy-based, enormously configurable, with fine-grained traffic management, authorization policy and multi-cluster support — and its complexity is real. Linkerd is the deliberately minimal alternative, with a purpose-built Rust micro-proxy, near-zero configuration, automatic mTLS on by default and a much smaller operational and resource footprint; it is the CNCF-graduated "boring" choice. The newest development is ambient mode in Istio, which removes the per-pod sidecar entirely: a per-node ztunnel handles mTLS and L4 telemetry, and an optional per-namespace waypoint proxy handles L7 policy only where you actually need it. That drops the memory tax and the sidecar lifecycle problems (injection ordering, jobs that never terminate because the proxy is still running) that made sidecars painful at scale.

What the mesh takes over from your libraries — and what it costs

Concretely, a mesh can own: mutual TLS and workload identity (certificates issued and rotated automatically, so encryption in transit stops being an application concern); retries, timeouts and outlier ejection at the connection level; load balancing policy; traffic shifting for canary and blue-green releases by weight or by header; and consistent request-level metrics for every hop without instrumenting anything. Notice how much of that overlaps with the resilience and discovery modules earlier in this track — that overlap is the design decision. Anything the mesh does is uniform across languages and changeable without a redeploy; anything your library does is per-language but has business context the proxy will never have.

The honest split: keep semantic resilience in the application — fallbacks, bulkheads sized from your own thread model, idempotency keys, and the decision that a payment must never be retried — because a proxy cannot know that a POST is unsafe to replay. Push transport concerns to the mesh. And price the mesh properly before adopting it: a second proxy on every request path adds latency and memory, someone must own control-plane upgrades and certificate expiry, and debugging gains an extra hop where a misconfigured policy returns a 503 that appears in neither service's logs. For a team running eight services on one cluster with a working chassis, a mesh is usually premature; at forty services, several languages, and a compliance requirement for encryption everywhere, it stops being optional.

# Istio: shift 10% of traffic to v2 with no application change and no redeploy
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: { name: order-service }
spec:
  hosts: [ order-service ]
  http:
    - route:
        - destination: { host: order-service, subset: v1 }
          weight: 90
        - destination: { host: order-service, subset: v2 }
          weight: 10
      retries: { attempts: 3, perTryTimeout: 2s, retryOn: 5xx,connect-failure }

The testing pyramid for microservices

The classic pyramid still holds, but the layers mean different things once the system is distributed. Unit tests (the wide base) cover domain logic with no Spring context and no network — fast, numerous, and where most of your assertions should live. Component or service tests boot one service in isolation with its collaborators stubbed, proving the service's own behaviour end to end within its boundary. Integration tests exercise the real adapters — the actual database, the actual broker, the actual HTTP client — because an ORM mapping, a migration script or a serializer is exactly the sort of thing a mock will never catch. Contract tests occupy the layer that used to be the pyramid's weak point: they prove two services agree without either running the other.

At the top sits a deliberately thin layer of end-to-end tests. Full-estate end-to-end suites are the single most common testing failure in microservices: they are slow, they require a shared environment that is never in a known state, they are flaky enough that teams learn to re-run rather than investigate, and their ownership is ambiguous so nobody fixes them. Keep a handful covering your two or three revenue-critical journeys (sign up, place order, take payment), run them against a real deployed environment, treat any failure as a release blocker — and resist every request to add the fifty-first. Everything the deleted end-to-end tests were nominally covering should be re-expressed as contract tests plus production monitoring.

Integration tests that use the real thing: Testcontainers

The old compromise was an in-memory H2 database standing in for PostgreSQL and an embedded broker standing in for Kafka — which means your tests validate behaviour that production does not have, and miss behaviour that it does (dialect differences, JSONB columns, transaction isolation, partition rebalancing). Testcontainers removes the compromise: your JUnit test starts a real PostgreSQL, Kafka, Redis, MongoDB or LocalStack container from a Docker image, hands Spring the generated connection URL through @DynamicPropertySource or a @ServiceConnection bean, and tears it down afterwards. The dependency is genuine, the test is hermetic, and it runs the same on a laptop and in CI.

Spring Boot 3 and later make this first-class: @ServiceConnection removes the property-wiring boilerplate entirely, and Testcontainers-at-development-time lets bootTestRun start the same containers for local development so a new joiner needs Docker and nothing else. Two practical notes for interviews: reuse containers across test classes (a single static container per class hierarchy, or testcontainers.reuse.enable) or startup cost will dominate your build; and pin exact image tags, because a floating latest tag turns your test suite into an unpinned dependency on someone else's release schedule.

@SpringBootTest
@Testcontainers
class OrderRepositoryIT {

    @Container
    @ServiceConnection                                  // Spring Boot wires the datasource itself
    static PostgreSQLContainer<?> db =
        new PostgreSQLContainer<>("postgres:16.4-alpine");   // pin the tag, never "latest"

    @Autowired OrderRepository repository;

    @Test void persistsAndReloadsAnOrder() {
        repository.save(new Order("A-1042", Status.SHIPPED));
        assertThat(repository.findById("A-1042")).isPresent();
    }
}

Testing in production: canary releases, feature flags and synthetic monitoring

No pre-production environment reproduces production's data volume, traffic mix, third-party behaviour or hardware, so the last testing layer necessarily runs in production — the choice is only whether you do it deliberately. A canary release routes a small slice of live traffic to the new version, compares its error rate and latency against the incumbent, and promotes or rolls back automatically on that evidence; Argo Rollouts and Flagger drive this on Kubernetes, and a service mesh supplies the traffic weights. Blue-green is the coarser sibling: two full environments, an instant switch and an instant rollback, at the cost of running double capacity and needing a database schema both versions can serve — which is expand–contract again, now applied to your tables.

Feature flags decouple deploy from release: ship the code dark, enable it for internal users, then a percentage of traffic, then everyone, and kill it instantly if the graphs turn without needing a redeploy. The discipline that keeps this from becoming technical debt is a removal date on every release toggle — long-lived flags multiply the code paths you must reason about and are a genuine source of production incidents. Finally, synthetic monitoring runs your critical journeys as scripted transactions against production on a schedule, from outside the network, so you find out the checkout flow is broken from a robot at three in the morning rather than from a customer at nine. Pair it with real-user monitoring and SLO-based alerting: at this stage of a distributed system, your monitoring genuinely is part of your test suite.

The verdict: what you would actually do on Monday

Closing this track, here is the defensible ordering. First, write down the compatibility rules and enforce them in code review: additive changes only, tolerant readers everywhere, no field ever renamed. That costs nothing and prevents most breakage. Second, pick your two noisiest service pairs — the ones that have actually broken each other — and put contract tests between them, plus a broker and a can-i-deploy gate in those two pipelines. Do not attempt estate-wide contract testing in month one; a contract suite nobody trusts is worse than none. Third, delete end-to-end tests aggressively as contract coverage arrives, and replace the confidence with Testcontainers-backed integration tests plus real production monitoring.

Fourth, invest in the chassis and the service template before you invest in a mesh — a shared starter that gives every service the same logs, traces, health checks and error format pays back immediately and costs one library. Fifth, adopt a mesh only when the pain is concretely one a mesh solves: many languages, mandatory mTLS, or traffic shifting you cannot do at the gateway; and when you do, start with the smaller tool or with ambient mode rather than the maximal configuration. Sixth, put canary releases and feature flags in place early, because they are what let you ship on a Friday and sleep. If you only remember one line from this module: microservices are not about small services, they are about independent deployment — and contracts, tests and a boring platform are the only three things that keep it independent.

Interview questions

These are the architecture-judgement questions that close a senior microservices round in Indian product and service companies — the versioning and contract questions come up almost every time, and the platform ones are where interviewers decide between "has used microservices" and "has run microservices":

Beginner What makes an API change backward compatible?

Existing clients keep working without any change on their side. Safe: adding an optional response field, adding a new endpoint, adding an optional request parameter, adding a new enum value that clients can ignore. Breaking: removing or renaming a field, changing its type, making an optional request field required, tightening validation, or changing the meaning of an existing value. The rule of thumb is additive-only.

Beginner What is a tolerant reader, and why does it matter?

A consumer that reads only the fields it needs and ignores everything else instead of failing on unknown properties. It matters because a strict consumer turns the provider's safe additive change into an outage, which teaches the provider that no change is safe and freezes the API permanently. In Jackson terms: do not enable fail-on-unknown-properties for inbound service responses.

Beginner Name the ways to version a REST API, with one tradeoff each.

URI path (/api/v2/orders) — explicit and cacheable, but the version leaks into the resource identifier. Request header (API-Version: 2) — clean URIs, but invisible in a browser and easy to lose at a proxy unless you add it to the cache key. Media type (Accept: application/vnd.acme.order.v2+json) — most REST-correct content negotiation, most awkward for ordinary clients. Query parameter — simplest, but easily dropped and messy to cache.

Beginner What is a distributed monolith, and how would you spot one?

Services that are physically separate but must be released together. Symptoms: a shared release train, a version-matrix spreadsheet, "deploy A before B" runbooks, a shared database schema, and one team blocking another's deploy. The single diagnostic question is whether you can deploy any one service to production right now without deploying anything else.

Intermediate Explain the expand–contract (parallel change) pattern.

Three independently deployable steps. Expand: add the new field, endpoint or column beside the old one and write to both, so old and new consumers are both satisfied. Migrate: move consumers over one at a time on their own schedule. Contract: once telemetry shows nobody reads the old shape, delete it. Each step is separately revertible, which is what avoids the coordinated big-bang cutover. It applies identically to REST payloads, event schemas and database columns.

Intermediate How do you retire an old API version responsibly?

Announce it in the protocol, not just in email: emit the Deprecation header (RFC 9745) and a Sunset header (RFC 8594) with the date the endpoint stops responding, plus Link headers to the migration guide and successor version. Then instrument every call still hitting the old version tagged by consumer, chase the remaining callers individually, and delete only when that count reaches zero — the metric decides the date, not the calendar.

Intermediate What is consumer-driven contract testing and what problem does it solve that mocks do not?

The consumer writes a test against a mock provider; the framework records the interactions it relied on as a contract, and the provider's own build replays that contract against the real provider. A hand-written mock is a guess about the provider that silently drifts, so a green consumer build can ship against an API that no longer exists. A contract is verified against the real provider in CI, so drift becomes a build failure — and neither pipeline ever needs both services running.

Intermediate Pact versus Spring Cloud Contract — how do you choose?

Pact is polyglot and genuinely consumer-first: the consumer generates the pact, the broker distributes it, providers verify. Choose it when consumers include non-JVM clients or when consumers must drive the contract. Spring Cloud Contract is provider-first and JVM-native: contracts live with the provider, generate provider tests, and are published as a WireMock stub JAR consumers run via stub runner. Choose it for an all-Spring estate where you want contracts and stubs to fall out of the normal Maven or Gradle build. Both support messaging contracts.

Intermediate Why should contract tests match on types rather than exact values?

Because a contract's job is to prove the shape of the conversation, not the content of one sample. Asserting the literal string "A-1042" or a fixed timestamp makes the contract fail on any harmless data change, teams start ignoring red builds, and the safety net stops being trusted. Use type and regex matchers for values, and keep business assertions in the provider's own unit tests where they belong.

Intermediate What is a microservice chassis, and what is the catch?

A shared framework layer giving every service the same cross-cutting behaviour — structured logging with trace ids, metrics and tracing exporters, health and actuator endpoints, the standard error body, security and resilience defaults — usually as an in-house Spring Boot starter, delivered through a service template. The catch is that it is a shared library, so a chassis upgrade is a coordinated change across every service, the exact coupling microservices exist to avoid. Keep it thin, strictly non-business, versioned so services adopt at their own pace, and push transport concerns to the platform instead.

Pro Compare the four deployment topologies and say which you would pick today.

Multiple services per host: cheapest, no isolation, shared fate — avoid. Service per VM: real isolation and independent scaling, but minutes to boot and heavy per-instance overhead. Service per container on an orchestrator: seconds to start, immutable images, kernel-enforced resource limits, and the platform supplies discovery, restarts and rolling updates — the default answer for a typical dozen-service JVM estate. Serverless: scale to zero and per-invocation billing, at the cost of cold starts, runtime limits and vendor coupling; reserve it for spiky, stateless, event-driven edges. Also note that the topology dictates your other patterns — on Kubernetes, discovery is DNS and readiness probes replace much of what a discovery client did.

Pro When would you adopt a service mesh, and what does it take over from your code?

Adopt when the pain is one a mesh actually solves: several languages needing identical networking behaviour, mandatory mutual TLS with automatic certificate rotation, or traffic shifting you cannot do at the gateway. It takes over transport concerns — mTLS and workload identity, connection-level retries and timeouts, load balancing, outlier ejection, weighted traffic splitting, and uniform request telemetry — configurable without redeploying anything. It does not take over semantic resilience: fallbacks, bulkhead sizing, idempotency keys and the decision that a payment must never be replayed stay in the application, because a proxy has no business context. The cost is a proxy on every request path, control-plane and certificate ownership, and an extra hop that can fail invisibly to both services.

Pro Istio sidecar mode versus ambient mode — what changed and why?

Sidecar mode injects an Envoy proxy into every pod: uniform but expensive in memory, and it brings lifecycle problems — injection ordering, pods that never terminate because the proxy outlives the job, and a restart of every workload to upgrade the mesh. Ambient mode splits the data plane: a per-node ztunnel handles mTLS and L4 telemetry for all pods on that node, and an optional per-namespace waypoint proxy handles L7 policy only where you need it. The result is a much lower resource tax, no per-pod injection, and incremental adoption — you can get encryption everywhere first and add L7 policy selectively.

Pro Your team has 300 end-to-end tests and a red pipeline most mornings. What do you do?

Treat the suite as the defect, not the symptom. Keep three to five end-to-end journeys covering revenue-critical flows and make those blocking; delete or quarantine the rest. Re-express what they covered one layer down: contract tests for every cross-service expectation, Testcontainers-backed integration tests for real database and broker behaviour, and unit tests for domain logic. Backfill the residual risk with production signal — canary analysis, SLO alerting and synthetic probes on the same critical journeys. Full-estate end-to-end suites fail because they need a shared environment nobody owns and produce flakiness that trains people to re-run instead of investigate.

Pro How does a contract-testing pipeline actually block a bad deploy?

Consumers publish pacts to a broker tagged with version and branch; a broker webhook triggers the provider's verification build, which replays every relevant consumer contract against the real provider and publishes results back. The broker maintains the compatibility matrix of which consumer version works with which provider version in which environment. Before deploying, the pipeline runs can-i-deploy against the target environment — if this build is not verified compatible with what is currently live there, the deploy step fails. Record deployments back to the broker so it knows the true state, and use pending and WIP pacts so a brand-new consumer expectation cannot break the provider's main build before it is implemented.

Pro Canary release versus blue-green versus feature flags — when is each right?

Blue-green runs two full environments and switches all traffic at once: instant rollback, simple to reason about, needs double capacity and a schema both versions can serve. Canary shifts a small percentage of live traffic to the new version and promotes or rolls back on observed error rate and latency: the best evidence, needs traffic-splitting infrastructure and good metrics. Feature flags separate deploy from release entirely, so the code ships dark and is enabled per user segment and killed without a redeploy — the finest-grained control, at the cost of code paths that multiply if flags are not removed on a schedule. In practice mature teams run all three: flags for functional risk, canary for operational risk, blue-green where an instant whole-system rollback is required.
