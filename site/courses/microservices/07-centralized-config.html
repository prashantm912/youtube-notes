Module: Centralized Configuration

Config baked into a build means rebuilding an image to change a timeout. Config copy-pasted into twenty services means twenty places to edit and one of them will be wrong. This module is about the third option: config that lives outside the artifact and reaches the app at runtime.

Knowledge Library → Courses → Microservices → Centralized Configuration

What this module covers

Two paths solve the same problem and you will meet both. The Spring Cloud Config Server path keeps a Git-backed store of {application}-{profile} property files that services fetch at startup and can re-read on demand via @RefreshScope. The Kubernetes-native path mounts ConfigMaps and Secrets into pods as files or environment variables, with real secret management delegated to Vault, a cloud secrets manager, or Sealed Secrets.

Both paths inherit the same underlying discipline — the twelve-factor rule that config belongs in the environment, never in the artifact — and both raise the same hard question at the end: what happens when a value changes while the service is running?

Topics

Config in the environment: the twelve-factor rule

The twelve-factor definition of config is deliberately narrow: config is everything that varies between deploys — database URLs, credentials, per-environment hostnames, feature toggles — and nothing else. Internal wiring that is identical in dev, staging and production is code, not config. The litmus test the twelve-factor authors propose is blunt: could you open-source the repository right now without leaking a credential? If not, config and code are tangled.

Why it matters in a microservices context: the same build artifact must be promotable through every environment untouched. Once a jar or container image contains an environment-specific value, you have a per-environment artifact, and "it worked in staging" stops meaning anything. Spring Boot already gives you the machinery — a layered Environment with a defined precedence order in which command-line arguments and environment variables override packaged property files — so externalizing config is mostly about knowing that order rather than inventing a mechanism.

# same image, three environments — nothing rebuilt
docker run -e SPRING_PROFILES_ACTIVE=prod \
           -e SPRING_DATASOURCE_URL=jdbc:postgresql://db-prod/orders \
           orders-service:1.4.2

Spring Cloud Config Server: a Git-backed config store

Config Server is a small Spring Boot application whose entire job is to serve properties over HTTP. Its backing store — the environment repository — is usually a Git repo, which buys you the four things a config store needs almost for free: history, diffs, pull-request review, and rollback by git revert. Filesystem, JDBC, Vault, AWS Secrets Manager and Redis backends exist too, and can be composited so one server serves several kinds of source.

The naming convention is the whole API. Files are named {application}-{profile}.yml (or .properties), and a client asking for application orders with profile prod receives a merged result assembled from most-general to most-specific: application.yml (shared defaults for every service), then application-prod.yml, then orders.yml, then orders-prod.yml — with later, more specific sources winning. A {label} (Git branch or tag, default main) adds a third axis, which is how teams pin a release to a config snapshot. You can curl any of it directly, which makes debugging pleasantly boring.

config-repo/
  application.yml          # every service, every profile
  application-prod.yml     # every service, prod only
  orders.yml               # orders service, all profiles
  orders-prod.yml          # orders service, prod  (highest precedence)

GET http://config:8888/orders/prod          -> merged JSON
GET http://config:8888/orders-prod.yml      -> merged YAML

The client side: import, encryption and dynamic refresh

Modern Spring Boot clients no longer need a bootstrap.yml. A single spring.config.import=configserver:http://config:8888 in application.yml pulls remote properties in as an ordinary config-data import, in a documented position in the precedence chain; add optional: in front of it if you want local development to survive without a running config server. Sensitive values do not have to sit in Git as plaintext: the server can decrypt properties written as {cipher}... using a symmetric key or a keystore, so the repository holds ciphertext and the client receives plaintext over TLS.

Refresh is the part interviewers push on. Fetching config once at startup means a changed value needs a restart — acceptable for a datasource URL, painful for a feature flag or a rate limit. Annotating a bean @RefreshScope makes it a lazy proxy that is thrown away and rebuilt on the next access after someone POSTs to the Actuator refresh endpoint; @ConfigurationProperties beans rebind on refresh without the annotation. Calling that endpoint on every instance by hand does not scale, so Spring Cloud Bus links the instances over RabbitMQ or Kafka and turns one call to busrefresh into a broadcast. Note the honest limits: a refreshed value only reaches code that re-reads it, and things fixed at construction time — connection pool sizes, listener container concurrency — often need a restart regardless.

spring:
  application.name: orders
  config.import: "optional:configserver:http://config:8888"
management.endpoints.web.exposure.include: refresh,busrefresh,health

Kubernetes ConfigMaps: config as files and environment variables

If the platform is Kubernetes, a lot of Config Server's job is already done for you. A ConfigMap is a namespaced API object holding non-confidential key/value pairs, consumed by a pod in one of three ways: injected as individual environment variables, injected wholesale with envFrom, or mounted as a volume so each key becomes a file in a directory. Spring Boot reads a mounted directory natively through spring.config.import=configtree:/etc/config/, and Spring Cloud Kubernetes goes further by reading ConfigMaps and Secrets straight from the API server as a Spring PropertySource, matched by application name and profile — the same mental model as Config Server, without running a config server.

The consumption style is a real decision, not a preference. Environment variables are captured once when the container process starts, so an updated ConfigMap never reaches a running pod; you must roll the deployment. Mounted volumes are different: the kubelet refreshes projected files periodically, so the file content does change under a running process — which only helps if the application actually re-reads the file. Also worth knowing: ConfigMaps are size-limited (roughly 1 MiB) and are not a place for large blobs, and a ConfigMap referenced but absent will keep your pod from starting.

envFrom:
  - configMapRef: { name: orders-config }   # every key as an env var
volumeMounts:
  - name: cfg
    mountPath: /etc/config                  # every key as a file
    readOnly: true

Secrets, external secret managers and rotation

A Kubernetes Secret is a ConfigMap with a different name and slightly better manners: it is stored separately from pod specs, can be mounted into a tmpfs rather than written to disk, and is typed. What it is not, by default, is encrypted. Secret values are base64-encoded, and base64 is an encoding, not encryption — anyone who can run kubectl get secret -o yaml or read etcd can decode them in one command. Making Secrets meaningfully secret requires two deliberate steps the docs are explicit about: enable encryption at rest for the secrets resource, and lock down RBAC so only the service accounts that need a Secret can read it. Committing a Secret manifest to Git is the same mistake as committing a password, which is exactly the gap Sealed Secrets fills by encrypting the manifest so only the in-cluster controller can decrypt it.

Beyond the cluster, dedicated secret managers — HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager — add what Kubernetes does not have: audit trails, fine-grained policy, short-lived dynamic credentials, and rotation. Rotation is where a design either holds or quietly fails. Rotating a database password is worthless if every service read that password once at startup and cached it in a connection pool for the next thirty days; the rotation "succeeds", nothing errors, and the credential is stale until the next deploy. A rotation-aware design decides in advance how the new value arrives — a projected volume the app re-reads, a Vault Agent or Secrets Store CSI driver refreshing the mount, a busrefresh broadcast, an External Secrets Operator sync that triggers a rolling restart — and pairs it with overlapping validity windows so old and new credentials both work during the changeover. Ask "who re-reads this, and when?" while designing, not during the incident.

Interview questions

Configuration questions asked constantly in Indian product and service-company rounds — service companies push Spring Cloud Config hard, product companies push Kubernetes Secrets and rotation:

Beginner Why not just keep configuration inside the application jar?

Because it makes the artifact environment-specific. Changing a timeout or a database URL then means a rebuild and a redeploy, the same build cannot be promoted from staging to production unchanged, and secrets end up in version control. Twelve-factor separates config from code so one artifact runs everywhere and only the environment differs.

Beginner What is Spring Cloud Config Server and what backs it?

A standalone Spring Boot service that serves properties to other services over HTTP. The default backend is a Git repository, which gives versioning, diffs, review and rollback for free. Filesystem, JDBC, Redis, Vault and AWS Secrets Manager backends are also supported, and several can be composited into one server.

Beginner How does a client tell the config server which properties it wants?

Through three coordinates: application name (spring.application.name), active profile (spring.profiles.active), and label (the Git branch or tag, default main). They map onto the {application}-{profile}.yml file naming in the repository.

Beginner What is the difference between a ConfigMap and a Secret in Kubernetes?

Both hold key/value data consumed as environment variables or mounted files. ConfigMaps are for non-confidential data and stored as plain text. Secrets are intended for sensitive data: values are base64-encoded, they are stored apart from pod specs, they can be mounted into memory-backed tmpfs, and they can be encrypted at rest and restricted by RBAC. The API shape is nearly identical, the handling is not.

Intermediate Given application.yml, application-prod.yml, orders.yml and orders-prod.yml, which value wins?

orders-prod.yml. The server merges from most general to most specific — shared defaults, then profile-wide, then service-specific, then service-plus-profile — with the most specific source overriding. Put cross-cutting defaults in application.yml and only the genuine differences in the specific files.

Intermediate How do you change a property without restarting the service?

Annotate the bean holding the value with @RefreshScope (or use a @ConfigurationProperties bean, which rebinds automatically), expose the Actuator refresh endpoint, and POST to it after the config changes. The scoped bean is discarded and rebuilt with new values on next access. For many instances, use Spring Cloud Bus over RabbitMQ or Kafka and call busrefresh once to broadcast.

Intermediate Is bootstrap.yml still required for a config client?

No. The legacy bootstrap context is deprecated; current Spring Boot uses spring.config.import=configserver:http://host:port in ordinary application.yml, which slots remote config into the documented config-data precedence order. Prefix with optional: so the app still starts when the server is unreachable. Expect a follow-up on how you keep local development working.

Intermediate Is base64 in a Kubernetes Secret a form of encryption?

No — it is an encoding, reversible by anyone with the data and one command. Without extra work, Secret values sit in etcd as plain text. To make them meaningfully secret you must enable encryption at rest for the secrets resource (ideally with an external KMS provider) and restrict read access through RBAC and per-workload service accounts.

Intermediate What happens to a running pod when you update a ConfigMap it uses?

It depends on consumption style. Values injected as environment variables are fixed at process start and never change — the deployment must be rolled. Values mounted as a volume are refreshed by the kubelet after a short propagation delay, so the file content changes; whether the app notices depends on whether it re-reads the file. Immutable ConfigMaps and subPath mounts never update at all.

Intermediate How do you keep passwords out of the config Git repository?

Config Server can decrypt values stored as {cipher}..., so the repo holds ciphertext and clients receive plaintext over TLS — with the key held by the server, not committed. Stronger options move secrets out of Git entirely: a Vault or AWS Secrets Manager backend, Sealed Secrets for manifests, or the External Secrets Operator syncing from a manager into Kubernetes Secrets.

Pro The config server is down when fifty pods restart. What happens, and how do you design around it?

With fail-fast enabled the pods refuse to start; without it they start on possibly-wrong defaults, which is often worse. Mitigations: run the config server as a replicated, health-checked deployment; enable client retry with backoff so transient outages are absorbed; keep sane local fallbacks for non-critical values; and on Kubernetes prefer ConfigMaps and Secrets, which the platform delivers with no extra runtime dependency. This is the standard "you added a new single point of failure" follow-up.

Pro You rotated a database password in the secret manager and nothing broke — then everything broke a week later. Explain.

The services read the credential once at startup and cached it in their connection pools, so rotation changed the stored value without changing what the apps were using. The failure surfaced only when a pod restarted or a pool reconnected with the stale credential. A rotation-aware design defines the delivery path (re-read a projected volume, Vault Agent or the Secrets Store CSI driver refreshing the mount, a broadcast refresh, or an operator-triggered rolling restart) and keeps both old and new credentials valid during an overlap window.

Pro Spring Cloud Config Server or Kubernetes ConfigMaps — how do you choose?

If the platform is already Kubernetes, ConfigMaps and Secrets are the default: no extra service to run, native RBAC and audit, and Spring Cloud Kubernetes or a configtree import reads them with no custom code. Config Server earns its place with a heterogeneous estate (virtual machines, several platforms, or non-Kubernetes runtimes), a genuine need for Git-native review and history over config, or environment-and-label resolution richer than Kubernetes provides. Some teams run both: Config Server for application properties, Secrets for credentials.

Pro Which properties can a refresh event genuinely change, and which cannot?

Anything re-read on each use changes cleanly: feature flags, thresholds, URLs read per call, and @ConfigurationProperties beans. Anything captured at construction or startup does not: connection pool sizing, server port, thread pool and listener concurrency, and values injected once with @Value into a singleton outside refresh scope. Say this explicitly in an interview — claiming refresh changes everything is the trap the question is set for.

Pro How would you audit and control who can change production configuration?

Treat config as reviewed code: a protected branch in the config repository with required pull-request approval, signed commits, and CI validation of the resulting merged config. On the runtime side, restrict who can read or edit Secrets via namespaced RBAC and per-workload service accounts, enable API audit logging, and use a secret manager with its own audit trail and least-privilege policies for anything credential-shaped. The Git history and the audit log together answer "who changed the timeout at the time the incident started".
