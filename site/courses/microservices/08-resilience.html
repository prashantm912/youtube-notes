Module: Resilience with Resilience4j

In a distributed system nothing is either up or down — some fraction of calls is always failing. Resilience is the engineering that keeps one sick dependency from taking your service, and its callers, down with it.

Knowledge Library → Courses → Microservices track → Resilience with Resilience4j

What this module covers

Partial failure is the normal operating condition of a microservice estate: one downstream is slow, one node is garbage-collecting, one network path is flapping. The danger is not the failure itself but the cascade — callers block on a sick service, exhaust their own threads and connection pools, and stop serving requests they could have served.

This module covers the toolkit that contains that blast radius: the circuit breaker and its state machine, retries with exponential backoff and jitter, time limits, bulkheads and rate limiters — and, critically, the order these decorators must compose in. Resilience4j is the reference implementation on Spring Boot 3.x/4.x, usually behind the Spring Cloud Circuit Breaker abstraction.

Topics

Partial failure, cascading failure, and why Hystrix gave way to Resilience4j

A synchronous call to a healthy-but-slow service is worse than a call to a dead one: a dead service fails in milliseconds, a slow one holds your thread for the full socket timeout. Multiply that by request volume and the caller's thread pool fills with threads parked on one dependency; requests to unrelated endpoints queue behind them and the caller looks "down" even though only one of its ten dependencies is unhealthy. That is cascading failure, and it propagates upward one hop at a time until the edge.

Netflix Hystrix popularised the countermeasures, but it went into maintenance mode in 2018 and is no longer actively developed — Netflix moved to adaptive concurrency limits, and the JVM ecosystem moved to Resilience4j, a lightweight, functional-style library with no external dependencies beyond Vavr's successor internals. Spring's own spring-cloud-circuitbreaker project provides a vendor-neutral API with Resilience4j as the default implementation, so you can write against CircuitBreakerFactory or straight against Resilience4j annotations.

The circuit breaker state machine: CLOSED, OPEN, HALF_OPEN

A circuit breaker is a proxy around a remote call that keeps a rolling record of outcomes. In CLOSED it lets everything through and counts results. When the recorded failure rate crosses the threshold it flips to OPEN, where every call is rejected immediately with CallNotPermittedException — no thread parked, no socket opened, failure in microseconds instead of seconds. That fast rejection is the whole point: it gives the downstream room to recover and it gives the caller its threads back.

After waitDurationInOpenState the breaker moves to HALF_OPEN and admits a small, fixed number of probe calls (permittedNumberOfCallsInHalfOpenState). If those probes meet the threshold it returns to CLOSED; if not it goes back to OPEN and waits again. Resilience4j adds three non-counting states you should be able to name in an interview: DISABLED (always allow), FORCED_OPEN (always reject) and METRICS_ONLY (record but never trip) — the last is how you safely observe a breaker in production before letting it act.

Tuning the breaker: sliding window, thresholds and slow calls

The breaker decides on evidence held in a sliding window, and choosing the window type is the first real design decision. COUNT_BASED keeps the last N calls — predictable for steady traffic, but on a low-traffic endpoint it can hold hours-old outcomes. TIME_BASED keeps the calls of the last N seconds — self-expiring, better for bursty or low-volume endpoints. Either way minimumNumberOfCalls gates the maths: below it the breaker never trips, which stops two failures out of two from opening a circuit on a cold start.

Two rates can trip it. failureRateThreshold (percent) counts exceptions in recordExceptions; slowCallRateThreshold counts calls slower than slowCallDurationThreshold, which is what actually saves you from the healthy-but-degraded dependency that never throws. Also configure ignoreExceptions: a downstream returning HTTP 404 or a validation error is your caller's bug, not a downstream outage, and counting it as a failure opens circuits for no reason.

resilience4j.circuitbreaker:
  instances:
    inventory:
      slidingWindowType: TIME_BASED
      slidingWindowSize: 60          # seconds of history
      minimumNumberOfCalls: 20       # no verdict below this
      failureRateThreshold: 50       # percent
      slowCallDurationThreshold: 2s
      slowCallRateThreshold: 60      # percent
      waitDurationInOpenState: 30s
      permittedNumberOfCallsInHalfOpenState: 5
      automaticTransitionFromOpenToHalfOpenEnabled: true
      ignoreExceptions:
        - com.acme.order.NotFoundException

Fallbacks: designing the answer you give when the circuit is open

Annotate the protected method with @CircuitBreaker(name = "...", fallbackMethod = "..."). The fallback must live in the same class, return the same type, and repeat the original parameters with one extra trailing Throwable (or a narrower exception type — you can declare several overloads and Resilience4j dispatches on the thrown type, which is how you distinguish CallNotPermittedException from a genuine downstream error).

The design rule that separates seniors from juniors: a fallback that calls another remote service is not a fallback, it is a second chance to fail. Good fallbacks are local and near-instant — a cached value, a sensible default, a degraded-but-honest response ("stock level unavailable"), or a queued write acknowledged as pending. Also decide deliberately when not to fall back: silently returning an empty list where the caller expects real data turns an outage into silent data corruption, and for a payment call the right fallback is a clean error the user can act on.

@CircuitBreaker(name = "inventory", fallbackMethod = "stockFallback")
public Stock stockFor(String sku) {
    return inventoryClient.get(sku);            // the remote call
}

// same signature + trailing Throwable; local and cheap, never another remote call
private Stock stockFor(String sku, CallNotPermittedException open) {
    return Stock.unknown(sku);                  // breaker is open: degrade honestly
}
private Stock stockFor(String sku, Throwable other) {
    return cache.lastKnown(sku).orElseGet(() -> Stock.unknown(sku));
}

Retry with exponential backoff and jitter

Retry answers a different question from the circuit breaker: the breaker asks "is this dependency broken?", retry asks "was this one call unlucky?" Retries only help for transient faults — a dropped connection, a brief leader election, an HTTP 503 with a hint to come back. A fixed-interval retry storm is itself an outage amplifier: if a dependency wobbles, every caller retries at the same instant, and the retry traffic keeps it down. Exponential backoff spreads the attempts out in time; jitter — a random factor applied to each wait — spreads them out across callers, which is the actual fix for the thundering herd. Backoff without jitter still synchronises every client onto the same retry beat.

The second rule: never retry a non-idempotent write. A timeout does not tell you whether the request was lost on the way out or the response was lost on the way back — the payment may well have succeeded. Retrying it charges the customer twice. Make the operation idempotent first (an idempotency key, a client-generated request id, a conditional update), then retry. Budget the total too: three attempts at 2 seconds each inside a caller with a 3-second SLA is a guaranteed timeout, so the retry budget must fit inside the enclosing time limit.

resilience4j.retry:
  instances:
    inventory:
      maxAttempts: 3                    # 1 original + 2 retries
      waitDuration: 200ms
      enableExponentialBackoff: true
      exponentialBackoffMultiplier: 2   # 200ms, 400ms, 800ms ...
      enableRandomizedWait: true
      randomizedWaitFactor: 0.5         # the jitter: +/- 50% per wait
      retryExceptions:
        - java.io.IOException
        - java.util.concurrent.TimeoutException
      ignoreExceptions:
        - com.acme.order.BadRequestException

TimeLimiter and Bulkhead: capping time and concurrency

TimeLimiter puts a hard ceiling on how long a call may take, independent of whatever the HTTP client's socket timeouts happen to be. It works on a CompletableFuture or reactive type and cancels the running future when the budget expires. Without it the breaker's slow-call detection is your only defence against a dependency that answers in ninety seconds, and slow calls are the failure mode that most often takes a service down.

Bulkhead caps how many calls to one dependency may be in flight at once, so a single slow dependency can never consume the whole thread pool — the ship's-compartment metaphor. Resilience4j ships two: SemaphoreBulkhead (a permit counter, cheap, the call runs on the caller's own thread, good for blocking MVC code) and ThreadPoolBulkhead (a bounded pool plus queue, true isolation, only usable with async/CompletableFuture returns). Size maxConcurrentCalls from Little's law rather than a round number: concurrency roughly equals target throughput multiplied by expected latency.

resilience4j.bulkhead:                 # semaphore: caller's thread, blocking code
  instances:
    inventory:
      maxConcurrentCalls: 20
      maxWaitDuration: 0               # fail fast rather than queue

resilience4j.thread-pool-bulkhead:     # real isolation, async returns only
  instances:
    reporting:
      coreThreadPoolSize: 4
      maxThreadPoolSize: 8
      queueCapacity: 50

resilience4j.timelimiter:
  instances:
    inventory:
      timeoutDuration: 2s
      cancelRunningFuture: true

RateLimiter: protecting the callee, and staying inside your quota

RateLimiter caps calls per refresh period — limitForPeriod permits every limitRefreshPeriod, with timeoutDuration deciding whether a caller that finds no permit waits briefly or fails immediately with RequestNotPermitted. Two distinct uses: throttling inbound traffic so one tenant cannot starve the others, and throttling your own outbound calls to stay inside a third party's contracted quota (a payment gateway, an SMS provider, a KYC API) so you are never the client that gets banned.

Be clear about scope in interviews: a Resilience4j rate limiter is per JVM instance. Ten pods each permitting 100 requests per second is 1000 requests per second at the provider, not 100. Genuinely global limiting needs a shared counter — Redis-backed limiting at the API gateway, or a service mesh policy — and that is a different tool from the in-process limiter discussed here.

Combining patterns: the decorator order that decides whether any of it works

Stacking annotations is easy; stacking them in the wrong order quietly ruins the breaker. Resilience4j's documented default aspect order, outermost first, is Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( call ) ) ) ) ). Read it outside-in: the bulkhead admits the call, the time limiter bounds it, the rate limiter meters it, the circuit breaker records the outcome, and only then does retry decide whether to go round again. Higher aspect-order values run further out; the order you write the annotations in your source has no effect at all.

Get it backwards — retry inside the breaker — and every individual attempt is recorded as a separate sample, so one bad request logs three failures, the window fills with duplicated evidence and the breaker trips on inflated numbers. Worse, retries keep hammering a downstream the breaker has already judged dead, because the breaker never sees the traffic. The correct arrangement also has a pleasant property: once the breaker is OPEN, retry's attempts are rejected instantly by CallNotPermittedException, so add it to retry's ignore list rather than burning attempts on a circuit already judged open.

# Default order, outermost first:
#   Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( call ) ) ) ) )
# Higher value = further out. Override only if you know why.
resilience4j.retry.retryAspectOrder: 2
resilience4j.circuitbreaker.circuitBreakerAspectOrder: 1

# Don't spend retry attempts on an already-open circuit:
resilience4j.retry.instances.inventory.ignoreExceptions:
  - io.github.resilience4j.circuitbreaker.CallNotPermittedException

Seeing it in production: Micrometer metrics, events and health

An unobserved breaker is a liability — you find out it has been open for two days when a customer tells you. Resilience4j publishes Micrometer meters out of the box: resilience4j_circuitbreaker_state (a gauge tagged by state, so state="open" going to 1 is your alert), resilience4j_circuitbreaker_calls tagged kind=successful|failed|not_permitted, plus buffered-call and slow-call counts, and equivalents for retry, bulkhead and rate limiter. Alert on state transitions and on the not-permitted rate, and graph the failure rate next to the threshold you configured.

Alongside metrics, the Spring Boot starter exposes actuator endpoints — /actuator/circuitbreakers for current state and /actuator/circuitbreakerevents for the recent transition log, which is the fastest way to answer "when exactly did this open, and on what?" during an incident. Register an EventPublisher listener to log transitions at WARN so they land in your normal log pipeline, and remember that a breaker in the open state should usually make the dependent part of your health endpoint degraded rather than down, so Kubernetes does not restart a pod that is behaving correctly.

management.endpoints.web.exposure.include: health,metrics,prometheus,circuitbreakers,circuitbreakerevents
management.health.circuitbreakers.enabled: true
resilience4j.circuitbreaker.instances.inventory.registerHealthIndicator: true

# Prometheus series worth alerting on:
#   resilience4j_circuitbreaker_state{name="inventory",state="open"} == 1
#   rate(resilience4j_circuitbreaker_calls_seconds_count{kind="not_permitted"}[5m])

Interview questions

Resilience is the highest-yield microservices topic in Indian product and service-company rounds — the state machine gets asked almost every time, and the follow-ups separate candidates who have configured it from candidates who have read about it:

Beginner What is a circuit breaker and what problem does it solve?

A proxy around a remote call that tracks recent outcomes and, once failures cross a threshold, stops calling the dependency and fails immediately instead. It prevents cascading failure: without it, callers park threads on a sick downstream until their own pools are exhausted and they go down too. It also gives the downstream breathing room to recover.

Beginner Name the circuit breaker states and the transitions between them.

CLOSED (calls flow, outcomes recorded) → OPEN when the failure rate crosses the threshold with at least minimumNumberOfCalls samples → after waitDurationInOpenState → HALF_OPEN, which admits permittedNumberOfCallsInHalfOpenState probe calls → back to CLOSED if they pass, back to OPEN if they don't. Resilience4j adds three special states: DISABLED, FORCED_OPEN and METRICS_ONLY.

Beginner Why is Resilience4j used instead of Netflix Hystrix?

Hystrix went into maintenance mode in 2018 and is no longer actively developed. Resilience4j is the successor on the JVM: lightweight, no heavy dependency tree, functional decorator API, modular (you take only the modules you need), works with plain functions as well as Spring annotations, and integrates with Micrometer. Spring Cloud Circuit Breaker wraps it behind a vendor-neutral API.

Beginner What is a fallback, and how do you declare one?

The alternative result returned when the protected call fails or is rejected. In Spring you write @CircuitBreaker(name = "x", fallbackMethod = "y"); the fallback lives in the same class, returns the same type, and takes the original parameters plus a trailing Throwable. You can declare several overloads with narrower exception types and Resilience4j picks the closest match.

Intermediate Count-based vs time-based sliding window — which would you choose?

Count-based keeps the last N call results; time-based keeps results from the last N seconds. On a low-traffic endpoint a count-based window can be judging on stale evidence collected hours ago, so time-based is safer there. On steady high-volume traffic count-based is cheaper and more predictable. Either way set minimumNumberOfCalls so the breaker never rules on a handful of samples.

Intermediate What does slowCallRateThreshold do, and why isn't failure rate enough?

It trips the breaker on calls slower than slowCallDurationThreshold, even when they eventually succeed. A degraded dependency that answers in eight seconds throws no exception, so a failure-rate-only breaker stays closed while your threads pile up behind it. Slow calls, not exceptions, are the usual cause of cascading failure, so this setting is the one that matters most in production.

Intermediate Why add jitter to exponential backoff — isn't backoff enough?

No. Backoff alone spreads attempts over time but keeps every client synchronised: if a thousand callers fail at the same moment, they all wait 200ms, then all 400ms, so the retry traffic arrives in synchronised spikes that keep the recovering service down. That is the thundering herd. Jitter randomises each wait so attempts are smeared across the interval and the load arrives as a flat trickle instead of a wave.

Intermediate Semaphore bulkhead vs thread-pool bulkhead?

Semaphore is a permit counter — the call runs on the caller's own thread, near-zero overhead, works with ordinary blocking code, but it does not isolate the caller's thread from a slow downstream. Thread-pool bulkhead runs the call on a separate bounded pool with a queue, giving true isolation and enabling real timeouts, at the cost of context switching and requiring async (CompletableFuture) return types. Default to semaphore; use thread-pool where isolation genuinely matters.

Intermediate Circuit breaker vs retry — when do you use each, and can you use both?

Retry handles a transient, one-off fault; the circuit breaker handles a dependency that is persistently unhealthy. Retry says "try again", the breaker says "stop trying". Use both — the breaker prevents retry from becoming a denial-of-service attack on a dying service — but only in the correct nesting, with the breaker recording the outcome of the whole retried operation.

Pro In what order do Resilience4j decorators compose, and what breaks if you invert Retry and CircuitBreaker?

Outermost to innermost: Retry, CircuitBreaker, RateLimiter, TimeLimiter, Bulkhead, then the call. Higher aspect-order values sit further out; annotation order in the source is irrelevant. Put retry inside the breaker and each attempt is recorded separately, so a single failing request contributes three failure samples — the window fills with duplicated evidence and the breaker trips on inflated numbers while retries keep hammering a downstream the breaker cannot see. Override with retryAspectOrder and circuitBreakerAspectOrder only with a deliberate reason.

Pro Your fallback calls a secondary service. Critique that design.

It is not a fallback. The fallback path runs precisely when the system is unhealthy, so it must be local, fast and dependency-free: a cache, a default, a degraded response, or a queued write. A remote fallback needs its own breaker, its own timeout and its own failure mode, and it usually fails for the same underlying reason (shared network, shared database, shared region). It also converts a fast failure into a slow one, which is what the breaker existed to prevent.

Pro Why is retrying a non-idempotent write dangerous, and how do you make it safe?

A timeout is ambiguous: you cannot tell whether the request never arrived or the response was lost after the write committed. Retrying may therefore duplicate a payment or an order. Make the operation idempotent first — a client-generated idempotency key the server deduplicates on, a conditional update guarded by a version, or an upsert on a natural key — and only then enable retry. Also cap the total retry budget so it fits inside the caller's own time limit.

Pro How would you detect in production that a breaker has opened, and what do you alert on?

Micrometer meters: the resilience4j_circuitbreaker_state gauge tagged by state (alert when state="open" reaches 1), and resilience4j_circuitbreaker_calls tagged kind=successful|failed|not_permitted — a rising not_permitted rate means traffic is being shed. Back that with the actuator circuitbreakers and circuitbreakerevents endpoints for the transition log during an incident, and an event-publisher listener logging transitions at WARN. Open breakers should usually mark a health check degraded, not down, so the orchestrator does not restart a healthy pod.

Pro Your rate limiter permits 100 requests per second, but the provider says you sent 1000. Explain.

Resilience4j's RateLimiter is per JVM instance, not cluster-wide, so ten pods each permit 100 requests per second independently. Fix it by dividing the quota by the replica count (fragile under autoscaling), or by moving the limit to a shared counter — Redis-backed limiting at the API gateway or a service mesh policy — so the budget is enforced once for the whole cluster rather than once per process.
