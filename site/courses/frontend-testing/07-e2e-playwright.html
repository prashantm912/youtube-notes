Module: End-to-End with Playwright

A real browser, the real Angular bundle, a real HTTP round trip — end-to-end tests catch the wiring mistakes no unit test can see, and charge you minutes of CI time for every one you write. This module is about spending that budget well.

Knowledge Library → Courses → Frontend Testing → End-to-End with Playwright

What this module covers

Every test you have written so far in this track runs the component in isolation with a stubbed world. An end-to-end test does the opposite: it boots the actual Angular application, drives a genuine Chromium, Firefox or WebKit browser, and asserts on what a user would see. That fidelity is the whole point — and the whole cost. An e2e suite is orders of magnitude slower than a Vitest run, needs a server, and fails for reasons that have nothing to do with your code.

The practical rule is budget by journey, not by feature: cover sign-in, checkout, the one screen that loses money when it breaks. Everything else belongs lower in the pyramid. This module orients you on Playwright — setup and configuration, the locator model, auto-waiting and web-first assertions, fixtures — and then on the advanced half that separates a demo suite from a production one: network interception, the trace viewer, authentication reuse, parallelism, and an honest look at where Cypress still fits.

Topics

Setting Playwright up against an Angular app

npm init playwright@latest scaffolds everything in one step: the @playwright/test dependency, a playwright.config.ts, an example spec, and the downloaded browser binaries. Playwright ships its own test runner — you do not bolt it onto Vitest or Karma. Point testDir at a folder outside your unit tests (./e2e is the usual choice in an Angular workspace) so ng test and npx playwright test never collide.

Two config keys carry most of the weight. Projects are named run configurations — the generated file gives you one per browser engine, so a single command exercises Chromium, Firefox and WebKit; projects are also how you model mobile viewports and, later, a setup step that logs in before everything else. webServer tells Playwright to start your Angular dev server itself and wait for it to answer before the first test runs, so a fresh clone and a CI machine behave identically. Add baseURL and your specs can call page.goto('/checkout') instead of hard-coding a host.

export default defineConfig({
  testDir: './e2e',
  use: { baseURL: 'http://localhost:4200', trace: 'on-first-retry' },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'webkit',   use: { ...devices['Desktop Safari'] } },
  ],
  webServer: {
    command: 'npm start',              // ng serve
    url: 'http://localhost:4200',
    reuseExistingServer: !process.env.CI,
  },
});

The locator model: getByRole first, getByTestId last

A locator is not an element — it is a recipe for finding one, re-evaluated every time you act on it. That laziness is why a locator survives Angular re-rendering the DOM underneath it, and why page.$()-style element handles are legacy. Locators are also strict: if the recipe matches two nodes, the action throws instead of silently picking the first, which turns an ambiguous selector into a loud failure at authoring time rather than a flake six weeks later.

Playwright's recommended default is getByRole(role, { name }) — it queries the accessibility tree, so the test asserts what a screen reader and a sighted user both perceive, and it breaks when you break accessibility. getByLabel is the idiomatic way into form fields, with getByText, getByPlaceholder and getByTitle filling the gaps. getByTestId (mapped to data-testid by default) is the deliberate escape hatch for elements with no user-visible handle. CSS and XPath selectors still work, but they bind your test to markup structure — exactly the coupling that makes e2e suites expensive to own. Chain with .filter(), .nth() and nested locator() calls rather than writing longer CSS.

await page.getByRole('button', { name: 'Add to cart' }).click();
await page.getByLabel('Email address').fill('asha@example.com');

// scope first, then narrow — safer than one long CSS selector
const row = page.getByRole('row').filter({ hasText: 'ORD-4417' });
await row.getByRole('button', { name: 'Cancel' }).click();

Auto-waiting and web-first assertions

Before every action Playwright runs a list of actionability checks against the located element — attached to the DOM, visible, stable (not mid-animation), able to receive events (not covered by an overlay), and enabled; fill additionally requires editable. It retries those checks until they all pass or the timeout expires. So click() already contains the wait, and the usual reasons an Angular app is "not ready yet" — a pending HTTP call, a running route transition, a CSS transition on a modal — are absorbed without you writing anything.

Assertions work the same way. await expect(locator).toBeVisible() is a web-first assertion: it polls the page until the condition holds or the assertion times out. That is fundamentally different from expect(await locator.isVisible()).toBe(true), which samples once and fails on the first render that has not caught up. The anti-pattern to unlearn is page.waitForTimeout(...) — a fixed sleep is simultaneously too short on a loaded CI runner and pure wasted time everywhere else. Playwright's own docs describe it as discouraged outside debugging. If a wait genuinely needs expressing, express the condition: assert on the element, or await page.waitForResponse().

await expect(page.getByTestId('cart-count')).toHaveText('1'); // polls until true
await expect(page.getByRole('alert')).toBeVisible();
await expect(page).toHaveURL(/\/checkout$/);

await page.waitForTimeout(2000);   // anti-pattern: flaky and slow at the same time

Fixtures, hooks and test structure

Playwright's runner is fixture-based rather than hook-based. When you write test('...', async ({ page }) => { ... }), page is a fixture: the runner constructs a fresh BrowserContext and page for that test, injects it, and disposes it afterwards. Because each test gets its own context, cookies and storage never leak between tests — isolation is the default, not something you remember to clean up. Other built-ins you will reach for are request (an API client that shares the browser's cookies), context, and browserName.

Custom fixtures via test.extend are where suites stay readable at scale: a page-object, a seeded test user, a feature flag, or a worker-scoped resource created once per parallel worker instead of per test. They compose and they are lazy — a fixture is only built if a test actually asks for it, which is more than beforeEach can say. Alongside them, test.describe groups related tests, beforeEach/afterEach still exist for simple setup, test.step() labels phases so the trace and report read like a scenario, and test.skip/test.fixme/test.slow annotate the awkward cases honestly instead of leaving commented-out code.

const test = base.extend<{ checkout: CheckoutPage }>({
  checkout: async ({ page }, use) => {
    await use(new CheckoutPage(page));   // built only if a test asks for it
  },
});

test.describe('checkout', () => {
  test('places an order', async ({ checkout }) => {
    await test.step('pay', () => checkout.payWithCard());
  });
});

Network interception and stubbing with page.route()

page.route(pattern, handler) puts your test in front of the browser's network layer. The handler receives a Route and decides its fate: fulfill() to answer with a canned body, abort() to simulate a failure, continue() to let it through with modified headers or payload, or fetch() then fulfill() to take the real response and patch one field. Glob patterns like '**/api/orders' match the URLs your Angular HttpClient calls.

This is the lever that makes e2e affordable. Real backends are slow, shared, and refuse to produce the states you need to test — a 500, an empty result set, a payment gateway timeout, a token that expires mid-session. Stub those routes and the scenario becomes a two-line setup that runs in milliseconds. The discipline is knowing when not to: if you stub every request, you are no longer testing integration, just an expensive component test. Keep the critical journey talking to the real API and stub the edge cases around it. page.route is also how you block analytics, fonts and third-party widgets to cut noise and runtime, and waitForResponse/expect(request) let you assert that the app actually sent what it should.

await page.route('**/api/orders', route =>
  route.fulfill({ status: 200, json: [{ id: 7, total: 499 }] }));

await page.route('**/api/payment', route => route.abort('failed')); // gateway down
await page.route(/analytics|hotjar/, route => route.abort());       // cut the noise

Debugging: trace viewer, UI mode and codegen

The traditional pain of e2e work is a red CI job with a one-line error and no way to reproduce it locally. Playwright's answer is the trace: set trace: 'on-first-retry' and every retried failure produces a trace.zip containing a DOM snapshot before and after each action, the full network log, console output, source, and screenshots. Open it with npx playwright show-trace (or drop it on the hosted viewer) and step backwards through the run, hovering any action to see the exact page state and the locator it resolved. Attach the trace as a CI artifact and remote failures stop being guesswork.

Locally, npx playwright test --ui is the same machinery in watch mode: pick tests, re-run on save, time-travel through the timeline, and use the pick-locator tool to get a suggested locator for anything on the page. npx playwright codegen <url> records your clicks and typing into a runnable spec — excellent for discovering the right locator and for onboarding, though generated code always wants cleaning up into page objects. Round it out with --debug (Playwright Inspector, step-through), --headed, and page.pause().

npx playwright test --ui                 # watch mode + time-travel debugging
npx playwright codegen http://localhost:4200
npx playwright test --debug              # Playwright Inspector, step by step
npx playwright show-trace trace.zip      # open a trace from CI

Authentication once, and running in parallel

Logging in through the UI at the start of every test is the single biggest waste in most suites. The Playwright answer is storageState: run a setup project that performs the login once, call page.context().storageState({ path: '.auth/user.json' }) to dump cookies and local storage to a file, then declare use: { storageState: '.auth/user.json' } so every subsequent test starts already authenticated. Multiple roles are just multiple state files, wired to different projects. Do not commit those files — they hold live session tokens.

Parallelism is on by default: Playwright shards test files across worker processes, each with its own browser instance, so a suite that takes twenty minutes serially can finish in three. test.describe.configure({ mode: 'parallel' }) parallelises within a file; mode: 'serial' forces order when tests genuinely depend on each other (a smell worth resisting). fullyParallel, workers and --shard tune it for CI. Retries deserve care: retries: 2 on CI plus trace: 'on-first-retry' gives you a diagnosable artifact for every flake, but retries hide instability rather than fix it — treat a test that only passes on retry as a bug report, and note that the HTML reporter marks it "flaky" precisely so it cannot be ignored.

// auth.setup.ts — runs once as a setup project
await page.getByLabel('Username').fill(process.env.E2E_USER!);
await page.getByRole('button', { name: 'Sign in' }).click();
await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
await page.context().storageState({ path: '.auth/user.json' });

Cypress awareness, and component tests versus e2e

Cypress is the tool Playwright displaced, and you will still meet it in interviews and in existing codebases, so know the shape of the difference. Cypress runs its commands inside the browser alongside your app, which gives an excellent interactive runner and easy access to app internals, but historically constrained it: one browser tab and origin per test, no WebKit engine, no true cross-browser parity, and a chained command API that is not real promises. Playwright drives the browser over the DevTools/CDP-style protocol from Node, so multiple tabs, multiple origins, iframes, downloads, WebKit and cross-browser projects all fall out naturally, and tests are plain async/await. Cypress's own strength worth borrowing conceptually is retry-ability — the same idea as Playwright's web-first assertions. A fair answer in an interview: Playwright for new work and anything needing cross-browser or multi-origin coverage; Cypress is a reasonable place to stay if a mature suite and team habits already exist there.

Separately, do not confuse component tests with e2e. Playwright ships an experimental component-testing mode that mounts a single component in a real browser — useful when jsdom-style environments misrepresent layout or native browser behaviour, but it is not an end-to-end test: no routing, no backend, no journey. For Angular specifically, TestBed plus Vitest (modules 03 to 06 of this track) remains the component layer. Playwright's job starts where the whole application, served and routed, is what you need to prove.

Interview questions

Playwright has become a standard line item in Indian frontend and SDET interviews — service companies probe setup and locators, product companies push on flake, traces and suite economics:

Beginner What is end-to-end testing and how is it different from a unit or component test?

An e2e test exercises the deployed application as a user does — real browser, real routing, real (or deliberately stubbed) HTTP — and asserts on visible outcomes. A unit or component test isolates one piece with fakes around it. E2E gives the highest confidence that the pieces are wired together and the lowest speed and stability, so it sits at the top of the pyramid and covers critical journeys only.

Beginner How do you add Playwright to an existing Angular project?

npm init playwright@latest — it installs @playwright/test, downloads the browser binaries, and generates playwright.config.ts plus a sample spec. Point testDir at a dedicated folder such as ./e2e so it does not clash with unit tests, set baseURL, and configure webServer to run ng serve and wait for it before the suite starts.

Beginner What is a locator in Playwright, and why is it preferred over a stored element reference?

A locator describes how to find an element and is resolved fresh on every action, so it stays valid when Angular re-renders the DOM. Old-style element handles point at a specific node and go stale. Locators also bring auto-waiting and strict mode along for free.

Beginner Which locator should you reach for first, and what is getByTestId for?

getByRole(role, { name }) first — it queries the accessibility tree, matches how users and assistive technology perceive the page, and doubles as an accessibility check. Then getByLabel for form controls, then text-based queries. getByTestId (data-testid) is the explicit escape hatch for elements with no accessible name or stable visible text; it is stable but tells you nothing about user experience, so it should not be the default.

Beginner What does Playwright's auto-waiting actually do?

Before each action it retries a set of actionability checks on the element — attached, visible, stable (animations finished), receiving events (not obscured), enabled, and editable for fill — until they all pass or the timeout expires. So a click() already waits for the button to be genuinely clickable; you do not add sleeps around it.

Intermediate Why is page.waitForTimeout an anti-pattern, and what do you use instead?

A fixed sleep guesses. On a loaded CI runner it is too short and the test flakes; everywhere else it is dead time multiplied by every test. Replace it with a condition: a web-first assertion such as await expect(locator).toBeVisible(), toHaveText, toHaveURL, or page.waitForResponse() when you are genuinely waiting on a specific call. Playwright's docs mark waitForTimeout as for debugging only.

Intermediate What is a web-first assertion, and how does it differ from expect(await locator.isVisible())?

await expect(locator).toBeVisible() polls the page until the condition holds or the expect timeout expires. expect(await locator.isVisible()).toBe(true) takes a single snapshot at one instant, so it fails whenever the app has not finished rendering yet. The auto-retrying form is what removes most timing flake from a suite.

Intermediate Explain fixtures in Playwright. Why not just use beforeEach?

Fixtures are dependency-injected, per-test (or per-worker) resources declared in the test signature — page, context, request are built in, and test.extend adds your own such as page objects or seeded data. They are lazy (only constructed if a test requests them), composable, scoped, and they tear down automatically. beforeEach runs unconditionally for every test in scope and communicates through shared variables, which does not compose.

Intermediate How do you mock an API response in a Playwright test, and when should you not?

await page.route('**/api/orders', route => route.fulfill({ json: [...] })); route.abort() simulates failure and route.continue() forwards a modified request. Use it for error states, empty states, third-party services and analytics noise. Do not stub the whole backend on your primary journey — at that point the test no longer proves integration and you are paying browser prices for a component test.

Intermediate How do you avoid logging in through the UI in every test?

Run a setup project that logs in once and saves cookies plus local storage with page.context().storageState({ path: '.auth/user.json' }), then set use: { storageState: '.auth/user.json' } so every test starts authenticated. One state file per role for multi-role suites. Keep the files out of version control — they contain live session tokens.

Intermediate A test fails only on CI and passes locally. How do you investigate?

Turn on tracing (trace: 'on-first-retry'), publish trace.zip as a CI artifact, and open it with npx playwright show-trace. The trace gives before/after DOM snapshots per action, the network log, console output and the resolved locator, so you see the actual page state at the failing step. Common culprits it exposes: a slower machine changing ordering, missing seed data, a different viewport, or a third-party request that only fails in CI.

Pro How does Playwright achieve test isolation, and what does that mean for parallelism?

Each test gets a fresh BrowserContext — an independent cookie jar, storage and cache — created and destroyed by the page fixture, so no state leaks between tests. Because tests are independent by construction, the runner can shard test files across worker processes safely (fullyParallel, workers, --shard for multi-machine CI). Contexts are cheap compared with launching a browser, which is why this is fast rather than merely correct.

Pro Your e2e suite is slow and intermittently red. What do you actually change?

Cut the suite to genuine critical journeys and push the rest down to component and unit tests. Reuse auth via storageState instead of UI logins. Stub third-party and analytics traffic. Turn on parallel workers and shard across CI machines. Replace every fixed sleep with a web-first assertion, and every CSS/XPath selector with a role- or test-id-based locator. Enable retries with tracing so flakes are diagnosable — but treat each "flaky" result in the report as a defect to fix, not a pass.

Pro Playwright versus Cypress — give a balanced comparison.

Cypress executes inside the browser next to your app: great interactive runner and easy app-internal access, but historically limited to one origin and tab per test, no WebKit engine, and a chained non-promise command API. Playwright drives browsers out of process from Node, giving real cross-browser coverage (Chromium, Firefox, WebKit), multi-tab and multi-origin flows, iframes, downloads, native async/await, built-in tracing and parallelism. Recommendation: Playwright for new suites and anything cross-browser; keep an existing well-maintained Cypress suite rather than rewriting for its own sake.

Pro Is Playwright component testing a replacement for TestBed in an Angular project?

No. Playwright's component mode is experimental and mounts a single component in a real browser — valuable when a jsdom-style environment misrepresents layout, focus or native browser behaviour, but it is not an end-to-end test and it is not the cheap default. In Angular the component layer stays with TestBed plus Vitest and CDK harnesses; Playwright earns its cost at the whole-application, real-routing, real-journey level.
