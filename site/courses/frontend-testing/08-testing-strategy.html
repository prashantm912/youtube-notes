Module: Test Strategy and CI

Every technique in the previous seven modules is worthless if the suite is slow, flaky or ignored. This closing module is about the difference between a suite people trust and one they learn to skip.

Knowledge Library → Courses → Frontend Testing → Test Strategy and CI

What this module covers

A test suite is a product with its own users — the developers who run it. This module pulls the track together around the two things that decide whether they keep using it: determinism (mocking the network in one place with MSW, building test data instead of copy-pasting it, and hunting flake by cause) and the pipeline (coverage targets that mean something, GitHub Actions wiring for Vitest and Playwright, headless browsers, sharding across machines, artifacts you can debug from, and which suite runs at which gate).

Stack assumed throughout: Angular v20+ with Vitest as the unit runner, Playwright for end-to-end, and GitHub Actions as the CI host. The principles port to any runner; the commands do not.

Topics

Mock Service Worker: one set of handlers for every layer

MSW intercepts requests at the network layer rather than patching your code. In the browser it registers a Service Worker that answers matching requests; in Node it swaps the request interceptors under fetch/XMLHttpRequest. The consequence is the whole point: the same http.get('/api/orders', …) handler file serves your Vitest component tests, your Playwright end-to-end run, and ng serve while the backend team is still building the endpoint. One definition of "what the API returns", not three that drift apart.

Why it matters: the usual alternative is a mock stubbed per test file, which means your test asserts against a fiction only that file believes in. Because MSW sits below your application code, nothing in the component or service knows it is being tested — you exercise the real HttpClient, the real interceptors, the real error mapping. It is also the standard answer to "how do you develop a feature when the API does not exist yet?", a question that comes up constantly in service-company interviews where teams are split across vendors.

// src/mocks/handlers.ts — shared by unit tests, e2e and the dev server
import { http, HttpResponse } from 'msw';

export const handlers = [
  http.get('/api/orders', () => HttpResponse.json([{ id: 1, total: 250 }])),
  http.post('/api/orders', async ({ request }) => {
    const body = await request.json();
    return HttpResponse.json({ id: 2, ...body }, { status: 201 });
  }),
];

Three places to fake a response: MSW, HttpTestingController, page.route

These are not competitors so much as three different altitudes, and choosing the wrong one is a common design mistake. HttpTestingController (from provideHttpClientTesting) works at the framework level: it replaces Angular's HTTP backend, so it can assert that exactly one request was issued to a URL with given headers, then flush a response synchronously. That precision is exactly right for testing a service or an interceptor — and useless for anything that bypasses HttpClient. Playwright's page.route works at the browser level: it intercepts real network traffic in a real page, including requests from third-party scripts and images, which is what you want when stubbing a payment gateway or blocking analytics to speed a run up. MSW sits in the middle, at the application network layer, and is the only one of the three whose handlers can be reused across all your suites and your dev server.

A practical rule: use HttpTestingController when the request itself is the thing under test; use MSW when the request is background scenery for a component or page test; use page.route when you need to control traffic the application does not own. Interviewers like this question because a candidate who reaches for one tool everywhere has not thought about layers.

Test data builders instead of copy-pasted fixture literals

The commonest rot in a mature suite is the fixture literal: a fully-populated const user = { … } pasted into forty test files. When the model gains a required field, forty files break; worse, a reader cannot tell which of the twenty properties actually matters to the assertion below it. A builder (or Object Mother, Martin Fowler's older name for a factory of well-known example objects) fixes both: it supplies sane defaults centrally and lets each test override only the one field it cares about — so the test reads as "an order that is already cancelled" rather than as a wall of JSON.

Apply the same discipline to MSW handlers. Keep a default happy-path handler set, then override per test with server.use(…) for the error and empty cases, and reset between tests so no override leaks. Builders and handler overrides together are what let a test state its scenario in one line, and that readability is what makes people willing to maintain the suite.

export const anOrder = (over: Partial<Order> = {}): Order => ({
  id: 1, status: 'PLACED', total: 250, items: [anItem()], ...over,
});

// the test states only what differs — the rest is noise it does not own
it('hides the cancel button once cancelled', () => {
  render(anOrder({ status: 'CANCELLED' }));
});

The flake taxonomy: six causes and their fixes

A flaky test is one that passes and fails against unchanged code. It is worse than a missing test, because it teaches the team to re-run the build instead of reading the failure — and once that habit forms, real regressions get re-run away too. Flake is not mysterious; it comes from a short list of non-determinism sources, and each has a mechanical fix. Time: freeze the clock (vi.useFakeTimers in Vitest, page.clock in Playwright) so "expires tomorrow" does not depend on the day the build runs. Randomness: seed it, or inject the generator, so a shuffled array or a random id is reproducible. Network: stub it — a test that talks to a staging API inherits that API's uptime. Animation: disable transitions in the test environment, or the assertion races the fade-in.

The two subtler causes: test-order coupling, where test B only passes because test A left state behind — reset stores, local storage and MSW handlers in a global afterEach, and prove independence by randomising execution order rather than by hoping. And race conditions, the biggest source of e2e flake: never assert after a fixed sleep, assert on a condition. Playwright's web-first assertions retry until the expectation holds or the timeout expires, which is exactly the sleep-free pattern you want. Retries in CI are a diagnostic, not a cure: mark the test, look at the trace, fix the cause. Quarantining a flaky test is acceptable; leaving it retried and green forever is not.

Coverage: a useful signal, a terrible target

Line and branch coverage measure exactly one thing — which lines executed while the tests ran. They say nothing about whether an assertion checked the result. A test that renders a component and asserts nothing produces the same coverage as one that verifies every output, which is why a coverage target reliably produces tests written to move the number. Chasing 100% is the extreme case: the last stretch is defensive branches, framework glue and untestable error paths, and the tests you write to reach it are exactly the brittle ones that will break on your next refactor.

What works in practice: treat coverage as a leak detector, not a grade. Set a floor rather than a goal — somewhere around 70 to 80 percent for a typical Angular app is honest — and enforce it with a ratchet so it can never drop. Then apply the stricter rule where it actually pays: require high coverage on changed lines in a pull request, which catches the new untested code without demanding an archaeology project on legacy files. Vitest exposes v8 and istanbul providers with per-metric thresholds; Angular's CLI wires the same reporters through ng test --coverage. If you want a stronger signal than coverage, that is what mutation testing is for.

Wiring the suites into GitHub Actions

A CI job is just your local commands run on a clean machine, so most CI pain is really environment pain. Unit tests are easy: check out, set up Node with a dependency cache, npm ci, then ng test (Vitest) in a non-watch, headless run. End-to-end is where teams get stuck — Playwright needs actual browser binaries plus their OS libraries, so a bare Ubuntu runner fails until you run npx playwright install --with-deps, or skip the problem entirely by running the job inside Microsoft's official mcr.microsoft.com/playwright container image, which ships the browsers and dependencies preinstalled and pinned to your Playwright version.

The other half is evidence. A red e2e job with only a stack trace is nearly undebuggable; a red job with the HTML report, the failure screenshots and a Playwright trace is a two-minute fix. Configure traces and video on first retry, then upload playwright-report and test-results as workflow artifacts with if: always() so they survive a failing step. Add webServer to the Playwright config so CI starts and waits for your app itself, instead of a hand-rolled sleep-and-hope script.

- run: npx playwright install --with-deps
- run: npx playwright test
- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: playwright-report
    path: playwright-report/
    retention-days: 7

Parallelism, sharding, and where each suite belongs in the pipeline

Two different knobs get confused constantly. Workers parallelise within one machine: Playwright runs test files in parallel worker processes (Vitest does the same with its thread pool), so a four-core runner does roughly four files at once. Tests inside a single file run serially unless you opt in with test.describe.configure({ mode: 'parallel' }). Sharding parallelises across machines: npx playwright test --shard=2/4 runs one deterministic quarter of the suite, so a CI matrix of four jobs quarters the wall-clock time. Vitest offers the same --shard flag. Afterwards you merge the per-shard blob reports into one HTML report, otherwise you get four partial reports and no overall picture.

Then the strategy question interviewers actually care about: not every suite belongs at every gate. Unit and component tests are fast and deterministic, so they run on every push and every pull request — that is your fast feedback loop and it should stay under a few minutes. The full end-to-end suite is slow and comparatively fragile, so run a smoke subset (tagged @smoke, the critical login-to-checkout paths) on pull requests, and the complete matrix on merge to main and on a nightly cron. Anything expensive — cross-browser, visual regression, mobile viewports — goes nightly. The governing principle is the continuous-integration one: keep the commit gate fast enough that nobody is tempted to bypass it, and put everything else where a slow answer is still a useful answer.

strategy:
  fail-fast: false
  matrix:
    shard: [1, 2, 3, 4]
steps:
  - run: npx playwright test --shard=${{ matrix.shard }}/4

Interview questions

Strategy questions dominate the senior rounds at Indian product and service companies — panels want to hear judgement about pipelines and flake, not just API recall:

Beginner What is MSW and why use it instead of mocking your service?

Mock Service Worker intercepts requests at the network layer — a Service Worker in the browser, request interceptors in Node — so your application code runs unchanged and unaware. Mocking your own service replaces the code under test; MSW leaves HttpClient, interceptors and error mapping in the picture, and the same handlers work in unit tests, end-to-end runs and the dev server.

Beginner What makes a test flaky, and why is a flaky test worse than no test?

Flaky means it passes and fails against unchanged code — from time, randomness, network, animation, leftover state or races. It is worse than no test because it trains the team to re-run the build instead of reading failures, so genuine regressions get re-run away too. Trust in the suite is the asset you are protecting.

Beginner What does line coverage actually measure?

Which lines executed while the tests ran — nothing more. It cannot tell whether anything was asserted, so a test that renders a component and asserts nothing scores identically to one that verifies every output. Useful for finding untested code; useless as a measure of test quality.

Beginner Why do Playwright tests fail on a fresh CI runner but pass locally?

Almost always missing browser binaries or their OS libraries. Fix with npx playwright install --with-deps in the workflow, or run the job inside the official mcr.microsoft.com/playwright image which ships browsers and dependencies preinstalled. Second-most-common cause: no server running, solved by the webServer config block.

Intermediate MSW, HttpTestingController and page.route — when do you use each?

Three altitudes. HttpTestingController is framework level: it replaces Angular's HTTP backend and lets you assert the exact request and flush a reply — right when the request itself is under test, such as a service or interceptor. MSW is application-network level: use it when HTTP is background scenery for a component or page test, and reuse the handlers everywhere. page.route is browser level: use it for traffic your app does not own — third-party scripts, payment gateways, analytics you want blocked.

Intermediate What is a test data builder and what problem does it solve?

A factory returning a valid default object with per-test overrides — Fowler's Object Mother pattern. It removes copy-pasted fixture literals, so a new required field is one edit instead of forty, and it makes intent readable: anOrder({ status: 'CANCELLED' }) states the scenario, while a twenty-property literal hides which property the assertion depends on.

Intermediate Difference between parallelism and sharding, and when do you need each?

Parallelism is within a machine: worker processes run test files concurrently, sized to available cores. Sharding is across machines: --shard=2/4 gives each CI job a deterministic slice of the suite, so four jobs quarter the wall clock. Use workers first because they are free; add sharding when a single runner is saturated and the suite is still too slow. With sharding you must merge the per-shard reports afterwards.

Intermediate Our e2e suite takes forty minutes and blocks every pull request. What do you change?

Split by gate, not by shrinking coverage. Fast unit and component tests on every push; a tagged smoke subset of critical journeys on pull requests; the full suite on merge to main plus a nightly cron; cross-browser, visual and mobile-viewport runs nightly only. In parallel, shard the full run across a CI matrix and check for tests that are slow because they sleep rather than because they do work.

Intermediate Why is an explicit wait or sleep an anti-pattern in end-to-end tests?

A fixed sleep is a bet on machine speed: too short and it flakes on a loaded CI runner, too long and it wastes time on every run forever. Assert on a condition instead — Playwright's web-first assertions and locators retry until the expectation holds or the timeout expires, which is both faster on a fast machine and stable on a slow one.

Intermediate How do you make a test that depends on the current date deterministic?

Freeze the clock rather than computing around it: vi.useFakeTimers() with vi.setSystemTime(...) in Vitest, page.clock in Playwright, and restore in teardown. The same discipline applies to randomness — seed the generator or inject it — and to time zones, which should be pinned in the test environment so a build behaves the same in Bengaluru and on a UTC runner.

Pro Management wants a 100% coverage gate. What do you argue?

That it optimises the wrong number. Coverage records execution, not verification, so a hard gate produces assertion-free tests written to satisfy it, and the final stretch is defensive branches and framework glue whose tests are the most brittle in the suite. Counter-proposal: a floor around 70 to 80 percent with a ratchet so it cannot fall, a stricter threshold on changed lines in each pull request, and mutation testing on the genuinely critical modules if a real quality signal is wanted.

Pro A test passes alone but fails in the full run. How do you diagnose it?

That is test-order coupling: shared state surviving between tests. Bisect by running subsets to find the polluting predecessor, then look for the usual carriers — module-level singletons, a store never reset, local or session storage, an MSW server.use override not reset, a stubbed global left patched. Fix by resetting in a global teardown, then defend the fix by randomising execution order so the coupling cannot come back silently.

Pro Is turning on CI retries a fix for flaky tests?

No — it is instrumentation. Retries stop one bad test blocking a release, but a retried-and-passed test is a bug report you have chosen not to read, and the underlying non-determinism will eventually hide a real regression. Use retries to keep the pipeline moving while tracking every flaky-pass in a dashboard, quarantine repeat offenders out of the blocking suite with an owner and a deadline, and fix the cause using the trace from the failed attempt.

Pro You are joining a team whose suite everyone skips. What is your first month?

Measure before changing: which tests fail intermittently, what the commit build costs in minutes, where coverage is genuinely absent. Then attack trust first — quarantine or fix the flakiest handful, because a red-by-default pipeline makes every other improvement invisible. Next attack speed: shard the slow suite, move the expensive runs to nightly, and get the pull-request gate under a few minutes. Only then add coverage, and add it as changed-lines enforcement on new code rather than a retrospective campaign on legacy files.
