Module: Service and HTTP Testing

Services are the cheapest thing in Angular to test well — most are plain classes that a constructor call and one fake dependency will cover. The ones that reach the network get a first-party mock transport instead of a real server.

Knowledge Library → Courses → Frontend Testing → Service and HTTP Testing

What this module covers

Two halves. First, testing a service as an ordinary unit: instantiating it directly, reaching for TestBed only when injection actually earns its cost, overriding providers with useValue / useClass / injection-token stubs, and choosing the right kind of test double. Second, testing everything that talks HTTP: provideHttpClientTesting(), HttpTestingController, the expect/flush/verify rhythm, error simulation, and functional interceptors end to end. Examples assume Angular v20 or newer with Vitest as the runner.

Topics

Services in isolation — start with plain instantiation

An Angular service is a TypeScript class. If its dependencies arrive through the constructor, the simplest possible test is new CartService(fakePricing) — no TestBed, no configureTestingModule, no change detection, no async plumbing. The test runs in microseconds, the failure message points straight at your logic, and nothing about the framework can break it. The official guide opens on exactly this note: services are often the easiest files to unit test, and the plainest approach is usually the right one.

Why it matters: TestBed compiles a miniature Angular application for every test. Paying that price for a class that only maps some data is how suites quietly become slow. Reach for the framework when the code under test genuinely needs the injector — hierarchical providers, inject() in field initialisers, tokens resolved at runtime — and not before. In an interview, "when do you not need TestBed?" separates people who understand the tool from people who memorised the boilerplate.

// cart.service.ts — an ordinary class with an injected collaborator
export class CartService {
  constructor(private pricing: PricingService) {}
  total(items: Item[]) { return this.pricing.apply(items); }
}

// cart.service.spec.ts — no TestBed anywhere
const pricing = { apply: vi.fn().mockReturnValue(250) } as unknown as PricingService;
expect(new CartService(pricing).total([])).toBe(250);

When TestBed earns its keep — TestBed.inject and provider overrides

Once a service uses inject() internally, depends on an InjectionToken, or is provided somewhere other than the root, you need a real injector. TestBed.configureTestingModule({ providers: [...] }) builds one, and TestBed.inject(CartService) pulls the instance out — the modern replacement for the old TestBed.get. Everything the service asks for must be present in that provider array, so the array itself becomes an honest, readable declaration of the unit's dependencies.

Overriding is the whole point. { provide: PricingService, useValue: fake } swaps a collaborator for an object you control; useClass: FakePricingService swaps in a whole substitute implementation when the fake needs behaviour rather than canned values; useFactory builds one lazily. Injection tokens get stubbed the same way — { provide: API_BASE_URL, useValue: 'https://test.local' } — which is how you keep environment configuration out of your assertions. TestBed.overrideProvider exists for the case where the module is already configured and you want to replace one entry before the first injection.

TestBed.configureTestingModule({
  providers: [
    CartService,
    { provide: PricingService, useValue: fakePricing },        // canned collaborator
    { provide: TaxService,     useClass: FakeTaxService },     // substitute implementation
    { provide: API_BASE_URL,   useValue: 'https://test.local' } // stubbed token
  ]
});
const service = TestBed.inject(CartService);

Test doubles: stub, spy, fake, mock — and where the boundary sits

The words are used loosely in standups and precisely in interviews. A stub returns canned answers and asserts nothing. A spy is a stub that also records how it was called, so the test can assert on interactions — in Vitest that is vi.fn(), and in the older Jasmine world jasmine.createSpyObj. A fake is a working but simplified implementation, such as an in-memory repository. A mock is pre-programmed with expectations and fails the test itself when they are not met. Martin Fowler's original essay draws the line that matters: stubs support state verification, mocks perform behaviour verification.

The rule that keeps suites maintainable is mock at the boundary, not in the middle. Replace the things you do not own or cannot control — the network, the clock, storage, third-party SDKs — and let your own collaborating classes run for real. Faking every internal service produces tests that pass while the application is broken, because each double encodes an assumption nobody re-checked. This is also the reason component tests generally fake HTTP rather than faking the data service: the double sits at the edge of the system, so refactoring the service does not break twenty specs.

HTTP testing: provideHttpClientTesting, expectOne and flush

Angular ships a mock backend. Put provideHttpClient() and provideHttpClientTesting() in the testing module — in that order — and the real XHR/fetch transport is replaced by one that queues requests instead of sending them. Note that HttpClientTestingModule is the deprecated older form of the same thing; new code uses the two provider functions, which is also what lets you test standalone, provider-based applications without inventing an NgModule.

The rhythm is always the same: call the service, assert which request it made, then hand it a response. httpMock.expectOne('/api/orders/7') asserts that exactly one matching request is outstanding and returns it; the argument can be a URL string, a { method, url } object, or a predicate function for anything more interesting (query parameters, headers, body shape). req.request exposes method, headers, params and body for assertions. req.flush(body) then delivers the response, at which point the subscriber callback runs synchronously — which is why a service test rarely needs fakeAsync. Sibling helpers match() (many requests) and expectNone() (assert nothing was sent, useful for cache-hit paths) round the API out.

TestBed.configureTestingModule({
  providers: [provideHttpClient(), provideHttpClientTesting()]
});
const service  = TestBed.inject(OrderService);
const httpMock = TestBed.inject(HttpTestingController);

let received: Order | undefined;
service.load(7).subscribe(o => received = o);

const req = httpMock.expectOne('/api/orders/7');
expect(req.request.method).toBe('GET');
req.flush({ id: 7, status: 'PAID' });   // subscriber runs now
expect(received?.id).toBe(7);

Failure paths, verify(), and testing functional interceptors

Half of a service's job is what it does when the call fails, and the mock backend can produce both kinds of failure. An HTTP error response comes from the same flush method with a status: req.flush('Not found', { status: 404, statusText: 'Not Found' }), which drives your retry, mapping and error-handling code down the error path. A transport-level failure — DNS, offline, connection reset — is req.error(new ProgressEvent('network error')). Getting a candidate to name both, and to explain that they surface differently to an HttpErrorResponse handler, is a common senior-round probe.

Then the safety net: afterEach(() => httpMock.verify()) throws if any request is still outstanding. Without it, a service that fires an unexpected extra call — a duplicate fetch, a stray analytics ping, a request from a leaked subscription — passes silently. Treat it as mandatory, exactly like closing a resource. Interceptors are tested through the same machinery rather than by calling them directly: register the functional interceptor with provideHttpClient(withInterceptors([authInterceptor])), make a request through HttpClient, and assert on the request the controller captured — headers added, URL rewritten, retries performed. Test one interceptor per spec so a failure names its own culprit.

// error paths
req.flush('Not found', { status: 404, statusText: 'Not Found' }); // HTTP error response
req.error(new ProgressEvent('network error'));                    // transport failure

// interceptor under test, wired through the real HttpClient pipeline
TestBed.configureTestingModule({
  providers: [
    provideHttpClient(withInterceptors([authInterceptor])),
    provideHttpClientTesting()
  ]
});
httpClient.get('/api/me').subscribe();
const req2 = httpMock.expectOne(r => r.headers.has('Authorization'));
expect(req2.request.headers.get('Authorization')).toBe('Bearer test-token');

afterEach(() => httpMock.verify()); // nothing unexpected was sent

Interview questions

Service and HTTP testing is the part of the Angular testing round that Indian product and services companies probe hardest — it is where candidates either recite boilerplate or show judgement:

Beginner Do you always need TestBed to test an Angular service?

No. If the dependencies come in through the constructor, new MyService(fakeDep) is a complete, valid unit test — faster and simpler. TestBed is required when the class uses inject() internally, depends on injection tokens, or relies on the injector hierarchy. Preferring plain instantiation where possible is a signal of maturity, not a shortcut.

Beginner How do you obtain a service instance from TestBed?

TestBed.inject(MyService) after TestBed.configureTestingModule({ providers: [...] }). It is the type-safe replacement for the deprecated TestBed.get. Everything the service depends on must appear in the providers array.

Beginner What does provideHttpClientTesting() actually do?

It replaces HttpClient's real backend (the XHR/fetch transport) with a mock backend that queues requests instead of sending them, and it provides HttpTestingController so the test can inspect those requests and supply responses. No server, no network, and the whole flow stays synchronous.

Beginner HttpClientTestingModule or provideHttpClientTesting — which do you use now?

provideHttpClient() plus provideHttpClientTesting() in the providers array. HttpClientTestingModule is the deprecated NgModule form of the same feature, kept for older codebases; the provider functions are what standalone, module-free Angular applications use and are required if you want functional interceptors registered via withInterceptors.

Beginner How do you assert that a service issued a GET to a particular URL?

Call the service method and subscribe, then const req = httpMock.expectOne('/api/orders/7') and assert req.request.method equals 'GET'. expectOne fails if there is no match or more than one. Finish by calling req.flush(...) so the subscriber actually receives data.

Intermediate expectOne vs match vs expectNone?

expectOne asserts exactly one outstanding matching request and returns it. match returns an array of all matching requests, for cases like parallel fetches where you need to flush several. expectNone asserts that no matching request was made — the way you prove a cache hit, a debounce, or a guard actually prevented a call. All three accept a URL string, a method/URL object, or a predicate.

Intermediate How do you simulate a server error, and how is that different from a network failure?

Server error: req.flush(body, { status: 500, statusText: 'Server Error' }) — the backend responded, so the subscriber receives an HttpErrorResponse carrying that status and body. Network failure: req.error(new ProgressEvent('network error')) — no response at all, so the error has status 0 and an error property holding the event. Retry and offline logic behave differently on the two, which is exactly why interviewers ask.

Intermediate Why call httpMock.verify() in afterEach?

It throws if any request is still outstanding when the test ends, catching calls you never expected — a duplicate fetch, a leaked subscription firing again, an analytics ping. Without it those tests pass while the service quietly misbehaves. Treat it as the HTTP equivalent of asserting no resource was left open.

Intermediate Explain stub, spy, fake and mock.

Stub — returns canned values, no assertions. Spy — a stub that also records calls so you can verify interactions (vi.fn(), or jasmine.createSpyObj in older suites). Fake — a real but simplified working implementation, such as an in-memory store. Mock — pre-programmed with expectations that it verifies itself. Fowler's shorthand: stubs enable state verification, mocks do behaviour verification.

Intermediate useValue vs useClass vs useFactory when overriding a provider in a test?

useValue supplies a ready-made object — the usual choice for a literal fake or a stubbed configuration token. useClass supplies a substitute class that Angular instantiates, right when the double needs real behaviour or its own dependencies. useFactory builds the value lazily from a function, useful when construction depends on other injected values. TestBed.overrideProvider replaces an entry in an already-configured module before first injection.

Intermediate How do you test a functional HTTP interceptor?

Register it in the testing module with provideHttpClient(withInterceptors([myInterceptor])) alongside provideHttpClientTesting(), then make a normal HttpClient call and assert on the request the controller captured — added headers, rewritten URL, retry count — or on the response the interceptor transformed. Test one interceptor per spec so a failure names its own cause; calling the interceptor function directly is possible but skips the pipeline you actually ship.

Pro Your service uses inject() in a field initialiser and the test throws about running outside an injection context. Why?

inject() is only legal while Angular is constructing the class inside an injection context. Calling new MyService() yourself has no such context, so it fails. Fix by obtaining the instance from TestBed.inject(MyService), or by wrapping the construction in TestBed.runInInjectionContext(() => new MyService()). This is the most common reason a previously TestBed-free spec suddenly needs TestBed after a refactor to inject().

Pro A service spec passes alone but fails inside the full suite. How do you diagnose it?

Shared mutable state across tests. Usual suspects: a root-provided singleton carrying data between specs, a spy configured in one file and not reset, a subscription never torn down, module-level test data mutated in place, or a missing httpMock.verify() letting a stray request leak into the next test. Practical steps: run the suite in a fixed order to reproduce, build fixtures inside beforeEach rather than at module scope, enable spy restoration between tests, and make sure every spec configures its own TestBed rather than relying on one built elsewhere.

Pro When would you not use HttpTestingController and reach for MSW instead?

HttpTestingController intercepts inside Angular's HttpClient, so it is ideal for unit and component tests but cannot see traffic from fetch, a third-party SDK, or a real browser session. Mock Service Worker intercepts at the network layer, so the same handlers serve unit tests, component tests, end-to-end runs and local development from one definition of the API. Rule of thumb: controller for focused service and component specs, MSW when you want one shared contract across the whole suite and the dev server.
