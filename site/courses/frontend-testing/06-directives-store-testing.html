Module: Directives, Router and Store Testing

Everything in an Angular app that is neither a component nor a service still has to be proven: the one-method pipe, the directive with no template of its own, the guard that only exists inside an injection context, and the store that turns user intent into state.

Knowledge Library → Courses → Frontend Testing → Directives, Router and Store Testing

What this module covers

Components and services are the easy half of an Angular suite. This module handles the rest: pipes (often testable with plain new and a method call), attribute and structural directives (which need a host component to attach to), functional guards and resolvers (which must run inside an injection context), routed navigation with provideRouter and RouterTestingHarness, and the whole NgRx surface — reducers, selectors, mock stores and effects with marble diagrams.

The stack assumed throughout is Angular v20+ with the Vitest runner, standalone APIs and functional guards. Depth for every topic lives in the linked official documentation and the community writing beside it.

Topics

Testing pipes — usually just a class and a method

A pipe is a class with one public method, transform. For a pure pipe with no injected dependencies that means the whole test is arithmetic: construct the pipe with new, call transform with an input, assert on the output. No TestBed, no fixture, no change detection — and consequently no reason for the test to be slow or flaky. Angular's own guide leads with exactly this technique, and edge-case coverage (null, undefined, empty string, boundary values, extra arguments) is where the real value sits.

The exceptions matter for interviews. A pipe that injects something (a LOCALE_ID, a translation service, an HttpClient) needs either constructor-injected fakes or a TestBed so DI can resolve it. An impure pipe (pure: false) re-runs on every change-detection cycle, so its behaviour only shows up when rendered in a host template. And async pipes over observables need fakeAsync/tick or a fixture whose change detection you drive. Knowing which of the three cases you are in is the whole skill.

describe('TruncatePipe', () => {
  const pipe = new TruncatePipe();          // no TestBed needed

  it('shortens long text', () => {
    expect(pipe.transform('abcdefghij', 4)).toBe('abcd…');
  });

  it('leaves short text alone', () => {
    expect(pipe.transform('abc', 4)).toBe('abc');
  });
});

Directives need a host component to attach to

A directive has no template of its own — it only exists once applied to an element. So the standard pattern is a small test host component declared inside the spec that renders every way the directive can be used (bound input, no input, applied to different element types), then assertions against the resulting DOM via fixture.debugElement.queryAll(By.directive(MyDirective)) or By.css. Testing the directive class in isolation is possible for trivial cases, but the host approach is what Angular's guide recommends because it exercises the binding and host-listener plumbing you actually shipped.

Structural directives (the * ones) add and remove DOM through TemplateRef and ViewContainerRef, so their tests read as "set the input, run change detection, count the rendered nodes". Attribute directives that react to events use @HostListener, so you dispatch a real event (or call triggerEventHandler) and assert the host element's changed class, style or attribute. Interviewers like this topic precisely because a candidate who has never written a host component gets stuck immediately.

@Component({
  standalone: true, imports: [HighlightDirective],
  template: `<p appHighlight="yellow">host element</p>`,
})
class HostComponent {}

const el = fixture.debugElement.query(By.directive(HighlightDirective));
el.triggerEventHandler('mouseenter');
fixture.detectChanges();
expect(el.nativeElement.style.backgroundColor).toBe('yellow');

Functional guards and resolvers: run them in an injection context

Since Angular 15 the idiomatic guard is a plain function — const authGuard: CanActivateFn = (route, state) => inject(AuthService).isLoggedIn() — and the same is true of ResolveFn, CanDeactivateFn and CanMatchFn. That function calls inject(), which only works inside an injection context. Calling it directly from a spec throws NG0203. The fix is one line: configure a TestBed with the providers (real or faked) and invoke the guard through TestBed.runInInjectionContext(() => authGuard(route, state)).

From there it is ordinary unit testing: build an ActivatedRouteSnapshot-shaped object and a RouterStateSnapshot-shaped object (usually a cast literal with only the fields the guard reads), swap the collaborator for a fake, and assert the return — true, false, or a UrlTree for a redirect. Async guards return a promise or observable, so unwrap accordingly. Resolvers are identical in shape; assert on the resolved value and on the service call arguments taken from route params.

TestBed.configureTestingModule({
  providers: [{ provide: AuthService, useValue: { isLoggedIn: () => false } }],
});

const result = TestBed.runInInjectionContext(() =>
  authGuard({} as ActivatedRouteSnapshot, { url: '/admin' } as RouterStateSnapshot));

expect(result).toEqual(new Router().parseUrl('/login')); // redirect UrlTree

Router testing with provideRouter and RouterTestingHarness

The old habit was to stub the Router and assert that navigate was called — a test that passes even when the route configuration is wrong. The modern approach uses the real router over a fake location: provide provideRouter(testRoutes) plus provideLocationMocks() in the testing module, then drive navigation through RouterTestingHarness. harness.navigateByUrl('/heroes/5', HeroComponent) navigates, waits for the navigation to settle, activates the outlet and hands you back the typed component instance — the boilerplate of a wrapper host component disappears.

This is the sharpest tool for testing guards and resolvers in situ: point a test route at a component, attach the guard, navigate, and assert either that the component activated or that harness.routeDebugElement is null and the URL is the redirect target. Resolver output arrives through ActivatedRoute.data, so a resolved-data assertion is a genuine integration test of route config plus resolver plus component. Named outlets and a few exotic cases still want a hand-written host component; the harness docs say so explicitly.

TestBed.configureTestingModule({
  providers: [
    provideRouter([{ path: 'admin', component: AdminComponent, canActivate: [authGuard] }]),
    provideLocationMocks(),
  ],
});

const harness = await RouterTestingHarness.create();
await harness.navigateByUrl('/admin');
expect(harness.routeDebugElement).toBeNull();          // guard blocked activation
expect(TestBed.inject(Router).url).toBe('/login');

NgRx reducers and selectors: pure functions, plain tests

A reducer is (state, action) => newState with no dependencies, so its test needs no framework at all: build a known state, call the reducer with an action creator's result, assert the returned state. Because NgRx state is immutable, also assert that the input object was not mutated — a returned-the-same-reference bug is a classic. Cover the "unknown action returns the current state" case too; it is the reducer's contract and a favourite interview follow-up.

Selectors split into two kinds. A feature/property selector that just reaches into the state tree is thin enough that many teams skip testing it and let TypeScript do the work. A composed selector with real derivation logic is worth testing through its projector: selectVisibleTodos.projector(todos, filter) calls only the final transformation with inputs you supply, so you never have to build the entire state tree. Where you do want the tree, selector.projector's counterpart is calling the selector with a state object directly.

it('adds a todo', () => {
  const state = { items: [] as Todo[] };
  const next = todosReducer(state, TodoActions.added({ title: 'write tests' }));
  expect(next.items.length).toBe(1);
  expect(state.items.length).toBe(0);             // original untouched
});

// composed selector: test the projector, not the whole state tree
expect(selectVisibleTodos.projector(allTodos, 'done')).toEqual([doneTodo]);

provideMockStore and overrideSelector in component tests

A component that talks to the store should not drag the whole state machine into its spec. provideMockStore({ initialState }) from @ngrx/store/testing swaps in a fake store whose state you set directly and whose dispatch is a spy — so a component test becomes "given this slice of state, does the template render it, and does clicking this button dispatch that action?". Assert dispatches with expect(store.dispatch).toHaveBeenCalledWith(SomeActions.loaded({ id })).

For selector-driven components, store.overrideSelector(selectUser, fakeUser) pins a selector's emission regardless of state. Two gotchas that come up constantly: overrides do not re-emit by themselves, so after changing one you call store.refreshState() and then fixture.detectChanges(); and mock selectors leak between specs, so store.resetSelectors() belongs in afterEach. Tim Deschryver's write-up is the reference text on where mocking the store helps and where it quietly removes the coverage you thought you had.

TestBed.configureTestingModule({
  providers: [provideMockStore({ initialState: { user: null } })],
});
const store = TestBed.inject(MockStore);

store.overrideSelector(selectUser, { name: 'Asha' });
store.refreshState();
fixture.detectChanges();
expect(el.textContent).toContain('Asha');

afterEach(() => store.resetSelectors());

Effects: provideMockActions and marble diagrams

An effect listens to an action stream, does something impure, and emits another action. Tests therefore need a controllable actions stream: provideMockActions(() => actions$) supplies one, and the effect's dependencies are faked as usual. Push an action in, assert the action that comes out. Many teams (Tim Deschryver among them) push a plain observable of one action and subscribe to the effect, which keeps the test readable and focused on the flow rather than on timing.

Timing is where marble tests earn their place: debounced search, retries, switchMap cancellation, concatMap ordering. RxJS's TestScheduler with run() gives you virtual time — cold('-a|') and hot('-a') build input streams, expectObservable(effect$).toBe('-b') asserts the output, and one frame of virtual time stands for whatever the operator asked for. The syntax is the barrier, not the concept: - is a frame, a letter is an emission, | completes, # errors, and () groups emissions into the same frame. Learn to read a diagram before you try to write one.

const scheduler = new TestScheduler((actual, expected) =>
  expect(actual).toEqual(expected));

scheduler.run(({ hot, cold, expectObservable }) => {
  actions$ = hot('-a', { a: SearchActions.query({ term: 'ng' }) });
  api.search.mockReturnValue(cold('--r|', { r: [hit] }));
  expectObservable(effects.search$).toBe('---s', { s: SearchActions.success({ hits: [hit] }) });
});

Interview questions

Angular testing rounds in Indian product and service companies move quickly from "how do you test a component" to these — pipes and guards in screening, NgRx and marbles for senior roles:

Beginner How do you unit test an Angular pipe?

For a pure pipe with no dependencies, instantiate it directly — const pipe = new MyPipe() — and assert on pipe.transform(input, args). No TestBed, no fixture, no change detection. Cover edge cases: null, undefined, empty values and boundary arguments. Only pipes that inject dependencies or are impure need TestBed or a host component.

Beginner Why can't you test a directive the way you test a component?

A directive has no template of its own — it only takes effect once applied to a host element. So you declare a small test host component inside the spec whose template applies the directive in every supported way, create a fixture for that host, and assert on the resulting DOM through By.directive(...) or By.css(...).

Beginner What is a test host component and why is it used?

A throwaway component declared in the spec file purely to render the thing under test in a realistic template — used for directives, for pipes that must be rendered, for content projection, and for components whose inputs and outputs you want bound through real template syntax rather than set on the instance.

Beginner How do you test a reducer?

Call it as a plain function: const next = reducer(initialState, action), then assert on next. Also assert that the original state object was not mutated, and check the default branch — an unrecognised action must return the current state reference unchanged. No TestBed, no store, no mocks.

Intermediate Your functional guard test throws NG0203 "inject() must be called from an injection context". Why, and how do you fix it?

A functional guard calls inject() in its body, which is only legal inside an injection context. Calling the guard directly from a spec is outside one. Configure a TestBed with the required providers and invoke the guard through TestBed.runInInjectionContext(() => myGuard(route, state)). The same applies to functional resolvers and functional interceptors.

Intermediate What does RouterTestingHarness give you over stubbing the Router?

A stubbed Router only proves that your component called navigate; it cannot catch a wrong route path, a guard that blocks activation or a resolver that fails. The harness runs the real Router over test routes provided by provideRouter plus provideLocationMocks: navigateByUrl performs a real navigation, waits for it to settle, activates the outlet and returns the typed routed component. You test route configuration and component together.

Intermediate How do you test a resolver?

Two levels. Unit: run the ResolveFn through TestBed.runInInjectionContext with a fake data service and a route snapshot carrying the params it reads, then assert the resolved value (unwrapping the observable or promise). Integration: attach it to a test route, navigate with RouterTestingHarness and assert on what the routed component received via ActivatedRoute.data.

Intermediate What is provideMockStore and when do you prefer it to the real store?

provideMockStore({ initialState }) from @ngrx/store/testing supplies a store whose state you set directly and whose dispatch is a spy. Prefer it for component specs — you want to assert "renders this state" and "dispatches that action" without wiring reducers, effects and the full state tree. Prefer the real store when the point of the test is the reducer-plus-selector integration.

Intermediate How do you test an NgRx selector without building the entire state tree?

Use its projector. selectVisibleTodos.projector(todos, filter) invokes only the final projection function with the inputs you pass, skipping the parent selectors and the state shape entirely. Thin property selectors that only read a slice are usually left untested — TypeScript already guards the shape.

Intermediate After overrideSelector, your component still shows the old value. What is missing?

Overriding a mock selector does not push a new emission on its own. Call store.refreshState() to make MockStore re-emit, then fixture.detectChanges() to render it. And because mock selectors persist across specs, call store.resetSelectors() in afterEach or later tests inherit the override.

Pro How do you test an effect, and what does provideMockActions do?

provideMockActions(() => actions$) supplies the Actions stream the effect subscribes to, so the spec controls exactly which actions arrive. Fake the effect's collaborators, push an action into actions$, subscribe to the effect and assert the emitted action — including the failure path, where the service errors and the effect must emit a failure action rather than killing the stream. Many teams skip TestBed here and construct the effects class directly for speed.

Pro Explain marble testing: hot vs cold, and when is it worth the syntax?

TestScheduler.run() gives virtual time, so time-dependent operators resolve instantly and deterministically. A cold observable starts emitting when subscribed (a typical HTTP call); a hot one emits on a shared timeline regardless of subscribers (the actions stream, a subject). In the diagram, - is one frame, a letter is an emission, | completes, # errors and () groups emissions into one frame. Worth it for debounce, retry, cancellation and ordering; overkill for a straightforward request-to-action mapping, where a plain subscribe assertion reads better.

Pro How would you test that a search effect debounces and cancels stale requests?

Marble test. Emit two query actions a few frames apart on a hot actions stream, return a cold response for each from the faked API, and assert with expectObservable that only the second produces a success action — proving debounceTime swallowed the first and switchMap cancelled the in-flight request. Add expectSubscriptions on the inner observable to prove the unsubscribe actually happened.

Pro What is the risk of mocking the store in every component test?

You end up asserting against a state shape you invented rather than one your reducers can actually produce, so a reducer or selector change breaks production while every spec stays green. Mitigation: keep reducer and selector tests real and thorough, derive mock state from the same factories the reducers use, and keep a thin layer of integration tests using the real store so the pieces are proven to fit.

Pro A guard-protected route test passes but production still lets unauthorised users in. What kind of test was missing?

The suite almost certainly tested the guard function in isolation and never tested the route configuration — the guard was never attached to the route, or was attached with canMatch where canActivate was expected, or the redirect target route did not exist. The fix is a navigation-level test: real provideRouter with the production route array, RouterTestingHarness.navigateByUrl, and assertions that the outlet stayed empty and the URL became the redirect target.
