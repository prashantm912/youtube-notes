Module: Vitest Fundamentals

Learn the runner before the framework. Everything here — matchers, spies, hooks, fake timers — is plain Vitest that would work in a React or Node project, and it is the layer every Angular test sits on now that Karma has been retired.

What this module covers

Vitest is the Vite-native test runner that Angular now ships as its default, replacing the Karma browser launcher and the Jasmine assertion library in one move. This module deliberately ignores Angular: it orients you on the runner's own surface — the shape of a test file, the matcher families behind expect, the vi mocking utilities, the four lifecycle hooks, timer faking and async assertions — and closes with what actually changes when a Jasmine codebase moves across. TestBed, fixtures and component rendering arrive in the next module.

Topics

Anatomy of a Vitest test — describe, it, expect, spies and hooks

A Vitest file is an ordinary TypeScript module ending in .spec.ts or .test.ts. describe groups related cases and can nest; it (or its exact alias test) declares one case; expect states what must be true. Unlike Jasmine, none of these are magic globals — you import them from vitest unless the project turns on the globals option, which the Angular schematics do so that files carried over from Jasmine keep compiling. Variants you will meet immediately: it.only and describe.only to focus a run, it.skip and it.todo to park one, and it.each for table-driven cases.

The expect API is Jest-compatible, and its matchers fall into families worth memorising as families rather than as a flat list. Equality: toBe compares with Object.is (reference identity for objects), toEqual walks structurally and treats an undefined property as absent, and toStrictEqual is the pedantic version that also compares class prototypes and refuses to ignore undefined keys. Truthiness: toBeTruthy, toBeFalsy, toBeNull, toBeUndefined, toBeDefined. Numbers: toBeGreaterThan, toBeLessThanOrEqual, and toBeCloseTo for floating point, because binary arithmetic makes toBe a trap. Strings: toMatch with a regular expression or substring. Arrays and iterables: toContain (identity), toContainEqual (structural), toHaveLength, and the asymmetric expect.arrayContaining. Exceptions: toThrow, which needs the call wrapped in a function so the matcher can invoke it. Snapshots: toMatchSnapshot and toMatchInlineSnapshot, which record a value on first run and compare thereafter. Every matcher inverts through .not.

import { describe, it, expect } from 'vitest';

describe('priceFormatter', () => {
  it('formats rupees with two decimals', () => {
    expect(format(1234.5)).toBe('1,234.50');
  });

  it('rejects negatives', () => {
    expect(() => format(-1)).toThrow(/negative/);
  });
});

Test doubles come from the vi namespace and there are three tools, not one. vi.fn() creates a standalone spy function that records every invocation in fn.mock.calls and fn.mock.results; program its answer with mockReturnValue, mockResolvedValue (or mockRejectedValue) for promise-returning collaborators, or mockImplementation for real logic, each with a ...Once variant that applies to a single call so you can script a sequence. vi.spyOn(obj, 'method') wraps an existing method: by default it still calls through, so you can observe without changing behaviour, and chaining .mockReturnValue(...) turns observation into replacement; mockRestore puts the original back. vi.mock('./module') replaces a whole module for the file — note that Vitest hoists these calls above the imports, so a factory cannot close over variables declared later unless you wrap them in vi.hoisted. Assert on any of them with toHaveBeenCalled, toHaveBeenCalledTimes, toHaveBeenCalledWith and toHaveBeenNthCalledWith.

const load = vi.fn().mockResolvedValue([{ id: 7 }]);   // programmed spy
const spy  = vi.spyOn(logger, 'warn');                  // observe, still calls through
vi.mock('./analytics');                                 // whole module auto-mocked

await service.refresh(load);
expect(load).toHaveBeenCalledTimes(1);
expect(spy).toHaveBeenCalledWith(expect.stringContaining('stale'));

Finally the four lifecycle hooks, which exist so that no test inherits another test's state. beforeAll and afterAll run once around the enclosing block — the place for genuinely expensive one-time setup — while beforeEach and afterEach run around every single case and are where fresh fixtures belong. They are scoped to the describe they sit in, outer beforeEach hooks run before inner ones and afterEach hooks unwind in the opposite order, all four accept async functions, and a beforeEach may return a cleanup function instead of writing a separate afterEach. Pair them with vi.clearAllMocks, vi.resetAllMocks or vi.restoreAllMocks (or the equivalent config flags) so spy history never leaks between cases — leaked state is the single most common cause of a suite that passes alone and fails in a full run.

Async assertions, fake timers, and migrating off Jasmine and Karma

Asynchrony is where test suites quietly stop asserting anything. The rule is simple: an async test must return or await its promise, because a test function that finishes before the promise settles is reported as passing whatever happens next. For promises you can assert on the settled state directly with expect(p).resolves.toEqual(...) and expect(p).rejects.toThrow(...) — both must themselves be awaited. When a code path is supposed to fail, expect.assertions(n) guards against the silent case where the expected rejection never happened and the catch block simply never ran.

Time is the other trap. Anything built on setTimeout, setInterval or Date — debounce, throttle, polling, retry backoff, token expiry — should never be tested by actually waiting. vi.useFakeTimers() swaps the timer functions and the clock for controllable fakes (backed by the sinon fake-timers library), after which vi.advanceTimersByTime(ms) jumps the virtual clock, vi.runAllTimers() drains the queue, vi.runOnlyPendingTimers() fires what is currently scheduled without chasing timers that reschedule themselves, and vi.setSystemTime() pins Date.now for date-sensitive logic. Always restore with vi.useRealTimers() in afterEach, and reach for the ...Async variants such as advanceTimersByTimeAsync when the timer callback returns a promise that must also flush. For the cases you cannot drive deterministically, vi.waitFor() re-runs a callback until it stops throwing (or the timeout expires) and vi.waitUntil() polls for a truthy value.

beforeEach(() => vi.useFakeTimers());
afterEach(()  => vi.useRealTimers());

it('debounces the search call', () => {
  const search = vi.fn();
  const debounced = debounce(search, 300);
  debounced('a'); debounced('ab');
  vi.advanceTimersByTime(299);
  expect(search).not.toHaveBeenCalled();
  vi.advanceTimersByTime(1);
  expect(search).toHaveBeenCalledExactlyOnceWith('ab');
});

it('surfaces a failed load', async () => {
  await expect(api.load('missing')).rejects.toThrow('404');
});

Now the migration story, because it is the part interviewers ask about right now. For roughly a decade the Angular default was Jasmine (the assertion and spy library) driven by Karma (the browser launcher). Karma was deprecated by its own maintainers and Angular followed: v20 shipped experimental Vitest support, and v21 promoted it to stable and made it the default for new applications through the @angular/build:unit-test builder, so ng test runs Vitest with no karma.conf.js in sight. Existing Karma projects still work and are still supported — this is a migration, not a forced march — and the CLI ships a refactor-jasmine-vitest schematic that mechanically rewrites most of a suite.

What actually changes is narrower than people expect, because Vitest's API is Jest-compatible and Jest borrowed its shape from Jasmine. describe, it, expect and all four hooks keep their names. The spy vocabulary is what moves: jasmine.createSpy() becomes vi.fn(); jasmine.createSpyObj('Api', ['get']) becomes a plain object of vi.fn()s; spyOn(obj, 'm').and.returnValue(x) becomes vi.spyOn(obj, 'm').mockReturnValue(x), with .and.callFake mapping to mockImplementation and .and.callThrough simply being the Vitest default; jasmine.any and jasmine.objectContaining become expect.any and expect.objectContaining; jasmine.clock() becomes vi.useFakeTimers(). The done callback style disappears in favour of async functions returning promises, which is a genuine improvement — a forgotten done() used to mean a timeout instead of a failure message.

One clarification worth carrying into an interview: fakeAsync, tick, flush and waitForAsync are not Jasmine APIs and are not replaced by vi.useFakeTimers. They come from @angular/core/testing, they work by draining zone.js task queues inside a TestBed test, and they remain fully valid under Vitest. Vitest's fake timers are the right tool for framework-free code; the Angular utilities are the right tool inside a fixture — and in a zoneless application you increasingly replace both with await fixture.whenStable().

// Jasmine                              ->  Vitest
// jasmine.createSpy('save')            ->  vi.fn()
// spyOn(api, 'get').and.returnValue(r) ->  vi.spyOn(api, 'get').mockReturnValue(r)
// spyOn(api, 'get').and.callFake(fn)   ->  vi.spyOn(api, 'get').mockImplementation(fn)
// jasmine.objectContaining({ id: 1 })  ->  expect.objectContaining({ id: 1 })
// jasmine.clock().install()            ->  vi.useFakeTimers()
// it('x', (done) => { ... done(); })    ->  it('x', async () => { await ... })

Interview questions

Frontend testing has moved from a nice-to-have to a standard round in Indian product and services interviews — and since the runner changed recently, the Jasmine-to-Vitest questions are the ones candidates fumble:

Beginner What is Vitest, and why did Angular move to it?

Vitest is a Vite-native test runner with a Jest-compatible API: it reuses the project's Vite pipeline, so it is TypeScript- and ESM-first, starts almost instantly and supports watch mode with hot reloading. Angular moved because Karma — the browser launcher behind the old stack — was deprecated, and because Vitest gives one integrated tool (runner, assertions, mocking, coverage) instead of Karma plus Jasmine plus separate plugins. It became the default runner in Angular v21 via the @angular/build:unit-test builder.

Beginner What do describe, it and expect each do — and is test different from it?

describe groups related cases (and can nest, which also scopes hooks); it declares one test case with a human-readable name and a body; expect creates an assertion on a value. test is an exact alias of it — pick one and stay consistent. In Vitest these are imported from vitest unless the globals option is enabled.

Beginner toBe vs toEqual vs toStrictEqual?

toBe is Object.is — identity, so two structurally identical objects fail. toEqual compares recursively by value and treats a property explicitly set to undefined as if it were absent. toStrictEqual is toEqual plus two extra checks: undefined properties must match, and the objects must share the same class/prototype. Use toBe for primitives and identity, toEqual for plain data, toStrictEqual when the exact shape matters.

Beginner Name the four lifecycle hooks and say when each runs.

beforeAll once before every test in its block, beforeEach before each test, afterEach after each test, afterAll once at the end. They are scoped to the enclosing describe: outer beforeEach hooks run before inner ones, and afterEach hooks unwind inside-out. Per-test fixtures go in beforeEach; only genuinely expensive, immutable setup belongs in beforeAll.

Beginner How do you assert that a function throws?

Wrap the call in a function so the matcher can invoke it: expect(() => parse('bad')).toThrow(TypeError). Passing parse('bad') directly would throw before expect ever ran. toThrow accepts a constructor, a substring or a regular expression to match the message. For a rejected promise, use await expect(p).rejects.toThrow(...) instead.

Intermediate vi.fn, vi.spyOn and vi.mock — when do you use each?

vi.fn() creates a brand-new spy function you inject as a collaborator or pass as a callback. vi.spyOn(obj, 'method') wraps an existing method on a real object so you can assert on it while it still calls through, or override it by chaining a mock implementation. vi.mock('./path') replaces an entire module for the whole file — the heaviest tool, for cutting off a hard dependency such as an HTTP client or an analytics SDK. Prefer the smallest one that answers the question.

Intermediate mockReturnValue vs mockResolvedValue vs mockImplementation, and what do the Once variants add?

mockReturnValue(v) makes the spy return v synchronously. mockResolvedValue(v) is shorthand for returning Promise.resolve(v) (with mockRejectedValue for the failure path). mockImplementation(fn) substitutes real logic when the answer must depend on the arguments. Each has a ...Once form that applies to the next call only, so you can script a sequence — for example, fail once and then succeed, to test retry logic.

Intermediate Why is vi.mock hoisted, and what commonly breaks because of it?

ES module imports are evaluated before any statement in the file, so to intercept a module the mock registration must be applied first — Vitest hoists vi.mock calls to the top of the file. The consequence is that a mock factory cannot reference variables declared above it in source order, because at run time they do not exist yet. The fix is vi.hoisted(), which lifts the variable definition alongside the mock, or declaring the value inside the factory.

Intermediate How do you test a debounce or a polling interval without slowing the suite?

Fake the clock. Call vi.useFakeTimers() in beforeEach, trigger the behaviour, then move virtual time with vi.advanceTimersByTime(ms) and assert either side of the boundary — nothing called at 299 ms, called once at 300 ms. vi.runOnlyPendingTimers() is the safe drain for self-rescheduling intervals, since runAllTimers would loop forever. Restore with vi.useRealTimers() in afterEach so later tests are not affected.

Intermediate An async test passes but the assertion inside it never ran. What went wrong?

The promise was not returned or awaited, so the test function completed before the assertion executed. Always await the call (or return the promise), use await expect(p).resolves/.rejects for settled-state assertions, and add expect.assertions(n) when testing a failure path so the runner fails if the expected number of assertions did not fire.

Intermediate clearAllMocks vs resetAllMocks vs restoreAllMocks?

clearAllMocks wipes recorded calls and results but keeps the programmed implementation. resetAllMocks also drops the implementation, returning the spy to a bare vi.fn(). restoreAllMocks additionally undoes vi.spyOn wrapping, putting the original methods back — which is why it is the one that matters for spies on shared or global objects. The same three exist as clearMocks, mockReset and restoreMocks config flags.

Pro Translate the common Jasmine spy idioms into Vitest.

jasmine.createSpy() becomes vi.fn(); jasmine.createSpyObj('Api', ['get','put']) becomes an object literal of vi.fn()s; spyOn(o,'m').and.returnValue(x) becomes vi.spyOn(o,'m').mockReturnValue(x); .and.callFake(fn) becomes mockImplementation(fn); .and.callThrough() is unnecessary because calling through is Vitest's default for spyOn; jasmine.any and jasmine.objectContaining become expect.any and expect.objectContaining; jasmine.clock() becomes vi.useFakeTimers(). The done-callback style is replaced by async test functions. The CLI's refactor-jasmine-vitest schematic performs most of this rewrite automatically.

Pro Do fakeAsync and tick still work under Vitest, and how do they differ from vi.useFakeTimers?

Yes — they are Angular TestBed utilities from @angular/core/testing, not Jasmine ones, so the migration does not touch them. They work by intercepting zone.js macro- and micro-task queues inside a fixture, which is why tick() also flushes pending promises. vi.useFakeTimers patches the global timer functions instead and knows nothing about Angular's change detection. Rule of thumb: Vitest fake timers for framework-free code, fakeAsync/tick inside TestBed tests, and await fixture.whenStable() as the preferred idiom in zoneless applications.

Pro When is a snapshot assertion the right tool, and how does it go wrong?

Snapshots earn their place for large, stable, mostly-inert output where writing explicit assertions would be noise — a serialised configuration object, an error report, a rendered markup fragment that rarely changes. They go wrong when the snapshot covers volatile data (dates, ids, ordering), when the file is large enough that reviewers rubber-stamp the diff, or when failures are habitually fixed by re-recording. Prefer toMatchInlineSnapshot so the expected value sits next to the test, keep them small, and never use them as a substitute for asserting the behaviour you actually care about.

Pro A test suite passes locally but fails intermittently in CI. Which runner-level habits cause that?

Shared mutable state that a hook never resets — module-level variables, spies whose call history carries over, a beforeAll fixture mutated by one test and read by another. Real timers and real network calls, whose latency differs on a loaded CI machine. Reliance on test execution order, which breaks as soon as files are sharded across workers running in parallel. Unawaited promises leaking work into the next test. The fixes are mechanical: build fixtures in beforeEach, enable restoreMocks, fake the clock, stub the network, and never let one test depend on another having run.
