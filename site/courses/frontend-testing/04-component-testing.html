Module: Component Testing Deep

A component test is only worth writing if it drives the component the way a user does — set an input, click a real button, read the rendered text. This module is the craft of doing that in Angular without welding your tests to the component's private internals.

Knowledge Library → Courses → Frontend Testing → Component Testing Deep

What this module covers

Module 03 got you a ComponentFixture. This one is about what you do with it: pushing values through the input pipeline with fixture.componentRef.setInput() instead of assigning fields, capturing emitted outputs by subscribing, firing genuine DOM events rather than calling handler methods, querying the rendered tree with By.css, and wrapping the component in a small host component so you can test it through the public template API — including anything projected into ng-content.

The second half raises the abstraction. Angular CDK component harnesses give you a typed, DOM-agnostic API over a component (the PageObject pattern, shipped as a framework feature) so your tests survive markup refactors — indispensable with Angular Material. Angular Testing Library attacks the same brittleness from the other direction, with accessibility-first queries and a user-event model. Both are legitimate; this module orients you on when each fits. Stack assumed throughout: Angular v20+ with signal inputs and outputs, running under Vitest.

Topics

Setting inputs the right way, and asserting on outputs

With signal inputs (input(), input.required()) the component's field is a read-only signal — there is nothing to assign. The supported way to feed one from a test is fixture.componentRef.setInput('name', value), which drives the same pipeline Angular uses for a real template binding: it records the change, marks an OnPush component dirty, and lets ngOnChanges and any computed/effect derived from the input react. Direct assignment to the instance field — the reflex carried over from decorator-era @Input() — either fails to compile or silently skips all of that, which is why an OnPush component "doesn't update" in a test that looks correct. After setting, await fixture.whenStable() (or call detectChanges() in a zone-based setup) before asserting.

Outputs are the mirror image. An output() returns an OutputEmitterRef with subscribe() and emit(); a test subscribes before acting and collects what arrives, then asserts on the payload. Prefer capturing real emissions over spying on the emitter — a spy proves a method was called, a subscription proves the component actually notified its parent with the right value. Assert on payload contents, not just call counts, or the test passes while the data is wrong.

const fixture = TestBed.createComponent(RatingComponent);
fixture.componentRef.setInput('score', 4);   // goes through the input pipeline
await fixture.whenStable();

const emitted: number[] = [];
fixture.componentInstance.scoreChange.subscribe(v => emitted.push(v));
// ...act on the DOM...
expect(emitted).toEqual([5]);

Dispatching real DOM events and querying with By.css

The single biggest quality jump in a component test is acting through the DOM instead of calling the component's methods. element.click() on the native element fires a genuine click that goes through the template binding, the host listener and any parent handler; calling component.onClick() proves only that a method you already wrote does what you wrote. For form fields the two-step idiom matters: set nativeElement.value, then dispatchEvent(new Event('input')) so Angular's value accessor notices — setting the value alone updates nothing, which is the classic "my form control stays pristine" puzzle.

To find those elements, fixture.debugElement.query(By.css(...)) returns a DebugElement (Angular's wrapper, with nativeElement, injector and listener metadata) and queryAll returns every match; By.directive() finds elements by the directive or component instance on them. Select on things a user or the accessibility tree can see — roles, labels, text, or an explicit data-testid — rather than on structural CSS classes, which change every time a designer touches the stylesheet.

const qty = fixture.debugElement.query(By.css('[data-testid="qty"]')).nativeElement;
qty.value = '3';
qty.dispatchEvent(new Event('input'));       // without this, Angular never sees it

fixture.debugElement.query(By.css('button.add')).nativeElement.click();
await fixture.whenStable();
expect(fixture.nativeElement.textContent).toContain('3 items');

The host-component wrapper and testing projected content

Some behaviour only exists when a component is used by someone else: two-way bindings, outputs wired to a parent handler, and anything the caller projects into ng-content. You cannot express that with a bare createComponent of the component under test, so you declare a tiny host component in the spec file whose template uses the real component exactly as an application would, and create a fixture of the host. Now inputs arrive as template bindings, emitted outputs land in host fields you can assert on, and projected markup genuinely renders inside the component's slots.

This is the only reliable way to test content projection — a component that renders <ng-content select="[actions]"> shows nothing at all when instantiated directly, because nobody supplied content. It also keeps the test honest about ownership: projected nodes belong to the host's view and are change-detected with it, so querying them through the host fixture mirrors the real runtime. Keep the host minimal (one template, a couple of fields) so it stays readable evidence of how the component is meant to be consumed.

@Component({
  standalone: true, imports: [CardComponent],
  template: `<app-card [title]="t" (dismissed)="closed = true">
               <button actions>Save</button>   <!-- projected -->
             </app-card>`,
})
class HostComponent { t = 'Invoice'; closed = false; }

CDK component harnesses: a typed API instead of selectors

A component harness is a class that exposes a component's behaviour as methods — getValue(), check(), openMenu() — and hides how that behaviour maps onto the DOM. It is the PageObject pattern promoted to a framework feature: your test says what the user does, the harness owns the selectors. When the component's internal markup changes, the harness is updated once by its author and every test that uses it keeps passing. That is the whole argument, and it is why Angular Material ships a harness for every component: a Material version bump that reshuffles class names breaks a suite full of By.css('.mat-mdc-form-field-infix input') and leaves a harness-based suite untouched.

The wiring is small. TestbedHarnessEnvironment.loader(fixture) yields a HarnessLoader; loader.getHarness(MatSelectHarness) or getAllHarnesses fetch instances, optionally filtered (MatButtonHarness.with({ text: 'Save' })). Every harness method is async and awaits stability for you, so await replaces most manual change-detection calls. Use getChildLoader or documentRootLoader to reach into sub-regions and into overlays (dialogs, menus, snackbars) that render outside the fixture's element. You can also write harnesses for your own components by extending ComponentHarness with a static hostSelector and locator factories — worth doing for any shared design-system component.

const loader = TestbedHarnessEnvironment.loader(fixture);
const save = await loader.getHarness(MatButtonHarness.with({ text: 'Save' }));
await save.click();                       // awaits stability internally

const status = await loader.getHarness(MatSelectHarness);
await status.open();
await status.clickOptions({ text: 'Approved' });

Angular Testing Library: the user-centric alternative style

@testing-library/angular is a thin layer over TestBed built on one rule: the more your test resembles how the software is used, the more confidence it gives. render(CardComponent, { inputs: { title: 'Invoice' }, on: { dismissed: spy } }) replaces the fixture ceremony — it can even take a template string, giving you the host-component pattern for free. You then query through screen using accessibility-first selectors — getByRole('button', { name: /save/i }), getByLabelText, getByText — and act with userEvent, which simulates a real interaction sequence (focus, keydown, input, change) instead of a single synthetic event. Because the queries mirror the accessibility tree, a component that is unreachable by keyboard or screen reader is often literally untestable, so accessibility bugs surface as test failures.

Honest comparison. CDK harnesses win when you consume a component library: Material's harnesses already exist, they encapsulate genuinely gnarly DOM (overlays, virtual scroll), and they are typed against the component's real API — and the two styles compose, since you can pull a harness out of an Angular Testing Library render. Angular Testing Library wins for your own feature components: no harness to author, queries that double as accessibility assertions, and a vocabulary shared with React and Vue teams. Plain TestBed with By.css is still fine for small, private components. What is not fine is a suite that reaches into component internals — spying on private methods, asserting on class fields — because that is the code that breaks on every refactor while catching nothing.

await render(CardComponent, {
  inputs: { title: 'Invoice' },
  on: { dismissed: vi.fn() },
});
await userEvent.click(screen.getByRole('button', { name: /dismiss/i }));
expect(screen.getByRole('heading', { name: /invoice/i })).toBeInTheDocument();

Interview questions

Component testing is where Angular interviews in India get practical — service-company rounds probe the mechanics, product-company rounds probe why your tests do not break on every refactor:

Beginner How do you set an input on a component under test?

fixture.componentRef.setInput('name', value), then await fixture.whenStable() (or call fixture.detectChanges()) before asserting. This routes the value through Angular's input pipeline exactly as a parent template binding would.

Beginner Why can't you just assign to the component instance field any more?

A signal input is a read-only signal, so there is nothing to assign. Even with a decorator @Input(), plain assignment skips the input pipeline: no change record, no ngOnChanges, and no dirty marking for an OnPush component — so the view may never update and the test fails for the wrong reason.

Beginner How do you assert that a component emitted an output?

Subscribe before acting and collect the values: component.saved.subscribe(v => received.push(v)), act through the DOM, then assert on received. With signal outputs the emitter is an OutputEmitterRef, which exposes subscribe and emit. Alternatively, bind the output in a host component and assert on the host's field.

Beginner What does By.css do, and what does query return?

fixture.debugElement.query(By.css(selector)) finds the first matching node in the component's rendered tree and returns a DebugElement — an Angular wrapper exposing nativeElement, the injector and event listeners. queryAll returns all matches; By.directive(Type) matches elements carrying a given directive or component.

Beginner Why click the DOM element instead of calling the component's handler method?

Calling the method tests only the method. A real click() exercises the template binding, the host listener, any disabled guard and the event path — so it catches a handler that was never wired up, a button hidden behind @if, or a disabled state that should have blocked the action.

Intermediate You set an input's value on a text field but the form control stays empty. Why?

Setting nativeElement.value only changes the DOM property; no event fires, so Angular's value accessor never learns about it. You must dispatch the event too: el.dispatchEvent(new Event('input')) (and 'change' for selects and checkboxes), after which the control value, validity and dirty flag update.

Intermediate What is a host (test wrapper) component and when do you need one?

A small component declared in the spec whose template uses the component under test the way an application would. You need it when the behaviour only exists in that relationship: two-way bindings, outputs handled by a parent, and — critically — content projected into ng-content, which renders nothing when the component is created directly because no caller supplied it.

Intermediate Which view owns projected content, and why does the test care?

Projected nodes belong to the caller's (host's) view and are change-detected with it, not with the component they visually sit inside. So the host fixture is what you drive and assert through, and DI or lifecycle expectations that follow the visual nesting will be wrong — the same rule that makes contentChild, not viewChild, the query for projected nodes.

Intermediate What is a CDK component harness and what problem does it solve?

A class exposing a component's behaviour as async methods while hiding its DOM structure — the PageObject pattern as a framework feature. It decouples tests from markup, so an internal refactor or a Material version upgrade that renames classes breaks the harness in one place instead of breaking every spec that hard-coded selectors.

Intermediate How do you obtain a harness in a unit test?

Create the fixture, then const loader = TestbedHarnessEnvironment.loader(fixture) and await loader.getHarness(MatSelectHarness). Use getAllHarnesses for lists, Harness.with({...}) to filter by text or attributes, getChildLoader to scope to a region, and documentRootLoader for overlay content such as dialogs and menus that renders outside the fixture element.

Intermediate What does Angular Testing Library change about how you write component tests?

render() replaces the TestBed and fixture ceremony (and accepts a template string, giving you a host component for free), screen queries by role, label and text instead of CSS, and userEvent simulates full interaction sequences. The effect is tests written in the user's vocabulary, which also means accessibility problems show up as failing queries.

Pro CDK harnesses vs Angular Testing Library — how do you choose?

They are complementary, not rivals. Harnesses are the better fit when consuming a component library — Material ships them, they encapsulate overlays and virtual scroll, and they are typed against the component's own API; they also work in end-to-end environments, not just TestBed. Angular Testing Library is the better fit for your own feature components: nothing to author, accessibility-first queries, realistic user events. You can use both in one spec by loading a harness from an Angular Testing Library render.

Pro How do you keep component tests from breaking on every UI refactor?

Assert on observable behaviour, never internals: no spying on private methods, no reading class fields. Select by role, label or an explicit data-testid rather than structural CSS classes. Push shared components behind harnesses so selector knowledge lives in one place. Drive the component through inputs and DOM events and verify through rendered output and emitted outputs — the public contract, which is exactly what should break a test when it changes.

Pro How would you write a harness for your own design-system component?

Extend ComponentHarness, declare a static hostSelector matching the component's element, and build locators with this.locatorFor(...) / locatorForOptional / locatorForAll. Expose async methods in the domain's language (await chip.remove(), await table.getRowTexts()) and add a static with() predicate for filtering. Ship it beside the component so every consuming team's tests inherit the refactor protection.
