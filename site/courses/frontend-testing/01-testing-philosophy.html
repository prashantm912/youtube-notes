Module: Testing Philosophy for SPAs

Before any runner, matcher or harness, a team has to answer two questions: how many tests of each kind, and what should a test be allowed to know? Get these wrong and the suite becomes the thing everyone disables.

Knowledge Library → Courses → Frontend Testing → Testing Philosophy for SPAs

What this module covers

This module frames the whole Frontend Testing track. It orients you on the two competing shapes for a suite — Mike Cohn's test pyramid and Kent C. Dodds' testing trophy — on why single-page applications argue for a fatter integration layer than the classic pyramid allows, and on the concrete mapping for an Angular app: pipes and services at the bottom, component-plus-template tests in the middle, Playwright journeys at the top.

The second half is discipline rather than shape: test observable behaviour instead of implementation details, recognise what makes a test brittle, structure every test as Arrange-Act-Assert, and price the maintenance honestly — a flaky suite is worse than no suite, because it trains the team to ignore red. Everything after this module (Vitest, TestBed, harnesses, Playwright) is mechanics in service of these decisions.

Topics

The test pyramid — Cohn's shape and why it holds

The test pyramid, introduced by Mike Cohn in Succeeding with Agile and popularised through Martin Fowler's writing, is a guideline about proportions: a wide base of fast, isolated unit tests, a narrower band of integration/service tests, and a thin cap of slow end-to-end tests. The two axes it encodes are cost and confidence — as you climb, each test gets slower, more expensive to write and maintain, more prone to non-determinism, but closer to what a user actually experiences.

Why it matters: the pyramid is the default answer interviewers expect, and its inverse — the "ice-cream cone", where a team leans on a huge UI suite because nobody wrote the lower layers — is the anti-pattern you are asked to diagnose. Fowler's related distinction between solitary tests (every collaborator replaced by a double) and sociable tests (real collaborators allowed in) is what actually decides how wide your base is, and it is the hinge the whole trophy argument turns on.

         /  \     -------------------------------
        /    \    integration  component + template + DI
       /______\   unit         pipes, services, pure logic

The testing trophy — why the frontend fattens the middle

Kent C. Dodds' testing trophy reshapes the pyramid for UI work: a base of static analysis (TypeScript, ESLint — free bug-catching that costs no test at all), a modest band of unit tests, a deliberately fat integration layer, and a small e2e cap. His slogan is "write tests, not too many, mostly integration". The argument is that in a component-based UI, most defects live in the wiring — a template binding, an input that never arrives, a service swapped for the wrong provider — and a unit test of a component class in isolation cannot see any of them.

Why it matters: the trophy is not a rejection of the pyramid, it is a claim about where the cost/confidence curve peaks for a specific kind of software. On the backend, a solitary unit test is cheap and meaningful; on the frontend, a component divorced from its template tests almost nothing. Be able to argue both shapes and say which you would pick for the codebase in front of you — that nuance is exactly what senior frontend interviews probe.

Mapping the layers onto an Angular SPA

The shapes only help once they name real files. In an Angular v20+ codebase the mapping is: unit = anything you can construct with new and call directly — pipes, pure functions, validators, and services whose dependencies you pass in; no TestBed, microsecond runtimes. Integration = a component rendered through TestBed with its real template, real change detection and a configured injector, driven the way a user drives it and asserted on rendered output; this is where most of your tests should live. End-to-end = Playwright running a real browser against a real (or realistically stubbed) backend, covering the handful of journeys the business cannot afford to break — sign-in, checkout, submit.

Why it matters: candidates who cannot place a concrete artefact at a layer give vague answers. "Where would you test a currency pipe? A form component that disables submit until valid? The whole payment flow?" has one correct set of answers, and it is the practical follow-up to every pyramid question. The layer choice also decides the tool — plain Vitest, Vitest plus TestBed, or Playwright — which is the rest of this track.

Test behaviour, not implementation

A test should assert what the software does, not how it is built. Testing Library states the principle as: "the more your tests resemble the way your software is used" — the more confidence they earn. Practically, that means reaching for the things a user or an assistive technology can perceive: visible text, accessible roles and names, form labels. It means not asserting on a component's private fields, not calling lifecycle hooks by hand, not selecting elements by a styling class such as .btn-primary, and not asserting that a particular private method was invoked.

Why it matters: implementation-coupled tests produce both failure modes at once — false negatives (a pure refactor turns the suite red although behaviour is unchanged) and false positives (the internals still match, so the suite stays green while the button no longer works). Over-mocking is the same mistake in another costume: if every collaborator is a double, you have verified your mocks, not your application. This principle is why Angular's own docs push you toward asserting on rendered output, and why component harnesses exist.

// Brittle — couples the test to internals and to styling
expect(component.panelOpen).toBe(true);
expect(el.querySelector('.pnl--open')).not.toBeNull();

// Durable — asserts what a user can observe
expect(screen.getByRole('region', { name: 'Order summary' })).toBeVisible();

Arrange-Act-Assert, and the honest cost of a suite

Every readable test has three visually separated phases: Arrange the world (build the subject, stub what it needs), Act once (call the method, click the button), Assert the outcome. One logical action per test, a name that reads as a behavioural sentence ("disables submit until the form is valid"), and assertions on the result rather than on the steps. The structure is not decoration: when a test fails at three in the morning, the shape is what makes the failure legible.

Then the part teams skip — tests are code you must maintain forever. A suite that is slow, flaky or coupled to internals gets skipped, then xit-ed, then deleted, and the team ends up worse off than with no suite, because they spent the money and lost trust in red builds. Budget for this explicitly: keep the fast layers fast, quarantine and fix non-determinism rather than retrying it away, treat coverage as a diagnostic rather than a target, and delete tests that only assert the framework works. Angular's current default runner is Vitest (Karma is retired and the CLI ships a Karma-to-Vitest migration path), and its speed is precisely what keeps the fat middle layer affordable.

import { describe, it, expect } from 'vitest';
import { TitleCasePipe } from '@angular/common';

describe('TitleCasePipe', () => {
  it('capitalises each word', () => {
    const pipe = new TitleCasePipe();        // Arrange
    const result = pipe.transform('asha rao'); // Act
    expect(result).toBe('Asha Rao');           // Assert
  });
});

Interview questions

Frontend testing strategy is now a standard round in Indian product and service company interviews — these open it, from screening through to design discussion:

Beginner What is the test pyramid?

A guideline for the proportions of a suite: many fast unit tests at the base, fewer integration tests in the middle, very few end-to-end tests at the top. As you go up, tests get slower, costlier and flakier but more realistic. Attributed to Mike Cohn and popularised by Martin Fowler.

Beginner What is the difference between unit, integration and end-to-end tests in a frontend app?

A unit test exercises one piece in isolation (a pipe, a pure function, a service with stubbed dependencies). An integration test renders a component with its real template, change detection and injector and drives it as a user would. An end-to-end test runs the built application in a real browser and walks a complete journey across pages and the network.

Beginner What does Arrange-Act-Assert mean?

The three phases of a readable test: arrange the subject and its inputs, perform exactly one action, then assert on the observable outcome. Keeping them visually separate — and keeping one action per test — makes failures self-explanatory and stops tests from drifting into multi-purpose scripts.

Beginner Which runner does a new Angular project use today, and what did it replace?

Vitest is the current default; Karma is deprecated and removed from new projects. Vitest runs on the Vite pipeline, so start-up and watch-mode feedback are far faster than the old browser-launching Karma runs. The Angular CLI documents a Karma-to-Vitest migration for existing codebases. Playwright (or Cypress) still covers the end-to-end layer.

Beginner Where would you test a currency pipe, a form component and the checkout journey?

The pipe is a pure unit test — construct it and assert the transform output. The form component is an integration test through TestBed: render it with its template, type into the fields, assert the submit button state and the emitted output. Checkout is end-to-end in Playwright, because its value lies in crossing routes, services and the network.

Intermediate What is the testing trophy and how does it differ from the pyramid?

Kent C. Dodds' reshaping of the pyramid for UI work: static analysis at the base, some unit tests, a deliberately large integration layer, and a small e2e cap — "write tests, not too many, mostly integration". The difference is where the cost/confidence curve peaks. In a component UI most bugs are wiring bugs (bindings, inputs, providers) that a solitary unit test cannot see, so the middle layer earns the most confidence per rupee spent.

Intermediate What makes a test brittle? Give concrete Angular examples.

Any coupling to something that is not behaviour: asserting on component fields or private methods, calling ngOnInit by hand instead of letting change detection run, selecting elements by styling classes such as .btn-primary, asserting on DOM structure or child ordering, snapshotting entire templates, and mocking every collaborator. Each of these breaks on a refactor that changed nothing a user can see.

Intermediate Why is querying by CSS class a poor selector strategy in component tests?

Classes are a styling concern and change whenever design does, so a purely visual refactor turns the suite red. They also carry no semantics — a class does not tell you the element is a button or is labelled "Submit". Prefer accessible role and name, then visible text or label, and fall back to an explicit data-testid only when nothing user-facing identifies the element. That ordering also nudges the markup toward being accessible.

Intermediate Should you test private methods and component internals?

No. Private members are implementation; if a private method matters enough to test, drive it through the public behaviour that uses it, or extract it into its own collaborator with a public contract of its own. Testing internals produces false negatives on refactors and false positives when the internals still match but the rendered behaviour has broken.

Intermediate How much should you mock?

As little as gets you determinism and speed. Stub the genuinely uncontrollable boundaries — HTTP, time, randomness, browser APIs — and let the rest of your own code run for real. When every dependency is a double you are asserting that your mocks behave like your mocks; the integration bugs the trophy is aimed at slip straight through.

Intermediate What is a flaky test, and why is it said to be worse than no test?

A test that passes and fails on the same code, usually through timing, shared state, test ordering or real network calls. It is worse than nothing because it destroys the signal: once a red build might mean nothing, people stop reading builds, and a genuine regression sails through. The remedy is to quarantine the test immediately and fix the root cause, never to paper over it with blanket retries or sleeps.

Pro Your team demands a hundred percent code coverage. What do you say?

That coverage measures which lines executed, not whether anything was verified — you can reach full coverage with no assertions at all. Use it as a diagnostic to find untested areas, and set a floor on critical modules rather than a global target, because the last stretch is usually bought with brittle tests of trivial code. Confidence comes from meaningful assertions at the right layer, and from mutation testing if you want a real measure of test strength.

Pro The suite takes forty minutes and fails randomly on roughly one run in ten. Walk me through fixing it.

Measure first — collect per-test timings and a failure history so you fix causes, not impressions. Quarantine the flaky tests out of the blocking pipeline so the build regains meaning, then fix them by removing real timing, real network and shared state (fake timers, request mocking, fresh fixtures per test). For speed, check the shape: an over-large e2e layer is usually the cost centre, so push those assertions down into component-level tests, and parallelise or shard the rest in CI. Finally, delete tests that only assert the framework works.

Pro When would you deliberately depart from the pyramid?

When the risk profile justifies it. A legacy application with no seams may only be safely covered end-to-end while you refactor toward testability. A thin presentational layer over a heavily tested API needs few unit tests and a handful of journeys. A design-system library inverts the other way — its components are the product, so component-level tests plus visual and accessibility checks dominate. The shape is a heuristic about cost and confidence, not a rule; state the trade-off you are making and why.
