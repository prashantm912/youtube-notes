Module: Deployment Strategies

The pipeline has built, tested and signed your artifact. Everything up to this point was rehearsal — this module is about the last hop, where a new version has to reach real users without an outage, and where the database refuses to play by the same rules as the code.

Knowledge Library → Courses → DevOps and Deployment track → Deployment Strategies

What this module covers

Everything earlier in this track — Git history you can reason about, reproducible Maven and Gradle builds, small immutable images, a Kubernetes cluster that can schedule them, a pipeline that gates them — exists to make one moment safe: the moment production starts running code it was not running a minute ago. This is the closing module, so it is also the one that ties the rest together.

Two halves. The first is the mechanics of shifting traffic: recreate, rolling update, blue-green and canary, compared honestly on risk, cost, rollback speed and operational complexity, plus the idea that makes all of them optional — deploy and release are different events, and feature flags are what separates them. The second half is the part that turns a five-minute rollback into a three-hour incident: data. Schema changes do not roll back the way code does, so backward-compatible migrations, the expand-contract pattern, migration tooling, an honest rollback policy and dev/prod parity are not footnotes here — they are the substance.

Topics

Deploy is not release: the distinction the whole module rests on

Deployment is a technical event: a build artifact is installed and started in an environment. Release is a business event: users can now reach the behaviour that artifact contains. Most teams conflate the two because their tooling conflates them — pushing the image is what turns the feature on — and every painful launch you have sat through is downstream of that conflation. Once the two events are separable, deployment becomes boring and frequent, and release becomes a deliberate, reversible decision made by whoever owns the feature rather than by whoever owns the pipeline.

The twelve-factor formulation is useful vocabulary here: build, release, run are three strictly separated stages, a release is an immutable build-plus-config pair with its own id, and you can roll back to a previous release without rebuilding. Note also what the DORA research consistently finds: elite performers are not elite because they deploy carefully, they are elite because they deploy often, in small pieces, which is only tolerable when a deployment is low-drama by construction. Everything below is machinery for making it low-drama.

The four strategies, compared honestly

There are only four shapes, and the differences between them are entirely about who absorbs the risk of a bad version: all users at once, some users for a while, no users until you flip a switch, or a small measured slice. Read the table as a decision aid, not a ranking — the safest strategy is also the most machinery, and a nightly batch service with a maintenance window genuinely should take the simple option.

Recreate and rolling update: the two the platform gives you free

Recreate terminates every old Pod before creating new ones. It is the strategy everyone dismisses and occasionally the correct one: a singleton that cannot tolerate two writers, a job runner holding an exclusive lock, a schema change so invasive that running both versions is genuinely impossible. It buys simplicity with an outage, and if the outage is thirty seconds at three in the morning on an internal tool, that is a rational trade rather than a failure of ambition.

RollingUpdate is the Kubernetes default and the one you will use for almost everything. Two knobs govern it: maxSurge (how many extra Pods above the desired count may exist during the rollout) and maxUnavailable (how far below the desired count you may drop). The rollout is gated on readiness probes, so a new Pod receives traffic only when it says it is ready — which is why a badly written readiness probe converts a rolling update into a silent outage. The tax you pay is structural, not configurable: for the duration of the rollout, version N and version N+1 are both serving live traffic. Every API contract, every message schema, every cache key and every database column touched by that release must be compatible with both versions simultaneously. That single sentence is the reason the second half of this module exists.

spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%          # extra capacity allowed during the rollout
      maxUnavailable: 0      # never dip below desired replicas
  minReadySeconds: 10        # a Pod must stay ready this long before it counts
  progressDeadlineSeconds: 600
  template:
    spec:
      containers:
        - name: api
          readinessProbe:    # gates traffic; get this wrong and the rollout lies
            httpGet: { path: /readyz, port: 8080 }
          lifecycle:
            preStop:
              exec: { command: ["sleep", "5"] }   # let endpoints drain first

Blue-green: two environments and one switch

Blue-green keeps two production-capable environments. Blue is live; you deploy the new version to green, run smoke tests and health checks against it with no user traffic on it at all, and then switch the router — a load balancer target group, a Kubernetes Service selector, a DNS record, an Ingress or Gateway route. The appeal is the rollback story: it is the same switch in the other direction, executable in seconds by someone who does not need to understand the change. That is a genuinely different risk profile from "wait for a reverse rolling update to finish while the incident channel fills up".

Two costs, and interviewers ask about both. The obvious one is infrastructure: you are paying for double capacity, at least during the cutover window, plus the discipline to keep the idle environment identical to the live one. The subtle one is data. Both environments almost always talk to the same database — duplicating the datastore means replicating writes and reconciling them, which most teams sensibly refuse — so the instant switch does not undo any schema change the green version applied. Blue-green gives you an instant code rollback and no data rollback at all, which is exactly why blue-green shops end up more rigorous about backward-compatible migrations than anyone else. Note also the long-lived in-flight work: sessions, WebSocket connections and half-finished jobs pinned to blue need a drain policy, or the switch is instant for you and an error page for them.

Canary: a small slice of real traffic, promoted on evidence

A canary release routes a deliberately small share of live production traffic — often two or five percent to begin with — to the new version, holds it there while you watch error rate, latency percentiles and business metrics, and only then ramps. It is the only strategy that tests the new version against the thing your staging environment cannot simulate: real users, real data distribution, real concurrency, real third-party latency. The blast radius of a bad build is bounded by the split rather than by how fast a human notices.

The machinery is the price. You need traffic splitting that is finer-grained than "one Service, N Pods" — an Ingress controller with weighted backends, the Kubernetes Gateway API's weighted backendRefs, or a service mesh — and you need to decide how a user is assigned: sticky by session (so one unlucky user does not flip between versions mid-checkout) or purely by weight. You also need a baseline to compare against. Google's own canary-analysis guidance is emphatic on this point: compare the canary to an equivalent freshly-deployed baseline of the old version, not to the long-running production fleet, or you will attribute warm-cache and JIT differences to your change.

Progressive delivery: Argo Rollouts, Flagger and automated analysis

Canary by hand is a person watching a dashboard and typing kubectl — which works until the release happens on a Friday evening. Progressive delivery is the automation of that judgement. Argo Rollouts replaces the Deployment resource with a Rollout that owns a scripted sequence of steps (set weight, pause, analyse, set weight, pause, promote) and an AnalysisTemplate that queries Prometheus, Datadog, New Relic or a web endpoint at each pause. If the metric fails its success condition, the rollout aborts and traffic goes back to stable without a human. Flagger, part of the Flux project, does the same job driven by an annotated Canary custom resource and integrates with the common meshes and ingress controllers.

What both really buy you is not the ramping — it is the defined stop condition. The failure mode of manual canaries is not that nobody looks; it is that the person looking has no pre-agreed threshold, so ambiguity resolves as "it's probably fine, promote it". Writing the success criteria into an AnalysisTemplate forces the team to answer, before the release, the question they otherwise argue about during the incident: what number means we stop?

apiVersion: argoproj.io/v1alpha1
kind: Rollout
spec:
  strategy:
    canary:
      analysis:
        templates: [{ templateName: success-rate }]   # aborts the rollout on failure
      steps:
        - setWeight: 5
        - pause: { duration: 10m }
        - setWeight: 25
        - pause: { duration: 30m }
        - setWeight: 50
        - pause: {}            # indefinite: a human promotes the last step

Feature flags: the thing that actually separates deploy from release

All four strategies above still couple "this code is running" to "this behaviour is visible". A feature flag breaks that coupling in the one place it is cheapest to break: a conditional in your own code, evaluated per request against a rule set you can change at runtime. The workflow it enables is the whole point of this module. Ship dark: merge and deploy the feature behind a flag that is off, so the code reaches production in small increments and is continuously integration-tested there. Enable internally: turn it on for your own staff or a beta segment. Ramp: five percent, then twenty-five, then everyone, watching metrics at each step. Kill instantly: when something breaks, flip the flag off — no rebuild, no redeploy, no pipeline, no rollback of unrelated changes that happened to ride the same release.

The discipline half. Martin Fowler's taxonomy is worth learning because the answer to "how long does this flag live?" depends on its kind: release toggles are transitional and should be deleted within days or weeks of full rollout; experiment toggles live as long as the test; ops toggles (kill switches, load-shedding) may be permanent by design; permission toggles are really entitlements and belong in your authorisation model rather than your flag system. What kills teams is flag debt: every flag doubles the notional number of code paths, and a codebase with two hundred stale release toggles has a combinatorial test surface nobody can reason about, plus real incidents caused by a forgotten flag defaulting the wrong way. Treat removal as part of the feature — a ticket created when the flag is created, an owner and expiry date on every flag, a periodic report of flags older than their expiry, and a rule that the release toggle is deleted in the same sprint the feature goes to a hundred percent.

// Ship dark: the code is deployed, the behaviour is not released.
if (flags.isEnabled("checkout-v2", user)) {   // per-request, per-user evaluation
    return newCheckout.quote(cart);
}
return legacyCheckout.quote(cart);            // delete this branch, and the flag,
                                              // in the sprint after full rollout

Adjacent techniques: shadow traffic and A/B testing

Shadow (mirrored) traffic copies live requests to the new version while the real response still comes from the old one. The user never sees the shadow result, so a crash or a wrong answer costs nothing — you are testing whether the new version survives production-shaped load and production-shaped data. It is the right tool for a rewrite, a database engine swap or a big refactor where you want confidence before any user is exposed. The trap is side effects: a mirrored request that charges a card, sends an SMS or writes a row does it for real. Shadowing is safe only for genuinely read-only paths, or with the downstream writes stubbed and the shadow environment pointed at a copy.

A/B testing looks like canary and is not. Canary asks a technical question — is this build healthy? — and is judged on error rate and latency over minutes or hours. A/B testing asks a product question — does variant B convert better? — is judged on business metrics over days or weeks, needs a statistically meaningful sample, and requires sticky assignment so a user sees one consistent variant. Same traffic-splitting plumbing, completely different owner, duration and success criterion. Saying that cleanly in an interview signals you have shipped rather than read.

The part people forget: schema changes are not code changes

Code is stateless and disposable; you can replace a container with its predecessor and nothing is lost. A database holds state, and a migration is a one-way transformation of that state. DROP COLUMN has no inverse — the values are gone. A type narrowing has no inverse for rows that no longer fit. A backfill that mangles data cannot be un-mangled by running the migration backwards. This asymmetry is why "we can just roll back" is the most dangerous sentence in a release meeting, and why database change management is a distinct DORA capability rather than a detail of deployment automation.

The governing rule follows directly from rolling updates: during a rollout, old and new application versions are both live against the same schema, so every migration must be compatible with both. A migration that renames user_name to username breaks version N the instant it runs, and version N is still serving half your traffic. The consequence is that database change stops being a step in a release and becomes a sequence spread across several releases — which is exactly what the expand-contract pattern formalises. Practically: version your schema in the same repository as the code that uses it, make migrations forward-only and additive by default, and treat "is this change backward-compatible with the currently deployed version?" as a mandatory review question on every pull request that touches the schema.

Expand-contract (parallel change), step by step

Expand-contract — Danilo Sato's parallel change — is how you make a breaking schema change without ever having a breaking moment. You expand the schema so old and new shapes coexist, migrate the readers and writers across while both work, then contract by removing the old shape once nothing references it. The canonical example is renaming a column, and the point is that it takes at least three deployments rather than one. Deliberately slower, and enormously cheaper than an outage.

Walk the steps for renaming full_name to display_name:

  1. Expand. Add the new nullable column. Purely additive, so the running version is unaffected and this migration is safe to deploy on its own.
  2. Dual-write. Deploy an application version that writes both columns and still reads the old one. Now every new or updated row is correct in both places.
  3. Backfill. Copy historical rows into the new column in batches, throttled, restartable and idempotent — never one giant transaction that locks the table and blocks production.
  4. Switch reads. Deploy a version that reads the new column and still writes both. This is the reversible step: if the new column is wrong, redeploy the previous version and reads go back to the old column, which is still being maintained.
  5. Stop writing the old. Once the read switch has soaked in production, deploy a version that writes only the new column. The old column is now stale but harmless.
  6. Contract. After the retention period you are comfortable with — and only when no deployed version and no report, ETL job or downstream consumer references it — drop the old column.

Two frequently-missed details. Constraints expand the same way: add a new constraint as NOT VALID (or the equivalent for your engine) and validate it separately, so you never take a full-table lock during a release. And the same pattern applies beyond columns — renaming a Kafka topic field, changing a REST response shape, or splitting a table all follow expand, migrate, contract, because in each case two versions of a consumer are live at once.

Migration tooling, and where migrations should actually run

Flyway applies ordered, versioned SQL files (V1__init.sql, V2__add_display_name.sql) and records what it applied in a schema-history table, refusing to proceed if a previously applied file's checksum changed. Liquibase models changes as changesets in XML, YAML, JSON or SQL, tracks them in DATABASECHANGELOG, takes a lock so two instances cannot migrate concurrently, and supports declared rollback instructions per changeset. Flyway is simpler and SQL-native; Liquibase is more abstract and more capable of describing a rollback. Either is fine; having none — schema changes applied by hand from someone's laptop — is the actual failure.

The operational question interviewers actually care about is where the migration runs. Both Spring Boot starters will happily run migrations on application startup, which is convenient on a laptop and wrong in a multi-replica deployment: five Pods start simultaneously, contend for the lock, four wait, startup probes may time out and the orchestrator kills Pods mid-rollout. Worse, it couples schema change to Pod scheduling, so you cannot verify the migration succeeded before shipping code that depends on it. Run migrations as their own pipeline step against the target database — a Kubernetes Job or Helm pre-upgrade hook, an init container that only the migration workload runs, or a dedicated CD stage — so exactly one process applies them, its exit code gates the deployment, and its output is a first-class artifact of the release.

# Migration as its own gated step, not a side effect of application startup
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate-v2
  annotations:
    helm.sh/hook: pre-upgrade          # runs and must succeed before the rollout
    helm.sh/hook-delete-policy: before-hook-creation
spec:
  backoffLimit: 0                      # fail loudly; do not half-apply twice
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: flyway
          image: flyway/flyway:11
          args: ["-connectRetries=10", "migrate"]

Rollback discipline, and why roll-forward is often the better answer

Be precise about what is rollback-safe. Safe: a stateless code change, a config value, a feature flag, an image tag with no schema or contract change. Conditionally safe: a change that ran only additive migrations — the extra column is unused by the old version, so redeploying it works. Not safe: anything that dropped or narrowed a column, rewrote data, published a new message schema consumers have already begun reading, or migrated a cache format. For that last category, "roll back" is not a button, it is a project.

Which is why mature teams bias toward roll-forward: fix the defect, ship a new version through the same pipeline you trust. Rolling back to version N means running a build that has not been exercised against the current data, current config and current downstream contracts for however long — the old version is not a known-good state, it is an untested state that used to be good. Roll-forward is only viable if your pipeline is fast, so pipeline duration is a reliability property, not a developer-convenience property. Feature flags shorten this further: a kill switch is a partial rollback that needs no build at all.

Two habits worth more than any tool. First, test the rollback path — rehearse it in a lower environment, actually run the previous image against the migrated schema, because an untested rollback procedure is a rumour. Second, write the decision rule before the incident: state in the runbook, per release, which of roll back, roll forward or flag-off applies, who may call it, and what threshold triggers it. Deciding this at three in the morning with a paging alert going off produces the worst version of the decision, every time.

Environment parity, preview environments, and what you would do on Monday

Every strategy above assumes the thing you tested resembles the thing you shipped to. Dev/prod parity is the twelve-factor principle that the gap between environments should be small in time (hours between write and deploy, not weeks), in personnel (the people who wrote it deploy it) and in tools (the same database engine, the same message broker, the same versions). The classic violation is backing-service substitution — SQLite or H2 in dev against PostgreSQL in production, an in-memory queue against Kafka — which works right up to the first transaction-isolation, collation or timezone difference, and then produces a bug that is unreproducible by definition. Containers plus Compose, and Testcontainers in the test suite, remove most of this excuse.

Ephemeral preview environments are parity's practical form: every pull request gets a temporary, fully deployed environment built from that branch, torn down on merge. Reviewers click the change instead of imagining it, integration tests run against real infrastructure, and the environment is disposable so nobody nurses a long-lived "staging" that has quietly drifted three months away from production. Keep them cheap and short-lived, seed them with anonymised or synthetic data, and make teardown automatic.

The Monday verdict for this track. If you take one action away from these fourteen modules, take this sequence. Get every deploy to production going through the pipeline you built, from a commit on trunk, with no manual step. Set your Deployments to rolling update with maxUnavailable: 0 and readiness probes that tell the truth. Adopt a migration tool and run it as a gated pipeline step, forward-only and additive, and make backward compatibility a review question. Introduce one feature flag on your next risky change and delete it once the feature is fully rolled out — that single habit converts scary releases into ordinary ones faster than any deployment strategy. Add canary automation later, when your metrics are good enough to make the decision automatable. Everything else in this track was preparation for shipping on a Tuesday afternoon without anyone holding their breath.

Interview questions

Deployment strategy is where Indian product and service-company interviews check whether you have actually operated a system or only configured one — the strategy comparison is near-guaranteed, and the database follow-ups are where most candidates come apart:

Beginner What is the difference between a deployment and a release?

Deployment is technical: the build artifact is installed and running in an environment. Release is the business event: users can reach the new behaviour. They are separable — you can deploy code that is switched off, and release it later by flipping a flag — and separating them is what makes frequent deployment safe.

Beginner Name the main deployment strategies and the trade-off each makes.

Recreate: stop all, start all — downtime, but simplest and sometimes correct. Rolling update: replace instances gradually — no downtime, little extra cost, but two versions run at once. Blue-green: two full environments and an instant traffic switch — instant rollback, double infrastructure, and no data rollback. Canary: a small share of live traffic on the new version, promoted on metrics — smallest blast radius, most machinery.

Beginner What do maxSurge and maxUnavailable control in a Kubernetes rolling update?

maxSurge is how many Pods above the desired replica count may exist during the rollout (extra capacity); maxUnavailable is how far below the desired count you may drop. Setting maxUnavailable to 0 with a non-zero maxSurge means capacity never dips, at the cost of briefly needing extra room. Readiness probes gate when a new Pod starts receiving traffic.

Beginner What is a feature flag and what does it let you do that a deployment cannot?

A runtime conditional whose value comes from a configuration service rather than the build, evaluated per request. It lets you deploy code that is off, enable it for internal users, ramp by percentage, and turn it off instantly during an incident — all without a rebuild, a redeploy, or rolling back unrelated changes that shipped in the same release.

Intermediate Blue-green versus canary — when would you choose each?

Blue-green when you need a clean version boundary and an instant, obvious rollback: regulated or big-bang cutovers, changes that cannot tolerate two versions running, teams that value a simple switch over gradual exposure. Canary when the service is high-traffic and user-facing and a bad build is expensive: it limits the blast radius to a small percentage and lets metrics decide. Blue-green exposes everyone at the switch instant but is trivially reversible; canary exposes few but takes longer and needs traffic splitting plus automated analysis. Blue-green costs double infrastructure; canary costs complexity. Neither solves the database.

Intermediate During a rolling update, two versions of your service are live. What must you guarantee?

Mutual compatibility. The API contract must be backward-compatible (additive fields, no renames, no removed endpoints); message and event schemas must be readable by both; shared caches must use versioned keys or tolerant serialisation; and every database change in that release must work for both versions — which in practice means additive-only migrations and the expand-contract pattern. If two versions cannot coexist, you need Recreate and a window, not a rolling update.

Intermediate How do you roll back a database migration?

Usually you do not — that is the honest answer, and it is what the interviewer is listening for. Structural changes such as DROP COLUMN or a type narrowing destroy data and have no inverse, so a symmetric rollback is impossible. You avoid needing one: make migrations forward-only and additive, use expand-contract so every intermediate state works with both application versions, and keep the old shape around long enough that redeploying the previous application version still works. When something is genuinely wrong you roll forward with a corrective migration. Beyond that: Liquibase lets you declare rollback instructions per changeset and Flyway has undo migrations in its paid tier, but both only help for reversible changes; a point-in-time restore is the last resort and costs you every write since the snapshot.

Intermediate Why should migrations not run at application startup in a multi-replica deployment?

Several replicas start at once and contend for the migration lock, so most of them block; startup or readiness probes can time out and the orchestrator kills Pods mid-rollout. It also couples schema change to Pod scheduling, so you cannot verify the migration succeeded before shipping dependent code, and a failure surfaces as a crash-looping Pod rather than a failed pipeline stage. Run it as a separate gated step — a Kubernetes Job, a Helm pre-upgrade hook, or a dedicated CD stage — so exactly one process applies it and its exit code gates the rollout.

Intermediate Flyway or Liquibase — how would you choose?

Flyway applies ordered, versioned SQL files and records them with checksums in a schema-history table: simple, SQL-native, minimal learning curve, and it fails fast if an applied file was edited. Liquibase describes changes as changesets in XML, YAML, JSON or SQL, is more database-agnostic, and supports declared rollback per changeset. Choose Flyway when the team is comfortable writing SQL and wants transparency; choose Liquibase when you need database portability or want rollback instructions expressed alongside each change. The important part is that you use one, version it with the application code, and never apply schema changes by hand.

Intermediate What is shadow or mirrored traffic, and what is the risk?

Live requests are duplicated to the new version while the real response still comes from the old one, so the new version is exercised with production-shaped load and data at zero user risk. The risk is side effects: a mirrored request that writes a row, charges a card or sends a notification does it for real, and duplicated writes can corrupt state or double-bill. Mirror read-only paths, or point the shadow at a copied datastore with outbound integrations stubbed.

Pro Walk me through renaming a column with zero downtime.

Expand-contract, across at least three releases. (1) Add the new nullable column — additive, safe alone. (2) Deploy a version that writes both columns and reads the old one. (3) Backfill history in throttled, restartable, idempotent batches, never one locking transaction. (4) Deploy a version that reads the new column and still writes both — the reversible checkpoint. (5) Deploy a version that writes only the new column. (6) After a soak period, and only once no deployed version, report, ETL job or downstream consumer touches it, drop the old column. Constraints follow the same shape: add as NOT VALID, then validate separately to avoid a full-table lock.

Pro Your team wants blue-green. What do you tell them about the database?

That blue-green gives an instant code rollback and no data rollback. Both environments almost always share one database — duplicating it means replicating writes and reconciling them, which nobody sensibly does — so any schema change green applied is still applied after you switch back to blue. The consequence is that blue-green requires the same backward-compatible, expand-contract migration discipline as a rolling update; it does not exempt you from it. Also plan connection and session draining for in-flight work pinned to the old environment, and budget for keeping the idle environment configured identically, because drift between blue and green is a common incident cause.

Pro Roll back or roll forward? How do you decide, and when?

Decide before the release, not during the incident. Roll back when the change is stateless and rollback-safe — image tag, config, no destructive migration, no new contract already consumed — and the previous version is genuinely known-good. Roll forward when data or contracts moved, when the old version has not been exercised against the current schema, or when the fix is small and your pipeline is fast; rolling back to an untested-against-current-state version can be more dangerous than shipping the fix. Fastest of all, when available, is flipping the feature flag off: a partial rollback with no build at all. Write the rule, the threshold and the person who may call it into the runbook per release, and rehearse the rollback path in a lower environment so it is a procedure rather than a rumour.

Pro What is flag debt and how do you keep it under control?

Every flag adds a branch, so N flags mean an exponential notional number of code paths, most of them never tested together. Stale release toggles cause real incidents when a forgotten flag defaults the wrong way after a config migration, and they make the codebase unreadable. Control it by classifying flags on creation — release toggles are transitional and must die within weeks, experiment toggles die with the experiment, ops toggles and kill switches may be permanent by design, and permission toggles belong in the authorisation model instead. Give every flag an owner and an expiry date, create the removal ticket at the same time as the flag, report on flags past expiry, and treat deleting the toggle and its dead branch as part of finishing the feature.

Pro How would you automate canary promotion, and what stops it?

Use a progressive delivery controller — Argo Rollouts or Flagger — that replaces the plain Deployment with a resource owning a scripted sequence of weight steps and pauses, with a metric analysis at each pause querying Prometheus, Datadog or a web endpoint. Define success conditions on error rate, latency percentiles and one business metric; a failed condition aborts and shifts traffic back to stable automatically. Compare the canary against a freshly-deployed baseline of the old version rather than the long-running fleet, so warm-cache and JIT differences are not blamed on your change. Use sticky assignment so one user does not flip versions mid-session, and keep an indefinite pause before the final step if you want a human on the last decision. The real value is that the stop threshold is agreed in advance instead of argued about during the incident.

Pro Why does dev/prod parity matter, and how do preview environments help?

Every strategy above assumes what you tested resembles what you shipped to. The twelve-factor argument is to shrink three gaps: time (deploy hours after writing, not weeks), personnel (the authors deploy it), and tools (the same database engine, broker and versions in every environment). Substituting backing services — an in-memory database in dev, a real one in production — produces bugs that are unreproducible by construction, because the difference is the bug. Ephemeral preview environments make parity practical: each pull request gets a temporary full deployment from that branch, reviewers exercise the real thing, integration tests run against real infrastructure, and the environment is destroyed on merge, so nobody nurses a long-lived staging that has drifted months away from production.
