Module: GitHub Actions

The previous module argued for fast feedback, quality gates and promotion. This one is where those arguments become YAML that actually runs — and where the difference between a pipeline that works and a pipeline that leaks your cloud account is about six lines of configuration.

Knowledge Library → Courses → DevOps and Deployment → GitHub Actions

What this module covers

GitHub Actions is the CI/CD engine built into GitHub: a workflow is a YAML file in .github/workflows/, GitHub watches for the events you declare, and runs your jobs on machines it provisions per run. Because it lives next to the code and the pull request, it has become the default pipeline for open source and for a large share of enterprise Java and Angular work.

The first half of this module is mechanics — the object model, triggers, expressions, matrices, caching, service containers and the two ways to share workflow code. The second half is the part interviewers actually probe: secrets and environments, least-privilege tokens, why you pin third-party actions to a commit SHA, and OIDC federation, which removes long-lived cloud credentials from your repository entirely. We finish by wiring the course's own Java service and Angular app into a real publishing pipeline, then survey Jenkins so you can read a Jenkinsfile and say honestly when a self-hosted controller is still the right answer.

Topics

The object model: workflow, job, step, action, runner

Five nouns carry the whole system. A workflow is one YAML file under .github/workflows/, triggered by events. It contains jobs. Each job is assigned a runner — a fresh virtual machine or container — and contains an ordered list of steps. A step either runs a shell command (run) or invokes an action (uses), which is a packaged, versioned unit of reusable behaviour published from a repository.

The single fact that explains most beginner confusion: jobs run in parallel on separate runners by default; steps run sequentially and share one filesystem and one workspace. Two steps in the same job can pass files by writing to disk. Two jobs cannot — different machines, different disks — so they need needs for ordering, job outputs for small values, and artifacts for files. Each job also starts from a clean machine, which is why actions/checkout is the first step of nearly every job you will ever write.

name: build
on: [push]
jobs:
  test:                      # job: gets its own runner
    runs-on: ubuntu-latest   # the runner label
    steps:
      - uses: actions/checkout@v4   # an action
      - run: mvn -B verify          # a shell command, same machine as the step above

Triggers: the on block, and the pull_request_target trap

The on key declares what starts a run. The four you will use constantly: push (optionally filtered by branches, tags and paths, which is how a monorepo avoids rebuilding everything), pull_request (validate the merge result before it lands, with types selecting opened/synchronize/reopened), workflow_dispatch (a manual Run workflow button, with typed inputs — the honest way to build a deploy button), and schedule (cron, in UTC, and best effort — GitHub delays scheduled runs under load, so never depend on exact firing times).

Now the trap. A pull_request run from a forked repository gets a read-only token and no access to secrets, deliberately, because the code being tested is a stranger's. pull_request_target exists to lift that restriction: it runs the workflow definition from the base branch but with full write permissions and secrets available. If you then check out and execute the pull request's code — ref: ${{ github.event.pull_request.head.sha }} followed by a build — you have handed a repository write token to anyone who can open a pull request. GitHub's own Security Lab named this the "pwn request". Use pull_request_target only for workflows that never execute contributor code (labelling, commenting, triage), and treat every value in the github context — branch names, titles, body text — as untrusted input, never interpolated directly into a run script.

on:
  push:
    branches: [main]
    paths: ['service/**']        # monorepo: only build what changed
  pull_request:
    types: [opened, synchronize, reopened]
  workflow_dispatch:
    inputs:
      environment:
        type: choice
        options: [staging, production]
  schedule:
    - cron: '17 2 * * *'         # UTC, best effort, not a guarantee

Jobs and steps: needs, if, uses vs run, and outputs

runs-on picks the runner label. needs turns the default parallel fan-out into a dependency graph — needs: [build] makes a job wait, and GitHub runs everything else concurrently. if gates a job or step on an expression; the crucial subtlety is that a job with any failed dependency is skipped unless you say otherwise, which is why the status functions exist: success() (the implicit default), always(), failure() and cancelled(). A "publish the test report even when tests failed" step is if: always(); a "notify Slack on red" job is if: failure().

A step is either uses (invoke an action, parameterised by with:) or run (execute a shell script, with the shell chosen by shell: and the working directory by working-directory:) — never both in one step. Values move outward in two hops: a step writes echo "name=value" >> $GITHUB_OUTPUT and a later step in the same job reads steps.<id>.outputs.name; a job declares outputs: mapping to a step output and a dependent job reads needs.<job>.outputs.name. env can be set at workflow, job or step scope, innermost winning. Expressions are written ${{ ... }} and read from contexts — github, env, vars, secrets, needs, steps, matrix, runner — and support functions like contains(), startsWith(), fromJSON() and hashFiles().

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.ver.outputs.version }}
    steps:
      - uses: actions/checkout@v4
      - id: ver
        run: echo "version=$(mvn -q help:evaluate -Dexpression=project.version -DforceStdout)" >> "$GITHUB_OUTPUT"
  publish:
    needs: [build]
    if: github.ref == 'refs/heads/main' && success()
    runs-on: ubuntu-latest
    steps:
      - run: echo "shipping ${{ needs.build.outputs.version }}"

Matrix builds: one job definition, many combinations

strategy.matrix expands a single job into one run per combination of the values you list — the classic being java: [17, 21] crossed with os: [ubuntu-latest, windows-latest], giving four parallel jobs from one definition. Inside the job, ${{ matrix.java }} selects the value for that run. This is how libraries prove they work across supported versions without four copies of the same YAML, and how a slow test suite is sharded across runners.

Two keys refine the product. include either adds extra properties to combinations that already match, or appends a whole new combination — the way you say "on Java 21 only, also publish coverage". exclude removes combinations that make no sense. The one to think about hardest is fail-fast, which defaults to true: the moment one combination fails, GitHub cancels every sibling. That saves minutes on a large matrix but destroys exactly the information you wanted — whether the bug is on all four platforms or only Windows. Set fail-fast: false on compatibility matrices, keep it on for shards where the first failure is enough. max-parallel throttles concurrency when the matrix would otherwise saturate your runner quota.

strategy:
  fail-fast: false          # see every combination's result, not just the first failure
  max-parallel: 4
  matrix:
    java: [17, 21]
    os: [ubuntu-latest, windows-latest]
    include:
      - java: 21
        os: ubuntu-latest
        coverage: true      # extra property on one existing combination
    exclude:
      - java: 17
        os: windows-latest

Caching: why a bad key is worse than no cache

Every job starts on a clean machine, so without a cache each run re-downloads the whole Maven or npm dependency tree. actions/cache fixes that: it restores a tarball at the start of the job and saves it at the end if the key was not already present. The design lives entirely in two fields. key is the exact identity of the cache entry and should be derived from the lockfile — hashFiles over your pom.xml or package-lock.json files — so that any dependency change produces a new key. restore-keys is an ordered list of prefixes tried when the exact key misses, giving you a near-miss cache from the previous dependency set that you then top up.

Get the key wrong and you have built something worse than no cache at all. A key that never changes (say, just maven-cache) is written once and restored forever: the entry is immutable after its first write, so your build keeps resolving against a stale dependency set, and a genuinely upgraded library is silently ignored until someone spends a day debugging it. A key that changes on every run — anything containing github.sha — never hits, so you pay the upload cost on every single build for zero benefit. Also know the scope rules: caches are keyed per branch, a branch can read caches from its base branch and from the default branch but not from sibling branches, and GitHub evicts entries unused for seven days as well as trimming the oldest once a repository exceeds its cache quota. For the common cases you often need none of this — actions/setup-java takes cache: maven and actions/setup-node takes cache: npm, and those built-ins already compute a correct lockfile-derived key.

- uses: actions/setup-java@v4      # built-in caching: correct key for free
  with:
    java-version: '21'
    distribution: temurin
    cache: maven

- uses: actions/cache@v4           # manual control, when you need it
  with:
    path: ~/.m2/repository
    key: ${{ runner.os }}-m2-${{ hashFiles('**/pom.xml') }}
    restore-keys: |
      ${{ runner.os }}-m2-

Service containers: real dependencies for integration tests

Unit tests need nothing; integration tests need a database, a broker, a cache. The services key starts Docker containers alongside the job on the same network, healthchecked, for the job's lifetime — a Postgres for repository tests, a Kafka or Redis for messaging tests. Steps running directly on the runner reach them on localhost via the ports you map; steps running inside a container job reach them by service label as hostname. GitHub tears them down when the job ends, so there is no cleanup to forget.

Worth knowing the alternative, because interviewers ask: on the JVM, Testcontainers starts the same dependencies from inside the test code, which means the identical setup runs on a developer laptop and in CI with no YAML duplication, and the version lives in the test rather than in the pipeline. Service containers win when the dependency must exist before your process starts, or when the same containers serve several steps; Testcontainers wins when you want laptop/CI parity. Either way, healthcheck options matter — without --health-cmd and friends, your first test can race a database that has not finished starting.

services:
  postgres:
    image: postgres:16
    env:
      POSTGRES_PASSWORD: test
    ports: ['5432:5432']
    options: >-
      --health-cmd pg_isready
      --health-interval 10s
      --health-retries 5

Reusable workflows vs composite actions

Copy-pasted YAML rots the same way copy-pasted code does. GitHub offers two ways to factor it out, and choosing between them is a genuine interview question. A reusable workflow is a whole workflow file declaring on: workflow_call with typed inputs, secrets and outputs; a caller invokes it as a job with uses: org/repo/.github/workflows/build.yml@v1. It can contain multiple jobs, choose its own runners, and use environment gates — because it is a workflow.

A composite action is a sequence of steps packaged behind an action.yml and dropped into an existing job with uses:. It has no jobs and no runner of its own; it runs on whatever machine the calling job already has. The rule of thumb: if you are sharing a piece of a job — the four steps that set up Java, restore the cache and log in to a registry — write a composite action. If you are sharing an entire pipeline shape, including which runners to use and how jobs depend on each other, write a reusable workflow. Practical limits to remember: nesting is capped (a caller chain up to four levels deep), a reusable workflow is called at job level so it cannot be one step among others, and secrets are either passed explicitly or forwarded wholesale with secrets: inherit — the convenient option that also widens the blast radius, so prefer naming them.

# .github/workflows/java-build.yml  (the reusable workflow)
on:
  workflow_call:
    inputs:
      java-version: { type: string, default: '21' }
    secrets:
      SONAR_TOKEN: { required: false }

# caller — invoked at JOB level, never as a step
jobs:
  build:
    uses: acme/ci-workflows/.github/workflows/java-build.yml@v1
    with: { java-version: '17' }
    secrets: { SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }} }

Secrets and environments: scope, masking, and deployment gates

Secrets are encrypted values injected as environment variables or step inputs, and they exist at three scopes: repository (available to that repo's workflows), organization (shared, with a repository access policy), and environment (available only to jobs that declare environment: production). Environment scope is the one that carries real security value, because it binds a credential to a protected deployment target rather than to the whole repository.

Understand precisely what masking does and does not buy you. GitHub redacts known secret values from log output, so an accidental echo prints asterisks. That is a guard against mistakes, not against malice: a workflow that runs with a secret in scope can base64 it, split it, or send it anywhere, and the redaction will not notice. The security boundary is therefore which jobs can see the secret, not the masking. This is exactly why environment secrets plus required reviewers are worth the setup: a GitHub Environment can require named approvers before the job starts, impose a wait timer, and restrict which branches may deploy to it — a genuine human gate that also produces an audit trail on the deployment record. Add concurrency with a per-environment group so two deploys never overlap, and prefer vars (unencrypted configuration) over secrets for anything that is merely environment-specific, so your secret list stays short enough to audit.

jobs:
  deploy:
    environment: production        # required reviewers + wait timer + branch policy apply here
    concurrency:
      group: deploy-production
      cancel-in-progress: false    # never cancel a deploy mid-flight
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh
        env:
          API_TOKEN: ${{ secrets.PROD_API_TOKEN }}   # environment-scoped secret

Least privilege: permissions, GITHUB_TOKEN and pinning to a SHA

Every run gets an automatically minted GITHUB_TOKEN, scoped to the repository and expired when the job ends. Its default permissions are set at the repository or organization level and have historically been generous. Declare permissions explicitly — an empty or read-only block at workflow level, then the narrowest additions per job that needs them (contents: write only on the release job, packages: write only on the publish job, id-token: write only where you request an OIDC token). A workflow-level declaration replaces the defaults entirely, so writing permissions: { contents: read } at the top is the single highest-value line in most pipelines.

The other half is supply chain. uses: some/action@v3 resolves a mutable Git tag: whoever controls that repository can repoint v3 at new code, and if their account is compromised, every workflow in the world using that tag executes the attacker's code on the next run with whatever token scope you granted. The 2025 tj-actions/changed-files compromise did exactly this and dumped runner memory — including secrets — into public build logs across thousands of repositories. Pin third-party actions to a full 40-character commit SHA (with the version in a trailing comment so humans can read it), let Dependabot raise the bumps, and consider an organization policy that only allows actions from GitHub, verified creators and an explicit allow-list. Pinning is not paranoia; it is the difference between reviewing a change and inheriting one.

permissions:
  contents: read              # workflow default: read-only, replaces repo defaults
jobs:
  release:
    permissions:
      contents: write         # widened only where genuinely needed
      packages: write
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2
      - uses: docker/build-push-action@ca877d9245402d1537745e0e356eab47c3520991  # v6.13.0

OIDC federation: deploying to the cloud with no stored keys

The old pattern stores a long-lived cloud access key as a repository secret. It works, and it is a standing liability: the key never expires, it is copied into every fork policy discussion and every audit, rotating it means coordinating across repositories, and anyone who exfiltrates it owns your cloud account until someone notices. OIDC federation removes it. GitHub runs an OpenID Connect identity provider; when a job declares permissions: id-token: write, it can request a short-lived, signed JWT from GitHub describing exactly who is asking — repository, ref, workflow, environment, and the sub claim that encodes them.

The cloud provider is configured to trust that issuer and to exchange such a token for temporary credentials. On AWS you create an IAM OIDC identity provider for token.actions.githubusercontent.com and a role whose trust policy conditions on aud = sts.amazonaws.com and on a sub that matches only the repository and ref you intend; aws-actions/configure-aws-credentials then performs AssumeRoleWithWebIdentity and the job holds credentials that expire in minutes. Azure and Google Cloud have the same shape with different names (federated credentials, Workload Identity Federation). The mistake to avoid is a sloppy trust condition: a sub wildcard like repo:acme/*, or worse a StringLike that matches any repository, hands your production role to anyone who can create a repo in scope. Pin the subject to repo:owner/name:ref:refs/heads/main or to repo:owner/name:environment:production, and let the GitHub Environment's reviewers gate who can trigger it.

{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:acme/orders-service:environment:production"
    }
  }
}

Publishing the stack: Java service and Angular app to GHCR

Time to assemble everything against this course's own stack. The shape that holds up in practice: a verify job that checks out, sets up Java with Maven caching, runs mvn -B verify against a Postgres service container and uploads the surefire report as an artifact; a parallel web job that sets up Node with npm caching and runs the Angular lint, unit tests in headless Chrome, and ng build --configuration production; then an images job with needs: [verify, web] that logs in to ghcr.io with the built-in GITHUB_TOKEN (this is the one place packages: write is granted), builds both container images with docker/build-push-action and Buildx layer caching, and pushes them tagged with the commit SHA plus a semantic version.

Two habits separate this from a demo pipeline. First, tag images with the immutable commit SHA, not only latest — the SHA is what makes a deployment reproducible and a rollback a one-line change, and docker/metadata-action generates the whole tag set from the triggering event. Second, keep deployment in its own job behind environment: production, authenticating by OIDC, so that promoting a build is a reviewed decision against an already-published artifact rather than a rebuild. GHCR images inherit the repository's visibility and permissions by default, so a private repo's images stay private, and Kubernetes pulls them with an image pull secret or a linked package permission.

images:
  needs: [verify, web]
  permissions: { contents: read, packages: write }
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: docker/setup-buildx-action@v3
    - uses: docker/login-action@v3
      with:
        registry: ghcr.io
        username: ${{ github.actor }}
        password: ${{ secrets.GITHUB_TOKEN }}
    - uses: docker/build-push-action@v6
      with:
        context: ./service
        push: true
        tags: ghcr.io/${{ github.repository }}/orders:${{ github.sha }}
        cache-from: type=gha
        cache-to: type=gha,mode=max

Jenkins survey: the Jenkinsfile, agents and shared libraries

Jenkins still runs an enormous amount of enterprise CI in India, so you should be able to read it fluently even if you never choose it for a greenfield project. A modern Jenkins pipeline is a Jenkinsfile in the repository using the declarative syntax: a top-level pipeline block containing agent (where it runs — any, a labelled node, or docker { image '...' }), environment, options, stages holding named stage blocks of steps, and post blocks (always, success, failure) for notification and cleanup. The older scripted syntax is raw Groovy and is now the escape hatch, reachable from declarative via a script block. The mapping to Actions is almost one to one: workflow to pipeline, job to stage, step to step, runner to agent, action to shared-library step or plugin.

The Jenkins answer to reuse is the shared library — a separate Git repository with vars/ and src/, loaded with @Library('platform-ci'), exposing custom steps so a hundred teams' Jenkinsfiles shrink to a few lines. It is more powerful than composite actions (it is real Groovy on the JVM) and correspondingly easier to turn into an unreviewable platform monolith. So when is a self-hosted controller still right? When builds must sit inside a private network with no egress to a hosted control plane; when regulation or a bank's policy requires the CI system and its audit trail on your own infrastructure; when you need exotic agents — mainframe, embedded hardware, licensed toolchains, GPU fleets you already own; when a decade of plugins and shared libraries encodes process you cannot rewrite this quarter; or when your source is not on GitHub at all. Otherwise the operational cost — patching the controller, curating plugin versions, keeping agents alive, owning the security of a system that holds every credential you have — usually argues for a managed runner and self-hosted runners only where the network demands it.

@Library('platform-ci') _
pipeline {
  agent { docker { image 'maven:3.9-eclipse-temurin-21' } }
  options { timestamps(); buildDiscarder(logRotator(numToKeepStr: '30')) }
  stages {
    stage('Build') { steps { sh 'mvn -B verify' } }
    stage('Publish') {
      when { branch 'main' }
      steps { publishImage repo: 'orders', tag: env.GIT_COMMIT }   // shared-library step
    }
  }
  post { failure { notifyTeam channel: '#ci-alerts' } }
}

Interview questions

GitHub Actions now appears in almost every Indian backend and full-stack round that touches DevOps — service companies ask the mechanics, product companies push straight to secrets, token scope and OIDC:

Beginner Explain workflow, job, step, action and runner.

A workflow is a YAML file in .github/workflows/ triggered by events. It contains jobs; each job is scheduled onto a runner, a fresh machine or container. A job contains ordered steps. A step either runs a shell command (run) or invokes an action (uses), an action being a packaged, versioned unit of reusable behaviour published from a repository.

Beginner Do jobs run in parallel or in sequence? How do you change it?

Jobs run in parallel on separate runners by default; steps within a job run sequentially on one machine. Add needs: [other-job] to force ordering. Because parallel jobs are different machines with different filesystems, they cannot share files implicitly — pass small values via job outputs and files via upload/download artifact actions.

Beginner What is the difference between uses and run?

run executes a shell command on the runner; uses invokes a published action, parameterised by with:. One step does one or the other, never both. Use actions for standard, reusable behaviour (checkout, language setup, registry login) and run for your own build commands.

Beginner Which triggers have you used, and what does workflow_dispatch give you?

push and pull_request for CI (filtered by branches and paths so a monorepo builds only what changed), schedule for nightly jobs (cron in UTC, best effort — it can be delayed), workflow_dispatch for manual runs with typed inputs, which is how you build a deploy button, and workflow_call to make the workflow reusable by others.

Beginner How does a step pass a value to a later step, and to a later job?

Within a job: give the step an id, write name=value to the $GITHUB_OUTPUT file, and read steps.<id>.outputs.name. Across jobs: declare outputs: at job level mapping to that step output, add needs: in the consumer, and read needs.<job>.outputs.name. Files go through upload-artifact and download-artifact instead.

Intermediate What does a matrix build do, and why would you set fail-fast: false?

strategy.matrix expands one job definition into one run per combination of the listed values, so you test Java 17 and 21 on Linux and Windows from a single block, with include and exclude refining the product. fail-fast defaults to true and cancels all siblings on the first failure — which hides whether the bug is platform-specific. Turn it off for compatibility matrices; leave it on for test shards where one failure is enough.

Intermediate Design a cache key for a Maven build. Why is a bad key worse than no cache?

Key on the lockfile: ${{ runner.os }}-m2- followed by ${{ hashFiles(...) }} over every pom.xml, with restore-keys: ${{ runner.os }}-m2- as the near-miss prefix. A constant key is written once and immutable thereafter, so the build silently keeps resolving a stale dependency set even after an upgrade — a real correctness bug, not just a slow build. A key containing the commit SHA never hits, so you pay the save cost every run for nothing. Easiest correct answer: use cache: maven on actions/setup-java, which computes the key for you.

Intermediate Reusable workflow or composite action — how do you choose?

A composite action packages a sequence of steps behind an action.yml and runs inside a job you already have, on that job's runner. A reusable workflow is a whole workflow with on: workflow_call, invoked at job level, and it can define multiple jobs, pick its own runners and use environment gates. Share a piece of a job with a composite action; share an entire pipeline shape with a reusable workflow. Nesting is limited to a four-level call chain.

Intermediate How do you run integration tests that need Postgres and Kafka?

Either the services key, which starts healthchecked Docker containers on the job's network for the job's lifetime and exposes them on localhost, or Testcontainers from inside the test code. Service containers suit dependencies that must exist before your process starts and are shared across steps; Testcontainers gives identical setup on a laptop and in CI with the versions pinned in the test rather than in YAML. Always configure healthchecks so the first test does not race a database that is still starting.

Intermediate Secrets are masked in logs. Does that make them safe?

No. Masking redacts known secret values from log output, which protects against accidental printing. It cannot stop a workflow that has the secret in scope from encoding it, splitting it or sending it to an external host. The real boundary is which jobs can see the secret at all — so scope credentials to a GitHub Environment protected by required reviewers rather than making them repository-wide, and prefer OIDC so there is no long-lived secret to steal.

Intermediate How would you add a human approval gate before a production deploy?

Create a GitHub Environment named production with required reviewers, optionally a wait timer, and a branch policy restricting which refs may deploy to it. Put the deploy job behind environment: production: it pauses until an approver acts, the credential is environment-scoped so only that job can read it, and the approval is recorded on the deployment for audit. Add a concurrency group so two deploys to the same environment never overlap.

Pro Why pin third-party actions to a commit SHA instead of a tag?

A tag is a mutable pointer. Whoever owns the action repository — or whoever compromises that account — can repoint v3 at new code, and every workflow using the tag executes it on the next run with whatever token scope you granted. That is not hypothetical: the 2025 tj-actions/changed-files compromise dumped runner memory including secrets into public logs across thousands of repositories. Pin to the full 40-character SHA with the version in a trailing comment, let Dependabot propose bumps so you review each change, and restrict allowed actions at organization level.

Pro Explain OIDC federation for cloud deploys. What does it replace and how does the trust work?

It replaces long-lived cloud access keys stored as repository secrets. GitHub runs an OIDC identity provider; a job with permissions: id-token: write requests a short-lived signed JWT whose claims identify the repository, ref, workflow and environment. The cloud provider trusts that issuer and exchanges the token for temporary credentials — on AWS, an IAM OIDC provider for token.actions.githubusercontent.com plus a role whose trust policy conditions on the aud and on a sub matching exactly repo:owner/name:environment:production, then AssumeRoleWithWebIdentity. Nothing long-lived is ever stored, and credentials expire in minutes.

Pro What is a pwn request, and how do you avoid it?

pull_request runs from forks get a read-only token and no secrets, by design. pull_request_target runs the base branch's workflow with write permissions and secrets available. If such a workflow checks out and builds the pull request head, any stranger who opens a PR executes code with a write token — that is the pwn request. Use pull_request_target only for workflows that never run contributor code (labelling, triage, comments), never check out the untrusted ref in it, and treat every github context value as untrusted input rather than interpolating it into a shell script.

Pro Your pipeline is green but takes 25 minutes. How do you attack it?

Measure first from the run timeline, then: split sequential stages into parallel jobs and keep needs only where a real dependency exists; cache dependencies on a lockfile-derived key and enable Buildx layer caching for images; shard the test suite across a matrix; run the slow suites (end-to-end, security scans) only on main or nightly while pull requests get the fast gate; use path filters so unrelated modules do not rebuild; add concurrency with cancel-in-progress so superseded pull request runs stop immediately; and size runners up where the job is genuinely CPU-bound.

Pro Map GitHub Actions onto Jenkins, and say when you would still choose Jenkins.

Workflow maps to pipeline, job to stage, step to step, runner to agent, action to a shared-library step or plugin, and on: to build triggers. A declarative Jenkinsfile has pipeline { agent … environment … stages { stage { steps } } post { } }, with shared libraries in vars/ and src/ as the reuse mechanism. Choose a self-hosted controller when builds must run inside a closed network, when regulation requires the CI system and its audit trail on your own infrastructure, when you need exotic or licensed agents, when a decade of plugins encodes process you cannot rewrite, or when the source is not on GitHub. Otherwise the cost of patching the controller, curating plugins and securing a system that holds every credential usually argues for managed runners.

Pro How do you make GITHUB_TOKEN least-privilege, and what breaks if you forget?

Declare permissions: { contents: read } at workflow level — that replaces the repository defaults outright — then widen per job: packages: write only on the publish job, contents: write only on the release job, id-token: write only where OIDC is requested, pull-requests: write only where a bot comments. Forget it and every job in the workflow, including any third-party action you invoke, runs with a token that can push commits, publish packages and edit issues — so one compromised dependency becomes repository write access. A useful side note: pushes made with GITHUB_TOKEN deliberately do not trigger further workflows, which prevents infinite loops but surprises people building release automation.
