Module: Gradle

Maven hands you a fixed lifecycle and asks you to fit inside it. Gradle hands you a programmable task graph and asks you to be disciplined with it. That trade — flexibility bought with predictability — explains almost everything about how Gradle behaves, and every mistake teams make with it.

Knowledge Library → Courses → DevOps and Deployment track → Gradle

What this module covers

Gradle is a build tool whose build file is a real program. Instead of declaring a POM that a fixed lifecycle interprets, you write Kotlin (or Groovy) that configures a graph of tasks, which Gradle then orders and executes. That gives you flexibility Maven cannot reach, and it gives you a whole class of failures Maven cannot have — build logic that runs at the wrong time, tasks whose inputs are not declared, caches that miss because the build script read an environment variable behind Gradle's back.

The first half of this module is the model: the build script and its plugins block, the two phases that trip everyone up, tasks as a directed acyclic graph with declared inputs and outputs, the dependency configurations that replaced Maven's scopes, and how multi-project builds are wired together. The second half is where Gradle actually earns its place — the daemon, incremental builds, the build cache, the configuration cache that Gradle 9 made the preferred execution mode, version catalogs and the wrapper — and closes with an honest comparison against Maven. Everything here assumes Gradle 9 or later and the Kotlin DSL.

Topics

The build script: build.gradle.kts, the plugins block, and Kotlin vs Groovy DSL

A Gradle build is described by scripts, not by a schema. settings.gradle.kts defines the build (its name and its subprojects) and build.gradle.kts configures one project inside it. The Kotlin DSL (.gradle.kts) is the current default for new builds and the one to learn: it is statically typed, so your IDE gives you real completion and click-through into plugin APIs, and typos fail at script-compile time rather than at task-execution time. The older Groovy DSL (build.gradle) is dynamically typed and still very common in existing codebases and in most tutorials written before roughly 2021 — you must be able to read both, and Gradle happily runs a build with a mix of the two.

Almost every build starts with the plugins {} block, and it is deliberately restricted: it must be the first block in the script, it takes only literal plugin ids and versions, and it cannot contain arbitrary logic. That restriction is what lets Gradle resolve plugins before the script is compiled and, later, what lets the configuration cache reason about the build. Applying a plugin is what creates tasks and extensions — java gives you compileJava, test, jar and the source sets; the Spring Boot plugin adds bootRun and bootJar. Understand that a Gradle build has almost no behaviour of its own: nearly everything you use is contributed by a plugin.

plugins {                                   // must come first, literal ids only
    java
    id("org.springframework.boot") version "3.5.0"
    id("io.spring.dependency-management") version "1.1.7"
}

group = "com.acme"
version = "1.4.0"

java {
    toolchain { languageVersion = JavaLanguageVersion.of(21) }   // build with a pinned JDK
}

repositories { mavenCentral() }

The two-phase model: configuration versus execution

This is the single concept that separates people who use Gradle from people who fight it. A Gradle build runs in three stages: initialization (read settings.gradle.kts, work out which projects exist), configuration (evaluate every build script from top to bottom, building the in-memory task graph), and execution (run the tasks actually needed for the requested goal, in dependency order). Configuration evaluates every project's script on every invocation, whatever you asked for. Running ./gradlew help still configures the whole build.

The consequence is the classic Gradle bug: code written at the top level of a build script is configuration-time code. A stray println, a file read, a shell-out to git rev-parse, or a database check placed directly in the script body runs on every single build — including builds that execute none of your tasks — and it runs even when the task it "belongs to" is up to date. Work belongs inside a task action (doLast { }) or, better, behind a lazy provider so it is only computed if something asks for it. Gradle's own best-practice guidance pushes the same way: use the lazy configuration APIs (tasks.register rather than tasks.create, Property and Provider rather than plain fields) so configuration stays cheap and the configuration cache can serialise it.

println("this runs at configuration time, on EVERY build")       // almost always a mistake

tasks.register("stamp") {
    val out = layout.buildDirectory.file("stamp.txt")            // lazy: no work yet
    outputs.file(out)
    doLast {                                                     // runs only if the task runs
        out.get().asFile.writeText("built ${'$'}{project.version}")
    }
}

Tasks: the directed acyclic graph, dependsOn, inputs and outputs

A task is the unit of work, and the set of tasks plus their dependencies forms a directed acyclic graph. You never tell Gradle the order to run things in; you declare relationships and Gradle derives the order. dependsOn is the coarse hammer ("run that before this"). Most real dependencies are implicit and better: if task B's input is task A's output, Gradle infers the edge itself, which is why wiring tasks by files and providers rather than by name is the recommended style. There is also ordering that is not dependency — mustRunAfter and shouldRunAfter constrain order without forcing execution — and cycles are a hard error, hence "acyclic".

The property that makes Gradle fast is that every task declares its inputs and outputs. Before running a task Gradle hashes the declared inputs (source files, classpath, properties, the task's own implementation) and compares them against the snapshot from last time; if nothing changed and the outputs are still there, the task is skipped and reported UP-TO-DATE. Some tasks go further and are incremental — given the set of changed input files they recompile only what is affected. Undeclared inputs are the root of nearly every "it works on my machine but CI rebuilt everything" complaint: if a task reads a file it never declared, Gradle cannot see the change, and the task is wrongly skipped or wrongly rerun. Use --scan or -i to see exactly why a task ran.

val generateVersionFile by tasks.registering {
    val version = project.version.toString()          // captured, not read at execution time
    val outDir = layout.buildDirectory.dir("generated/version")
    inputs.property("version", version)               // declared input  -> part of the hash
    outputs.dir(outDir)                               // declared output -> enables up-to-date
    doLast { outDir.get().file("version.txt").asFile.writeText(version) }
}

tasks.named<org.gradle.api.tasks.bundling.Jar>("jar") {
    from(generateVersionFile)                         // implicit dependency, inferred from the output
}

Dependency configurations: implementation vs api, and the rest

Maven has five scopes attached to a dependency. Gradle has configurations, which are named buckets of dependencies with declared roles — some you declare into, some are resolved into a classpath, some are what your project exposes to consumers. The java and java-library plugins give you the set you use every day: implementation (needed to compile and to run, but not exposed to consumers), api (needed to compile and leaks onto the consumer's compile classpath — java-library plugin only), compileOnly (compile classpath only, absent at runtime — annotations, provided servlet APIs), runtimeOnly (runtime only, never on the compile classpath — JDBC drivers, logging backends), testImplementation and testRuntimeOnly for the test source set, and annotationProcessor for processors such as Lombok or MapStruct that must run during compilation but never ship.

implementation versus api is the most-asked Gradle interview question and it is genuinely about build performance, not aesthetics. If library A declares Guava as api, every consumer of A gets Guava on its compile classpath, can import it accidentally, and — this is the expensive part — must be recompiled whenever Guava's ABI changes, because it might be using it. If A declares Guava as implementation, Guava is still there at runtime but not on any consumer's compile classpath, so a change inside A that does not alter A's own public API recompiles A and nothing else. In a large multi-project build this is the difference between a two-minute and a twenty-minute incremental build. The rule: use implementation by default; use api only when a type from that dependency genuinely appears in your public signatures.

dependencies {
    api("com.google.guava:guava:33.4.0")                    // Guava types appear in MY public API
    implementation("org.apache.commons:commons-lang3:3.17.0") // internal only; consumers never see it
    compileOnly("org.projectlombok:lombok:1.18.36")           // compile-time only, not packaged
    annotationProcessor("org.projectlombok:lombok:1.18.36")   // the processor itself
    runtimeOnly("org.postgresql:postgresql:42.7.4")           // driver: loaded, never imported
    testImplementation("org.junit.jupiter:junit-jupiter:5.11.4")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

Multi-project builds, settings.gradle.kts and convention plugins

A Gradle build is one build containing one or more projects. settings.gradle.kts at the root is the entry point: it names the build and calls include(":app", ":domain", ":infra") to declare subprojects, each of which may have its own build.gradle.kts. Subprojects depend on each other with implementation(project(":domain")), and Gradle wires the task graphs together — asking for :app:test builds whatever of :domain is needed, in parallel where the graph allows, with the same up-to-date and caching machinery applied per project.

The real question in a multi-project build is where shared configuration lives. The old habit — a root subprojects { } or allprojects { } block that reaches into every child — is now discouraged: it couples every project to the root script, defeats parallel configuration, and is hostile to both the configuration cache and isolated projects. The recommended replacement is a convention plugin: a small precompiled script plugin (for example buildSrc/src/main/kotlin/acme.java-conventions.gradle.kts, or a plugin in a separate build-logic project pulled in with includeBuild) that each subproject applies explicitly by id. Note that buildSrc is built before anything else and any change to it invalidates the whole build, which is why larger repositories prefer an included build-logic build.

// settings.gradle.kts
rootProject.name = "orders"
includeBuild("build-logic")            // convention plugins live in their own build
include(":app", ":domain", ":infra")

// domain/build.gradle.kts
plugins { id("acme.java-conventions") }   // shared config applied explicitly, not injected

// app/build.gradle.kts
dependencies { implementation(project(":domain")) }

The daemon, incremental builds and the wrapper

Every Gradle invocation talks to a long-lived background JVM called the daemon. It exists because starting a JVM, loading Gradle and warming up the JIT costs seconds you would otherwise pay on every command; the daemon pays that once and then keeps hot caches, a warm compiler and in-memory file hashes between builds. It is on by default and you should leave it on — the honest measure of a Gradle build is the second run, not the first. Daemons are matched by JVM version and JVM arguments, so a build that keeps changing org.gradle.jvmargs will keep spawning fresh daemons and lose the benefit. Add org.gradle.parallel=true so independent projects execute concurrently, and consider --configuration-cache and configure-on-demand for very large builds.

The wrapper (gradlew, gradlew.bat, and gradle/wrapper/gradle-wrapper.properties) is checked into the repository and downloads the exact Gradle version the build was written for. Everyone — laptops, CI, the new joiner on day one — then runs the same Gradle, and upgrading is a one-line commit (./gradlew wrapper --gradle-version 9.x). Never invoke a locally installed gradle in CI; always use ./gradlew. Because the wrapper downloads a binary, verify the distribution checksum (distributionSha256Sum) in supply-chain-sensitive repositories.

# gradle.properties — checked in, applies to every developer and CI
org.gradle.parallel=true
org.gradle.caching=true
org.gradle.configuration-cache=true
org.gradle.jvmargs=-Xmx4g -XX:MaxMetaspaceSize=1g

# upgrade the wrapper, then commit gradlew + gradle/wrapper/*
# ./gradlew wrapper --gradle-version 9.1.0

The build cache: local, remote, and why it beats up-to-date checks

An up-to-date check only helps if this directory already contains the result. The build cache generalises it: for every cacheable task Gradle computes a hash of the task's inputs, its implementation and its output properties, and stores the outputs under that key. Ask for the same task with the same inputs again — after a clean, on a different branch, on a colleague's laptop, on a fresh CI agent — and Gradle unpacks the stored outputs instead of doing the work, reporting the task FROM-CACHE. Enable it with org.gradle.caching=true.

There are two layers. The local cache is a directory in your Gradle home and mostly rescues you from your own clean builds and branch switching. The remote cache is a shared HTTP-backed node (self-hosted, or Develocity) that CI populates and everyone reads, which is where the large wins live: a developer pulls the outputs of tasks a CI machine already ran. The catch is correctness — caching amplifies any task whose inputs are not fully declared, and non-reproducible outputs (embedded timestamps, absolute paths, non-deterministic ordering) mean cache keys that never match. Cache misses are a debugging skill: a build scan comparing two builds tells you which input differed.

The configuration cache: Gradle 9's preferred execution mode

The build cache skips execution. The configuration cache skips configuration. Recall that Gradle evaluates every build script on every invocation; on a large repository that alone can cost several seconds before a single class is compiled. The configuration cache serialises the fully configured task graph — the tasks, their configured state, and the values they captured — to disk, keyed on the things configuration depended on: the build scripts themselves, system properties, environment variables, files read at configuration time, and the requested tasks. A subsequent build with the same key skips initialization and configuration entirely and goes straight to execution. It also enables more parallelism, because a cached graph can be executed without re-evaluating scripts. Gradle 9 enables it by default and the Gradle team now describe it as the preferred mode of execution.

The price is constraints on build logic, and these are what interviewers probe. Task actions may not reach back into the Project object at execution time (no project.property(...), no project.file(...) inside doLast) — capture what you need at configuration time into a Property or Provider. Shared mutable state between tasks is out; undeclared reads of environment variables or system properties must go through providers.environmentVariable(...) and providers.systemProperty(...) so Gradle can track them as cache inputs. Everything stored in the graph must be serialisable. Legacy plugins that violate these rules are the usual blocker, so the migration path is incremental: run with --configuration-cache, read the HTML problems report it generates, and fix or replace offenders one at a time.

// Configuration-cache friendly: read through providers, capture into the task
val gitSha = providers.environmentVariable("GIT_COMMIT").orElse("local")

tasks.register("banner") {
    val sha = gitSha                      // captured value, tracked as a cache input
    val target = layout.buildDirectory.file("banner.txt")
    outputs.file(target)
    doLast {
        // NOT allowed here: project.property(...), project.file(...), task.project
        target.get().asFile.writeText("build ${'$'}{sha.get()}")
    }
}

Version catalogs: libs.versions.toml as the single source of dependency truth

Hard-coded version strings scattered across twenty build.gradle.kts files is the Gradle equivalent of Maven's problem before dependencyManagement — and the fix is the version catalog. Declare libraries, versions, plugins and bundles once in gradle/libs.versions.toml, and every project refers to them with type-safe accessors that the Kotlin DSL generates: implementation(libs.spring.boot.starter.web). The IDE completes them, a typo fails at compile time, and upgrading a library is a one-line change in one file. [bundles] group libraries that always travel together; [plugins] centralises plugin versions so the plugins block reads alias(libs.plugins.spring.boot).

Know how a catalog differs from a BOM, because interviewers ask. A version catalog is a build-time convenience: it tells your build which versions to declare, and it disappears from the published metadata. A platform or BOM (implementation(platform("..."))) is a resolution-time constraint that also applies to transitive dependencies and is published with your artifact. They compose well — the catalog names the Spring Boot BOM, and the BOM then aligns every transitive version. Catalogs also make automated upgrade bots trivial to review, since every bump is a diff in one small TOML file.

# gradle/libs.versions.toml
[versions]
springBoot = "3.5.0"
junit = "5.11.4"

[libraries]
spring-boot-starter-web = { module = "org.springframework.boot:spring-boot-starter-web", version.ref = "springBoot" }
junit-jupiter = { module = "org.junit.jupiter:junit-jupiter", version.ref = "junit" }

[bundles]
testing = ["junit-jupiter"]

[plugins]
spring-boot = { id = "org.springframework.boot", version.ref = "springBoot" }
plugins { alias(libs.plugins.spring.boot) }

dependencies {
    implementation(libs.spring.boot.starter.web)   // type-safe accessor, completed by the IDE
    testImplementation(libs.bundles.testing)
}

Maven versus Gradle: an honest comparison

Neither tool is a mistake, and a candidate who says "Gradle is just better" is showing inexperience. Maven's fixed lifecycle and XML POM make every Maven project look the same: a new engineer can read any POM on day one, tooling can analyse it without executing it, and the build is boring in the way infrastructure should be. Gradle's programmable graph makes the easy things slightly harder and the hard things possible — custom packaging, code generation, polyglot builds, Android — and its caching story (incremental tasks, build cache, configuration cache) is genuinely ahead. Maven 4 narrows several of these gaps, and Maven's build/consumer POM split addresses some long-standing complaints, so treat the comparison as a moving target.

The pragmatic reading: Gradle repays you on large multi-project repositories, on teams that need custom build logic, and anywhere build time is a daily tax; Maven repays you on straightforward JVM services, in teams with high churn, and in organisations that value uniformity over speed. The decisive risk with Gradle is not the tool but the discipline — an undisciplined Gradle build (logic in the root script, undeclared task inputs, plugins that break the configuration cache) is slower and less predictable than the Maven build it replaced.

Interview questions

Gradle questions in Indian product and service-company rounds cluster hard around two things — implementation vs api, and "why would you pick Gradle over Maven" — with the phase model and the caches as the follow-ups that separate users from operators:

Beginner What is Gradle and how does its build file differ from a Maven POM?

Gradle is a JVM build automation tool. A Maven POM is declarative XML data interpreted by a fixed lifecycle; a Gradle build file is a Kotlin or Groovy script that executes and programmatically configures a graph of tasks. That means Gradle can express arbitrary build logic, but it also means you cannot fully understand a Gradle build without running it.

Beginner What is the Gradle wrapper and why is it committed to the repository?

gradlew, gradlew.bat and gradle/wrapper/gradle-wrapper.properties. The wrapper downloads and runs the exact Gradle version the build was written for, so every developer, every CI agent and every new joiner runs the same build with no local installation. Upgrading is one commit. In CI you should always invoke ./gradlew, never a preinstalled gradle.

Beginner What does the plugins block do, and why is it restricted?

It applies plugins, which is what actually creates tasks and extensions — the java plugin contributes compileJava, test and jar; Spring Boot's plugin adds bootJar. It must appear first and accepts only literal plugin ids and versions so Gradle can resolve plugins before compiling the script, which also keeps the build analysable for the configuration cache.

Beginner Kotlin DSL or Groovy DSL — which should a new project use?

Kotlin DSL (build.gradle.kts). It is the current default for new builds: statically typed, so the IDE gives real completion and navigation into plugin APIs, and errors surface when the script compiles rather than mid-build. Groovy DSL is still everywhere in existing repos and older tutorials, so you must be able to read it; script compilation for Kotlin is slightly slower on a cold build, which the daemon and caches absorb.

Intermediate Explain implementation vs api. Why does it matter for build time?

Both put the dependency on your own compile and runtime classpath. api additionally exposes it on the compile classpath of everyone who depends on you; implementation does not. Consequence: with api, an ABI change in that dependency (or in your module) forces recompilation of every downstream module, because they might be using it. With implementation, changes that do not alter your own public API recompile only your module. On a large multi-project build that is the difference between a couple of minutes and twenty. Default to implementation; use api only when the dependency's types appear in your public signatures. api requires the java-library plugin.

Intermediate compileOnly, runtimeOnly and annotationProcessor — when do you use each?

compileOnly for things needed to compile but provided at runtime by the environment or not needed at all — Lombok's annotations, a container-provided servlet API. runtimeOnly for things loaded reflectively and never imported — JDBC drivers, a logging backend — which also keeps them off the compile classpath so nobody imports them by accident. annotationProcessor for processors that must run during compilation (Lombok, MapStruct, Spring's configuration-metadata processor) but must never be packaged.

Intermediate Why does a println at the top of build.gradle.kts run even for an unrelated task?

Because it is configuration-time code. Gradle evaluates every project's build script on every invocation to construct the task graph, before deciding what to execute. So top-level statements run on every build, including ./gradlew help, and regardless of whether the surrounding task is up to date. Real work belongs inside a task action (doLast) or behind a lazy Provider, and tasks should be registered with tasks.register rather than eagerly created.

Intermediate How does Gradle decide a task is UP-TO-DATE?

Each task declares inputs (files, properties, classpath, and the task implementation itself) and outputs. Before executing, Gradle hashes the declared inputs and compares them with the snapshot from the previous run, also checking the outputs still exist and are unchanged. Match means skip. The failure mode is undeclared inputs: if a task reads something it never declared, Gradle cannot see the change and wrongly skips the task. Use -i or a build scan to see why a task ran.

Intermediate Build cache versus configuration cache — what does each actually cache?

Different phases. The build cache stores task outputs keyed by a hash of the task's inputs, so a task can be satisfied from cache after a clean, on another branch, or on another machine (a task shows as FROM-CACHE); it has local and remote layers. The configuration cache stores the configured task graph keyed on build scripts, system properties, environment variables and files read during configuration, so Gradle can skip initialization and configuration entirely and go straight to execution. They are complementary and usually both enabled.

Intermediate What problem do version catalogs solve, and how do they differ from a BOM?

A catalog (gradle/libs.versions.toml) centralises library, plugin and bundle coordinates so every project declares libs.spring.boot.starter.web instead of a hard-coded string, with IDE completion and one place to bump versions. It is a build-time convenience and does not appear in your published metadata. A BOM or platform is a resolution-time constraint that also governs transitive dependencies and is published. They are complementary: the catalog names the BOM, the BOM aligns the transitive graph.

Pro Maven or Gradle for a new microservice at your company — argue both sides.

Maven: uniform and boring, readable by anyone on day one, analysable without executing it, minimal ways for a team to hurt itself, and Maven 4 has closed several old gaps — the right default for a straightforward service in an organisation with many teams and high churn. Gradle: substantially faster on incremental and repeat builds thanks to task-level up-to-date checks plus the build and configuration caches, and able to express custom build logic through convention plugins — the right default for large multi-project repositories, Android, and anywhere build time is a daily tax. The deciding factor is usually the team, not the tool: an undisciplined Gradle build is slower and far less predictable than the Maven build it replaced.

Pro What constraints does the configuration cache put on build logic, and how do you migrate?

Task actions may not access the Project object at execution time — no project.file(...) or project.property(...) inside doLast; capture values at configuration time into Property/Provider fields. Environment variables and system properties must be read through providers.environmentVariable(...) / providers.systemProperty(...) so Gradle tracks them as cache inputs. No shared mutable state between tasks, and everything stored in the graph must be serialisable. Migrate incrementally: turn it on, read the HTML problems report Gradle emits, fix your own tasks, and upgrade or replace third-party plugins that violate the rules. Gradle 9 enables it by default and treats it as the preferred execution mode.

Pro Your root build script uses subprojects { }. Why is that now discouraged, and what replaces it?

Cross-project configuration couples every subproject to the root script: you cannot read a subproject's build in isolation, configuration cannot be parallelised safely, and it conflicts with the configuration cache and isolated projects. The replacement is a convention plugin — a precompiled script plugin in buildSrc or, better for large repos, in a separate build-logic build pulled in with includeBuild — which each subproject applies explicitly by id. Explicit application also makes it obvious what configuration a module actually has. Note that any change to buildSrc invalidates the whole build, which is the main argument for the included-build variant.

Pro CI never gets build cache hits even though caching is enabled. How do you debug it?

Cache keys are hashes of task inputs, so a miss means some input differs. Usual culprits: absolute paths or machine-specific values baked into inputs, a different JDK or Gradle version, timestamps or non-deterministic ordering inside produced archives (fix with reproducible archive settings), environment variables read at configuration time that differ per agent, and a task that is simply not cacheable. Debug by running a build scan on both builds and comparing the task input hashes to find the first differing property, and check whether the remote cache is configured for push from CI and pull from developers.

Pro How do dependsOn, mustRunAfter and finalizedBy differ, and which should you reach for?

dependsOn is a real dependency: requesting the task forces the other to run first. mustRunAfter and shouldRunAfter only constrain ordering if both tasks are already in the graph — they never pull a task in; shouldRunAfter is a hint Gradle may drop to break a cycle. finalizedBy schedules a task to run after another finishes, including on failure, which is how report and cleanup tasks are wired. Prefer none of them where possible: wire tasks by files and providers so Gradle infers the dependency from an output feeding an input, which stays correct when tasks are added or renamed.
