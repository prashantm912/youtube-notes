Module: Kubernetes Fundamentals

Kubernetes looks like a hundred unrelated concepts until you see the one idea underneath all of them: you write down the state you want, and a crowd of small controllers spends forever making reality match it. Learn the reconciliation loop and the rest is variations on a theme.

Knowledge Library → Courses → DevOps and Deployment track → Kubernetes Fundamentals

What this module covers

Docker gives you one container on one machine. Kubernetes is what you reach for when there are forty containers across a dozen machines, they need to find each other, survive node failures, roll out new versions without downtime, and do all of it while you sleep. It is a cluster operating system: you hand it a fleet of machines and a description of what should be running, and it works out the placement, the restarts, the routing and the replacement.

This module covers the mental model and the vocabulary. First the architecture — what the control plane actually consists of, what runs on every node, and how the declarative model plus the reconciliation loop turns "here is my YAML" into "this is now true and stays true". Then the workload objects bottom-up: Pods, ReplicaSets, Deployments, Services, namespaces, and the labels and selectors that wire them together. It closes with kubectl fluency, because in an interview and in an incident the difference between knowing Kubernetes and being useful at Kubernetes is which commands you reach for first. Production concerns — probes, resource limits, autoscaling, Ingress, RBAC and Helm — are the next module.

Topics

Cluster architecture: the control plane and the worker nodes

A Kubernetes cluster is two populations of processes. The control plane holds the cluster's brain and its memory: kube-apiserver is the front door and the only component that ever talks to etcd; etcd is the consistent key-value store holding every object in the cluster; kube-scheduler watches for Pods with no node assigned and picks one for them; kube-controller-manager runs the built-in controllers (node, replication, endpoints, service-account and more) in a single binary; and cloud-controller-manager, where present, holds the provider-specific logic that talks to a cloud's load balancers, routes and node metadata so the rest of Kubernetes stays vendor-neutral.

The "only the API server talks to etcd" rule is the architectural keystone, and it is worth being able to say out loud. It means every read and write in the cluster passes one place that can authenticate it, authorise it, validate it, apply admission control to it and version it. Every other component — schedulers, controllers, kubelets, your kubectl, third-party operators — is just a client of that one API, watching for changes and reacting. That is why extending Kubernetes with a custom controller feels natural rather than invasive: you are not plugging into a framework, you are joining a crowd of peers that all read and write the same API. Worker nodes are the machines that actually run your containers, and a node in a managed cluster is typically a plain virtual machine registered with the API server.

The declarative model and the reconciliation loop

This is the single idea that makes Kubernetes make sense. You do not issue commands like "start three copies of this". You submit an object describing the state you want — three replicas of this image — and Kubernetes stores it. A controller then runs a loop forever: read desired state, observe actual state, compute the difference, take one step to close it, repeat. Nobody told the system to restart a crashed Pod; the replica count simply stopped matching, and the controller did what it always does. The imperative alternative ("run this, then check, then react") is what you would otherwise write yourself, badly, in a shell script that stops running when your laptop closes.

Two consequences fall out of this and both show up in interviews. First, the loop never ends: Kubernetes is not a deployment tool that finishes, it is a control system that keeps converging, which is why deleting a Pod that belongs to a Deployment gets you a new Pod within seconds rather than an empty slot. Second, every object carries both a spec and a status — spec is what you asked for, status is what the controller most recently observed — and reading the gap between them is how you debug almost anything. Controllers are level-triggered rather than edge-triggered: they act on the current state of the world, not on the event that woke them up, so a missed event is not a lost update, just a slightly later correction.

Node components: kubelet, kube-proxy and the container runtime

Three things run on every worker node. The kubelet is the node's agent: it watches the API server for Pods assigned to its node, tells the container runtime to start them, mounts their volumes, runs their probes and reports status back. It manages containers that Kubernetes created and deliberately ignores containers started by other means. kube-proxy maintains the network rules that make Service virtual IPs work on that node — traditionally iptables rules, increasingly IPVS or an eBPF dataplane supplied by a CNI plugin that replaces kube-proxy entirely. The container runtime does the actual work of pulling images and running containers.

On the runtime, know the history because it still gets asked. The kubelet talks to runtimes through the Container Runtime Interface (CRI), a gRPC contract. Docker Engine did not implement CRI, so Kubernetes shipped an adapter called dockershim; it was deprecated in v1.20 and removed in v1.24, and it is long gone from every supported release today. The standard runtime is now containerd (which Docker itself uses underneath), with CRI-O as the other common choice. Nothing about this affects your images: Docker builds OCI images, Kubernetes runs OCI images, and "Kubernetes dropped Docker" only ever meant it dropped one shim, never the image format.

The API object model: apiVersion, kind, metadata, spec, status

Everything in Kubernetes is an object in the same API, and every object has the same four top-level fields. apiVersion names the API group and version the object belongs to (v1 for the core group, apps/v1 for Deployments, networking.k8s.io/v1 for Ingress) — a mismatch here is the most common "error validating data" a beginner hits. kind is the object type. metadata carries the name, the namespace, labels, annotations, the UID and the owner references that let garbage collection clean up children when a parent is deleted. spec is your desired state; status is written by the controller and is read-only to you.

Learning this shape once pays off everywhere, because it is the same shape for a Pod, a Service, a CustomResourceDefinition and any operator's custom resource. It is also why you should learn kubectl explain early: it walks the live API schema of the cluster you are connected to, so kubectl explain deployment.spec.strategy answers a field question authoritatively without a browser. Prefer keeping manifests in Git and applying them declaratively with kubectl apply; imperative kubectl create and kubectl run are for scratch experiments, and their best use in real work is generating a starting manifest with --dry-run=client -o yaml.

apiVersion: apps/v1        # API group + version — must match the kind
kind: Deployment           # what type of object this is
metadata:
  name: orders             # unique within its namespace + kind
  namespace: shop
  labels:
    app: orders
spec:                      # what YOU want to be true
  replicas: 3
# status:                  # what the CONTROLLER observed — never hand-written
#   readyReplicas: 3

Labels and selectors: the glue between objects — and annotations

Kubernetes objects do not hold pointers to each other. A Deployment does not contain a list of its Pods; a Service does not contain a list of endpoints. Instead objects carry labels — arbitrary key/value pairs in metadata — and other objects carry selectors that match on them. The Deployment's selector.matchLabels is how it claims its ReplicaSets; the ReplicaSet's selector is how it claims its Pods; the Service's selector is how it finds the Pods to send traffic to. This loose coupling is deliberate and powerful: relabel a Pod and it silently leaves its Service, which is exactly how you pull a misbehaving Pod out of rotation for debugging while keeping it alive.

It also means a typo in a selector produces no error at all — just a Service with zero endpoints or a Deployment that never adopts anything, which is one of the most common self-inflicted outages in Kubernetes. Kubernetes suggests a set of recommended labels (app.kubernetes.io/name, /instance, /component, /part-of, /managed-by) so tooling can understand your objects; use them. Annotations are the same key/value shape but explicitly not selectable: they hold arbitrary non-identifying metadata for humans and tools — build ids, checksums that force a rollout when config changes, ingress controller directives, the kubectl.kubernetes.io/last-applied-configuration blob that makes apply work. Rule of thumb: if something will ever be queried or selected on, it is a label; if it is only ever read, it is an annotation.

kubectl get pods -l app=orders,tier=backend      # AND of equality selectors
kubectl get pods -l 'env in (staging,prod)'      # set-based selector
kubectl get pods -l '!canary'                    # objects WITHOUT the label
kubectl label pod orders-7f9c quarantine=true    # add a label at runtime
kubectl label pod orders-7f9c app-                # remove 'app' — Pod leaves its Service

Pods: the smallest deployable unit, and why it holds more than one container

Kubernetes never schedules a container; it schedules a Pod. A Pod is a group of one or more containers that share a network namespace (one IP address, one port space — they reach each other on localhost), share storage volumes, and are always co-scheduled onto the same node and scaled as a unit. Most Pods hold exactly one application container. The reason the abstraction allows more is tight co-operation: a helper that has to share the main container's network or filesystem, not merely run nearby.

Two shapes matter. Init containers run to completion, in order, before the app containers start — waiting for a dependency, running a schema migration, fetching a secret — and a failing init container keeps the Pod in Init: state, which is a distinctive and easily diagnosed symptom. Sidecars run alongside the app for its whole life: a log shipper, a service-mesh proxy, a config reloader. Since v1.29 sidecars have first-class support as init containers with restartPolicy: Always, which fixes the old problems of startup ordering and of a sidecar keeping a Job from ever completing. Finally: you almost never write a bare Pod. A bare Pod is not rescheduled if its node dies — nothing owns it, so nothing recreates it. Bare Pods are for a one-off debug shell; everything else goes behind a controller.

ReplicaSets and Deployments: replica count, rollouts and rollbacks

A ReplicaSet does one job: keep exactly N Pods matching its selector alive. It is a textbook reconciliation loop — count the Pods, create or delete until the count matches. But a ReplicaSet's Pod template is effectively fixed; changing the image on a ReplicaSet does not roll anything out, it just means future replacements use the new image. That is why you almost never write one directly.

A Deployment is the object you actually write, and it manages ReplicaSets on your behalf. Change the Pod template and the Deployment controller creates a new ReplicaSet, then shifts replicas from the old one to the new one according to the strategy — RollingUpdate by default, governed by maxUnavailable and maxSurge, or Recreate when the app cannot tolerate two versions at once. Because the old ReplicaSet is kept (scaled to zero, up to revisionHistoryLimit), rollback is instant: kubectl rollout undo just scales the previous ReplicaSet back up. The hierarchy to be able to recite is Deployment → ReplicaSet → Pod, with ownership expressed through owner references and matching label selectors at each hop. Deployments suit stateless workloads; StatefulSets (stable identity and storage), DaemonSets (one Pod per node) and Jobs/CronJobs (run to completion) are the other controllers, covered in the next module.

kubectl apply -f deployment.yaml
kubectl rollout status deployment/orders        # blocks until the rollout settles
kubectl rollout history deployment/orders       # revisions kept via old ReplicaSets
kubectl rollout undo deployment/orders          # back one revision, instantly
kubectl scale deployment/orders --replicas=5
kubectl get rs -l app=orders                    # see old + new ReplicaSets side by side

Services and the networking model: a stable address in front of ephemeral Pods

Start from the networking model, because Services only make sense once you accept it. Every Pod gets its own cluster-routable IP address, and every Pod can reach every other Pod's IP without NAT — a flat network, implemented by a CNI plugin such as Calico, Cilium or a cloud provider's own. The problem is that Pod IPs are worthless as an address to write down: a Pod that is rescheduled, updated or scaled comes back with a different IP, and there may be three of them or thirty. A Service is the stable name and virtual IP in front of that moving set. It selects Pods by label, tracks the ready ones through EndpointSlices, and load-balances across them.

Know the four types and the fact that each builds on the previous. ClusterIP (the default) allocates a virtual IP reachable only inside the cluster — the right answer for service-to-service traffic. NodePort additionally opens the same port on every node, in the 30000–32767 range, so external traffic hitting any node reaches the Service; useful for local clusters and bare metal, crude for production. LoadBalancer additionally asks the cloud provider for an external load balancer pointing at those node ports — one cloud load balancer per Service, which is precisely why Ingress and the Gateway API exist. Headless (clusterIP: None) allocates no virtual IP at all and instead makes DNS return the individual Pod IPs, which is what StatefulSets and client-side-load-balancing clients want. Finally, cluster DNS gives every Service a name: orders from inside the same namespace, or the fully qualified orders.shop.svc.cluster.local from anywhere — the fastest fix for "my service cannot reach the other service" is usually the missing namespace in that name.

apiVersion: v1
kind: Service
metadata: { name: orders, namespace: shop }
spec:
  type: ClusterIP        # ClusterIP | NodePort | LoadBalancer  (or clusterIP: None)
  selector:
    app: orders          # matches Pod LABELS — a typo here means zero endpoints
  ports:
    - port: 80           # the port the Service listens on
      targetPort: 8080   # the port the container listens on

Namespaces: scoping, isolation and quota

A namespace is a virtual cluster inside the physical cluster: a scope for names, so orders in staging and orders in prod are different objects, and a boundary that RBAC rules, resource quotas and network policies attach to. Every cluster starts with default, kube-system (control-plane workloads — treat as read-only), kube-public and kube-node-lease. Most objects are namespaced; a handful — Nodes, PersistentVolumes, StorageClasses, ClusterRoles, CustomResourceDefinitions — are cluster-scoped, and kubectl api-resources --namespaced=false lists them for the cluster in front of you.

Namespaces are the natural place to enforce fairness. A ResourceQuota caps the total CPU, memory, storage and object counts a namespace may consume — so one team's runaway Deployment cannot starve the cluster — and a LimitRange supplies defaults and per-object ceilings so Pods submitted without resource requests do not slip through. Be honest about what namespaces are not: they are a soft boundary. They do not isolate the network by default (any Pod can still reach any other Pod's IP across namespaces until you add NetworkPolicies), they do not isolate the kernel, and they are not a security boundary between untrusted tenants — that argument ends at separate clusters or a sandboxed runtime. In interviews, "namespace per environment" is usually the wrong answer at scale for exactly this reason; namespace per team or per application within one environment, and separate clusters for staging and production, is the more defensible position.

kubectl fluency and the debugging sequence when a Pod is not Running

Ten commands cover almost everything. kubectl get lists (add -o wide for node and IP, -w to watch, -A for all namespaces); describe renders an object plus — crucially — the recent events attached to it; logs reads a container's stdout (-f to follow, -c to pick a container in a multi-container Pod, --previous to read the instance that just died); exec -it ... -- sh gets you a shell inside a running container; apply -f is your declarative workhorse; delete removes; port-forward tunnels a local port straight to a Pod or Service so you can hit an internal endpoint from your laptop without exposing anything. Add -o yaml to see an object exactly as the API server holds it, -o jsonpath= to extract one field for a script, and --dry-run=client -o yaml to have kubectl generate a manifest skeleton you then edit and commit rather than typing YAML from memory.

Two pieces of hygiene separate the fluent from the flustered. First, context and namespace: kubectl config get-contexts and use-context switch clusters, kubectl config set-context --current --namespace=shop stops you typing -n forever, and the tools kubectx/kubens plus a shell prompt showing the current context are how experienced people avoid running a command against production by accident. Second, the debugging sequence, which is a genuine interview favourite: kubectl get pod to read the status column, then kubectl describe pod and read the Events at the bottom first — ImagePullBackOff and ErrImagePull mean a bad image name or missing registry credentials, Pending with a FailedScheduling event means no node satisfies the requests/affinity/taints, CrashLoopBackOff means the container starts and exits repeatedly. Only when it is crash-looping do you go to kubectl logs --previous, because the current container may be too young to have logged anything; that is where the application's own stack trace is waiting.

kubectl get pods -o wide -w                       # status, node, IP; keep watching
kubectl describe pod orders-7f9c                  # read the Events section FIRST
kubectl logs orders-7f9c -c app --previous        # the crashed instance's last words
kubectl exec -it orders-7f9c -- sh                # shell inside the container
kubectl port-forward svc/orders 9090:80           # local 9090 to the Service
kubectl get deploy orders -o jsonpath='{.spec.template.spec.containers[0].image}'
kubectl create deployment web --image=nginx --dry-run=client -o yaml > web.yaml
kubectl config set-context --current --namespace=shop

Interview questions

Kubernetes is now a default screening topic for backend and DevOps roles at Indian product and service companies alike. The Pod-versus-Deployment question and the Service-types question come up in almost every round; the architecture and debugging follow-ups are what separate candidates who have used a cluster from candidates who have watched a course about one:

Beginner What is Kubernetes and what problem does it solve?

A container orchestrator: it takes a pool of machines and a declarative description of what should be running, then places containers on nodes, restarts them when they fail, reschedules them when a node dies, scales them, gives them stable network identities and rolls out new versions without downtime. It solves the problems you hit the moment you have more containers than one machine can hold and more availability requirements than a restart script can meet.

Beginner Name the control plane components and what each does.

kube-apiserver — the REST front end, does authentication, authorisation, admission and validation, and is the only component that talks to etcd. etcd — the consistent key-value store holding all cluster state. kube-scheduler — assigns unscheduled Pods to nodes based on resource requests, affinity, taints and constraints. kube-controller-manager — runs the built-in control loops (node, replication, endpoints, service accounts). cloud-controller-manager — the cloud-provider-specific loops for load balancers, routes and node metadata.

Beginner What runs on a worker node?

The kubelet (the node agent: starts and supervises the Pods assigned to this node, mounts volumes, runs probes, reports status), kube-proxy (maintains the iptables/IPVS rules that implement Service virtual IPs — some CNI plugins replace it), and a container runtime such as containerd or CRI-O, which the kubelet drives through the Container Runtime Interface.

Beginner What is a Pod, and why can it contain more than one container?

A Pod is the smallest deployable unit — one or more containers that share a network namespace (one IP, reachable from each other on localhost), share volumes, and are always scheduled onto the same node and scaled together. Multiple containers are for tightly coupled helpers that genuinely need that shared context: an init container that runs a migration before the app starts, or a sidecar such as a log shipper or a service-mesh proxy. Anything that merely needs to run nearby belongs in its own Pod.

Beginner Pod vs Deployment — what is the difference and which do you create?

A Pod is a single running instance; nothing owns it, so if its node dies it is gone and nothing recreates it, and it has no concept of versions or rollout. A Deployment is a controller that owns a Pod template plus a replica count: it creates a ReplicaSet, keeps the requested number of Pods alive, reschedules them after failures, and performs rolling updates and rollbacks when the template changes. You create Deployments; you create bare Pods only for a throwaway debug container.

Beginner Explain the Service types: ClusterIP, NodePort, LoadBalancer, headless.

ClusterIP (default) — a virtual IP reachable only inside the cluster; used for service-to-service traffic. NodePort — everything ClusterIP does, plus the same port opened on every node (roughly 30000–32767) so outside traffic can reach it; fine for local or bare-metal clusters, crude for production. LoadBalancer — everything NodePort does, plus the cloud provider provisions an external load balancer with a public IP; one per Service, which is why Ingress or the Gateway API is preferred at scale. Headless (clusterIP: None) — no virtual IP; DNS returns the individual Pod IPs instead, which StatefulSets and client-side load-balancing clients need.

Intermediate What is the reconciliation loop, and why does it matter?

Every controller runs the same loop forever: read desired state from the API server, observe actual state, and take one step to close the gap. Kubernetes is therefore declarative and level-triggered — controllers act on the current state of the world rather than on the event that woke them, so a missed event is corrected on the next pass rather than lost. It is why a deleted Pod comes back, why scaling is just editing a number, and why every object has both a spec you write and a status the controller writes.

Intermediate How does a Service know which Pods to send traffic to?

By label selector, not by any list of Pods. The Service's spec.selector matches labels in Pod metadata; the endpoints controller keeps an EndpointSlice of the matching Pods that are Ready, and kube-proxy (or the CNI dataplane) programs the node's rules to load-balance the Service IP across them. A mismatch between the selector and the Pod labels produces a Service with zero endpoints and no error message — check with kubectl get endpointslices or kubectl describe svc.

Intermediate Deployment vs ReplicaSet — do you ever write a ReplicaSet directly?

A ReplicaSet only maintains a replica count; its Pod template is effectively fixed, so it offers no rollout, no revision history and no rollback. A Deployment manages ReplicaSets: on a template change it creates a new ReplicaSet and shifts replicas across per the strategy, keeping the old one scaled to zero so rollout undo is instant. In practice you never author a ReplicaSet — you author a Deployment and let it own them. The chain is Deployment → ReplicaSet → Pod.

Intermediate Labels vs annotations — when do you use each?

Both are key/value maps in metadata, but labels are identifying and selectable — selectors, kubectl get -l, Service and controller matching all work on labels — while annotations are non-identifying metadata that nothing selects on: build ids, config checksums used to force a rollout, ingress-controller directives, the last-applied-configuration blob. If it will ever be queried or matched, make it a label; if it is only ever read by a human or a tool, make it an annotation.

Intermediate Why do we need Services at all — why not just use Pod IPs?

Because Pod IPs are ephemeral. Every Pod gets a routable IP, but a Pod that is rescheduled, updated or scaled comes back with a different one, and there is usually more than one replica. A Service supplies a stable virtual IP and a stable DNS name in front of the changing set, tracks which backing Pods are Ready, and load-balances across them — so callers configure one name and never learn about Pod churn.

Intermediate A Pod is stuck in Pending. Walk me through your diagnosis.

Pending means it has not been scheduled onto a node. Run kubectl describe pod and read the Events: a FailedScheduling event names the reason — insufficient CPU or memory for the requests, a node selector or affinity rule nothing matches, a taint with no matching toleration, or an unbound PersistentVolumeClaim. Cross-check with kubectl get nodes and kubectl describe node for capacity and taints. Logs are useless here because no container has started.

Pro A Pod is in CrashLoopBackOff. What exactly does that mean and how do you debug it?

The container starts, exits, and the kubelet restarts it with an increasing backoff delay — the Pod is not broken at the Kubernetes level, the process inside is exiting. kubectl describe pod gives you the exit code and restart count (exit 137 is a SIGKILL, typically an OOM kill against the memory limit; a non-zero application exit code points at config). Then kubectl logs POD --previous, because the current container may be too young to have logged; the previous instance holds the stack trace. Common causes: missing environment variable or Secret, unreachable dependency at startup, a failing migration, a wrong command or entrypoint, or a memory limit set below what the JVM actually needs.

Pro Why is only the API server allowed to talk to etcd?

It makes one process the single point of authentication, authorisation, admission control, validation, defaulting, versioning and audit for all cluster state — no component can write an object that skipped those checks. It also decouples every other component from etcd's schema and consistency semantics, so the storage layer can evolve or be replaced without touching controllers, and it makes the watch/list API the universal integration point that lets any operator behave exactly like a built-in controller.

Pro Kubernetes removed dockershim. Do my Docker images still work, and what changed?

Images are unaffected — Docker builds OCI images and Kubernetes runs OCI images; the format was never the issue. What was removed was the in-tree shim that let the kubelet drive Docker Engine, which never implemented the Container Runtime Interface. Deprecated in v1.20 and removed in v1.24, so on any supported release the node runs containerd or CRI-O directly. Practical fallout is operational, not developmental: docker ps on a node shows nothing useful (use crictl), and any tooling that assumed a Docker socket on the host — some in-cluster image builders and log agents — had to change.

Pro Are namespaces a security boundary? How would you actually isolate two teams?

No. A namespace scopes names and gives RBAC, ResourceQuota and NetworkPolicy something to attach to, but by default any Pod can still reach any other Pod's IP across namespaces, the kernel is shared, and a container escape is cluster-wide. Real isolation is layered: RBAC scoped to the namespace, default-deny NetworkPolicies, ResourceQuota and LimitRange to stop resource starvation, Pod Security Admission plus a restrictive securityContext, separate node pools for sensitive workloads, and — for genuinely untrusted tenants — separate clusters or a sandboxed runtime such as gVisor or Kata.

Pro Two Deployments accidentally share a label selector. What happens?

Ownership becomes ambiguous and the controllers fight. Each Deployment's ReplicaSet believes the other's Pods match its selector, so it counts them toward its replica target and deletes what it sees as surplus, while the other recreates them — a churn loop with Pods being created and terminated continuously, and neither Deployment converging. This is why the Deployment selector is immutable after creation and why app.kubernetes.io/instance-style unique labels matter. Diagnose it with kubectl get pods --show-labels and by inspecting owner references; fix it by giving each workload a genuinely unique selector, which for an existing Deployment means recreating it.
