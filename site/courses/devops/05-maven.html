Module: Maven

Maven is not a scripting tool you program — it is a model you describe. Learn the two ideas it is built on, convention over configuration and a declarative dependency graph, and almost every mysterious build failure stops being mysterious.

Knowledge Library → Courses → DevOps and Deployment track → Maven

What this module covers

Maven has run the Java build for twenty years, and the reason it still does is that it refuses to let each project invent its own build. You do not tell Maven how to compile, test and package; you declare what the project is — coordinates, packaging, dependencies, a parent — and a fixed lifecycle plus a set of plugins does the rest. Everything that feels strange about Maven follows from that choice, including the parts people complain about.

Two things cause almost all the confusion. The first is the lifecycle-phase-goal relationship: most developers can type mvn clean install without being able to say what each word does or why package also compiles. The second is dependency mediation: Maven flattens a graph of transitive dependencies into one version per artifact using a rule that is simple, documented, and consistently surprising. This module covers POM anatomy, the lifecycles, plugins and the wrapper, then scopes, mediation, BOMs, multi-module reactor builds, profiles and the plugins you will actually configure.

Topics

POM anatomy: coordinates, packaging, parent inheritance and the effective POM

The pom.xml is a description of a project, not a build script. Its core is the GAV triple — groupId (a reverse-DNS namespace you control), artifactId (the module name) and version — which uniquely addresses the artifact in every repository on earth. Add packaging (jar by default, plus war, pom for aggregators and BOMs, maven-plugin, ear) and you have told Maven what to produce; packaging also silently selects which goals get bound to which phases, which is why a pom-packaged module never produces a jar.

Every POM inherits, whether you declare a <parent> or not: with no parent you still inherit the Super POM baked into the Maven distribution, which supplies Central as a repository, the default directory layout and default plugin versions. What actually runs is the effective POM — your file merged with its parents, the Super POM, active profiles and property interpolation. When a dependency version, plugin configuration or property is not what you expected, mvn help:effective-pom is the tool that ends the argument, and knowing it exists is a genuine seniority signal in interviews. Keep versions in <properties> rather than sprinkled through the file, and never use the ${project.version}-style expressions in places Maven cannot resolve at model-build time.

<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>          <!-- always 4.0.0 on Maven 3.x -->
  <parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.5.4</version>
    <relativePath/>                             <!-- empty: resolve from the repository -->
  </parent>

  <groupId>com.acme.orders</groupId>             <!-- G -->
  <artifactId>order-service</artifactId>         <!-- A -->
  <version>1.4.0-SNAPSHOT</version>              <!-- V -->
  <packaging>jar</packaging>

  <properties>
    <java.version>21</java.version>
    <testcontainers.version>1.20.4</testcontainers.version>
  </properties>
</project>

Convention over configuration: the standard directory layout

Maven's second founding idea is that if every project puts sources, resources and tests in the same place, no project needs to configure where they are. src/main/java, src/main/resources, src/test/java, src/test/resources, output in target/ — obey that and the compiler, resource, surefire and jar plugins all work with zero configuration. Deviate and you are writing configuration to fight defaults for the rest of the project's life.

The payoff is portability of people, not just builds. A developer who has never seen your repository can clone it, run one command and know where the integration tests live. That is also why Maven is still the default in large service companies: onboarding cost matters more than build-script expressiveness. The same convention is what lets tools — IDEs, Sonar, Jacoco, container plugins — work on your project without being told anything about it.

order-service/
  pom.xml
  mvnw  mvnw.cmd  .mvn/wrapper/     <- the wrapper, committed
  src/
    main/java/            <- production sources
    main/resources/       <- application.yml, static files, become classpath root
    test/java/            <- *Test.java  (surefire) and *IT.java (failsafe)
    test/resources/
  target/                 <- everything generated; never committed
    classes/  test-classes/  order-service-1.4.0-SNAPSHOT.jar

The three lifecycles, and why one phase runs every phase before it

Maven ships exactly three built-in lifecycles. clean has three phases (pre-clean, clean, post-clean) and deletes target/. site generates project documentation. default is the one that builds software, and it has twenty-three ordered phases; the ones worth memorising are validate, compile, test, package, verify, install, deploy, with process-resources, test-compile and the integration-test trio in between. The single rule that explains most beginner confusion: invoking a phase runs that phase and every phase before it in the same lifecycle. So mvn package also validates, compiles, processes resources and runs unit tests, and mvn deploy runs the entire default lifecycle.

The lifecycles are independent of each other, which is why mvn clean install is two arguments rather than one: you are asking for the clean phase of the clean lifecycle and then the install phase of the default lifecycle. Know the difference between the last three too, because it is a stock interview question. package produces the artifact in target/; verify additionally runs integration tests and quality checks bound after packaging; install copies the artifact into your local repository at ~/.m2/repository so other local projects resolve it; deploy pushes it to a remote repository such as Nexus or Artifactory for everyone else. On CI, mvn verify is usually the right command — install pollutes a shared local repository for no benefit.

default lifecycle (abridged, in order — running one runs all preceding):
  validate -> compile -> test -> package -> verify -> install -> deploy
             |          |        |          |
             |          |        |          +-- integration-test + failsafe:verify
             |          |        +------------- jar/war assembled into target/
             |          +---------------------- surefire runs unit tests
             +--------------------------------- sources compiled to target/classes

clean lifecycle:  pre-clean -> clean -> post-clean
site  lifecycle:  pre-site -> site -> post-site -> site-deploy

Goals, plugin executions, and calling plugin:goal directly

Phases do nothing by themselves. A phase is a slot; the work is done by goals, and a goal is one task inside a plugin. compiler:compile, surefire:test, jar:jar, install:install — those are goals, and the default lifecycle mapping for jar packaging is what binds them to compile, test, package and install. That mapping is why an empty POM still builds a jar correctly. When you add a plugin with an <execution> you are declaring "run this goal at this phase, with this configuration", and you can bind several executions of the same plugin to different phases with different settings, each identified by an <id>.

You can also skip the lifecycle entirely and invoke a goal directly as plugin:goal — mvn dependency:tree, mvn help:effective-pom, mvn versions:display-dependency-updates, mvn spring-boot:run. Nothing before it runs, which is exactly what you want for a diagnostic. Two related habits keep builds reproducible: pin every plugin version (in <pluginManagement> on the parent, so children inherit the version without inheriting the binding), and remember that <pluginManagement> only declares configuration while <plugins> actually activates it — the same split as dependencyManagement versus dependencies.

<build>
  <pluginManagement>                <!-- versions + config, no activation -->
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-failsafe-plugin</artifactId>
        <version>3.5.2</version>
      </plugin>
    </plugins>
  </pluginManagement>

  <plugins>
    <plugin>
      <artifactId>maven-failsafe-plugin</artifactId>
      <executions>
        <execution>
          <id>integration-tests</id>
          <goals>                    <!-- these goals bind to their default phases: -->
            <goal>integration-test</goal>   <!-- phase: integration-test -->
            <goal>verify</goal>             <!-- phase: verify -->
          </goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

The Maven wrapper: mvnw belongs in the repository

The wrapper is a tiny committed script pair (mvnw, mvnw.cmd) plus a .mvn/wrapper/maven-wrapper.properties file naming an exact Maven version. On first run it downloads that distribution into a user-level cache and then delegates to it. The result is that the Maven version becomes part of the source tree, versioned and reviewed like any other dependency, instead of being an undeclared property of whichever laptop or agent happens to run the build.

This matters more than it sounds. Without it, a developer on an old Maven and a CI agent on a new one can produce different results, and "works on my machine" becomes a build problem rather than a code problem. With it, a fresh clone needs only a JDK — ./mvnw verify works with nothing else installed, which is why Spring Initializr has generated it into every project for years. Generate or upgrade it with mvn wrapper:wrapper -Dmaven=3.9.9, commit all the wrapper files, and always invoke ./mvnw rather than mvn in scripts, Dockerfiles and CI pipelines. Note that Maven 3.9.x remains the current stable line; keep the wrapper pinned there rather than tracking pre-release versions.

# create or upgrade the wrapper, then commit everything it writes
mvn wrapper:wrapper -Dmaven=3.9.9

git add mvnw mvnw.cmd .mvn/wrapper/maven-wrapper.properties

# from now on, every script and pipeline uses the wrapper
./mvnw clean verify          # Linux / macOS / Git Bash
mvnw.cmd clean verify        # Windows shell

Dependency scopes and what each one means for the classpath

A scope answers two questions at once: which classpaths this dependency appears on, and whether it propagates to projects that depend on you. compile (the default) is on all three classpaths and propagates. provided is on compile and test classpaths but excluded at runtime and never propagated — the container or the JDK supplies it (a servlet API, a Lombok-style annotation processor, a Spring Boot configuration processor). runtime is the mirror image: absent at compile time, present at runtime and test — the classic case is a JDBC driver you must not let anyone import directly. test is visible only to test compilation and execution and never propagates, which is what keeps JUnit out of your shipped jar. system points at an absolute path on disk, is deprecated, and should be treated as a code smell. import is different in kind — it is legal only inside <dependencyManagement> on a pom-packaged artifact and pulls in that POM's managed versions rather than any jar.

Two consequences are worth internalising because interviewers probe them. First, scope is a compile-time and a packaging decision: mark something provided that the runtime does not actually provide and you get a NoClassDefFoundError in production that no test caught. Second, scope controls transitivity, so it is your main lever for not inflicting your test and tooling dependencies on your consumers. The related <optional>true</optional> flag says "I use this, but you decide whether you need it" — it stops propagation without changing your own classpath.

<dependencies>
  <dependency>                                <!-- compile: everywhere, propagates -->
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>

  <dependency>                                <!-- runtime: no compile access -->
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
  </dependency>

  <dependency>                                <!-- provided: compile only, not packaged -->
    <groupId>jakarta.servlet</groupId>
    <artifactId>jakarta.servlet-api</artifactId>
    <scope>provided</scope>
  </dependency>

  <dependency>                                <!-- test: never shipped, never propagated -->
    <groupId>org.testcontainers</groupId>
    <artifactId>postgresql</artifactId>
    <scope>test</scope>
  </dependency>
</dependencies>

Transitive dependencies, nearest-wins mediation, and dependency:tree

You declare a handful of dependencies; Maven resolves the closure of everything they need. That closure is a graph, but the classpath is a flat list, so Maven must pick exactly one version per groupId:artifactId. The rule is nearest wins: the version at the shallowest depth in the tree from your POM. If two candidates sit at the same depth, the one declared first in the POM wins. Maven does not pick the highest version — that is Gradle's rule, and mixing the two up is a classic interview trap.

Nearest-wins surprises people because it makes your build sensitive to declaration order and to depth, both of which change when you add an unrelated library. The symptom is a NoSuchMethodError or ClassNotFoundException at runtime after a dependency bump: the code was compiled against one version of a transitive library and ran against another. The diagnosis is always the same command — mvn dependency:tree, ideally with -Dverbose to show the omitted candidates and -Dincludes= to filter to the artifact in question. Three fixes, in order of preference: declare the artifact directly in your POM (depth 1 always wins, and it documents the intent), pin the version in <dependencyManagement>, which overrides mediation entirely, or add an <exclusion> to the dependency dragging in the wrong copy. Also run mvn dependency:analyze occasionally: it names dependencies you use but do not declare (the ones a transitive change will break) and dependencies you declare but never use.

./mvnw dependency:tree -Dverbose -Dincludes=com.google.guava:guava

# [INFO] com.acme:order-service:jar:1.4.0-SNAPSHOT
# [INFO] +- com.acme:billing-client:jar:2.1.0:compile
# [INFO] |  \- com.google.guava:guava:jar:32.1.3-jre:compile      <- depth 2, WINS
# [INFO] \- com.acme:search-client:jar:4.0.0:compile
# [INFO]    \- (com.google.guava:guava:jar:33.4.0-jre:compile - omitted for conflict)

./mvnw dependency:analyze     # used-but-undeclared / declared-but-unused
<!-- fix 1 (best): declare it yourself at depth 1 -->
<dependency>
  <groupId>com.google.guava</groupId>
  <artifactId>guava</artifactId>
  <version>33.4.0-jre</version>
</dependency>

<!-- fix 3: cut the offending copy out of the offender -->
<dependency>
  <groupId>com.acme</groupId>
  <artifactId>billing-client</artifactId>
  <version>2.1.0</version>
  <exclusions>
    <exclusion>
      <groupId>com.google.guava</groupId>
      <artifactId>guava</artifactId>
    </exclusion>
  </exclusions>
</dependency>

dependencyManagement and BOMs: pinning a whole family of versions

<dependencies> adds a dependency. <dependencyManagement> adds nothing — it only says "if anyone in this project or its children uses this artifact, here is the version, scope and exclusions to use". Children then declare the dependency with no <version> at all. That separation is what makes a parent POM useful: one place to change a version, and no risk of forcing an unwanted jar onto every module. It also beats mediation outright — a managed version wins over the nearest-wins rule no matter how deep the transitive copy is, which makes it the cleanest way to force a security patch across a whole tree.

A BOM is that idea packaged for reuse: a pom-packaged artifact whose entire content is a <dependencyManagement> block covering a family of mutually tested versions. You consume it with <scope>import</scope> inside your own dependencyManagement. Spring Boot is the worked example and shows both routes: inherit spring-boot-starter-parent (you get managed versions plus plugin configuration, resource filtering and a Java version, but you spend your one <parent> slot), or import spring-boot-dependencies as a BOM (versions only, and you keep your parent for your own company POM). You can import as many BOMs as you like — that is the point of import scope, since a POM has only one parent. Note the ordering rule when BOMs overlap: the first import wins, so put the one you consider authoritative first.

<dependencyManagement>
  <dependencies>
    <dependency>                                  <!-- BOM import: versions only -->
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.5.4</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
    <dependency>                                  <!-- a second BOM, also fine -->
      <groupId>org.testcontainers</groupId>
      <artifactId>testcontainers-bom</artifactId>
      <version>${testcontainers.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <dependency>                                    <!-- no version: it is managed -->
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>
</dependencies>

Multi-module reactor builds: aggregation and inheritance are not the same thing

These two ideas share a file and are constantly conflated. Aggregation is a pom-packaged POM listing <modules>; running Maven on it starts the reactor, which collects all listed modules, reads their inter-module dependencies and topologically sorts them so each module is built after everything it needs. Order in the <modules> list is irrelevant — the dependency graph decides. Inheritance is a child naming a <parent> to receive its properties, dependencyManagement, pluginManagement and common dependencies. A typical repository uses one POM for both, but you can aggregate modules that inherit from something else entirely, and you can inherit from a company parent that aggregates nothing.

The reactor is also where the useful command-line flags live. -pl (project list) restricts the build to named modules; -am (also make) adds the upstream modules those depend on, which is the combination you want when iterating on one service in a large repository; -amd builds the downstream dependents instead; -rf resumes from a module after a mid-build failure; -T 1C builds independent modules in parallel with one thread per core. One caveat that bites in CI: inside a reactor build, modules resolve their siblings from the reactor itself, but a build of a single module alone will look in the local or remote repository — which is why a module that builds fine as part of the whole project can fail when built in isolation.

# aggregator pom.xml: <packaging>pom</packaging> + <modules>
#   order-domain, order-service, order-api, order-batch

./mvnw -pl order-service -am verify   # build order-service + what it depends on
./mvnw -pl order-api -amd verify      # build order-api + everything depending on it
./mvnw -rf order-service verify       # resume from this module after a failure
./mvnw -T 1C clean verify             # one build thread per CPU core

Profiles and activation: the same POM, different environments

A profile is a named block of POM fragments — properties, dependencies, plugins, repositories, even an alternative build configuration — that is merged into the effective POM only when the profile is active. Use them for genuine build-time variation: a slow test suite you run only on CI, a different packaging for an on-premise release, an extra plugin for a release build. Do not use them to select application configuration at build time; that is what Spring profiles and externalised configuration are for, and baking environment settings into an artifact defeats build-once-deploy-anywhere.

Activation has several routes and knowing them all is a common interview probe: explicitly with -P name (and -P !name to deactivate), by JDK version range, by operating system, by the presence or the value of a system property, by a file existing or missing, or via <activeProfiles> in settings.xml for machine-level concerns such as an internal mirror. <activeByDefault> has one sharp edge that catches everyone: it is disabled the moment any other profile in the same POM is activated by any means, so "default" profiles silently vanish. Prefer a property-based activation, and check what is actually on with mvn help:active-profiles.

<profiles>
  <profile>
    <id>integration</id>
    <activation>
      <property><name>env.CI</name></property>   <!-- active when CI is set -->
    </activation>
    <properties>
      <skipITs>false</skipITs>
    </properties>
  </profile>

  <profile>
    <id>native</id>                                <!-- opt in with -P native -->
    <build><plugins>
      <plugin>
        <groupId>org.graalvm.buildtools</groupId>
        <artifactId>native-maven-plugin</artifactId>
      </plugin>
    </plugins></build>
  </profile>
</profiles>

The plugins you will actually configure

Six or seven plugins carry almost every real build. maven-compiler-plugin selects the language level — on modern Maven set <maven.compiler.release> rather than the old source/target pair, because release also checks that you only use APIs present in that JDK. maven-surefire-plugin runs unit tests at the test phase and by default matches *Test, Test*, *Tests, *TestCase. maven-failsafe-plugin is its sibling for integration tests: it matches *IT, binds to integration-test and verify, and — the point of the split — its failures are reported in the verify goal after the post-integration-test phase, so containers and servers still get torn down when a test fails. Surefire failing the build immediately would leave them running.

For packaging, maven-jar-plugin produces the plain jar; maven-shade-plugin produces an uber-jar with dependencies unpacked and optionally relocated (the relocation feature is how libraries avoid inflicting their own dependency conflicts on you); for Spring, spring-boot-maven-plugin's repackage goal rewrites the jar into an executable, nested-jar layout and also gives you spring-boot:run and spring-boot:build-image. Finally the two governance plugins: maven-enforcer-plugin fails the build on rule violations — minimum Maven and JDK version, banned dependencies, no duplicate classes, dependency convergence — and is the single most effective way to stop bad dependencies entering a large codebase; versions-maven-plugin reports available upgrades with versions:display-dependency-updates and can apply them.

<properties>
  <maven.compiler.release>21</maven.compiler.release>
</properties>

<plugin>
  <artifactId>maven-enforcer-plugin</artifactId>
  <executions><execution>
    <id>enforce-rules</id>
    <goals><goal>enforce</goal></goals>
    <configuration><rules>
      <requireMavenVersion><version>[3.9.0,)</version></requireMavenVersion>
      <requireJavaVersion><version>[21,)</version></requireJavaVersion>
      <dependencyConvergence/>      <!-- fail when a transitive version conflicts -->
      <bannedDependencies><excludes>
        <exclude>commons-logging:commons-logging</exclude>
      </excludes></bannedDependencies>
    </rules></configuration>
  </execution></executions>
</plugin>

Maven 4 on the horizon: what changes, and what you should still learn first

Maven 4 has been in release candidates for a while and is not yet generally available — the 3.9.x line is what real projects run and what interviews ask about, so learn that first. The headline change is the split between the build POM and the consumer POM: your source POM may use the new modelVersion 4.1.0 with conveniences that were previously impossible, while Maven publishes a cleaned, fully-resolved 4.0.0-model POM to the repository for consumers. That decoupling is what finally allows a parent version to be inferred, module versions to be omitted, and build-only sections to be stripped from what downstream users see.

Other changes worth recognising by name: a dedicated bom packaging type that distinguishes a real bill of materials from a parent POM, <subprojects> as the clearer replacement for <modules>, a root="true" attribute plus a ${project.rootDirectory} property that fix the perennial "where is the top of this multi-module build" problem, and an mvnup upgrade tool. Maven 4 requires Java 17 to run (though it can still build for older targets) and keeps backwards compatibility as an explicit goal, so existing 4.0.0-model POMs continue to work. Treat it as awareness, not as something to migrate to today.

Interview questions

Maven is asked in almost every Java round in India, from L1 screening at service companies to design-adjacent rounds at product firms. Scopes and transitive-conflict debugging come up more than anything else — expect to be handed a broken dependency tree and asked to reason out loud:

Beginner What is Maven and what problem does it solve?

A build and project-management tool built on convention over configuration and a declarative project model. You describe the project in pom.xml — coordinates, packaging, dependencies, parent — and a standard lifecycle plus plugins compile, test, package and publish it. It solves three things at once: reproducible builds, automatic transitive dependency resolution from repositories, and a uniform project layout so any Java developer can work on any Maven project without learning a bespoke build script.

Beginner What are GAV coordinates, and what does packaging control?

groupId, artifactId and version — the address that uniquely identifies an artifact in any repository. packaging (jar, war, pom, ear, maven-plugin) says what to produce and, less obviously, selects the default lifecycle mapping: which plugin goals get bound to which phases. That is why a pom-packaged aggregator never builds a jar and a war project runs the war plugin instead of the jar plugin.

Beginner Explain the difference between a lifecycle, a phase and a goal.

A lifecycle is an ordered sequence of phases; Maven has three (clean, default, site). A phase is a stage in that sequence — compile, test, package, install. A goal is a single task implemented by a plugin, such as compiler:compile or surefire:test. Goals are bound to phases, so running a phase executes every goal bound to it and to all preceding phases. You can also run a goal directly as mvn plugin:goal, which skips the lifecycle entirely.

Beginner What does mvn clean install actually do, and why two words?

Two separate lifecycles. clean deletes target/. install runs the whole default lifecycle up to and including install: validate, compile, test, package, verify, then copy the artifact into the local repository at ~/.m2/repository so other local projects can resolve it. On CI, mvn verify is usually more appropriate — installing into a shared agent's local repository gains nothing and can hide resolution problems.

Beginner Name the Maven dependency scopes and what each means.

compile — default; on compile, test and runtime classpaths, and propagates transitively. provided — compile and test only, excluded from the packaged artifact, not transitive; the container or JDK supplies it. runtime — runtime and test but not compile; JDBC drivers. test — test compilation and execution only, never propagated, never shipped. system — like provided but with an explicit local file path; deprecated, avoid. import — only valid inside dependencyManagement on a pom artifact; pulls in that POM's managed versions rather than a jar.

Intermediate Two libraries pull in different versions of the same jar. Which one does Maven use?

Nearest wins: the version at the shallowest depth from your POM. If both are at the same depth, the first one declared in the POM wins. Maven does not choose the highest version — that is Gradle's default. Diagnose with mvn dependency:tree -Dverbose -Dincludes=group:artifact, which shows the omitted candidates and the reason. Fix by declaring the artifact directly (depth 1 always wins), pinning it in dependencyManagement (which overrides mediation completely), or excluding it from the offending dependency.

Intermediate dependencyManagement versus dependencies — what is the difference?

dependencies actually adds the dependency to the classpath. dependencyManagement adds nothing; it centrally declares the version, scope and exclusions to use if this project or a child declares that artifact. Children then omit the version. Two extra properties matter: a managed version overrides transitive mediation regardless of depth, and it lets a parent govern versions without forcing unwanted jars onto every module.

Intermediate What is a BOM, and how do you use one without inheriting from it?

A bill of materials is a pom-packaged artifact whose content is a dependencyManagement block covering a family of mutually tested versions. You consume it inside your own dependencyManagement with <type>pom</type><scope>import</scope>. That is how you get Spring Boot's managed versions while keeping your <parent> for a company POM — inherit spring-boot-starter-parent or import spring-boot-dependencies, and you can import many BOMs but have only one parent. When two imported BOMs manage the same artifact, the first import wins.

Intermediate Surefire or failsafe — why are there two test plugins?

Surefire runs unit tests at the test phase and fails the build immediately. Failsafe runs integration tests (*IT) at integration-test but deliberately does not fail there — it records the result and fails later in the verify goal, after post-integration-test has run. That ordering is the whole reason it exists: containers, embedded servers and Testcontainers resources get torn down even when a test fails, instead of being left running by an immediate build abort.

Intermediate What is the Maven wrapper and why commit it?

mvnw, mvnw.cmd and .mvn/wrapper/maven-wrapper.properties — a committed launcher that downloads and uses an exact Maven version. It makes the build tool itself a versioned part of the repository, so every developer, CI agent and Docker build uses the same Maven, and a fresh clone needs only a JDK. Always invoke ./mvnw in scripts and pipelines rather than whatever mvn happens to be on the machine.

Intermediate Aggregation and inheritance in a multi-module project — are they the same?

No, they are independent mechanisms that usually share a file. Aggregation is a pom-packaged POM listing <modules>; it drives the reactor, which topologically sorts modules by their inter-module dependencies and builds them in one run — the order you list them is irrelevant. Inheritance is a child pointing at a <parent> to receive properties, dependencyManagement, pluginManagement and common dependencies. You can aggregate modules that inherit from something else, and inherit from a parent that aggregates nothing.

Pro Your service throws NoSuchMethodError in production but every test passed. Walk through the diagnosis.

Classic mediation mismatch: compiled against one version of a transitive library, running against another — or a second copy is on the runtime classpath. Run mvn dependency:tree -Dverbose filtered to the class's artifact and find which version won and why. Check whether the failing artifact is marked provided while nothing actually provides it at runtime, and whether the packaging (shaded uber-jar, Spring Boot repackage, application server) is contributing a second copy. Fix by pinning the version in dependencyManagement, then prevent recurrence with the enforcer plugin's dependencyConvergence and bannedDependencies rules so the build fails at commit time instead of at 2am.

Pro How do you debug a value in the POM that is not what you expect?

mvn help:effective-pom — it prints your POM merged with all parents, the Super POM, active profiles and resolved properties, which is what Maven actually executes. Pair it with mvn help:active-profiles to see which profiles are contributing, and mvn help:evaluate -Dexpression=project.version for a single value. Most "Maven is ignoring my configuration" reports turn out to be a parent overriding it, a profile that is or is not active, or a plugin declared in pluginManagement but never activated in plugins.

Pro How would you speed up a slow multi-module build on CI?

Build in parallel with -T 1C; restrict scope with -pl module -am when only part of the tree changed; use -o offline or a repository manager mirror so artifact downloads are local; cache ~/.m2/repository between pipeline runs keyed on the POM checksums; use -rf to resume rather than rebuilding after a mid-build failure; run verify rather than install; and split slow integration tests behind a failsafe-driven profile so the fast feedback loop stays fast. Beyond that, look at build caching or incremental extensions, and question whether one giant reactor should be several independently versioned repositories.

Pro Why is activeByDefault on a profile considered a trap?

Because it is not really a default. <activeByDefault>true</activeByDefault> is disabled as soon as any other profile in the same POM becomes active by any mechanism — a -P flag, a property, a JDK match. Developers then discover that passing an unrelated profile silently removed their "default" dependencies or plugin configuration. Prefer explicit property-based or file-based activation, or put the configuration in the main build and let a profile override it, and verify with mvn help:active-profiles.

Pro A security advisory requires a specific version of a library that only arrives transitively, four levels deep. How do you force it everywhere?

Pin it in <dependencyManagement> on the root parent POM: managed versions override nearest-wins mediation at any depth, and every module inherits the pin without gaining a new direct dependency. Verify with mvn dependency:tree -Dverbose -Dincludes= across the reactor, add an enforcer bannedDependencies rule with a version range so a vulnerable copy can never come back, and where the library ships its own BOM, import that instead of pinning artifacts one by one. Exclusions are the last resort — they must be repeated on every dependency that drags the artifact in, so they rot quietly as the tree changes.

Pro What is the build POM versus consumer POM split in Maven 4?

In Maven 4 the POM you author (build POM, optionally modelVersion 4.1.0) is decoupled from the POM published to the repository (consumer POM, still the 4.0.0 model). Maven generates the consumer POM during the build with everything resolved and build-only sections stripped, so older tools keep working. That decoupling is what enables the new conveniences — inferred parent and module versions, the root attribute and ${project.rootDirectory}, a dedicated bom packaging type and <subprojects>. Worth recognising, but Maven 4 is still pre-GA and 3.9.x is what production projects run.
