Module: Docker for Production Images

An image that starts on your laptop and an image you would put in front of customers are two different artifacts. This module is about the distance between them: size, layer discipline, secrets, architecture, memory and the scanner report.

Knowledge Library → Courses → DevOps and Deployment track → Docker for Production Images

What this module covers

The previous module got a Dockerfile working. This one asks the harder question: would you run it? A naive Java image ships a full JDK, Maven, a local repository of downloaded jars and the source tree — roughly a gigabyte of attack surface to run a forty-megabyte application. A naive Angular image ships Node and node_modules to serve static files a web server could hand out on its own.

Multi-stage builds fix most of that in a dozen lines, and everything after it is refinement: layer your jar so a code change does not re-download the internet, choose a base image on evidence rather than habit, cache dependencies without leaking credentials into a layer, build for both amd64 and arm64, wire up networking and storage deliberately, and give the JVM a memory budget it can actually see. The end state is a small, reproducible, scanned image that an orchestrator can schedule and restart without surprises.

Topics

Multi-stage builds: the build stage, the runtime stage, and COPY --from

A multi-stage Dockerfile has more than one FROM. Each FROM starts a fresh stage with its own filesystem, and COPY --from=<stage> reaches back into an earlier one to lift out just the finished artifact. The build stage can be as fat as it likes — JDK, Maven, Node, compilers, test fixtures — because none of it survives into the final image. Only the layers written after the last FROM are shipped, so the toolchain is deleted for free rather than deleted with a RUN rm -rf that merely hides bytes in an earlier layer.

This is the single biggest win available in container work, and it is two wins at once. Size: a Spring Boot image goes from roughly 800 MB to under 250 MB, and pull time across a hundred nodes drops with it. Security: every package you do not ship is a CVE you do not have to triage, and a compiler that is not present cannot be used by an attacker who lands a shell. You can also target an intermediate stage directly with docker build --target build, which is how a CI job runs tests in the fat stage and then builds the thin stage from the same file.

# syntax=docker/dockerfile:1
FROM maven:3.9-eclipse-temurin-21 AS build       # fat stage: JDK + Maven, thrown away
WORKDIR /src
COPY . .
RUN mvn -B -DskipTests package

FROM eclipse-temurin:21-jre-jammy                # thin stage: JRE only
WORKDIR /app
COPY --from=build /src/target/app.jar app.jar    # carry the artifact across
USER 1001                                        # never run as root
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

Java images done properly: Spring Boot layered jars

Copying a fat jar into the runtime stage works, but it wastes the layer cache in the way that hurts most. A Spring Boot jar is one file of maybe sixty megabytes, of which fifty-five are third-party dependencies that change a few times a quarter and five are your code that changes hourly. As a single COPY it is a single layer, so every commit produces a completely new sixty-megabyte layer to push and pull. Spring Boot's answer is the layered jar: the jar records a layer index that separates dependencies, spring-boot-loader, snapshot-dependencies and application, most-stable first.

You unpack it in the build stage with the jar's own tooling — java -Djarmode=tools -jar app.jar extract --layers on Spring Boot 3.3 and later, or the older -Djarmode=layertools extract — and then issue one COPY --from per layer in stability order. Now a code-only change invalidates only the small application layer; the dependency layer is reused from the registry and the push is measured in kilobytes. The zero-Dockerfile alternative is Cloud Native Buildpacks via mvn spring-boot:build-image, which produces an already-layered, already-hardened image with a memory calculator baked in — the right default when nobody on the team wants to own a Dockerfile.

FROM eclipse-temurin:21-jre-jammy AS builder
WORKDIR /builder
ARG JAR_FILE=target/*.jar
COPY ${JAR_FILE} application.jar
RUN java -Djarmode=tools -jar application.jar extract --layers --destination extracted

FROM eclipse-temurin:21-jre-jammy
WORKDIR /application
COPY --from=builder /builder/extracted/dependencies/ ./          # changes rarely
COPY --from=builder /builder/extracted/spring-boot-loader/ ./
COPY --from=builder /builder/extracted/snapshot-dependencies/ ./
COPY --from=builder /builder/extracted/application/ ./           # changes every commit
ENTRYPOINT ["java", "-jar", "application.jar"]

Smaller Java runtimes: jdeps and jlink

A JRE is a general-purpose runtime carrying every module the JDK defines — CORBA-era leftovers are gone, but you still ship XML, desktop, management and scripting modules a REST service never touches. Since Java 9 the platform is modular, so you can build a runtime containing only the modules your application resolves: jdeps --print-module-deps analyses the jar and names them, and jlink assembles a self-contained runtime image from that list. With --strip-debug, --no-man-pages, --no-header-files and compression, a typical Spring Boot runtime lands around 50–70 MB instead of 180 MB.

Know the caveats before you sell this in an interview. jdeps only sees static bytecode references, so anything loaded reflectively — JDBC drivers, JAXB, security providers, a framework's dynamic proxies — can be missed and must be added by hand with --add-modules; run the full test suite against the trimmed runtime, not just a smoke test. The jlink runtime must be built on the same OS and architecture as the final base image, which is exactly what a multi-stage build gives you. And weigh the payoff honestly: if the dependency layer is already cached on every node, shaving the JRE saves cold-start pull time and CVE surface rather than steady-state bandwidth.

FROM eclipse-temurin:21-jdk-jammy AS jre-build
COPY target/app.jar /app.jar
RUN jdeps --ignore-missing-deps --print-module-deps --multi-release 21 /app.jar > /mods.txt
RUN jlink --add-modules $(cat /mods.txt) --strip-debug --no-man-pages \
          --no-header-files --compress=zip-6 --output /javaruntime

FROM debian:bookworm-slim
ENV JAVA_HOME=/opt/java/openjdk
ENV PATH="${JAVA_HOME}/bin:${PATH}"
COPY --from=jre-build /javaruntime $JAVA_HOME
COPY --from=jre-build /app.jar /app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]

Angular images: build with Node, serve with nginx

An Angular production build is a folder of static files. Node is needed to produce them and is useless afterwards, so the two-stage shape is obvious: stage one runs npm ci and ng build on a Node image, stage two copies the dist output into an nginx (or Caddy) image. The result is roughly 50 MB instead of 1.5 GB, it starts instantly, and it has no JavaScript runtime for an attacker to reach. Use npm ci rather than npm install so the lockfile is authoritative, and copy package.json and the lockfile before the rest of the source so the install layer caches across source-only changes.

The detail everyone forgets is the SPA fallback. The Angular router owns paths like /orders/42 that exist only in the browser; a hard refresh sends that path to nginx, which looks for a file, finds none and returns 404. The fix is one try_files directive that falls back to index.html. Also mind the output path — modern Angular builds emit dist/<app>/browser, not dist/<app> — and remember that anything baked in at build time (an API base URL) is fixed per image, so environment-specific configuration belongs in a small runtime-fetched JSON file or in nginx's reverse-proxy rules rather than in a rebuilt image per environment.

FROM node:22-alpine AS build
WORKDIR /src
COPY package.json package-lock.json ./
RUN npm ci                                   # cached unless the lockfile changes
COPY . .
RUN npm run build -- --configuration production

FROM nginx:1.27-alpine
COPY --from=build /src/dist/shop-web/browser /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf

# nginx.conf — the SPA fallback that makes deep-link refreshes work:
#   location / { try_files $uri $uri/ /index.html; }

Choosing a base image: distro, slim, Alpine, distroless, UBI

The base image decides your CVE count, your image size and — for the JVM — sometimes whether the thing runs correctly at all. The honest framing is a tradeoff, not a ranking: smaller images have less to patch but less to debug with, and the most locked-down options give you no shell at all. Pick per workload, and pin by digest for reproducibility rather than trusting a floating latest.

The Alpine question deserves its own paragraph because it is an interview favourite. Alpine uses musl libc instead of glibc, and the JVM was built and tuned for glibc. Historically that meant no supported OpenJDK build at all; today Temurin and others publish musl-native builds, but you can still hit different thread-stack defaults, slower DNS resolution behaviour, and native libraries (Netty's transports, JNI-based drivers, anything compiled against glibc) that simply are not available for musl. For Java the safe defaults are a slim glibc distro, a distroless Java image, or UBI — reach for Alpine when you have measured the benefit and tested the workload. Separately, always ship a JRE (or a jlink runtime), never a JDK: the compiler, jcmd, jstack and the rest are build-time tools, and shipping them hands a foothold to anyone who gets code execution.

BuildKit cache mounts and build secrets

The classic dependency trick — copy pom.xml first, run mvn dependency:go-offline, then copy the source — works, but it is a workaround for a missing feature. Any change to the POM throws the whole download away, the "offline" step never quite matches what the real build resolves, and it does nothing for a monorepo with a dozen modules. BuildKit's RUN --mount=type=cache solves it directly: the target directory is a persistent cache volume owned by the builder, shared across builds and not written into any layer. Mount /root/.m2, /root/.gradle or /root/.npm and dependency resolution goes from minutes to seconds without contorting the Dockerfile. The cache is a build-time convenience, not a source of truth — the build must still succeed on a cold builder, and in CI you point the cache at the registry with --cache-from / --cache-to because each runner starts empty.

Secrets get the same treatment. Passing a token via ARG or ENV writes it into image metadata that docker history will happily print, and deleting the file in a later RUN does not remove it from the earlier layer — the image is an append-only stack, so a leaked credential is leaked permanently and must be rotated. RUN --mount=type=secret,id=... exposes the value as a file only for the duration of that one command, in a tmpfs that is never committed. Use it for private registry credentials, an .npmrc token or an SSH key for a private Git dependency, and add --mount=type=ssh when you need agent forwarding.

# syntax=docker/dockerfile:1
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY . .
# persistent, never baked into a layer:
RUN --mount=type=cache,target=/root/.m2 \
    --mount=type=secret,id=mvnsettings,target=/root/.m2/settings.xml \
    mvn -B -DskipTests package

# docker build --secret id=mvnsettings,src=$HOME/.m2/settings.xml .

buildx: multi-architecture images and Bake

Developer laptops are increasingly arm64 while most cluster nodes are still amd64, and an image built on one will not start on the other — you get exec format error, the most common "works on my machine" failure of the container era. docker buildx build --platform linux/amd64,linux/arm64 builds both and publishes a manifest list: a single tag whose index points at one image per architecture, so every host pulls the right one automatically. It needs a builder with the docker-container driver (the default driver cannot produce manifest lists), and the foreign architecture is either emulated through QEMU — correct but slow, and prone to failures in native toolchains — or, much better for CI, farmed out to a native remote builder node.

Two habits keep multi-arch builds fast. First, use the automatic platform arguments — --platform=$BUILDPLATFORM on the build stage so compilation runs natively, with $TARGETARCH passed in to cross-compile — so only the tiny runtime stage is architecture-specific. Second, once the command line grows past a couple of targets, move it into a Bake file: docker buildx bake reads an HCL/JSON definition of targets, platforms, tags and cache settings, builds them in parallel, and gives CI and developers one declarative file instead of a shell script nobody can read.

docker buildx create --name multi --driver docker-container --use

docker buildx build \
  --platform linux/amd64,linux/arm64 \
  --cache-from type=registry,ref=registry.example.com/shop-api:cache \
  --cache-to   type=registry,ref=registry.example.com/shop-api:cache,mode=max \
  -t registry.example.com/shop-api:1.4.0 --push .

docker buildx imagetools inspect registry.example.com/shop-api:1.4.0   # see the manifest list

Runtime wiring: networks, volumes, bind mounts and tmpfs

Containers on the default bridge network can reach each other only by IP address, which is why the first thing any real setup does is create a user-defined bridge: on one of those, Docker's embedded DNS resolves container names, so jdbc:postgresql://db:5432/shop just works and survives a restart that changes the IP. host networking removes the network namespace entirely — full host performance, no port mapping, and no isolation, and it is Linux-only — while none gives a container no connectivity at all. Publishing with -p 8080:8080 is a separate concern from container-to-container traffic: services that only talk to each other need a shared network, not published ports.

Storage has three shapes and the distinction is a reliable interview question. A named volume is managed by Docker under its own directory, is portable across hosts through volume drivers, and is the correct home for database files and any state that must outlive the container. A bind mount maps a specific host path into the container — perfect for mounting source code during development or dropping in a config file, but it couples the container to the host's filesystem layout and permissions, so it belongs in development and in deliberate config-injection cases. tmpfs lives in RAM and vanishes on stop: use it for scratch space and for secrets you never want written to disk. And keep the container's own writable layer for nothing important — the whole point of the model is that deleting the container should lose no data.

docker network create shop-net                       # user-defined bridge: DNS by name
docker volume create pgdata                          # managed, survives the container

docker run -d --name db --network shop-net \
  -v pgdata:/var/lib/postgresql/data postgres:16

docker run -d --name api --network shop-net -p 8080:8080 \
  -e SPRING_DATASOURCE_URL='jdbc:postgresql://db:5432/shop' \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --read-only registry.example.com/shop-api:1.4.0

Resource limits and the container-aware JVM

By default a container may use every core and every byte the host has. --memory and --cpus set cgroup limits, and their failure modes differ sharply: exceeding the memory limit gets the process killed by the kernel OOM killer with exit code 137 and no stack trace, while exceeding the CPU limit merely throttles you — latency degrades, nothing dies, and it is far harder to spot. Set both anyway; an unlimited container is a noisy neighbour that can take down everything else on the node, and orchestrators need declared requests to schedule sanely.

Then the Java-specific part that interviewers love. Old JVMs read /proc/meminfo, saw the host's 64 GB, sized the default heap at a quarter of it, and were killed the moment the workload grew past a 512 MB container limit — the classic "my container keeps dying at exit 137". Since JDK 10 (backported to late 8u) the JVM is container-aware: UseContainerSupport is on by default and it reads the cgroup limit instead. So the modern knob is -XX:MaxRAMPercentage, not -Xmx — a percentage travels correctly when the container is resized, a hard -Xmx does not. Leave real headroom, because heap is not the whole footprint: metaspace, thread stacks, code cache, GC structures and direct byte buffers are all outside it, so 75% of a 512 MB limit is a sensible starting point and native memory tracking is how you tune it. CPU matters too — --cpus feeds availableProcessors(), which sizes GC threads, the common ForkJoinPool and most connection pools, and giving a JVM less than one full CPU is a reliable way to produce mysterious latency.

docker run -d --name api \
  --memory=512m --memory-swap=512m --cpus=1.5 \
  -e JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75.0 -XX:+UseSerialGC -XX:MaxMetaspaceSize=128m" \
  registry.example.com/shop-api:1.4.0

# prove the JVM sees the limit, not the host:
docker run --rm --memory=512m eclipse-temurin:21-jre-jammy \
  java -XX:+PrintFlagsFinal -version | grep -E 'MaxHeapSize|ActiveProcessorCount'

HEALTHCHECK: telling the platform what "working" means

A running process is not a working service. A JVM that has deadlocked, lost its database pool or wedged in a full-GC loop is still Up as far as the daemon is concerned, so without a health probe an orchestrator will keep routing traffic to it. HEALTHCHECK declares a command whose exit status defines health — 0 healthy, 1 unhealthy — and the container's status becomes starting, then healthy or unhealthy. The four options that matter are --interval (how often), --timeout (how long before the probe itself counts as a failure), --retries (consecutive failures before the verdict flips) and --start-period, the grace window during which failures do not count — indispensable for a Spring Boot app that needs half a minute to warm up.

Design the probe, do not copy it. It must be cheap, local and dependency-light: hitting /actuator/health/readiness is right, hitting an endpoint that fans out to three downstream services is a way to make one dependency's outage restart your whole fleet. Prefer a readiness-style check that reports whether this instance can serve traffic now, and keep liveness dumber than readiness. Two practical notes: the probe binary has to exist inside the image, which is exactly what a distroless base takes away, so people either add a small static healthcheck binary or rely on the orchestrator instead; and in Kubernetes the Dockerfile's HEALTHCHECK is ignored entirely — liveness, readiness and startup probes in the pod spec take over — so it is Compose and plain Docker where it earns its keep.

HEALTHCHECK --interval=30s --timeout=3s --start-period=40s --retries=3 \
  CMD wget -q --spider http://localhost:8080/actuator/health/readiness || exit 1

# docker inspect --format='{{.State.Health.Status}}' api   -> starting | healthy | unhealthy

Image scanning, SBOMs and the security posture of an image

Every image inherits the vulnerabilities of everything inside it, and the base image contributes most of them. Scanning turns that into a fact you can act on: docker scout cves, Trivy and Grype all enumerate the OS packages and application dependencies in an image, match them against vulnerability feeds, and — most usefully — tell you which layer introduced each finding, so "bump the base tag" versus "upgrade this library" is an evidence-based decision rather than a guess. Wire it into CI with a severity gate (--severity HIGH,CRITICAL --exit-code 1) so a regression fails the build, and re-scan published images on a schedule: an image that was clean at build time accumulates CVEs while sitting in the registry, because the disclosures are new, not the bytes.

An SBOM — a software bill of materials, usually SPDX or CycloneDX — is the inventory that makes this fast. Generate and attach one at build time with docker buildx build --sbom=true --provenance=true, and the next Log4Shell-scale disclosure becomes a query over your registry instead of a week of archaeology. Round the posture out with the things scanners cannot see: a non-root USER, --read-only with explicit tmpfs for scratch, dropped Linux capabilities, no secrets in ENV, a .dockerignore that keeps .git and .env out of the build context, and tags pinned by digest so what you scanned is what you deploy.

docker scout cves registry.example.com/shop-api:1.4.0
docker scout recommendations registry.example.com/shop-api:1.4.0   # better base image tags

trivy image --severity HIGH,CRITICAL --exit-code 1 registry.example.com/shop-api:1.4.0
grype registry.example.com/shop-api:1.4.0

docker buildx build --sbom=true --provenance=true -t registry.example.com/shop-api:1.4.0 --push .

Interview questions

Production Docker is the DevOps topic Indian product and service companies probe hardest, because it is where a candidate either has shipped something or has only read about it. Image size and the JVM memory question come up almost every round:

Beginner What is a multi-stage build and why use one?

A Dockerfile with more than one FROM. Earlier stages hold the build toolchain (JDK, Maven, Node); the final stage starts from a small runtime base and pulls in only the built artifact with COPY --from. Everything in the discarded stages never reaches the shipped image, so you get a much smaller image and a much smaller attack surface without any cleanup commands.

Beginner How do you reduce the size of a Docker image?

In order of impact: use a multi-stage build so the toolchain never ships; choose a smaller base (a JRE tag, slim, distroless) instead of a full distro plus JDK; use a .dockerignore so the build context excludes .git, target and node_modules; combine related RUN steps and clean package-manager caches within the same layer; do not install debugging tools you will not use; and layer the artifact (Spring Boot layered jars) so pushes and pulls transfer only what changed. Then measure with docker history and docker scout to see which layer is actually large.

Beginner Volume vs bind mount — when do you use each?

A named volume is managed by Docker in its own storage area, is host-path independent, works with volume drivers and is the right place for persistent state such as database files. A bind mount maps an exact host directory into the container, which makes it ideal for live-reloading source code in development or injecting a config file, but it ties the container to the host's filesystem layout and permissions. Production data goes in volumes; bind mounts are mostly a development and configuration tool. tmpfs is the third option: in-memory, gone on stop, good for scratch and secrets.

Beginner Why should the runtime image use a JRE rather than a JDK?

The JDK adds the compiler and the whole diagnostic toolchain, which is a hundred-plus megabytes you do not need to run a jar, plus extra CVE surface and a ready-made toolkit for anyone who gets code execution in your container. The JDK belongs in the build stage. If you need to go smaller still, build a custom runtime with jlink; if you need diagnostics in production, attach them deliberately rather than shipping them by default.

Intermediate What are Spring Boot layered jars and what problem do they solve?

A fat jar copied as one COPY is one large layer, so a one-line code change produces a completely new sixty-megabyte layer to push and pull. A layered jar carries a layer index splitting it into dependencies, spring-boot-loader, snapshot-dependencies and application. You extract it in the build stage with java -Djarmode=tools -jar app.jar extract --layers (or the older layertools jarmode) and issue one COPY per layer, stable ones first. A code change then invalidates only the small application layer, and the dependency layer stays cached.

Intermediate Why is Alpine risky as a base image for Java?

Alpine uses musl libc, not glibc, and the JVM plus most native libraries are built and tuned for glibc. Musl-native OpenJDK builds do exist now, but you can still meet different thread-stack and allocator behaviour, DNS resolution differences, and native dependencies (Netty native transports, JNI drivers, anything compiled against glibc) with no musl build at all. For Java, a slim glibc base, a distroless Java image or UBI is the safer default; use Alpine only when you have tested the specific workload and measured a real benefit.

Intermediate How do you build an image that runs on both Apple Silicon and an amd64 server?

Use buildx with a docker-container driver builder and pass --platform linux/amd64,linux/arm64 with --push. That publishes a manifest list under one tag, and each host pulls the matching image automatically. The other architecture is built either under QEMU emulation (correct but slow) or on a native remote builder node (much faster in CI). Use $BUILDPLATFORM on the build stage so compilation runs natively and only the runtime stage is architecture-specific.

Intermediate How do you serve an Angular app from a container, and what breaks if you get it wrong?

Stage one uses a Node image to run npm ci and the production build; stage two copies the dist output (modern Angular emits dist/app/browser) into nginx and ships no Node at all. The classic bug is the missing SPA fallback: a hard refresh on a router-only path such as /orders/42 makes nginx look for a file that does not exist and return 404. One try_files $uri $uri/ /index.html directive fixes it. Also remember that build-time configuration is frozen per image, so per-environment settings should be fetched at runtime rather than rebuilt per environment.

Intermediate Two containers need to talk to each other. How do you wire that up?

Put them on a user-defined bridge network and address each other by container or service name — Docker's embedded DNS resolves names on user-defined networks, unlike the legacy default bridge where only IP addresses work. Published ports (-p) are for reaching a container from the host or outside world and are not needed for container-to-container traffic; leaving a database unpublished but on the shared network is the more secure default.

Pro Your Java container is killed with exit code 137 despite a 512m limit and no obvious leak. Diagnose it.

Exit 137 is the kernel OOM killer: the cgroup's memory limit was exceeded. Two usual causes. On an old JVM without container support, the heap was sized from the host's total RAM, so the default max heap alone exceeded the limit — fix by upgrading, or by setting the size explicitly. On a modern JVM the more likely cause is that heap is not the whole footprint: metaspace, thread stacks, code cache, GC structures and direct byte buffers all live outside it, so a MaxRAMPercentage set too close to 100 leaves no room for native memory. Set MaxRAMPercentage around 70–75, cap MaxMetaspaceSize and direct memory, and use native memory tracking to see where the rest is going.

Pro Why is -XX:MaxRAMPercentage preferred over -Xmx in a container?

Because it is relative to the cgroup limit the JVM already reads via UseContainerSupport, so the same image behaves correctly whether it is scheduled with 512 MB or 4 GB — resize the container and the heap follows. A hard -Xmx is a constant baked into the image or the manifest, so it silently wastes memory on a large limit and gets the process OOM-killed on a small one. It also keeps one image valid across environments, which is the point of building once and promoting the same artifact.

Pro A teammate passes an artifactory token with ARG and deletes the file in a later RUN. What is wrong?

Both halves are broken. Build arguments end up in image metadata that docker history will print, and layers are append-only — deleting a file in a later layer leaves the bytes readable in the earlier one, so anyone who can pull the image can extract the token. The credential must be treated as compromised and rotated. The correct mechanism is RUN --mount=type=secret, which exposes the value as a file in a tmpfs only for the duration of that command and never commits it to a layer, with --mount=type=ssh for private Git dependencies.

Pro Cache mounts versus the copy-the-POM-first trick — why prefer cache mounts?

Copying the dependency descriptor first only preserves the cache while that file is untouched: any dependency change discards every download, the pre-fetch step rarely resolves exactly what the real build needs, and multi-module projects make it unwieldy. RUN --mount=type=cache gives the builder a persistent directory for the local repository that is shared across builds and never written into a layer, so resolution stays incremental and the image stays small. The caveat is that it is builder-local, so a cold CI runner starts empty — that is what registry-backed --cache-from and --cache-to are for — and the build must still succeed with an empty cache.

Pro How do you keep a production image's vulnerability count under control over time?

Treat it as a continuous process, not a build-time check. Scan in CI with Docker Scout, Trivy or Grype and fail the build on new high or critical findings; attach an SBOM so you can answer "are we affected?" with a registry query instead of a manual audit; re-scan published images on a schedule because new disclosures land against unchanged bytes; and rebuild regularly so base-image patches actually reach production. Reduce what has to be patched by using a minimal base (distroless or a vendor-supported UBI) and pinning by digest, and pair it with the hardening scanners cannot check: non-root USER, read-only root filesystem, dropped capabilities and no secrets in the image.

Pro Your HEALTHCHECK calls an endpoint that verifies three downstream services. Critique that.

It converts a single dependency's outage into a fleet-wide restart storm: every instance reports unhealthy, the platform kills and reschedules all of them, and the restarts add load to the dependency that was already struggling. A health probe should report whether this instance can serve traffic, using cheap local checks. Keep liveness dumber than readiness, use Spring Boot's readiness group and a start-period long enough to cover warm-up, and remember Kubernetes ignores the Dockerfile HEALTHCHECK entirely in favour of pod-spec probes.
