Module: Git Fundamentals

Git looks arbitrary until you understand what it actually stores on disk. Learn the object model first and the commands stop being incantations — almost every confusing Git behaviour turns out to be an obvious consequence of four object types and three trees.

Knowledge Library → Courses → DevOps and Deployment track → Git Fundamentals

What this module covers

This module opens the DevOps track, and it deliberately teaches Git from the inside out. Most people learn Git as a list of commands to memorise, which is why the same handful of situations — a detached HEAD, a file that refuses to be ignored, a reset that ate an afternoon's work — keep catching them out. The underlying data structure is small enough to hold in your head: a content-addressed store of four object types, plus a set of pointers into it.

We start with blobs, trees, commits and tags and the SHA hashing that names them; then refs, HEAD and why a branch is nothing more than a movable file containing one commit id. From there the three trees — working directory, index and HEAD — explain exactly what add, commit, restore, checkout and the three flavours of reset do. The second half is the daily surface: the everyday command loop, remotes, real diff fluency, and the history-inspection commands that turn a repository into a searchable record of why the code looks the way it does.

Topics

The four object types: blob, tree, commit, tag

Everything Git stores lives in .git/objects as one of four immutable object types. A blob is the raw bytes of a file — no name, no path, no permissions, just content. A tree is a directory listing: a table of entries, each holding a mode, a type, an object id and a name, pointing at blobs (files) or other trees (subdirectories). A commit points at exactly one top-level tree and at zero or more parent commits, and adds the author, committer, timestamps and message. An annotated tag is a fourth object that points at a commit and carries its own message and tagger — which is why annotated tags survive in the object database while lightweight tags are merely a ref.

Why it matters: this is the entire model. Branches, merges, rebases, stashes and remote tracking are all bookkeeping on top of these four types. Once you can say "a commit is a pointer to a tree plus pointers to parents" you can reason about history as a directed acyclic graph, and interview questions about detached HEAD, dangling commits and orphaned objects answer themselves. Note also what is not in the model: file renames. Git stores no rename record at all — git log --follow and diff rename detection infer them after the fact by comparing content similarity.

# Look at the objects directly — this is the whole database
git cat-file -t HEAD              # commit
git cat-file -p HEAD              # tree id, parent id, author, message
git cat-file -p HEAD^{tree}       # the directory listing
git cat-file -p HEAD:README.md    # the blob's raw bytes
git rev-parse HEAD                # the commit's own object id

Content addressing: why a commit is a snapshot, not a diff

Git names every object by the SHA hash of its own contents (SHA-1 historically, with SHA-256 repositories now supported). The name is a checksum, so an object can never be silently altered — change one byte and you have a different object with a different id. Identical content is stored once no matter how many times it appears, and because a commit's id incorporates its tree and its parents, a commit id transitively fingerprints the entire history that leads to it. That is why rewriting any commit changes the id of every commit after it, and why comparing two repositories reduces to comparing a few hashes.

The consequence people get wrong in interviews: a Git commit is a full snapshot of the tree, not a delta against its parent. Older systems such as Subversion stored per-file change lists; Git stores the complete state and shares unchanged blobs by identity. Diffs are computed on demand when you ask for them. (Packfiles do apply delta compression on disk to save space, but that is a storage optimisation underneath the model, not the model itself.) This is what makes branching cheap, git checkout of an old revision instant, and history verifiable.

Refs and HEAD: branches are movable pointers, nothing more

A ref is a file under .git/refs whose entire content is an object id. refs/heads/main is your local branch, refs/remotes/origin/main is your last-known position of the remote's branch, refs/tags/v1.0 is a tag. Creating a branch writes a 41-byte file, which is why it is instantaneous and why "branches are expensive" habits carried over from older tools make no sense here. HEAD is one level of indirection above: normally it contains ref: refs/heads/main, meaning "I am on main", so committing advances the branch pointer automatically.

Detached HEAD is simply HEAD holding a raw commit id instead of a ref name. Nothing is broken; you are just not on a branch, so new commits are reachable from nothing once you leave, and garbage collection will eventually reap them. The fix is always the same — git switch -c some-branch to give those commits a name. Understanding refs also demystifies merge: a fast-forward merge is Git noticing the target is an ancestor and simply moving the pointer forward, with no merge commit at all.

cat .git/HEAD                     # ref: refs/heads/main
cat .git/refs/heads/main          # a single 40-character object id
git symbolic-ref HEAD             # the same, the supported way
git branch feature                # creates one small file; O(1), not O(repo)
git switch -c rescue              # give a detached HEAD's commits a name

The three trees: working directory, index and HEAD

Git manages three views of your project simultaneously. HEAD is the snapshot of the last commit on the current branch. The index (also called the staging area or cache — one binary file at .git/index) is the proposed next commit. The working directory is the actual files on disk you edit. Nearly every core command is best described as "which of these three does it move data between": git add copies working directory to index, git commit turns the index into a new commit and moves HEAD's branch to it, git restore copies out of the index or a commit back into the working directory.

git reset is the command that finally makes sense in this frame, because its three modes stop one step further each time. --soft moves the branch pointer only, leaving index and working directory untouched (this is how you squash the last three commits into one staged change). --mixed, the default, also resets the index, so your changes survive as unstaged edits. --hard resets all three and is the only one that destroys uncommitted work — everything else is recoverable through the reflog. Note the modern split: git switch changes branches and git restore restores files, taking over the two unrelated jobs that git checkout historically did in one overloaded command. They have been available since Git 2.23 and are far clearer for beginners, but checkout is not deprecated and is still what most teams actually type, so you need to read both.

git reset --soft  HEAD~1   # branch moves back; index + files untouched
git reset          HEAD~1   # (--mixed) branch + index move back; files kept
git reset --hard  HEAD~1   # all three move back; uncommitted work is gone

git restore --staged file.txt   # unstage: index <- HEAD, working copy kept
git restore file.txt            # discard edits: working copy <- index
git switch main                 # change branch (the old: git checkout main)

The staging area in practice: add, status and partial commits

The index exists so that what you commit is a deliberate choice rather than whatever happens to be on disk. This is the feature that distinguishes Git from most tools that came before it, and skipping it with a reflexive git commit -am throws away the main benefit: you fixed a bug and also reformatted an unrelated file, and those belong in two commits so the bug fix can be reviewed, reverted or cherry-picked on its own. git add -p stages selected hunks within a file interactively, so even a single messy file can be split into clean commits.

Read git status carefully rather than skimming it: it reports three distinct groups — staged ("Changes to be committed"), unstaged tracked changes ("Changes not staged for commit") and untracked files — and it tells you the exact command to undo each one. git status --short gives the two-column form worth learning, where the left column is the index state and the right column the working tree, so MM means "staged, then edited again" and only the staged version will be committed. Also know that git commit -a stages modifications and deletions of already-tracked files but never adds untracked ones.

git add -p            # stage hunk by hunk; the habit that produces clean commits
git status --short    # XY columns: X = index, Y = working tree
git diff              # what you have NOT staged
git diff --staged     # what you are about to commit
git commit --amend    # fold staged changes into the previous commit

.gitignore: patterns, precedence, and the already-tracked trap

.gitignore holds glob patterns for paths Git should not offer as untracked. The rules that actually matter: a leading slash anchors the pattern to the directory containing the file, a trailing slash matches directories only, * does not cross a slash but ** does, and a leading ! re-includes something previously excluded. Later rules override earlier ones. There is one exception that trips everyone: you cannot re-include a file if one of its parent directories is excluded, because Git never descends into an excluded directory to find it — you must un-exclude the directory first, then exclude its contents.

The classic trap is that .gitignore only affects untracked files. Once a file has been committed, Git keeps tracking it forever and adding it to the ignore file changes nothing. The fix is git rm --cached to stop tracking while keeping the file on disk, then commit that removal. Two more things to know for real projects: ignore rules can also live outside the repository, in .git/info/exclude for repo-local personal rules and in a global core.excludesFile for editor and OS noise that has no business in a shared file; and secrets committed by accident are not removed from history by any of this, since the blob remains in every past commit and must be treated as leaked and rotated.

build/            # any directory named build, at any depth
/dist             # only dist at the repository root
*.log             # every .log file
!important.log    # ...except this one
docs/**/tmp/      # ** crosses directory boundaries

# Already committed? The ignore rule does nothing until you untrack it:
#   git rm --cached secrets.env
#   git check-ignore -v path/to/file   shows WHICH rule matched

The everyday loop: status, add, commit, branch, switch, merge

Ninety percent of real Git use is a short cycle: check status, stage deliberately with add, write a commit message that says why rather than restating the diff, create or switch a branch, and merge when the work is reviewed. Commit small and often — a commit that changes one thing is a commit you can revert, cherry-pick, bisect across or explain in a review. The message convention worth adopting early is a short imperative subject line under about fifty characters, a blank line, then a body explaining the reasoning and any ticket reference; tools, changelogs and git log --oneline all assume that shape.

Merging comes in two flavours you should be able to name. If the branch you are merging into has not moved, Git performs a fast-forward: no merge commit is created, the pointer simply advances. If both branches have new commits, Git performs a three-way merge using the common ancestor, producing a merge commit with two parents. Use --no-ff when you want the merge commit to record that a feature branch existed even where a fast-forward was possible. Conflicts are not errors: Git stages what it could resolve, leaves conflict markers in the rest, and waits for you — the deeper mechanics of conflict resolution, rebase and recovery are the subject of the next module.

Remotes: clone, fetch, pull and push

A remote is a named URL — origin by convention — plus a set of remote-tracking refs under refs/remotes/origin/. Those refs are your local cache of where the remote's branches were the last time you talked to it; they are not live, and this is the single most useful thing to understand about remotes. git fetch downloads new objects and updates those tracking refs without touching your working directory at all, so it is always safe to run. git pull is fetch followed immediately by a merge (or a rebase with --rebase) into your current branch, which is why pull can produce conflicts and fetch never can.

Prefer fetch plus an explicit look at what arrived when the stakes are high: git log --oneline HEAD..origin/main shows exactly what you are about to take. On the push side, git push -u origin feature sets the upstream so later pushes and pulls need no arguments; a push is rejected when the remote has commits you do not, and the correct response is to integrate them, never --force on a shared branch. If you must overwrite a branch you own, use --force-with-lease, which refuses when someone else has pushed since your last fetch.

git fetch origin                       # safe: updates origin/* refs only
git log --oneline HEAD..origin/main    # what would pull bring in?
git log --oneline origin/main..HEAD    # what have I not pushed?
git pull --rebase                      # fetch + rebase; linear local history
git push -u origin feature             # set upstream on the first push

Diff mastery: which two of the three trees are you comparing?

Most confusion about git diff disappears once you ask which pair of trees it is comparing. Plain git diff compares the working directory against the index — your unstaged changes. git diff --staged (identical to --cached) compares the index against HEAD — precisely what a commit right now would contain. git diff HEAD compares the working directory against HEAD — everything you have changed since the last commit, staged or not. Getting this wrong is why people commit half of what they meant to, and it is asked in interviews constantly.

Beyond the three defaults, a handful of options do real work. --stat gives a per-file summary instead of a wall of text, which is the right first look at any large change. --word-diff highlights changed words rather than whole lines, indispensable for prose, config and long lines. Two dots versus three matters: git diff main..feature compares the two endpoints, while git diff main...feature compares feature against the merge base, which is what a pull request actually shows you. And git diff --name-only or --name-status feeds scripts and pre-commit hooks; add -- path/ at the end to restrict any diff to a subtree.

git diff                  # working tree vs index   (unstaged)
git diff --staged         # index vs HEAD           (about to be committed)
git diff HEAD             # working tree vs HEAD    (everything)

git diff --stat           # per-file summary of insertions/deletions
git diff --word-diff      # word-level, not line-level
git diff main...feature   # vs the merge base — what a pull request shows
git diff HEAD~3 HEAD -- src/   # a range, restricted to one subtree

History inspection: log, the pickaxe, blame and show

A repository's real value is that it answers "why is this line here?" — but only if you can query it. git log --oneline --graph --all --decorate is the one invocation to memorise: it draws the branch topology as ASCII art with every ref labelled, and it turns an abstract argument about merge history into a picture. Narrow it with --since, --author, -- path/to/file, or -p to show each commit's patch inline. --follow keeps tracking a file across renames, which Git has to infer because renames are never recorded.

Three tools do the forensic work. The pickaxe, git log -S"someString", finds commits where the number of occurrences of a string changed — the fastest way to find when a function, config key or feature flag was introduced or deleted; -G is the regex variant that matches any diff line. git blame annotates each line of a file with the commit, author and date that last touched it, and -w (ignore whitespace) plus -C (detect moved code) stop a reformatting commit from taking the blame for everything. Finish with git show <commit> to read the full message and patch, and git shortlog -sn for a per-author commit count. One caution to voice in interviews: blame identifies the last change, not the responsible person — use it to find context, not culprits.

git log --oneline --graph --all --decorate   # the topology, at a glance
git log -p -- src/auth.ts                    # patches for one file
git log --follow -- src/auth.ts              # keep going across renames
git log -S"parseToken" --oneline             # pickaxe: when did this string appear?
git blame -w -C src/auth.ts                  # per-line, ignoring reformatting
git show a1b2c3d                             # full message + patch
git shortlog -sn                             # commits per author

Interview questions

Git is asked in nearly every Indian interview loop, from a service-company screening round to a product-company system-design panel — the beginner questions are pure recall, but the later ones separate candidates who understand the object model from those who memorised a command list:

Beginner What are the four object types Git stores, and what does each hold?

Blob (raw file content, no name), tree (a directory listing of mode, type, object id and name entries pointing at blobs or other trees), commit (one tree pointer, zero or more parent pointers, author, committer, timestamps and message) and annotated tag (a pointer to a commit plus a tagger and message). Everything else in Git is bookkeeping on top of these.

Beginner What is the staging area and why does Git have one?

The index is a binary file at .git/index holding the proposed next commit. It exists so that what you commit is a deliberate selection rather than the whole working directory — you can fix a bug and reformat a file, then commit them separately. git add -p even lets you stage part of a single file.

Beginner Difference between git fetch and git pull?

Fetch downloads new objects and updates the remote-tracking refs (origin/main) without touching your branch or working directory — it is always safe. Pull is fetch plus an immediate merge (or rebase with --rebase) into your current branch, so it can produce conflicts and change your files.

Beginner git diff vs git diff --staged vs git diff HEAD?

Plain diff: working directory against the index, i.e. what is not yet staged. --staged (or --cached): the index against HEAD, i.e. exactly what a commit would contain right now. diff HEAD: working directory against HEAD, i.e. everything changed since the last commit whether staged or not.

Beginner I added a file to .gitignore but Git still tracks it. Why?

Ignore rules apply only to untracked files. Once a path is in the index Git keeps tracking it regardless of any pattern. Run git rm --cached path to stop tracking while keeping the file on disk, then commit that removal. Use git check-ignore -v path to see which rule (if any) is matching.

Beginner What are git switch and git restore, and do they replace checkout?

They split the two unrelated jobs git checkout did: switch changes branches, restore restores file contents from the index or a commit. Introduced in Git 2.23, they are clearer and less error-prone. checkout is not deprecated and remains what most teams type, so you should be fluent in both.

Intermediate Explain the three modes of git reset.

All three move the current branch pointer; they differ in how far the effect propagates through the three trees. --soft stops there — index and working directory keep your changes, which is how you squash the last N commits into one staged change. --mixed (the default) also resets the index, so changes remain as unstaged edits. --hard also resets the working directory and is the only one that discards uncommitted work.

Intermediate Is a Git commit a snapshot or a delta against its parent?

A snapshot. Each commit points at a complete tree of the project; unchanged files simply reuse the same blob object because the content hash is identical, so snapshots cost almost nothing. Diffs are computed on demand. Packfiles do delta-compress objects on disk, but that is a storage optimisation, not the data model — and this is exactly where Git differs from Subversion.

Intermediate What is detached HEAD, how do you get into it, and how do you get out?

HEAD normally contains a symbolic ref like ref: refs/heads/main. Checking out a commit id, a tag, or a remote-tracking ref puts a raw object id in HEAD instead, so you are not on any branch. Commits made there are reachable from nothing once you leave and will eventually be garbage collected. Escape with git switch -c newbranch to name them, or git switch - to abandon them; the reflog can still recover them for a while.

Intermediate Why is creating a branch in Git effectively free?

A branch is a file under .git/refs/heads/ containing a single 40-character object id. Creating one writes 41 bytes; no files are copied and no history is duplicated. Switching branches just rewrites HEAD and updates the working tree to match the target commit's tree, reusing blobs that are already present.

Intermediate How do you find the commit that introduced a particular string or function?

The pickaxe: git log -S"parseToken" --oneline lists commits where the count of that string changed, so it finds both the introduction and the deletion. git log -G"regex" matches any diff line against a regular expression instead. Add -p to see the patches, or a pathspec to narrow the search. For line-level history use git log -L; for the current state of each line use git blame.

Intermediate When does a merge fast-forward, and when do you avoid it?

Fast-forward happens when the target branch is an ancestor of the branch being merged — Git just moves the pointer forward and creates no merge commit. Pass --no-ff when you want an explicit merge commit recording that a feature branch existed, which many teams require so a feature can be reverted as a unit. If both branches have diverged, Git performs a three-way merge from the common ancestor and always creates a merge commit.

Pro Two files in a repository have identical content but different names. How many blobs?

One. Blobs are content-addressed by the hash of their bytes, and they store no filename — the names live in the tree entries that point at the blob. Two identical files therefore share a single blob, and one tree holds two entries with different names and the same object id. This is also why Git records no rename information at all and has to infer renames by similarity when you ask for --follow or rename detection in a diff.

Pro What is the difference between two dots and three dots in git diff and git log?

They mean different things in the two commands, which is a common trap. In git log A..B the two-dot form lists commits reachable from B but not A, and A...B is the symmetric difference — commits in either but not both. In git diff A..B the two-dot form compares the two endpoints directly, while A...B compares B against the merge base of A and B, which is what a pull request diff shows and usually what you want when a long-lived branch has drifted.

Pro A teammate committed an AWS key, then removed it in the next commit and added the file to .gitignore. Is the repository safe?

No. The blob still exists in the earlier commit and in every clone, fork and CI cache that ever fetched it, and anyone can read it with git show. The credential must be treated as compromised and rotated immediately — that is the first action, not the last. Removing it from history additionally requires rewriting every affected commit (git-filter-repo or BFG) plus a force push and re-clone by everyone, and on a hosted platform you should also contact support because cached views can persist. The ignore rule prevents recurrence but fixes nothing already committed.

Pro Your push is rejected as non-fast-forward. Walk through your options, including when force is acceptable.

Rejection means the remote branch has commits you do not have, so accepting your push would drop them. Correct response: git fetch, inspect with git log --oneline HEAD..origin/main, then integrate by merge or rebase and push again. Plain --force on a shared branch destroys other people's commits and is unacceptable. On a personal feature branch that you alone own — typically after an amend or interactive rebase — use --force-with-lease, which refuses the push if the remote moved since your last fetch and so cannot silently clobber a colleague.

Pro How would you split one large uncommitted change into three reviewable commits?

Use the index as the selection tool: git add -p and accept only the hunks belonging to the first logical change, verify with git diff --staged, commit, and repeat. If the change is already in one commit, git reset --soft HEAD~1 puts it back in the index (or --mixed to unstage entirely) and you re-stage in pieces. Keep each commit independently buildable so bisect and revert stay useful, and mention that a commit doing one thing is the precondition for cherry-picking and clean review.
