Module: Docker Fundamentals

A container is not a small virtual machine. It is an ordinary process on the host kernel, fenced off by namespaces, capped by cgroups, and given a filesystem assembled from stacked read-only layers. Everything that surprises people about Docker follows from that one sentence.

Knowledge Library → Courses → DevOps and Deployment → Docker Fundamentals

What this module covers

Two things, and they map one-to-one onto the two halves of using Docker well. First, the runtime model: what a container actually is at the kernel level, how an image differs from a container, what a layer is, how digests and tags identify content, where registries fit, and the command lifecycle you will run a hundred times a day. Second, the build model: BuildKit — the default builder since Docker Engine 23 — the Dockerfile instruction set, the build context that gets shipped to the builder, and the instruction ordering that decides whether your builds take four seconds or four minutes.

The production concerns — multi-stage builds, slim base images, multi-architecture builds, resource limits and image scanning — are the next module. This one gets the mental model right first, because almost every Docker mistake in production is a misunderstanding from this page, scaled up.

Topics

A container is a process, not a lightweight VM

The "lightweight VM" analogy is the single most expensive misconception in this field, and it is worth killing before anything else. A virtual machine boots its own kernel on virtualised hardware. A container does not boot anything: docker run starts an ordinary Linux process on your kernel, and then the kernel lies to it about the world. Namespaces provide the lies — a PID namespace so the process believes it is process 1 with no siblings, a mount namespace so it sees a different root filesystem, plus network, UTS, IPC, user and cgroup namespaces. Control groups (cgroups) provide the limits: how much CPU, memory, and I/O bandwidth that process tree may consume. The root filesystem it sees is a union (overlay) filesystem stitched together from stacked image layers.

Three practical consequences fall straight out of that model, and interviewers probe all three. Containers start in milliseconds because there is no kernel to boot and no hardware to emulate — you are just forking a process with unusual flags. Containers share the host kernel, so a Linux image cannot run natively on a Windows or macOS kernel (Docker Desktop quietly runs a Linux VM for you) and a kernel-level vulnerability such as a container escape is a host-level compromise. And a container is not the security boundary a VM is: the isolation is kernel-enforced policy, not hardware separation, which is why running as root inside a container, mounting the Docker socket, or using --privileged are all treated as serious findings in a review.

# The container's "PID 1" is just a host process wearing a namespace
docker run -d --name web nginx
docker top web                 # host-side view: real PIDs on the host kernel
docker exec web ps -e          # container-side view: PID 1 is nginx

# cgroups are the cap, namespaces are the fence
docker run --memory 256m --cpus 0.5 --pids-limit 100 alpine sleep 600

Images versus containers: read-only layers and one thin writable layer

An image is an immutable, ordered stack of read-only filesystem layers plus a JSON metadata blob (default command, environment, exposed ports, working directory, user). Each layer is a diff — the set of files added, changed or deleted relative to the layer beneath it. A container is that stack plus one thin writable layer on top, unioned together by a storage driver (overlay2 on modern Linux). When the process inside writes to a file that lives in a lower layer, the driver copies it up into the writable layer first; that copy-on-write step is why writing a large file inside a container is slower than writing to a volume, and why heavy write workloads belong in volumes rather than the container filesystem.

Say the relationship out loud until it is automatic: image is to container as class is to instance, or as executable is to process. Ten containers from one image share exactly one copy of the read-only layers on disk and differ only in their writable layers — which is the whole reason containers are cheap. And because that writable layer is deleted with the container, anything not written to a volume or a bind mount is gone the moment you docker rm. Layers are also the unit of transfer: pulling a new image version only downloads the layers you do not already have, which is why base image discipline pays for itself across an estate.

docker image history myapp:1.4.0   # every layer, its size, the instruction that made it
docker image inspect myapp:1.4.0   # RootFS.Layers (the diff ids) + Config metadata
docker diff web                    # A/C/D report of the container's writable layer
docker system df                   # how much of your disk is layers vs writable vs volumes

Tags versus digests: why :latest is not a version

An image is identified two ways, and only one of them is trustworthy. A tag is a mutable human label pointing at a manifest — myapp:1.4.0, node:22-alpine. A digest is the content-addressed SHA-256 hash of the manifest — myapp@sha256:ab3f… — and it is immutable by construction: change one byte of any layer and you get a different digest. Tags can be moved, overwritten and deleted; digests cannot. This is why reproducible builds and supply-chain policies pin base images by digest, and why docker pull prints the resolved digest even when you asked for a tag.

The :latest trap deserves its own paragraph because it is asked in interviews and it breaks real deployments. latest is not a keyword and carries no semantics whatsoever — it is simply the tag Docker assumes when you omit one. It is not "the newest image", it is "whatever someone last happened to tag latest", which might be six months old or might be a breaking major version pushed an hour ago. Deploying myapp:latest also makes rollback impossible (there is no previous tag to go back to) and makes two nodes pulling at different moments run different code. Tag deliberately instead: an immutable version tag such as 1.4.0 or the Git commit SHA, plus optional moving convenience tags such as 1.4 and stable.

# One image, several names; tagging is just adding a reference
docker build -t myapp:1.4.0 -t myapp:1.4 -t ghcr.io/acme/myapp:1.4.0 .

# Pin by digest when you need byte-for-byte reproducibility
docker pull node@sha256:cf1a2b9d0e4c7f8a6b5d3e2c1f0a9b8c7d6e5f4a3b2c1d0e9f8a7b6c5d4e3f2a

Registries: Docker Hub, GHCR, ECR — push, pull, authentication

A registry is the distribution layer: a content-addressed store of image manifests and layer blobs, spoken to over a standard HTTP API. Docker Hub is the default (an unqualified nginx means docker.io/library/nginx), but every serious team also uses a registry attached to their platform — GitHub Container Registry (ghcr.io) alongside GitHub Actions, Amazon ECR for AWS workloads, Azure ACR, Google Artifact Registry, or a self-hosted Harbor or Nexus. The registry name is simply the first path component of the image reference, which is why retagging is all that is needed to move an image between registries.

Two operational facts to carry into a real job. Authentication is per-registry via docker login, which writes credentials to ~/.docker/config.json — in CI you almost never want a long-lived password there; use a short-lived token (a GitHub Actions token for GHCR, aws ecr get-login-password for ECR, or OIDC federation) so no static secret exists to leak. And Docker Hub enforces anonymous pull rate limits per IP address: on a shared corporate NAT or a busy CI runner this shows up as sudden toomanyrequests failures in builds that worked yesterday, and the fix is to authenticate the pull or mirror the base images into your own registry.

docker login ghcr.io -u USERNAME --password-stdin < token.txt
docker tag myapp:1.4.0 ghcr.io/acme/myapp:1.4.0
docker push ghcr.io/acme/myapp:1.4.0

# ECR wants a short-lived token, never a stored password
aws ecr get-login-password --region ap-south-1 \
  | docker login --username AWS --password-stdin 123456789012.dkr.ecr.ap-south-1.amazonaws.com

The container lifecycle: run, ps, logs, exec

docker run looks like one action but is really two: docker create (materialise a writable layer and a container config from the image) followed by docker start (execute the entrypoint). Knowing that split matters because a container that has exited still exists — it keeps its writable layer, its logs and its exit code until you remove it, which is exactly what lets you debug a crash after the fact. Add --rm for throwaway runs, -d to detach, -p host:container to publish a port, -e or --env-file for configuration, -v for volumes, and --name so you are not copying hex ids around all day.

docker ps shows running containers and docker ps -a shows every container including the exited ones with their status and exit code — the first command to run when "the container does not start". docker logs reads whatever the main process wrote to stdout and stderr, which is why containerised apps log to the console rather than to files; -f follows and --tail limits. docker exec -it <name> sh opens a shell in an already running container for live inspection, and it is worth being precise about the difference between exec (join a running container) and run (create a brand new one) because candidates confuse them constantly. Round it out with inspect for the full JSON config, stats for live resource use, and cp to move a file in or out.

docker run -d --name api -p 8080:8080 --env-file .env myapp:1.4.0
docker ps -a                    # includes exited containers + exit codes
docker logs -f --tail 100 api   # stdout/stderr of PID 1
docker exec -it api sh          # shell inside the RUNNING container
docker inspect api              # full config, mounts, network, health

Stopping cleanly and cleaning up: stop versus kill, rm and prune

docker stop is polite: it sends SIGTERM to PID 1, waits for a grace period (ten seconds by default, tunable with -t), and only then sends SIGKILL. docker kill skips the courtesy and sends SIGKILL immediately. That grace period is where graceful shutdown lives — draining in-flight HTTP requests, committing a transaction, deregistering from service discovery, flushing a buffer. If your process ignores SIGTERM, or never receives it because the Dockerfile used shell form (see the ENTRYPOINT topic below), every deployment becomes a hard kill and you get truncated writes and dropped requests. The same mechanism drives Kubernetes pod termination, so understanding it here pays off twice.

Cleanup is the other half. docker rm deletes a stopped container and its writable layer; docker rmi deletes an image if nothing references it. Because layers accumulate silently, disk exhaustion on build agents is one of the most common Docker incidents in the wild, and docker system df then docker system prune is the standard response. Know exactly what the prune flags do before you type them on a shared machine: bare prune removes stopped containers, unused networks, dangling images and build cache; -a also removes every image not used by a running container; --volumes deletes anonymous volumes, which is how people destroy a local database they meant to keep.

docker stop -t 30 api      # SIGTERM, wait up to 30s, then SIGKILL
docker kill api            # SIGKILL now (or --signal to send another)
docker rm api              # remove the stopped container + its writable layer

docker system df           # ALWAYS look before you prune
docker image prune         # dangling (untagged) images only
docker builder prune       # BuildKit cache only
docker system prune -a     # everything unused — read the prompt carefully

BuildKit: the default builder, and what it changed

Since Docker Engine 23.0, docker build runs BuildKit rather than the legacy builder — and that is the answer to "why do the Docker tutorials from 2019 look different?" The old builder executed a Dockerfile strictly top to bottom, one linear chain of layers, with a cache keyed on the previous instruction. BuildKit instead parses the Dockerfile into a dependency graph and then does things the old builder could not: run independent stages in parallel, skip stages whose output nothing needs, cache more precisely (including cache mounts that persist a package-manager directory across builds), and produce far better build output.

Three BuildKit features are worth knowing by name even at fundamentals level. RUN --mount=type=cache keeps a Maven, npm or apt cache directory between builds without baking it into a layer. RUN --mount=type=secret exposes a credential to a single command without it ever landing in the image history — the correct replacement for the old ARG-a-token anti-pattern, since anyone can read build args back out of an image. And build checks lint your Dockerfile as it builds, warning about things like an undefined build argument or a stage name that shadows another. BuildKit is also what docker buildx drives for multi-platform and multi-node builds, covered in the next module.

# syntax=docker/dockerfile:1
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
# cache mount: ~/.m2 survives across builds, never becomes a layer
RUN --mount=type=cache,target=/root/.m2 mvn -q dependency:go-offline
COPY src ./src
RUN --mount=type=cache,target=/root/.m2 mvn -q -DskipTests package

# secret mount: the token is readable only by this one RUN, not by image history
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci

The Dockerfile instruction set, in practical order

A Dockerfile is a recipe, and roughly a dozen instructions cover almost everything you will write. FROM picks the base image and starts a stage. WORKDIR sets (and creates) the working directory — always use it instead of RUN cd, because each RUN is a separate shell and a cd does not survive. COPY brings files from the build context into the image; ADD does the same but additionally auto-extracts local tar archives and can fetch remote URLs, and those two conveniences are precisely why COPY is almost always the right choice — ADD's magic is implicit, its URL fetch skips your proxy and cache behaviour, and Docker's own best-practice guide says to prefer COPY. RUN executes a command and commits the result as a layer, so chain related shell commands with && and clean up package-manager caches in the same RUN; deleting a file in a later layer hides it but does not shrink the image, because the earlier layer still carries the bytes.

The rest configure the image rather than build it. ENV sets an environment variable that persists into the running container; ARG declares a build-time variable that does not — and critically, an ARG value is visible in docker history, so it must never carry a secret. EXPOSE is documentation plus a hint to tooling; it publishes nothing on its own, which surprises people, since only -p or -P at run time actually maps a port. VOLUME declares a path whose data should live outside the image. USER switches to a non-root account — Docker runs as root by default, and "container runs as root" is a standard finding in a security review, so create a user and drop to it before the final command. HEALTHCHECK teaches the engine how to test liveness, and LABEL attaches metadata such as source repository and version for supply-chain traceability.

# syntax=docker/dockerfile:1
FROM eclipse-temurin:21-jre-alpine
LABEL org.opencontainers.image.source="https://github.com/acme/myapp"

ARG APP_VERSION=1.4.0          # build time only, visible in image history
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75"   # persists into the container

WORKDIR /app
COPY --chown=app:app target/myapp.jar app.jar     # COPY, not ADD

RUN addgroup -S app && adduser -S -G app app
USER app                        # never leave the final stage running as root

EXPOSE 8080                     # documentation only; -p does the real mapping
HEALTHCHECK CMD wget -qO- http://localhost:8080/actuator/health || exit 1
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

ENTRYPOINT versus CMD, and the PID 1 signal problem

This pair is asked in almost every Docker interview, so be precise. ENTRYPOINT declares the executable the container exists to run; CMD declares default arguments. Anything you type after the image name in docker run replaces CMD and is appended to ENTRYPOINT; replacing ENTRYPOINT requires the explicit --entrypoint flag. So ENTRYPOINT ["java","-jar","/app/app.jar"] with CMD ["--spring.profiles.active=prod"] gives you a container that is always your app but whose arguments are overridable. If you specify only CMD, the whole line is the default command and any run argument replaces it entirely — convenient for general-purpose images like alpine or python, wrong for a single-purpose application image.

The subtler half is form, not choice. Exec form (a JSON array, ENTRYPOINT ["java","-jar","app.jar"]) executes the binary directly, so your process becomes PID 1 and receives SIGTERM from docker stop. Shell form (a bare string, ENTRYPOINT java -jar app.jar) is silently rewritten to /bin/sh -c "…", making the shell PID 1 — and a shell does not forward signals to its child, so your application never sees SIGTERM, sits there until the grace period expires, and is SIGKILLed. Every "my app never shuts down gracefully in Kubernetes" thread traces back to this. Prefer exec form; when you genuinely need shell features or a wrapper script, either exec the real binary as the last line of that script so it takes over PID 1, or run with --init (or add a tiny init such as Tini) to get a real init that reaps zombies and forwards signals.

# GOOD — exec form: java is PID 1 and gets SIGTERM
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
CMD ["--spring.profiles.active=prod"]     # overridable default arguments

# BAD — shell form becomes /bin/sh -c "java -jar /app/app.jar"
# sh is PID 1, never forwards SIGTERM, so shutdown is always a hard kill
# ENTRYPOINT java -jar /app/app.jar

# If a wrapper script is unavoidable, hand over PID 1 with exec:
#   #!/bin/sh
#   setup_things
#   exec java -jar /app/app.jar "$@"

The build context, and what .dockerignore is really for

The final argument to docker build — the dot in docker build -t myapp . — is not "where the Dockerfile is". It is the build context: the directory whose entire contents get packaged and transferred to the builder before the first instruction runs. That transfer is why a build in a repository with a 900 MB node_modules, a target/ full of jars, and a .git history spends ages on "transferring context" before doing any work, on every single build. It is also a correctness rule: COPY can only reach paths inside the context, which is why COPY ../shared/lib . fails and why monorepo Dockerfiles are usually built from the repository root with -f pointing at the Dockerfile.

A .dockerignore file at the context root fixes both problems at once, using the same pattern syntax as .gitignore. Excluding .git, build output, dependency directories, local environment files and IDE folders routinely takes a context from hundreds of megabytes to a few. It is a security control as well as a performance one: without it, a careless COPY . . bakes your .env, your .aws credentials or your private keys into a layer that anyone who pulls the image can extract — deleting them in a later instruction does not help, because the earlier layer still holds them. Treat .dockerignore as mandatory, not optional, and keep it at least as strict as .gitignore.

# .dockerignore — same syntax as .gitignore, at the context root
.git
.gitignore
node_modules
target/
build/
dist/
**/*.log
.env
.env.*
.aws
*.pem
.idea
.vscode
Dockerfile*
README.md

Instruction ordering: writing a Dockerfile that hits the cache

The builder caches per instruction. For each one it computes a key — for RUN the command string, for COPY and ADD a checksum of the files being copied — and reuses the existing layer if the key matches. The rule that follows is absolute: a cache miss on one instruction invalidates every instruction after it. So the ordering principle is to put the things that rarely change near the top and the things that change on every commit near the bottom. In practice that means declaring the base image, installing OS packages, then copying only the dependency manifest, resolving dependencies, and only then copying your source code.

Get it backwards — COPY . . before mvn dependency:go-offline or npm ci — and every one-character source edit changes the copied files, busts the cache, and re-downloads the entire dependency tree. The correct split turns a four-minute rebuild into a ten-second one and is one of the highest-value things you can know about Docker. Two related habits: keep the layer count sane by chaining related RUN commands with && and cleaning package caches inside the same instruction, and remember that a cache hit depends on inputs, so a RUN apt-get update alone in a layer can serve a stale package index for months — pair it with the install in one instruction.

# Dependencies first — this layer is reused until pom.xml/package.json changes
COPY pom.xml .
RUN mvn -q dependency:go-offline

# Source last — the only layer that rebuilds on an ordinary commit
COPY src ./src
RUN mvn -q -DskipTests package

# One RUN, cleanup inside it: a later "rm" cannot shrink an earlier layer
RUN apt-get update && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*

Interview questions

Docker is asked in essentially every Indian backend, full-stack and DevOps interview, from service-company screening rounds to product-company system design. The first two here are near-certainties:

Beginner What is the difference between a container and a virtual machine?

A VM virtualises hardware and boots its own guest kernel on a hypervisor; a container is a process running on the host kernel, isolated by namespaces and capped by cgroups, with a root filesystem built from union-mounted image layers. Consequences: containers start in milliseconds and use megabytes rather than gigabytes, but they share the host kernel — so a Linux image needs a Linux kernel, and the isolation is kernel-enforced policy rather than hardware separation, making a container a weaker security boundary than a VM.

Beginner ENTRYPOINT vs CMD — what is the difference, and when do you use each?

ENTRYPOINT is the executable the container always runs; CMD supplies default arguments. Arguments passed to docker run after the image name replace CMD entirely and are appended to ENTRYPOINT; overriding ENTRYPOINT needs the --entrypoint flag. Use ENTRYPOINT (exec form) plus CMD for a single-purpose application image, so the app is fixed and its flags are overridable; use CMD alone for general-purpose images where the user should be able to run anything. If both are given in exec form, the final command is ENTRYPOINT followed by CMD.

Beginner What is the difference between an image and a container?

An image is an immutable, ordered stack of read-only layers plus metadata — the template. A container is a running (or stopped) instance of that image with one thin writable layer on top. Class versus object, or executable versus process. Many containers share one on-disk copy of the read-only layers; only their writable layers differ, and that writable layer is destroyed when the container is removed.

Beginner What is a Docker layer, and what creates one?

A layer is a filesystem diff — files added, changed or deleted relative to the layer below. Instructions that change the filesystem (FROM, COPY, ADD, RUN) create layers; metadata-only instructions (ENV, LABEL, EXPOSE, CMD, ENTRYPOINT, USER, WORKDIR) update the image config rather than adding filesystem content. Layers are content-addressed and shared, so a pull only downloads the layers you do not already have.

Beginner Why is deploying myapp:latest to production a bad idea?

latest is not a version and has no special meaning — it is just the tag assumed when you omit one, and it is mutable. Two nodes pulling at different times can run different code, you cannot tell from the tag what is actually deployed, and rollback is impossible because there is no earlier tag to return to. Use an immutable version tag (SemVer or the Git commit SHA), and pin base images by digest when reproducibility matters.

Intermediate COPY vs ADD — which do you use and why?

COPY, almost always. Both copy from the build context, but ADD also auto-extracts local tar archives and can fetch remote URLs. That implicit behaviour is the problem: a file named like an archive silently expands, remote fetches bypass your caching and proxy expectations and produce unverified content in a layer, and the intent of the line is no longer obvious. Docker's own best-practice guide says to prefer COPY; the legitimate ADD cases are extracting a local tarball deliberately and, in newer syntax versions, fetching a Git repository.

Intermediate What is the build context, and why does a big one slow every build?

The context is the directory passed as the final argument to docker build; its entire contents are packaged and sent to the builder before any instruction executes. A repository containing .git, node_modules and build output can push hundreds of megabytes across on every build. It also constrains correctness — COPY cannot reference anything outside the context. Fix it with a .dockerignore at the context root, which is also a security control, since COPY . . would otherwise bake .env files and credentials into a layer.

Intermediate ENV vs ARG — what is the difference and which may hold a secret?

ARG is build-time only and is gone at run time; ENV is baked into the image config and is present as an environment variable in every container. Neither may hold a secret: ARG values are recoverable from docker history and ENV values from docker inspect. Use BuildKit's RUN --mount=type=secret for build-time credentials and inject runtime configuration through -e, an env file, or a secret manager.

Intermediate What happens, precisely, when you run docker run nginx?

The CLI asks the daemon for the image; if it is not local, the daemon resolves nginx to docker.io/library/nginx:latest, authenticates if needed, pulls the manifest and the missing layers. It then creates a container — a writable layer over the image layers, plus namespaces, cgroups and a network endpoint — and starts it by executing the image's ENTRYPOINT/CMD as PID 1 in those namespaces. run is literally create plus start, which is why an exited container still exists with its logs and exit code until you remove it.

Intermediate Does EXPOSE publish a port?

No. EXPOSE is documentation and a hint to tooling — it records which port the image listens on. Only -p hostPort:containerPort (or -P to map every exposed port to random high ports) actually publishes anything, and Compose or Kubernetes do the equivalent. You can publish a port that was never EXPOSEd, and an EXPOSEd port is unreachable from the host unless published.

Intermediate Why is BuildKit the default builder, and what did it change?

BuildKit became the default in Docker Engine 23.0. Instead of executing the Dockerfile as a linear top-to-bottom chain, it builds a dependency graph, which lets it run independent stages in parallel, skip stages nothing depends on, and cache more precisely. It adds cache mounts (a package-manager directory persisted across builds without becoming a layer), secret and SSH mounts so credentials never enter the image history, build checks that lint the Dockerfile, and it is the engine behind buildx for multi-platform builds.

Pro Your Spring Boot container is never shut down gracefully in Kubernetes. Diagnose it.

Almost certainly shell-form ENTRYPOINT. A bare string is rewritten to /bin/sh -c "…", so the shell is PID 1 and does not forward SIGTERM to the JVM; the app sits idle through the whole grace period and is then SIGKILLed, dropping in-flight requests. Fix with exec form (ENTRYPOINT ["java","-jar","app.jar"]), or if a wrapper script is genuinely needed, end it with exec java … so the JVM takes over PID 1. Then confirm the app actually handles SIGTERM (Spring Boot's graceful shutdown) and that the grace period is long enough. Running with --init or Tini also gives you signal forwarding and zombie reaping.

Pro A one-line change to a source file triggers a full dependency re-download on every build. Why, and how do you fix it?

The Dockerfile copies the whole project (COPY . .) before resolving dependencies. A COPY's cache key is a checksum of the copied files, so any source edit invalidates it — and a cache miss invalidates every subsequent instruction, including the dependency resolution. Reorder so rarely-changing inputs come first: copy only pom.xml / package.json, run mvn dependency:go-offline or npm ci, then copy the source. Add a BuildKit cache mount for the local repository directory to survive even a manifest change.

Pro A secret was committed into an image in an early layer and deleted in a later one. Is the image safe?

No. Layers are additive diffs; a deletion in a later layer only records a whiteout entry, and the earlier layer still contains the bytes. Anyone who pulls the image can extract them with docker save or by inspecting the layer tarballs, and docker history exposes build arguments too. The secret must be rotated, and the image rebuilt so the credential never enters a layer — via a BuildKit secret mount at build time, or runtime injection through environment variables or a secret manager. Prevent recurrence with a .dockerignore and image scanning in CI.

Pro Tag or digest — how would you pin images across an estate, and what do you give up?

A tag is a mutable pointer; a digest is the SHA-256 of the manifest and is immutable, so base@sha256:… is the only reference that guarantees byte-identical content on every pull. Pin base images by digest in Dockerfiles for reproducible and auditable builds, and deploy your own images by an immutable version tag (or digest) so rollback is a one-line change. The cost is that digests do not float: you no longer pick up base-image security patches automatically, so pair digest pinning with an automated bump (Renovate or Dependabot) and image scanning, otherwise you have traded a reproducibility problem for a vulnerability problem.

Pro Your CI agents keep running out of disk. What is consuming it, and how do you clean up safely?

Accumulated image layers, stopped containers, dangling images from rebuilt tags, BuildKit cache and orphaned volumes. Start with docker system df to see the split rather than guessing. Then prune narrowly: docker container prune for stopped containers, docker image prune for dangling images, docker builder prune (with a filter such as --keep-storage or an age filter) for build cache. Reserve docker system prune -a for agents, and never pass --volumes on a machine holding data you care about, since it deletes anonymous volumes. The durable fix is a scheduled prune with age filters plus a smaller build context so less is created in the first place.
