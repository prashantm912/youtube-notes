Module: Docker Compose

One command should be enough to bring up the whole system on a laptop. Compose is the file that makes that true — and, in most teams, the only architecture diagram that is actually executable.

Knowledge Library → Courses → DevOps and Deployment → Docker Compose

What this module covers

A single container is easy. A real application is a web service, an API, a database, a cache, a broker and a migration job — six containers that must be built, networked, configured and started in a workable order. Compose is the declarative file that describes that whole set and the CLI that runs it, so a new joiner clones the repo, types one command, and has the system running by lunchtime instead of by Friday.

This module covers the Compose specification and the shape of compose.yaml — services, networks, volumes — then the everyday CLI, and then the part interviews actually probe: why depends_on on its own does not do what people think it does, how healthchecks fix startup ordering properly, and how profiles, override files and variable interpolation let one repository serve local development, CI and demo environments. It closes on the operational detail that breaks pipelines at the worst moment: Docker Hub pull rate limits.

Topics

Compose today: the specification, compose.yaml, and the V1 to V2 shift

Compose stopped being "a Docker tool" and became a specification. The Compose Specification is an open, vendor-neutral schema for describing multi-container applications, implemented by Docker Compose and by other runtimes too — so what you learn here transfers. The canonical filename is now compose.yaml; docker-compose.yml still works and is looked up as a fallback, but new projects should use the modern name.

Two conventions catch out people who learned Compose a few years ago. First, the top-level version: key is obsolete — it belonged to the old versioned file formats (v2.x, v3.x) and the current specification ignores it, emitting a warning. Delete it; the schema is now determined by the keys you use, not by a version string. Second, the command is docker compose (a Go plugin bundled with the Docker CLI, known as Compose V2), not docker-compose (the standalone Python script, V1, which reached end of life and stopped receiving updates). If a tutorial hyphenates the command, it predates the current tooling — treat the rest of its advice with the same suspicion.

# compose.yaml — modern, minimal, correct
# NO `version:` key. It is obsolete and only produces a warning.
name: shop            # optional: pins the project name (else the folder name is used)

services:
  api:
    image: ghcr.io/acme/shop-api:1.4.0

The services block: image vs build, ports, environment, command, restart

Everything begins with services. Each key under it is a service name — and that name is load-bearing: it becomes the DNS hostname other containers use, the default container name prefix, and the argument you pass to nearly every CLI subcommand. A service either pulls a prebuilt image or declares a build context that Compose hands to BuildKit; declaring both means "build it, then tag it with this name", which is the pattern you want so a locally built image gets a stable tag.

The remaining keys are the ones you will type daily. ports publishes a container port on the host in HOST:CONTAINER order — the direction people reverse constantly, and the reason a service is unreachable from the browser but perfectly reachable from a sibling container. expose, by contrast, publishes nothing to the host and is rarely needed, because containers on the same Compose network can already reach each other on any port. environment sets variables inline while env_file loads them from a file (inline values win); command overrides the image's default command; and restart decides what happens when the process exits — unless-stopped is the sane default for backing services on a developer machine.

services:
  api:
    build:
      context: ./api          # build from source...
      dockerfile: Dockerfile
    image: shop/api:dev       # ...and tag the result with a stable name
    ports:
      - "8080:8080"           # HOST:CONTAINER — get the order wrong and nothing answers
    env_file: [.env]
    environment:
      SPRING_PROFILES_ACTIVE: local   # inline values override env_file
    command: ["java", "-jar", "/app/app.jar", "--server.port=8080"]
    restart: unless-stopped

Networks: the default network and service-name DNS

Compose creates a network for your project automatically and attaches every service to it, so you almost never need to write a networks block at all. Inside that network, Docker's embedded DNS resolves each service name to that service's container. The api service reaches the database at the hostname db on the database's own port — not on the host port you published, and never at localhost, because inside a container localhost means that container. That single misunderstanding accounts for a large share of "connection refused" issues in first Compose setups.

You declare explicit networks when you want segmentation — putting the database on an internal network the front end cannot reach, or marking a network internal: true so it has no route out to the internet — or when you need to join a pre-existing network with external: true, typically to talk to another Compose project. Publishing ports is then purely for your convenience as a developer: it lets your IDE, psql client or browser reach the container. Services talking to each other need no published ports whatsoever.

services:
  api:
    environment:
      # host is the SERVICE NAME; port is the CONTAINER port, not the published one
      DB_URL: jdbc:postgresql://db:5432/shop
      REDIS_HOST: cache
    networks: [backend]
  db:
    image: postgres:17
    networks: [backend]       # no `ports:` — nothing on the host needs to reach it

networks:
  backend:
    internal: true            # no egress to the internet from this network

Volumes: named volumes for data, bind mounts for source

Containers are disposable; their writable layer disappears with them. Volumes are how state survives, and Compose gives you two kinds with genuinely different jobs. A named volume is storage Docker manages for you, declared under the top-level volumes key and mounted into a service — this is what you use for PostgreSQL data directories, broker logs and upload folders. It lives outside the container lifecycle, so docker compose down followed by up finds the data intact.

A bind mount maps a host path straight into the container, and its main development use is mounting your source tree so an edit on the laptop is visible inside the container immediately, enabling hot reload without a rebuild. The trade-offs are real: bind mounts are noticeably slower on macOS and Windows than on Linux, they inherit host file ownership (the classic permission-denied on a root-created file), and mounting a source directory over a path that contains build output — the node_modules problem — hides what the image built. The usual fix is an anonymous or named volume mounted over the nested path to shadow the bind mount. For the modern alternative, develop.watch syncs and rebuilds selectively instead of mounting everything.

services:
  db:
    image: postgres:17
    volumes:
      - pgdata:/var/lib/postgresql/data     # named volume: survives `down`
  web:
    build: ./web
    volumes:
      - ./web/src:/app/src                  # bind mount: live source for hot reload
      - /app/node_modules                   # anonymous volume shadows the bind mount

volumes:
  pgdata:                                   # declared here, managed by Docker

The everyday CLI: up, down, logs, exec, ps, config

Six subcommands cover almost everything. docker compose up -d starts the stack detached and is idempotent — re-run it after editing the file and Compose recreates only the services whose definition changed. Add --build when you have changed source that a service builds from, because Compose reuses an existing image otherwise and you will spend twenty minutes debugging code that is not running. docker compose ps shows what is up along with each container's health status, logs -f api tails one service, and exec db psql -U app shop opens a shell inside an already-running container (run, by contrast, starts a brand-new throwaway container — a distinction interviewers like).

Two more are worth reflexes. docker compose config prints the fully resolved file after merging every override and substituting every variable, which is the fastest way to answer "why is this service getting that value?" And the sharp edge: docker compose down removes containers and networks but keeps named volumes, while down -v also deletes them. That -v is how developers silently destroy the local database they had seeded — learn the difference before you learn it the hard way.

docker compose up -d --build        # start detached, rebuilding changed services
docker compose ps                   # state + health of every service
docker compose logs -f --tail=100 api
docker compose exec db psql -U app shop     # shell into a RUNNING container
docker compose config               # the effective, fully merged and interpolated file
docker compose down                 # containers + networks; named volumes SURVIVE
docker compose down -v              # ...and now the data is gone. Deliberately.

The realistic stack: why depends_on is not enough, and how healthchecks fix it

Here is the trap, and it is the single most-asked Compose interview question. Plain depends_on: [db] only guarantees that the db container has been started before the api container is started. It says nothing about whether PostgreSQL inside that container has finished initialising, replayed WAL, created the database and begun accepting connections — a process that routinely takes several seconds. So the API starts, tries to connect, gets "connection refused", and crashes. It appears to work on a fast laptop and fails in CI, which is the worst possible failure mode.

The fix is to give the dependency a healthcheck and depend on the condition, not the container: depends_on: { db: { condition: service_healthy } }. Now Compose runs the healthcheck command inside the container on an interval and holds the dependent service until it reports healthy. Choose a check that proves readiness rather than liveness — pg_isready for PostgreSQL, redis-cli ping for Redis, a broker API call for Kafka — and set start_period generously so slow first-boot initialisation does not count failures against you. The two other conditions matter too: service_started is the weak default, and service_completed_successfully is how you make a migration job run to completion before the API comes up. Keep an application-level retry as well, because in Kubernetes there is no depends_on at all and your service must tolerate a dependency that is briefly absent.

services:
  db:
    image: postgres:17
    environment: { POSTGRES_USER: app, POSTGRES_DB: shop }
    volumes: [ "pgdata:/var/lib/postgresql/data" ]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 30s        # grace window for first-boot initialisation

  cache:
    image: redis:7
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      retries: 10

  broker:
    image: apache/kafka:latest
    healthcheck:
      test: ["CMD-SHELL", "/opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list"]
      interval: 10s
      retries: 12
      start_period: 40s

  migrate:
    build: ./api
    command: ["./migrate.sh"]
    depends_on:
      db: { condition: service_healthy }

  api:
    build: ./api
    depends_on:
      db:      { condition: service_healthy }
      cache:   { condition: service_healthy }
      broker:  { condition: service_healthy }
      migrate: { condition: service_completed_successfully }
    ports: ["8080:8080"]

  worker:
    build: ./worker
    depends_on:
      broker: { condition: service_healthy }

volumes:
  pgdata:

Profiles: optional services in one file

A full stack accumulates services nobody needs all the time — pgAdmin, a mail catcher, Prometheus and Grafana, a load generator, an LDAP stub. Splitting them into a second file works but fragments the definition. profiles is the better answer: tag a service with one or more profile names and Compose skips it unless that profile is activated, either by --profile tools on the command line or the COMPOSE_PROFILES environment variable. A service with no profile is always started, so the default docker compose up stays fast and lean.

Two behaviours are worth knowing. Naming a profiled service explicitly (docker compose up pgadmin) activates its profile implicitly, so you rarely need the flag interactively. And profiles compose with depends_on: if an enabled service depends on a profiled one, that dependency is pulled in automatically. Related and often confused with profiles is required: false on a dependency, which lets a service start even when the named dependency is not part of the current run — useful precisely when an optional profile is switched off.

services:
  api:                         # no profile: always started
    build: ./api
  pgadmin:
    image: dpage/pgadmin4
    profiles: ["tools"]        # only with --profile tools
  grafana:
    image: grafana/grafana
    profiles: ["tools", "observability"]

# docker compose up -d                      -> api only
# docker compose --profile tools up -d      -> api + pgadmin + grafana
# COMPOSE_PROFILES=observability docker compose up -d

Override files, fragments, and one file per environment

Compose reads compose.yaml and, if present, compose.override.yaml automatically, merging the second over the first. That convention is the cleanest way to separate what is universal from what is local: the base file holds images, networks and dependencies, while the override adds bind-mounted source, debug ports, verbose logging and the developer tools. Commit both if the whole team shares them, or commit only the base and let each developer keep their own override. For CI, name the files explicitly — -f compose.yaml -f compose.ci.yaml — and remember the merge rules: mappings merge key by key, scalars are replaced, and sequences are replaced wholesale rather than concatenated, which surprises people expecting their extra ports entry to be added to the base list.

For reuse inside a file, YAML anchors and aliases (Compose calls them fragments) let you define a block once with &name and splice it into several services with <<: *name — ideal for a shared logging configuration or a common set of environment variables. Use x- prefixed top-level keys to hold these definitions, since the specification reserves that prefix for extensions and ignores them. Where reuse must cross files or projects, extends pulls a service definition from another file, giving several repositories one canonical database service rather than five drifting copies. Whatever you use, verify the outcome with docker compose config rather than reasoning about it.

x-logging: &default-logging     # x- keys are reserved for extensions and ignored
  driver: json-file
  options: { max-size: "10m", max-file: "3" }

services:
  api:
    logging: *default-logging
  worker:
    logging: *default-logging

# compose.override.yaml is merged automatically on top of compose.yaml.
# For CI, be explicit and skip the implicit override:
#   docker compose -f compose.yaml -f compose.ci.yaml up -d --wait

Variable interpolation and the .env file

Compose substitutes ${VARIABLE} references anywhere in the file before the configuration is applied, drawing values from the shell environment and from a .env file sitting next to the Compose file. This is how one file serves several environments without branching: image tags, ports, replica counts and credentials all become variables. Two forms carry most of the weight — ${TAG:-latest} supplies a default when the variable is unset or empty, and ${DB_PASSWORD:?password required} fails the command loudly with your message instead of silently starting a database with a blank password.

Be precise about the two different things that look alike. The .env file feeds interpolation of the Compose file itself; the env_file key feeds variables into a container. They are not the same file and not the same mechanism, and mixing them up is a common source of "the variable is set but the app cannot see it". Precedence runs, roughly, from most specific to least: an inline environment entry beats env_file, which beats the image's own ENV; and for interpolation, a shell variable beats the .env file. Keep real secrets out of both — commit a .env.example with placeholder values, git-ignore the real .env, and use Compose secrets for anything genuinely sensitive.

# .env (git-ignored)     ->  TAG=1.4.0
#                            API_PORT=8080
services:
  api:
    image: ghcr.io/acme/shop-api:${TAG:-latest}
    ports: ["${API_PORT:-8080}:8080"]
    environment:
      DB_PASSWORD: ${DB_PASSWORD:?set DB_PASSWORD before starting}

# `docker compose config` shows the file AFTER substitution — always check there first.

Compose beyond the laptop: Spring Boot support, Testcontainers, and the production line

Two integrations remove most of the remaining friction for JVM teams. Spring Boot's Docker Compose support detects a compose.yaml in the project root, starts the stack when the application starts, reads connection details from the running containers and injects them as properties — so you delete the hand-written local datasource configuration entirely and stop the stack when the app stops. Testcontainers attacks the same problem from the test side, starting real dependencies per test run against throwaway containers; its Compose module can drive an existing Compose file directly, which is how integration tests stop depending on whatever happens to be running on the developer's machine.

Know where Compose stops, because interviewers ask. It is a single-host tool: no scheduling across nodes, no rolling updates with surge and unavailability budgets, no autoscaling, no self-healing beyond restart policies. The deploy key exists but most of it is honoured only by Swarm. The honest answer is that Compose is superb for local development, integration testing and modest single-server deployments, and that beyond that you move to Kubernetes — which is where this track goes next.

Docker Hub pull rate limits in CI, and the registry mirror that fixes them

The failure that takes a team by surprise: the pipeline that has run for months starts failing with toomanyrequests: You have reached your pull rate limit. Docker Hub meters image pulls per account, and anonymous pulls are metered by IP address — which on a shared CI runner, a corporate NAT or a cloud provider's egress range means you are sharing one small budget with strangers. Authenticated free accounts get a larger allowance than anonymous pulls, and paid subscriptions raise it further, so the first and cheapest mitigation is simply to docker login in CI with a service account and a read-only access token before anything pulls.

The structural fix is to stop pulling from Docker Hub on every build. Run a registry mirror — a pull-through cache that fetches an image from Hub once and serves every subsequent request locally — or use the equivalent managed feature in the registry you already pay for (Artifactory remote repositories, ECR pull-through cache, Azure Container Registry artifact cache, GCP Artifact Registry remote repos). Configure the Docker daemon or BuildKit with registry-mirrors and builds transparently hit the cache. Two habits make this stick: pin base images by digest so the cache is deterministic, and mirror the handful of images your Compose stack pulls — Postgres, Redis, Kafka — since a full local stack can pull half a dozen images per developer per day.

// /etc/docker/daemon.json on a CI runner — pull through a local cache
{
  "registry-mirrors": ["https://registry-cache.internal.example.com"]
}

// In the pipeline, before anything pulls:
//   echo "$DOCKERHUB_TOKEN" | docker login -u "$DOCKERHUB_USER" --password-stdin

Interview questions

Compose comes up in almost every backend and DevOps round in India, from service-company screens ("what does this file do?") to product-company system rounds ("your stack is flaky on startup — fix it"):

Beginner What is Docker Compose and what problem does it solve?

A tool for defining and running multi-container applications from one declarative file. Instead of a page of docker run commands with hand-wired networks, volumes and environment variables, you describe every service once in compose.yaml and bring the whole stack up with a single command. Its main value is reproducibility: every developer and the CI pipeline get an identical local environment.

Beginner What are the top-level sections of a Compose file?

services (the containers, and the only mandatory one), networks, volumes, plus configs and secrets. An optional name pins the project name. Note what is not there any more: version is obsolete under the current Compose Specification and should be deleted.

Beginner Difference between docker-compose and docker compose?

The hyphenated form is Compose V1, a standalone Python program that reached end of life. The space-separated form is Compose V2, a Go plugin shipped with the Docker CLI, which is what you should use — it is faster, supports the current specification including profiles and the new dependency conditions, and is the only version receiving development. Docker Desktop aliases the old command to the new one, which is why some scripts still appear to work.

Beginner In ports: "8081:8080", which number is which?

Host first, container second — HOST:CONTAINER. So the application listening on port 8080 inside the container is reachable at port 8081 on your machine. Publishing ports is only needed for access from the host; containers on the same Compose network reach each other directly on the container port.

Beginner How does one service talk to another?

By service name. Compose creates a default network for the project, attaches all services to it, and Docker's embedded DNS resolves each service name to its container. So the API connects to db on port 5432, not to localhost — inside a container localhost is that container itself. No published ports and no legacy links are required.

Intermediate Named volume vs bind mount — when do you use each?

Named volumes are managed by Docker, declared under the top-level volumes key, portable across platforms and fast — use them for database data directories and anything the application persists. Bind mounts map a host path in, so they are for development conveniences: mounting source for hot reload, injecting a config file, reading generated output. Bind mounts are slower on macOS and Windows and bring host file-ownership problems, so do not use them for database storage.

Intermediate What is the difference between docker compose down and down -v?

down stops and removes containers and the project network but leaves named volumes alone, so your database data survives. down -v (or --volumes) additionally deletes the named volumes declared in the file — that is a permanent data loss and the usual cause of "my local database is empty again". Use -v deliberately when you want a clean slate.

Intermediate environment, env_file and .env — what is the difference?

environment sets variables on the container inline. env_file loads container variables from a named file. The .env file next to the Compose file is different in kind: it supplies values for ${VAR} interpolation within the Compose file itself, before the configuration is applied. Precedence for the container runs inline environment over env_file over the image's ENV; for interpolation, the shell environment beats .env.

Intermediate How do you keep one Compose file usable for both local development and CI?

Keep the shared truth in compose.yaml and layer differences on top. compose.override.yaml is picked up automatically for local development (bind-mounted source, debug ports, dev tools); CI names its files explicitly with -f compose.yaml -f compose.ci.yaml, which skips the implicit override. Move anything that genuinely varies — image tags, ports, credentials — into interpolated variables with defaults, and mark optional services with profiles. Verify the result with docker compose config.

Intermediate What are profiles and when would you reach for them?

Profiles tag services as optional. A service with profiles: ["tools"] is skipped unless you pass --profile tools or set COMPOSE_PROFILES; services with no profile always start. They keep monitoring stacks, admin UIs, mail catchers and load generators in the same file as the application without slowing down the default up. Naming a profiled service directly also activates its profile.

Pro Your API container keeps crashing at startup because the database is not ready, even though you have depends_on: [db]. Explain and fix it.

depends_on in its plain form only orders container start: Compose starts the db container before the api container and then immediately considers the dependency satisfied. It has no idea whether PostgreSQL inside that container has finished initialising and is accepting connections, which typically takes several seconds. The fix is to add a healthcheck to db (for example pg_isready -U app, with interval, retries and a generous start_period) and change the dependency to depends_on: { db: { condition: service_healthy } }. Compose then holds the API until the check passes. Keep an application-level connection retry as well, since production orchestrators have no equivalent of depends_on.

Pro Name the depends_on conditions and give a use for each.

service_started — the default, container-start ordering only, adequate for a stateless sidecar. service_healthy — waits for the dependency's healthcheck to pass, which is what you want for databases, caches and brokers. service_completed_successfully — waits for a one-shot container to exit with status zero, the correct way to run a schema migration or seed job before the application starts. Add required: false when the dependency may legitimately be absent, for instance because its profile is disabled.

Pro How do you write a good healthcheck, and what makes a bad one?

A good check proves the service can do its job: pg_isready against the actual database name, redis-cli ping, an HTTP request to a readiness endpoint that verifies dependencies. Tune interval, timeout, retries and especially start_period, during which failures do not count — that is what stops a slow first boot from being marked unhealthy. Bad checks: anything that only proves the process exists (a port being open, or curl against a path that returns success while the app is still loading), anything expensive enough to add load, and anything depending on a tool the image does not actually contain.

Pro Your CI pipeline suddenly fails with a Docker Hub pull rate limit error. Diagnose and fix.

Docker Hub meters pulls per account, and anonymous pulls are counted per IP address — so shared CI runners, corporate NAT or a cloud egress range put you in one pool with everyone else on that address. Short-term fix: authenticate in the pipeline with a service account and read-only access token before any pull, which moves you onto the account's larger allowance. Structural fix: stop pulling from Hub on every build — run a registry mirror or pull-through cache (Docker's own distribution mirror, Artifactory, ECR pull-through cache, ACR artifact cache) and point the daemon or BuildKit at it via registry-mirrors. Also pin base images by digest so the cache is deterministic, and cache the handful of images your Compose stack pulls repeatedly.

Pro Can you use Compose in production? Argue both sides.

For a single server with modest requirements — an internal tool, a demo environment, a small deployment where downtime during a restart is acceptable — Compose is defensible and vastly simpler than the alternatives. What it cannot do: schedule across multiple hosts, perform rolling updates with surge and unavailability control, autoscale, reschedule work off a failed node, or manage secrets and configuration at cluster scope. The deploy key hints at these but most of it is only honoured by Swarm. Once you need multi-node availability or zero-downtime releases, move to Kubernetes and keep Compose for local development and integration tests.

Pro How do multiple Compose files merge, and what surprises people?

Files given with repeated -f flags are merged left to right, with later files overriding earlier ones; compose.override.yaml is applied automatically when you do not name files explicitly. Mappings merge key by key and scalars are replaced — both intuitive. The surprise is sequences: lists such as ports, command arguments and volumes are replaced wholesale, not appended, so an override adding "one more port" silently drops the base list. Relative paths resolve against the first file's directory, another common trap. Always confirm with docker compose config, which prints the fully merged and interpolated result.
