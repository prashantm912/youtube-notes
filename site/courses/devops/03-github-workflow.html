Module: GitHub and Code Review

Git is the data structure; GitHub is the social protocol layered on top of it. This module is about that protocol — the pull request, the review conversation, and the rules a repository enforces when nobody is watching.

Knowledge Library → Courses → DevOps and Deployment → GitHub and Code Review

What this module covers

Everything in the previous two modules ran on your laptop. This one is about the part of the job that involves other people: proposing a change, having it read, arguing about it politely, and getting it onto the branch that ships. The mechanics take an afternoon to learn; the practice takes years, and it is what separates a team where review catches bugs from a team where review is a rubber stamp with a two-day delay.

The first half walks the pull request lifecycle end to end — fork versus branch, drafts, the three merge methods and what each does to your history, closing keywords, keeping a branch current, required status checks — and then review practice itself: why small PRs are the single biggest lever, what a human reviewer should look for that a linter cannot, and how to write a comment that gets the fix made instead of a fight started. The second half is governance: branch protection, the newer repository rulesets, CODEOWNERS, issues and labels and templates, Projects, and releases.

Topics

The pull request: fork or branch, and what a PR actually is

A pull request is a request to merge one ref into another, wrapped in a durable conversation. Underneath it is nothing exotic — GitHub computes the diff between your head branch and the base branch's merge base and renders it — but around that diff it attaches review threads, status checks, labels, linked issues and an audit trail that survives long after the branch is deleted. That trail is the real product: six months later the PR is where you find out why a line looks the way it does, which is a question git blame alone answers badly.

Two topologies exist. Inside a company you almost always use the shared-repository model: you have push access, you create a branch in the same repo, you open a PR from it. In open source you use the fork model: you copy the repo into your own account, push a branch there, and open a PR across repositories — the maintainer never grants you write access, and can still merge your work. Know both, because Indian interviewers regularly ask candidates who only ever worked on private repos to describe contributing to an open-source project, and the fork step is where people stumble.

git switch -c feat/invoice-pdf         # branch off the current base
git push -u origin feat/invoice-pdf    # publish it
gh pr create --fill --base main        # open the PR (GitHub CLI)

# fork model: your fork is 'origin', the project is 'upstream'
git remote add upstream https://github.com/acme/billing.git
git fetch upstream && git rebase upstream/main

Draft PRs, keeping the branch current, and required status checks

A draft pull request is a PR that cannot be merged and does not request review. It exists so you can open the conversation early — get CI running, let a colleague sanity-check the approach after two commits instead of twenty, publish a design in code form — without pinging four reviewers who will find it half-finished. Marking it "ready for review" is the moment the social contract starts. Teams that discover drafts stop the "I did not want to bother anyone so I built the wrong thing for a week" failure mode almost immediately.

Keeping the branch current is the other half. The base branch moves while your PR sits, and GitHub's diff is computed against the merge base, so an out-of-date branch can pass CI and still break main — the classic semantic conflict, where two changes merge cleanly as text but contradict each other in meaning. The button that updates a branch performs a merge from base (or a rebase, if the repository is configured for it). Required status checks then act as the gate: a rule names the checks that must report success, and the merge button stays disabled until they do. Turning on "require branches to be up to date before merging" is what forces a re-run against the current base — safe, but it serialises merges on a busy repo, which is the tradeoff to mention when asked.

Merge, squash or rebase — and what each does to your history

GitHub offers three merge methods and a repository can enable any combination. Merge commit keeps every commit from the branch and adds a merge commit with two parents: history is complete and truthful, and also full of "wip", "fix typo" and "address review comments". Squash and merge collapses the branch into a single new commit on the base: main becomes one readable commit per change, trivially revertable and bisectable, at the cost of losing the intermediate steps — and the branch's commits are not ancestors of the result, which is why you must delete the branch rather than reuse it. Rebase and merge replays each commit onto the base with no merge commit, giving a linear history that preserves individual commits, but rewrites their SHAs and drops the record that they arrived together.

Most product teams land on squash for feature branches because it makes main one-change-per-commit; library and long-lived open-source repos more often keep merge commits or rebase so the individual commits survive. Whichever you pick, the merge message becomes the permanent record, so treat the PR title as a commit subject: imperative mood, under about fifty characters, and a body that explains why rather than what. Linking work is done in the description with a closing keyword — Closes #412, Fixes #412, Resolves #412 — which auto-closes the issue when the PR merges into the default branch. Keywords in a comment do not count; they must be in the description (or a commit message), and they only close issues in the same repository unless you use the fully qualified owner/repo#412 form.

Review practice: small pull requests are the whole game

If you change one thing about how your team reviews code, change the size of the pull requests. Review quality falls off a cliff with diff size: a two-hundred-line PR gets line-by-line attention, a two-thousand-line PR gets "looks good to me" because nobody can hold it in their head, and the reviewer's guilt about blocking you for three days does the rest. Google's engineering practices guide is blunt about it — small changes are reviewed faster, reviewed more thoroughly, are easier to revert, and are less likely to be blocked by an unrelated argument. Splitting work into a refactor PR, then a behaviour PR, is not bureaucracy; it is the trick that makes the behaviour PR reviewable at all.

The second lever is knowing what a human should look for. Formatting, import order, trailing whitespace and unused variables are a linter's job — if you are commenting on those, fix the tooling instead. A reviewer's actual budget should go on: correctness (does it do what the description claims, including edge cases and error paths); design (is this the right seam, does it fit the existing architecture, is it over-engineered for a requirement that does not exist); tests (do they fail if the code is wrong, or only assert that it runs); naming and readability for the next person; and security and data safety (input validation, authorization checks, secrets, logging of personal data, an N+1 query that only shows up under production volume). Google's standard for approving is deliberately not "perfect" — it is "does this definitely improve the overall code health of the system", because holding out for perfect is how review queues die.

Review mechanics: comments, nits, suggestions, approve vs request changes

GitHub gives a reviewer three verdicts. Comment leaves feedback without a verdict. Approve says merge it. Request changes blocks the merge until you re-review — which is why it should be reserved for things that genuinely must change, not for preferences. Always submit a review rather than firing individual comments one at a time: batched comments arrive as one notification and one coherent argument, whereas eleven separate emails read as an ambush. Conversely, do not let a review consist only of blocking demands — commenting on the parts you liked is not politeness theatre, it tells the author you actually read the change.

Two conventions carry most of the tone. The nit: prefix marks a comment as non-blocking preference — "nit: this reads better as a guard clause" — and its absence therefore means the comment matters, which removes an enormous amount of guessing. And suggested changes let you write the replacement code directly inside a review comment; the author applies it with one click, either singly or batched into one commit. Anything you can express as a suggestion, express as a suggestion — it converts a round trip into a button press. Beyond that: comment on the code, never the coder ("this method has three responsibilities", not "you always do this"); ask rather than instruct when you might be wrong; and give a reason, because a reviewer's reason is how a junior engineer learns instead of just complying.

nit: guard clause reads better here — non-blocking, merge without it if you disagree.

    if (order == null) {
        throw new OrderNotFoundException(id);

Self-review first, and knowing when a pull request is the wrong tool

Read your own diff before you request a review. Open the Files changed tab and go through it as a stranger would: the debug print you forgot, the commented-out block, the file that has no business in this change, the test you renamed but did not update. Every one of those you catch yourself is a review round trip you did not spend, and reviewers who repeatedly find debris stop reading carefully. While you are there, annotate your own PR — leave comments on the two or three places where the reasoning is not obvious from the code. A reviewer who is told where to look reviews better and faster.

On the receiving side, a review comment is not an order. Push back with a reason when you disagree, and take the discussion to a call after the second round trip — text is a terrible medium for design arguments and an excellent one for recording the conclusion afterwards. And be aware that the PR-for-everything default has real costs: it puts a queue between every change and production, and it is not the only model. Martin Fowler's "Ship / Show / Ask" frames the choice explicitly — ship straight to trunk for the trivial and reversible, show by merging and opening a PR afterwards for visibility, ask by blocking on review when the change genuinely needs a second opinion. Continuous integration in its original sense, and pair programming, are review too — done continuously rather than in a batch at the end.

Branch protection rules and repository rulesets

Everything above is convention until the repository enforces it. Branch protection rules are the classic mechanism: pick a branch name pattern and switch on requirements — require a pull request before merging, require N approvals, dismiss stale approvals when new commits are pushed, require review from Code Owners, require status checks to pass, require branches to be up to date, require conversation resolution, require signed commits, require linear history, block force pushes and deletions. Two settings deserve emphasis. Linear history forbids merge commits on the protected branch, so the repo must use squash or rebase merges. Signed commits requires every commit to carry a verified GPG, SSH or S/MIME signature, which is how you stop someone forging authorship in the log — increasingly a compliance requirement in Indian BFSI and fintech shops.

Repository rulesets are the newer, generally available replacement, and interviewers at product companies now ask what they add. Four things: rulesets can be defined once at the organisation level and applied across many repositories, so you stop clicking the same checkboxes in fifty repos; they layer, with the most restrictive combination of all applicable rulesets winning rather than one rule silently overriding another; they can be set to evaluate mode, which reports what would have been blocked without blocking anything, so you can roll a policy out safely; and they have explicit, auditable bypass actors — named teams, roles, or apps — instead of the blunt "administrators can override" switch. They also target tags and repository names, not just branches, and everyone can see which rules apply to a branch, where classic protection was visible only to admins.

CODEOWNERS: automatic reviewers and how its path matching works

A CODEOWNERS file maps paths in the repository to the users or teams responsible for them. Put it in .github/, the repository root, or docs/ on the default branch, and GitHub automatically requests review from the matching owners whenever a PR touches those paths. Pair it with the "require review from Code Owners" branch protection setting or the equivalent ruleset rule and it becomes an enforcement mechanism: the payments team cannot be bypassed on a change to /services/payments, and the security team is a required reviewer on anything under /infra. This is how large repositories stay reviewable — nobody has to know who to ask.

The path matching is where people trip. Patterns follow gitignore syntax with two important exceptions: ! negation and bracket ranges like [a-z] are not supported. The rule that matters most in interviews is that the last matching pattern wins — unlike most config formats, order is significance, not precedence by specificity. So put the broad defaults at the top and the specific overrides at the bottom, or your carefully written override will be silently ignored. Also note that owners must have write access (teams must be visible and have write access to the repo), a syntax error in the file makes the whole file inert, and a pattern's owners apply to every file under a directory match.

# Broad default first — the LAST matching pattern wins.
*                           @acme/platform-team

# Everything under a directory, at any depth
/services/payments/         @acme/payments-team @priya-r
/infra/                     @acme/sre @acme/security

# By extension, anywhere in the repo
*.sql                       @acme/dba
*.tf                        @acme/sre

# Most specific override goes LAST or it will not take effect
/services/payments/README.md  @acme/tech-writers

Issues, labels, templates and GitHub Projects

Issues are the unit of work: a title, a body, assignees, labels, a milestone, and a thread. Their value comes from discipline rather than features — a bug report with reproduction steps, expected behaviour and environment is worth ten "not working" issues, which is exactly why issue templates exist. Drop Markdown templates or, better, an issue form (a YAML file under .github/ISSUE_TEMPLATE/) into the repo and GitHub renders structured, required fields instead of an empty box. The same mechanism gives you a PULL_REQUEST_TEMPLATE.md, which is the cheapest possible way to make every PR arrive with a description, a test note and a rollback plan. Labels are the cross-cutting axis — type (bug, feature), priority, area, and the good first issue / help wanted pair that open-source newcomers filter on.

GitHub Projects sits on top: a spreadsheet-like database whose rows are issues and pull requests from any repository, plus optional draft items, with custom fields you define (status, iteration, estimate, team) and table, board and roadmap views over the same data. The point is that it is not a separate tracker — the status you set on the board is attached to the real issue, and built-in workflows move items automatically when a linked PR is opened, merged or closed, so the board stops lying without anyone maintaining it. For teams already living in GitHub this replaces a good deal of what a separate Jira instance was doing, which is a discussion worth being able to have in an interview rather than a religious position.

Releases: tags, release notes and artifacts

A Git tag names a commit; a release is GitHub's object wrapped around that tag, adding a title, notes, a pre-release or latest flag, and — the part that matters operationally — binary assets. Source archives are generated for you, but you attach the things you actually ship: the jar or the container digest reference, checksums, signatures, an SBOM. That gives you one immutable, addressable answer to "what exactly is running in production", which is the question every incident starts with. Tag first (annotated tags, not lightweight, so the tag carries an author and message), then create the release from that tag.

Two features remove most of the manual work. Automatically generated release notes build the changelog from the pull requests merged since the previous release, and a .github/release.yml lets you group them into sections by label and exclude noise such as dependency bumps — which is the reward for having labelled PRs consistently. And the whole thing is scriptable: gh release create from the CLI, or a workflow triggered on a tag push so that tagging is the release. Mark anything not production-ready as a pre-release so that "latest" keeps meaning what people assume it means, and never move or delete a published tag — downstream consumers pin to it.

git tag -a v2.4.0 -m "Async invoice rendering"
git push origin v2.4.0

gh release create v2.4.0 \
  --title "v2.4.0" \
  --generate-notes \
  --latest \
  build/libs/billing-2.4.0.jar build/libs/billing-2.4.0.jar.sha256

Interview questions

Collaboration questions appear in almost every Indian interview loop — service companies probe the mechanics and the process you followed, product companies probe judgement about review, governance and release hygiene:

Beginner What is a pull request, and is it a Git feature?

A request to merge a head branch into a base branch, wrapped in a review conversation, status checks and an audit trail. It is not a Git feature — Git has no concept of a PR. It is a platform feature (GitHub, GitLab merge requests, Bitbucket pull requests) built on top of ordinary Git refs and diffs.

Beginner Walk me through raising a PR to an open-source project you do not have write access to.

Fork the repo into your account, clone your fork, add the original repo as an upstream remote, create a branch, commit, push to your fork, then open a PR from your fork's branch to the upstream base branch. Keep the branch current by fetching upstream and rebasing. The maintainer reviews and merges; you never need write access to their repository.

Beginner What is a draft pull request and why would you open one?

A PR that cannot be merged and does not request review. You open one to start CI early and get informal feedback on the approach before the work is finished, without pulling reviewers in prematurely. Marking it ready for review is the explicit signal that it now wants attention.

Beginner How do you make a merged PR close its issue automatically?

Put a closing keyword plus the issue reference in the PR description or a commit message — Closes #412, Fixes #412, Resolves #412. It fires when the PR merges into the default branch. Keywords in ordinary comments do not work, and cross-repository closing needs the fully qualified owner/repo#412 form.

Intermediate Merge commit vs squash and merge vs rebase and merge — what do you use and why?

Merge commit keeps every branch commit plus a two-parent merge commit: complete history, noisy main. Squash collapses the branch into one commit on main: readable one-change-per-commit history that is easy to revert and bisect, but the intermediate commits are lost and the branch's commits are not ancestors of the result, so never reuse the branch. Rebase replays the commits linearly with no merge commit: preserves individual commits, rewrites their SHAs, loses the grouping. Most product teams squash feature branches; libraries and open-source repos more often keep merge commits or rebase.

Intermediate Your PR shows all checks green but merging it breaks main. How is that possible?

The branch was tested against an older base. Someone else merged a change that conflicts semantically — not textually — with yours: they renamed a method your new caller uses, tightened a validation your code violates, changed a shared contract. The diff merged cleanly, so Git saw no conflict. The fix is "require branches to be up to date before merging", which forces a re-run against the current base; the cost is serialised merges on a busy repository, sometimes managed with a merge queue.

Intermediate What is the single most effective thing a team can do to improve code review quality?

Make pull requests smaller. Review attention degrades sharply with diff size — small PRs get reviewed faster, more thoroughly, are easier to revert and are less likely to stall on an unrelated argument. Practically: separate refactoring from behaviour change into different PRs, and land work behind a feature flag in increments rather than one giant branch.

Intermediate As a reviewer, what should you look for that a linter cannot catch?

Correctness against the stated intent including error paths and edge cases; design fit — is this the right abstraction, is it over-engineered for a requirement that does not exist; whether the tests would actually fail if the code were wrong; naming and readability for the next reader; and security and data concerns such as missing authorization checks, unvalidated input, secrets, personal data in logs, or an N+1 query that only bites at production volume. Formatting and style should be automated so review time is not spent on them.

Intermediate What do the "nit:" prefix and suggested changes do for a review?

nit: marks a comment as a non-blocking preference, so its absence signals that a comment genuinely matters — that removes most of the guessing about which feedback is mandatory. A suggested change embeds the replacement code in the comment; the author applies it in one click, batched into a single commit, turning a review round trip into a button press. Anything expressible as a suggestion should be one.

Intermediate Approve, comment, or request changes — when do you use each?

Approve when the change improves the code health of the system, even if it is not perfect — the standard is improvement, not perfection. Comment for feedback without a verdict, typically a partial review or questions. Request changes only for things that must change before merge, because it blocks the merge until you re-review; using it for preferences is how review queues become resented. Always submit as one batched review rather than a stream of individual comments.

Pro What do repository rulesets give you that classic branch protection does not?

Organisation-level definition applied across many repositories instead of per-repo checkboxes; layering, where multiple applicable rulesets combine and the most restrictive wins rather than one silently overriding another; an evaluate mode that reports what would have been blocked without blocking, so policy can be rolled out safely; explicit named bypass actors — teams, roles, apps — instead of a blanket admin override, with an audit trail; targeting of tags and repository name patterns, not just branches; and visibility of the active rules to everyone, where classic protection settings were admin-only.

Pro Explain CODEOWNERS path matching. Why might an owner rule you wrote have no effect?

Patterns use gitignore syntax minus ! negation and bracket ranges, and the last matching pattern wins — order determines the outcome, not specificity. So a specific override placed above a broad pattern is silently overruled by the broader line below it. Other common causes: the file is not on the default branch or not in one of .github/, the repo root or docs/; a syntax error anywhere makes the whole file inert; or the named user or team lacks write access to the repository.

Pro Which protection settings would you require on main for a regulated fintech repository, and why?

Require a pull request with at least one approval; require review from Code Owners for sensitive paths; dismiss stale approvals on new pushes so an approval cannot be reused for different code; require conversation resolution; require status checks including build, tests and a security scan, with branches up to date; require signed commits so authorship cannot be forged; require linear history so the audit trail is a straight line; block force pushes and branch deletion; and restrict bypass to a named break-glass role that is audited. Enforce it as an organisation-level ruleset so a new repository is compliant on day one, and roll it out in evaluate mode first.

Pro Is a pull request always the right way to integrate? Argue the other side.

No. A PR inserts a queue between every change and production, and review latency is integration latency — long-lived branches, bigger merges, more semantic conflicts, which is the opposite of continuous integration. The Ship / Show / Ask framing makes the choice explicit: ship trivial reversible changes straight to trunk, show by merging and opening a PR afterwards for visibility, ask by blocking on review when a change genuinely needs a second opinion. Pair programming and mob programming are review performed continuously rather than batched at the end. What is non-negotiable is that changes get reviewed and that trunk stays releasable; the pull request is one implementation of that, not the definition of it.

Pro How do you get a trustworthy, automated changelog and release out of GitHub?

Enforce labelled, well-titled PRs (squash merge makes the PR title the commit subject), then use automatically generated release notes with a .github/release.yml that groups entries into sections by label and excludes noise such as dependency bumps. Tag with an annotated tag, create the release from that tag with gh release create --generate-notes or a workflow triggered on tag push, attach the real artefacts plus checksums and an SBOM, and flag anything unfinished as a pre-release so "latest" stays meaningful. Never move or delete a published tag — consumers pin to it.
