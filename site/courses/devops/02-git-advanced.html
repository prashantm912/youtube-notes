Module: Git Advanced

Anyone can commit and push. What marks out a senior engineer is the half hour after something goes wrong — a branch that needs cleaning before review, a conflict nobody understands, a colleague who force-pushed over a day of work. This module is that half hour, learned in advance.

Knowledge Library → Courses → DevOps and Deployment → Git Advanced

What this module covers

Module 01 covered the object model and the everyday commands. This module covers the operations that rewrite history, resolve disagreements between two histories, and recover history you thought you had destroyed. The first half is integration and cleanup: merge versus rebase, interactive rebase, conflict resolution done properly, plus cherry-pick, stash and tags.

The second half is rescue and scale: the reflog as the safety net that means almost nothing in Git is ever truly lost, git bisect as a binary search for the commit that broke your build, hooks and worktrees as workflow tools, and the flags that make Git usable on a repository with a million files and a decade of history. Every one of these is a common interview topic, and every one of them is something you will eventually need under pressure.

Topics

Merge vs rebase: two ways to integrate, two shapes of history

git merge joins two histories by creating a new commit with two parents. Nothing that already existed is altered — every original commit keeps its hash, its author date and its true context. The cost is shape: a repository where every feature branch merges back produces a graph with lots of forks and joins, and a git log that interleaves work from different branches. git rebase takes the commits unique to your branch, replays them one at a time on top of the new base, and gives you a straight line. The commits are not moved — they are copied, so each replayed commit is a new object with a new hash and the originals become unreferenced.

That copy step is the whole argument. Linear history is easier to read, easier to bisect and easier to revert, which is why most teams rebase feature branches onto main before merging. But because rebasing rewrites commits, the golden rule follows directly: never rebase commits that other people have already pulled. Their clone still points at the originals, yours points at the copies, and their next merge will duplicate every commit. Rebase your own unshared branch freely; on a shared branch use git revert and a merge instead. When you do rebase a branch you have already pushed for review, push with --force-with-lease, never bare --force, so you refuse to overwrite work someone else pushed while you were rebasing.

# integrate main into a feature branch, two ways
git switch feature
git merge main        # new merge commit; history preserved, graph forks
git rebase main       # commits replayed on top of main; new hashes, straight line

# after rebasing a branch you had already pushed:
git push --force-with-lease   # refuses if the remote moved since your last fetch

Interactive rebase: cleaning a branch before anyone reviews it

git rebase -i opens the list of commits you are about to replay and lets you rewrite the plan before Git executes it. The verbs are the vocabulary: pick keeps a commit, reword edits only its message, edit stops so you can amend the content, squash folds a commit into the previous one and lets you combine the messages, fixup folds it in and throws its message away, drop deletes it, and reordering the lines reorders the commits. There is also exec to run a command (a test suite, say) after a commit, so you can prove every commit in the branch builds.

The workflow that makes this painless is --autosquash. Instead of remembering at the end which review comment belonged to which commit, fix the code immediately and commit with git commit --fixup=<sha>; Git writes a message prefixed fixup!. When you later run git rebase -i --autosquash, those commits are automatically moved directly under their targets and marked fixup, so you only confirm the plan. Set rebase.autosquash=true and it is the default. Two more flags worth knowing: git rebase --onto transplants a range of commits onto a completely different base (the fix when you branched off the wrong branch), and --update-refs keeps a stack of dependent branches pointing at the right replayed commits instead of at the abandoned originals.

git commit --fixup=a1b2c3d          # marks this as a fix for that commit
git rebase -i --autosquash main     # fixups slide under their targets automatically

# branched off the wrong base? move only your three commits onto main:
git rebase --onto main wrong-base feature

# mid-rebase controls
git rebase --continue | --skip | --abort

Conflict resolution: markers, ours/theirs, mergetool and rerere

A conflict means both sides changed overlapping lines and Git refuses to guess. It writes conflict markers into the file: your side between <<<<<<< and =======, the other side between ======= and >>>>>>>. Set merge.conflictStyle=zdiff3 and Git adds a third block showing the common ancestor, which turns guesswork into a readable three-way comparison. Resolution is always the same loop: run git status (it lists the unmerged paths and tells you the exact next command), edit each file until no markers remain and the result actually makes sense, git add it, then git merge --continue or git rebase --continue. Resolving means producing correct code, not deleting one side to make the markers go away.

Now the classic trap. git checkout --ours <file> and --theirs take a whole side, and their meaning inverts between merge and rebase. In a merge, "ours" is the branch you are standing on and "theirs" is the branch being merged in — what you would expect. In a rebase, Git first checks out the upstream branch and then replays your commits on top of it, so "ours" is the upstream you are rebasing onto and "theirs" is your own work being replayed. Candidates get this backwards constantly; state it explicitly and you look like someone who has actually done it. Two tools reduce the pain: git mergetool opens a configured three-pane diff tool, and rerere ("reuse recorded resolution") records how you resolved each conflict hunk and replays it automatically the next time the same conflict appears — invaluable when a long-lived branch is rebased repeatedly.

git config --global merge.conflictStyle zdiff3   # show the common ancestor too
git config --global rerere.enabled true          # record and replay resolutions

git status                       # which files are unmerged, and what to run next
git checkout --ours   path/file  # merge: my branch  |  rebase: the upstream base
git checkout --theirs path/file  # merge: their branch |  rebase: my replayed commit
git add path/file
git rebase --continue

Cherry-pick, stash and tags

git cherry-pick copies one commit (or a range) onto your current branch by computing its diff against its own parent and applying that as a three-way merge. The everyday use is a hotfix: the fix lands on main, and you cherry-pick it onto the release branch instead of merging the whole of main. Because it copies, the same change now exists as two commits with two hashes, which is fine for a deliberate backport and a mess if you do it habitually — the later merge has to reconcile them. -x records the source hash in the message, which makes the relationship traceable.

git stash parks uncommitted work so you can switch context. Learn three things beyond the basic command: -u (or --include-untracked) is required or brand-new files are silently left behind, which is the number one stash surprise; git stash push -m "message" -- path/ stashes a message and a subset of paths; and git stash branch <name> creates a branch from the commit the stash was taken on and applies it there, which is the clean escape when the stash no longer applies to your current head. Treat the stash as a short-lived scratchpad — a stash entry is not on any branch and is easy to forget.

Tags name a specific commit permanently. A lightweight tag is just a file containing a hash — fine for a private bookmark. An annotated tag (-a, or -s to sign it) is a real object in the database carrying a tagger, a date, a message and optionally a GPG signature, and it is what you must use for anything a release depends on. Tags are not pushed by git push: you push them explicitly with git push origin v1.4.0 or --follow-tags, and moving a published tag is as antisocial as rewriting published history.

git cherry-pick -x a1b2c3d          # backport one commit, recording its origin

git stash push -u -m "wip: checkout form"   # -u also stashes untracked files
git stash list && git stash pop
git stash branch fix/checkout       # apply the stash on a fresh branch instead

git tag -a v1.4.0 -m "Release 1.4.0"   # annotated: real object, author + message
git push origin v1.4.0                 # tags are NOT pushed automatically

The reflog: nothing is really lost (and reset vs revert)

Every time HEAD or a branch tip moves — commit, checkout, merge, rebase, reset, pull — Git appends a line to the reflog recording where it moved from and where it moved to. So a "lost" commit after a bad reset --hard, a rebase that mangled a branch, or a branch you deleted is not gone: the commit object is still in the object database and the reflog still names its hash. git reflog lists the recent positions, addressable as HEAD@{1}, HEAD@{2} and so on; recovery is then git reset --hard HEAD@{1}, or safer, git branch rescue <sha> so you can inspect before committing to it. If the reflog entry is gone too, git fsck --lost-found lists dangling commits. Two caveats that make good follow-up answers: the reflog is local to your clone — it is not pushed and it cannot recover work that only ever existed on someone else's machine — and unreachable entries expire (30 days by default, 90 days for reachable ones) before garbage collection can prune them.

The reflog is also the reason the reset/revert distinction matters less than people fear locally, and more than they think publicly. git reset moves a branch pointer: --soft keeps the index and working tree, --mixed (the default) resets the index, --hard discards working tree changes too — which are the only changes not recoverable from the reflog, because they were never committed. Use reset freely on commits you have not pushed. For anything already public, use git revert, which creates a new commit whose diff undoes the target. Everyone's history stays valid and the undo is itself reviewable. "Reset for local history, revert for public history" is a one-line answer that lands well in interviews.

git reflog                       # every recent position of HEAD, with hashes
git branch rescue HEAD@{3}       # safest recovery: name it, then look at it
git reset --hard HEAD@{1}        # undo the previous history-moving command
git fsck --lost-found            # dangling commits when the reflog can't help

git revert a1b2c3d               # public history: a new commit that undoes it

git bisect: binary search for the commit that broke it

Something works in the release from two months ago and fails on main. Between them sit four hundred commits. git bisect turns that into roughly nine checkouts instead of four hundred, because it is a binary search over history. You mark one commit bad and one known-good ancestor; Git checks out the midpoint, you test and answer git bisect good or git bisect bad, and it halves the range each time until one commit is left. git bisect skip handles a revision that will not build, and git bisect reset puts you back where you started. Rename the terms with git bisect start --term-old=fast --term-new=slow when you are hunting a performance regression rather than a bug.

The version that actually changes your life is git bisect run. Give it a script that exits 0 when the revision is good and 1 through 127 when it is bad — 125 means "cannot test, skip this one" — and Git drives the entire search unattended while you do something else. The script can be a single test, a build plus a test, or a curl-and-grep against a locally started server. This is also where a linear, rebased history and small commits pay for themselves: bisecting a history of enormous merge commits tells you a merge is at fault without telling you which line, and every commit must build for the search to mean anything.

git bisect start
git bisect bad                 # current HEAD is broken
git bisect good v1.3.0         # this release was fine
# ... test, then: git bisect good   OR   git bisect bad
git bisect reset               # return to where you started

# unattended: exit 0 = good, 1-127 = bad, 125 = untestable
git bisect start HEAD v1.3.0
git bisect run ./scripts/reproduce.sh

Hooks and worktrees

Hooks are executable scripts Git runs at defined points in its own workflow. The client-side ones you will meet are pre-commit (lint, format, run fast tests — reject the commit by exiting non-zero), commit-msg (enforce a Conventional Commits or ticket-id format), pre-push (run the test suite before anything leaves the machine) and prepare-commit-msg. They live in .git/hooks, which is not version-controlled and is not copied by git clone, so sharing them across a team means either setting core.hooksPath to a directory that is committed, or using a manager such as Husky, Lefthook or pre-commit that wires that up for you. The critical judgement call: client-side hooks are a convenience, not a control — any developer can bypass them with --no-verify. Real enforcement belongs on the server: CI checks required by branch protection rules, or pre-receive/update hooks on a self-hosted server. Say that in an interview and you have answered the question behind the question.

git worktree lets one repository have several working directories at once, each on a different branch, all sharing a single object database. Instead of stashing to review a colleague's branch, git worktree add ../review-1234 feature/1234 gives you a second directory you can build and test in while your main directory keeps its branch, its node_modules and its half-finished work untouched. git worktree list shows them, remove and prune clean up. The rules to remember: a branch can only be checked out in one worktree at a time, and worktrees cost almost nothing in disk space because the history is not duplicated. They pair naturally with long-running builds, with comparing two branches side by side, and with running an agent or a long test suite on one branch while you keep working on another.

# share hooks with the team: commit them, then point Git at the directory
git config core.hooksPath .githooks

# a second working directory on another branch, same repository
git worktree add ../review-1234 feature/1234
git worktree list
git worktree remove ../review-1234

Git at scale: shallow and partial clone, sparse-checkout, maintenance

Clone a decade-old monorepo and you download every version of every file that ever existed. Git has three independent levers for that, and knowing which to pull is the interview differentiator. A shallow clone (--depth=1) truncates history: fast, small, but you cannot bisect, blame or diff against anything older, and it is the wrong default for a developer machine. A partial clone (--filter=blob:none) keeps the entire commit and tree graph but downloads file contents lazily, only when a command actually needs them — so history commands still work and you get most of the speed-up with none of the shallow-clone limitations. --filter=tree:0 goes further and is aimed at CI jobs that only ever check out one commit. Independently, git sparse-checkout set --cone apps/web libs/shared limits which directories appear in your working tree, which is what makes a monorepo with a hundred thousand files feel like a small project.

The other half of scale is upkeep. Loose objects, unpacked refs and a stale commit-graph make everyday commands crawl. git gc compresses loose objects into packfiles, packs refs and prunes unreachable objects past their grace period. git maintenance start is the modern replacement for cron-ing that yourself: it registers background jobs — prefetch, commit-graph, incremental-repack, loose-objects, pack-refs — that keep the repository fast without the long stop-the-world pause of a full gc. For very large checkouts also look at the file-system monitor (core.fsmonitor) so git status does not have to stat every file, and at Microsoft's Scalar, which bundles these settings as a single opinionated configuration.

# blobless clone: full history, file contents fetched on demand
git clone --filter=blob:none https://example.com/big-repo.git

# only materialise the directories you work in
git sparse-checkout set --cone apps/web libs/shared

# background upkeep instead of a stop-the-world gc
git maintenance start
git config core.fsmonitor true      # skip stat-ing every file on status

Interview questions

Advanced Git is asked in almost every Indian product and service-company round, from a two-year TCS or Infosys internal transfer panel to a senior interview at Flipkart or Zoho — the first two here are near-guaranteed:

Beginner Merge vs rebase — what is the difference and when do you use each?

Merge creates a new commit with two parents and preserves every existing commit exactly as it was, producing a branching graph. Rebase replays your branch's commits on top of a new base, creating copies with new hashes and producing a linear history. Use rebase to keep your own feature branch up to date and tidy before review; use merge to integrate into a shared branch and to preserve the fact that a feature was developed separately. The rule that decides it: never rebase commits that others have already pulled.

Beginner You deleted a branch / did a hard reset and lost a commit. How do you get it back?

Run git reflog. It records every position HEAD has held, so the lost commit's hash is still listed even though nothing points at it. Recover with git branch rescue <sha> (safest — you can inspect it first) or git reset --hard HEAD@{1} to undo the previous move. If even the reflog entry is gone, git fsck --lost-found lists dangling commits. Two caveats: the reflog is local to your clone, so it cannot recover someone else's work, and uncommitted working-tree changes destroyed by reset --hard were never objects and are genuinely gone.

Beginner What is the golden rule of rebasing, and what happens if you break it?

Do not rebase commits that exist outside your own repository — anything already pushed to a shared branch that colleagues have pulled. Rebasing replaces those commits with copies that have different hashes. Your teammate's clone still references the originals, so their next pull merges two versions of the same work and the history fills with duplicate commits. Fix a shared branch with git revert instead, and when you must force-push your own reviewed branch, use --force-with-lease.

Beginner Difference between a lightweight and an annotated tag?

A lightweight tag is just a ref pointing at a commit — a bookmark with no metadata. An annotated tag is a full object in the database with a tagger name, date, message and optional GPG signature. Use annotated for releases (anything auditable), lightweight for temporary local markers. Either way tags are not pushed by a plain git push — push them explicitly or with --follow-tags.

Beginner What does git stash do, and what is the most common mistake with it?

It saves your uncommitted tracked changes and reverts the working tree to HEAD so you can switch context, then reapplies them with pop or apply. The common mistake is forgetting -u: untracked files are not stashed by default, so brand-new files stay in your working directory and often get committed to the wrong branch. Also useful: git stash branch <name>, which creates a branch from the commit the stash was made on and applies it there when the stash no longer applies cleanly to HEAD.

Intermediate Walk me through cleaning up a messy branch before raising a pull request.

git fetch, then git rebase -i origin/main. In the todo list: reword vague messages, squash or fixup the "fix typo" and "address review" commits into the commits they belong to, drop debug commits, and reorder so each commit is a self-contained, buildable change. Better still, while working, commit fixes with git commit --fixup=<sha> and finish with git rebase -i --autosquash, which arranges everything for you. Then push with --force-with-lease.

Intermediate During a rebase conflict, what do --ours and --theirs refer to?

They are inverted compared to a merge. In a merge, "ours" is the branch you are on and "theirs" is the branch being merged in. In a rebase, Git checks out the upstream branch first and then replays your commits on top of it, so "ours" is the upstream base you are rebasing onto and "theirs" is your own commit currently being applied. Getting this backwards silently discards the wrong side, which is why git status and a three-way view (merge.conflictStyle=zdiff3) beat blindly taking a side.

Intermediate git reset vs git revert — which do you use and when?

Reset moves the branch pointer backwards and rewrites local history: --soft keeps index and working tree, --mixed resets the index, --hard discards working-tree changes as well. Revert leaves history intact and adds a new commit whose diff is the inverse of the target. Use reset on commits you have not pushed; use revert on anything already public, because it does not invalidate anyone else's clone and the undo is itself reviewable in the log.

Intermediate A bug appeared somewhere in the last 400 commits. How do you find the commit that introduced it?

git bisect. Mark the current commit bad and a known-good older commit or tag good; Git checks out the midpoint and you answer good or bad until one commit remains — about nine steps for 400 commits instead of 400. Automate it with git bisect run ./script.sh, where the script exits 0 for good, 1 through 127 for bad and 125 for "cannot test, skip". Then git bisect reset. This is a strong argument for small, individually buildable commits and a linear history.

Intermediate When would you cherry-pick instead of merging, and what is the downside?

When you need exactly one commit somewhere else — typically backporting a hotfix from main onto a release branch without dragging along everything else that has landed. The downside is duplication: cherry-pick copies the change, so the same logical fix now exists as two commits with different hashes, and a later merge between those branches has to reconcile them (usually harmlessly, sometimes as a conflict). Use -x so the new commit records the original hash, and prefer merges for routine integration.

Intermediate Where do Git hooks live, and why can't you rely on a pre-commit hook to enforce a policy?

In .git/hooks, which is not version-controlled and is not copied by git clone — so they are not shared unless you commit a directory and set core.hooksPath, or use a manager like Husky or Lefthook. And any developer can skip them with git commit --no-verify. Client hooks are for fast feedback (formatting, lint, message format); enforcement has to live where it cannot be bypassed — required CI checks under branch protection, or server-side pre-receive/update hooks.

Pro What is git rerere and when does it earn its keep?

"Reuse recorded resolution". With rerere.enabled=true, Git records how you resolved each conflict hunk and, when it sees the identical conflict again, replays your resolution automatically. It pays off when the same conflict recurs: a long-lived branch rebased onto a fast-moving main day after day, repeatedly testing a merge before committing to it, or a release branch that keeps taking the same backports. Without it you resolve the same hunk by hand every single time.

Pro You branched off the wrong branch and have three commits on top of it. How do you move only those three onto main?

git rebase --onto main wrong-base feature. It replays the commits that are in feature but not in wrong-base on top of main, leaving the wrong base's commits behind — which plain git rebase main would not do. Verify the set first with git log wrong-base..feature. If the replay goes wrong, git rebase --abort, and if you have already finished, the reflog still has the pre-rebase tip.

Pro Cloning our monorepo takes forty minutes. What are your options and what do they cost?

Three independent levers. Shallow clone (--depth=1) is fastest but truncates history, so blame, bisect and old diffs stop working — acceptable for a throwaway CI job, wrong for a developer machine. Partial clone (--filter=blob:none) keeps the full commit and tree graph and fetches file contents lazily, so history commands still work; --filter=tree:0 is the more aggressive CI variant. Sparse-checkout (set --cone) is orthogonal — it limits which directories are materialised in the working tree. Combine partial clone with sparse-checkout for developers, and add git maintenance start plus core.fsmonitor so the clone stays fast afterwards.

Pro Why use git worktree instead of stashing and switching branches?

A worktree gives you a second working directory backed by the same object database, so you can have main and a review branch checked out simultaneously. Nothing is stashed, your build output, dependency directory and IDE indexes stay intact per directory, and a long test run on one branch does not block work on another. It is cheap because history is not duplicated. Constraints: the same branch cannot be checked out in two worktrees at once, and you should git worktree remove or prune rather than deleting the directory by hand.

Pro How long does the reflog protect you, and when is data genuinely unrecoverable?

Reflog entries for reachable commits expire after 90 days by default and unreachable ones after 30 (gc.reflogExpire and gc.reflogExpireUnreachable); once expired, a git gc can prune the objects for good. Genuinely unrecoverable: uncommitted working-tree changes destroyed by git reset --hard or git checkout --, because they were never written as objects; and anything that only existed in a clone you no longer have, since the reflog is never pushed. That is the real argument for committing early and often — a commit, even an ugly one, is protected.
