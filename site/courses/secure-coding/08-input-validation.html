Module: Input Validation and File Handling

Every value that crosses into your process was written by someone else. This module is about deciding what you will accept before you do anything with it — and about files, where a sloppy decision stops being abstract and starts writing bytes to your disk.

Knowledge Library → Courses → Secure Coding track → Input Validation and File Handling

What this module covers

Start with the sentence that keeps this module honest: validation is not a security control on its own. It is a defense-in-depth layer that shrinks the blast radius while the real fix does the work — parameterized statements stop SQL injection, context-correct output encoding stops XSS, an authorization check stops IDOR. A validator in front of any of those is a useful second wall; a validator instead of any of those is a bug waiting for a payload you did not imagine.

With that framing in place, the module covers how to decide what "valid" means (allow-list over block-list), where to decide it (the trust boundary), when to decide it (after canonicalization, never before), and how to express it in Java with Jakarta Bean Validation. The second half moves to file handling — path traversal, upload hardening and archive extraction — because that is where a validation failure stops returning wrong data and starts writing attacker-chosen bytes to attacker-chosen paths.

Topics

Validation is a layer, not the fix

The most common way validation goes wrong is not a weak regex — it is a strong regex used as a substitute for the actual defense. A team blocks quote characters in a search box and calls the SQL injection ticket closed; six months later a numeric field, a JSON body or a header takes a different route into the same string-concatenated query and the "fix" is not on that path. Validation constrains the shape of the input; parameterization removes the vulnerability entirely by ensuring data never becomes code. Those are different classes of control and only one of them is a guarantee.

So the rule to internalise: always name the primary control first, then add validation as the layer that reduces what an attacker can even attempt. Validation earns its place by rejecting nonsense early (a 400 costs you almost nothing and costs the attacker a probe), by keeping garbage out of downstream systems that have weaker defenses than you do, and by turning a silent data-corruption bug into a loud, logged rejection. What it must never do is let you skip the prepared statement, the encoder, or the authorization check.

Allow-list versus block-list: enumerate the good, not the bad

A block-list (deny-list) tries to enumerate everything dangerous: strip <script>, reject ../, forbid the word SELECT. It is a bet that you thought of every encoding, every case variation, every Unicode homoglyph, every nesting trick and every representation the downstream parser will accept — and you did not, because that set is defined by someone else's parser, not by your imagination. Every block-list in history has been bypassed by a form of the input its author never considered, and stripping a forbidden substring often creates the forbidden substring in the leftovers.

An allow-list inverts the burden. You describe the small, closed set of values that are acceptable — this field is a 10-digit mobile number, this one is one of four enum values, this one is a UUID, this one is at most 120 characters from a named character class — and everything else is rejected without further thought. The set is defined by your domain, which is fully known to you, so it is finite and reviewable. Where an allow-list genuinely cannot be expressed (free-text comments, rich descriptions), do not fall back to a block-list: accept the text and rely on correct handling at the sink, which is encoding on output or parameterization at the query.

// BLOCK-LIST — a bet you will lose
if (name.contains("<script>") || name.contains("../")) throw new BadRequest();
// bypassed by case, by encoding, by nesting, by anything you did not list

// ALLOW-LIST — a closed set you can reason about
private static final Pattern SKU = Pattern.compile("\\A[A-Z]{3}-[0-9]{6}\\z");
if (!SKU.matcher(sku).matches()) throw new BadRequest("sku");
// note \A and \z, not ^ and $: in Java, $ also matches before a trailing newline

Syntactic versus semantic validation, and the trust boundary rule

Syntactic validation asks whether the value has the right shape: correct type, length within bounds, number inside a range, string matching a format. It is cheap, stateless, and easy to declare — this is what Bean Validation annotations express. Semantic validation asks whether the value makes sense for this user, in this state, right now: does this account id belong to the caller's tenant, is this discount code still active, can an order in SHIPPED state be cancelled, is this quantity available. Semantic checks need the database, the session and the domain model, so they live in the service layer — and they are also where authorization hides. A syntactically perfect UUID belonging to another customer is the entire IDOR vulnerability class; no @Pattern will catch it.

The trust boundary rule tells you where to run both. Validate at the edge where untrusted data enters — the controller, the message listener, the file reader, the third-party webhook — and validate again at every boundary where the trust level changes, such as the call into a module that will build a shell command or a file path. Data does not become trustworthy by travelling; it becomes trustworthy by being checked. And validation deep inside the domain, after the value has already been concatenated into a query or resolved into a path, is not validation — it is a post-mortem. Note also that a browser-side check is a usability feature, not a control: anything a client validates, a client can skip.

@PostMapping("/orders/{id}/cancel")
public ResponseEntity<Void> cancel(@PathVariable UUID id,          // syntactic: type does the work
                                   @AuthenticationPrincipal User me) {
    Order order = orders.findById(id).orElseThrow(NotFound::new);
    if (!order.ownedBy(me)) throw new NotFound();      // semantic: ownership, not shape (404, not 403)
    if (!order.isCancellable()) throw new Conflict();  // semantic: state machine
    order.cancel();
    return ResponseEntity.noContent().build();
}

Canonicalize first, then validate — the step everyone skips

A string can be written many ways that mean the same thing to the component that finally consumes it: percent-encoded, doubly percent-encoded, in an alternate Unicode normalization form, with a backslash instead of a forward slash, with an overlong UTF-8 sequence, with a full-width character that a later step folds to ASCII. If you validate one representation and then transform it into another before use, you validated a different string from the one you used. That gap is the bug, and it is entirely self-inflicted.

The double-encoding illustration makes it concrete. A filter that rejects the literal sequence ../ sees nothing wrong with the doubly-encoded form %252e%252e%252f; the request passes the filter, and a decoding step further down turns it into %2e%2e%2f and then into ../. The string that reached the file system is not the string the filter judged. The fix is ordering, not cleverness: decode and normalize to exactly one canonical form, then validate that form, then use that same value. Decode once and reject anything that still contains an encoded marker rather than looping "until it stops changing" — a decode loop is itself an attack surface. Apply Unicode NFKC normalization before comparing or matching where the field will be compared, normalize path separators before any path check, and never re-transform a value after it has been approved.

// WRONG ORDER: validate, then transform — you approved a different string
if (raw.contains("../")) reject();
String name = URLDecoder.decode(raw, UTF_8);      // decoding may reintroduce it

// RIGHT ORDER: canonicalize once, validate the canonical form, use that value
String decoded = URLDecoder.decode(raw, UTF_8);
if (decoded.indexOf('%') >= 0) reject("still encoded");   // no decode loops
String canonical = Normalizer.normalize(decoded, Normalizer.Form.NFKC)
                             .replace('\\', '/');
if (!SAFE_NAME.matcher(canonical).matches()) reject("name");
use(canonical);                                    // the approved value, unchanged

Bean Validation in Spring, concretely

Jakarta Bean Validation (formerly JSR-380, implemented on Spring Boot by Hibernate Validator) lets you declare the syntactic contract on the DTO itself instead of scattering if statements through controllers. The everyday set: @NotNull (present), @NotBlank (present and not just whitespace — the right choice for strings, where @NotNull happily accepts ""), @Size(min, max), @Min/@Max or @Positive for numbers, @Email, and @Pattern for a domain format. Put @Valid on the request-body parameter to trigger it, and @Valid again on nested object and collection fields — validation does not recurse into a nested DTO unless you ask it to, which is the single most common "but I annotated it!" bug. On path variables and request parameters you need @Validated on the class to activate method-level constraint validation.

Two features carry real weight beyond the basics. Validation groups let one class express different rules in different states — an id must be null on create and present on update — by tagging constraints with marker interfaces and selecting the group with @Validated(OnCreate.class); that is how you express state-dependent syntax without duplicating the DTO. Custom constraints (an annotation plus a ConstraintValidator) let you name a domain rule once — a GSTIN, a PAN, an IFSC code, an Indian mobile number — and reuse it everywhere, which is far better than copying the same regex into fifteen classes. Register a single @RestControllerAdvice handler for MethodArgumentNotValidException and ConstraintViolationException so every failure returns one consistent, non-leaky error shape.

public record CreateCustomer(
    @NotBlank @Size(max = 80) String name,
    @NotBlank @Email @Size(max = 254) String email,
    @NotNull @Pattern(regexp = "\\A[6-9][0-9]{9}\\z") String mobile,   // allow-list format
    @NotNull @Valid Address address,                                   // @Valid: recurse into nested
    @NotEmpty List<@Valid OrderLine> lines) {}                        // and into collection elements

@PostMapping("/customers")
public CustomerView create(@Valid @RequestBody CreateCustomer body) { ... }

The @Pattern trap: ReDoS in a validator you wrote yourself

A validation regex is untrusted-input-facing code that runs before authentication on most endpoints, and Java's java.util.regex engine is a backtracking engine. Give it a pattern with nested or adjacent quantifiers over overlapping character classes — the classic shapes are (a+)+, (a|a)*, (\\s*,\\s*)* and the "helpful" email regex someone pasted from a forum — and a moderately long non-matching string forces the engine to explore an exponential number of ways to fail. One request pins a CPU core for seconds or minutes. A handful of concurrent requests take the service down, and because it happens inside the validator it happens before any rate limit tied to a user, before any business logic, on every replica.

The defense is design, not detection. Prefer a bounded, unambiguous pattern with no nested quantifier and no alternation over overlapping branches; anchor with \A and \z; enforce @Size alongside @Pattern so the engine never sees a 100 KB string in the first place; and for anything structured (email, URL, date) parse with a real parser rather than matching with a regex. Compile patterns once into static final Pattern constants, run a linter or SAST rule that flags exponential shapes, and if you must accept a caller-supplied pattern — you should not — run it in a bounded worker with a timeout. Treat this as an availability bug of the same seriousness as an unbounded query.

// VULNERABLE: nested quantifier over an overlapping class = exponential backtracking
@Pattern(regexp = "^([a-zA-Z0-9]+\\s?)+$")
private String description;

// FIXED: bounded length first, then a flat, unambiguous, fully anchored pattern
@Size(max = 200)
@Pattern(regexp = "\\A[a-zA-Z0-9]+( [a-zA-Z0-9]+)*\\z")
private String description;

Error messages, mass assignment, and why the DTO is the boundary

Two failures live at the edge of a validation layer. The first is the error response. Never echo the raw rejected value back into an HTML or HTML-ish response unencoded — a validation error page is a reflected-XSS sink like any other, and "it failed validation so it can't be dangerous" is exactly backwards. Never leak internal detail either: a stack trace, an SQL fragment, a class name, a file path or an ORM constraint name in a 400 response hands an attacker your schema for free. Return a stable machine-readable code plus a field name and a human message that does not quote the payload; log the full detail server-side, correlated by request id, and make sure the log line itself is encoded so an attacker cannot forge log entries.

The second is mass assignment (over-posting): binding a request body straight onto a JPA entity or a domain object. The client sends fields you never intended to expose — role, isAdmin, balance, tenantId, createdBy — the binder happily sets them, and a "profile update" endpoint becomes a privilege escalation. Trying to fix it with an ignore list is a block-list, with all the same problems. The fix is a purpose-built DTO per operation, containing exactly the fields that operation may accept, mapped explicitly onto the entity in the service layer. Anything the DTO does not declare cannot be set, whatever the client sends, and it is enforced by the type system rather than by a configuration file someone will forget to update when a column is added.

// VULNERABLE: the entity is the binding target — every column is client-writable
@PutMapping("/me")
public User update(@RequestBody User user) { return repo.save(user); }  // role, tenantId, ...

// FIXED: a DTO that declares exactly what this operation accepts
public record UpdateProfile(@NotBlank @Size(max = 80) String displayName,
                            @Size(max = 200) String bio) {}

@PutMapping("/me")
public UserView update(@Valid @RequestBody UpdateProfile in,
                       @AuthenticationPrincipal User me) {
    me.setDisplayName(in.displayName());     // explicit, field by field
    me.setBio(in.bio());
    return UserView.of(repo.save(me));       // and a view DTO on the way out
}

Path traversal: how it escapes, and the only check that holds

Path traversal happens whenever untrusted text becomes part of a file system path. The mechanism is trivial: the path grammar has a "parent" element, .., so a value like ../../etc/passwd appended to your intended base directory resolves upward and out of it. The result is arbitrary file read where the code reads, and arbitrary file write where the code writes — and arbitrary write near a web root or a class path is usually remote code execution, which is why this ranks as CWE-22 rather than as a bug report.

Textual filtering fails for the same reason every block-list fails. ../ is only one spelling: there is ..\\ on Windows, percent-encoded and doubly percent-encoded forms, alternate Unicode representations, mixed and nested sequences that survive a single strip pass, and absolute paths that never need .. at all. The correct check does not inspect the string; it inspects the result. Resolve the candidate against your intended base directory, canonicalize both to real absolute paths, and verify by path elements that the resolved path is still inside the base — in Java, Path.normalize().toRealPath() (or toAbsolutePath().normalize() when the file does not exist yet) followed by startsWith on Path, never a String.startsWith on the rendered text, which happily accepts /data/uploads-evil as being inside /data/uploads. Best of all, avoid the problem: look the file up by an opaque id in a database and never let user text touch a path at all.

// VULNERABLE: user text concatenated into a path
File f = new File("/data/uploads/" + request.getParameter("name"));

// FIXED: resolve, canonicalize, then prove containment on path elements
private static final Path BASE = Paths.get("/data/uploads").toAbsolutePath().normalize();

Path target = BASE.resolve(userSuppliedName).normalize();   // resolve() also absorbs absolute paths
if (!target.startsWith(BASE)) {                             // Path.startsWith, not String.startsWith
    throw new AccessDeniedException("outside base directory");
}
return Files.readAllBytes(target);

Naming and storing what you accept

The client-supplied filename is untrusted data that looks like metadata, and treating it as a storage name is the root of most upload incidents. Do not use it. Generate your own storage identifier — a UUID or a content hash — store the file under that name in a directory you control, and keep the original name only as a display label in the database, escaped when rendered. A generated name eliminates traversal in the write path, eliminates collisions and overwrites of existing files, eliminates dangerous extensions and double extensions, and eliminates reserved device names on Windows in one move, without you having to enumerate any of them.

Where the file lands matters just as much. Store uploads outside the web root, or better, in object storage — if the bytes are not under a directory the application server will execute or serve, an uploaded server-side script is inert. Keep the storage directory non-executable and owned by a different user from the one that serves requests, so even a successful write cannot become a running process. On the framework side, Spring Security's StrictHttpFirewall rejects requests whose URLs contain encoded path separators, semicolons and other normalization hazards before your controller ever sees them: keep it on and understand the RequestRejectedException it throws rather than reflexively loosening it — every relaxation of that firewall re-opens a normalization gap you now have to defend by hand.

Upload hardening, part one: size limits and knowing what the bytes actually are

Enforce the size limit in two places. The framework limit (spring.servlet.multipart.max-file-size and max-request-size) protects your heap and temp directory; the reverse proxy limit (nginx's client_max_body_size, or the equivalent on your load balancer or ingress) rejects the request before a byte reaches the application, which is the only limit that helps when someone streams a 10 GB body at you. Cap the number of parts and the total request size too, not just the per-file size, and remember that multipart parsing writes to a temp directory — bound and monitor it, and clean it up on failure.

Then decide what the file is, and do it by looking at the bytes. The extension is client-supplied text. The Content-Type header in the multipart part is client-supplied text. Both are trivially set to anything, so neither is evidence. Detect the type by content sniffing — Apache Tika reads magic bytes and container structure and is the standard JVM answer — then check the detected type against a short allow-list of types you actually support, and check that the declared extension agrees with the detected type rather than trusting either alone. Two extra cautions: sniffing tells you the format, not that the file is safe, so a detected image/svg+xml is still an XML document that can carry script and usually should not be on your allow-list at all; and image-processing libraries are a real attack surface in their own right (the ImageTragick family of ImageMagick vulnerabilities turned "we resize the avatar" into remote code execution). Process images in an isolated, resource-limited worker, pin and patch those libraries, restrict enabled decoders, and re-encode uploads to a known-good format instead of storing the original bytes where the risk warrants it.

// Framework limit (application.yml) — and set client_max_body_size at the proxy too
// spring.servlet.multipart.max-file-size: 5MB
// spring.servlet.multipart.max-request-size: 10MB

private static final Set<String> ALLOWED = Set.of("image/png", "image/jpeg", "application/pdf");

String detected = new Tika().detect(file.getInputStream(), file.getOriginalFilename());
if (!ALLOWED.contains(detected)) throw new BadRequest("unsupported file type");

String storedName = UUID.randomUUID() + extensionFor(detected);   // never the client's name
Path target = UPLOAD_BASE.resolve(storedName).normalize();
if (!target.startsWith(UPLOAD_BASE)) throw new AccessDeniedException("bad target");
try (InputStream in = file.getInputStream()) {
    Files.copy(in, target, StandardCopyOption.REPLACE_EXISTING);
}

Upload hardening, part two: serving files without serving an attack

A stored file becomes dangerous at download time. If your application serves an uploaded HTML file from its own origin, the browser runs that HTML with your origin's cookies and storage — a stored XSS with full session access, delivered by your own file endpoint. So serve user content from a separate origin (a distinct domain, not just a path or a subdomain sharing cookies), which means the same-origin policy contains anything that does execute. Add Content-Disposition: attachment with a sanitized filename so the browser downloads rather than renders, and X-Content-Type-Options: nosniff so the browser honours the Content-Type you send instead of sniffing its own — without nosniff, a file you serve as text/plain can still be interpreted as HTML. Send an explicit, narrow Content-Type from your detection result, never from the value the client uploaded, and consider a restrictive Content-Security-Policy and a sandboxed response on the download route.

Round it out with authorization and hygiene. Every download must run the same ownership and tenancy check as any other resource — an upload endpoint guarded by login and a download endpoint guarded by an unguessable URL is an IDOR waiting to be enumerated; prefer short-lived signed URLs for object storage over long-lived public ones. Scan for malware where the risk warrants it (files shared between users, anything reaching an internal desktop, regulated data) and treat the scanner as one layer, not the control. Log uploads with the uploader, size, detected type and storage id so an incident can be reconstructed, rate-limit the endpoint, and quarantine rather than delete when a check fails, so you retain the evidence.

Archive extraction: zip slip and the decompression ratio

Accepting an archive means accepting a list of file names and a list of sizes, both written by the uploader, and then acting on them. Zip slip is path traversal through the entry name: an archive entry called ../../../../opt/app/config/app.properties extracted by naive code that joins the entry name onto the output directory writes wherever the process has permission — configuration, a template, a JSP under a web root, a cron file, a JAR on the class path. Snyk's 2018 research showed the pattern was endemic across ecosystems and archive formats (zip, tar, war, jar, 7z, apk), and it still turns up in new advisories every year. The defense is exactly the containment check from the traversal section, applied per entry: resolve the entry against the target directory, normalize, and verify with Path.startsWith before opening any output stream. Also refuse absolute entry names and symbolic-link entries, which bypass the name check entirely by pointing elsewhere after extraction.

The second archive problem is resource exhaustion. A zip bomb is a small archive with an enormous decompressed size — a few hundred kilobytes expanding to many terabytes, or a nested archive that multiplies at each layer — and the naive extraction loop happily writes until the disk or heap is gone. Do not trust the declared size in the entry header; it is attacker-controlled. Instead, count the bytes you actually write, enforce a total uncompressed budget, a per-entry budget, an entry-count cap, a maximum directory depth and a compression-ratio ceiling, and abort the whole extraction the moment any is exceeded. Never call a library helper that extracts an entire archive in one line unless you have read what it validates, and extract into a fresh temporary directory that you delete atomically on failure rather than into the live tree.

long written = 0, entries = 0;
try (ZipInputStream zin = new ZipInputStream(Files.newInputStream(archive))) {
    for (ZipEntry e; (e = zin.getNextEntry()) != null; ) {
        if (++entries > MAX_ENTRIES) throw new SecurityException("too many entries");

        Path out = TARGET.resolve(e.getName()).normalize();      // zip slip check, per entry
        if (!out.startsWith(TARGET)) throw new SecurityException("entry escapes target");
        if (e.isDirectory()) { Files.createDirectories(out); continue; }
        Files.createDirectories(out.getParent());

        try (OutputStream os = Files.newOutputStream(out)) {
            byte[] buf = new byte[8192];
            for (int n; (n = zin.read(buf)) > 0; ) {
                written += n;                                     // count real bytes, not the header
                if (written > MAX_TOTAL_BYTES) throw new SecurityException("decompression budget");
                os.write(buf, 0, n);
            }
        }
    }
}

A validation design checklist

Run this over any endpoint that takes input from outside your trust boundary. It is short on purpose — the point is that each line is checkable in review.

  • Name the primary control for each sink first (parameterized query, output encoding, authorization) — validation is the extra layer, never the substitute.
  • Every field has an allow-list: a type, a length bound, a range or a format. No field is accepted merely because nothing forbidden was found in it.
  • Canonicalize once — decode, normalize Unicode, normalize separators — then validate the canonical value, then use that exact value unchanged.
  • Syntactic rules live on the DTO as Bean Validation constraints; semantic rules (ownership, tenancy, state) run in the service against the database.
  • Validation happens at the edge and again at each trust-level change, server-side; client-side checks are usability only.
  • Request bodies bind to per-operation DTOs, never to entities, and responses go out through view DTOs.
  • Every @Pattern is anchored, quantifier-flat and paired with a @Size bound; structured formats are parsed, not regex-matched.
  • Rejections return a stable code and field name — no raw input echoed, no stack trace, no internal identifiers.
  • File paths are never string-concatenated: resolve against a base, normalize, and prove containment with Path.startsWith.
  • Uploads get a generated storage name, a size limit at both the framework and the proxy, a content-sniffed type checked against an allow-list, storage outside the web root, and delivery from a separate origin with attachment and nosniff.
  • Archives are extracted entry by entry with a containment check, an entry-count cap, a total-uncompressed-bytes budget and a ratio ceiling.
  • Every rejection is logged with enough context to investigate and encoded so the log itself cannot be forged.

Interview questions

Validation and file handling questions are staples of Indian product and service-company security rounds — the allow-list question opens almost every one, and the upload-endpoint design question is the standard senior-level follow-up:

Beginner What is the difference between an allow-list and a block-list, and which should you use?

A block-list enumerates what is forbidden; an allow-list enumerates what is permitted and rejects everything else. Always prefer the allow-list. A block-list can only stop the attacks its author imagined, and attackers have encodings, case variants, Unicode equivalents and nesting tricks the author did not list. An allow-list is defined by your own domain, so it is finite, closed and reviewable — and anything new is rejected by default rather than accepted by default.

Beginner Is input validation enough to prevent SQL injection?

No. Parameterized statements (or a properly used ORM) are the fix, because they keep data out of the query grammar entirely. Validation is a defense-in-depth layer that reduces what an attacker can even submit and catches nonsense early, but it makes no guarantee — the same value can reach the query by a path your validator does not cover. If an interviewer asks "how do you stop SQL injection", the first word out of your mouth should be parameterization, and validation should come second as a supporting layer.

Beginner Where should validation run, and is client-side validation useful?

Server-side, at the trust boundary where untrusted data enters — controller, message listener, webhook handler, file reader — and again at any boundary where the trust level changes. Client-side validation is a usability feature that gives fast feedback; it provides no security at all because anyone can send the request directly with a proxy or a shell. Never treat a value as validated because a form validated it.

Beginner Which Bean Validation annotations would you put on a customer registration DTO, and how do you trigger them?

@NotBlank plus @Size(max = ...) on names, @Email plus @Size on the email, @Pattern with an anchored allow-list regex on the mobile number, @NotNull on required references, and @Valid on nested objects and collection elements. Trigger with @Valid on the @RequestBody parameter; use @Validated on the class for constraints on path variables and request parameters. Handle MethodArgumentNotValidException in a @RestControllerAdvice so every failure returns one consistent error shape.

Intermediate Difference between @NotNull, @NotEmpty and @NotBlank?

@NotNull only requires the reference to be present, so an empty string passes. @NotEmpty requires non-null and size greater than zero — it works on strings, collections, maps and arrays — so a string of spaces passes. @NotBlank applies to character sequences only and requires at least one non-whitespace character, which is what you almost always want for a user-entered string field.

Intermediate Explain syntactic versus semantic validation with an example.

Syntactic validation checks shape: is this a well-formed UUID, is the amount positive, is the string under 80 characters. Semantic validation checks meaning in context: does this order id belong to the calling user's tenant, is the coupon still active, is the order in a state that allows cancellation, is there enough stock. Syntactic rules are declarative and belong on the DTO; semantic rules need the database and the session and belong in the service layer. A syntactically perfect id belonging to someone else is exactly the IDOR class of vulnerability — no annotation catches it.

Intermediate Why must canonicalization happen before validation? Give an example.

Because otherwise you validate one representation and use a different one. A filter rejecting the literal ../ passes a doubly percent-encoded form such as %252e%252e%252f; a decoding step downstream turns it back into ../, so the string that reached the file system was never judged. Decode and normalize once — percent-decoding, Unicode NFKC, path separators — then validate that canonical form, then use exactly that value with no further transformation. Reject anything still containing encoding markers rather than looping decode until stable.

Intermediate What is mass assignment, and how do you prevent it in Spring?

Mass assignment (over-posting) is binding a request body directly onto an entity or domain object, so a client can set fields the endpoint never meant to expose — role, isAdmin, tenantId, balance. A profile-update endpoint becomes privilege escalation. Prevent it with a purpose-built DTO per operation containing only the accepted fields, mapped explicitly onto the entity in the service. Ignore lists and @JsonIgnore sprinkled on the entity are block-lists and rot the moment someone adds a column.

Intermediate How would you validate a file's type on upload?

By its content, not its label. The extension and the multipart Content-Type header are both client-supplied strings and prove nothing. Sniff the actual bytes — Apache Tika on the JVM — check the detected type against a short allow-list of types you support, and require the extension to agree with the detected type. Remember that detection tells you the format, not that it is safe: SVG is a valid image type and also an XML document that can carry script, so it usually should not be on the list.

Pro What is path traversal, and why does filtering "../" fail?

Path traversal is untrusted text becoming part of a file system path, letting .. elements resolve outside the intended directory — arbitrary read where you read, arbitrary write (often remote code execution) where you write. Textual filtering fails because ../ is only one spelling: backslash variants, percent-encoded and double-encoded forms, alternate Unicode representations, sequences that reassemble after a single strip pass, and absolute paths that need no .. at all. The fix inspects the result, not the string: resolve against the base directory, normalize to a real absolute path, and verify with Path.startsWith — never String.startsWith, which accepts /data/uploads-evil as inside /data/uploads.

Pro Design a secure file upload endpoint. Walk through every layer.

Authenticate and authorize first, and rate-limit the endpoint. Enforce a size limit twice — at the reverse proxy or ingress so oversized bodies never reach the app, and in the framework's multipart settings — plus caps on part count and total request size. Discard the client filename and generate your own storage name (UUID or content hash), keeping the original only as an escaped display label. Detect the content type by sniffing the bytes and check it against a narrow allow-list, requiring the extension to agree. Write into a base directory resolved and containment-checked, outside the web root or straight to object storage, non-executable and owned by a different user. Scan for malware where risk warrants and quarantine rather than delete on failure. On download, authorize per file, serve from a separate origin with Content-Disposition: attachment, X-Content-Type-Options: nosniff and an explicit narrow Content-Type, preferring short-lived signed URLs. Log uploader, size, detected type and storage id throughout.

Pro What is zip slip, and how do you extract an archive safely?

Zip slip is path traversal through archive entry names: an entry named with .. segments, extracted by code that joins the entry name onto the output directory, writes outside it — over configuration, templates, a file under a web root or a JAR on the class path. It affects zip, tar, jar, war, 7z, apk and more. Extract entry by entry: resolve each name against the target, normalize, and verify with Path.startsWith before opening an output stream; refuse absolute names and symlink entries; extract into a fresh temp directory you can discard atomically. Never call a one-line "extract everything" helper without knowing what it validates.

Pro How do you defend against a zip bomb?

Never trust the declared uncompressed size in the entry header — it is attacker-controlled. Count the bytes you actually write and enforce a total uncompressed budget, a per-entry budget, an entry-count cap, a maximum nesting depth and a compression-ratio ceiling, aborting the whole extraction the instant any threshold is crossed. Extract in a resource-limited context (bounded temp space, a worker with its own memory and time budget) so a failure degrades one job rather than the node, and clean up partial output on abort.

Pro A code review shows @Pattern(regexp = "^([a-zA-Z0-9]+\\s?)+$"). What is wrong with it?

It is a ReDoS risk: a quantified group containing a quantifier over an overlapping character class, so a moderately long non-matching input drives Java's backtracking engine through an exponential number of failure paths and pins a CPU core. Because validation runs before business logic and often before rate limiting, a few requests can take the service down. Fix it by bounding length with @Size first, flattening the pattern so no quantifier nests, anchoring with \A and \z rather than ^ and $, compiling it once as a static constant, and parsing structured formats with a real parser instead of a regex.

Pro Why does an uploaded HTML file served from your own domain matter, and how do you neutralise it?

Because the browser executes it in your origin: it can read your cookies and storage and call your APIs as the victim — stored XSS delivered by your own download endpoint. Neutralise it by serving user content from a genuinely separate origin (a different domain, not a cookie-sharing subdomain), sending Content-Disposition: attachment so it downloads rather than renders, sending X-Content-Type-Options: nosniff so the browser does not second-guess your Content-Type, sending a narrow explicit type from your own detection rather than the client's, and keeping the storage location outside the web root so the server never interprets it either.
