Module: Secure API Design Review

Nine modules taught you where the holes are. This one is the walk-through you do on a Thursday afternoon before a service ships — the headers, the CORS policy, the TLS config, the audit trail, and the honest limits of every tool that claims to find bugs for you.

Knowledge Library → Courses → Secure Coding track → Secure API Design Review

What this module covers

Security review is not a mystical activity performed by people with black hoodies. It is a bounded, repeatable pass over a service: read the configuration, read the entry points, read the logs, and ask a fixed set of questions in a fixed order — highest-yield first. Most real findings in a corporate codebase are boring: an Access-Control-Allow-Origin that reflects whatever the caller sent, a login endpoint with no throttle, an audit log that helpfully records the password it just rejected.

This closing module pulls the whole track together. The first half is the configuration surface a reviewer can check in an hour: security response headers one at a time with a value you can defend, the headers you should be deleting, CORS explained properly because it is the most-misconfigured control on the list, TLS settings that are still current, and rate limiting reframed as a security control rather than a capacity knob. The second half is the review discipline itself: what a security-relevant audit event is and what it must contain, an ordered checklist you can actually run against a service, an honest account of what SAST, DAST, IAST and SCA each see and each miss, and where penetration testing and bug bounty fit — including the uncomfortable fact that a clean pentest report is a sample, not a proof.

Topics

Security response headers: the transport-and-trust core

Security headers are cheap defence in depth. None of them fixes a vulnerability — they narrow what a browser is willing to do with your response if something else has already gone wrong. Start with Strict-Transport-Security, which tells the browser that this host must only ever be reached over HTTPS for the stated lifetime, so a user who types the bare hostname never emits a plaintext request that could be intercepted and downgraded. A defensible production value is max-age=31536000; includeSubDomains — one year, covering every subdomain. Add preload only with your eyes open: submitting to the browser preload list bakes the rule into the browsers themselves, it applies to every subdomain including the intranet one nobody remembers, and removal takes months to propagate. Preload after you are certain, never as part of a first hardening pass.

The habit that matters more than any individual header is checking them on the deployed artefact, not in the source. Headers get stripped and rewritten by reverse proxies, ingress controllers, CDNs and API gateways, so what your application sets and what the browser receives are two different questions. Fetch a real response from the real environment and read what actually arrived; a scanner such as securityheaders.com gives you the same answer with a grade attached, which is useful mainly as a conversation starter with the team that owns the ingress.

Strict-Transport-Security: max-age=31536000; includeSubDomains
# add "; preload" only after every subdomain is HTTPS-only and you accept
# that browsers will hard-code this for a long time

nosniff, framing, and why frame-ancestors replaced X-Frame-Options

X-Content-Type-Options: nosniff is the single cheapest header on the list and it has exactly one value. It stops the browser guessing a response's type from its bytes when the declared Content-Type looks wrong. Without it, a file upload endpoint that serves user content as text/plain can have that content sniffed as HTML and executed in your origin — a stored XSS delivered entirely through a MIME guess. Set it globally, on every response, including the JSON ones.

Framing control stops clickjacking: an attacker embeds your real, authenticated page in a transparent iframe over their own UI so the victim's click lands on your "Transfer funds" button. The old control is X-Frame-Options: DENY (or SAMEORIGIN); the modern replacement is the CSP directive frame-ancestors, which supports a real source list rather than one hard-coded origin, and which browsers prefer when both are present. The legacy header is not yet worthless — it is still honoured by some embedded and enterprise browser stacks — so the common posture is to send both, with frame-ancestors as the authority. Content Security Policy itself is a full topic and was covered in Module 04, XSS and Content Security Policy; for review purposes the question is narrower: does a CSP exist at all, does it contain frame-ancestors, and is it in enforcing mode rather than report-only three years after someone "temporarily" switched it.

X-Content-Type-Options: nosniff
X-Frame-Options: DENY                                  # legacy, still send it
Content-Security-Policy: frame-ancestors 'none'        # the modern authority

Referrer-Policy, Permissions-Policy and the cross-origin isolation trio

Referrer-Policy controls how much of the current URL is leaked to the next site the user visits or the next third-party asset the page loads. The default in modern browsers is already strict-origin-when-cross-origin, but setting it explicitly is worth doing because it documents the intent and survives proxies that rewrite defaults. If your URLs carry identifiers — order numbers, tenant ids, password-reset tokens that never should have been in the path in the first place — tighten it to no-referrer for those routes and fix the URL design separately.

Permissions-Policy (the header formerly called Feature-Policy) switches off browser capabilities the page has no business using: camera, microphone, geolocation, payment, USB. For a back-office API-driven app the honest value is "almost everything off", and the payoff is that an injected script cannot silently reach for the microphone even if it gets to run. The Cross-Origin isolation trio — Cross-Origin-Opener-Policy, Cross-Origin-Embedder-Policy and Cross-Origin-Resource-Policy — is awareness-level for most reviewers: COOP severs the window-opener relationship with cross-origin pages, CORP declares who may embed your resources, and COEP requires every subresource to opt in. Together they enable cross-origin isolation, which is a prerequisite for high-resolution timers and SharedArrayBuffer and a mitigation for speculative-execution side channels. Know what they are and when someone would need them; do not bolt COEP onto an existing app on review day, because it breaks third-party embeds in ways that take a sprint to untangle.

The headers to delete, and what Spring Security does and does not set

Adding headers is half the job; the other half is removing the ones that volunteer information. Server: Apache/2.4.41 (Ubuntu) and X-Powered-By: Express hand an attacker your exact stack and version, which turns "find a vulnerability" into "look up the CVE list for this version". The same applies to X-AspNet-Version, verbose X-Generator values, and framework banners in error pages. This is not a serious control by itself — it is not security through obscurity as a strategy, it is refusing to publish a targeting list — but it costs one line of proxy configuration and it reliably drops your service out of the automated mass-exploitation traffic that scans for specific banner strings. While you are there, delete the debug endpoints and stack traces that do the same job more thoroughly.

On Spring Boot, know your defaults so you audit the gap rather than the whole set. With Spring Security on the classpath you get, out of the box: X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Strict-Transport-Security on HTTPS requests, Cache-Control: no-cache, no-store, max-age=0, must-revalidate, and X-XSS-Protection: 0 (deliberately disabling the legacy, itself-exploitable browser XSS auditor). What Spring Security does not set for you is the modern half of the list: no Content-Security-Policy, no Referrer-Policy, no Permissions-Policy, no cross-origin isolation headers, and no HSTS preload directive. Those are opt-in through the headers() DSL. Two traps worth naming in a review: any custom SecurityFilterChain that ignores a path also skips its header writers, and a static-resource route served outside the filter chain gets no headers at all.

http.headers(h -> h
    .contentSecurityPolicy(c -> c.policyDirectives(
        "default-src 'self'; object-src 'none'; frame-ancestors 'none'"))
    .referrerPolicy(r -> r.policy(STRICT_ORIGIN_WHEN_CROSS_ORIGIN))
    .permissionsPolicyHeader(p -> p.policy("camera=(), microphone=(), geolocation=()"))
    .httpStrictTransportSecurity(s -> s.includeSubDomains(true).maxAgeInSeconds(31536000)));
// and at the proxy: server_tokens off;  proxy_hide_header X-Powered-By;

CORS done correctly — the most-misconfigured control on the list

Start from what you are relaxing. The same-origin policy stops a page on evil.example from reading the response to a request it makes to bank.example — the request may still be sent, and cookies may still ride along, but the script cannot see what came back. That read barrier is what protects a logged-in user from having their account data hoovered out by any tab they happen to open. CORS is not a security feature layered on top of that: CORS is the mechanism for switching parts of it off in a controlled way. Every CORS header you add makes a browser more permissive than its default, never less. Say that sentence in an interview and you are ahead of most candidates.

Mechanically: a "simple" request goes straight out and the browser withholds the response unless Access-Control-Allow-Origin matches. Anything else — a custom header, a JSON content type, a PUT or DELETE — triggers a preflight: an OPTIONS request carrying Access-Control-Request-Method and Access-Control-Request-Headers, which your server must answer with the methods and headers it permits plus an Access-Control-Max-Age to cache the verdict. Two rules a reviewer checks first. One: Access-Control-Allow-Origin: * together with Access-Control-Allow-Credentials: true is invalid and browsers reject the pair outright — the wildcard exists precisely because it is only safe without credentials. Two, and this is the dangerous shortcut people reach for when rule one bites: reflecting the incoming Origin header straight back into Access-Control-Allow-Origin. That looks like it "supports multiple origins", but it means every origin is allowed, including the attacker's, and combined with credentials it converts the same-origin policy into a hole the size of your whole API. The correct pattern is an explicit allow-list of exact origins, matched with string equality, configured per environment. Watch for the near-misses too: a startsWith check that lets myapp.com.evil.net through, a regex with an unescaped dot, and the literal string null, which sandboxed iframes and some redirects send and which must never be on the list.

@Bean
CorsConfigurationSource corsConfigurationSource() {
    var cfg = new CorsConfiguration();
    cfg.setAllowedOrigins(List.of("https://app.example.com"));   // exact, per-env
    cfg.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    cfg.setAllowedHeaders(List.of("Authorization", "Content-Type"));
    cfg.setAllowCredentials(true);       // therefore: never a wildcard origin
    cfg.setMaxAge(1800L);               // seconds to cache the preflight verdict
    var src = new UrlBasedCorsConfigurationSource();
    src.registerCorsConfiguration("/api/**", cfg);
    return src;
}
// NOT this: cfg.setAllowedOriginPatterns(List.of("*"))  with credentials enabled
// NOT this: echoing request.getHeader("Origin") back into the response

TLS configuration: versions, ciphers, certificates and proof

The modern answer is short: TLS 1.2 and TLS 1.3 only. SSL 2 and 3, TLS 1.0 and TLS 1.1 are deprecated and are audit findings on sight; if a legacy integration still needs one, that is a documented, time-boxed exception on a dedicated endpoint, not a global setting. On ciphers, resist the urge to hand-craft a suite string from a blog post — the practical approach is to take Mozilla's "intermediate" profile from the SSL Configuration Generator, which emits ready configuration for nginx, Apache, HAProxy and the rest, and to use "modern" only when you control every client. Prefer suites with forward secrecy (ECDHE key exchange) and AEAD ciphers (AES-GCM, ChaCha20-Poly1305), disable compression, and let TLS 1.3 do most of this for you by construction.

Certificates are an operational problem more than a cryptographic one, and the failure mode is always the same: expiry on a Saturday. Automate issuance and renewal with ACME (Let's Encrypt, or your cloud provider's managed certificates), monitor days-to-expiry as a metric with an alert well before the edge, and know where each certificate's private key lives and who can read it. Verify the chain is complete — a server that works in your browser because your laptop happens to cache an intermediate will fail for a Java client that does not. Then prove the result rather than asserting it: run the host through SSL Labs, read the protocol and cipher table, and confirm HSTS shows up. Two extras for the review: enforce TLS on internal service-to-service hops as well, since "it is inside the VPC" is not an encryption strategy, and remember that terminating TLS at a load balancer means everything behind it is plaintext unless you deliberately re-encrypt.

Rate limiting as a security control, not a capacity knob

Most teams add rate limiting to protect the database. That is a capacity argument, and it produces capacity-shaped limits: a generous per-client ceiling on the whole API. The security argument is different and gives different numbers. An attacker with a list of leaked credentials does not need volume — credential stuffing works at a few attempts per account across a million accounts, which sails under any global limit. So the security-relevant limits are narrow and per-identity: login, password reset, one-time-password verification, token exchange, invite acceptance, and any endpoint whose response differs for a valid and an invalid identifier. Limit those per account and per source, not just per IP, because IPs are cheap and mobile carriers share them across thousands of users in India.

Enumeration deserves its own thought. If "no such user" and "wrong password" return different messages, different status codes, or measurably different response times, your login endpoint is a user-directory export tool; the same applies to password reset ("we have sent an email" must be the answer either way) and to signup ("this email is already registered"). Rate limiting reduces the throughput of that leak, but the actual fix is a uniform response. Alongside the limits, decide the response: return 429 with a Retry-After header, prefer progressive delays and step-up challenges over hard account lockout — lockout by identifier is itself a denial-of-service tool an attacker can aim at your users — and log every trip as a security event so the pattern is visible. The algorithms, the token-bucket versus sliding-window trade-off, and how to make limits work across a horizontally scaled fleet are covered in System Design, Module 05, Rate Limiting; the point here is only that the security limits are a different, tighter set than the capacity ones, and that a per-instance limiter multiplied by your replica count is not the number you promised.

Audit logging: the record you will be judged on

An audit log answers "who did what, when, from where, and did it work?" for events that matter to security and compliance — which is a much smaller set than "everything the application logs". The events worth recording are: authentication success and failure, logout and session termination, authorization denial, privilege or role change, credential and MFA changes, creation and deletion of accounts, data export and bulk read, administrative actions and configuration changes, and the security decisions your own controls make (rate limit tripped, input rejected at the trust boundary, token replay detected). Each entry needs the same five things: who (a stable subject identifier, not a display name), what (an event type from a controlled vocabulary, plus the target object's identifier), when (an unambiguous timestamp with timezone, ideally UTC in ISO-8601), from where (source address, user agent, and the request/correlation id that ties it to your traces), and outcome (success or failure, and the reason on failure).

Three design rules separate an audit log from a pile of log lines. First, it is separate from application logs — different sink, different retention, different access control — because the people who can edit application logging config should not be able to edit the record of their own actions. Second, it is tamper-evident: append-only storage, write-once buckets with object lock, or hash chaining where each entry includes a digest of the previous one, so deletion and alteration are detectable even by an administrator. Third — and this is the rule that gets broken most — the audit log must never contain the secrets or personal data it is auditing access to. Log that a user exported the payroll report; do not log the report. Log a failed login; do not log the password that was tried, and never the one that was correct-but-mistyped for another account. No tokens, no session ids, no card numbers, no Aadhaar or PAN, no full request bodies "for debugging". A log that duplicates the sensitive data is a second copy of your breach, held in the system with the widest read access in the company. Set retention deliberately (regulators and your incident-response team will both have an opinion, and one year is a common floor), and remember that an audit log nobody queries is decoration — the general logging pipeline, structured formats and correlation ids are covered in Observability, Module 02, Logging.

{
  "event": "authz.denied",              // controlled vocabulary, not free text
  "at": "2026-07-25T09:41:07.412Z",     // UTC, unambiguous
  "actor": {"subject": "u_8f31c2", "tenant": "acme"},
  "target": {"type": "invoice", "id": "inv_44190"},
  "source": {"ip": "203.0.113.19", "agent": "Mozilla/5.0 ..."},
  "correlationId": "c1f0a7d2-...",      // joins to traces and app logs
  "outcome": "denied",
  "reason": "role_lacks_finance_read"
}
// absent by design: tokens, passwords, card numbers, the record's own contents

The review itself: an ordered checklist you can run against a service

A review without an order becomes a review of whatever you noticed first. Work top-down and stop when you run out of time, because the list is deliberately sorted by yield: the questions near the top catch the findings that end up in breach reports, and the ones near the bottom catch the findings that end up in scanner output. Ask each question of the running service and its configuration, not of the design document, and write the answer down — "we think so" is a finding. Timebox it: two focused hours against this list on every service beats an annual four-week audit nobody schedules.

  1. Authorization on every endpoint. Is there a check per request, evaluated against the authenticated subject and the specific object — not just "is the user logged in"? Can you change an id in a URL and read another tenant's record? Are the checks default-deny, so a new controller is protected before anyone remembers to annotate it? (Module 05.)
  2. Authentication and session handling. Where do tokens live, how long do they last, can they be revoked before expiry, does logout actually terminate the session server-side? Cookie flags: HttpOnly, Secure, SameSite. Is MFA available for privileged roles? (Modules 05 and 06.)
  3. Input handling at the trust boundary. Is every external input validated against an allow-list at the edge of the service, including message-queue payloads and inter-service calls? Are queries parameterised everywhere, with zero string-concatenated SQL, JPQL, LDAP filters or shell commands? (Modules 03 and 08.)
  4. Output encoding and rendering. Is data encoded for the context it lands in, is framework auto-escaping switched on, and is every bypass of the sanitizer justified in a code comment by a named human? (Module 04.)
  5. Secrets. Anything in git history, in a container image layer, in a CI log, in a config map? Where does the service get its credentials at runtime, and when were they last rotated? Is there a secret-scanning gate on the repository? (Module 07.)
  6. Dependencies and build integrity. Is there an SBOM, does a scanner run on every build, are known-critical findings blocking or advisory, and can you name who reviews new transitive dependencies? (Module 09.)
  7. Transport and headers. HTTPS everywhere including internal hops, TLS 1.2+ only, certificates automated and monitored, and the response header set above — checked on a real response from the real environment.
  8. CORS. Explicit allow-list, no wildcard with credentials, no origin reflection, and the same policy in every environment except for the hostnames.
  9. Logging and audit. Are the security events above recorded, is the audit trail separate and tamper-evident, and does anything sensitive leak into it? Can you reconstruct an incident from it?
  10. Error handling. Do failures fail closed? Does a 500 return a stack trace, a framework banner, a SQL fragment or an internal hostname to the caller?
  11. Rate limits and abuse. Are the authentication-adjacent endpoints throttled per identity, are responses uniform enough to prevent enumeration, and does tripping a limit raise a signal someone sees?

Two calibration notes. Use OWASP ASVS when you need a level to certify against rather than a conversation — it is the same material expressed as testable requirements at three assurance levels, and it is the right artefact to hand a client or an auditor. Use the Web Security Testing Guide when you need the technique for verifying a specific control rather than the list of controls. And if the service is an API rather than a rendered application, read the API Security Top 10 alongside the main Top 10: the risks that dominate APIs — broken object-level authorization, broken function-level authorization, unrestricted resource consumption — are exactly the ones a browser-shaped checklist under-weights.

SAST and SCA: what static analysis sees before you deploy

SAST reads source or bytecode and reasons about data flow from sources (request parameters, message payloads) to sinks (query execution, command execution, HTML rendering). Its virtues are speed and position: it runs in the IDE and on every pull request, it needs no deployed environment, and it points at a file and a line, so the fix is obvious. Its vices are equally structural. False positive rates are high — a tainted-flow warning cannot know that a value was validated by a framework annotation three layers up, so teams learn to click "ignore" and the tool becomes wallpaper. It is blind to runtime context: it cannot see your reverse proxy, your feature flags, your production configuration, or the fact that the vulnerable endpoint is unreachable. And it finds nothing about authorization logic, because "this user should not be allowed to read this object" is a business rule, not a data-flow property.

SCA (software composition analysis) is a different job that often ships in the same product: it inventories your dependencies, matches them against vulnerability databases, and tells you that a transitive library four levels down has a critical CVE. It is the highest-value-per-rupee tool in the list because the finding is usually true and the fix is usually a version bump — but treat reachability seriously, since a CVE in a code path your application never calls is a backlog item, not an incident. Practical pipeline placement: SCA and a fast SAST ruleset on every pull request as a blocking gate on new critical findings only, a deeper SAST run nightly, and a suppression file that requires a reason and an owner so exceptions are visible rather than silent. Dependency scanning, SBOMs and signing were covered in Module 09, Supply Chain Security.

DAST and IAST: testing the thing that is actually running

DAST attacks a deployed instance from the outside with no knowledge of the source. That is its whole advantage: it exercises the real stack — proxy, framework, container, configuration — so it finds the class of problem SAST cannot see, which is precisely the class this module is about. Missing security headers, a permissive CORS policy, TLS misconfiguration, verbose error pages, exposed actuator or admin endpoints, cookies without flags, directory listings left on. It also validates that a control you believe is enabled is enabled in this environment. The costs: it needs a deployed, seeded, authenticated environment; it is slow, so it belongs on a nightly or pre-release stage rather than every pull request; it can write data, so never point it at production without a written agreement; and it only tests what it can reach, so a crawler that cannot log in, cannot complete a multi-step wizard, or cannot guess an undocumented endpoint reports a clean scan of ten percent of your application. Feeding it an OpenAPI specification and real credentials is the single change that most improves its yield.

IAST sits in between: an agent runs inside the application during functional or integration tests and watches real requests flow through real code, so it reports with the line-level precision of SAST and the runtime truth of DAST, with far fewer false positives. Its limitation is coverage — it only sees code paths your tests actually exercise — and it requires instrumenting the runtime, which some platforms and some security teams will not accept. A sane maturity ladder for a normal enterprise team: SCA first (cheapest, truest findings), then SAST on pull requests, then DAST nightly against a staging environment, then IAST if you have a good integration-test suite and want to raise signal quality. None of the four finds broken authorization between two legitimate users. That remains a human reading the code with the checklist above, which is why the tooling section comes after the checklist section and not before it.

Penetration testing, disclosure, and what you actually do on Monday

A penetration test is a time-boxed, scoped, authorised engagement in which skilled humans try to reach a defined objective in your system and write down how they did it. What it is: evidence about the paths they tried, a demonstration of real business impact that moves budgets in a way a scanner report never does, and a second opinion from people who do not share your blind spots. What it is not: proof of security. Three testers had three weeks against six of your forty services, in an environment that differed from production, using the knowledge they had at the time — a clean report means "they did not find it", which is a much weaker statement than "it is not there". Absence of evidence, and so on. Scoping is where the value is decided: name the targets and the excluded systems, state whether it is black, grey or white box (grey box with documentation and credentials nearly always finds more per rupee), agree the rules of engagement including test windows and who to call if something breaks, and — the part teams skip — book the remediation and retest time in the same plan. A pentest report with no retest is a document, not a fix.

Bug bounty and coordinated disclosure are the continuous complement: a published policy plus a /.well-known/security.txt file so that a researcher who finds something has an obvious, non-scary way to tell you, and a triage process so the report does not sit in a shared inbox for six weeks. You do not need to pay bounties to benefit from this; you do need a documented intake path, an SLA for first response, and a safe-harbour statement. So — Monday. Pick your most exposed service. Fetch a real response and diff its headers against the set above. Read the CORS configuration and confirm it is an explicit allow-list. Run the host through SSL Labs. Check that login and password reset are throttled per identity and answer uniformly. Grep the audit log for anything that looks like a token or a personal identifier. Then take the eleven-item checklist, answer each question honestly in a shared document with a name against every "we think so", and put the three worst answers on the sprint board. That is the whole of security review: not a mystique, a habit — one afternoon, repeated.

Interview questions

The closing module is also the most interviewable one: security headers, CORS and SAST-versus-DAST are standard rounds at Indian product companies and in service-company client interviews, and the follow-ups reward anyone who has actually configured these rather than read about them:

Beginner Which security response headers would you set on a new API, and why each?

A defensible baseline: Strict-Transport-Security (force HTTPS, prevent downgrade), X-Content-Type-Options: nosniff (stop MIME sniffing turning an upload into script), Content-Security-Policy with frame-ancestors (limit script sources and stop clickjacking), X-Frame-Options: DENY as the legacy companion, Referrer-Policy: strict-origin-when-cross-origin (stop URL leakage), and Permissions-Policy disabling camera, microphone and geolocation. Then remove Server and X-Powered-By. Say that you verify them on a real response from the deployed environment, because proxies rewrite headers.

Beginner What does CORS actually do — is it a security feature?

It relaxes the same-origin policy in a controlled way. The same-origin policy already stops a page on one origin reading the response from another; CORS is how a server opts in to letting specific origins read its responses. Every CORS header makes the browser more permissive, never less — so a "CORS vulnerability" is always a misconfiguration that gave away too much, and CORS is not protecting your server from a non-browser client at all.

Beginner What is a preflight request and when does the browser send one?

An OPTIONS request the browser sends before the real one when the request is not "simple" — a method other than GET, HEAD or POST; a content type other than form-urlencoded, multipart or text/plain; or custom headers such as Authorization. It carries Access-Control-Request-Method and Access-Control-Request-Headers; the server answers with what it permits plus Access-Control-Max-Age so the verdict is cached. In Spring, the OPTIONS request must not be blocked by the security filter chain before CORS handling runs — a classic bug.

Beginner Why remove the Server and X-Powered-By headers?

They publish your stack and exact version, which converts reconnaissance into a CVE lookup and puts you in the target set for automated mass exploitation that scans for banner strings. It is not a real defence on its own — patch and harden regardless — but it is one line of proxy config and it removes free information. The same reasoning applies to stack traces, framework error pages and exposed debug endpoints.

Intermediate Why is Access-Control-Allow-Origin: * with Allow-Credentials: true invalid, and what do people do instead that is worse?

The browser rejects the combination outright: the wildcard is only permitted for requests that carry no credentials, because "any origin may read this" plus "with the user's cookies attached" is a universal account-data leak. The dangerous workaround is reflecting the request's Origin header back into Access-Control-Allow-Origin — that satisfies the browser while allowing literally every origin, including the attacker's, so any site the victim visits can read authenticated responses from your API. The fix is an explicit allow-list compared by exact string match, per environment, with null never on the list.

Intermediate SAST versus DAST — what does each find, what does each miss, and where do they run?

SAST reads code, runs in the IDE and on every pull request, needs no deployment, and points at a file and line — but it produces many false positives, is blind to runtime configuration, and cannot see your proxy, environment or feature flags. DAST attacks a running instance from outside, so it finds configuration and integration flaws — missing headers, bad CORS, TLS problems, exposed admin endpoints — but needs a deployed authenticated environment, is slow enough to belong in a nightly stage, and misses any code path its crawler cannot reach. They are complementary; neither finds broken object-level authorization, which needs a human.

Intermediate What belongs in an audit log entry, and what must never appear in one?

Five fields: who (a stable subject id), what (an event type from a controlled vocabulary plus the target object id), when (UTC timestamp with timezone), from where (source IP, user agent, correlation id), and outcome with a reason on failure. Never the secrets or personal data the event is about — no passwords even when wrong, no tokens or session ids, no card numbers, no Aadhaar or PAN, no full request bodies. Otherwise the audit trail becomes a second copy of the sensitive data in the system with the widest read access.

Intermediate Which TLS versions and settings would you insist on, and how would you prove the result?

TLS 1.2 and 1.3 only; everything earlier is deprecated. Take Mozilla's intermediate profile from the SSL Configuration Generator rather than hand-writing a cipher string; prefer forward-secret ECDHE key exchange and AEAD ciphers. Automate certificate issue and renewal with ACME, monitor days-to-expiry, and confirm the chain is complete for non-browser clients. Prove it by running the host through SSL Labs and reading the protocol and cipher table, and check that HSTS is present. Also encrypt internal hops — "it is inside the VPC" is not encryption.

Intermediate How is rate limiting a security control rather than a capacity control?

Capacity limits are global and generous, so they never see credential stuffing, which runs at a few attempts per account across a huge account list. Security limits are narrow and per-identity, applied to authentication-adjacent endpoints — login, password reset, OTP verification, token exchange, signup — and limited per account as well as per source, because IPs are cheap and shared. Return 429 with Retry-After, prefer progressive delay and step-up challenges over hard lockout (which is itself a denial-of-service weapon against your users), and log every trip as a security event.

Intermediate Which security headers does Spring Security set by default, and what does it leave to you?

By default you get X-Content-Type-Options: nosniff, X-Frame-Options: DENY, HSTS on HTTPS requests, a no-store Cache-Control set, and X-XSS-Protection: 0 (deliberately disabling the legacy browser auditor). It does not set Content-Security-Policy, Referrer-Policy, Permissions-Policy, the cross-origin isolation headers, or HSTS preload — those are opt-in through the headers() DSL. Watch for paths excluded from the filter chain and static resources served outside it: they get no headers at all.

Pro Walk me through how you would review a service for security before it ships.

Top-down by yield, timeboxed, against the running service rather than the design doc. Authorization per endpoint and per object first (default-deny, tenant isolation, id-swap tests), then authentication and session handling, then input validation at the trust boundary and parameterised queries, then output encoding, then secrets (git history, image layers, CI logs, rotation), dependencies and SBOM, transport and headers checked on a real response, CORS allow-list, audit logging and what leaks into it, error handling and fail-closed behaviour, and finally rate limits and enumeration. Write every answer down with an owner; "we think so" is a finding. Use ASVS when you need testable requirements at an assurance level, and the WSTG for how to verify a specific control.

Pro A clean penetration test report lands on your desk. What does it prove?

That a small number of testers, in a limited window, against an agreed scope, in an environment that probably differed from production, did not find a way in with the techniques they tried. It is a sample, not a proof — absence of evidence. Read the scope and the rules of engagement before the findings; check what was excluded and whether they had credentials and documentation (grey box usually yields more per rupee than black box). Then ask the question that matters: is remediation and a retest booked? A report without a retest is a document, not a fix. Pair it with continuous controls — SCA, DAST, a disclosure policy with security.txt — because a pentest is a snapshot and your code changes weekly.

Pro Your team enabled a CSP and it broke the app, so someone left it in report-only mode. How do you fix that properly?

Report-only for two years is a control that does nothing. Use the reports: collect violation reports to an endpoint, group them, and you have an inventory of every inline script, eval and third-party origin the app depends on. Fix them in order — move inline scripts to files or nonces, drop dead third parties, replace eval-based templating — and tighten the policy incrementally, promoting directives to enforcing one at a time rather than flipping the whole policy. Nonce-based or hash-based policies with strict-dynamic beat long host allow-lists, which are easy to bypass. Keep frame-ancestors and object-src 'none' enforcing from day one — they almost never break anything.

Pro Your scanner reports a critical CVE in a transitive dependency. How do you decide whether it is an incident?

Ask reachability first: does your code call the affected function, on a path that handles untrusted input, in a deployment where the preconditions hold? A critical CVE in a code path you never execute is a backlog item; a medium one on your login path may be urgent. Then check for a fixed version and whether the bump is safe, whether a mitigation exists (configuration, a WAF rule, disabling a feature), and what the exposure window is. Record the decision with an owner and an expiry rather than silently suppressing it, and make the pull-request gate block only on new critical findings so the pipeline stays credible.

Pro How do you make an audit log trustworthy against an insider with administrator rights?

Separate it from application logs with its own sink, retention and access control, so the people who can change logging configuration cannot rewrite the record of their own actions. Make it append-only and tamper-evident: write-once storage with object lock, or hash chaining where each entry embeds a digest of the previous one so any deletion or alteration is detectable. Ship entries off the host promptly so a compromised box cannot edit history. Restrict read access too, since the log is itself sensitive, and monitor for the tell-tale event that is missing rather than present — a gap in a hash chain, or a privileged session with no corresponding audit entries.
