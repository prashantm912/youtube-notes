Module: Injection

Injection has stayed near the top of every vulnerability list for twenty years not because it is subtle, but because the pattern that causes it — building a command out of string pieces — is the most natural thing a programmer can do.

Knowledge Library → Courses → Secure Coding track → Injection

What this module covers

SQL injection, command injection, LDAP injection, log injection, expression-language injection, XPath and NoSQL injection are usually taught as a list of separate vulnerabilities to memorise. They are not separate. They are one bug wearing different clothes, and once you can see the shape of it you can spot it in an interpreter you have never used before.

This module states that shared principle first, then works through the variants a Java and Spring developer actually meets: the JDBC and JPA layer where most real defects live, the process-launching and directory-lookup APIs that get reached for once a year and therefore get reviewed by nobody, the logging framework that turned out to be an interpreter all along, and the Java-specific expression languages that quietly evaluate whatever string you hand them. Everything here is framed as prevention — vulnerable code next to the fixed version — because the point is to write the fixed version by reflex.

Topics

One bug, one fix: data that an interpreter parses as code

Every injection flaw has the same anatomy. Your program builds a string that some interpreter will parse — a SQL engine, a shell, an LDAP directory, an XML query processor, a logging layout, an expression evaluator. Untrusted input is concatenated into that string. The interpreter has no way to know which characters came from you and which came from the request, so it parses the whole thing uniformly, and any character in the input that happens to be syntax in that grammar changes the meaning of the command rather than the value inside it. The attacker did not "inject code" in any exotic sense; they supplied data that crossed the line into the code position because there was no line.

That single diagnosis produces a single prescription: keep data and code in separate channels instead of trying to clean the data. Every real defense in this module is one implementation of that idea — bind parameters in JDBC, named parameters in JPQL, an argument array instead of a shell string, a structured logging API instead of a formatted message, a fixed expression compiled once with the input supplied as a variable. Filtering and escaping are the alternative approach, and they are the approach that keeps failing, because they require you to model the interpreter's grammar perfectly, including the parts introduced in the version that shipped last week. Note the asymmetry that makes this worth internalising: the parameterised fix is usually the same length as the vulnerable code or shorter, so unlike most security work it costs nothing to adopt.

SQL injection: how concatenation changes a query's structure

Write "SELECT * FROM users WHERE email = '" + email + "'" and you have handed the caller control of the SQL grammar. The value they send is pasted between two quote characters, so a quote inside their value ends the string literal early and everything after it lands in the query as syntax: a boolean condition that is always true, an extra clause, a comment marker that discards the rest of your statement, or a second statement entirely if the driver permits batching. The database is behaving correctly throughout — it received a valid query and ran it. The defect is entirely upstream, in the moment the two strings were joined.

Know the impact classes, because interviewers grade on whether you understand the range rather than just the login-bypass demo. Authentication bypass: a tampered WHERE clause makes the credential check succeed. Data exfiltration: a UNION-style addition appends rows from another table to a result set the page already renders. Blind injection: the page shows no data or errors, but a conditional expression changes the response — a different page, a different status code — so the attacker reconstructs data one true/false question at a time. Time-based blind injection: even the response is identical, so a conditional sleep turns the answer into a measurable delay; this one works against a completely silent endpoint and is why "we don't show SQL errors" is not a mitigation. And injection is not read-only — a reachable statement can update or delete rows, and on some engines call into the file system or run OS commands through database features. Second-order injection deserves its own mention: input that was safely parameterised on the way in is stored, then later concatenated into a query by a batch job, and the flaw surfaces far from the code that accepted it.

PreparedStatement: why binding works at the protocol level

A PreparedStatement is not a fancier way of escaping quotes. The SQL text, with ? markers where values go, is sent to the server and parsed first — the statement's structure is fixed and named before any user value exists in the same room as it. The values then travel as separate, typed fields in a distinct part of the wire protocol (or, for drivers that emulate binding client-side, through the driver's own type-correct encoder). By the time your value arrives, the parser has already finished its job and there is no longer any parsing step for the value to influence. A quote inside the value is just a byte in a character field. That is why binding is a categorical defense and escaping is a probabilistic one.

Three practical notes. Bind by type, not by toString() — use setLong, setInt, setTimestamp rather than pushing everything through setString, because a numeric column bound as text can force a cast and, on some engines, an index-defeating plan. Reuse the prepared statement across a loop instead of rebuilding it; correctness is the point but the parse-once behaviour is a genuine performance win. And do not let the concatenation sneak back in as a "convenience" — the moment any part of the SQL string is assembled from a variable, the protection is gone for that part, even if the other twelve values are properly bound.

// VULNERABLE — the value becomes part of the parsed statement
String sql = "SELECT id, email FROM users WHERE email = '" + email + "'";
try (Statement st = conn.createStatement();
     ResultSet rs = st.executeQuery(sql)) { ... }

// FIXED — structure is parsed first, the value arrives as a typed field
String sql = "SELECT id, email FROM users WHERE email = ? AND status = ?";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, email);
    ps.setInt(2, status);          // bind by type, not via toString()
    try (ResultSet rs = ps.executeQuery()) { ... }
}

JPA, JPQL and Spring Data: where Java developers actually get caught

"We use JPA, so we are safe from SQL injection" is the single most common wrong answer in Java security interviews. JPA protects you when you let it build the SQL; it does nothing at all when you build the query text yourself. entityManager.createQuery("FROM User u WHERE u.email = '" + email + "'") is injectable exactly like the JDBC version — Hibernate faithfully translates your JPQL, including the parts an attacker wrote, into SQL. JPQL injection is more constrained than raw SQL injection because JPQL is a smaller grammar over your entity model, but it is quite enough to bypass a condition or read entities the user should not see, and with createNativeQuery you are back to full SQL with nothing between the input and the database.

In Spring Data the same fork appears inside @Query. A query string with " + param + " spliced into it is vulnerable; the same query with a :name placeholder and @Param is not, because Spring Data hands the value to the JPA binder. Two more mechanisms are safe by construction and worth naming: derived query methods such as findByEmailAndStatus, where the query is generated from the method name at bootstrap and user input can only ever arrive as an argument; and the Criteria API (or Spring Data Specification), where you assemble a typed object tree rather than a string, so predicates are built from metamodel attributes and literals become bind parameters automatically. Criteria code is verbose, which is why people abandon it for string building — that abandonment is where the bug is introduced, so prefer Specifications for genuinely dynamic filters.

// VULNERABLE — JPA does not save you here; the JPQL string is attacker-shaped
em.createQuery("SELECT u FROM User u WHERE u.email = '" + email + "'", User.class);
em.createNativeQuery("SELECT * FROM users WHERE email = '" + email + "'");

// FIXED — named parameters, bound by the provider
em.createQuery("SELECT u FROM User u WHERE u.email = :email", User.class)
  .setParameter("email", email);

// Spring Data: vulnerable @Query on the left, safe on the right
@Query("SELECT u FROM User u WHERE u.status = '" + "?#{[0]}" + "'")   // don't
@Query("SELECT u FROM User u WHERE u.status = :status")               // do
List<User> findByStatus(@Param("status") String status);

// Safe by construction: derived method name, and Criteria/Specification
List<User> findByEmailAndStatus(String email, String status);

What you cannot bind: ORDER BY, identifiers, LIKE, and stored procedures

Bind parameters occupy value positions only. You cannot bind a table name, a column name, a sort direction, or an operator, because those are parsed as part of the statement's structure — the very thing the prepare step froze. So the endpoint that accepts ?sort=createdAt&dir=desc and pastes both into an ORDER BY clause is the classic hole that survives an otherwise perfectly parameterised codebase, and it is a favourite interview question precisely because the reflex answer ("use a bind variable") does not work. The only correct answer is an allow-list: map the incoming token through a fixed set of permitted column names and reject anything not in the set — do not regex-validate it, do not escape it, look it up. In Spring Data, prefer passing a Sort or Pageable that you constructed from allow-listed properties; Spring Data validates sort properties against the domain model and refuses function calls in Order instances unless you deliberately opt in with JpaSort.unsafe — an API whose name is telling you something. Note also that Spring Data cannot apply dynamic sorting to native queries at all, which is exactly when people start concatenating.

Three related traps. LIKE patterns: binding the parameter stops injection, but % and _ inside the bound value are still wildcards to the pattern matcher, so a user-supplied search term can widen the match to everything and turn a lookup into a full scan; escape those two characters within the value and declare an ESCAPE character. Stored procedures are frequently offered as an automatic defense and are nothing of the kind — a procedure that builds a statement internally and passes it to dynamic SQL is injectable through its own parameters; a procedure is safe only if it does not concatenate, which is a property of its body, not of being a procedure. Escaping and sanitising remain the last-resort answer and keep failing: encodings that reach the parser differently than they reached your filter, engine-specific escape rules, multi-byte character sets, an operator you did not think of, and the perennial problem that a blocklist enumerates badness and reality keeps adding to the list. Use validation as defense in depth on top of parameterisation, never instead of it.

// VULNERABLE — sort column and direction are structure, so they get concatenated
String sql = "SELECT * FROM orders ORDER BY " + sortBy + " " + direction;

// FIXED — look the token up in a fixed set; anything unknown is rejected
private static final Map<String, String> SORTABLE =
    Map.of("created", "created_at", "total", "total_amount", "id", "id");

String column = SORTABLE.get(sortBy);
if (column == null) throw new BadRequestException("unknown sort field");
String dir = "desc".equalsIgnoreCase(direction) ? "DESC" : "ASC";
String sql = "SELECT * FROM orders ORDER BY " + column + " " + dir; // only literals now

// LIKE: bound, but still escape the wildcard characters inside the value
String term = raw.replace("!", "!!").replace("%", "!%").replace("_", "!_");
ps.setString(1, "%" + term + "%");   // query text: ... LIKE ? ESCAPE '!'

OS command injection: pass an argument array, not a shell string

The same bug, a different interpreter. Runtime.getRuntime().exec("convert " + filename + " out.png") hands the caller control of the shell's grammar wherever a shell is involved: separators, pipes, backgrounding, substitution, redirection. Java's exec(String) is doubly dangerous because it does its own naive whitespace tokenisation, so what actually gets run bears little relation to what you thought you wrote. The fix is structural, not lexical — use ProcessBuilder (or exec(String[])) and pass the program and each argument as separate array elements. The operating system then receives an argv array directly; the value with the semicolon in it is one argument, because argument boundaries were decided by your array and not by a parser reading a string.

Two escalations of that principle. First, avoid the shell entirely: never invoke sh -c or cmd.exe /c with an assembled string, because that reintroduces the parser you just eliminated. If you need a pipeline, build it with ProcessBuilder.startPipeline or wire the streams yourself rather than delegating to the shell. Second, ask whether you need a process at all — the overwhelming majority of exec calls in enterprise Java are doing something a library already does in-process (archiving, image conversion, hashing, HTTP), and no process launch means no command injection. Where a process is genuinely required, keep the executable path a fixed constant chosen from an allow-list rather than something derived from a request, validate arguments against a strict pattern as defense in depth, set an explicit working directory, and run the process as a low-privilege account so a mistake is contained.

// VULNERABLE — one string, tokenised naively, and shell metacharacters survive
Runtime.getRuntime().exec("convert " + userFile + " -resize 200x200 out.png");

// FIXED — fixed executable, one array element per argument, no shell anywhere
List<String> cmd = List.of("/usr/bin/convert", userFile, "-resize", "200x200", "out.png");
ProcessBuilder pb = new ProcessBuilder(cmd);
pb.directory(sandboxDir);
pb.redirectErrorStream(true);
Process p = pb.start();   // userFile is ONE argument, whatever bytes it contains

LDAP, XPath and NoSQL: the interpreters people forget they are using

LDAP injection shows up in exactly the place that matters — the login path — because corporate authentication often ends in a directory search whose filter was built by concatenation. LDAP search filters are a small prefix grammar with their own metacharacters (parentheses, the asterisk wildcard, the backslash, the NUL byte, and the boolean operators), so a username containing filter syntax can widen the filter or short-circuit a condition and return a user record the query was never meant to match. Two distinct escaping contexts exist and are commonly confused: values inside a search filter and values inside a distinguished name follow different rules. Do not hand-roll either — use the escaping helper your API provides (Spring LDAP and the JNDI-based helpers both offer one) and build filters through a filter-construction API rather than string formatting. And prefer binding as the user over comparing a password you fetched, so the directory performs the credential check.

XPath injection is the same story against an XML document: a concatenated XPath expression lets input add a predicate or terminate one, exposing nodes outside the intended subtree. Use a variable resolver and precompiled expressions so values are supplied as XPath variables rather than spliced into the expression text. NoSQL injection is the modern reincarnation and catches people who assumed "no SQL, no SQL injection". MongoDB's danger is not string syntax but operator injection: if a JSON request body is deserialised straight into a query document, a field whose value is an object containing a query operator turns an equality test into a comparison that matches everything — no quoting involved, purely a structural substitution. Bind request bodies to typed DTOs with declared scalar field types instead of maps or generic documents, build queries with the driver's typed builders or Spring Data repositories, and treat server-side JavaScript evaluation such as $where as something to keep disabled rather than something to sanitise.

// VULNERABLE — username lands in the filter grammar
String filter = "(&(objectClass=person)(uid=" + username + "))";

// FIXED — escape the value for the filter context, or use a filter builder
String filter = "(&(objectClass=person)(uid={0}))";
ctx.search(base, filter, new Object[] { username }, searchControls);

// NoSQL: bind to a typed field, so a JSON object cannot become an operator
public record LoginRequest(String username, String password) { }  // not Map<String,Object>

Log injection, and the Log4Shell lesson

Logs feel like a write-only sink, which is why log.info("login failed for " + username) passes review everywhere. But a log file is parsed — by humans, by a log shipper, by a dashboard, by an alerting rule. A username containing carriage return and line feed characters produces what looks like additional log lines, so an attacker can forge entries: a fake successful login, a fabricated admin action, a plausible-looking error attributed to someone else. That is CRLF log forging, and its real cost is that your incident timeline — the artifact you will rely on when something goes wrong — becomes untrustworthy evidence. Downstream, the same untrusted text can carry markup or formulas into whatever renders the logs, turning a log viewer into a delivery mechanism. Defenses: strip or encode CR and LF from any value before it enters a message, log to a structured format (JSON) where values are encoded fields rather than free text, use parameterised logging (log.info("login failed for {}", username)) so the layout treats the value as a value, and never log secrets or full request bodies "just in case".

Then there is the harder lesson. Log4Shell (CVE-2021-44228) was not a log-forging bug — it was the discovery that the logging framework itself contained an interpreter. Log4j's message lookup substitution evaluated ${...} expressions found inside logged strings, including JNDI lookups that would fetch and load a remote resource, so merely logging an attacker-controlled string was remote code execution. Every application that logged a user agent or a username was affected, which is essentially every application. The generalisable takeaway, and the one worth saying in an interview: a component that evaluates the data it is handed is an interpreter, and passing untrusted data to an interpreter is injection — no matter how mundane the component looks. Keep logging, template and expression libraries patched, disable evaluation features you do not need, and treat "does this thing evaluate my input?" as a question you ask of every dependency.

// VULNERABLE — line breaks in the value forge new log entries
log.info("login failed for " + username);

// FIXED — parameterised logging plus a scrub of the line-break characters
log.info("login failed for {}", username.replaceAll("[\\r\\n]", "_"));

// Better still: structured logging, where the value is an encoded field
log.atInfo().addKeyValue("event", "login_failed")
            .addKeyValue("username", username)
            .log("authentication rejected");

Expression-language and template injection: the Java-specific blind spot

The JVM ecosystem is unusually rich in string-evaluating engines, and that richness is a liability. SpEL is the obvious one: parser.parseExpression(userSuppliedString).getValue() against a default evaluation context gives the caller access to type references and reflection, which is remote code execution rather than a data leak. The same applies to MVEL, OGNL, Jakarta Expression Language, and any rules engine whose rules are strings. The fix is the standard shape once more: the expression is code, so the expression must be a constant your program owns, compiled once, with untrusted input supplied as a variable or root object rather than concatenated into the expression text. If user-authored expressions are a genuine product requirement, run them in a restricted evaluation context (SimpleEvaluationContext rather than StandardEvaluationContext) that exposes only property access on an allow-listed root, and treat that as a sandbox to defend, not a solved problem.

Server-side template injection is the same defect in the view layer, and it has a distinctive Java flavour. The rule is simple: templates are code, template data is data. Selecting a template by a user-controlled name, or worse assembling template source from request values, hands the caller the template engine's own language — and in Thymeleaf, fragment and expression syntax reaches SpEL, so a template-level injection escalates to the same code execution as above. Keep template names fixed or allow-listed, pass everything variable through the model, never build template source at runtime, and be equally careful with the "expression fragment" features in Spring Data @Query and Spring Security annotations that quietly evaluate SpEL — a @PreAuthorize string assembled from configuration is an expression-injection sink.

// VULNERABLE — the user's string IS the program
Expression e = parser.parseExpression(userInput);
Object result = e.getValue(new StandardEvaluationContext(order));

// FIXED — fixed expression, user data supplied as a variable, restricted context
Expression e = parser.parseExpression("#candidate == order.customerId");  // constant
EvaluationContext ctx = SimpleEvaluationContext.forReadOnlyDataBinding()
        .withRootObject(order).build();
ctx.setVariable("candidate", userInput);
Boolean ok = e.getValue(ctx, Boolean.class);

Defense summary, and what testing actually catches

Every row below is the same instruction: move the untrusted value out of the code channel. Memorise the table as a shape rather than as a list, and when you meet an interpreter that is not on it — a GraphQL filter, a search-engine query language, a spreadsheet formula, a prompt — ask the two questions that generate the right row: what grammar will parse this string, and does this API give me a way to supply values separately?

On testing: a good SAST tool is genuinely effective against this class because injection is a taint-flow problem — source (request parameter) to sink (query execution) with no sanitiser in between — which static analysis models well. Expect it to find plain concatenation into Statement, createQuery, exec and template APIs. Expect it to miss: taint that travels through a database round trip (second-order injection), flows through reflection or dependency-injected indirection it cannot resolve, custom "sanitiser" methods it charitably assumes are correct, string building in configuration files or SQL held in resources, and everything about the ORDER BY allow-list problem, since the concatenation there is intentional and only the missing allow-list makes it a bug. Complement SAST with DAST or an interactive proxy against a running instance, with dependency scanning (Log4Shell was a dependency finding, not a code finding), and with a code-review habit that treats any string-built query as a defect regardless of how safe the inputs look today.

Interview questions

Injection is the security topic Indian product and service companies ask about most, and it appears in backend rounds as often as in security rounds — the JPA questions in particular separate candidates who have shipped Spring code from candidates who have read about it:

Beginner What is SQL injection, in one sentence?

Untrusted input is concatenated into a SQL string, so characters that are syntax in SQL change the structure of the query instead of being treated as a value — letting the caller alter conditions, read other tables, or modify data. The database is not malfunctioning; it is faithfully running the query your code assembled.

Beginner How do prepared statements prevent SQL injection?

The SQL text with ? placeholders is sent and parsed first, so the statement's structure is fixed before any user value is involved. Values then travel separately as typed protocol fields, and there is no remaining parse step for them to influence — a quote inside a value is just a character in a string. That is why binding is a categorical fix rather than escaping, which merely tries to neutralise characters and depends on modelling the engine's grammar perfectly.

Beginner Statement vs PreparedStatement — differences beyond security?

PreparedStatement is precompiled, so repeated executions reuse the parsed plan, which helps throughput in loops and batches. It is typed, so setInt / setTimestamp avoid conversion bugs and cast-induced bad plans. It handles binary and large values properly. Statement is only appropriate for fully static SQL with no external input, and even then PreparedStatement is the better habit.

Beginner Name three interpreters other than SQL that can be injected, and the fix for each.

The operating system shell — fixed by passing an argument array to ProcessBuilder and avoiding a shell. LDAP — fixed by a filter-building API with context-correct escaping. A logging framework or expression evaluator — fixed by parameterised or structured logging, and by keeping expressions constant with input supplied as variables. The pattern is identical in all three: separate the data channel from the code channel.

Intermediate Is JPA automatically safe from SQL injection?

No. JPA is safe when it generates the query — derived method names, Criteria API, Specifications, and JPQL with named parameters all bind values. It is not safe when you build the query text yourself: createQuery or @Query with concatenated strings is injectable JPQL, and createNativeQuery with concatenation is plain SQL injection with an ORM logo on it. The protection comes from the binding, not from the letters J-P-A.

Intermediate A user picks the sort column and direction. You cannot bind either. How do you make it safe?

Allow-list. Keep a fixed map from public sort tokens to real column names, look the incoming value up, reject anything absent, and normalise the direction to exactly ASC or DESC. Never regex-validate or escape the identifier — enumerate it. In Spring Data, construct Sort or Pageable from allow-listed properties and let the framework validate them against the domain model; be aware that dynamic sorting is not supported on native queries, which is precisely the situation where people start concatenating.

Intermediate Are stored procedures an automatic defense against SQL injection?

No. A stored procedure is safe only if its body does not build a statement by concatenation. Procedures that assemble dynamic SQL internally and execute it are injectable through their own parameters, and the injection is now hidden inside the database where application scanners will not see it. Calling a procedure with bound parameters from Java is fine; assuming the procedure is safe because it is a procedure is not.

Intermediate What is blind SQL injection, and why doesn't hiding error messages fix it?

Blind injection extracts data without the application ever displaying it: the attacker injects a condition and infers the answer from an observable difference — a different page, a different status code, or, in the time-based variant, a deliberate delay. Since the channel is the response's behaviour rather than its content, suppressing error messages removes a convenience, not the vulnerability. Hiding errors is good practice for other reasons; it is not a fix.

Intermediate Why is Runtime.exec with a concatenated string worse than ProcessBuilder with a list?

A single string has to be split into a program and arguments by someone, and that someone parses metacharacters. Java's exec(String) tokenises naively on whitespace, and if a shell is involved the caller also gets separators, pipes, redirection and substitution. Passing a list means argument boundaries are decided by your array and delivered to the OS as argv, so a value containing a semicolon is one argument. Better still, ask whether the process is needed at all — a library call cannot be command-injected.

Intermediate How does binding a LIKE parameter still cause a problem, and what do you do about it?

Binding stops injection but not wildcards: % and _ inside the bound value are still pattern syntax, so a user-supplied term can match far more rows than intended and turn a lookup into a full scan — a denial-of-service and a data-exposure issue rather than a code-execution one. Escape those characters within the value and declare an ESCAPE character in the query, and cap result sizes independently.

Pro Why is escaping considered a last-resort defense rather than a primary one?

Because it requires you to model the interpreter's grammar exactly, in every context, forever. Escape rules differ per engine and per position (a value inside a string literal, an identifier, an LDAP filter, an LDAP distinguished name); character-set and encoding differences can let a sequence reach the parser differently from how it reached your filter; and blocklists enumerate a badness set that reality keeps extending. Parameterisation removes the parsing step entirely instead of trying to win an argument with it, so escaping is reserved for the positions where binding is genuinely impossible — and there it is paired with an allow-list.

Pro What was the Log4Shell lesson, beyond "patch Log4j"?

That a logging framework was an interpreter. Log4j evaluated substitution expressions inside logged strings, including lookups that fetched and loaded a remote resource, so merely logging an attacker-controlled header was remote code execution. The generalisation is that any component which evaluates the data you hand it is an interpreter, and untrusted data reaching an interpreter is injection — regardless of how boring the component looks. Practically: keep evaluation features disabled unless needed, keep such libraries patched, scan dependencies rather than only code, and never assume a sink is inert because it is "just logging".

Pro Explain NoSQL operator injection in MongoDB, and how the fix differs from SQL.

There is no string grammar to break — the query is a document. If a JSON request body is deserialised into a map or generic document and used as the query, a field whose value is an object containing a query operator turns an equality test into a comparison that matches broadly, so no quoting or escaping is involved at all. The fix is therefore structural typing rather than parameterisation: bind the body to a DTO with declared scalar fields, build queries with typed builders or repositories, reject unexpected fields, and keep server-side evaluation such as $where disabled.

Pro Where does SpEL injection appear in an ordinary Spring application, and how do you make expression evaluation safe?

Anywhere an expression string is influenced by input or by mutable configuration: parsing a user-supplied rule, Thymeleaf fragments and template names, expression fragments inside Spring Data @Query, and @PreAuthorize strings assembled at runtime. Evaluating input against a StandardEvaluationContext exposes type references and reflection, which is code execution rather than a data leak. Keep the expression a compiled constant, pass input as a variable or root object, and where user-authored expressions are a real requirement use SimpleEvaluationContext with read-only data binding over an allow-listed root — and treat it as a sandbox you must defend.

Pro What is second-order injection, and why do scanners miss it?

Input is stored safely — correctly parameterised on the way in — and later read back and concatenated into a query by a different component, often a batch job, report or admin screen. The vulnerable code is nowhere near the code that accepted the value. Static analysis loses the taint at the database boundary because it cannot follow a value out through an insert and back in through a select, and dynamic testing misses it because the effect is delayed and triggered elsewhere. The defense is a rule rather than a tool: parameterise at every sink, including for data that came from your own database, since "trusted source" is not a property of a value once it has been stored.

Pro A team says "we validate all input, so injection is handled". Critique that.

Validation and parameterisation solve different problems. Validation enforces business shape — this is an email, this is a positive integer, this is one of five statuses — and is valuable defense in depth. It does not make a concatenated query safe, because the moment a field legitimately contains free text (a name with an apostrophe, a search term, an address) the filter must either reject valid data or let syntax through. It also has to be applied at every entry point forever, whereas binding is applied at the sink where the risk actually is. Correct answer: parameterise at the sink, allow-list where binding is impossible, and validate on top of both — never instead of them.
