Module: Secrets and Applied Cryptography

Almost nobody breaks AES. They find the key in a repository, in a log line, in an environment dump, or in a home-made protocol that used the same nonce twice. These two topics fail at the edges, not at the algorithm.

Knowledge Library → Courses → Secure Coding track → Secrets and Applied Cryptography

What this module covers

Two subjects that look separate and are really one. Cryptography turns a confidentiality problem into a key-management problem — that is its whole value proposition — and secrets management is what you do with the keys afterwards. When an application is breached through this area, the cause is almost never a broken cipher. It is a database password in application.properties, an access key pasted into a Slack thread and then into a commit, a token logged at DEBUG, or a bespoke "encryption" routine written by someone in a hurry.

The first half is operational: where secrets may live, how they get out, how you rotate them, and how you detect a leak before someone else does. The second half is the practising developer's slice of applied cryptography — enough to make correct choices and recognise wrong ones, deliberately stopping short of implementation. This module teaches defensive mechanisms and their correct use; the goal is that you can pick the right primitive, configure it properly, and know when to stop and call a library.

Topics

A credential committed to git is compromised permanently

Deleting a secret in a later commit does nothing. Git is an append-only object store: the blob containing the old value stays reachable from the earlier commit, so git log -p, git show against any historical revision, and any tooling that walks history will still surface it. Worse, the secret has already been distributed. Every clone on every laptop and CI runner holds a full copy of that history, every fork has its own copy, and on GitHub a commit that has been pushed to a fork network can remain fetchable by its hash even after the branch is rewritten. Rewriting history with git filter-repo or BFG helps you stop republishing it, but it cannot un-distribute what has already left.

The correct mental model is therefore blunt: the moment a live credential lands in a repository — public or private — treat it as known to an attacker and rotate it. Public repositories are scraped continuously and credentials committed to them are routinely used within minutes; private repositories are safer only until the next contractor, the next backup, or the next misconfigured mirror. History rewriting is cleanup, not remediation. Prevention is the real answer, and it starts with an honest .gitignore that excludes .env, *.pem, keystores and local override files, plus the discipline of never templating a real value into a file that git tracks.

# "I removed it in the next commit" — the value is still right there:
git log -p -- src/main/resources/application.properties | grep -i password
git rev-list --all | xargs -n1 -I{} git grep -l "AKIA" {} 2>/dev/null

# .gitignore is prevention, not remediation
.env
.env.*
*.pem
*.p12
*.jks
src/main/resources/application-local.properties

The storage ladder: hardcoded, config file, environment variable, mounted file, secret manager

There is a ladder here and most teams stop one rung too early. Hardcoded in source is never acceptable — it is in git, in every build artifact, and decompilable out of any JAR you ship. A config file committed to the repo is the same failure wearing a different hat. Environment variables are a genuine improvement and the twelve-factor default: they keep the value out of the artifact and let the same image run in every environment. But they are not a security boundary. On Linux they are readable from the process environment by anything running as the same user, they are inherited by every child process you fork, they land in crash dumps and heap dumps, they are printed by well-meaning diagnostic endpoints, and they leak into CI logs the moment somebody adds a debug printenv to a failing pipeline.

Mounted secret files are the next rung: the value arrives as a file with restrictive permissions, it is not inherited by child processes, and — critically — the file can be updated underneath a running process, which is what makes rotation without a restart possible at all. The top rung is a dedicated secret manager — HashiCorp Vault, AWS Secrets Manager, AWS Systems Manager Parameter Store with SecureString, Azure Key Vault, GCP Secret Manager. What you buy there is not storage; it is the surrounding machinery: per-identity access control, a full audit trail of who read which secret and when, versioning so you can roll back, managed rotation, and in Vault's case dynamic credentials that are minted per application instance and expire on their own. In Spring Boot, spring-cloud-vault or the AWS parameter-store integration wires these into the normal Environment, so application code keeps reading @Value and never learns where the value came from.

Kubernetes Secrets are base64, not encryption

A Kubernetes Secret is a ConfigMap with a different name and base64 encoding, and base64 is an encoding, not a cipher — anyone who can read the object can decode it in one command. By default the value is stored in etcd essentially in the clear, which is why the two controls that actually matter are RBAC (who may get secrets in this namespace, and does your default ServiceAccount really need it?) and encryption at rest via an EncryptionConfiguration on the API server, ideally backed by a KMS provider so the encryption key is not sitting next to the data. Checking a Secret manifest into git is exactly as bad as checking in the plaintext, because it is the plaintext with extra steps.

The pattern that resolves this is external secrets: keep the real values in Vault or a cloud secret manager, and let a controller project them into the cluster. The External Secrets Operator does this with an ExternalSecret custom resource that references a SecretStore; the operator authenticates with a workload identity, fetches the value, and materialises a normal Kubernetes Secret which it refreshes on an interval. Nothing sensitive is ever committed, the source of truth stays in the audited store, and a rotation upstream propagates automatically. The sibling approach, Sealed Secrets, encrypts values so they can be committed — useful for GitOps, but the ciphertext is still permanent history, so prefer external references when you have the choice.

# A Secret is base64, and base64 is trivially reversible:
#   kubectl get secret db -o jsonpath='{.data.password}' | base64 -d
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata: { name: db-credentials }
spec:
  refreshInterval: 1h              # picks up upstream rotation
  secretStoreRef: { name: aws-secrets, kind: SecretStore }
  target: { name: db-credentials } # the K8s Secret the operator creates
  data:
    - secretKey: password
      remoteRef: { key: prod/orders/db, property: password }

Rotation: the step everyone documents and nobody exercises

A secret you cannot rotate is a secret you cannot respond to an incident with. The first blocker is architectural: most applications read credentials once at startup and cache them in a connection pool or a client object for the lifetime of the process. Rotate upstream and nothing changes until the next deploy — or worse, the old value stops working and the service fails at three in the morning with an authentication error nobody can explain. Rotation only works if the application can re-read the secret: a file mount plus a watcher, a config-refresh event (@RefreshScope in Spring Cloud), a client library that fetches on demand with a short cache, or a pool that can be rebuilt when credentials change.

The second blocker is that naive rotation is an outage. If you change the password in one atomic step, every instance still holding the old one starts failing. The fix is a dual-credential window: provision the new credential alongside the old, let both authenticate for a period comfortably longer than your rollout, cut traffic over, verify, and only then revoke the old one — the same alternating-user pattern AWS Secrets Manager implements for databases. The better answer, where the platform supports it, is to stop having long-lived credentials at all: Vault's database secrets engine mints a unique username and password per application instance with a lease measured in hours and revokes them automatically, and cloud IAM roles do the same for cloud APIs. A credential that expires on its own turns "rotate everything" from a project into a non-event, and it makes a leaked value nearly worthless by the time anyone finds it.

Detecting leaked credentials, and what to do in the first hour

Detection belongs at three points, and you want all three because each catches what the others miss. A pre-commit hook — gitleaks or TruffleHog wired through the pre-commit framework — stops the commit on the developer's machine, which is the only place a leak is still cheap. CI scanning catches what people bypass with --no-verify and scans the full history on a schedule, so you learn about the key somebody committed last April. Platform scanning is the safety net: GitHub secret scanning matches known provider token formats and notifies the provider, which can revoke on your behalf, and push protection rejects the push outright when it recognises a live token. Detection is imperfect — a generic database password looks like any other string, so high-entropy heuristics produce false positives and false negatives — which is why prevention still carries most of the weight.

When something does leak, the order of operations matters more than the thoroughness. Rotate first, investigate second. Revoke and reissue the credential immediately; until you do, every minute of investigation is a minute an attacker may be using it. Only then work out the blast radius: what could that credential reach, what did it actually do (audit logs, CloudTrail, database access logs), and how long was it exposed. Then remove it from history and from any downstream copies — build caches, container image layers, log aggregation, error-tracker payloads, Slack and ticket attachments. Finally close the loop: add the pattern to your scanner, and ask why the credential was long-lived and broadly scoped enough for the leak to matter, because "least privilege plus short lease" is what turns the next leak into a shrug.

Hashing, encryption and encoding are three different things

This is the distinction interviewers use to sort candidates in thirty seconds, and it is worth being precise. Hashing is a one-way function: arbitrary input to a fixed-size digest, with no key and no inverse. You use it to verify — does this password match, is this file unchanged, do these two records have the same content. Encryption is reversible and keyed: you use it for confidentiality, when the plaintext must come back later, and its security lives entirely in the key. Encoding — base64, URL-encoding, hex — is a reversible transformation with no key and no secret at all. It exists to make bytes safe for a transport that expects text. It provides exactly zero security, and calling base64 "encryption" in an interview is disqualifying.

Two follow-ups are worth pre-loading. First, choose by intent: if you never need the original value back, hash it; if you do, encrypt it. Passwords are hashed because you only ever need to check them. A customer's PAN or Aadhaar number, a stored OAuth refresh token, an API key you must present to a third party — these are encrypted, because the system needs the value. Second, the same word "hashing" covers two very different jobs: hashing for integrity, where a fast general-purpose digest like SHA-256 is exactly right, and hashing for password storage, where fast is the entire problem. Using SHA-256 in the second role is the single most common cryptographic mistake in production Java code.

Password storage: what a salt actually prevents

Start from the attack model. An attacker with your user table does not "reverse" the hash; they guess candidate passwords and hash them, billions per second on a GPU. Against unsalted SHA-256 they do better still: they precompute once and look answers up, which is what a rainbow table is. A salt is a unique random value stored alongside each hash and mixed into it. It does not slow a single guess down, and it is not secret. What it does is make precomputation useless — a table built for one salt is worthless against every other — and it decouples identical passwords, so two users who both chose the same weak password no longer produce the same digest. That second property matters more than people expect: without it, a leaked table hands the attacker a frequency histogram pointing at the most common passwords in your user base.

A pepper is an optional extra: a single site-wide secret value mixed in as well, but stored outside the database — in a KMS, an HSM, or at least a separate config store. Its purpose is narrow and specific: if the database alone leaks (SQL injection, a stolen backup) and the pepper does not, the hashes are uncrackable without it. It is not a substitute for a proper password hash, it complicates rotation, and OWASP treats it as a defence-in-depth extra rather than a requirement. Two more rules to internalise: never impose a low maximum password length or strip characters, because that shrinks the search space for no benefit; and check candidate passwords against a breached-password list, which NIST now recommends in place of the old composition-and-expiry rules that pushed users toward predictable patterns.

Choosing the password hash — and upgrading it in place

The requirement for a password hash is the opposite of every other performance requirement you have: it must be slow, and ideally expensive in memory too, so that an attacker's GPU or ASIC advantage collapses. That rules out SHA-256, SHA-3, MD5 and every other general-purpose digest, however many times you loop it by hand. The current recommendations are Argon2id first (memory-hard, standardised in RFC 9106, tuned by memory size, iterations and parallelism), then scrypt where Argon2 is unavailable, then bcrypt — which is old, capped at 72 bytes of input, but still respectable and ubiquitous in the Java ecosystem. PBKDF2 remains acceptable mainly where FIPS compliance demands it, at a high iteration count. Whichever you pick, take the work factors from the current OWASP cheat sheet rather than from a blog post, and re-evaluate them periodically; hardware moves, so a work factor is a decision with an expiry date.

The practical problem in a long-lived system is that you already have a table full of hashes from a scheme you now regret. Spring Security solves this with DelegatingPasswordEncoder, the default since version 5: stored hashes carry an algorithm prefix such as {bcrypt} or {argon2}, matching dispatches to the right encoder, and new passwords are always written with the current default. Combine that with upgradeEncoding — or simply re-encode on successful login — and the table migrates itself as users sign in, with no big-bang rewrite and no forced password reset. Never call the raw encoder's matches yourself with string comparison, and never log the encoded value; it is not a secret you can afford to leak either.

@Bean
PasswordEncoder passwordEncoder() {
    // Stored as {argon2}$argon2id$v=19$m=..., legacy rows keep {bcrypt}...
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}

// Upgrade-in-place on a successful login: re-encode with the current default.
if (encoder.matches(raw, user.getHash())) {
    if (encoder.upgradeEncoding(user.getHash())) {
        user.setHash(encoder.encode(raw));   // silently migrated
    }
}

Symmetric, asymmetric, and why unauthenticated encryption is a trap

Symmetric encryption uses one key for both directions — AES is the standard, it is fast, and it is what you use for actual data. Asymmetric encryption uses a public/private key pair — RSA, or elliptic-curve schemes — and it is comparatively slow and size-limited, so in practice it is used to establish or wrap a symmetric key and to produce signatures, not to encrypt payloads. That combination is exactly what TLS does during its handshake, and what envelope encryption does for data at rest. If a design has you RSA-encrypting a large document directly, the design is wrong.

The subtler point is authenticated encryption. A cipher mode that only provides confidentiality tells you nothing about whether the ciphertext was tampered with, and an attacker who can flip bits in transit can often flip corresponding bits in the plaintext. ECB is worse still: it encrypts each block independently, so identical plaintext blocks produce identical ciphertext blocks and the structure of the data survives encryption — the notorious image where the penguin is still visible. Raw CBC without a separate MAC has its own well-documented failure modes. The rule: use an AEAD mode — AES/GCM/NoPadding, or ChaCha20-Poly1305 — which produces an authentication tag that decryption verifies, so tampering fails loudly instead of silently. And use the highest-level API you can: Google Tink, the AWS Encryption SDK, or libsodium make the safe choice the default, whereas the raw JCA Cipher API will happily let you request ECB.

// AES-GCM: confidentiality AND integrity. Nonce is random, unique per message,
// and stored alongside the ciphertext (it is not secret).
byte[] nonce = new byte[12];
SecureRandom.getInstanceStrong().nextBytes(nonce);

Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, nonce));
cipher.updateAAD(tenantId.getBytes(UTF_8));   // bound, authenticated, not encrypted
byte[] ciphertext = cipher.doFinal(plaintext);

// Wrong by construction: "AES" alone means AES/ECB/PKCS5Padding on most JDKs.

Nonces, randomness, HMAC and constant-time comparison

Three implementation details cause a disproportionate share of real cryptographic failures. First, never reuse an IV or nonce with the same key. In GCM this is catastrophic rather than merely weak: two messages encrypted under the same key and nonce leak the XOR of their plaintexts and, worse, allow recovery of the authentication subkey, which breaks integrity for every message under that key. Generate the nonce randomly per message (or use a strict counter you can prove never repeats), store it with the ciphertext, and rotate the key long before you approach the birthday bound. Second, use SecureRandom, never java.util.Random or Math.random() — the latter are fast, predictable pseudo-random generators seeded from low-entropy sources, and an attacker who observes a few outputs can predict the rest. Anything that must be unguessable — nonces, salts, session identifiers, password-reset tokens, API keys — comes from SecureRandom.

Third, when you need to prove a message came from who it claims and has not been altered, the primitive is an HMAC: a keyed hash (RFC 2104) that a party without the key cannot forge. It is what signs webhook payloads, what protects opaque tokens, and what verifies a payment gateway callback. Two traps go with it: never build your own by concatenating a key and hashing it (that is length-extension bait — use the HMAC construction), and never compare the result with String.equals or Arrays.equals. Those return as soon as bytes differ, so the time they take reveals how many leading bytes were correct, and an attacker can recover a valid signature byte by byte. Compare with a constant-time routine — MessageDigest.isEqual in the JDK, or Spring Security's crypto utilities — which always examines the whole buffer.

Mac mac = Mac.getInstance("HmacSHA256");
mac.init(new SecretKeySpec(webhookSecret, "HmacSHA256"));
byte[] expected = mac.doFinal(rawBody);

// Constant-time: examines every byte regardless of where it first differs.
if (!MessageDigest.isEqual(expected, providedSignature)) {
    throw new BadSignatureException();       // never Arrays.equals here
}

TLS: what it gives you, and the cost of turning validation off

TLS provides three things over the wire: confidentiality (an observer on the path sees ciphertext), integrity (tampering is detected), and authentication of the server (the certificate proves you are talking to the host you asked for, not to whoever answered). Notice what it does not provide — it says nothing about the data once it lands, nothing about who the user is, and nothing about the server's own hygiene. Getting it right in practice is mostly configuration: TLS 1.2 as the floor and 1.3 preferred, modern cipher suites, no compression, and HTTPS everywhere including internal service-to-service hops, because "it is only inside the VPC" stops being true the first time a load balancer is misconfigured or a sidecar is added.

The failure mode that actually shows up in code review is disabled certificate validation. Somebody hits a handshake error in a test environment, installs a trust-all TrustManager or a hostname verifier that returns true, ships it "temporarily", and now every TLS guarantee is gone: an attacker who can intercept the connection presents any certificate and reads and rewrites everything, silently. There is no partial version of this — validation is on or the channel is worthless. If a self-signed or internal CA certificate is the real problem, fix it properly by adding that CA to a truststore. Treat any trust-all code as a production incident wherever you find it, and add a lint or SAST rule so it cannot come back.

HSTS and certificate management

Serving HTTPS is not enough on its own, because the first request a browser makes may still be plaintext and redirectable. Strict-Transport-Security closes that gap: once the browser has seen the header, it refuses to make a plaintext request to that host for max-age seconds and will not let the user click through a certificate warning. Ship it with a long max-age, add includeSubDomains once you are confident every subdomain is served over HTTPS, and consider the preload list so even the very first visit is protected. Be deliberate: HSTS is sticky by design, so a short max-age while you validate the rollout is the sane way to start.

Certificates then become an operations problem, and the classic outage is expiry — a certificate nobody owned lapsing on a weekend. Automate it. AWS Certificate Manager issues and renews certificates for load balancers and CloudFront at no cost, and Let's Encrypt with an ACME client does the same anywhere else; either way the renewal is a cron job, not a calendar reminder. Add monitoring on days-to-expiry for every certificate you terminate, including internal ones, and use an external scanner such as Qualys SSL Labs to check the deployed configuration rather than what you believe you configured — it catches missing intermediate chains, weak protocol versions and mismatched hostnames that a browser on your own machine may quietly tolerate because of a cached chain.

Key management: envelope encryption, rotation, and never rolling your own

Encryption relocates the secret rather than removing it, so the design question is always "where does the key live, and who can reach it?" The first rule is separation: a key stored in the same database as the data it protects, or in the same repository as the code, protects nothing — one breach takes both. That is what a KMS is for. AWS KMS, Google Cloud KMS, Azure Key Vault and hardware security modules keep the master key inside a boundary it never leaves; you send data or a data key to be wrapped or unwrapped, and every operation is authorised by IAM and recorded in an audit log. The key is never in your process memory, so a heap dump does not surrender it.

Because calling a KMS for every record would be slow and size-limited, the standard pattern is envelope encryption: generate a fresh data key locally, encrypt the payload with it using AES-GCM, ask the KMS to encrypt that data key with the master key, then store the wrapped key beside the ciphertext and discard the plaintext data key. Decryption reverses it with one KMS call. This also makes rotation tractable — rotating the master key means re-wrapping data keys rather than re-encrypting terabytes — though be clear in interviews that rotating the master key does not retroactively re-encrypt old data; a true re-key requires reading and rewriting the records, so plan for it (a version tag on every ciphertext and a background re-encryption job). Close on the hard rule that governs this entire half of the module: do not design your own cryptographic protocol or primitive. Not a custom cipher, not a custom key-derivation scheme, not a "sign the request by concatenating the fields and hashing them" login flow. Use a vetted library at the highest level of abstraction available, and let people who do this full time carry the risk.

Interview questions

Secrets and crypto are asked in almost every Indian backend round — service companies favour the definitional questions, product companies push into rotation, envelope encryption and the incident scenario:

Beginner How do you store user passwords?

Never in plaintext and never encrypted — hashed, because you only ever need to verify, not recover. Use a deliberately slow, memory-hard password hash: Argon2id first, then scrypt, then bcrypt, with work factors taken from the current OWASP Password Storage Cheat Sheet. Each password gets a unique random salt (the library generates and stores it inside the hash string). Optionally add a site-wide pepper held outside the database. In Spring Security, use PasswordEncoderFactories.createDelegatingPasswordEncoder() so the stored value carries its algorithm prefix.

Beginner Difference between hashing, encryption and encoding?

Hashing is one-way and keyless — fixed-size digest, used to verify (passwords, integrity). Encryption is two-way and keyed — used for confidentiality when you need the plaintext back; its security is entirely in the key. Encoding (base64, hex, URL-encoding) is two-way, keyless and public — it makes bytes safe for a transport and provides no security whatsoever. Base64 is not encryption.

Beginner What is a salt and what attack does it stop?

A unique random value per password, stored with the hash and not secret. It defeats precomputation — rainbow tables and any shared dictionary of hashes — because a table built for one salt is useless against another. It also stops identical passwords producing identical hashes, so a leaked table no longer reveals which users share a common weak password. It does not make a single guess slower; that is the job of the work factor.

Beginner Why not SHA-256 for passwords? It is a strong hash.

It is strong for integrity and wrong for passwords, precisely because it is fast. SHA-256 is designed to be cheap, so a GPU can test billions of candidates per second and a leaked table falls quickly. Password hashes are designed to be slow and, in Argon2's case, memory-hard, so an attacker cannot buy their way past with parallel hardware. Iterating SHA-256 yourself is not a fix; use a purpose-built password hash.

Beginner Are Kubernetes Secrets encrypted?

No — by default they are base64-encoded and stored in etcd essentially in the clear. Anyone who can read the object, or read etcd or an etcd backup, has the value. To make them meaningfully protected you need RBAC restricting who may read secrets, encryption at rest configured on the API server (ideally with a KMS provider), and preferably an external store with the External Secrets Operator projecting values in rather than committing manifests to git.

Intermediate You accidentally committed an API key and pushed it. What now?

Rotate first, investigate second. Revoke and reissue the credential immediately — the value is compromised the moment it is pushed, because it lives in history, in every clone and in every fork, and deleting it in a later commit changes nothing. Then assess blast radius from audit logs (what could it reach, what did it actually do, how long was it exposed). Then clean up: rewrite history with git filter-repo or BFG, purge downstream copies in CI caches, image layers and logs, and notify the provider if they offer revocation. Finally add scanning and push protection so the next one is blocked, and ask why the credential was long-lived enough to matter.

Intermediate Environment variables or a secret manager — what is actually wrong with env vars?

Env vars are a real improvement over hardcoding, but they are not a security boundary. They are readable from the process environment by anything running as the same user, inherited by every child process, captured in crash and heap dumps, exposed by careless diagnostic endpoints, and easily echoed into CI logs. They also have no audit trail, no access control and no rotation story. A secret manager adds per-identity access control, an audit log of every read, versioning, managed rotation and — with Vault — short-lived dynamic credentials. Mounted secret files sit in between and, unlike env vars, can be updated under a running process.

Intermediate What is a pepper, and how is it different from a salt?

A salt is per-user, random and stored with the hash; it is not secret and it defeats precomputation. A pepper is a single site-wide secret mixed into every hash and deliberately stored somewhere else — a KMS, an HSM, a separate config store. Its only job is to protect you when the database alone leaks and the pepper does not. It is defence in depth, not a replacement for a slow hash, and it makes rotation harder because changing it invalidates every existing hash unless you version it.

Intermediate Symmetric vs asymmetric encryption — when do you use each?

Symmetric (AES) uses one shared key, is fast, and is what you use for actual data of any size. Asymmetric (RSA, elliptic curve) uses a key pair, is slow and size-limited, and is used for key establishment, key wrapping and digital signatures. Real systems combine them: TLS uses asymmetric cryptography in the handshake to agree a symmetric session key, and envelope encryption wraps a symmetric data key with a KMS master key. Encrypting a large payload directly with RSA is a design smell.

Intermediate Why AES-GCM rather than AES-CBC or ECB?

GCM is authenticated encryption: it produces an authentication tag, so decryption detects tampering and fails instead of returning attacker-influenced plaintext. ECB encrypts each block independently, so identical plaintext blocks yield identical ciphertext and data structure leaks straight through. Raw CBC gives confidentiality but no integrity, and has well-known failure modes when used without a separate MAC. Also note that requesting "AES" alone in the JCA gives you ECB on most JDKs — always name the full transformation.

Intermediate Someone disables certificate validation to fix a handshake error in staging. Your response?

Block it. A trust-all TrustManager or a hostname verifier returning true removes server authentication entirely, which means an attacker on the path can present any certificate and read and modify all traffic — the confidentiality and integrity guarantees go with it, silently. "Temporary" code of this kind reliably reaches production. Fix the actual cause instead: add the internal or self-signed CA to a truststore. Then add a SAST or lint rule so the pattern cannot reappear.

Pro How do you rotate a database password without downtime?

With a dual-credential window. Provision the new credential while the old one still authenticates, publish it to the secret store, let instances pick it up and rebuild their connection pools, verify no traffic is still using the old one, then revoke it. That requires the application to re-read the secret rather than cache it at startup — a watched file mount, a refresh event, or a client that fetches on demand. The better answer is to remove the problem: Vault's database secrets engine issues a unique short-lived credential per instance and revokes it on lease expiry, so rotation becomes continuous and automatic.

Pro Explain envelope encryption and what KMS key rotation actually rotates.

Envelope encryption generates a fresh data key per record or per batch, encrypts the payload locally with AES-GCM, asks the KMS to wrap that data key under a master key that never leaves the KMS, then stores the wrapped key next to the ciphertext and discards the plaintext data key. It avoids sending bulk data to the KMS and limits the blast radius of any one data key. Automatic KMS key rotation creates new key material for future encryptions and keeps old material available for decryption — it does not re-encrypt existing data. A genuine re-key means reading and rewriting every record, so version-tag your ciphertexts and plan a background re-encryption job.

Pro Why must a GCM nonce never be reused, and why is SecureRandom non-negotiable?

Reusing a nonce with the same key in GCM is catastrophic: two messages under the same key and nonce leak the XOR of their plaintexts, and the reuse also allows recovery of the authentication subkey, which forfeits integrity for every message under that key. Generate the nonce randomly per message (or from a counter you can prove never repeats), store it with the ciphertext, and rotate keys well before the birthday bound. java.util.Random and Math.random() are predictable pseudo-random generators — observing a few outputs lets an attacker predict the rest — so anything that must be unguessable (nonces, salts, session ids, reset tokens) comes from SecureRandom.

Pro You verify a webhook signature with Arrays.equals. What is the problem?

It is a timing side channel. Arrays.equals and String.equals return as soon as two bytes differ, so the comparison takes longer the more leading bytes are correct. An attacker who can send many requests and measure response time recovers a valid signature one byte at a time. Compare with a constant-time routine that always examines the whole buffer — MessageDigest.isEqual in the JDK. Related traps: build the MAC with the HMAC construction rather than hashing key-plus-message yourself (length extension), and verify against the exact raw body bytes rather than a re-serialised object.

Pro When is it acceptable to write your own cryptographic algorithm or protocol?

Effectively never in application work. Cryptographic primitives and protocols fail in ways that testing does not reveal — the code produces plausible output while being trivially breakable, and the flaws (padding oracles, nonce reuse, timing leaks, unauthenticated modes, weak key derivation) are found only by specialist review. Use a vetted library at the highest level of abstraction available: Tink, libsodium, the AWS Encryption SDK, Spring Security's crypto module, or platform TLS, rather than assembling Cipher calls yourself. The correct senior instinct is to reduce the problem to a key-management problem and then hand the key to a KMS.
