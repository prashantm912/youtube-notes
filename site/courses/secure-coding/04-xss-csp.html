Module: XSS and Content Security Policy

Cross-site scripting is not "an alert box pops up". It is attacker-supplied text that the browser's parser decides is code — and once that code runs inside your origin it can do everything the logged-in user can do, silently. This module is about writing the code that never gives the parser that chance, and the browser-level policy that catches the one time you slip.

Knowledge Library → Courses → Secure Coding track → XSS and Content Security Policy

What this module covers

Every XSS bug has the same shape: data crosses into a place where the browser expects code, and nothing along the way converted it back into data. The previous module covered injection into a SQL or shell parser; this one covers injection into the browser's HTML, JavaScript, URL and CSS parsers. The consequence is worse than it looks, because the same-origin policy is a privilege boundary: injected script inherits your origin, so it can read the DOM, call your APIs with the user's session, rewrite the page a user is trusting, and exfiltrate anything it finds — no password needed.

The first half is the mechanics you need in order to prevent it: the three types classified by where the injection happens, sources and sinks as the mental model for DOM XSS, why the correct output encoding depends on context, how Angular's contextual sanitization works and when bypassSecurityTrust* is defensible, and the equivalent controls in server-rendered Java templates. The second half builds a Content Security Policy properly — the strict nonce-based pattern rather than a host allow-list, wired into Spring Security, rolled out in report-only mode — and finishes with Trusted Types, which closes DOM XSS at the sink rather than at the source. If you have already done the Angular Advanced security module, this is the deeper, framework-agnostic treatment of the same ground.

Topics

Reflected, stored and DOM-based XSS: three delivery routes, one bug class

The taxonomy is about where attacker data enters and how it reaches the victim's parser, not about different vulnerabilities. In reflected XSS the payload rides in the request — a query parameter, a form field, a header — and the server echoes it straight back into the response for that same request. It needs a delivery trick (a crafted link, a link in an email or a chat message) because the attacker has to get the victim to make the request, which is also why it is often rated lower than it deserves: a single click is not a high bar.

Stored XSS is the dangerous one. The payload is persisted — a comment, a profile bio, a product review, a support-ticket body, an imported CSV field, even a log line rendered in an admin console — and then served to everyone who views that record. No social engineering is required, the blast radius is every viewer including administrators, and it is wormable: a payload that posts itself into the victim's own profile propagates without further attacker involvement, which is exactly how the Samy worm took MySpace down in under a day. DOM-based XSS is different in kind: the payload may never reach the server at all. Client-side JavaScript reads an attacker-influenced value and writes it into a dangerous API, so the server logs are clean, the WAF sees nothing, and a fragment after # is not even transmitted. That is why DOM XSS survives in applications whose server-side encoding is impeccable.

// Vulnerable (reflected): request data concatenated into the response body
String q = req.getParameter("q");
resp.getWriter().write("<p>No results for " + q + "</p>");   // parser sees markup

// Fixed: convert data back into data for the context it lands in
String safe = Encode.forHtml(q);                                  // OWASP Java Encoder
resp.getWriter().write("<p>No results for " + safe + "</p>");

Sources and sinks: the mental model that makes DOM XSS findable

DOM XSS is best reasoned about as a data flow with two ends. A source is any DOM property an attacker can influence: location.href, location.search, location.hash, document.referrer, document.cookie, window.name, the data of a postMessage event, and anything read back out of localStorage. A sink is any API that turns a string into code or markup: innerHTML, outerHTML, insertAdjacentHTML, document.write, eval, Function, the string form of setTimeout, an href or src assignment that accepts a javascript: scheme, and framework-specific sinks such as jQuery's $(...) when given HTML. A vulnerability exists precisely when a source flows to a sink without a sanitizing step in between.

The defensive move is almost always to change the sink rather than to filter the source. textContent cannot parse markup, so it is safe by construction where innerHTML is not; setAttribute on a non-URL attribute is safe where a raw href assignment is not; JSON.parse replaces eval outright. When you genuinely must render HTML, run it through a well-maintained sanitizer such as DOMPurify rather than a regular expression of your own — filter-evasion is a decades-old cat-and-mouse game and hand-rolled blocklists lose it. Reviewers should grep for the sink list above; that single search finds most DOM XSS in a codebase.

// Vulnerable: source (URL fragment, never sent to the server) flows into an HTML sink
const tab = decodeURIComponent(location.hash.slice(1));
panel.innerHTML = 'Section: ' + tab;          // browser parses the string as markup

// Fixed: change the sink — textContent cannot create elements or handlers
panel.textContent = 'Section: ' + tab;

// If markup really is required, sanitize at the boundary
panel.innerHTML = DOMPurify.sanitize(tab);

Output encoding is the primary defense — and the context decides the encoding

Input validation is useful but it is not the fix: the same string is harmless in one place and executable in another, so the decision can only be made correctly at the moment of output. Encoding means converting characters that carry meaning in the destination grammar into their inert representations, immediately before the value is written into that grammar. Do it late, do it once, and do it per context — double-encoding produces visible mojibake, and encoding at input time makes the stored data wrong for every other consumer.

This is why a single project-wide escapeHtml() helper is a false comfort. HTML body text needs & < > replaced. An attribute value needs the quote characters too, and needs to be quoted in the first place — an unquoted attribute can be escaped with a space alone. A URL context needs a scheme allow-list (reject javascript: and data: before you even get to percent-encoding) because escaping does nothing to a dangerous scheme. A JavaScript context needs JavaScript string escaping and is so error-prone that the correct answer is not to interpolate at all: emit the value as JSON into a data- attribute or a <script type="application/json"> block and read it from script. A CSS context is similarly unsafe to interpolate. And there is one place no encoding saves you: never place untrusted data inside a <script> block, an event-handler attribute, or a stylesheet, because those grammars execute before your escaping is meaningful.

<p>VALUE</p>                   <!-- HTML body: escape & < > -->
<a title="VALUE">               <!-- attribute: also escape " and ', and always quote -->
<a href="VALUE">                <!-- URL: allow-list the scheme, then percent-encode -->
<script>var x = "VALUE";</script>   <!-- JS: do not interpolate; pass JSON via data-* -->
<!-- CSS in a stylesheet or an inline styling attribute: do not interpolate at all -->

Angular: contextual auto-sanitization, and the bypassSecurityTrust discipline

Angular's design decision is that every value bound into a template is untrusted until proven otherwise, and the framework picks its treatment from the binding's security context. Interpolation with {{ }} and property bindings into text always escape, so markup renders as visible characters. Binding into [innerHTML] is the HTML context: Angular does not escape, it sanitizes — parses the fragment, drops <script> elements, on* handler attributes and javascript: URLs, keeps benign markup. Style and URL contexts get their own sanitizers. The resource-URL context (<script src>, <iframe src>, <object data>) is the strict one: a resource URL causes the browser to load and execute code from that address, so there is no partial sanitization that is meaningful, and Angular simply refuses a bound value unless you hand it a SafeResourceUrl.

DomSanitizer.bypassSecurityTrustHtml / Style / Script / Url / ResourceUrl is how you produce those trusted wrappers, and it is a loaded gun pointed at your own users: it does not sanitize, it turns sanitization off. There are legitimate uses — rendering rich text your CMS produces, building an embed URL from a validated video id, injecting an SVG icon you ship yourself — and the discipline that makes them defensible is uniform. Sanitize before you bypass, using a real sanitizer such as DOMPurify, so the bypass is only asserting "this has already been checked". Bypass a value you constructed, never a value a user typed, and construct it from validated components rather than accepting a whole URL. Keep every call in one small pipe or service so code review has a single choke point. Treat any bypassSecurityTrust* call reachable from user input as a finding, not a style preference. Note the limit of all of this: Angular protects the paths it renders, so an ElementRef.nativeElement.innerHTML assignment, a Renderer2 raw-HTML write, or a server-side template that stamps unescaped values into the HTML shell walks straight around it.

<p>{{ comment }}</p>                    <!-- escaped: renders as text, always -->
<div [innerHTML]="commentHtml"></div>  <!-- sanitized: handlers and scripts stripped -->
<iframe [src]="embedUrl"></iframe>     <!-- resource URL: needs a SafeResourceUrl -->

// Wrong: user input handed straight to a bypass — the hole is fully reopened
this.html = this.sanitizer.bypassSecurityTrustHtml(userSuppliedHtml);

// Defensible: sanitize first, bypass a value we constructed, one place in the codebase
const clean = DOMPurify.sanitize(cmsRichText);
this.html = this.sanitizer.bypassSecurityTrustHtml(clean);
this.embed = this.sanitizer.bypassSecurityTrustResourceUrl(EMBED_BASE + validatedId);

Server-rendered Java templates: Thymeleaf, JSP and JSTL

Single-page apps are not the only front end you will ship, and the Java template engines have the same escaped-versus-unescaped split — with the unescaped variant sitting one character away from the safe one. In Thymeleaf, th:text escapes its result and is what you should be writing; th:utext deliberately does not, and every Thymeleaf XSS bug in the wild is a th:utext (or its inlining twin [(...)] versus the safe [[...]]). Grep for utext during review the way you grep for innerHTML in JavaScript, and where you truly need stored markup, run it through the OWASP Java HTML Sanitizer with an explicit element and attribute policy before it is ever written to the template.

JSP is the sharper edge, because the unsafe behaviour is the default rather than an opt-in. A bare ${value} expression in a JSP page writes the value out with no escaping at all, so legacy pages are full of latent reflected XSS. The JSTL <c:out> tag escapes by default (and can be turned off with escapeXml="false" — another review grep). Servlet-level defenses matter too: set the response character encoding explicitly so a browser cannot be talked into re-interpreting your bytes as UTF-7-style alternate encodings, and set Content-Type plus X-Content-Type-Options: nosniff so a JSON or text response containing user data is never sniffed and rendered as HTML. That last one turns a whole family of "file download becomes stored XSS" bugs into non-issues.

<!-- Thymeleaf: escaped, correct by default -->
<p th:text="${comment}"></p>

<!-- Thymeleaf: unescaped — this is where the bug lives -->
<p th:utext="${comment}"></p>

<!-- JSP: a bare EL expression is NOT escaped -->
<p>${comment}</p>

<!-- JSTL: c:out escapes by default; escapeXml="false" undoes it -->
<p><c:out value="${comment}"/></p>

Content Security Policy: the header, the directives, and why script-src 'self' is weak

CSP is a response header that tells the browser which resources this document is allowed to load and execute. The browser enforces it, so it holds even when your application logic has already lost. The directives you will actually configure are script-src (what may execute — the one that matters for XSS), object-src (plugins, which should be 'none'), base-uri (which should be 'none' so an injected <base> tag cannot repoint every relative script URL), frame-ancestors (clickjacking, replacing the old framing header), default-src as the fallback for fetch directives, and connect-src, img-src, style-src and font-src for the rest.

The tempting first policy is a host allow-list: script-src 'self' https://cdn.example.com. Google's large-scale study of deployed policies found this approach is bypassable in the overwhelming majority of real sites, and the reasons are mundane rather than exotic. If any allowed host serves a JSONP endpoint, an attacker names your callback and gets arbitrary script from an approved origin. If any allowed host serves a framework with a client-side template compiler — an older AngularJS bundle is the classic — the attacker injects markup that the framework itself evaluates. If any allowed host lets users upload files, they upload a script. And a CDN allow-list transitively trusts every library that CDN hosts. Add the fact that a real application's allow-list only grows, and the conclusion is that host allow-listing is not a security boundary. Run any candidate policy through Google's CSP Evaluator before you ship it; it names these bypasses explicitly.

# Weak: one JSONP endpoint or one templating library on an allowed host defeats it
Content-Security-Policy: script-src 'self' https://cdn.example.com

# Also useless: 'unsafe-inline' permits exactly the injected inline script you fear
Content-Security-Policy: script-src 'self' 'unsafe-inline'

Strict CSP: nonces, hashes and strict-dynamic, wired into Spring Security

The modern recommendation replaces the allow-list with per-response trust. A nonce is a cryptographically random value generated fresh for every response, placed in the header as 'nonce-...' and stamped as a nonce attribute on each script tag you intend to run. An attacker injecting a script tag cannot guess the value, so their script does not execute. Two rules make or break it: the nonce must come from a CSPRNG with at least 128 bits of entropy, and it must be unique per response — a nonce cached in a static HTML file or reused across requests is worthless. Hashes ('sha256-...') are the alternative for genuinely static inline scripts, which suits fully static hosting where you cannot generate a per-response value.

'strict-dynamic' is what makes this practical. It says: any script that has already been trusted (by nonce or hash) may load further scripts programmatically, and while it is in effect the browser ignores host allow-lists. That is precisely the behaviour a bundled application needs, because your entry bundle loads chunks whose names you cannot enumerate. Pair it with object-src 'none' and base-uri 'none', and keep the legacy fallbacks https: and 'unsafe-inline' at the end of the directive — modern browsers ignore both when 'strict-dynamic' and a nonce are present, and older ones fall back to something rather than nothing. Note what a strict CSP does not give you: it does not stop an attacker rewriting page content, planting a fake login form, or exfiltrating data through an allowed channel. It stops script execution, which is most of the damage, not all of it.

// Per-response nonce: CSPRNG, 128 bits, never cached, never reused
byte[] raw = new byte[16];
secureRandom.nextBytes(raw);
String nonce = Base64.getUrlEncoder().withoutPadding().encodeToString(raw);
request.setAttribute("cspNonce", nonce);        // template reads it: nonce="${cspNonce}"

response.setHeader("Content-Security-Policy",
      "script-src 'nonce-" + nonce + "' 'strict-dynamic' https: 'unsafe-inline'; "
    + "object-src 'none'; base-uri 'none'; frame-ancestors 'none'");

// Static parts of the policy can equally come from the Spring Security DSL:
// http.headers(h -> h.contentSecurityPolicy(csp -> csp.policyDirectives("...")));

Rolling CSP out on a single-page app without breaking it

Ship a policy blind and you will break production. The safe sequence is: send it as Content-Security-Policy-Report-Only first, which makes the browser evaluate and report violations while enforcing nothing; collect reports for long enough to cover your real traffic mix; fix the genuine violations; only then switch the header name to the enforcing one. Reporting has two generations — the older report-uri directive posting to your endpoint, and the newer Reporting-Endpoints header plus report-to directive — and because browser support is uneven you generally emit both for a while. Budget for noise: browser extensions and injected ISP scripts generate violation reports you cannot act on, so filter before you alert.

The SPA-specific friction is predictable. Inline styles are everywhere — component libraries, animation code and Angular's own style handling produce them — so style-src usually needs a nonce, a hash set, or (pragmatically, and much less dangerous than its script counterpart) 'unsafe-inline' for styles only. Development builds want 'unsafe-eval' because source maps, hot module replacement and some dev-mode compilers evaluate strings; the correct answer is a different, looser policy for the dev server and the strict one for production, never 'unsafe-eval' in the shipped header. Your bundler must be told to stamp the nonce onto the tags it generates — Angular reads it from the ngCspNonce attribute on the root element or from the CSP_NONCE injection token — and any HTML shell that carries a nonce must not be cached at a CDN, since a cached nonce is a shared nonce.

# Phase one: observe only, break nothing
Content-Security-Policy-Report-Only:
  script-src 'nonce-RANDOM' 'strict-dynamic' https: 'unsafe-inline';
  style-src 'self' 'unsafe-inline';
  object-src 'none'; base-uri 'none';
  report-uri /csp-violations;
  report-to csp-endpoint

Reporting-Endpoints: csp-endpoint="https://example.com/csp-violations"

Trusted Types: closing DOM XSS at the sink

Everything above asks developers to remember something at every call site. Trusted Types inverts that. Sending require-trusted-types-for 'script' in the CSP header makes the browser refuse plain strings at the dangerous DOM sinks — innerHTML, outerHTML, insertAdjacentHTML, document.write, script src, eval and the rest. Those sinks now accept only TrustedHTML, TrustedScript or TrustedScriptURL objects, which can be produced only by a policy you registered with trustedTypes.createPolicy(). The security property is structural rather than behavioural: instead of auditing thousands of assignments, you audit the handful of policies, because nothing else in the application can create a value the sinks will accept. The trusted-types directive additionally names which policies may exist, so a third-party script cannot quietly register a permissive one.

Deployment follows the same report-only path as the rest of CSP, and the reports are unusually actionable — each one is a real source-to-sink flow in your code. Angular supports Trusted Types and its own rendering paths are already compliant, so a well-behaved Angular application typically switches it on with little churn; the violations you do see are precisely the raw-DOM escape hatches you wanted to find. Two honest caveats: browser support is Chromium-led rather than universal, so treat it as defense in depth on top of encoding, not a replacement; and a policy whose createHTML simply returns its input is a policy that protects nothing. Point it at a real sanitizer.

// With require-trusted-types-for 'script' this now throws instead of injecting
el.innerHTML = userHtml;                       // TypeError: requires TrustedHTML

// One audited choke point for the whole application
const policy = trustedTypes.createPolicy('app-html', {
  createHTML: (input) => DOMPurify.sanitize(input)    // a real sanitizer, not identity
});
el.innerHTML = policy.createHTML(userHtml);    // allowed, and provably sanitized

Limiting the blast radius, and the honest verdict on CSP

Assume for a moment that one XSS gets through. What the attacker can reach is a design decision you made earlier. A session cookie marked HttpOnly is invisible to document.cookie, so the classic one-line session theft stops working; add Secure so it never crosses plaintext, and SameSite to blunt the forgery angle covered in a later module. Tokens kept in localStorage have the opposite property — they are readable by any script in the origin, which is the strongest practical argument for cookie-based session handling in a browser app. Round it out by binding sessions to sensible lifetimes, re-authenticating for high-value actions so a hijacked session cannot change an email address or a payout account unchallenged, and keeping X-Content-Type-Options: nosniff on every response.

The verdict to carry into an interview and into a design review: CSP is a second line of defense, not a substitute for encoding. It is genuinely valuable — it converts many injections from full compromise into a blocked-script console message, and its violation reports tell you about bugs you did not know you had. But it does not stop an attacker who can inject markup from defacing the page or phishing through it, it does nothing about server-side template injection, a badly built policy is theatre, and every serious deployment still rests on getting output encoding right at every sink. Build the encoding correctly, then add CSP and Trusted Types so that the day you get one call site wrong is a bad day rather than a breach.

Interview questions

XSS is the security question Indian product and service companies ask most often, and it scales cleanly from a screening round to a senior design discussion — the three types get asked almost every time, and the follow-ups about Angular and CSP nonces separate people who have shipped a policy from people who have read about one:

Beginner What is XSS, and why is it serious when the page is "just" a comment box?

Attacker-supplied data ends up in a place the browser parses as code, so the attacker's script runs inside your origin. Because the same-origin policy grants that script everything the page has, it can read the DOM, call your APIs with the user's session, steal readable tokens, rewrite the interface the user trusts, and exfiltrate results — all without a password. A comment box that renders unescaped is a comment box that runs code for every viewer.

Beginner Name the three types of XSS and how they differ.

Reflected: the payload is in the request and the server echoes it into that same response, so the attacker needs the victim to follow a crafted link. Stored: the payload is persisted and served to everyone who views the record — no social engineering, largest blast radius, and potentially wormable. DOM-based: the payload never has to reach the server; client-side JavaScript reads an attacker-influenced source and writes it to a dangerous sink, so server logs and a WAF see nothing.

Beginner Why is stored XSS usually rated more severe than reflected?

Delivery is free and automatic. Reflected XSS needs each victim to click the attacker's link; stored XSS fires for every user who loads the affected page, including administrators viewing it in a privileged console. It also persists until someone cleans the data, and a payload that writes itself into the viewer's own content becomes self-propagating.

Beginner What are sources and sinks in DOM XSS?

A source is a DOM property an attacker can influence — location.search, location.hash, document.referrer, window.name, postMessage data, values read back from storage. A sink is an API that turns a string into markup or code — innerHTML, document.write, insertAdjacentHTML, eval, a javascript: URL assignment. A bug exists when a source reaches a sink with no sanitization in between; the usual fix is to change the sink (textContent, JSON.parse) rather than filter the source.

Intermediate Why is a single project-wide escapeHtml() function not enough?

Because the correct encoding depends on the destination grammar. HTML body text needs the angle brackets and ampersand; an attribute value additionally needs the quote characters and needs to be quoted at all; a URL needs a scheme allow-list before percent-encoding, since escaping does nothing to javascript:; a JavaScript or CSS context needs different rules again and is best not interpolated at all — pass data as JSON via a data- attribute. One helper applied everywhere is under-escaping in some contexts and mangling output in others.

Intermediate Should you encode on input or on output, and why?

On output, immediately before the value enters a specific context. Encoding at input corrupts the stored data for every other consumer (an API, a report, a mobile client) and is still wrong, because at input time you do not yet know which grammar the value will land in. Validate on input — type, length, format, allow-list — and encode on output. Doing both at input produces double-encoded text and a false sense of safety.

Intermediate Is Angular immune to XSS?

No — it is safe by default, which is different. Interpolation escapes, [innerHTML] is sanitized, and resource-URL bindings are refused outright, so idiomatic template code is safe. You lose that the moment you opt out: any bypassSecurityTrust* call on user-influenced data, a direct ElementRef.nativeElement.innerHTML write, a Renderer2 raw-HTML write, a server-rendered shell that stamps unescaped values into index.html, or a dependency with a known XSS advisory. Angular protects the paths Angular renders; it cannot protect the ones you route around.

Intermediate What are Angular's security contexts, and why does binding to a script src behave differently from innerHTML?

HTML, style, URL and resource URL. Angular chooses its treatment by context because the same string is dangerous in different ways in each. [innerHTML] is the HTML context, so Angular can parse the fragment and strip scripts, handlers and javascript: URLs while keeping benign markup. A resource URL (script/iframe/object source) causes the browser to fetch and execute whatever lives at that address, so there is no meaningful partial cleaning — Angular refuses the binding unless you supply an explicitly trusted SafeResourceUrl.

Intermediate In Thymeleaf and JSP, where does the XSS bug usually live?

In the unescaped variant. Thymeleaf's th:text escapes; th:utext (and the [(...)] inlining form) does not, and that is where Thymeleaf XSS comes from. In JSP the default is the unsafe one: a bare ${value} expression is written out unescaped, while JSTL's <c:out> escapes unless you pass escapeXml="false". Review greps: utext, bare EL in JSP, and escapeXml="false". If stored HTML is genuinely required, clean it with the OWASP Java HTML Sanitizer under an explicit policy.

Intermediate How does a CSP nonce work, end to end?

For each response the server generates a fresh random value from a CSPRNG (at least 128 bits), puts it in the header as script-src 'nonce-VALUE', and stamps the same value as a nonce attribute on every script tag it intends to run. The browser executes only scripts whose nonce matches. An injected script tag cannot carry the right value because the attacker never sees it. It fails if the nonce is predictable, if it is reused across responses, or if the HTML carrying it is cached — a cached nonce is a published nonce.

Pro Why is script-src 'self' plus a CDN allow-list considered weak?

Because allow-listing a host trusts everything that host can serve. A JSONP endpoint on an allowed origin returns attacker-chosen script through an approved URL. A client-side templating library on an allowed origin (an old AngularJS bundle is the standard example) evaluates injected markup for you. A host that accepts user uploads serves the attacker's file. A general-purpose CDN transitively trusts every library it hosts. Google's measurement study found the large majority of deployed allow-list policies were bypassable on these grounds, which is why the recommendation moved to nonces or hashes with 'strict-dynamic'.

Pro What does 'strict-dynamic' do, and what would you pair it with?

It propagates trust: a script already trusted via nonce or hash may load further scripts programmatically, and while it is active the browser ignores host allow-lists. That makes bundled applications workable, since chunk URLs are not enumerable in advance. Pair it with a per-response nonce, object-src 'none', base-uri 'none' (otherwise an injected <base> repoints every relative script URL), frame-ancestors 'none', and the legacy fallbacks https: and 'unsafe-inline' at the end, which modern browsers ignore and older ones use as a weaker net.

Pro How would you roll a strict CSP onto an existing single-page app in production?

Start with Content-Security-Policy-Report-Only so nothing breaks, wire up report-uri plus Reporting-Endpoints and report-to, and collect over a full traffic cycle. Filter extension noise out of the reports, fix genuine violations, then flip to the enforcing header. Expect specific friction: inline styles from component libraries usually force a style-src nonce, hash set or (for styles only) 'unsafe-inline'; dev builds want 'unsafe-eval', so keep a separate looser dev policy and never ship it; the bundler and framework must stamp the nonce (Angular via ngCspNonce or the CSP_NONCE token); and the HTML shell carrying a nonce must not be CDN-cached.

Pro What are Trusted Types, and why are they a stronger guarantee than sanitizing at each call site?

require-trusted-types-for 'script' makes the browser reject plain strings at dangerous DOM sinks; those sinks accept only TrustedHTML, TrustedScript or TrustedScriptURL objects, and only a policy registered via trustedTypes.createPolicy() can mint them. The guarantee is structural: you audit a handful of policies instead of thousands of assignments, and the trusted-types directive can restrict which policy names may exist. Caveats: support is Chromium-led so it is defense in depth, not a replacement for encoding, and a policy whose createHTML returns its input unchanged protects nothing.

Pro If XSS still happens, what limits the damage — and is CSP a substitute for encoding?

Damage limiting: HttpOnly on session cookies so script cannot read them, Secure and SameSite alongside, cookie-based sessions rather than tokens in localStorage (which any script can read), short session lifetimes, step-up re-authentication for high-value actions, and nosniff so a user-controlled response is never rendered as HTML. And no, CSP is not a substitute: it is a second line of defense. It blocks script execution but not defacement, phishing forms rendered into your page, or server-side template injection, and a badly built policy is theatre. Get output encoding right first; CSP and Trusted Types are what make one mistake survivable.
