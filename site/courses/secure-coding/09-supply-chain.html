Module: Supply Chain Security

You reviewed every line your team wrote. Nobody reviewed the nine hundred packages your build downloaded. This module is about the code you ship but did not write, and about the fact that one compromised library reaches every one of its users at once.

Knowledge Library → Courses → Secure Coding track → Supply Chain Security

What this module covers

Count the dependencies in a typical Spring Boot plus Angular application. The pom.xml might declare thirty artifacts and the package.json another fifty; the resolved graph is routinely several hundred JARs and well over a thousand npm packages. Every one of them executes inside your process, with your credentials, against your database. Your direct dependency count is not your attack surface — it is a small, comfortable fraction of it.

That asymmetry is what makes the supply chain attractive to an attacker. Compromising your application gets them one application; compromising a library that fifty thousand applications depend on gets them all fifty thousand, and they arrive through your own trusted build pipeline rather than through your firewall. This module covers the defensive half of that story in two parts: managing what you depend on — scanning for known vulnerabilities, prioritising them honestly, tracing transitive versions, locking builds so they are reproducible, and resisting typosquatting and dependency confusion — and then hardening the pipeline that turns those dependencies into a running artifact: container scanning, SBOM, provenance and signing, and the CI gates that decide what is allowed to ship.

Topics

Most of the code you ship is code you did not write

Run mvn dependency:tree on a real service and the output is usually a shock: a handful of declared starters expand into hundreds of artifacts, most of which you have never heard of, several of which are the third-order dependency of a logging shim. The npm side is worse by an order of magnitude. Those packages are not sandboxed. A JAR on the classpath can read your environment, open sockets and load classes; an npm package can execute an install script on the machine that ran npm install, which on a build agent means it runs with the pipeline's credentials.

Two incidents make the blast radius concrete without needing any attack detail. Log4Shell (CVE-2021-44228) was a remote code execution flaw in Log4j, a library almost nobody chose deliberately — it arrived transitively through frameworks — and in December 2021 an enormous share of the Java-speaking internet discovered simultaneously that it was affected and could not quickly say where. xz-utils (CVE-2024-3094) was different and more unsettling: a patient social-engineering campaign in which a contributor spent years earning maintainer trust on a compression library before landing a backdoor into release tarballs. The first is a bug; the second is a human process failure. Your defences have to address both, and the practical lesson from Log4Shell is that the expensive part was not patching — it was inventory.

CVE, CVSS, EPSS: scoring tells you where to start, not what to do

A CVE is an identifier — a stable name for one publicly disclosed flaw, so that your scanner, the vendor advisory and your ticket all refer to the same thing. CVSS is a severity score attached to it, computed from characteristics like attack vector, required privileges and impact on confidentiality, integrity and availability. The number is useful and it is also the single most misused figure in application security, because CVSS base scores describe the vulnerability's worst plausible case in the abstract. They know nothing about your deployment. A 9.8 in a parser you never invoke, inside a library loaded only by a CLI tool you do not ship, is not a 9.8 to you.

Two things narrow the list to what matters. EPSS, published by FIRST, estimates the probability that a given CVE will be exploited in the wild in the next thirty days, drawn from observed exploitation data rather than theory — and the distribution is brutally skewed, with a tiny fraction of CVEs accounting for most real-world exploitation. CISA's Known Exploited Vulnerabilities catalogue is the blunt version of the same idea: these are being exploited now, patch them regardless of score. The third input is reachability analysis, which several commercial scanners now perform: static call-graph analysis that asks whether any path in your code actually reaches the vulnerable function. The mature policy combines all of it — high CVSS and high EPSS and reachable and internet-facing is an emergency; high CVSS alone is a ticket. Say exactly that in an interview and you will sound like someone who has run a backlog rather than read a dashboard.

Scanning your dependencies: Dependency-Check, Dependabot, Snyk

Software composition analysis works the same way everywhere: enumerate the resolved dependency graph, match each component against a vulnerability database, report. OWASP Dependency-Check is the free, self-hosted baseline for the JVM — Maven and Gradle plugins, plus a CLI — matching artifacts to CPE identifiers and CVE records from the National Vulnerability Database. Its failBuildOnCVSS property is the crude but effective build gate. Its two operational quirks are worth knowing before an interview: it needs an NVD API key and a warmed local data cache or the first run is painfully slow, and CPE matching produces false positives you will need a suppression file for.

Dependabot is the zero-setup option on GitHub: alerts tell you a vulnerable version is in the graph, and version updates open pull requests to bump it. Snyk and equivalents add a curated database that is often ahead of NVD, reachability analysis, and fix advice that accounts for transitive paths. Whichever you pick, the design decisions are the same: scan on every pull request and on a schedule (a dependency you have not touched becomes vulnerable while you sleep — new CVEs arrive against code you already shipped), maintain a reviewed suppression file with an expiry date on every entry rather than a permanent silence, and treat the scanner as an input to triage rather than an oracle.

<plugin>
  <groupId>org.owasp</groupId>
  <artifactId>dependency-check-maven</artifactId>
  <configuration>
    <nvdApiKey>${env.NVD_API_KEY}</nvdApiKey>
    <failBuildOnCVSS>7</failBuildOnCVSS>      <!-- fail on high and critical -->
    <suppressionFiles><suppressionFile>owasp-suppressions.xml</suppressionFile></suppressionFiles>
  </configuration>
</plugin>

Transitive risk: where did that version come from, and how do you move it?

The scanner names a vulnerable artifact you never declared. The first question is always who pulled it in. On Maven, mvn dependency:tree -Dincludes=groupId:artifactId prints the paths that reach it, and -Dverbose additionally shows the versions that were considered and rejected. On Gradle, gradle dependencyInsight --dependency <name> --configuration runtimeClasspath explains not just the path but the reason the chosen version won. Learn both commands properly; "how would you find where this transitive dependency comes from" is a stock interview question and the answer is a command, not a paragraph.

Then understand the resolution rules, because they differ and the difference bites. Maven uses nearest-wins mediation: the version at the shallowest depth in the tree is selected, with declaration order breaking ties at equal depth — so a transitive version can quietly beat one you consider newer. Gradle instead selects the highest requested version by default. To force an outcome, Maven's idiomatic tool is <dependencyManagement>, which pins a version for the whole reactor without adding a dependency (and which Spring Boot's parent POM already uses extensively); Gradle offers constraints, and a stricter strictly/force when a constraint is not enough. Exclusions exist too, but excluding a dependency that something actually calls trades a CVE for a NoClassDefFoundError at runtime.

The genuinely hard case is the maintenance one: a direct dependency pins a vulnerable transitive version, and overriding it may break that library's assumptions. The order of preference is: upgrade the direct dependency to a release that already picks up the fix (correct, supported, and someone else tested the combination); if none exists, override the transitive version yourself and back it with integration tests, accepting that you now own an unsupported combination; if the API changed incompatibly, open an issue or a pull request upstream and, meanwhile, assess exploitability honestly — reachability, exposure, compensating controls — and record the risk acceptance with an owner and a review date rather than letting it rot silently in a suppression file.

# Maven - who pulls in the vulnerable artifact, and which versions lost?
mvn dependency:tree -Dincludes=com.fasterxml.jackson.core:jackson-databind -Dverbose

# Gradle - the same question, with the reason the winning version was chosen
gradle dependencyInsight --dependency jackson-databind --configuration runtimeClasspath
<!-- Maven: force a fixed version everywhere, without declaring a new dependency -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.fasterxml.jackson.core</groupId>
      <artifactId>jackson-databind</artifactId>
      <version>${jackson.patched.version}</version>
    </dependency>
  </dependencies>
</dependencyManagement>

Lockfiles and reproducible builds

A build that can resolve different bytes tomorrow than it did today is not auditable, and a scan of yesterday's resolution says nothing about tomorrow's artifact. That is what a lockfile fixes. package-lock.json records the exact resolved version and integrity hash of every package in the tree, direct and transitive. The critical discipline is which command you run: npm install is allowed to update the lockfile to satisfy the ranges in package.json, whereas npm ci installs strictly from the lockfile, fails if the two files disagree, and wipes node_modules first. CI should always run npm ci. A pipeline that runs npm install is a pipeline that can silently ship a version nobody reviewed.

The JVM story is looser. A Maven POM with a hard version coordinate is already close to deterministic for that module, but ranges, LATEST/RELEASE, and snapshot dependencies destroy it — a version range in a build file means your build is not reproducible, full stop, and someone else's release can change what you ship without a commit on your side. Gradle offers explicit dependency locking, which writes lockfiles per configuration and fails the build when resolution drifts. Beyond version pinning there is the wider reproducible builds goal: the same source producing byte-identical artifacts, which requires stripping timestamps and ordering nondeterminism out of the archive. Maven supports this through the project.build.outputTimestamp property and the reproducible-build guidance, and the payoff is verifiability — if the published JAR is bit-for-bit what your source produces, a tampered release is detectable rather than a matter of trust.

# CI: install exactly what the lockfile says, or fail
npm ci                     # never `npm install` on a build agent

# Gradle: write and then enforce lock state
gradle dependencies --write-locks
gradle build --update-locks=none

Typosquatting, dependency confusion and the human failure modes

Typosquatting is the cheapest attack in the catalogue: publish a package whose name is one keystroke or one hyphen away from something popular, and wait for installs. Defences are unglamorous — copy dependency names from the official documentation rather than typing them, review every new dependency in code review the way you would review new code, prefer packages with real maintenance signals, and let a lockfile plus npm ci ensure that only reviewed names ever get installed on a build agent.

Dependency confusion is subtler and has hit very large companies. Internal packages often carry unscoped names like acme-billing-utils, and package managers configured with both a private registry and the public one may resolve to whichever offers the "best" match — commonly the highest version number. An attacker who learns your internal package name (from a leaked package.json, a stack trace, a public build log) publishes that name on the public registry with an absurdly high version, and your build prefers it. The defences are structural rather than reactive: use scoped package names (@acme/billing-utils) so the namespace itself is owned, map that scope explicitly to your private registry in .npmrc, run a private registry with a deliberate upstream policy so internal names are never resolved from a public source, and — as a belt-and-braces move — defensively register your organisation's scope publicly. The equivalent JVM discipline is to keep internal group IDs on a repository manager that does not fall through to Maven Central for those coordinates.

Finally the human layer, where tooling helps least. Protestware is a maintainer deliberately shipping disruptive behaviour in their own package for political reasons — rare, but a reminder that "the maintainer is on your side" is an assumption, not a guarantee. Maintainer-account compromise is the commoner and more dangerous version: a stolen npm token or a phished account publishes a malicious patch release of a legitimate library, and it flows straight into every build using a caret range. That is precisely why pinned lockfiles, integrity hashes, a delay before adopting brand-new patch versions, and signed releases are worth the friction. The xz-utils case adds the slow version of the same problem — a trusted maintainer who was never trustworthy — and the honest defence there is project health signals such as OpenSSF Scorecard, multiple maintainers, and preferring dependencies you could realistically fork.

Container image scanning: most of your CVEs come from the base image

Scan a freshly built application image and the finding count is usually dominated by things you never wrote or chose: OpenSSL, glibc, curl, coreutils, a shell, a package manager. They came with the base image. Trivy, Grype and Docker Scout all read the image layer by layer, enumerate OS packages from the distribution database and language packages from lockfiles and JARs, and match everything against vulnerability feeds. Trivy is the common default in CI because it is a single binary, scans images, filesystems, IaC and repositories, and emits SARIF or SBOM formats directly.

The consequence is the point worth carrying into an interview: choosing a base image is a security decision, not a packaging preference. A full distribution image ships hundreds of packages your application never calls, and every one of them is CVE surface you must triage forever. A slim variant cuts that; an Alpine variant cuts it further (with the musl caveat for JVM workloads); a distroless image ships the runtime and your application and essentially nothing else — no shell, no package manager, no busybox — which shrinks both the vulnerability count and what an attacker can do after landing a foothold. Pair that with multi-stage builds so build tooling never reaches the runtime layer, pin base images by digest rather than by a mutable tag like latest, and rebuild regularly: an image built six months ago accumulates CVEs even if your code has not changed by a single line.

# Fail CI only on fixable high/critical findings in the image
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 acme/orders:1.4.2

# Same scan, emitting an SBOM for the artifact store
trivy image --format cyclonedx --output orders-sbom.json acme/orders:1.4.2

SBOM: the inventory you will want before the next Log4Shell

A Software Bill of Materials is a machine-readable list of every component in a build: name, version, package URL, licence, hashes, and the dependency relationships between them. Two formats matter. CycloneDX came out of OWASP and is security-first — compact, with first-class support for vulnerabilities, VEX statements, services and attestations. SPDX came out of the Linux Foundation with a licence-compliance heritage and is now an ISO standard; it is the format procurement and legal teams usually ask for. Both describe the same underlying facts; generate whichever your consumers want, and note that most tools convert between them.

Generate the SBOM at build time, from the resolved graph, and publish it as a release artifact alongside the binary. Generating it later by re-scanning a running container is guesswork; generating it during the build is exact. On the JVM the CycloneDX Maven and Gradle plugins attach one to the build; container scanners emit one for an image; GitHub can export a dependency graph as SPDX.

The real value is not the file, it is the query. When the next Log4Shell lands on a Tuesday evening, the only question your leadership will ask is "which of our services contains this library, and at what version?" A team with SBOMs stored per release answers in minutes with a database query. A team without them spends three days grepping repositories, and still cannot be sure about the services nobody has rebuilt this year. Store SBOMs centrally and make them searchable — that is the difference between an inventory and a compliance checkbox.

# Attach a CycloneDX SBOM to a Maven build (goal binds to the package phase)
mvn org.cyclonedx:cyclonedx-maven-plugin:makeAggregateBom

Provenance, SLSA levels and signing what you ship

An SBOM says what is in an artifact. Provenance says where the artifact came from: which source commit, which builder, which build definition, with what inputs. Without it, "this image is our release" rests entirely on the fact that it is sitting in your registry under the expected tag — which is exactly the assumption an attacker with registry write access is counting on.

SLSA (Supply-chain Levels for Software Artifacts) turns that into a ladder you can actually climb. In the current specification, Build Level 1 means provenance exists and is published; Level 2 means it is signed and produced by a hosted build platform, so it cannot be forged from a developer laptop; Level 3 means the build platform additionally provides strong protection against tampering with the build itself — isolated, ephemeral builds with non-falsifiable provenance. The useful framing in an interview is that SLSA describes properties of the build process, not of the code; it makes "our releases are built only by our pipeline from our reviewed source" a verifiable claim instead of a policy statement.

Sigstore is what made signing practical, because the historic obstacle was key management — long-lived signing keys that must be stored, rotated and never leaked. Sigstore's keyless flow issues a short-lived certificate bound to an OIDC identity (your CI workflow's identity, for example), signs with it, records the signature in the public Rekor transparency log, and discards the key. cosign sign and cosign verify are the everyday commands. The part teams skip, and the part that makes all of it worthwhile, is verification at deploy time: an admission controller in the cluster that refuses any image without a valid signature from your expected identity. Signing without enforced verification produces a signature nobody checks — reassuring and useless.

# Keyless sign in CI (identity comes from the workflow's OIDC token)
cosign sign --yes ghcr.io/acme/orders@sha256:9f2c...

# Verify at deploy: only images built by our workflow are admitted
cosign verify ghcr.io/acme/orders@sha256:9f2c... \
  --certificate-identity-regexp '^https://github.com/acme/orders/.github/workflows/release.yml@' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

CI security gates, secret scanning and least-privilege pipelines

Every control above needs a decision point: fail the build, or warn. The pragmatic policy that survives contact with a real backlog is block on new findings, warn on the existing ones. A team that switches on a scanner and immediately fails the build on a two-hundred-finding legacy backlog will have the gate disabled within a week — and the gate that got disabled protects nothing. So gate hard on newly introduced critical and high findings that have a fix available, gate hard on anything in the CISA KEV catalogue, gate hard on secrets, and drive the historic backlog down on a schedule with named owners. Any exception must be time-boxed and re-reviewed, never a permanent suppression.

Secret scanning deserves its own gate because a leaked credential needs no exploit at all. Scanning history finds what is already committed; push protection is the control that matters more, because it blocks the credential at the moment of the push, before it ever reaches a remote where it must be treated as compromised. Remember the rule that catches people out: rewriting history does not un-leak a secret — anything pushed must be rotated, not merely deleted.

Then harden the pipeline itself, because CI is a machine with production credentials that executes third-party code on demand. Pin third-party actions to a full commit SHA rather than a mutable tag: @v4 is a pointer the action's owner can repoint at any time, and a compromised maintainer repointing a popular tag reaches every workflow that uses it on the next run. Give each job the minimum permissions block it needs rather than inheriting a broad default token. Prefer short-lived OIDC credentials over long-lived cloud keys stored as repository secrets — the pipeline exchanges a workflow-scoped identity token for temporary credentials, so there is no static key to steal, and the trust policy on the cloud side can be scoped to a specific repository, branch and environment. And treat pull requests from forks as untrusted input: they must not be able to read secrets or run privileged workflows.

permissions:                       # least privilege, per job
  contents: read
  id-token: write                  # only what OIDC needs

steps:
  # Pin to an immutable commit SHA, not a mutable tag; the comment records the version
  - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683   # v4.2.2

The operational verdict: cadence beats perfect scanning

Here is the uncomfortable conclusion of everything above. Teams invest heavily in choosing the perfect scanner and comparatively nothing in the boring habit that actually reduces risk: upgrading regularly. A team on a weekly patch cadence is, on the day a new CVE drops, usually one small version bump away from safe. A team that upgrades once a year faces a major-version migration under incident pressure, with breaking API changes, at the worst possible moment. The scanner tells you what is wrong; only cadence lets you act on it quickly. Automate the churn — Dependabot or Renovate opening grouped, scheduled pull requests — and make a decent test suite the thing that gives you the confidence to merge them.

The second verdict concerns dependencies nobody is maintaining. An unmaintained dependency is a vulnerability with a delayed fuse: it has no known CVE today only because nobody is looking, and when a flaw is finally found there will be no patch, so your options collapse to forking it or ripping it out under pressure. Evaluate maintenance before you adopt — recent releases, more than one maintainer, responsive issue tracker, a security policy — and re-evaluate periodically; OpenSSF Scorecard automates exactly those checks. Weigh the cost of a dependency honestly too: pulling in a large library for one utility function buys you its entire transitive graph, forever. The cheapest supply chain vulnerability to fix is the dependency you never added.

Interview questions

Supply chain questions have moved from "nice to know" to standard in Indian product-company and services interviews, largely because clients now ask for SBOMs contractually — expect the transitive-CVE question in almost every senior round:

Beginner What is a software supply chain attack, and why is it attractive to an attacker?

An attack that compromises something you depend on — a library, a base image, a build tool, a CI action, a registry — rather than your application directly. It is attractive because of leverage: compromising one popular library reaches every downstream consumer at once, and the malicious code arrives through your own trusted build pipeline rather than across your firewall, so perimeter controls never see it.

Beginner What is the difference between a direct and a transitive dependency, and why does the distinction matter?

A direct dependency is one you declared in your POM or package.json; a transitive dependency is one pulled in by a direct dependency, at any depth. It matters because the transitive set is usually an order of magnitude larger and nobody chose it. Log4j reached most affected applications transitively — teams did not know they had it. Your real attack surface is the resolved graph, not the declared list.

Beginner What is CVSS, and is a critical CVSS score always a critical risk to you?

CVSS is a standard severity score derived from a vulnerability's characteristics — attack vector, required privileges, impact. It is a starting point, not a verdict, because the base score describes the flaw in the abstract and knows nothing about your deployment. A critical CVE in a code path you never call, in a component that is not network reachable, is a low practical risk. Add EPSS (probability of exploitation in the wild), the CISA KEV catalogue, reachability and exposure before you decide.

Beginner What is the difference between npm install and npm ci, and which belongs in CI?

npm install resolves against the ranges in package.json and may update the lockfile; npm ci installs strictly from package-lock.json, deletes node_modules first, and fails if the lockfile and manifest disagree. CI must use npm ci — it makes the build deterministic and guarantees you ship the exact versions that were reviewed and scanned. A pipeline running npm install can silently ship a version nobody looked at.

Intermediate A scanner reports a critical CVE in a transitive dependency. Walk me through how you handle it.

First locate it: mvn dependency:tree -Dincludes=group:artifact -Dverbose or gradle dependencyInsight --dependency name to find which direct dependency pulls it in and which version won. Second, assess: is the vulnerable code reachable from our paths, is the component exposed, what do EPSS and KEV say — that decides emergency versus ticket. Third, fix in order of preference: upgrade the direct dependency to a release that already picks up the patched version; failing that, force the transitive version through <dependencyManagement> or a Gradle constraint and back it with integration tests; failing that, raise it upstream and record a time-boxed, owned risk acceptance. Last resort is exclusion, which risks a NoClassDefFoundError if the class is actually used. Then add a regression test or a scan gate so it cannot silently return.

Intermediate How does Maven decide which version wins when two paths request different versions? How does Gradle differ?

Maven uses nearest-wins mediation: the version at the shallowest depth in the dependency tree is selected, and at equal depth the first declaration wins. Gradle by default selects the highest requested version. The practical consequence is that on Maven a shallow transitive path can beat a newer version you expected, so you pin explicitly with <dependencyManagement>; on Gradle you express intent with constraints, or strictly when a constraint is not binding enough.

Intermediate What is a dependency confusion attack and how do you defend against it?

Internal packages often have unscoped names. If the build resolves from both a private registry and a public one, an attacker who learns an internal name can publish it publicly with a very high version number, and the resolver prefers the public package — malicious code executes in your build. Defences are structural: use scoped names (@acme/lib) so the namespace is owned, map that scope explicitly to the private registry in .npmrc, run a private registry whose upstream policy never resolves internal names from a public source, defensively register your scope publicly, and use lockfiles with integrity hashes so only reviewed artifacts install. Same discipline on the JVM for internal group IDs.

Intermediate What is an SBOM, and what is its actual operational value?

A machine-readable inventory of every component in a build — name, version, package URL, hashes, licence and dependency relationships — in CycloneDX (OWASP, security-oriented) or SPDX (Linux Foundation, ISO, compliance-oriented) format. Its value is answering one question fast: "which of our services contains this library, at what version?" With SBOMs generated at build time and stored per release, the next Log4Shell is a database query answered in minutes. Without them it is days of grepping repositories with no certainty about services nobody has rebuilt. Generate at build time from the resolved graph; generating later by re-scanning is guesswork.

Intermediate Why do most CVEs in a container image come from the base image, and what do you do about it?

Because a general-purpose base ships an entire userland — OpenSSL, glibc, curl, a shell, a package manager — none of which your application chose, and all of which is CVE surface. Choosing a base is therefore a security decision: prefer slim or distroless images that contain the runtime and your application and little else, which cuts both the finding count and post-exploitation capability since there is no shell to use. Also use multi-stage builds so build tooling never reaches the runtime layer, pin the base by digest rather than a mutable tag, and rebuild on a schedule — an old image accumulates CVEs even when your code has not changed.

Intermediate Where in the pipeline do you fail the build versus warn, and why?

Fail hard on newly introduced critical and high findings that have a fix available, on anything listed in the CISA KEV catalogue, and on detected secrets. Warn and track for the pre-existing backlog. The reason is behavioural: switch on a gate that fails a two-hundred-finding legacy backlog and the team disables the gate, so it protects nothing. Blocking the delta keeps the codebase from getting worse while the backlog is burned down on a schedule with named owners and time-boxed exceptions rather than permanent suppressions.

Pro Why pin GitHub Actions to a commit SHA instead of a version tag, and what else hardens a pipeline?

A tag like @v4 is a mutable pointer the action owner can move at any time; if that account is compromised, repointing the tag executes attacker code inside every workflow using it on the next run — with your pipeline's credentials. A full commit SHA is immutable, so the code you reviewed is the code that runs (keep the version in a trailing comment, and let Dependabot bump the pin). Beyond pinning: a minimal per-job permissions block instead of a broad default token, OIDC-issued short-lived cloud credentials instead of long-lived keys in repository secrets, no secret access for fork pull requests, isolated ephemeral runners, and never interpolating untrusted PR content into a shell step.

Pro What do SLSA levels describe, and how do signing and verification fit in?

SLSA describes properties of the build process, not of the code. Build Level 1 means provenance is generated and published; Level 2 adds a signed provenance produced by a hosted build platform, so it cannot be forged locally; Level 3 requires a build platform with strong tamper resistance — isolated, ephemeral builds with non-falsifiable provenance. Sigstore makes the signing practical by removing key management: a short-lived certificate bound to your CI workflow's OIDC identity, signature recorded in the Rekor transparency log, key discarded. The step teams skip is enforcement — an admission controller that verifies the signature and the expected certificate identity at deploy time. Signing without verification produces a signature nobody checks.

Pro A version range in a build file — what is wrong with it, and what does "reproducible build" mean?

A range means resolution can differ between two builds of the same commit, so what you scanned and reviewed is not necessarily what you shipped, and someone else's release can change your artifact without any commit on your side. Pin exact versions, lock the full graph (package-lock.json with integrity hashes, Gradle dependency locking), and install strictly from the lock in CI. A reproducible build goes further: the same source produces byte-identical artifacts, which needs timestamps and ordering nondeterminism stripped out — in Maven via project.build.outputTimestamp. The payoff is verifiability: anyone can rebuild and confirm the published artifact matches the source, so a tampered release is detectable instead of a matter of trust.

Pro A direct dependency you cannot upgrade pins a vulnerable transitive version. What now?

Establish exploitability first — is the vulnerable function reachable, is the component exposed, what are EPSS and KEV saying — because that sets the urgency and justifies the effort. Then work down the options: force the patched transitive version through dependencyManagement or a constraint and run the integration suite hard, accepting that you now own an untested combination; check whether a maintained fork or a backported release exists; contribute the upgrade upstream and get it released; apply a compensating control such as disabling the vulnerable feature, blocking the input path at a gateway, or configuring the library to avoid the affected code path; and if none of that is viable, plan replacement of the dependency. Whatever you choose, record it as a dated risk acceptance with a named owner and a review date — never as a silent permanent suppression.

Pro How do you assess whether a new dependency is safe to adopt, and why is an unmaintained library a problem before any CVE exists?

Assess maintenance and blast radius, not just features: release recency and cadence, more than one active maintainer, a published security policy and disclosure history, responsiveness on issues, whether releases are signed, popularity as a weak proxy for scrutiny, and how large a transitive graph the package drags in. OpenSSF Scorecard automates many of these checks. An unmaintained library is dangerous before any CVE because the absence of findings reflects the absence of anyone looking; when a flaw is eventually reported there will be no patch, so your only options are forking or emergency removal. Maintainer-account compromise and the xz-utils case also show that trust in a maintainer is an assumption, which is why lockfiles, integrity hashes, a short delay before adopting brand-new releases, and signed artifacts are worth the friction. The cheapest supply chain vulnerability to fix is the dependency you never added.
