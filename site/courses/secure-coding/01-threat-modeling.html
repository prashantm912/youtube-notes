Module: Threat Modeling and the Security Mindset

Security is not a library you import in the last sprint. It is the accumulated result of hundreds of small design decisions — and threat modeling is the cheap, structured habit that surfaces those decisions while they are still cheap to change.

Knowledge Library → Courses → Secure Coding track → Threat Modeling and the Security Mindset

What this module covers

This module frames the whole track. Everything that follows — injection, cross-site scripting, broken access control, secrets, supply chain — is a specific failure of a general habit: shipping a design whose assumptions nobody ever wrote down or challenged. Threat modeling is that habit made explicit, and it is the one security activity that pays for itself before a single line of code exists.

The first half is the practice: the four questions every threat model answers, STRIDE used as a prompt list rather than a taxonomy to memorise, data flow diagrams and the trust boundaries that are the real output, and the attacker mindset as a learnable skill. The second half is the set of design principles those conversations keep landing on — defense in depth, least privilege, fail securely, secure defaults, complete mediation, economy of mechanism — taught as decisions with tradeoffs rather than slogans on a poster.

Topics

Security is a design property: the four questions

The Threat Modeling Manifesto reduces the whole practice to four questions: what are we building, what can go wrong, what are we going to do about it, and did we do a good job. That framing matters because it is small enough to run in a whiteboard hour with the people who are actually building the thing, which is the only version that survives contact with a delivery schedule. A twenty-page document produced by a specialist who leaves the project is not a threat model; a shared, revisited understanding of where the system can be attacked is.

The reason to do it at design time is economic. A missing authorization check found in a design conversation costs a sentence; found in review it costs a pull request; found in production it costs an incident, a forced password reset, and possibly a regulatory notification. OWASP made this its own Top 10 category — A04:2021 Insecure Design — precisely to say that a class of defects cannot be found by any scanner, because the code correctly implements a design that should never have been approved. No amount of careful implementation rescues a feature that was specified to trust the client.

STRIDE as a prompt list, not a taxonomy to memorise

STRIDE exists to answer "what can go wrong" when the room goes quiet. It is six prompts, each the negation of a security property, and its value is that it makes you consider threats you would not have thought of unaided — not that you can recite it. Run each element of your diagram past all six and write down only the ones that are real for that element.

Concretely, in a typical Spring Boot plus Angular application: Spoofing breaks authentication — a forged or replayed JWT, a session cookie stolen because it lacked HttpOnly, a service calling an internal API with no mutual TLS. Tampering breaks integrity — a price or a role field posted from the browser and bound straight onto an entity by mass assignment, or a message edited in transit. Repudiation breaks accountability — a refund with no audit trail, so nobody can prove who issued it. Information disclosure breaks confidentiality — a stack trace returned to the client, a JPA projection that quietly includes the password hash, one tenant's data returned because the query filtered on id but not on tenant. Denial of service breaks availability — an unbounded page size, an unbounded file upload, a regular expression that backtracks catastrophically. Elevation of privilege breaks authorization — a user reaching an admin endpoint that was protected only by hiding the button in the Angular UI. Each prompt maps to a defense, and naming the pairing is what interviewers listen for.

Data flow diagrams and trust boundaries

The diagram is a means, not the product. Draw the system as external entities, processes, data stores and the flows between them — a whiteboard photograph is a perfectly good artefact — and then draw the lines that matter: the trust boundaries. A trust boundary is any place data or control crosses from a less-trusted zone into a more-trusted one, and it is where validation, authentication and authorization belong. Everything else is decoration.

In a normal enterprise application the boundaries are predictable once you look for them: browser to API (the browser is the attacker's machine), API to database (the query is data plus code, so parameterise), service to third party (their response is untrusted input to you, and your outbound call may be steerable by a user-supplied URL), tenant to tenant inside one database (the sharpest boundary in most SaaS products, and the one most often missing), job scheduler or message consumer to domain logic (a queue message is input too), and admin plane to data plane. Once you have the boundary list, the security requirements almost write themselves — for each crossing, name what is validated, who is authenticated, what they are authorized to do, and what gets logged.

The attacker mindset: what does this trust that it shouldn't?

The mindset is one habit repeated: for every component, ask what it trusts, and whether that trust is justified. Developers are trained to imagine the intended path; an attacker only cares about the unintended ones. So read your own code adversarially — what happens if this field is absent, enormous, negative, a different type, or belongs to somebody else? What happens if these two requests arrive at once, or in the wrong order, or the second one replays the first? What happens if the user simply calls the endpoint the UI never links to?

The load-bearing consequence is that the client is under the attacker's control. Angular's form validators, disabled buttons, hidden menu items and route guards are user-experience features: they help honest users, and they help nobody else. Anyone can open developer tools, edit the request, or skip the app entirely and call the API with a scripted HTTP client. Every check that decides whether something is allowed — validation of ranges and formats, ownership, roles, prices, quantities, tenancy — has to be re-made on the server, where the attacker cannot reach it. This has a formal name in the weakness catalogue, CWE-602, and it is one of the most common findings in real reviews. The same rule extends past the browser: a mobile app can be decompiled, a third-party webhook can be forged, and a message on an internal queue is still input from somewhere.

Defense in depth: assume every single control will fail

Defense in depth is the decision to place independent controls in series so that no single one is load-bearing. It is not "add more security"; it is a specific bet that some control will fail — because a library has a zero-day, because a configuration change is fat-fingered, because a developer removes an annotation while refactoring — and that the system should still not be breached when it does. The useful test of a design is the question "if exactly one of these controls is broken, what does the attacker get?"

Work it through on a single endpoint, a money transfer. At the edge, TLS, a rate limit per token and per address, and a maximum body size. At the gateway, the token is authenticated and its issuer and audience checked, so an expired or foreign token never reaches your code. In the controller, an explicit authorization annotation. In the service, an ownership re-check that the account being debited actually belongs to the calling tenant — because roles say what kind of thing you may do, not which rows you may do it to. In the domain, validation of the amount, currency and idempotency key. At the data layer, a parameterised statement executed by a database role that cannot drop tables. Afterwards, an immutable audit record and an alert on anomalous volume. Remove any one layer and the transfer is still hard to abuse; that is the property you are buying. The cost is real too — every layer is code to maintain and a chance to reject a legitimate request — so layer deliberately around the assets that matter rather than uniformly everywhere.

POST /api/v1/accounts/{id}/transfers
  edge        TLS, request size cap, rate limit per token and per address
  gateway     verify token signature, issuer, audience, expiry
  controller  @PreAuthorize("hasAuthority('SCOPE_transfer')")
  service     assert account.tenantId().equals(principal.tenantId())
  domain      validate amount > 0, currency allowed, idempotency key present
  data        parameterised statement, DB role without DDL or DELETE
  after       append audit event; alert on unusual volume per account

Least privilege: for database users, service accounts, roles and containers

Least privilege says every actor gets exactly the permissions its job requires, for exactly as long as it requires them. The reason is blast radius: privileges are what convert a foothold into a breach. An injection flaw against a connection owned by the database superuser is a catastrophe; the same flaw against a role that can only read and write two tables is a bad afternoon. You cannot prevent every vulnerability, but you can decide in advance how much one is worth.

Apply it in four places you will actually be asked about. Database users: the application's runtime role should not own the schema, should not hold DDL rights, and often should not be able to DELETE from ledger-style tables at all — migrations run under a separate role during deployment. Service accounts: one identity per service with its own credentials, scoped to the specific queues, buckets and APIs it uses, so a compromised reporting service cannot publish payment events. Cloud IAM roles: prefer short-lived, workload-attached credentials over long-lived keys, grant named actions on named resources rather than wildcards, and treat "administrator access" on a build pipeline as the production risk that it is. Container users: images default to running as root, so add an unprivileged user, drop capabilities, and mount the root filesystem read-only — a container escape starts from whatever the process already had. Least privilege is also a process, not a one-off: entitlements accumulate, so review and expire them.

-- PostgreSQL: the runtime role owns nothing and cannot change the schema
CREATE ROLE orders_app LOGIN;
GRANT CONNECT ON DATABASE orders TO orders_app;
GRANT USAGE  ON SCHEMA app       TO orders_app;
GRANT SELECT, INSERT, UPDATE ON app.orders TO orders_app;
GRANT SELECT, INSERT           ON app.ledger TO orders_app;  -- append only
-- migrations run as orders_migrator during deploy, never held by the app

# Container: do not ship a process running as uid 0
RUN useradd --system --uid 10001 appuser
USER 10001

Fail securely: an exception in an authorization check must deny

Failing securely means that when a control cannot reach a verdict, the answer is "no". It sounds obvious and it is one of the most common real bug classes, because the natural shape of defensive Java code produces exactly the wrong behaviour: initialise a boolean to a permissive value, wrap the check in a try, log the exception, carry on. The policy service times out, the token introspection endpoint returns a 500, the entitlement cache is cold — and the system quietly grants access to everyone until somebody notices. MITRE catalogues it as CWE-636, "not failing securely", and it turns a dependency's outage into your authorization bypass.

The fix is structural rather than clever: make "permitted" reachable only by an explicit positive answer, keep the deny path in the catch, and never derive access from the absence of an error. Two related rules travel with it. First, fail securely does not mean fail informatively — the error returned to the caller should be a generic denial, while the stack trace, the tenant id and the reason go to the log, because a helpful message ("no such user" versus "wrong password") is itself a disclosure. Second, decide consciously where availability outranks confidentiality; a door lock that fails open on fire is a deliberate exception, and if you make one, write down why. In Spring Security the same instinct shows up as configuration: deny by default with anyRequest().authenticated() at the end of the chain, so that a newly added controller is protected by omission rather than exposed by it.

// Wrong: an exception leaves the permissive default in place
boolean allowed = true;
try { allowed = policy.permits(user, doc); }
catch (Exception e) { log.warn("policy check failed", e); }   // still true
if (allowed) return doc;

// Right: only an explicit positive answer permits; every other path denies
boolean permitted = false;
try { permitted = policy.permits(user, doc); }
catch (Exception e) { log.warn("policy check failed - denying", e); }
if (!permitted) throw new AccessDeniedException("Not permitted");
return doc;

Secure defaults, complete mediation, economy of mechanism, and obscurity

Secure defaults mean the out-of-the-box configuration is the safe one and exposure is opt-in. Most people never change a default, so the default is the policy: registration disabled rather than open, actuator endpoints closed rather than published, CORS restricted to named origins rather than *, TLS on rather than optional, verbose error pages off in production. Framing it as opt-in exposure rather than opt-out lockdown matters because forgetting to opt in produces a broken feature that someone reports, whereas forgetting to lock down produces a silent hole that nobody reports. This is the whole content of the Security Misconfiguration category, and the same idea underpins hardened container profiles: start from the restricted baseline and grant back what a workload demonstrably needs.

Complete mediation says every access to every object is checked every time, not once at login and then cached in a session flag or, worse, in a hidden form field. It is the principle behind re-checking ownership on each request rather than trusting an id the client sent back to you. Economy of mechanism says keep the security-relevant code small and boring enough to be reviewed and reasoned about — one authorization path rather than five, a framework's session handling rather than your own. And open design, the counterpart of no security through obscurity, says the strength must live in the secret (the key, the credential), never in the secrecy of the design. Renaming an admin endpoint, minifying JavaScript or hiding a parameter raises the effort by an afternoon and buys nothing against anyone who reads your bundle; those measures are fine as friction on top of a real control, and fatal as a substitute for one. Saltzer and Schroeder wrote all of this down in 1975 and it has not needed revision.

Where this fits in the delivery process

Threat modeling belongs at design time, when the diagram is still an argument; security review belongs at pull-request time, when a reviewer can ask "which trust boundary does this cross, and what does it check?"; automated scanning belongs in continuous integration, where dependency checks, static analysis and secret detection run on every commit because they are cheap and tireless. These are complementary, not alternatives — scanners find known bad patterns in code that exists, threat modeling finds design decisions no scanner can see, and review catches the human-shaped gaps between them. Maturity models such as OWASP SAMM and NIST's Secure Software Development Framework exist to tell you which of these you are actually missing rather than which you enjoy doing.

The honest closing note: a threat model nobody revisits is a document, not a control. Value comes from redoing the four questions when the architecture changes — a new integration, a new tenant model, a new public endpoint — and from tracking the mitigations you agreed as ordinary backlog items with owners, so they are delivered rather than admired. A short model that is refreshed each quarter beats a thorough one written once and filed. Use a verification standard such as ASVS to answer the fourth question, "did we do a good job", with evidence rather than opinion.

Interview questions

Threat modeling and the design principles open almost every security round in Indian product and service companies — the first three below are near-guaranteed, and the later ones are where senior candidates separate themselves:

Beginner What is threat modeling, and when do you do it?

A structured conversation about how a system could be attacked, run while the design is still cheap to change. The practical frame is four questions: what are we building, what can go wrong, what are we going to do about it, and did we do a good job. Do it at design time for a new feature or a changed architecture, and revisit it when the system changes — not once at the start of the project.

Beginner What is STRIDE? Give an example of each in a web application.

Six prompts, each the negation of a security property: Spoofing (authentication) — a forged or replayed token; Tampering (integrity) — a price or role field edited in the request; Repudiation (non-repudiation) — a refund with no audit trail; Information disclosure (confidentiality) — a stack trace or another tenant's rows returned; Denial of service (availability) — an unbounded page size or upload; Elevation of privilege (authorization) — a normal user reaching an admin endpoint. Use it as a checklist against each element of the diagram, not as a definition to recite.

Beginner Why is client-side validation not a security control?

Because the client is under the attacker's control. Anyone can open developer tools, edit the request, or bypass the app entirely with a scripted HTTP client, so validators, disabled buttons, hidden menu items and route guards are user-experience features only. Every decision about what is allowed — formats, ranges, ownership, roles, prices, tenancy — must be re-made on the server. MITRE tracks the failure as CWE-602. Keep client validation for fast feedback, and never as the control.

Beginner What is a trust boundary, and why do you draw it?

Any place data or control crosses from a less-trusted zone into a more-trusted one — browser to API, API to database, service to third party, one tenant to another, queue consumer to domain logic. It is where validation, authentication, authorization and logging belong. Drawing them turns a vague diagram into a concrete list of security requirements: for every crossing, say what is validated, who is authenticated, what they may do, and what is recorded.

Beginner Explain defense in depth with an example from an application you have built.

Independent controls placed in series so no single one is load-bearing. On a transfer endpoint: TLS and a rate limit at the edge, token verification at the gateway, an authorization annotation on the controller, an ownership re-check in the service, bean validation in the domain, a parameterised statement run by a restricted database role, and an audit event afterwards. The test of the design is what an attacker gets if exactly one layer is broken — with defense in depth, very little.

Intermediate What is the principle of least privilege, and where would you apply it in a Spring Boot service?

Every actor gets only the permissions its job needs, for only as long as it needs them, because privileges convert a foothold into a breach. In a Spring Boot service: a database role that owns nothing and holds no DDL rights, with migrations run under a separate deploy role; one service account per service scoped to its own queues, buckets and APIs; short-lived cloud credentials with named actions on named resources instead of wildcards; and a container image that runs as an unprivileged user with dropped capabilities and a read-only root filesystem.

Intermediate What does "fail securely" mean, and show the bug it prevents.

When a control cannot reach a verdict, the answer must be deny. The classic bug is a boolean initialised to true, the check wrapped in a try, the exception logged and execution continuing — so a policy-service timeout silently grants access to everyone. Make "permitted" reachable only from an explicit positive answer and keep the deny in the catch. Fail securely, but not informatively: a generic denial to the caller, the detail to the logs. It is CWE-636.

Intermediate What are secure defaults, and why phrase them as opt-in exposure?

The shipped configuration should be the safe one: registration disabled, actuator endpoints closed, CORS limited to named origins, TLS required, verbose errors off in production. Most people never change a default, so the default is the policy. Opt-in exposure fails loudly — someone reports a feature that does not work — while opt-out lockdown fails silently, leaving a hole nobody notices. This is the substance of OWASP's Security Misconfiguration category.

Intermediate Why is "security through obscurity" criticised, and is it ever acceptable?

Because the strength must live in the secret — the key or credential — not in the secrecy of the design. Renaming an admin path, minifying JavaScript or hiding a parameter costs an attacker an afternoon of reading your bundle and traffic, and it cannot be rotated once discovered. It is acceptable only as friction layered on top of a real control (a non-guessable path in addition to authentication), never as a substitute for one. The counterpart principle is open design: assume the attacker has your source.

Intermediate What is complete mediation, and how is it violated in practice?

Every access to every object is checked on every request, not once at login. It is violated by caching an authorization decision in a session flag, by trusting an identifier the client sends back, and by checking a role but never checking that the specific row belongs to the caller — which is exactly how insecure direct object reference bugs appear. Roles say what kind of operation you may perform; ownership and tenancy say which rows, and both must be evaluated server side each time.

Pro Threat model a multi-tenant SaaS API. What do you look at first?

Start with the trust boundaries and put tenant-to-tenant at the top, because it is the boundary most often missing and the breach with the worst consequences. Then check that tenancy is derived from the authenticated principal and never from a request parameter; that it is enforced in one place — a repository filter, row-level security or an enforced query predicate — rather than remembered by every developer; that background jobs, exports, caches, search indexes, file storage keys and log pipelines carry the same partition; and that ids are non-enumerable. Then run STRIDE over the remaining flows, and finish with the noisy-neighbour availability question of per-tenant quotas.

Pro Roles are checked in the gateway. Is that enough? Defend your answer.

No. The gateway can authenticate the caller and enforce coarse scopes, but it does not know which rows the request touches, so it cannot decide ownership or tenancy — and anything that reaches the service by another path (an internal caller, a message consumer, a scheduled job, a misrouted request) skips the check entirely. Treat the gateway as one layer of defense in depth and keep authoritative authorization next to the data, where every path passes through it. This is complete mediation applied to a distributed system.

Pro How do threat modeling, secure code review and CI scanning divide the work?

Scanners find known bad patterns in code that already exists — dependency vulnerabilities, injection sinks, committed secrets — cheaply and on every commit, but they cannot see a design that was wrong on purpose. Threat modeling finds exactly those design flaws before the code exists. Review catches the human-shaped gaps between the two, and is the moment to ask which trust boundary a change crosses. They are complementary; a programme with only scanners keeps shipping insecure designs that pass every gate. Use SAMM or the NIST SSDF to work out which of the three you are actually missing.

Pro A team says they threat modelled the system two years ago. What is your response?

Ask what has changed since, and what happened to the mitigations. A threat model nobody revisits is a document, not a control: architecture drifts, integrations are added, tenancy models change, and the model silently stops describing the system. The two habits that make it real are refreshing the four questions whenever the design changes, and tracking agreed mitigations as ordinary backlog items with owners and dates. Then answer "did we do a good job" with evidence — an ASVS level, a test, a control that demonstrably exists — rather than with the document itself.
