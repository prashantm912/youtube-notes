Module: The OWASP Top 10 Tour

Ten category names that every security conversation in this industry is conducted in. Learn them as vocabulary and as a map of where defects cluster — then learn why treating them as a checklist is the most common way teams get the Top 10 wrong.

What this module covers

The OWASP Top 10 is the shared vocabulary of application security. When a pentest report says "A01", when a client's security questionnaire asks whether you cover the Top 10, when an interviewer asks you to name a few categories — everyone is pointing at the same document. Knowing the current list, in the current order, with the current names is table stakes for a senior developer.

This module is the survey. Each of the ten categories gets a short, concrete treatment: what the weakness actually is, a Java or Angular shape it takes in real code, and the one-line defense. Depth is deliberately deferred — injection, XSS, access control, secrets and cryptography and supply chain each get their own module later in the track, so here we orient rather than exhaust.

The second half of the module is the part most courses skip: how the list is built, what changed in the 2025 revision, and why a ranking derived from aggregated scan and CVE data tells you what is commonly found, not what is most dangerous for the application you happen to be writing. That distinction is the difference between using the Top 10 well and using it as a box-ticking exercise.

This page reflects the OWASP Top 10:2025, which is the current released version at the time of writing. Category names, numbering and ordering changed from the 2021 edition — if you learned the list from an older course or blog post, the names in your head are out of date.

Topics

The current Top 10 categories, top to bottom

The 2025 edition is the ranking below. Two entries are new — Software Supply Chain Failures and Mishandling of Exceptional Conditions — one category (Server-Side Request Forgery) was absorbed into another, and several were renamed. Read the numbers as "where defects cluster", not as "attack severity", for reasons the last two sections of this module unpack.

  1. A01:2025 – Broken Access Control — an authenticated user reaching data or functions that are not theirs. Still first; every tested application in the dataset had some form of it.
  2. A02:2025 – Security Misconfiguration — insecure defaults, debug endpoints, permissive cloud permissions, missing hardening. Climbed from fifth to second as software became more configurable.
  3. A03:2025 – Software Supply Chain Failures — new, and voted first by the community survey. Wider than the old "vulnerable components": it covers the build, the registry, the pipeline and the update channel too.
  4. A04:2025 – Cryptographic Failures — data that should have been encrypted, hashed or transported safely, and was not.
  5. A05:2025 – Injection — untrusted input reaching an interpreter as code. Still includes cross-site scripting, which was folded into Injection back in 2021.
  6. A06:2025 – Insecure Design — flaws you cannot patch because the control was never designed, only implemented badly-shaped requirements.
  7. A07:2025 – Authentication Failures — renamed from "Identification and Authentication Failures": credential stuffing, weak recovery flows, broken session handling.
  8. A08:2025 – Software or Data Integrity Failures — trusting code, updates or serialized data whose integrity was never verified. Note the "or", which replaced 2021's "and".
  9. A09:2025 – Security Logging and Alerting Failures — renamed from "Monitoring" to "Alerting", because collecting logs nobody is paged on is not detection.
  10. A10:2025 – Mishandling of Exceptional Conditions — new. Error handling that leaks internals, fails open, or leaves state half-written when something goes wrong.

Learn the names as names. In interviews, in vendor calls and in audit reports these labels are used as shorthand, and being fluent in the current edition — rather than reciting the 2021 order from a tutorial — is itself a signal.

A01 Broken Access Control and A02 Security Misconfiguration

A01 is the failure where a logged-in user reaches something that belongs to someone else. In a Spring Boot service it is almost always the same shape: the controller checks that you are authenticated, the repository looks up by the id in the path, and nobody checks that the row belongs to you. Change the id in the URL and you read another tenant's invoice. The 2025 edition also folds Server-Side Request Forgery into this category, on the reasoning that SSRF is the server reaching a resource it should not be allowed to reach. Defense: deny by default, enforce every decision server-side, and make ownership part of the query rather than an afterthought.

A02 is what your framework does when you leave it alone. Actuator endpoints exposed without authentication, an H2 console reachable in production, server.error.include-stacktrace=always shipped to prod, an S3 bucket left readable, a CORS policy that reflects any origin, an Angular build served without the security headers the app assumed. It moved from fifth to second in 2025 largely because modern stacks have so many more knobs; every application in the tested dataset had some form of misconfiguration. Defense: harden by automation, not by memory — identical, reviewed configuration across environments, differing only in credentials.

// A01: authorisation that includes ownership, not just authentication
@PreAuthorize("hasRole('CUSTOMER')")
@GetMapping("/invoices/{id}")
public InvoiceDto get(@PathVariable UUID id, @AuthenticationPrincipal AppUser user) {
    // the tenant/owner is part of the lookup, so a guessed id simply returns nothing
    return invoices.findByIdAndCustomerId(id, user.customerId())
                   .map(InvoiceDto::from)
                   .orElseThrow(NotFoundException::new);   // not "forbidden" — do not confirm existence
}

Both categories go deep later: object-level authorization, multi-tenancy isolation and function-level checks in module 05, SSRF in module 06, and headers, CORS and configuration review in module 10.

A03 Software Supply Chain Failures and A04 Cryptographic Failures

A03 is the headline change of the 2025 edition and the category the community survey ranked first — half of respondents put it at number one. It replaces and widens 2021's "Vulnerable and Outdated Components": the risk is no longer only "my pom.xml pins a library with a CVE", it is the whole path from a maintainer's account to your running container. A compromised npm publish token, a typosquatted package name, an unpinned GitHub Action, a build server with write access to production — all of these are A03, and none of them show up in a dependency-version report. Defense: generate and keep an SBOM, pin and verify what you pull, and treat the CI pipeline as production infrastructure with the access controls to match.

A04 is about data that should have been protected and was not: passwords stored with a fast hash (or, still, MD5) instead of a memory-hard one, sensitive fields written to the database in plaintext, tokens signed with a weak or hard-coded key, TLS not enforced on an internal hop because "it is inside the VPC". In Java, the common tell is new Random() or MessageDigest.getInstance("MD5") anywhere near a credential or a token. Defense: classify the data first, then pick the algorithm the current OWASP guidance names — never invent the scheme yourself.

// A04: password storage — a deliberately slow, memory-hard hash, not a digest
@Bean
PasswordEncoder passwordEncoder() {
    // delegating encoder stores an {argon2}/{bcrypt} prefix so you can migrate later
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}

// A04: tokens and one-time codes need a CSPRNG, never java.util.Random
private static final SecureRandom RNG = new SecureRandom();
byte[] token = new byte[32];
RNG.nextBytes(token);

Dependency scanning, SBOM formats, artifact signing and CI gates are the whole of module 09; key management, rotation and password hashing are module 07.

A05 Injection and A06 Insecure Design

A05 is the oldest idea in the list and still the one candidates explain best: data supplied by a user is concatenated into something that gets interpreted — SQL, a shell command, an LDAP filter, a template expression, a log line. The interpreter cannot tell your intent from the attacker's, because by the time it sees the string there is no boundary left. Cross-site scripting lives here too; it is injection into an HTML or JavaScript interpreter. Defense: never build the statement by concatenation — bind parameters so the query shape is fixed before any user data arrives, and encode for the exact context on output.

On the front end, Angular does most of the work for you: interpolation escapes by default, and the framework sanitizes values by context (HTML, style, URL, resource URL). The dangerous move is the deliberate opt-out — bypassSecurityTrustHtml and its siblings, or reaching around the framework with innerHTML or direct DOM writes. Defense: keep bypassSecurityTrust* out of the codebase unless a reviewer signed off on the specific value being trusted.

A06 is the category people find hardest to pin down, because it is defined by absence. Insecure design is a missing control, not a broken one: a password reset flow with no rate limit, a refund endpoint with no maximum, a business rule enforced only in the browser, a workflow where step three can be reached without step two. No amount of careful implementation fixes it, because there was nothing to implement. Defense: threat model the feature before you build it — which is exactly what module 01 is for — and write the abuse cases alongside the use cases.

// A05: the query shape is fixed before any user value is bound
@Query("select o from Order o where o.customer.id = :customerId and o.status = :status")
List<Order> findFor(@Param("customerId") UUID customerId, @Param("status") Status status);

// The unsafe sibling — string concatenation into JPQL/SQL — is the whole vulnerability:
//   "select o from Order o where o.status = '" + status + "'"   // never do this

A07 Authentication Failures and A08 Software or Data Integrity Failures

A07 — renamed in 2025 from "Identification and Authentication Failures" to plain "Authentication Failures" — covers everything around proving who someone is and keeping that proof valid: permitting weak or breached passwords, no throttling against credential stuffing, a "forgot password" flow that is easier to abuse than the login itself, session identifiers that survive a privilege change, tokens that cannot be revoked. Defense: use the framework's authentication rather than your own, enforce multi-factor on anything privileged, rotate the session on login, and rate-limit every credential-accepting endpoint.

A08 is about trusting things whose integrity you never checked. Deserializing attacker-controlled bytes into Java objects is the classic (a gadget chain turns "just data" into "just executed"), but the category is broader: auto-updating from an unverified source, a CI job that deploys an artifact nobody signed, or an Angular app pulling a script from a CDN with no Subresource Integrity hash. Note the 2025 rename from "Software and Data Integrity Failures" to "Software or Data Integrity Failures" — either half alone qualifies. Defense: never deserialize untrusted input into arbitrary types; verify signatures and integrity hashes on everything you execute.

// A08: bind JSON to a known type with unknown fields rejected — do not deserialise "whatever arrives"
ObjectMapper mapper = JsonMapper.builder()
        .disable(MapperFeature.ALLOW_FINAL_FIELDS_AS_MUTATORS)
        .enable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
        .build();                       // polymorphic/default typing stays OFF
PaymentRequest req = mapper.readValue(body, PaymentRequest.class);

Session versus token tradeoffs, cookie flags and revocation are module 05; deserialization gadget chains are module 06.

A09 Security Logging and Alerting Failures and A10 Mishandling of Exceptional Conditions

A09 was "Logging and Monitoring" in 2021 and is "Logging and Alerting" in 2025, and the rename is the whole point: a log file nobody is paged on is archaeology, not detection. The failures it names are concrete — authentication attempts and access-control denials never recorded, logs without the user or request context needed to reconstruct anything, logs that can be tampered with, and — the one developers cause most often — sensitive data written straight into the log stream. Defense: log security-relevant decisions with correlation context, keep the audit trail append-only, encode values written into log lines, and define at least one alert with a written response for each.

A10 is brand new in 2025 and the most developer-shaped category on the list. It covers what your code does when something goes wrong: a stack trace returned to the caller that names your ORM, your schema and your file paths; a catch block that swallows a failure and lets the request continue as if the check had passed (failing open); a multi-step operation that throws halfway and leaves the money debited but not credited; a resource never released on the error path until the pool is exhausted. Defense: handle exceptions where they occur, fail closed rather than open, roll back the whole unit of work, and return a generic message to the caller while the detail goes to the log with a correlation id.

@RestControllerAdvice
class ErrorHandler {
    private static final Logger log = LoggerFactory.getLogger(ErrorHandler.class);

    @ExceptionHandler(Exception.class)
    ResponseEntity<ApiError> onAny(Exception e) {
        String ref = UUID.randomUUID().toString();
        log.error("unhandled failure ref={}", ref, e);     // detail stays server-side
        return ResponseEntity.status(500)
            .body(new ApiError("Something went wrong.", ref));  // caller gets a reference, not internals
    }
}

What changed in the 2025 revision

Compare the two editions side by side and four kinds of change fall out. Additions: Software Supply Chain Failures (A03) and Mishandling of Exceptional Conditions (A10) are new entries. Absorption: 2021's A10 Server-Side Request Forgery is gone as a standalone category and now sits inside Broken Access Control. Expansion: A03 is not simply the old "Vulnerable and Outdated Components" renamed — its scope grew from "a component with a known CVE" to the entire build, distribution and update chain. Renaming and reordering: Security Misconfiguration climbed from fifth to second, "Identification and Authentication Failures" became "Authentication Failures", "Logging and Monitoring" became "Logging and Alerting", and "Software and Data Integrity Failures" became "Software or Data Integrity Failures".

For reference, the 2021 order ran: Broken Access Control, Cryptographic Failures, Injection, Insecure Design, Security Misconfiguration, Vulnerable and Outdated Components, Identification and Authentication Failures, Software and Data Integrity Failures, Security Logging and Monitoring Failures, Server-Side Request Forgery. If that is the list you memorised, four of the ten labels you would say out loud are now wrong.

Worth knowing too: the project publishes a "next steps" set of risks that were considered and did not make the cut — application resilience, memory management failures, and inappropriate trust in AI-generated code. They are a useful preview of where the list is heading, and a reminder that the ten are a cut line, not a boundary of what matters.

Using the list without treating it as a checklist

Start with how the ranking is made, because it explains everything else. Contributing organisations submit testing results — the 2025 edition drew on data covering roughly 2.8 million applications and around 589 mapped CWEs, plus about 175,000 CVE records carrying exploit and impact scores. Eight of the ten positions are derived from that data; the remaining two come from a community survey, specifically so that risks the industry is worried about but has not yet accumulated scan data for can appear at all. The positions themselves come out of a weighted formula combining incidence rate, coverage, average exploitability, average impact and total occurrences. OWASP itself is upfront about the limits, noting that this is not a perfect system but is valuable for ranking risk categories.

Now read the consequence carefully. Incidence rate measures how often a weakness was found across tested applications. It does not measure how badly that weakness would hurt your product. A category can rank high because it is trivially detectable by automated scanners and therefore reported constantly; a devastating risk specific to your domain — say, a business-logic flaw that lets a user approve their own loan — may not correspond to any CWE that scanners aggregate well, and so appears nowhere. The list reflects what is commonly found in the industry's aggregate, not what is most dangerous in your architecture.

That is why the Top 10 is an awareness document and a starting vocabulary rather than a requirements standard. "We covered the OWASP Top 10" is not a security posture, for three reasons: the categories are broad enough that "covered" has no fixed meaning; a passing scan against ten categories says nothing about the eleventh problem; and nothing in the document is written as a testable requirement. Teams that treat it as a compliance checklist end up with a green report and an unexamined threat model.

When you actually need requirements — something with numbered, verifiable statements you can put in a definition of done, hand to a tester, or use in a security review — the answer is the OWASP Application Security Verification Standard (ASVS). ASVS is written as levelled, individually testable controls, so it can carry the weight that the Top 10 cannot. The healthy pattern: use the Top 10 to build shared vocabulary and to orient people quickly, use threat modeling to find what is dangerous about your system, and use ASVS as the requirements standard you verify against.

Interview questions

The OWASP Top 10 is the single most predictable security topic in Indian product and service-company rounds — it appears in screening for Java backend roles, in client-facing interviews at service companies where the customer's security questionnaire drives the conversation, and as the warm-up before deeper design questions:

Beginner Name some OWASP Top 10 categories and how you would prevent them.

Answer from the current 2025 edition and pair each with a defense. Broken Access Control — deny by default and enforce ownership server-side in the query. Security Misconfiguration — automated hardening, no debug endpoints or stack traces in production. Software Supply Chain Failures — SBOM, pinned and verified dependencies, hardened CI. Cryptographic Failures — memory-hard password hashing, TLS everywhere, no home-made crypto. Injection — parameterised queries and context-correct output encoding. Then say the list has ten and offer to continue; naming four or five confidently with real defenses beats reciting ten names with no mitigation.

Beginner What is the OWASP Top 10 and who publishes it?

A periodically updated ranking of the ten most critical web application security risk categories, published by the Open Worldwide Application Security Project, a non-profit. It is compiled from testing data contributed by organisations plus a community survey. It is an awareness and vocabulary document, not a certification or a standard.

Beginner Which category is currently ranked first, and why has it stayed there?

Broken Access Control. It stays first because authorisation is per-resource and per-user, so it cannot be solved by one framework switch the way transport encryption can — every new endpoint is a new opportunity to forget the ownership check. In the 2025 dataset every tested application showed some form of it.

Beginner Where does cross-site scripting sit in the current list?

Inside Injection. XSS stopped being its own category in the 2021 edition and remains folded into Injection in 2025, on the reasoning that it is injection into an HTML or JavaScript interpreter. If a candidate says "XSS is A07" they are quoting the 2017 list.

Intermediate What are the two new categories in the 2025 edition, and what do they cover?

A03 Software Supply Chain Failures — compromises anywhere in building, distributing or updating software, which is much wider than the old "vulnerable and outdated components"; it was ranked first by the community survey. And A10 Mishandling of Exceptional Conditions — improper error handling, failing open, leaking internals in error responses, and leaving state or resources inconsistent when something throws.

Intermediate What happened to Server-Side Request Forgery — it used to have its own entry?

It was A10 in 2021 and no longer stands alone in 2025; it is now covered under A01 Broken Access Control, since SSRF is the server being made to reach a resource it should not be permitted to reach. It has not become less important — its data simply merged into a broader category.

Intermediate Show me a Java example of a Top 10 issue and its fix.

The cleanest to demonstrate is A01. An endpoint that takes an id from the path, is annotated only with an authentication check, and loads by id alone lets any logged-in user read another customer's record by changing the number. The fix is to make ownership part of the lookup — findByIdAndCustomerId(id, principal.customerId()) — and return not-found rather than forbidden so you do not confirm the row exists. Mention that centralising this in a reusable authorisation component beats repeating the check per controller.

Intermediate How does Angular help with the Top 10, and where does it stop helping?

Angular escapes interpolated values and sanitizes by context — HTML, style, URL, resource URL — so ordinary template binding is safe against injection by default, and it supports Trusted Types. It stops helping the moment you opt out: bypassSecurityTrustHtml and friends, direct innerHTML writes, or DOM manipulation outside the framework. It also does nothing for server-side categories — access control, misconfiguration, supply chain and cryptography are all backend concerns, and a client-side check is a usability feature, never a security control.

Intermediate Why was Security Misconfiguration promoted to second place?

Because modern stacks are far more configurable than they were — cloud IAM, container runtimes, service meshes, framework auto-configuration — so there are vastly more places to get it wrong, and misconfiguration was found in essentially every application in the contributed dataset. The practical takeaway is that hardening has to be automated and version-controlled: environments identical except for credentials, with configuration verified in CI rather than remembered by whoever deployed last.

Intermediate The renamed A09 says "Alerting" rather than "Monitoring". Does that change anything practically?

Yes, and it is a good question to answer concretely. Logging plus a dashboard nobody watches is not detection. The rename pushes teams to define, for each security-relevant event class, an actual alert with a threshold and a written response — plus the surrounding discipline: log authentication attempts and access-control denials with user and request correlation, encode values written into log lines so logs cannot themselves be injected, keep the audit trail append-only, and keep secrets and personal data out of logs entirely.

Pro How is the Top 10 actually compiled, and what does the ranking really measure?

Organisations contribute application testing results — the 2025 edition drew on data covering roughly 2.8 million applications and around 589 mapped CWEs, alongside about 175,000 CVE records with exploit and impact scores. Eight positions are derived from that data; two come from a community survey so that emerging risks without accumulated scan data can still appear. Positions come from a weighted formula over incidence rate, coverage, average exploitability, average impact and occurrence counts. So the ranking measures how commonly a weakness class is found across the contributing industry — not how dangerous it is in any particular system.

Pro A client asks you to certify that your application is "OWASP Top 10 compliant". How do you respond?

Explain, politely, that the Top 10 is an awareness document with no testable requirements, so "compliant" has no defined meaning against it — you cannot pass or fail a document that names broad categories rather than controls. Then offer what they actually want: verification against OWASP ASVS at an agreed level, since ASVS is written as numbered, individually testable requirements; testing methodology from the Web Security Testing Guide; plus your SAST/DAST/dependency-scan gates and a threat model for the system in question. Framing it that way turns a box-ticking request into a real scope, which is exactly the conversation a senior engineer is expected to lead.

Pro Give an example of a serious risk in your application that the Top 10 would not surface.

Business-logic flaws are the standard answer: a workflow where a user can approve their own high-value transaction, a refund path with no upper bound, a discount that stacks unboundedly, a state machine where a step can be skipped. These map poorly to CWEs that scanners aggregate, so they contribute little incidence data and cannot rise in a data-derived ranking. They are exactly what threat modeling and abuse-case analysis exist to find, which is why the Top 10 must be a starting point rather than the scope of your security work.

Pro Two categories on the list are only reachable at design time. Which, and what follows from that?

Insecure Design (A06) and, largely, Software Supply Chain Failures (A03). Insecure design is a missing control — no rate limit was specified, no segregation of duties was required — so there is no line of code to patch; it has to be caught in threat modeling and in the abuse cases written next to the requirements. Supply chain risk is set by choices about registries, pinning, signing and pipeline permissions, mostly made once at platform level. What follows is that a purely code-scanning security programme is structurally blind to both, and the security review has to move earlier than the pull request.

Pro A10 is new. Sketch how you would systematically address it in a Spring Boot service.

Four moves. First, a single @RestControllerAdvice that maps every exception to a generic client message plus a correlation reference, with the detail logged server-side — no stack traces, ORM names or file paths on the wire, and stack-trace inclusion switched off in configuration. Second, fail closed: any catch around a security decision must deny, never continue; audit every empty catch block. Third, transactional integrity — the whole unit of work rolls back on failure, with idempotency keys where a retry could duplicate an effect. Fourth, resource safety on the error path: try-with-resources everywhere, plus timeouts, quotas and rate limits so a stream of failing requests cannot exhaust connections or threads. Then test it — inject failures deliberately and assert the response body reveals nothing and the state is consistent.
