Module: CSRF, SSRF and Deserialization

Three flaw families, one root cause: the server trusts something it has no business trusting — the origin of a request, a URL somebody handed it, or a byte stream it was told to turn back into objects.

Knowledge Library → Courses → Secure Coding track → CSRF, SSRF and Deserialization

What this module covers

Injection and XSS are about data that gets treated as code. This module is about a subtler mistake: misplaced trust in a channel. In cross-site request forgery the server trusts that a request carrying a valid session cookie was intended by the user. In server-side request forgery it trusts a URL a user supplied and then fetches it from a network position the user could never reach. In insecure deserialization it trusts a byte stream enough to let that stream decide which classes the runtime constructs.

Each section pairs the mechanism with its defense, and every code example comes as a vulnerable/fixed pair, because the fixes are small and the bugs are recurring. The module closes on the category that quietly enables all three in production — exceptional conditions: the catch block that swallows an authorization failure and carries on, the error handler that defaults to "allowed", and the stack trace that hands an attacker your class names, framework versions and file paths.

Topics

CSRF: the browser as a confused deputy — and why a header token is immune

Cross-site request forgery works because of one browser behaviour: when a request goes to bank.example, the browser attaches every cookie scoped to bank.example, and it does so regardless of which page initiated the request. An attacker-controlled page can therefore cause the victim's browser to issue an authenticated request — an auto-submitting form, an image tag pointing at a state-changing URL, a fetch with credentials — and the server sees a perfectly valid session. The attacker cannot read the response (the same-origin policy still holds), so CSRF is a write attack: transfer money, change an email address, add an admin, delete a record. The classic name for it is the confused deputy: the browser has authority, the attacker has intent, and the server cannot tell them apart.

The key insight, and the single most-asked follow-up in interviews: this only works when the credential is ambient. A cookie is attached by the browser automatically, so the attacker gets it for free. An Authorization: Bearer <token> header is not — some JavaScript on your origin has to read the token from memory or storage and set the header explicitly, and an attacker's page cannot run JavaScript on your origin nor read your storage. So a pure token-in-header API is structurally immune to CSRF; an API that keeps the same token in a cookie is not, no matter that the token happens to be a JWT. The vulnerability tracks the transport, not the credential format.

SameSite cookies: the strong default, and exactly what it does not cover

SameSite attacks the mechanism rather than the symptom: it tells the browser not to attach the cookie on cross-site requests at all. SameSite=Strict withholds the cookie on every cross-site request including plain top-level navigation, which means arriving at your site from a search result or an email link looks logged-out — usually unacceptable for consumer apps. SameSite=Lax is the practical default (and the browser default when the attribute is absent): the cookie is sent on top-level safe navigations — a user clicking a link — but withheld on cross-site POSTs, iframes, images and background fetches. That single line kills the overwhelming majority of classic CSRF. SameSite=None re-enables cross-site sending and requires Secure; use it only for genuine third-party embedding, and expect it to keep shrinking as browsers restrict third-party cookies.

Do not treat it as complete protection, and be ready to say why in an interview. Lax still permits cross-site GET navigation, so any state-changing endpoint reachable by GET remains forgeable. Some browsers apply a short "Lax-allowing-unsafe" grace window to freshly issued cookies. Sibling subdomains are same-site but not same-origin, so an XSS or a takeover on promo.example.com can forge requests to app.example.com. And schemeful same-site means http:// and https:// versions of a host count as different sites. SameSite is a very good default layer; the token check underneath it is what you actually rely on.

Set-Cookie: SESSION=abc123; Path=/; Secure; HttpOnly; SameSite=Lax

server.servlet.session.cookie:
  same-site: lax
  secure: true

Synchronizer tokens, double submit, origin checks — and never a state change on GET

The canonical defense is the synchronizer token pattern: the server generates a random, per-session (or per-request) token, stores it server-side against the session, embeds it in every form or hands it to the SPA, and rejects any unsafe request whose submitted token does not match. It works because the attacker's page cannot read your response bodies and therefore cannot learn the token. Its cost is server-side state, which is exactly why the double-submit cookie exists: the server sets the token in a cookie and requires the same value in a header or form field, comparing the two without storing anything. Both arrive, but only your own JavaScript can copy the cookie into the header — an attacker's page can cause the cookie to be sent, not read.

Be honest about double submit's weaknesses, because that is the discriminating question. It leans on the same-site cookie boundary, so anything that can write a cookie for your domain breaks it: a compromised or attacker-controlled sibling subdomain, a cookie-injection bug, or an intermediary that sets cookies. The hardened variant signs or HMACs the token to the session so a planted value cannot be forged. Layer origin verification on top: on unsafe methods, compare the Origin header (falling back to Referer) against an allow-list of your own origins and reject mismatches — cheap, and it catches the cases the token pattern misses. Finally the rule that underwrites all of this: GET, HEAD and OPTIONS must be safe and side-effect free. A "delete" implemented as a GET is forgeable with a single image tag no matter how good your token scheme is, and it will also be triggered by prefetchers, link scanners and antivirus proxies.

Spring Security's CSRF filter: on by default, and when disabling it is actually correct

Spring Security enables CSRF protection for you: any request with an unsafe method (anything other than GET, HEAD, TRACE, OPTIONS) must carry a valid token or it is rejected with 403. The token comes from a CsrfTokenRepository — session-backed by default, or CookieCsrfTokenRepository.withHttpOnlyFalse() when a JavaScript front end needs to read it. That cookie form is what Angular's HttpClient expects out of the box: it looks for a cookie named XSRF-TOKEN and echoes it in an X-XSRF-TOKEN header, which is the double-submit pattern wired end to end. On Spring Security 6 you also normally set a SpaCsrfTokenRequestHandler so the deferred token is materialised for single-page clients.

Now the judgement call, which is a genuine interview separator. Disabling CSRF is correct for a stateless API whose only credential is an Authorization header — no cookie, no ambient authority, nothing for a cross-site page to abuse; pair it with SessionCreationPolicy.STATELESS so no session cookie sneaks back in. Disabling it is wrong in the far more common case: a browser app with a session cookie where a form POST started returning 403, so somebody added csrf.disable() to make the error go away. That is not a fix, it is the removal of the control that was working. The right response to that 403 is to find out why the token is not reaching the server — a form missing the hidden field, an SPA not echoing the cookie, a proxy stripping the header, or a login that rotated the session without rotating the token.

// WRONG: switched off because a form POST returned 403 and the deadline was close
http.csrf(csrf -> csrf.disable());

// RIGHT for a cookie-session browser app: keep it on, hand the SPA a readable token
http.csrf(csrf -> csrf
        .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
        .csrfTokenRequestHandler(new SpaCsrfTokenRequestHandler()));

// RIGHT for a stateless API: the credential is a header, never a cookie
http.csrf(AbstractHttpConfigurer::disable)
    .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS));

SSRF: the server fetches your URL, from inside the perimeter

Server-side request forgery is what happens when an application takes a URL (or a hostname, or anything that becomes one) from a user and then fetches it. The feature is usually innocent: render a link preview, import an image from a URL, call a customer-configured webhook, fetch an XML schema, generate a PDF from a page. The vulnerability is not the fetch — it is who is doing the fetching. Your server sits inside the VPC, behind the firewall, on the management network, holding an instance role. A request it makes reaches places the internet cannot: internal admin panels with no authentication because "it's internal", databases and caches bound to private addresses, service-mesh control planes, Kubernetes APIs, and other internal HTTP endpoints that were never designed to be reached by a stranger.

Two properties make SSRF nastier than it first looks. First, it is not limited to HTTP — depending on the client library, schemes like file://, gopher:// or ftp:// may be honoured, turning a URL fetch into local file disclosure. Second, it often works blind: the response never comes back to the attacker, but timing differences, error messages, or an out-of-band callback reveal whether the internal request succeeded, which is enough to map an internal network. And if your handler reflects the fetched body back to the caller, you have converted the server into a general-purpose proxy for your own private network.

Cloud metadata: the credential-theft scenario, and IMDSv2

The scenario every cloud interview wants to hear is the instance metadata service. Every major cloud exposes a link-local address — 169.254.169.254 on AWS, GCP and Azure — that a VM can query to learn about itself. On AWS that includes, under iam/security-credentials/, temporary credentials for the instance's IAM role. It is unauthenticated by design, because "only code running on this instance can reach it". SSRF breaks that assumption exactly: your application is code running on that instance, and an attacker who can steer its outbound fetch can ask it to retrieve the role's access key, secret and session token, then use them from anywhere until they expire. That is the mechanism behind several of the largest cloud breaches on record — an SSRF in a web tier, escalated into read access on object storage via stolen role credentials.

IMDSv2 is the mitigation and you should be able to explain why it works. It makes metadata access session-oriented: a client must first send a PUT to obtain a short-lived token, then present that token in an X-aws-ec2-metadata-token header on every subsequent request. Requests with a token hop limit above one are also refused, so the response cannot travel back through a container network hop. A typical SSRF gives the attacker control over a URL, not over the method, the headers or the multi-step flow — so the PUT-then-GET handshake is out of reach for most SSRF primitives. Set the instance metadata options to http-tokens: required so v1 is switched off entirely; leaving both enabled leaves the old path open. Treat this as one layer among several, not a substitute for validating the URL.

Defending against SSRF: allow-list, resolve the IP, refuse redirects, isolate egress

Start from the strongest position: does the user need to supply a URL at all? Very often the requirement is "fetch from one of these three partners", which becomes an identifier the user picks and a URL you construct. When a URL genuinely must come in, allow-list the destinations — scheme, host, port, and path prefix if you can — rather than block-listing internal ranges. Block-lists lose: there are too many spellings of an address (decimal, octal, hex, IPv6-mapped, shortened forms), too many redirect tricks, and the internal ranges you must cover keep growing. An allow-list of two hostnames is a rule you can read and reason about.

Then validate what the hostname actually resolves to, not just how it is spelled. Resolve the name, check every returned address against your policy — reject loopback, link-local, private and any-local ranges — and connect to a validated address, so a name that resolves once to a public address and again to 169.254.169.254 (DNS rebinding) cannot slip through the gap between check and use. Disable redirect following, or re-run the same validation on every hop, because a permitted host that answers with a redirect to an internal address defeats hostname-only checks in one step. Never reflect the raw upstream response, status code or error text back to the caller — that is what turns a blind SSRF into a readable one. And back all of it with network controls: run the fetching component in a subnet whose egress is restricted to the destinations it needs, or send the fetch through a dedicated forward proxy that enforces the allow-list outside your application code.

// VULNERABLE: whatever URL arrives is fetched from inside the VPC, with the instance role attached
@GetMapping("/preview")
String preview(@RequestParam String url) {
    return restClient.get().uri(url).retrieve().body(String.class);   // reaches 169.254.169.254 too
}

// FIXED: allow-list the host, validate the resolved addresses, refuse redirects, hide the body
private static final Set<String> ALLOWED = Set.of("images.partner.example", "cdn.partner.example");

String preview(String url) throws Exception {
    URI uri = URI.create(url);
    if (!"https".equals(uri.getScheme()) || !ALLOWED.contains(uri.getHost())) {
        throw new BadRequestException("destination not permitted");
    }
    for (InetAddress ip : InetAddress.getAllByName(uri.getHost())) {
        if (ip.isLoopbackAddress() || ip.isLinkLocalAddress()
                || ip.isSiteLocalAddress() || ip.isAnyLocalAddress()) {
            throw new BadRequestException("destination not permitted");
        }
    }
    HttpClient client = HttpClient.newBuilder()
            .followRedirects(HttpClient.Redirect.NEVER)   // re-validate every hop, or allow none
            .build();
    return summarise(client.send(HttpRequest.newBuilder(uri).build(), ofString()).body());
}                                                        // never return the raw upstream response

Insecure deserialization: a byte stream that tells the runtime what to build

Serialization turns an object graph into bytes; deserialization turns bytes back into an object graph. The security problem is in that second sentence. A native serialized stream does not merely carry data — it names types, and the runtime obeys. Deserializing untrusted input therefore hands an outsider partial control over which classes get instantiated and which of their lifecycle hooks (readObject, readResolve, readExternal, and the equivalents in other languages) execute. All of this happens during deserialization, before your code has looked at the result and decided whether it likes it. Validating the object afterwards is far too late; the damage is done on the way in.

From there the concern is what security researchers call a gadget chain: classes already present on your classpath — in your framework, your JSON library, your collections utilities — whose ordinary construction-time behaviour can be strung together to produce an effect the authors never intended, up to and including remote code execution. You do not need a vulnerable class of your own; you need a vulnerable combination in the libraries you already depend on. Tooling such as ysoserial exists to demonstrate that these chains are real and plentiful, which is precisely why "we don't deserialize anything dangerous" is not an argument you can make about your own classes. It also means dependency hygiene is part of this defense: which library versions are on your classpath decides which chains exist, so this topic connects directly to Module 09 — Supply Chain Security.

Safe deserialization: data-only formats, ObjectInputFilter, and Jackson's polymorphic trap

The primary defense is refusal: do not deserialize untrusted input with a format that can name types. In practice that means never accepting Java serialized bytes over an HTTP endpoint, a queue, a cookie or a cache key that a client can influence. Prefer a data-only format — JSON, or a schema-first binary format — bound to a concrete, closed target type you declared, ideally a record, and validated afterwards. If native serialization is genuinely unavoidable (a legacy RMI or JMX path, an old cluster protocol), put an allow-list filter in front of it. JEP 290 added ObjectInputFilter and process-wide filters in Java 9 and backported them to 8; JEP 415 added context-specific filter factories so different call sites can carry different policies. Write the pattern as an allow-list ending in !* — everything not explicitly named is rejected — and cap depth, array size and stream size while you are there.

Then the trap that catches JSON users who think they are safe: polymorphic type handling. Jackson's enableDefaultTyping() (and its successor activateDefaultTyping() with a permissive validator) writes the Java class name into the JSON and instantiates whatever it finds on the way back — which reintroduces exactly the "the input names the type" problem the JSON format was supposed to avoid. That is the root of a long tail of jackson-databind CVEs, and why default typing was deprecated in favour of validators. Do not enable global default typing on data you did not produce. When you legitimately need polymorphism, use @JsonTypeInfo with Id.NAME and an explicit @JsonSubTypes registry so the wire carries a short logical name you control, never a class name; a sealed interface makes the closed set explicit to the compiler as well.

// VULNERABLE: readObject() constructs whatever types the stream names
Object o = new ObjectInputStream(request.getInputStream()).readObject();

// BETTER (legacy paths only): an allow-list filter; anything not named is refused by "!*"
ObjectInputStream in = new ObjectInputStream(request.getInputStream());
in.setObjectInputFilter(ObjectInputFilter.Config.createFilter(
        "maxdepth=8;maxarray=1000;com.acme.dto.*;java.util.List;java.lang.String;!*"));
Object o = in.readObject();

// BEST: take data, not objects - bind JSON into a closed type you declared
OrderSnapshot dto = objectMapper.readValue(request.getInputStream(), OrderSnapshot.class);

// VULNERABLE Jackson config: the JSON gets to name the Java class
mapper.enableDefaultTyping();                  // removed in 2.10; the successor with a
mapper.activateDefaultTyping(LaissezFaireSubTypeValidator.instance);  // permissive validator is no safer

// FIXED: no global polymorphism; logical names you control, over a closed set
@JsonTypeInfo(use = Id.NAME, include = As.PROPERTY, property = "kind")
@JsonSubTypes({ @JsonSubTypes.Type(value = CardPayment.class, name = "card"),
                @JsonSubTypes.Type(value = UpiPayment.class,  name = "upi") })
public sealed interface Payment permits CardPayment, UpiPayment { }

Exceptional conditions: fail-open bugs and the error path nobody reviews

Every control in this module is a decision, and every decision has a path where the decision could not be made: the policy service timed out, the token store was unreachable, the signature verifier threw, the URL parser rejected the input in an unexpected way. What your code does on that path is a security property, and it is almost never reviewed. The recurring bug is fail-open: a catch (Exception e) that logs a warning and returns true, a default branch in a permission enum that maps unknown to "allowed", a feature flag that treats "could not evaluate" as "enabled", a JWT check whose validation error path falls through to the happy case. Under normal load these look fine; during the incident when your auth dependency is degraded, they turn an availability problem into an authorization bypass — usually for every user at once.

The rules are short. Fail closed by default: if you cannot prove access is permitted, deny it and return a 5xx or a clean 403 rather than proceeding. Never let a broad catch straddle a security decision — catch narrowly, and keep the decision and its failure handling in the same place so a reviewer can see both. Deny on unknown enum values instead of defaulting to permit. Separately, keep internal detail out of responses: stack traces, SQL fragments, framework versions, absolute file paths and library names are reconnaissance, and in Spring they leak by default unless you set the error attributes appropriately and add a @RestControllerAdvice that maps exceptions to a small set of generic, non-revealing responses. Log the detail with a correlation id; return the id, not the trace. Then test it: a test that asserts "when the policy service throws, access is denied" is worth more than any amount of review, and it is the artefact that proves the error path got the same scrutiny as the happy path.

// VULNERABLE: the catch swallows an authorization failure and lets the request continue
public boolean canEdit(User user, Document doc) {
    try {
        return policyService.check(user, doc);        // remote policy decision
    } catch (Exception e) {
        log.warn("policy check failed", e);
        return true;                                  // fail OPEN - everyone is now an editor
    }
}

// FIXED: fail closed, log with a correlation id, surface nothing internal to the caller
public boolean canEdit(User user, Document doc) {
    try {
        return policyService.check(user, doc);
    } catch (PolicyUnavailableException e) {          // narrow catch, decision stays local
        log.error("policy check failed user={} doc={} correlationId={}",
                  user.id(), doc.id(), MDC.get("correlationId"), e);
        throw new AuthorizationUnavailableException(); // -> 503, access is NOT granted
    }
}

// And the response the user sees: an id they can quote, never a stack trace
@RestControllerAdvice
class ErrorAdvice {
    @ExceptionHandler(Exception.class)
    ResponseEntity<ApiError> onAny(Exception e) {
        log.error("unhandled correlationId={}", MDC.get("correlationId"), e);
        return ResponseEntity.status(500)
                .body(new ApiError("Something went wrong", MDC.get("correlationId")));
    }
}

Interview questions

These three topics are staples of Indian product and service-company rounds — CSRF in every Spring Security screen, SSRF in every cloud-flavoured round, and deserialization plus fail-open error handling in the senior discussions:

Beginner What is CSRF, in one sentence?

An attacker's page causes a victim's browser to send a state-changing request to a site the victim is logged in to, and the browser attaches the session cookie automatically, so the server executes it as the victim. The attacker cannot read the response — it is a write attack, not a read attack.

Beginner Why doesn't CSRF affect an API that authenticates with an Authorization header?

Because the credential is not ambient. A cookie is attached by the browser to every request to that origin, including one initiated by an attacker's page. An Authorization: Bearer header has to be set explicitly by JavaScript running on your origin, and an attacker's page can neither run code on your origin nor read your storage. If you move that same token into a cookie, CSRF is back — the exposure follows the transport, not the token format.

Beginner What does SameSite=Lax do, and what does it not protect?

Lax withholds the cookie on cross-site subrequests — POSTs, iframes, images, background fetches — but still sends it on top-level safe navigation, so following a link from an email still works. It does not protect a state-changing endpoint reachable by GET, does not separate sibling subdomains (same-site is broader than same-origin), and can be undermined by a browser's short grace window for newly set cookies. Treat it as a strong default layer, not the whole defense.

Beginner Why must state-changing operations never use GET?

GET is defined as safe, so everything treats it as harmless: browsers prefetch it, proxies and link scanners follow it, SameSite=Lax still sends cookies with it, and an attacker can trigger it with a bare image tag. Any token scheme is irrelevant if the action can be performed by a URL alone. Use POST, PUT, PATCH or DELETE for anything with an effect.

Intermediate Synchronizer token versus double-submit cookie — which is stronger and why?

The synchronizer token is stronger: the token is stored server-side against the session, so an attacker must know a secret they can never read. Double submit stores nothing server-side and just compares a cookie with a header or field, which is convenient for stateless services but leans entirely on the assumption that nobody else can write cookies for your domain — a compromised sibling subdomain or a cookie-injection bug defeats it. If you use double submit, use the signed or HMAC-bound variant so a planted cookie value cannot be forged.

Intermediate Spring Security is returning 403 on your form POST. A teammate adds csrf.disable(). Critique that.

It removes the control that was doing its job. The 403 means the CSRF token did not arrive or did not match — a missing hidden field, an SPA not echoing the XSRF-TOKEN cookie into the X-XSRF-TOKEN header, a proxy stripping the header, or a session rotated at login without a fresh token. Fix the token flow. Disabling CSRF is only correct for a genuinely stateless API whose credential is an Authorization header and which creates no session cookie — pair it with SessionCreationPolicy.STATELESS.

Intermediate How does Angular's HttpClient participate in CSRF defense?

It implements the double-submit pattern automatically: it reads a cookie named XSRF-TOKEN and copies the value into an X-XSRF-TOKEN header on mutating same-origin requests. The server sets that cookie in a readable (non-HttpOnly) form — in Spring that is CookieCsrfTokenRepository.withHttpOnlyFalse() — and compares the two on arrival. It only helps for same-origin requests, and the server side is still the part that enforces anything.

Intermediate What is SSRF, and why is it far more dangerous on a cloud VM than on a laptop?

SSRF is the server fetching a URL that a user controls. The danger is the server's network position: inside the VPC it can reach internal admin panels, databases, mesh control planes and Kubernetes APIs that the internet cannot. On a cloud VM it can also reach the instance metadata service at 169.254.169.254, which on AWS will hand out temporary credentials for the instance's IAM role — turning a URL-fetch bug into stolen cloud credentials that work from anywhere until they expire.

Intermediate Why is a block-list of internal IP ranges an inadequate SSRF defense?

Because addresses have too many spellings and too many indirections: decimal, octal and hexadecimal encodings, IPv6-mapped forms, shortened notations, hostnames that resolve to internal addresses, and redirects from a permitted host to an internal one. You also have to keep the list current as your private ranges change. An allow-list of the handful of destinations the feature actually needs is small, auditable and does not degrade as the network grows.

Intermediate You validate the hostname, then fetch the URL. What is still wrong?

Two gaps. First, a name check is not an address check — the name can resolve to an internal address, and it can resolve differently between your validation and the connection (DNS rebinding), so you must resolve, validate every returned address against the policy, and connect to a validated address. Second, redirects: a permitted host answering with a 302 to an internal address bypasses a hostname-only check in one hop, so disable redirect following or re-run the full validation on each hop. And never reflect the raw upstream response back to the caller.

Intermediate How does IMDSv2 mitigate SSRF-driven credential theft?

It makes metadata access a session flow instead of a plain GET: the client must first issue a PUT to obtain a short-lived token and then send that token in a header on every request, and responses are refused beyond a configured token hop limit. A typical SSRF gives control of a URL, not of the HTTP method, arbitrary headers or a two-step handshake, so the primitive no longer reaches the credentials. Set the metadata options to require tokens so IMDSv1 is switched off — leaving both enabled leaves the old path wide open.

Pro Why is deserializing untrusted data dangerous even if you validate the resulting object?

Because the dangerous work happens during deserialization, before you ever see the object. A native serialized stream names types, so the input decides which classes are instantiated and which construction-time hooks run — readObject, readResolve, readExternal and their equivalents. By the time your validation code executes, those side effects have already happened. Validation after the fact is the wrong layer; the fix is to not let untrusted input choose types at all.

Pro What is a gadget chain, conceptually, and why can't you audit your own classes to rule it out?

A gadget chain is a sequence of ordinary classes already on the classpath whose normal construction and lifecycle behaviour can be composed into an effect their authors never intended, up to remote code execution. The classes come from your framework and library dependencies, not from your code, so auditing your own domain objects proves nothing — the exposure is a property of which library versions you ship. That is why the mitigation is refusing untrusted deserialization plus dependency hygiene, and why tools like ysoserial exist as evidence that such chains are commonplace rather than theoretical.

Pro A legacy service must keep native Java deserialization. How do you make it survivable?

Put an ObjectInputFilter allow-list in front of it — the JEP 290 mechanism, with JEP 415 filter factories if different call sites need different policies. Write the pattern as explicit permitted types ending in !* so anything unnamed is rejected, and set maxdepth, maxarray, maxrefs and maxbytes so a malicious stream cannot exhaust memory. Then contain it: run the endpoint with least privilege, isolate it on the network, authenticate and integrity-check the stream before reading it, keep dependencies patched, and plan to replace the protocol with a data-only format.

Pro You are on JSON, so deserialization attacks don't apply. True?

Not automatically. JSON is data-only until you enable polymorphic type handling. Jackson's enableDefaultTyping(), and activateDefaultTyping() with a permissive validator, embed Java class names in the JSON and instantiate whatever comes back — the same "input names the type" problem, which is the root of a long list of jackson-databind CVEs. Never enable global default typing on data you did not produce. Where polymorphism is genuinely needed, use @JsonTypeInfo with Id.NAME and an explicit @JsonSubTypes registry so the wire carries a logical name over a closed set you control.

Pro Review this: a permission check wrapped in catch (Exception e) that logs a warning and returns true.

Classic fail-open. When the policy dependency degrades — exactly the moment you are least able to notice — the system grants access to everyone, converting an availability incident into an authorization bypass. Fix it by failing closed: catch narrowly, deny or propagate an "authorization unavailable" error that becomes a 503, keep the decision and its failure handling in one place, and default unknown enum values to deny rather than permit. Then write a test that asserts access is denied when the policy service throws — that test is the proof the error path was reviewed.

Pro Why do stack traces in API responses matter, and what should you return instead?

They are free reconnaissance: class and package names, framework and library versions to look up known vulnerabilities against, absolute file paths, SQL fragments and sometimes data values. Return a generic message plus a correlation id, and log the full detail server-side against that id. In Spring, keep the default error attributes from including the trace or message, and add a @RestControllerAdvice that maps exceptions to a small, deliberate set of responses — the error path deserves the same review as the happy path.
