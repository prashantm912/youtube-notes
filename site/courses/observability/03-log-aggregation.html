Module: Log Aggregation

SSH in and tail the file — a workflow that dies the moment you run two replicas, and dies harder in Kubernetes, where the filesystem you were going to tail disappears with the pod. This module is about the machinery that replaces it, and about the bill it quietly generates.

Knowledge Library → Courses → Observability track → Log Aggregation

What this module covers

Module 02 got your application emitting good structured logs. This module is about what happens to them next: how they leave the process, where they land, how you search them, and what that costs. Centralization is not a nice-to-have — with three replicas behind a load balancer, the log line explaining a user's failed request is on exactly one of them, and nothing tells you which.

We cover the pipeline shape shared by every stack (emit, collect, ship, parse and enrich, store and index, query), the collectors that do the shipping, the Kubernetes DaemonSet pattern, and then the two dominant destinations compared honestly: ELK/EFK, which indexes everything and can find anything at a price, and Grafana Loki, which indexes only labels and is dramatically cheaper provided your search already has a rough address. The second half is the part that actually pays for the first: the debugging workflow, the query languages, and retention and cost control.

Topics

Why centralization stops being optional

Single-server logging works because there is one file and one machine. Every assumption behind that breaks at scale. With N replicas a request touches one of them, so "grep the log" becomes "grep N logs and hope"; with autoscaling, N changes while you are looking. In containers the situation is worse: the container filesystem is ephemeral, so a crash-looping pod destroys the evidence of why it crashed, and Kubernetes' own node-level log files are rotated and garbage-collected without asking you. Add a request that crosses six services and the story you need is scattered across six different machines' log files, none of which is complete on its own.

The fix is the twelve-factor rule: an application should not manage log files at all. It writes an unbuffered event stream to stdout/stderr, and the execution environment — the container runtime, then a collector — is responsible for routing, storing and archiving it. That single discipline decouples the application from the logging backend entirely, which is why you can swap ELK for Loki later without touching application code.

The architecture every stack shares

Vendors differ on components but not on shape. Six stages, always: emit (the application writes structured lines to stdout), collect (an agent reads the container's log files or a socket), ship (the agent buffers and forwards, with backpressure and retries so a backend outage does not lose data or stall the app), parse and enrich (turn text into fields, attach pod, namespace, host, environment), store and index (write to the backend in whatever indexing model it uses), query (a UI over the store). Debugging a broken logging pipeline means asking which of those six stages stopped.

Two stages deserve early attention because they are where teams get hurt. Shipping needs a durable buffer — a filesystem-backed queue rather than memory only — or a five-minute Elasticsearch outage becomes five minutes of permanently missing logs. And parsing is far cheaper if the application emitted JSON in the first place: every stage downstream gets easier when the fields already exist.

Collectors and shippers: Filebeat, Fluentd, Fluent Bit, Alloy, Vector

The collector is the piece that runs everywhere, so its resource footprint matters more than its feature list. Filebeat is Elastic's Go-based shipper: light, reliable, tracks file offsets in a registry so a restart resumes where it stopped, and speaks natively to Elasticsearch or Logstash. Fluentd is the CNCF-graduated Ruby-based router with an enormous plugin ecosystem and a unified logging layer philosophy; it is flexible but heavier, in the tens of megabytes of memory. Fluent Bit is the same project's C rewrite aimed at edge and node duty — around a megabyte of memory, so it is now the default node agent even in stacks that still run Fluentd as a central aggregator.

On the Grafana side, Promtail was the Loki-native agent; it is now deprecated in favour of Grafana Alloy, a single OpenTelemetry-compatible collector for logs, metrics, traces and profiles — worth knowing because tutorials still say Promtail. Vector is the vendor-neutral option: a Rust collector with strong throughput, a real transformation language, and end-to-end acknowledgement, usually deployed in the agent-plus-aggregator topology. In interviews the useful framing is agent role versus aggregator role: the agent must be tiny and never fall over; the aggregator does the expensive parsing, fan-out and routing in one place you can scale independently.

The Kubernetes pattern: a DaemonSet collector with metadata enrichment

In Kubernetes the container runtime already writes every container's stdout to files under /var/log/pods on the node. So the standard pattern is a DaemonSet: exactly one collector pod per node, mounting that host path read-only, tailing every container's file. One agent covers every workload on the node regardless of language or framework, new pods are picked up automatically, and applications need no logging sidecar and no library change. The alternatives — a sidecar per pod, or shipping directly from the application over the network — cost far more resources or couple your code to the backend.

The stage that makes this pattern valuable is enrichment. A raw line from a node file is useless without provenance, so the collector calls the Kubernetes API and attaches namespace, pod name, container name, labels and annotations to every record. That is what lets you write namespace = "payments" AND level = "ERROR" instead of trying to recognise a pod by its log format. Two operational details worth remembering: the CRI log format wraps each line with a timestamp and a partial/full flag, so multi-line stack traces must be reassembled by the collector, and the node's log files are rotated by kubelet — if your collector falls behind rotation, you lose lines silently.

# Fluent Bit as a DaemonSet: tail node log files, then enrich from the Kubernetes API
[INPUT]
    Name              tail
    Path              /var/log/containers/*.log
    Parser            cri
    DB                /var/log/flb_kube.db   # offsets survive a restart
    Mem_Buf_Limit     5MB
    Skip_Long_Lines   On

[FILTER]
    Name                kubernetes
    Match               kube.*
    Merge_Log           On                   # parse embedded JSON into real fields
    Keep_Log            Off
    Labels              On
    Annotations         Off

ELK/EFK versus Grafana Loki: the choice, honestly

The two stacks differ on one decision, and everything else follows from it. Elasticsearch indexes the content: every log line is analysed into terms and written to an inverted index, so you can ask "find every line anywhere containing OOMKilled in the last day" and get an answer in seconds without knowing which service produced it. That capability is real and sometimes irreplaceable — aggregations, full-text relevance, arbitrary field queries. The price is also real: the index is often as large as or larger than the raw data, the cluster wants a lot of memory and fast disks, and shard and JVM management becomes somebody's part-time job.

Loki indexes only the labels — a small set of low-cardinality key/value pairs such as namespace, app, pod, level — and stores the log content itself as compressed chunks in object storage. The index is tiny, the storage is S3-priced, and operating it is closer to running a stateless service. The trade is explicit: Loki cannot do a fast content search across everything. A LogQL query first selects a label stream, then brute-force filters that stream, so a query with a narrow label selector and a short window is fast and a query with a wide selector over a week is slow. Loki suits you if your investigations start from "which service, which time window" — which, if you have decent alerts and tracing, they usually do.

Two things not to be blindsided by. Elastic relicensed Elasticsearch and Kibana away from Apache 2.0 in 2021, which triggered AWS's OpenSearch fork — still Apache 2.0, now under the Linux Foundation, and a drop-in destination for most log pipelines. Elastic later added AGPL as an option, so Elasticsearch is open source again by OSI's definition, but the fork is permanent and OpenSearch is what many managed offerings run. If you would rather not operate any of it, hosted options exist at every point on the spectrum: Elastic Cloud, Amazon OpenSearch Service, Grafana Cloud Logs, and the log products of Datadog, New Relic and Splunk.

Ingestion pipelines: grok, or just emit JSON

Somewhere in the pipeline a line of text has to become fields, because level, service, trace_id and duration_ms are what you filter and aggregate on. The classic answer is grok: a named library of regular expressions that pull fields out of unstructured lines. It works, it is well documented, and it is the right tool for logs you do not control — nginx, Postgres, a legacy application nobody will rebuild. It is also the wrong default for your own services: grok patterns are slow (regex over every line at ingest, and a failed match is a silent data-quality bug), and they break the day a developer reorders the log format.

The real answer, following straight on from module 02, is to emit JSON at the source so no parsing is needed. Then the pipeline's remaining jobs are cheap and additive: rename fields onto a shared schema (Elastic Common Schema is a good default — @timestamp, log.level, service.name, trace.id, error.stack_trace), coerce types so numbers stay numbers, drop fields you must never store, and enrich with environment, region and version. Standardising the schema across services is the unglamorous work that makes a cross-service query possible at all; OpenTelemetry's log data model is the vendor-neutral version of the same idea, and it is what carries trace_id into your logs.

# Logstash: grok only where you must, then normalise onto a shared schema
filter {
  if [service] == "nginx" {
    grok { match => { "message" => "%{COMBINEDAPACHELOG}" } }   # unstructured, not ours
  } else {
    json { source => "message" }                                # our services: already JSON
  }
  mutate { rename => { "lvl" => "log.level" } convert => { "duration_ms" => "integer" } }
  mutate { remove_field => [ "authorization", "card_number" ] }
}

The debugging workflow: from an alert or a trace id to the line that matters

Aggregation only pays off if you have a method. The productive one is funnel-shaped and always starts from a known anchor, never from a free-text search of everything. Anchor first: an alert firing on a service, an error-tracker fingerprint, a support ticket with a request id, or — best of all — a trace id. Then narrow in this order: time window (start with the fifteen minutes around the incident, not the last seven days), service and environment (label or field selectors, so the backend scans a fraction of the data), level (errors and warnings first), and only then content. Read the first error in the window, not the loudest one; the noisiest signal is usually a downstream consequence of a quieter earlier cause.

The multiplier here is correlation by trace id. If every service logs the trace and span id that module 02 put into the MDC, then one query — trace_id = "4bf92f3577b34da6" with no service filter — returns the complete story of a single request across every service it touched, in order. Wire the two directions together in your UI: Grafana's Loki data source uses derived fields to turn a trace id in a log line into a link to the trace, and Kibana links logs to APM traces the same way. Round it out with two habits: pin the exact time range and share the query URL in the incident channel rather than screenshots, and when you find the line you needed, ask whether the log that would have made it obvious in one step exists yet.

Query languages side by side: Lucene and KQL versus LogQL

In Kibana you have two. Lucene query syntax is the raw form — level:ERROR AND service:payments AND message:timeout*, with wildcards, fuzzy matching, ranges and boosting. KQL is the friendlier default: same field-and-value shape, better autocompletion, cleaner boolean and nested-field handling, and it hands the query to the Elasticsearch query DSL underneath. Because the content is indexed, a bare term search across everything is legitimate — expensive, but it will return.

LogQL is deliberately a different shape, and understanding it is the fastest way to understand Loki. Every query is two parts: a mandatory label selector in braces that picks the streams, then a chain of filter and parser expressions applied to those streams' contents. {namespace="payments", app="checkout"} |= "trace_id" | json | duration_ms > 500 reads as select, then filter, then parse, then filter again. Wrap it in an aggregation such as sum by (status) (rate({app="checkout"} |= "error" [5m])) and you have a metric derived from logs, queryable and alertable exactly like Prometheus data. The performance rule follows directly from the design: put every cheap constraint in the label selector, keep the time range short, and never label on anything high-cardinality such as user id or trace id, because each distinct label combination creates a separate stream.

# Kibana (KQL) — content is indexed, so a bare field match across services is fine
log.level : "ERROR" and service.name : "checkout" and message : *timeout*

# Loki (LogQL) — select streams by label FIRST, then filter the content
{namespace="payments", app="checkout", level="error"} |= "timeout" | json | duration_ms > 500

# Same shape, turned into an alertable metric
sum by (status) (rate({app="checkout"} | json | __error__="" [5m]))

Retention, tiers and the index-size problem

Start from the arithmetic, because it is the part candidates skip. Raw log volume is roughly events per second × bytes per event × seconds retained. In Elasticsearch you then add the index on top: with default dynamic mapping the indexed form is frequently comparable in size to the source, and replicas multiply the whole thing again — a replica count of one doubles it. Loki changes the equation rather than the arithmetic: the index is a small fraction of the data because it covers labels only, and the compressed chunks sit in object storage at roughly a tenth of the price of provisioned SSD.

Then apply tiering instead of one flat retention number. Elasticsearch's index lifecycle management moves an index through hot (fast disks, actively written and searched), warm (cheaper nodes, read-only), cold and frozen (searchable snapshots served straight from object storage, slow but queryable), and finally delete — with rollover triggered by age or size rather than a nightly cron. Loki does the same job with a compactor enforcing per-tenant and per-stream retention, plus an export path to your own bucket for long-term archive. Crucially, retention should be set per log class, not globally: audit and payment logs may be legally required for years, application debug logs are worthless after a week, access logs sit somewhere between. One global setting means you either pay archive prices for debug noise or delete the compliance evidence.

{ "policy": { "phases": {
  "hot":    { "actions": { "rollover": { "max_primary_shard_size": "50gb", "max_age": "1d" } } },
  "warm":   { "min_age": "7d",  "actions": { "shrink": { "number_of_shards": 1 }, "forcemerge": { "max_num_segments": 1 } } },
  "cold":   { "min_age": "30d", "actions": { "searchable_snapshot": { "snapshot_repository": "archive" } } },
  "delete": { "min_age": "90d", "actions": { "delete": {} } }
} } }

Volume control: sampling and dropping at the collector

Retention decides how long you keep data; the collector decides how much arrives in the first place, and that is the bigger lever. Log storage is routinely the largest single line in an observability bill — industry surveys repeatedly put logs at over half of total observability spend, and the bill tends to grow with deploy count and log statements rather than with revenue. Two structural facts make this fixable. Most log volume comes from a handful of chatty sources: health-check access logs, per-item loop logging, third-party library DEBUG output, and stack traces duplicated at every layer that catches and rethrows. And the vast majority of what you ingest is never read by anyone.

So put the filter as early as possible, at the node agent, where dropping a line costs nothing and shipping it costs everything downstream. Practical levers, roughly in order of payoff: drop health-check and readiness-probe lines outright; sample high-frequency success events (keep one in a hundred INFO lines from a hot path, keep all errors); throttle per-stream rates so one misbehaving pod cannot flood the cluster; truncate enormous fields such as full request bodies; and route by class — errors and audit events to the expensive indexed store, verbose debug to cheap object storage or nowhere. Do all of this in collector configuration rather than application code, so you can turn the tap back on during an incident without a deploy. And meter it: track ingested bytes per service as a first-class metric, otherwise the first person to notice the growth is Finance.

Interview questions

Log aggregation shows up in almost every DevOps-adjacent backend round in India, from service-company screens on "what is the ELK stack" to product-company design rounds where the real question is what your logging bill will look like at ten times the traffic:

Beginner What does ELK stand for, and what does each piece do?

Elasticsearch (distributed search and analytics engine — stores and indexes the logs), Logstash (ingestion pipeline — collects, parses, transforms, routes), Kibana (the UI — search, dashboards, visualisation). EFK swaps Logstash for Fluentd or Fluent Bit, which is the common choice in Kubernetes because the agent is far lighter. Beats, especially Filebeat, are the lightweight shippers that feed Logstash or Elasticsearch directly.

Beginner Why can't you just SSH into the server and tail the log file?

It stops working the moment there is more than one instance: a request hits one of N replicas and you do not know which, and N changes under autoscaling. In containers it is worse — the filesystem is ephemeral, so a crash-looping pod destroys its own evidence, and kubelet rotates and garbage-collects node log files anyway. And a request crossing six services leaves six partial stories on six machines. Centralization makes the logs outlive the process and searchable in one place.

Beginner Where should a containerised application write its logs?

To stdout and stderr, unbuffered, as a stream of structured events — the twelve-factor rule. The application should not open log files, rotate them or know the backend exists. The runtime captures the stream, a collector picks it up from the node, and the routing decision lives in the platform. That is what lets you replace ELK with Loki without touching application code.

Beginner Describe the stages of a log aggregation pipeline.

Emit (application writes structured lines to stdout), collect (an agent tails the node's container log files), ship (buffer and forward with retries and backpressure), parse and enrich (fields extracted, Kubernetes metadata attached), store and index (the backend writes it in its indexing model), query (Kibana or Grafana over the store). When logs go missing, the diagnosis is always "which of these six stages stopped".

Intermediate Fluentd versus Fluent Bit — when do you use each?

Same project, different roles. Fluentd is Ruby-based with a very large plugin ecosystem and a footprint in the tens of megabytes — good as a central aggregator doing heavy routing and transformation. Fluent Bit is the C rewrite, around a megabyte of memory, designed for the node or edge — good as the per-node DaemonSet agent. The common production shape is Fluent Bit everywhere as the agent, optionally forwarding to a Fluentd or Logstash aggregator tier that does the expensive work once.

Intermediate How is logging typically deployed in Kubernetes, and why that way?

A DaemonSet: one collector pod per node, mounting the host's container log directory read-only and tailing every container's file. It covers every workload on the node regardless of language, picks up new pods automatically, and needs no application change. The collector then calls the Kubernetes API to enrich each record with namespace, pod, container and labels. Sidecar-per-pod is the alternative when an application insists on writing to a file, but it multiplies resource cost by pod count.

Intermediate Grok versus emitting JSON — which do you prefer and why?

JSON at the source, every time you control the code. Grok is regex over every line at ingest: CPU-expensive, brittle when a developer reorders the message, and a failed match fails silently, so you get a data-quality bug rather than an error. Grok is the right tool for logs you cannot change — nginx, database servers, legacy applications. For your own services, structured emission means the pipeline only has to rename fields onto a shared schema, coerce types, drop secrets and enrich.

Intermediate A user reports a failed checkout. Walk me through finding the cause in a centralized log system.

Anchor on something known — the request id or trace id from the error response, or the failing alert. Narrow the time window to the minutes around it. Filter by service and environment using labels or indexed fields so the backend scans a fraction of the data. Filter to errors and warnings, and read the earliest error in the window rather than the loudest, since the noisy one is usually a downstream consequence. Then query by trace id with no service filter to get the whole cross-service story in order, and pivot to the trace itself via the derived-field link. Finally, ask whether a missing log line would have made this a one-step diagnosis.

Intermediate What is LogQL, and how is its shape different from a Kibana query?

LogQL is Loki's query language and it is always two stages: a mandatory label selector in braces that picks the streams, then filter and parser expressions applied to those streams' content — for example {namespace="payments", app="checkout"} |= "timeout" | json | duration_ms > 500. Kibana's KQL or Lucene query goes straight at the inverted index, so a bare content match across everything is a legitimate query. In Loki that same query has no label selector to narrow on, so it degenerates into a brute-force scan. LogQL also wraps into aggregations such as rate(...), giving you Prometheus-style metrics and alerts derived from logs.

Pro ELK versus Grafana Loki — how do you choose?

The whole difference is what gets indexed. Elasticsearch builds an inverted index over the log content, so any term is findable fast anywhere without knowing the source, and you get aggregations and full-text relevance — at the cost of an index frequently comparable in size to the raw data, high memory and fast-disk requirements, replica multiplication, and real operational work in shards and JVM tuning. Loki indexes only a small set of low-cardinality labels and keeps compressed content in object storage, so it is dramatically cheaper and close to stateless to run, but queries must start from a label selector and time window; wide searches over long windows are slow. Choose Loki when investigations start from a known service and time — which they do if your alerting and tracing are decent — and when cost or operational headcount is the binding constraint. Choose Elasticsearch or OpenSearch when arbitrary content search, aggregation and analytics over logs are genuinely part of the product or the compliance requirement. Many organisations run both: Loki for volume, an indexed store for the small high-value subset.

Pro Your log storage bill has become the largest line in the observability budget. What do you do?

Measure first: ingested bytes per service and per log class, so you find the handful of chatty sources — health-check access logs, per-item loop logging, library DEBUG output, stack traces duplicated at every rethrow — that usually dominate. Then cut at the collector, not in application code, so it is reversible during an incident without a deploy: drop probe traffic, sample high-frequency success events while keeping all errors, throttle per-stream rates, truncate huge fields. Next, set retention per log class rather than globally — audit and payment logs for years, application debug for days — and tier the rest through hot, warm, cold and searchable-snapshot phases so old data lives in object storage instead of on provisioned SSD. Structurally, consider moving bulk volume to a label-indexed store like Loki and keeping only the high-value subset in an indexed one, and check whether a metric or a trace would answer the question the log was there to answer. Finally, drop replica counts on non-critical indices and revisit dynamic mapping, which quietly indexes fields nobody queries.

Pro Why is high-cardinality labelling catastrophic in Loki, and what is the equivalent trap in Elasticsearch?

In Loki each distinct combination of label values is a separate stream with its own chunks and index entries. Adding user_id or trace_id as a label creates millions of streams, exploding the index Loki exists to keep small, fragmenting chunks into tiny inefficient objects, and pushing ingesters into memory pressure. Keep such values inside the log line where a filter or the json parser can reach them at query time. The Elasticsearch equivalent is mapping explosion: dynamic mapping turns every new JSON key into an indexed field, so unbounded key names blow up the cluster state and the field count limit. The fixes are the mirror image — fixed label sets in Loki, explicit mappings or a strict dynamic policy in Elasticsearch.

Pro Elasticsearch was relicensed and OpenSearch forked. Why should an engineer care?

Elastic moved Elasticsearch and Kibana off Apache 2.0 to SSPL and the Elastic Licence in 2021 to stop cloud providers reselling them; AWS forked the last Apache-licensed release as OpenSearch, which is now under the Linux Foundation. Elastic later added AGPL as an option, so Elasticsearch qualifies as open source again, but the fork did not go away. Practically: the two have diverged in features, client libraries and version numbers, so "Elasticsearch client" and "OpenSearch client" are not interchangeable past a point; managed services differ in which one they actually run; and if your organisation has a licence policy, this is the question it will ask. The pipeline in front is mostly portable either way, which is another argument for keeping the application ignorant of the backend.

Pro Logs stopped arriving for one service while others are fine. How do you debug the pipeline?

Walk the six stages. Is the application still writing to stdout — exec into the pod and check, and confirm it did not switch to a file or block on a full buffer. Is the node agent tailing that path — check its own logs and metrics for the file, and whether the offset registry is stuck after a rotation it missed. Is shipping backed up — look at the agent's buffer and retry metrics; a full filesystem buffer usually means the backend is rejecting writes. Is parsing dropping records — a grok failure or a mapping conflict makes the backend refuse documents while everything upstream looks healthy, which is why an on-failure path that stores the raw line matters. Is the backend rejecting or rate limiting — check ingest rejection counts and per-tenant limits. Only then suspect the query: a wrong time zone, a stale index pattern or a label that changed name looks exactly like missing data.
