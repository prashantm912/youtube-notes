Module: Dashboards with Grafana

Most dashboards are wall art — dense, colourful, and no help whatsoever at two in the morning. This module teaches the design first and the tool second, because a beautiful board that answers no question is worse than no board at all.

Knowledge Library → Courses → Observability track → Dashboards with Grafana

What this module covers

Grafana is easy to learn and easy to abuse. Give a team a data source and within a month they have forty panels on one board, three different time ranges, four unit systems and a wall of sparklines nobody reads. The skill worth having is not "can you build a panel" — it is "can you build the board that shortens an incident".

The first half of this module is design: the question a dashboard exists to answer, the three distinct audiences that need three distinct boards, the layout rules that make a board readable in ten seconds, and how to pick a visualization deliberately rather than by whichever one looks nicest. The second half is Grafana mechanics — data sources, panels and transformations, template variables and repeats, annotations, alert visualization, and finally dashboards as code, because a board clicked together by hand is unversioned production configuration.

Topics

Start from the question: what a dashboard is for

Every good dashboard is the answer to a question somebody actually asks. "Is the checkout service healthy right now?" is a question. "Show me everything we collect about checkout" is not — it is a data dump wearing a dashboard costume. Before you add the first panel, write the question down, then judge every panel by whether it helps answer it. Panels that fail that test are not neutral: they cost screen space, they cost attention, and during an incident they cost minutes.

The corollary is that one board cannot serve everybody, because there are three audiences with three different questions. The service health board answers "is it broken?" — the RED signals (rate, errors, duration) for each service, a handful of panels, readable at a glance from across the room, and it should be the board on the wall and the first link in the runbook. The drill-down diagnostic board answers "why is it broken?" — dense by design, per-instance breakdowns, dependency latency, saturation, queue depths, the things you only look at once you already know something is wrong. The business or executive board answers "what is it costing us?" — orders per minute, signups, revenue, conversion, over hours and days rather than seconds. Mixing the three produces a board that serves none of them.

Layout rules that survive an incident

Reading a dashboard is visual work, and the eye follows a predictable path. Put the single most important signal top-left, because that is where attention lands first — usually error rate or availability for the service the board is named after. Keep a health board to one screen where you possibly can: scrolling hides exactly the panel you needed, and a board that requires scrolling has usually stopped being a health board and become a diagnostic one. Then order the remaining panels to follow the diagnostic path a human would actually take — symptoms at the top (user-visible errors and latency), causes below (dependency latency, database saturation, JVM memory, queue lag), so that scanning down the page is the same motion as reasoning about the outage.

Consistency is what makes a board readable rather than merely populated. Use one time range for the whole board, so two panels side by side are always comparable. Set units explicitly on every panel — seconds, bytes, requests per second — because an unlabelled axis reading "1.4" is not information. Set the axis minimum to zero wherever the absolute magnitude matters: an auto-scaled y-axis makes a wobble between 99.4% and 99.5% look like a cliff, which is how teams learn to ignore their own graphs. Give panels titles that state the signal and the unit, add a panel description explaining what "good" looks like, and above all prefer six panels whose meaning you can explain to sixty that you cannot.

Choosing the visualization: trends versus current values

Panel choice is a decision, not a decoration. Use a time series whenever the shape over time is the point — request rate, error rate, latency percentiles, saturation. It is the default for a reason: humans read trends and inflection points far more reliably than numbers, and "when did this start?" is the most common question a dashboard is asked. Use a stat panel when a single current number is the answer — current error budget remaining, pods ready, requests per second right now — and a gauge only when the value is genuinely bounded and the position within that range means something, such as disk used out of total or a quota consumed. A gauge on an unbounded value like requests per second is meaningless; there is no "full".

Two habits separate a useful board from a noisy one. First, mixing panel types costs the reader cognitive effort — every new visual encoding must be decoded — so limit yourself to a small vocabulary and reuse it. Second, remember that a single number hides its own history: a stat panel showing "0.4% errors" is fine on a health board precisely because the time series next to it shows whether that 0.4% is steady or the leading edge of an incident.

Comparisons and distributions: bar gauge, heatmap, table — and why not a pie chart

When the question is "which of these is worst?", use a bar gauge: it puts one bar per instance, pod, region or endpoint side by side against a shared scale, and the outlier is obvious without reading a legend. When the question is "what is the shape of latency?", use a heatmap — and this is the single most valuable visualization swap most teams have never made. An average latency line is a lie by construction: if 95% of requests take 20 milliseconds and 5% take four seconds, the mean is a comfortable-looking number that describes nobody's experience. A heatmap renders the full distribution over time as colour density, so a bimodal split, a slow cohort, or a second band appearing after a deploy is visible immediately. (A histogram panel does the same job for a single point in time; the heatmap adds the time axis.) Use a table for top-N answers — slowest endpoints, noisiest tenants, top error messages — where the value is the ranked list itself.

And the honest warning: pie charts are almost never right for telemetry. They encode magnitude as angle, which humans compare poorly; they collapse the time dimension entirely, which is the dimension that matters in an incident; they degrade into unreadable slivers past about five categories; and they cannot show a value going up. Grafana ships one because business dashboards occasionally want a share-of-total snapshot, but on a service board a bar gauge or a table beats it every time.

Thresholds, colour and legends: encoding meaning, not decoration

Colour on a dashboard should carry information. A threshold turns a raw number into a judgement — green below the SLO burn rate, amber approaching it, red past it — so the reader does not have to remember whether 240 milliseconds is acceptable for this endpoint. Set thresholds from the actual objective rather than round numbers, apply them consistently across the board so that red always means the same severity, and never rely on colour alone: pair it with a value, a label or a shape, because a meaningful fraction of your readers are colour-blind and a red-versus-green-only board is invisible to them.

Two settings do most of the remaining work. Standard options carry the unit, the decimal places and the min/max — this is where you set seconds versus milliseconds and pin the axis minimum to zero. Value mappings translate raw values into words, so a state gauge reads "Degraded" instead of "2", which removes an entire class of "what does 2 mean?" questions during an incident. Finally, fix the legend: an auto-generated legend reading {job="api", instance="10.4.2.19:8080", pod="api-7d9f"} is noise. Use a legend format that names the one thing that varies ({{pod}}), switch the legend to table mode with last/max/mean values when you are comparing series, and hide it entirely on a stat-style panel where it adds nothing.

# RED signals for one service — the three queries a health board is built from
sum(rate(http_server_requests_seconds_count{app="checkout"}[5m]))                     # rate
sum(rate(http_server_requests_seconds_count{app="checkout",status=~"5.."}[5m]))
  / sum(rate(http_server_requests_seconds_count{app="checkout"}[5m]))                 # errors (ratio)
histogram_quantile(0.99,
  sum by (le) (rate(http_server_requests_seconds_bucket{app="checkout"}[5m])))        # duration (p99)

# Legend format: {{pod}}   Unit: seconds (s)   Axis min: 0   Threshold: red above 0.5

Data sources: Prometheus, Loki, Tempo and mixed sources on one board

Grafana stores no telemetry of its own. It is a query and rendering layer over data sources you configure, each with a type, a URL, credentials and a unique identifier that dashboards reference. In a typical Grafana-stack estate that means three: Prometheus (or Mimir) for metrics queried with PromQL, Loki for logs queried with LogQL, and Tempo for traces queried with TraceQL — the same three pillars from module 01, now with one front end over all of them.

The feature that makes this more than a convenience is the mixed data source: a single panel can carry queries against different data sources at once, so an error-rate line from Prometheus and a count of matching log lines from Loki share one time axis. That is where a board stops being three separate tools and starts being an investigation surface — you see the error rate rise, and the log volume rise with it, on the same graph, without changing tabs. Two practical rules: always reference data sources through a data source variable rather than a hard-coded identifier, or the dashboard will not port between staging and production; and remember that every panel is a live query, so an unbounded query on a 30-day range is a way to take down your own metrics backend.

Building a panel: queries, transformations and the inspector

A panel is a query plus a visualization plus a set of field options. Each panel holds one or more queries (labelled A, B, C) against its data source, and the query editor offers both a builder and raw code — learn the raw mode, because PromQL and LogQL written by hand are far more precise than anything a builder will produce, and every real interview asks you to write the query, not to describe the buttons.

Transformations are the step most people never discover, and they solve the problems that otherwise get solved badly in the query. They reshape the query result before it reaches the visualization: join two queries on a shared field so a table can show request rate and error rate per endpoint side by side, filter fields by name, rename series for a readable legend, compute a new field as the ratio of two others, group by a label and aggregate, or reduce a time series to a single row for a table. Use them for presentation concerns and keep the query itself about the data. When a panel renders something you did not expect, open the panel inspector: it shows the raw data frames, the exact query Grafana sent, the response, and the request timing — which is how you find out that your legend is empty because the label you referenced does not exist on those series.

Template variables: one dashboard instead of forty

A template variable turns a hard-coded value in a query into a dropdown at the top of the board. Instead of one dashboard per service, you build one dashboard with a $service variable, and the same board serves every service in the estate. This is the difference between a Grafana instance with twelve dashboards and one with four hundred, and it is the highest-leverage thing you can learn about the tool.

The workhorse is the query variable, whose options come from the data source itself — typically label_values(up, job) against Prometheus — so new services appear in the dropdown automatically the day they start reporting. Set multi-value to select several at once (Grafana interpolates them into a regex, which is why the query must use =~"$service" rather than ="$service") and add an All option for the estate-wide view. Then chain them: define $namespace first, and make the $pod variable's query depend on it, so choosing a namespace narrows the pod list instead of showing you every pod in the cluster. Other useful types are the interval variable (a rate window you can widen when zooming out), the custom variable (a fixed list), the textbox, and the data source variable that lets one board point at staging or production. Finally, repeats close the loop: set a row or panel to repeat over a multi-value variable and Grafana renders one copy per selected value — pick five pods and you get five identical latency panels, generated, not copy-pasted.

$namespace  query   label_values(kube_pod_info, namespace)
$pod        query   label_values(kube_pod_info{namespace="$namespace"}, pod)   # chained
$interval   interval  1m,5m,15m,1h
$datasource datasource  type: prometheus

# Panel query — note =~ because $pod may be multi-value or "All"
sum by (pod) (rate(container_cpu_usage_seconds_total{namespace="$namespace", pod=~"$pod"}[$interval]))

# Row option: "Repeat for" -> $pod   => one row rendered per selected pod

Annotations and alert visualization: putting events on the time axis

An annotation is a marker drawn on the time axis of every panel that opts into it — a vertical line for a point event, a shaded region for a window. The single highest-value use is marking deployments: wire your CD pipeline to post an annotation to the Grafana HTTP API on every release, and from then on "did this regression start at a release?" is answered by looking, not by cross-referencing a deploy log against a graph. The same technique works for feature-flag flips, config changes, database migrations, scheduled batch jobs and declared incidents. Annotations can be added manually by dragging on a graph (useful during an incident to mark "mitigation applied"), fetched from a data source query, or driven by alert state changes.

Grafana's unified alerting then puts alert state onto the board itself: a Grafana-managed alert rule evaluates a query on a schedule, moves through pending and firing states, and its state history can be rendered as annotations on the panel it came from, so the graph shows both the metric and the moments it was judged unacceptable. At awareness level that is what you need here — alert rules, evaluation groups and the pending period, contact points and notification policies, and the fact that Grafana can either own the rules itself or read them from a Prometheus/Alertmanager it is pointed at. The serious treatment — SLIs, SLOs, error budgets, symptom-based alerting, burn-rate rules and the discipline that stops alert fatigue — is module 08, and it is a design problem more than a Grafana problem.

Dashboards as code: the JSON model, provisioning and Terraform

Every Grafana dashboard is a JSON document — panels, queries, variables, thresholds, layout, the lot — and the UI is simply an editor for it. Once you see that, the problem with hand-built dashboards is obvious: a board clicked together in the browser is production configuration that lives in one database, has no review history, cannot be diffed, cannot be rolled back, and disappears when somebody deletes it. Nobody would accept that for a Kubernetes manifest; a dashboard deserves the same treatment.

There are several routes and they layer. File provisioning is the simplest: point Grafana at a directory of dashboard JSON files (and data source YAML) via a provisioning config, ship them in the image or a ConfigMap, and Grafana loads them at startup — the boards become read-only in the UI, which is the point. The Grafana Terraform provider manages dashboards, folders, data sources, alert rules, teams and permissions as Terraform resources, which is the natural fit if your platform is already Terraform-managed and gives you plan/apply review on dashboard changes. Grizzly is a purpose-built CLI for pushing dashboard definitions (including Jsonnet/Grafonnet-generated ones) to an instance, and the Grafana Operator does the same job Kubernetes-natively via custom resources. Newer Grafana releases fold all of this under "observability as code", including Git-backed dashboard storage. Whichever you choose, the rule is the same: generate rather than duplicate — a Jsonnet or Terraform module that emits the standard RED board for any service beats forty hand-copied JSON files that have quietly drifted apart.

# /etc/grafana/provisioning/dashboards/services.yaml
apiVersion: 1
providers:
  - name: service-boards
    folder: Services
    type: file
    disableDeletion: true         # UI cannot delete a provisioned board
    allowUiUpdates: false         # edits must go through git
    options:
      path: /var/lib/grafana/dashboards
      foldersFromFilesStructure: true
resource "grafana_folder" "services" {
  title = "Services"
}

resource "grafana_dashboard" "checkout" {
  folder      = grafana_folder.services.id
  config_json = file("${path.module}/dashboards/checkout-red.json")
  overwrite   = true
}

Exemplars: from a metric spike to the actual trace

The last step ties the three pillars together on one board. An exemplar is a trace identifier attached to a specific metric observation — Prometheus stores it alongside a histogram bucket sample, and Grafana renders it as a small diamond on the time series. Click the diamond and you jump straight to the trace in Tempo for one of the actual slow requests behind that latency spike. This is the moment observability stops being three tools and starts being one workflow: the metric tells you that the p99 doubled at 40 minutes past the hour, and the exemplar hands you a concrete request to explain why.

The wiring is modest. The application must emit exemplars (Micrometer does this when a tracer is on the classpath), Prometheus must be started with the exemplar storage feature enabled and be scraping in a format that carries them, and the Grafana Prometheus data source needs its exemplar configuration pointed at the trace data source. Alongside exemplars, learn data links — arbitrary links from a panel value into another dashboard or an external system, with variables interpolated — and correlations, which generalise the same idea across data sources. Between them these are what turn a board from a status display into the first step of an investigation, which is where this module started: the dashboard exists to answer a question, and the best dashboards hand you the next question too.

Interview questions

Dashboard questions come up in almost every SRE, DevOps and senior-backend round in India, and they are unusually revealing — most candidates can build a panel, far fewer can explain why a board is designed the way it is:

Beginner What is Grafana, and where does it store its data?

Grafana is a visualization and query front end. It stores no telemetry of its own — only its own configuration (dashboards, users, data sources, alert rules) in a small internal database. Every panel is a live query executed against a configured data source such as Prometheus, Loki, Tempo, Elasticsearch or a SQL database.

Beginner Which panels would you put on a service health dashboard?

The RED signals for the service: request rate, error rate (as a ratio, not a raw count), and duration as percentiles rather than an average — plus availability or SLO burn as a stat panel. Half a dozen panels, one screen, most important signal top-left, readable in about ten seconds. Everything else belongs on a separate drill-down board.

Beginner What is a template variable and why would you use one?

A dropdown at the top of a dashboard that substitutes a value into panel queries. It lets one dashboard serve every service, namespace or environment instead of one dashboard per instance. The usual form is a query variable whose options come from the data source, for example label_values(up, job) in Prometheus, so new targets appear in the dropdown automatically.

Beginner What is an annotation in Grafana?

An event marker drawn on the time axis of a panel — a vertical line for a point in time, a shaded band for a window. The classic use is marking deployments from the CD pipeline via the Grafana HTTP API, so you can see whether a regression started at a release. Annotations can also be added by hand, queried from a data source, or generated from alert state changes.

Intermediate Why is a heatmap better than an average latency line?

An average hides the distribution. If most requests take 20 milliseconds and a small tail takes several seconds, the mean looks healthy and describes nobody's actual experience. A heatmap renders the whole bucket distribution over time as colour density, so a bimodal split, a slow cohort, or a new slow band appearing after a deploy is immediately visible. If you must use a line chart, plot percentiles — p50, p90, p99 — never the mean.

Intermediate When is a gauge the wrong panel, and when is a pie chart?

A gauge only makes sense for a bounded quantity where position within the range has meaning — disk used of total, quota consumed. On an unbounded value such as requests per second there is no "full", so the needle means nothing. A pie chart is almost always wrong for telemetry: it encodes magnitude as angle (which people compare badly), throws away the time dimension entirely, and becomes unreadable past a handful of categories. Use a bar gauge for comparison and a table for top-N.

Intermediate How do chained variables work, and why do multi-value variables need =~?

Chaining means one variable's query references another: define $namespace from label_values(kube_pod_info, namespace), then define $pod as label_values(kube_pod_info{namespace="$namespace"}, pod), so choosing a namespace filters the pod list. For multi-value or "All" selections Grafana interpolates the values as a regex alternation, so the panel query must use a regex matcher — pod=~"$pod". An equality matcher silently returns nothing as soon as more than one value is selected.

Intermediate What are Grafana transformations, and when do you use one instead of changing the query?

Transformations reshape the query result before it is visualized — join queries on a field, filter or rename fields, compute a new field such as a ratio, group and aggregate, or reduce a series to a single value for a table. Use them for presentation concerns that the data source cannot or should not express, such as joining two different data sources into one table. Keep the query itself about selecting data; anything you can express cleanly in PromQL usually belongs there.

Intermediate Your dashboard shows five different unit systems and each panel a different time range. Why is that a problem?

It destroys comparability, which is the entire value of putting panels next to each other. Two graphs side by side over different windows invite a false conclusion; an unlabelled axis reading "1.4" is not information. Use one dashboard time range, set explicit units on every panel, and pin axis minimums to zero where absolute magnitude matters — an auto-scaled axis makes a change from 99.4% to 99.5% look like a collapse.

Pro Design the dashboard set for a payments platform with twelve microservices.

Three tiers, not twelve boards. One estate-level health board with a compact RED row per service (repeated over a $service variable) showing rate, error ratio and p99 — the wall board and the first runbook link. One templated per-service drill-down board, built once and reused for every service through variables, carrying per-instance breakdowns, dependency latency, connection pools, JVM and queue lag, ordered symptoms-first. One business board for settlement volume, success rate by payment method and revenue over days. All of them defined as code, generated from a shared module, with deployment annotations wired in from the pipeline.

Pro What does "dashboards as code" mean, and what are the options on Grafana?

A dashboard is a JSON document, so it should be reviewed, versioned and deployed like any other config rather than clicked together and lost. Options: file provisioning (a provisioning config pointing at a directory of JSON, shipped in the image or a ConfigMap, with allowUiUpdates: false so edits must go through git); the Grafana Terraform provider for dashboards, folders, data sources and alert rules with plan/apply review; Grizzly as a purpose-built push CLI; the Grafana Operator for Kubernetes custom resources; and Jsonnet or Grafonnet to generate boards from a template. The real prize is generation — one module that emits the standard board for any service, instead of forty copies that drift.

Pro What are exemplars and how do you wire them up end to end?

An exemplar is a trace id attached to an individual metric observation, stored next to a histogram bucket sample and rendered by Grafana as a clickable diamond on the time series — clicking it opens that exact trace in Tempo or Jaeger. Wiring: the application emits exemplars (Micrometer does so when a tracer is present), Prometheus runs with exemplar storage enabled and scrapes a format that carries them, and the Grafana Prometheus data source has its exemplar config pointed at the trace data source. The payoff is going from "the p99 doubled" to one concrete slow request in a single click.

Pro Your Grafana instance has 400 dashboards and on-call still cannot find anything. What do you do?

That is a symptom of hand-built, per-service boards. Fix it structurally: consolidate to templated boards driven by variables so one board covers a class of services; delete or archive anything not referenced by a runbook or opened in the last quarter; move the survivors into code with folder and permission structure so creation goes through review; establish a naming convention and a single entry-point board that links onward; and put the correct board's link directly in each alert's annotations so on-call never has to search at all.

Pro A dashboard is slow to load and your Prometheus is struggling when it is open. Diagnose it.

Every panel is a live query, so a board is a query multiplier. Open the panel inspector to see the actual queries and their timings. Usual causes: too many panels each running a heavy query; long default time ranges with a fine step so millions of samples are scanned; high-cardinality label selectors or an "All" variable expanding to thousands of series; regex matchers that cannot use an index; and no recording rules for expensive expressions. Fixes: precompute with recording rules, reduce the default range, cap variable selections, cut panel count, raise the minimum interval, and cache at the query front end.

Pro How should colour be used on a dashboard, and what is the accessibility trap?

Colour should encode meaning, not decorate. Drive it from thresholds tied to the actual objective so green, amber and red mean the same severity on every panel, and keep the rest of the palette muted so the salient colour genuinely draws the eye. The trap is relying on colour alone: red-versus-green is invisible to a significant share of readers, so always pair it with the value, a text label or a value mapping such as "Degraded", and prefer a palette that also differs in lightness.
