Module: Logging Done Properly

Logs are the telemetry every team already has and almost nobody designs. This module turns log output from a stream of English sentences into a queryable data set, and then makes Logback emit it efficiently enough to survive production traffic.

Knowledge Library → Courses → Observability track → Logging Done Properly

What this module covers

Metrics and traces get designed; logs get written by whoever was debugging that method at the time. The result is the estate most engineers actually live with: gigabytes a day of string-concatenated prose that no query engine can filter, half of it at INFO, some of it containing an access token, and none of it carrying the request id that would let you reconstruct a single user's journey.

The first half of this module is discipline that is independent of any library: a log line is a data record, not a sentence; levels mean specific operational things; exceptions are logged once, at the boundary; per-request context lives in the MDC; and a defined set of values must never reach a log file at all. The second half is Logback specifically on Spring Boot 3.x/4.x — logback-spring.xml, appenders and encoders, JSON output, async appenders, and the rate limiting that stops one hot loop from flooding the whole pipeline.

Topics

Structured logging: a log line is a data record, not a sentence

The default habit is to write a log line for a human reading a terminal. In production nobody reads a terminal — a shipper collects the line, an aggregator indexes it, and an engineer queries it three weeks later at two in the morning. A sentence such as Order 91823 for user 4471 failed after 2 retries is fine for the terminal and useless for the query engine: to find "all failed orders for tenant X in the last hour" you need a fragile regular expression over free text, and every developer phrases their sentence differently. Structured logging emits the same event as a record with stable field names, so the query becomes a field comparison instead of a text search.

Two rules make structured logs pay off. First, field names must be stable across services — pick a schema (Elastic Common Schema is the widely used one, or your own documented set) so user.id means the same thing everywhere, rather than userId here and user_id there. Second, put values in fields, not in the message: keep the message a short constant describing the event, and attach the varying data as key-value pairs. A constant message is itself a groupable field — you can count occurrences of one event type without normalising ten phrasings of it.

// Unstructured — one sentence, ungroupable, unfilterable
Order 91823 for user 4471 failed after 2 retries: connect timeout

// Structured — the same event as a record a query engine can filter and aggregate
{"@timestamp":"2026-07-25T11-22-30.145Z","log.level":"ERROR","message":"order.submit.failed",
 "order.id":"91823","user.id":"4471","tenant":"acme","retry.count":2,
 "error.type":"java.net.SocketTimeoutException","trace.id":"4bf92f3577b34da6"}

Level discipline, and logging an exception exactly once

"Everything is INFO" is the normal failure mode, and it destroys the one cheap filter logs give you. Assign each level an operational meaning and hold the line: ERROR means a human must act — it is an alertable condition, so if nobody would be paged for it, it is not an ERROR. WARN means something is degraded or a fallback fired, worth reading in the morning but not worth waking anyone. INFO is the business narrative — the small set of events that describe what the system did (order accepted, payment captured, job completed), one or two per request, not per loop iteration. DEBUG is for development and for a temporary production bump when you are chasing something. TRACE is for desperation: payload dumps and per-iteration detail you would never leave enabled.

The companion rule is that an exception is logged once, at the boundary where you actually handle it — a controller advice, a message-listener error handler, a scheduled-job wrapper. The common anti-pattern is catch, log, rethrow at every layer, which turns one failure into four stack traces at four levels of the call stack; on-call then has to work out whether the service failed four times or once. Either handle it and log it, or add context and rethrow without logging. When you do log it, pass the throwable as the last argument so SLF4J prints the stack trace — log.error("order.submit.failed", ex), not log.error("failed: " + ex.getMessage()), which throws away the cause chain that usually holds the actual reason.

Parameterized logging and the SLF4J façade

SLF4J is the façade you compile against; Logback is the implementation Spring Boot wires in behind it (Log4j2 can be swapped in without touching a line of application code — that separation is the whole point of the façade). Always inject the logger through SLF4J's LoggerFactory, never through a Logback class, or you have hard-wired the implementation into your business code.

Write every call in parameterized form: log.info("order.submitted user={} order={}", userId, orderId). String concatenation builds the full message eagerly, before the logger has decided whether that level is even enabled, so a DEBUG line in a hot loop costs you string building on every iteration in production where DEBUG is off. The {} placeholder defers formatting until the framework knows the event will actually be written. That is also why the old guard clause if (log.isDebugEnabled()) is unnecessary around a parameterized call — the only case where it still earns its keep is when computing an argument is expensive (serialising an object graph, a database round trip), because argument evaluation happens before the call regardless. Parameterized calls also give structure for free: the constant message is a stable grouping key, and JSON encoders can capture the arguments as fields instead of smearing them into text.

private static final Logger log = LoggerFactory.getLogger(OrderService.class);

log.debug("cart.priced items=" + items.size() + " total=" + total);   // eager concat, always paid
log.debug("cart.priced items={} total={}", items.size(), total);       // deferred, free when DEBUG off

if (log.isTraceEnabled()) {                    // guard only when the ARGUMENT is expensive
    log.trace("cart.dump payload={}", serialiseWholeGraph(cart));
}
log.error("order.submit.failed order={}", orderId, ex);   // trailing throwable prints the stack trace

MDC, correlation ids, and the thread-pool pitfall

Mapped Diagnostic Context is a per-thread map that the logging framework merges into every line that thread writes. Populate it once at the edge of a request — trace id, span id, user id, tenant, request id — and every subsequent line, from the controller down to the repository, carries that context without a single method signature changing. That is what makes a log searchable by journey: trace.id = "4bf92f35…" returns every line from every layer of one request, in order, instead of forty unrelated lines interleaved with other users' traffic. On Spring Boot 3.x with Micrometer Tracing the trace and span ids are put into the MDC for you and appear in the default log pattern; you add your own domain keys (tenant, order id) on top.

The pitfall that gets asked in interviews: MDC is backed by a ThreadLocal, so it does not follow work onto another thread. Hand a task to an @Async method, a CompletableFuture, an executor or a parallel stream and the new thread's MDC is empty — the correlation id vanishes exactly where you needed it most. Fixes: capture MDC.getCopyOfContextMap() before submitting and restore it inside the task (a decorating Executor or Spring's TaskDecorator does this once for the whole application), and propagate the ids across service boundaries as HTTP headers or message headers so downstream services join the same trace. Equally important is cleanup: always clear the MDC in a finally block or a servlet filter, because pooled threads are reused and a leftover user id will silently contaminate the next request's logs.

// Edge: populate once, ALWAYS clear — pooled threads are reused
try {
    MDC.put("trace.id", traceId);
    MDC.put("tenant", tenant);
    chain.doFilter(request, response);
} finally {
    MDC.clear();
}

// Crossing a thread boundary: MDC is a ThreadLocal, so carry it yourself
Map<String, String> ctx = MDC.getCopyOfContextMap();
executor.submit(() -> {
    if (ctx != null) MDC.setContextMap(ctx);
    try { doWork(); } finally { MDC.clear(); }
});

What must never be logged, and how to mask what slips through

Treat the log pipeline as a system that copies data to third parties and keeps it for years. Logs are shipped to a hosted aggregator, indexed on machines you do not own, replicated into backups, and read by support engineers, contractors and anyone with dashboard access. So the list of values that must never enter it is short and absolute: passwords and password hashes, session tokens, JWTs, API keys and secrets, full card numbers (PAN), CVV, OTPs, Aadhaar and PAN-card style national identifiers, bank account numbers, and health data. Personal data under GDPR or India's DPDP Act is not banned outright, but it is subject to purpose limitation and storage limitation — an unbounded log retention full of email addresses and phone numbers is a compliance problem that nobody budgeted for.

The two habits that leak most are dumping whole request or response bodies at DEBUG (login payloads, payment payloads, tokens in headers) and calling toString() on an entity whose Lombok-generated @ToString happily includes every field. Defend in layers: exclude sensitive fields from toString at the source, log identifiers rather than objects, mask at the encoder with a Logback replacement or a custom converter so anything that does slip through is redacted before it hits disk, and never log a raw Authorization header. Also remember the injection angle — an unvalidated newline in user input can forge a whole extra log line, which is why OWASP treats log neutralisation as a security control rather than a formatting nicety.

logback-spring.xml: configuration, per-logger levels, additivity and profiles

Spring Boot picks up either logback.xml or logback-spring.xml from the classpath, and the choice matters. Plain logback.xml is read by Logback directly, very early, before Spring's environment exists — so none of Boot's extensions work in it. Name the file logback-spring.xml and Boot loads it through its own initialiser, which unlocks <springProfile> (profile-conditional blocks) and <springProperty> (values pulled from the Spring Environment, so the application name or an environment tag can be injected into the log pattern). That is the difference that lets one file emit human-readable colourised lines on a developer laptop and single-line JSON in production.

Inside the file, levels are set per logger and inherit down the package hierarchy: <logger name="com.acme.order" level="DEBUG"/> applies to every class under that package, while the root logger catches everything else. Turning a chatty framework down — Hibernate SQL, an HTTP client's wire log — is a one-line change here, and for simple cases you do not need the XML at all: logging.level.com.acme.order=DEBUG in application.yml does the same thing. The property that trips people up is additivity: by default a logger's events are also passed to its ancestors' appenders, so attaching a file appender to com.acme.audit without setting additivity="false" writes every audit line twice — once to the audit file, once to the root's console.

<configuration>
  <springProperty scope="context" name="appName" source="spring.application.name"/>

  <springProfile name="local">                <!-- humans read this one -->
    <root level="INFO"><appender-ref ref="CONSOLE"/></root>
  </springProfile>

  <springProfile name="prod">                 <!-- machines read this one -->
    <root level="INFO"><appender-ref ref="JSON"/></root>
  </springProfile>

  <logger name="com.acme.order" level="DEBUG"/>
  <logger name="org.hibernate.SQL" level="WARN"/>
  <logger name="com.acme.audit" level="INFO" additivity="false">  <!-- or it logs twice -->
    <appender-ref ref="AUDIT_FILE"/>
  </logger>
</configuration>

Appenders: console, rolling files, and the layout that formats them

An appender is the destination. ConsoleAppender writes to stdout — which is the correct and usually the only destination in a container, because the platform (Docker, Kubernetes, a log shipper as a sidecar) is what collects stdout; writing to a file inside a pod means your logs die with the pod and your disk fills up in the meantime. RollingFileAppender still matters for VM deployments and for a separate audit trail, and it is always paired with a rolling policy: TimeBasedRollingPolicy rotates by date, SizeAndTimeBasedRollingPolicy adds a per-file size cap, and maxHistory plus totalSizeCap are the two settings that stop the disk-full incident nobody plans for.

Formatting is the appender's other half. A PatternLayout conversion pattern names the fields and their order — timestamp, level, thread, logger, MDC values via %X{trace.id}, message, and %ex for the stack trace. Two conversion words are worth knowing because they cost real money: %L (line number), %M (method) and %C (caller class) are computed by capturing a stack trace on every line, which is orders of magnitude slower than everything else in the pattern — fine locally, a genuine throughput problem under load.

<appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
  <file>/var/log/app/app.log</file>
  <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
    <fileNamePattern>/var/log/app/app-%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
    <maxFileSize>100MB</maxFileSize>
    <maxHistory>14</maxHistory>
    <totalSizeCap>5GB</totalSizeCap>    <!-- the disk-full guard -->
  </rollingPolicy>
  <encoder>
    <pattern>%d %-5level [%thread] %logger{36} trace=%X{trace.id} - %msg%n</pattern>
  </encoder>
</appender>

JSON output: LogstashEncoder and Boot's built-in structured logging

An encoder turns a log event into bytes. Swap the pattern encoder for a JSON one and the same application code starts emitting the records from the first topic — no call-site changes, just configuration. The long-standing community option is logstash-logback-encoder, which provides LogstashEncoder (and LoggingEventCompositeJsonEncoder for full control over which fields appear). It writes the standard event fields, promotes every MDC entry to a top-level JSON field automatically, and adds structured-argument helpers — kv("order.id", id) or StructuredArguments.value(...) — so an argument becomes a real typed field rather than text inside the message.

Since Spring Boot 3.4 you no longer need a third-party encoder for the common cases: Boot ships structured logging with three built-in formats — Elastic Common Schema, Logstash JSON, and GELF (Graylog) — enabled with a single property, plus a StructuredLogFormatter interface for a custom format. Choose deliberately: Boot's built-in support if you want zero extra dependencies and one of the standard schemas; logstash-logback-encoder if you need fine-grained field control, structured arguments or markers. Either way, keep the JSON encoder behind a <springProfile> so local development still gets readable lines — reading raw JSON in a terminal is a needless tax on your own team.

# Spring Boot 3.4+: structured logs with no extra dependency
logging:
  structured:
    format:
      console: ecs        # or: logstash, gelf, or your own StructuredLogFormatter
    ecs:
      service:
        name: order-service
        environment: prod

AsyncAppender, sampling and rate limiting

Logging is synchronous by default: the request thread formats the event and writes it, so a slow disk or a blocked stdout pipe becomes application latency. AsyncAppender wraps another appender with a bounded queue and a single worker thread that drains it, handing the request thread back almost immediately. The behaviour to understand — and to be asked about — is what happens when the queue fills. The default queueSize is small (256 events) and the default discardingThreshold is 20%: once the queue is 80% full Logback silently drops TRACE, DEBUG and INFO events, keeping only WARN and ERROR. That is a sane default for latency and a nasty surprise during an incident, when the INFO trail you wanted is exactly what was thrown away. Set discardingThreshold to 0 to never discard (the appender then blocks the caller instead — you have chosen completeness over latency), size the queue for your burst, and set includeCallerData to false unless you truly need it, because caller data must be captured on the calling thread and destroys the benefit.

Async moves the cost; it does not remove it. The other half is emitting less. Logback's filters do the work in-process: a TurboFilter is evaluated before the event object is even created (the cheapest possible place to drop something), DuplicateMessageFilter suppresses a message repeated beyond a threshold, and an EvaluatorFilter lets you express a sampling or throttling rule. Reach for these whenever a hot loop or a retry storm can produce thousands of identical lines a second — one bad code path flooding the pipeline costs you ingest budget, buries the useful signal, and can push an aggregator into dropping everyone's logs. Sample high-volume, low-value events (log one in a hundred with a count), keep every error, and treat log volume as a budget you monitor rather than a side effect you discover on the invoice.

<appender name="ASYNC" class="ch.qos.logback.classic.AsyncAppender">
  <queueSize>8192</queueSize>             <!-- default 256 is small for bursty traffic -->
  <discardingThreshold>0</discardingThreshold>  <!-- 0 = never drop INFO/DEBUG; block instead -->
  <includeCallerData>false</includeCallerData>  <!-- true undoes most of the benefit -->
  <appender-ref ref="JSON"/>
</appender>

<turboFilter class="ch.qos.logback.classic.turbo.DuplicateMessageFilter">
  <allowedRepetitions>5</allowedRepetitions>   <!-- cheap throttle for the hot-loop case -->
</turboFilter>

Log4j2 as the alternative, and the Log4Shell lesson

Logback is Spring Boot's default, but Log4j2 is a first-class alternative and Boot ships a starter for it: exclude spring-boot-starter-logging, add spring-boot-starter-log4j2, and because your code talks to SLF4J nothing else changes. Log4j2's genuine advantages are its asynchronous loggers built on the LMAX Disruptor (a lock-free ring buffer rather than a blocking queue, materially better under high concurrency), garbage-free logging in steady state, and a richer plugin and configuration system. Logback's advantages are being the default, a simpler configuration surface, and logback-spring.xml's Spring integration. For most services the choice is not performance-critical; pick one, and never let both implementations onto the classpath.

Log4Shell (CVE-2021-44228, December 2021) is the case study every senior interview eventually reaches. A JNDI lookup feature meant that logging an attacker-controlled string — a User-Agent header, a username, a chat message — could make the library fetch and execute remote code. The severity came from the position of the component: a logging library is on every code path, in every service, and often several dependency levels deep, so nobody knew where they had it. The lessons are the transferable ones: log a message, do not interpret it; keep a software bill of materials so "do we use Log4j, and where?" is a query rather than a two-week audit; patch dependencies on a schedule rather than on an incident; and remember that a transitive dependency you have never heard of is still your production risk.

Interview questions

Logging is asked in almost every backend round in India — service companies test the mechanics (SLF4J, Logback config, levels), product companies push on MDC across threads, PII handling and what happens when the log pipeline is the bottleneck:

Beginner What is SLF4J and how does it relate to Logback?

SLF4J is a façade — an API your code compiles against. Logback is an implementation that sits behind it and does the actual work; it is Spring Boot's default. Because the application only knows SLF4J, you can swap Logback for Log4j2 by changing dependencies, with no source changes. Always obtain loggers via LoggerFactory.getLogger(...), never from a Logback class.

Beginner Name the log levels and say what each one should mean in production.

ERROR: a human must act — alertable. WARN: degraded, a fallback fired, read it in the morning. INFO: the business narrative, one or two lines per request describing what the system did. DEBUG: development, or a temporary production bump while investigating. TRACE: payload-level detail you would never leave on. The failure mode is putting everything at INFO, which destroys the only cheap filter you have.

Beginner Why is log.info("user {} did {}", id, action) better than string concatenation?

Concatenation builds the whole string before the logger decides whether the level is enabled, so a disabled DEBUG line still costs string building on every call. The placeholder form defers formatting until the event is known to be written. It also keeps the message constant, which makes it a stable grouping key, and lets JSON encoders capture the arguments as separate fields instead of text.

Beginner Is if (log.isDebugEnabled()) still needed around a parameterized call?

Usually no — the placeholders already defer the formatting cost. The guard still earns its place when computing an argument is expensive, because arguments are evaluated before the call regardless: serialising a large object graph, a database lookup, or anything with side effects should sit behind the guard.

Beginner Difference between logback.xml and logback-spring.xml?

logback.xml is loaded by Logback directly, before the Spring environment exists, so Boot's extensions are unavailable. logback-spring.xml is loaded through Boot's initialiser and supports <springProfile> for profile-conditional blocks and <springProperty> for values from the Spring Environment. Prefer logback-spring.xml in any Boot application.

Intermediate What is structured logging and why bother?

Emitting each event as a record with stable, typed field names instead of an English sentence. It makes queries field comparisons rather than fragile regular expressions, makes aggregation possible (count and group by event type or tenant), and keeps meaning consistent across services when you adopt a schema such as ECS. Rule of thumb: constant message, varying data in fields.

Intermediate What is MDC, and how do you get a correlation id onto every line of a request?

MDC is a per-thread key-value map that the logging framework merges into every line that thread emits. Populate it in a servlet filter or interceptor at the edge with trace id, request id, user and tenant, reference the keys in the log pattern with %X{...} (or let a JSON encoder promote them to fields), and clear it in a finally block. Propagate the id to downstream services as a header so the whole journey shares one value. On Boot 3.x Micrometer Tracing puts trace and span ids in the MDC for you.

Intermediate Your correlation id disappears inside an @Async method. Why, and how do you fix it?

MDC is backed by a ThreadLocal, so it does not follow work onto another thread — executors, CompletableFuture, parallel streams and @Async all start with an empty MDC. Fix it by capturing MDC.getCopyOfContextMap() before submitting and calling setContextMap inside the task, done once centrally via a decorating Executor or Spring's TaskDecorator. Always clear afterwards, because the pooled thread will be reused for someone else's request.

Intermediate What must never be logged, and how do you enforce it?

Never: passwords or hashes, session tokens and JWTs, API keys, full card numbers and CVV, OTPs, national identifiers such as Aadhaar or PAN, bank account numbers, health data. Personal data is allowed only under purpose and storage limitation (GDPR, DPDP) — unbounded retention of emails and phone numbers is a compliance problem. Enforce in layers: exclude sensitive fields from toString, log identifiers rather than whole objects, never dump raw request bodies or Authorization headers, and mask at the encoder so anything that slips through is redacted before it is written. Remember logs are shipped to third parties and kept for years.

Intermediate You are catching and logging the same exception in the DAO, the service and the controller. What is wrong?

One failure produces three or four stack traces, so on-call cannot tell whether the system failed once or four times, and error counts and alerts are inflated. Log an exception once, at the boundary where you actually handle it — a controller advice, a listener error handler, a job wrapper. Elsewhere either add context and rethrow without logging, or do not catch at all. Pass the throwable as the last SLF4J argument so the full cause chain is printed instead of just getMessage().

Intermediate What does additivity="false" do on a logger?

By default an event is passed to the appenders of the logger and all its ancestors, so attaching a dedicated appender to a package while the root logger also has one writes every line twice. Setting additivity="false" stops the event at that logger, which is exactly what you want for an audit or access log that must go to its own file and nowhere else.

Pro How do you make a Spring Boot service emit JSON logs, and what are the options?

Two routes. Boot 3.4+ has built-in structured logging: set logging.structured.format.console to ecs, logstash or gelf, with a StructuredLogFormatter for a custom shape — no extra dependency. Or use logstash-logback-encoder for finer control: LogstashEncoder or the composite encoder, automatic promotion of MDC entries to fields, and structured arguments such as kv("order.id", id). Wrap either in a <springProfile> so local runs stay human-readable.

Pro Explain AsyncAppender, and the default that surprises people during an incident.

It wraps another appender with a bounded queue drained by a worker thread, so the request thread is not blocked on I/O. The trap is the defaults: queueSize is 256 and discardingThreshold is 20%, so once the queue is 80% full Logback silently discards TRACE, DEBUG and INFO and keeps only WARN and ERROR — precisely during the traffic spike when you wanted the INFO trail. Set discardingThreshold to 0 to block instead of dropping, size the queue for realistic bursts, and leave includeCallerData false because caller data is captured on the calling thread and undoes the benefit.

Pro A retry loop is producing thousands of identical lines a second and flooding the pipeline. What do you do?

Fix the call site first — log the failure once with a retry count rather than once per attempt. Then defend systemically: a TurboFilter is evaluated before the event object is even constructed, so it is the cheapest place to drop noise; DuplicateMessageFilter caps repetitions of one message; an EvaluatorFilter expresses a sampling rule (one in N, plus a count). Keep every error, sample the high-volume low-value events, and treat log volume as a monitored budget — flooding costs ingest money, buries the signal, and can make the aggregator shed everyone's logs.

Pro Why did Log4Shell matter so much, and what would you change in a codebase because of it?

CVE-2021-44228: Log4j2's JNDI lookup meant that merely logging an attacker-controlled string could load and execute remote code, and a logging library sits on every code path in every service, frequently as a transitive dependency nobody had inventoried. Changes worth making: keep a software bill of materials so "where do we use this?" is a query not an audit, patch dependencies on a schedule, scan continuously rather than at release time, log messages without interpreting them, and treat unvalidated user input in log lines as a security concern (log injection) rather than a formatting one.

Pro Logback or Log4j2 for a high-throughput service — how do you decide?

Both sit behind SLF4J, so the decision is operational, not architectural. Log4j2's asynchronous loggers use the LMAX Disruptor — a lock-free ring buffer rather than a blocking queue — and it offers garbage-free logging in steady state, which measurably helps at very high concurrency. Logback is the Boot default with a simpler configuration surface and logback-spring.xml's profile and property integration. Benchmark with your own workload before switching; whichever you choose, ensure only one implementation is on the classpath and swap the starter dependency rather than touching application code.
