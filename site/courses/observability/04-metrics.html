Module: Metrics with Micrometer and Prometheus

Logs tell you what happened to one request; metrics tell you what is happening to all of them. They are cheap, pre-aggregated and the only pillar you can safely alert on — provided you pick the right meter and keep your tags under control.

Knowledge Library → Courses → Observability track → Metrics with Micrometer and Prometheus

What this module covers

A metric is a number sampled over time. That constraint is the whole value proposition: a counter incremented ten million times still costs one time series, so metrics stay affordable at volumes where logging every event would bankrupt you. That is why alerts, dashboards and capacity planning all sit on metrics rather than logs or traces.

This module covers instrumentation with Micrometer — the vendor-neutral facade Spring Boot wires up for you — then the backend that scrapes it. Two mistakes dominate real projects and interviews alike: choosing the wrong meter type (a counter for something that can decrease, a gauge on an object nobody holds a reference to), and letting a tag carry unbounded values until the cardinality explosion takes the metrics backend down. Both get a section of their own. Versions assumed: Spring Boot 3.x/4.x with current Micrometer and current Prometheus.

Topics

Micrometer: the vendor-neutral facade and its registry model

Micrometer is to metrics what SLF4J is to logging — you instrument once against a neutral API and choose the backend with a dependency. Swap micrometer-registry-prometheus for the Datadog, New Relic, CloudWatch, OTLP or Graphite registry and your instrumentation code does not change. Everything hangs off a MeterRegistry: meters are created through it, cached by name plus tag set, and the registry is what naming conventions and filters are applied to on the way out. A CompositeMeterRegistry can publish the same meters to several backends at once, and SimpleMeterRegistry holds them in memory for tests.

On Spring Boot you rarely construct one. Actuator auto-configures a registry for every implementation on the classpath, injects it as a bean, and pre-instruments the things you would otherwise write yourself: JVM memory and garbage collection, thread and class loading counts, HTTP server and client request timers, DataSource and HikariCP pool state, cache statistics, Tomcat internals, Kafka and RabbitMQ clients. Add spring-boot-starter-actuator plus the Prometheus registry and expose the endpoint, and a useful dashboard exists before you have written a single custom meter. Your job is then the handful of meters that describe your business — orders placed, payments declined, queue depth — not the platform.

@Service
class OrderService {
    private final Counter placed;

    OrderService(MeterRegistry registry) {          // injected by Actuator
        this.placed = Counter.builder("orders.placed")
            .description("Orders accepted by the checkout API")
            .tag("channel", "web")                  // bounded value set only
            .register(registry);
    }

    void place(Order o) { /* ... */ placed.increment(); }
}

Choosing the right meter: counter, gauge, timer, long task timer, distribution summary

A Counter is a single monotonically increasing value — use it for things that only ever happen more: requests served, messages consumed, errors thrown. Never use a counter for a quantity that can go down; queries assume it only rises, and a decrement makes rate() read the drop as a counter reset. A Gauge is the opposite: an instantaneous reading that moves in both directions — queue depth, active sessions, cache size, free disk. You do not set a gauge, you register a function that samples an object, and Micrometer polls it at publish time.

That sampling detail is the classic trap: a gauge holds a weak reference to the object it samples. Register a gauge on a local variable or a collection nobody else retains, the object is collected, and the gauge silently starts reporting NaN — no exception, no log line, just a dead line on the dashboard. Always keep a strong reference in a field. A Timer records duration and count together (so it gives you both latency and throughput from one meter) and should be used for anything short-lived; @Timed or timer.record(...) both work. A LongTaskTimer is for the opposite case — it reports on operations while they are still running, which is the only way to see that a nightly batch job has been stuck for forty minutes rather than waiting until it finishes to find out. A DistributionSummary is a timer for things that are not durations: payload sizes in bytes, items per batch, order values.

// WRONG: nothing else holds the list, so the gauge reports NaN after GC
Gauge.builder("queue.depth", new ArrayList<String>(), List::size).register(registry);

// RIGHT: strong reference kept in a field
private final Queue<Job> pending = new ConcurrentLinkedQueue<>();
Gauge.builder("queue.depth", pending, Queue::size).register(registry);

Timer.builder("payment.gateway").register(registry).record(() -> gateway.charge(req));
DistributionSummary.builder("order.value.rupees").register(registry).record(order.total());

Percentiles: client-side quantiles versus histogram buckets

Averages hide the users who are suffering, so latency is reported as percentiles. Micrometer offers two very different ways to get them and confusing the two is a genuine production bug. publishPercentiles(0.95, 0.99) computes the quantiles inside the JVM and ships the answers as pre-computed gauges — accurate for that one instance, cheap, and completely un-aggregatable. publishPercentileHistogram() instead ships a set of cumulative bucket counters, and the backend computes the quantile across whatever instances you ask for; serviceLevelObjectives lets you add bucket boundaries at the latencies you actually care about.

The rule that follows is the most-failed metrics question in interviews: you cannot average percentiles. The mean of ten pods' p99 values is not the fleet p99 and has no statistical meaning at all — a pod serving three requests contributes as much to the average as one serving thirty thousand, and a quantile is a position in a distribution, not a quantity you can add up. If you need a cross-instance percentile you must aggregate the underlying distribution, which means histogram buckets and histogram_quantile() at query time. Keep the two techniques straight: client-side percentiles for a single-instance debugging view, histograms for anything that feeds an SLO or an alert.

management.metrics.distribution:
  percentiles-histogram:
    http.server.requests: true      # bucket series the backend can aggregate
  slo:
    http.server.requests: 100ms,300ms,500ms,1s
  percentiles:
    payment.gateway: 0.95,0.99      # per-instance only — never average these

Tags, naming conventions and the cardinality bomb

Tags (Prometheus calls them labels) are the dimensions you slice a metric by — uri, status, method, outcome. Micrometer names meters in dot-delimited lower case (http.server.requests) and each registry translates that into its backend's convention, so the Prometheus registry emits http_server_requests_seconds_count without you thinking about it. Add tags that apply to every meter — application name, region, instance, environment — as common tags on the registry via a MeterRegistryCustomizer rather than repeating them at each call site.

Now the part that causes outages. Every unique combination of tag values is a separate time series, stored, indexed and kept in memory by the backend. A meter with 5 endpoints × 6 status codes × 3 regions is 90 series — fine. Add a tag carrying a user id, an order id, a request id, an email address, a session token, a full stack trace message, or a raw URL path such as /orders/8f3c-1a and you have created one series per distinct value, forever. Millions of near-empty series follow, the scrape slows, the backend's memory blows up, and queries across the metric stop returning. This is the cardinality bomb, and it is why the fix is URI templating: tag with the route pattern /orders/{id}, never the resolved path — which is exactly what Spring's built-in http.server.requests instrumentation does. Micrometer also gives you defensive tooling: MeterFilter.maximumAllowableTags(...) caps a tag's distinct values and buckets the rest into a ttl overflow value, MeterFilter.deny(...) drops meters entirely, and replaceTagValues rewrites offending values before they are ever published. High-cardinality context belongs in a trace or a log line, not a tag.

@Bean
MeterRegistryCustomizer<MeterRegistry> conventions() {
    return registry -> registry.config()
        .commonTags("application", "checkout", "region", "ap-south-1")
        // hard ceiling: after 100 distinct URIs, extra values collapse to "other"
        .meterFilter(MeterFilter.maximumAllowableTags(
                "http.server.requests", "uri", 100, MeterFilter.deny()));
}
// tag with the template, never the resolved path:
//   good  uri="/orders/{id}"      one series
//   bad   uri="/orders/9a41c2"    one series per order, forever

Prometheus: the pull model, scrape configuration and the exposition format

Prometheus inverts the assumption most people arrive with. Your application does not push metrics anywhere; it exposes a plain-text endpoint and the Prometheus server scrapes it on an interval — typically every 15 to 60 seconds. On Spring Boot that endpoint is /actuator/prometheus, and the whole integration is a starter dependency plus one exposure property. Pull has real consequences worth stating in an interview: the scrape itself is a health signal (the synthetic up series tells you the target is alive without any application code), targets can be discovered dynamically, a broken monitoring server cannot back-pressure your application, and you can point a browser at the endpoint to see exactly what will be collected. The cost is that short-lived batch jobs die before anyone scrapes them, which is what the Pushgateway exists for — and it is the only case where pushing is the right answer.

Targets come from scrape_configs. Static lists work for a fixed set of hosts, but in Kubernetes you use service discovery — kubernetes_sd_configs, or the Prometheus Operator's ServiceMonitor resources — so pods that scale up are scraped automatically and pods that vanish stop being alerted on. Relabelling rules then rewrite discovered labels into the ones you actually query by. The response body itself is the exposition format: one line per series, an optional # HELP and # TYPE comment per metric family, labels in braces, value last. It is deliberately boring text so anything can produce it, and OpenMetrics is its standardised successor.

management:
  endpoints.web.exposure.include: health,info,metrics,prometheus
  metrics.tags.application: ${spring.application.name}

# prometheus.yml on the server side
scrape_configs:
  - job_name: checkout
    metrics_path: /actuator/prometheus
    scrape_interval: 15s
    static_configs:
      - targets: ["checkout-1:8080", "checkout-2:8080"]

The four metric types on the wire, and what a histogram really is

Prometheus itself stores only float samples against a timestamp; the "type" is a convention plus a naming pattern. A counter only goes up and resets to zero on process restart — you never graph its raw value, you graph its rate. A gauge goes both ways and is meaningful as-is. A histogram is where people get confused: it is not one series but a family. Micrometer's http_server_requests_seconds histogram expands into many ..._bucket{le="0.1"} series (cumulative counts of observations at or below each boundary), plus ..._sum and ..._count. Quantiles are computed from those buckets at query time, which is precisely what makes them aggregatable across instances. A summary ships pre-computed quantiles from the client instead — cheaper to query, impossible to aggregate. That is the same tradeoff you met on the Micrometer side, seen from the backend.

Classic histograms have a real drawback: you must guess the bucket boundaries in advance, and boundaries that miss your latency range give you useless resolution while a generous set multiplies your series count. Native histograms (still evolving, but shipped as an experimental feature and worth naming) fix this by storing a single, self-scaling exponential-bucket structure per series — far higher resolution at a fraction of the cardinality cost, with no boundary tuning. Know that they exist and why they were introduced, even if your cluster is still on classic buckets.

# TYPE http_server_requests_seconds histogram
http_server_requests_seconds_bucket{uri="/orders/{id}",le="0.1"} 24041
http_server_requests_seconds_bucket{uri="/orders/{id}",le="0.3"} 24730
http_server_requests_seconds_bucket{uri="/orders/{id}",le="+Inf"} 24802
http_server_requests_seconds_sum{uri="/orders/{id}"} 1183.4
http_server_requests_seconds_count{uri="/orders/{id}"} 24802

PromQL: vectors, rate(), histogram_quantile() and recording rules

PromQL has two things you evaluate against. An instant vector is one sample per matching series at a moment in time — http_server_requests_seconds_count{status="500"}. A range vector is every sample in a window, written with a bracketed duration — ...[5m] — and it is not directly graphable; it is raw material for a function that collapses it back down. Selectors match on the metric name plus label matchers: =, !=, =~ and !~ for regular expressions.

The single most important habit: almost every counter query is wrapped in rate(). A counter's absolute value is meaningless — it depends on how long the process has been running — but rate(x[5m]) gives per-second change averaged over the window and, crucially, handles counter resets when a pod restarts. Use rate() for graphs and alerts, irate() only for fast-moving debug views, and increase() when you want a total over the window. Percentiles come from histogram_quantile(0.95, sum by (le, uri) (rate(http_server_requests_seconds_bucket[5m]))) — note the order: rate the buckets first, then sum, keeping le in the grouping, then take the quantile. Aggregation operators (sum, avg, max, count) take by (...) to keep labels or without (...) to drop them. When a query becomes expensive or is reused across dashboards, promote it to a recording rule: Prometheus evaluates it on a schedule and stores the result as a new series, so dashboards and alerts read a cheap pre-computed value instead of re-crunching millions of samples.

# request rate per endpoint
sum by (uri) (rate(http_server_requests_seconds_count{application="checkout"}[5m]))

# error ratio (the "E" of RED)
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
  / sum(rate(http_server_requests_seconds_count[5m]))

# p95 latency aggregated across every instance
histogram_quantile(0.95,
  sum by (le, uri) (rate(http_server_requests_seconds_bucket[5m])))

RED and USE: knowing what to measure, and where the data lives long-term

Two checklists stop you from instrumenting at random. RED — Rate, Errors, Duration — is Tom Wilkie's method for anything request-driven: for every service, measure requests per second, the number of those that failed, and the distribution of how long they took. Apply it uniformly to every service and you get a consistent operational view that lets an on-call engineer reason about code they did not write. USE — Utilization, Saturation, Errors — is Brendan Gregg's method for every resource: CPU, memory, disk, network, connection pools, thread pools. For each one ask how busy it is, how much work is queued waiting for it, and how many operations failed. The two are complements, not alternatives: RED tells you your users are unhappy, USE usually tells you which resource is why. Google's four golden signals (latency, traffic, errors, saturation) are the same idea with saturation folded in, and they are the phrasing most SRE interviews use.

One awareness-level point to close on: a single Prometheus server is designed for reliability rather than durability — local storage, no clustering, retention measured in weeks. For long retention, global query across clusters, or downsampling, you front it with a long-term storage layer. Grafana Mimir, Thanos and VictoriaMetrics are the three names to know; all speak PromQL and consume the remote-write protocol, so your instrumentation and your queries are unaffected by the choice. Knowing that this tier exists — and that you do not solve retention by turning up a single Prometheus's disk — is enough at this stage.

Interview questions

Metrics questions turn up in almost every backend and SRE round in India — the meter-type question is the screen, and cardinality and percentile aggregation are where product-company interviews separate candidates who have run this in production:

Beginner What is Micrometer and why does Spring Boot use it?

A vendor-neutral metrics facade — the SLF4J of metrics. You instrument once against MeterRegistry and choose the backend (Prometheus, Datadog, CloudWatch, OTLP, New Relic) by adding a dependency, with no code change. Spring Boot Actuator auto-configures the registry and pre-instruments the JVM, HTTP server and client, connection pools, caches and messaging clients, so you only write the meters that describe your business.

Beginner Counter vs gauge — when do you use each?

Counter for a value that only increases: requests handled, errors, messages consumed. Gauge for an instantaneous value that moves both ways: queue depth, active connections, cache size, free memory. The test is simple — if the number can ever go down, it is not a counter. Using a counter for a decreasing value breaks rate(), which reads any decrease as a process restart.

Beginner Why does Prometheus pull instead of push, and what breaks under pull?

Targets expose an endpoint and the server scrapes them. Benefits: the scrape itself is a liveness signal (the synthetic up series), targets are discovered dynamically, applications cannot be back-pressured by a struggling monitoring system, and you can inspect the endpoint by hand. What breaks: short-lived batch jobs that exit before any scrape — those push to the Pushgateway, which is the documented exception rather than a general pattern.

Beginner What are the four Prometheus metric types?

Counter (monotonic, reset on restart), gauge (goes up and down), histogram (observations bucketed into cumulative _bucket series plus _sum and _count), and summary (client-computed quantiles plus _sum and _count). The types are conventions over the same float-sample storage; the difference lives in the naming pattern and how you query them.

Intermediate Your gauge shows NaN in production. What happened?

A gauge holds a weak reference to the object it samples so instrumentation never leaks memory. If nothing else retains that object it is garbage collected and the gauge reports NaN — silently, with no exception. The fix is to keep a strong reference in a field (or use Gauge.builder(..., this, o -> ...) on a long-lived bean). Registering a gauge on a local variable is the usual cause.

Intermediate Why can't you average p99 across instances?

A percentile is a position within a distribution, not an additive quantity, so the arithmetic mean of ten pods' p99 values is a number with no statistical meaning — and it weights a pod serving three requests the same as one serving thirty thousand. To get a fleet-wide percentile you must aggregate the underlying distribution: publish histogram buckets, then histogram_quantile(0.95, sum by (le) (rate(..._bucket[5m]))). Client-side publishPercentiles values are per-instance only.

Intermediate What is metric cardinality and how do you blow it up?

Cardinality is the number of distinct time series a metric produces — one per unique combination of label values. It multiplies: 5 endpoints × 6 statuses × 3 regions is 90 series. You blow it up by putting an unbounded value in a tag: user id, order id, request id, email address, session token, an exception message, or a raw URL path containing an id. Each distinct value becomes a permanent series, memory and index size explode, scrapes slow down and queries over the metric stop returning.

Intermediate How do you keep the URI tag on HTTP metrics safe?

Tag with the route template, not the resolved path — uri="/orders/{id}", never uri="/orders/9a41c2". Spring's built-in http.server.requests instrumentation does this automatically from the handler mapping; the danger is hand-rolled instrumentation or a filter that reads request.getRequestURI(). Back it with MeterFilter.maximumAllowableTags so any leak is capped rather than unbounded, and put the per-request identifiers in a trace or a structured log instead.

Intermediate Why do you almost always wrap a counter in rate()?

A counter's raw value depends on how long the process has been up, so graphing it tells you nothing and comparing it across pods is meaningless. rate(x[5m]) gives per-second change over the window and explicitly handles counter resets, so a pod restart shows as a gap rather than a huge negative spike. Use rate for graphs and alerts, increase for a total over a window, and irate only for short, fast-moving debug views.

Intermediate Explain RED and USE, and when you would apply each.

RED — Rate, Errors, Duration — applies to request-driven services: how many requests, how many failed, how long they took. USE — Utilization, Saturation, Errors — applies to resources: CPU, memory, disk, network, connection and thread pools. Use RED for every service uniformly so on-call can reason about unfamiliar code; use USE when RED says something is wrong and you need to find which resource is the constraint. Google's four golden signals are the same idea with saturation added.

Intermediate Timer vs LongTaskTimer vs DistributionSummary?

Timer records the duration and count of short operations, and only reports once each one finishes. LongTaskTimer reports on tasks that are still running, which is the only way to see that a nightly batch has been stuck for forty minutes rather than finding out afterwards. DistributionSummary is a timer for non-time values — payload bytes, items per batch, order amounts — and supports the same histogram and percentile configuration.

Pro Walk through the p95 latency query and explain the operator order.

histogram_quantile(0.95, sum by (le, uri) (rate(http_server_requests_seconds_bucket[5m]))). Innermost first: rate converts each cumulative bucket counter into a per-second rate and absorbs restarts; sum by (le, uri) merges instances while keeping the le label, because histogram_quantile needs the full bucket set to interpolate; only then does the quantile function run. Drop le from the grouping and the query returns nothing; sum before rating and counter resets corrupt the result.

Pro publishPercentiles vs publishPercentileHistogram — which and why?

publishPercentiles computes quantiles inside the JVM and ships the answers, so they are accurate for that instance, cheap to store, and impossible to aggregate or re-quantile. publishPercentileHistogram ships cumulative bucket counters and lets the backend compute the quantile over any set of instances, at the cost of extra series. Anything feeding an SLO, an alert or a multi-instance dashboard must use histograms; client-side percentiles are for single-instance inspection. Add serviceLevelObjectives to place buckets at the latencies you actually promise.

Pro Your Prometheus is out of memory and queries time out. Diagnose it.

Almost always active-series growth. Check prometheus_tsdb_head_series over time and use topk(10, count by (__name__)({__name__=~".+"})) to find the offending metric families, then look at which label is unbounded. Typical culprits: an id or a raw path leaking into a tag, per-pod labels churning on every deploy, or a histogram with too many buckets multiplied by too many dimensions. Fixes in order: drop or rewrite the label with a meter filter or a relabel rule, template the URI, reduce bucket counts (or move to native histograms), and move long retention to Mimir, Thanos or VictoriaMetrics rather than growing one server.

Pro Why prefer histograms over summaries in a multi-instance deployment?

Summaries carry pre-computed quantiles from each client, so there is no correct way to combine them across replicas — you can only look at one instance at a time. Histograms ship the distribution as buckets, so the backend can sum bucket rates across every instance and compute a true fleet-wide quantile at query time. Summaries are cheaper to query and more accurate for a single process; histograms are the only option once you have more than one pod, which in practice you always do.

Pro What are recording rules, and when would you introduce one?

A recording rule evaluates an expression on a schedule and writes the result back as a new series. Introduce one when the same expensive query is repeated across dashboards and alerts, when a dashboard panel is slow because it re-aggregates millions of samples on every refresh, or when you want alert and dashboard definitions to agree by construction. Convention is to name them level:metric:operation, for example job:http_requests:rate5m. They trade a little storage and evaluation cost for large, repeated query savings.
