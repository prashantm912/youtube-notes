Module: Observability Foundations

Every dashboard you have ever built answers a question somebody thought of in advance. Observability is the discipline of being able to answer the questions nobody thought of — at three in the morning, on a system you cannot redeploy.

Knowledge Library → Courses → Observability track → Observability Foundations

What this module covers

This module frames the whole track. It defines observability properly — not as "logs plus metrics plus traces", which is a description of data types, but as the property borrowed from control theory: can you infer the internal state of a system from the signals it emits at the outside? It then draws the real boundary against monitoring, maps that boundary onto known and unknown unknowns, and takes the three pillars apart honestly, including the increasingly loud argument that the pillars are a vendor frame rather than an engineering one.

The second half is the part that decides whether any of it survives contact with a finance review: instrumentation strategy. Auto-instrumentation versus hand-written spans, what is actually worth instrumenting, and the cost mechanics — cardinality, log volume, sampling — that quietly govern every observability programme. The remaining seven modules are the implementation detail underneath this one.

Topics

Observability, properly defined: the control-theory origin

The word is borrowed, and the borrowing matters. In control theory a system is observable when its internal state can be reconstructed from knowledge of its external outputs — you do not get to open the box, you only get to read the instruments, and observability is the mathematical property that says the instruments are sufficient. Carry that across to software and the question stops being "do we have dashboards?" and becomes "given only the telemetry this system emits, can I determine any internal state it might have gotten itself into?"

That reframing has a sharp practical consequence. Observability is a property of your system, not a product you buy and not a team you hire; a vendor sells you tooling that makes the property easier to exploit, but a service that emits nothing but a request count and a stack trace is unobservable no matter which platform ingests it. The engineering work is therefore mostly upstream of the tool — deciding what the code emits, how much context travels with each emission, and whether that context is rich enough to reconstruct a story after the fact.

Monitoring vs observability: known unknowns and unknown unknowns

Monitoring answers questions you knew to ask in advance. You predicted a failure mode — the disk fills, the queue backs up, the error rate crosses five percent — and you encoded that prediction as a dashboard panel and an alert rule. It works beautifully, and it will keep working, for every failure mode you successfully anticipated. Those are your known unknowns: the question is already formulated, only its answer is missing, so you pre-compute that answer and put it on a wall.

Observability is what you need when the failure mode was not on the list. A distributed system has a combinatorially large space of possible states, and the ones that page you tend to be the ones nobody modelled: this build, for this tenant, on this shard, only for requests that arrived through the old mobile client. Those are unknown unknowns — you cannot pre-build a dashboard for a question you have not yet had. The operational test is blunt and worth memorising for interviews: can you ask a brand-new question of your live production system and get an answer, without shipping new code? If answering requires adding a log line and waiting for a deploy, you have monitoring. Both are legitimate; mature teams run monitoring for the known failure modes and rely on observability for everything else.

The three pillars: what logs, metrics and traces each answer — and cannot

The conventional decomposition is logs, metrics and traces, and it is worth learning precisely because everyone will use the vocabulary. A log is a discrete, timestamped record of something that happened, carrying the most detail per event and costing the most per event to store, index and query. A metric is a number aggregated over a time interval — a counter, a gauge, a histogram — which is cheap to store and fast to query over months, but has thrown away every individual request by construction. A trace is the causal path of one request as it crosses services, a tree of spans stitched together by a propagated trace context, which is the only one of the three that tells you where the time went across process boundaries.

Each pillar's strength is the direct cause of its blind spot, and being able to state that trade-off cleanly is what an interviewer is listening for.

What each signal answers, and where it goes blind
SignalAnswers wellCannot answerCost shape
LogsWhat exactly happened in this one execution, with full local context and the stack traceAnything aggregate — "is this getting worse?" needs a scan or a pre-built indexGrows with request volume × verbosity; ingest and index dominate
MetricsTrends, rates, percentiles, alert thresholds, months of history at constant costWhich requests were the slow ones, and why — the individual is gone by designGrows with the number of unique tag combinations, not with traffic
TracesWhere the latency went across services; the causal order of calls; the failing hopAggregate truth, unless sampling is understood — a sampled trace is an anecdoteGrows with request volume × span count; usually sampled hard

Notice how often the real answer needs two of them: metrics tell you the p99 doubled at a point in time, traces tell you which downstream hop absorbed the time, logs tell you the exception that hop threw. The pillars are not competing options — they are three projections of the same underlying events.

The critique: "three pillars" is a frame, and the pillars are converging

There is a serious and increasingly mainstream objection to the pillars framing, and knowing it marks you out in a senior interview. The objection is that three pillars describes three storage products a vendor would like to sell you, not three engineering capabilities. Splitting one request's story across three systems with three query languages, three retention policies and three bills means the debugging workflow becomes an exercise in manual correlation — and the thing you actually needed was never a pillar at all. What you needed was one arbitrarily wide, structured event per unit of work, carrying every dimension you might later want to filter or group by, in a store that lets you slice it after the fact.

That is the "wide events" position, sometimes labelled observability 2.0: emit one fat event per request with a hundred-plus fields — user id, tenant, build sha, feature flags, cache hit or miss, downstream latencies, queue depth on arrival — and derive metrics and traces from it rather than emitting three separate things. Meanwhile the pillars themselves are quietly converging in exactly that direction: exemplars attach a trace id to a specific bucket of a histogram so you can click from a latency spike straight into an example trace; trace and span ids are injected into log lines so a log search pivots to a trace; and OpenTelemetry models all three signals against a shared resource and shared semantic conventions. In practice you will inherit three pillars and should push the seams together with correlation ids at every layer.

Instrumentation strategy: auto-instrumentation vs manual spans

Auto-instrumentation (OpenTelemetry calls it zero-code instrumentation) attaches at runtime and instruments the libraries for you. On the JVM you add one flag — the OpenTelemetry Java agent — and without touching a line of application code you get spans for inbound HTTP, outbound HTTP clients, JDBC statements, Kafka producers and consumers, scheduled tasks, and JVM runtime metrics, with context propagation across all of them. The coverage is enormous for the effort, the naming follows semantic conventions so it is consistent across services, and it works on code you cannot change, including third-party libraries. Its weakness is that it only knows about frameworks: it will tell you a POST to /api/orders took eight hundred milliseconds and that four JDBC calls were involved, but it has no idea what an order is, which tenant placed it, or that this was a bulk import.

Manual instrumentation is where that meaning gets added — a hand-written span around a business operation, attributes carrying the domain facts, and custom metrics for outcomes the business actually cares about. It costs developer time and it is the part that rots if nobody owns it. The recommendation that survives every real rollout: start with the agent everywhere, then add manual instrumentation exactly where you have questions you could not answer. Turning on auto-instrumentation is a one-sprint platform task that lifts the whole estate; manual spans are a per-team investment justified by specific debugging pain. Adding attributes to the span the agent already created is usually cheaper and better than creating a new one.

# zero-code: attach the agent, name the service, point it at a collector
java -javaagent:/opt/otel/opentelemetry-javaagent.jar \
     -Dotel.service.name=order-service \
     -Dotel.exporter.otlp.endpoint=http://collector:4317 \
     -jar order-service.jar
// manual: enrich the span the agent already opened, rather than creating another
Span span = Span.current();
span.setAttribute("tenant.id", order.tenantId());
span.setAttribute("order.line_count", order.lines().size());
span.setAttribute("order.channel", order.channel());   // web | mobile | bulk-import
span.setAttribute("payment.provider", chosenProvider); // the dimension you will slice by later

What is actually worth instrumenting

The default answer for every service boundary is the RED signals — Rate (requests per second), Errors (how many of them failed), Duration (the latency distribution, as a histogram, never a pre-computed average). Emit those at every entry point and every outbound dependency call and you can answer "is this service healthy and is it the one at fault?" for any service in the estate using one dashboard shape. Consistency is the whole value: the same three signals with the same names everywhere means an on-call engineer who has never seen your service can still read it. Module 04 goes into RED and its infrastructure counterpart in depth.

Above that sits the layer most teams skip and later regret: business events that map to user outcomes. Orders placed, payments authorised, KYC checks completed, carts abandoned at the payment step — emitted with the dimensions that let you slice them by tenant, channel, region and build. These are what let you detect an incident that no infrastructure signal registers: every service is returning HTTP 200 and the checkout success rate has fallen by thirty percent because a feature flag broke one payment provider for one client version. Domain-oriented observability of this kind is also the cheapest telemetry you own, because business events are orders of magnitude rarer than requests. When adding attributes, follow OpenTelemetry semantic conventions for anything that has a standard name and reserve your own namespace for the rest — it is what makes cross-service queries possible at all.

Cardinality: the arithmetic that decides your metrics bill

This is the single most asked cost question in observability interviews, and the answer is arithmetic rather than opinion. In a dimensional metrics system such as Prometheus, every unique combination of metric name and label values is a separate time series, stored and indexed independently. A counter http_requests_total with labels for method (about 5 values), route (say 40) and status (say 15) is roughly three thousand series — entirely fine. Add a label for user id with a million users and you have created up to three billion series. Memory, index size, ingestion cost and query latency all scale with series count, not with request volume, which is why a low-traffic service can bankrupt a metrics backend while a high-traffic one sits comfortably.

The rule to state in an interview: metric labels must be bounded and low-cardinality. User ids, order ids, session ids, request ids, raw URL paths with ids embedded in them, email addresses, full exception messages and unsanitised query strings are all unbounded and must never become labels — put them on a log line or a span attribute instead, where the storage model is per-event rather than per-series and high cardinality is the point. Templated routes (/orders/{id}, not /orders/8f21c) are the standard fix, and most frameworks will do it wrongly by default if you let them. Guard it operationally too: cap the label values a metrics client will accept, alert on series growth per service, and periodically audit which series are never queried.

// WRONG: unbounded label — one time series per user, forever
Counter.builder("orders.placed").tag("user.id", userId).register(registry).increment();

// RIGHT: bounded labels on the metric; the identity lives on the span/log instead
Counter.builder("orders.placed")
       .tag("channel", order.channel())        // ~4 values
       .tag("region", order.region())          // ~6 values
       .tag("outcome", outcome.name())         // ~5 values
       .register(registry).increment();
Span.current().setAttribute("user.id", userId); // high cardinality belongs here

Volume, sampling, retention — and setting an explicit telemetry budget

Logs and traces scale with traffic, so their cost is bounded only by policy. Two levers control logs: verbosity (a DEBUG line per request in a service handling ten thousand requests per second is a firehose nobody will ever read) and retention tiers — hot, searchable storage for a few days, warm for a few weeks, cold object storage for the months you keep only for compliance. Most teams over-retain hot storage by an order of magnitude because nobody ever decided; deciding is the fix.

For traces, sampling is a necessity rather than a compromise, and saying so confidently is a good interview signal. Head-based sampling decides at the root span and propagates that decision, so it is cheap and consistent but blind — it discards errors and slow requests at the same rate as everything else. Tail-based sampling buffers complete traces in the collector and decides afterwards, letting you keep every error and every trace above a latency threshold while retaining a small percentage of the boring successes; it costs collector memory and buffering complexity. Whichever you choose, sampling must be consistent across services or you get broken traces, and any metrics derived from traces must be scaled by the sampling rate.

Pull all of this into an explicit telemetry budget — a number, agreed with the team that pays it, expressed as cost per service per month or per million requests, with an owner and a review cadence. Without one, telemetry spend grows monotonically and the only correction anyone ever applies is a panicked, indiscriminate cut during a cost review, which usually deletes the signals you needed. And the sharpest closing principle of the module: observability data you never query is pure cost. Audit your dashboards, your log indices and your metric series for what has actually been read in the last quarter, and delete without sentiment — a signal nobody has looked at in ninety days is a line item, not a safety net.

# Collector-side tail sampling: keep everything interesting, a slice of the rest
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: keep-all-errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: keep-slow-requests
        type: latency
        latency: { threshold_ms: 750 }
      - name: sample-the-boring-successes
        type: probabilistic
        probabilistic: { sampling_percentage: 2 }

Interview questions

Foundations questions open almost every observability round in Indian product and service companies — the monitoring-versus-observability definition is nearly guaranteed, and the cardinality question is the standard filter between candidates who have run a metrics backend and candidates who have only read about one:

Beginner What is observability, and where does the term come from?

It comes from control theory, where a system is observable if its internal state can be inferred from its external outputs. Applied to software: can you determine any internal state your system got into, using only the telemetry it emits, without shipping new code to find out? It is a property of the system — of what the code emits and how much context it carries — not a product you buy.

Beginner What are the three pillars of observability?

Logs (discrete timestamped event records, highest detail and highest cost per event), metrics (numeric values aggregated over time — counters, gauges, histograms — cheap to store and query but with the individual request thrown away), and traces (the causal path of a single request across services, as a tree of spans joined by propagated trace context). Add that they are three projections of the same events and are increasingly correlated rather than separate.

Beginner Monitoring vs observability — what is the actual difference?

Monitoring answers questions you asked in advance: you predicted a failure mode and encoded it as a dashboard and an alert. Observability lets you ask new questions of a live system without shipping code. Monitoring covers known unknowns, observability covers unknown unknowns. The practical test: when something breaks in a way nobody anticipated, can you slice your existing telemetry to find it, or do you have to add a log line and deploy?

Beginner Give an example of a known unknown and an unknown unknown.

Known unknown: the database connection pool may exhaust — that failure mode is predictable, so you graph pool utilisation and alert at eighty percent. Unknown unknown: checkout fails only for users on Android app version 4.2 in one region whose cart contains a discounted item, because a feature flag interacted with a rounding change. Nobody would build that dashboard in advance; you need to be able to group by app version, region and flag state after the fact.

Beginner When would you reach for a trace rather than a log?

When the question is "where did the time go?" or "which service in the chain failed?" A log tells you what happened inside one process; a trace shows the ordered, causal path across all of them with per-hop latency. In a request that crosses six services, a trace localises the problem in seconds; reading six services' logs to reconstruct the same picture takes an hour and needs a correlation id anyway.

Intermediate Auto-instrumentation vs manual instrumentation — how do you choose?

Auto-instrumentation (the OpenTelemetry Java agent) needs no code change and covers frameworks broadly — HTTP in and out, JDBC, Kafka, JVM metrics — with consistent semantic-convention naming, and it works on code you cannot modify. It is generic: it does not know your domain. Manual instrumentation adds business-meaningful spans and attributes at the cost of developer time. The strategy is start with the agent everywhere, then add manual instrumentation where you had a question you could not answer. Enriching the agent's existing span with attributes is usually better than creating a new one.

Intermediate What should every service emit as a baseline?

RED at every boundary: request rate, error count or rate, and duration as a histogram — on inbound endpoints and on every outbound dependency call. Then business events tied to user outcomes (orders placed, payments authorised, checks completed) with the dimensions you will want to slice by: tenant, channel, region, build. Baseline consistency matters more than cleverness — identical signal names across services mean anyone on-call can read any service.

Intermediate Why should you not add a user id as a metric label?

Because every unique combination of metric name and label values is a separate time series. With a million users, one user-id label multiplies your series count by a million, and memory, index size, ingest cost and query latency all scale with series count rather than traffic — so it will take down or bankrupt the metrics backend. High-cardinality identity belongs on span attributes or structured log fields, where storage is per-event. Keep labels bounded and enumerable, and template your route labels so ids never leak into them.

Intermediate Is sampling a compromise that hurts debugging?

At any real traffic level it is a necessity, not a compromise — storing every span of every request is unaffordable and almost all of them are identical successes. The design question is which sampler. Head-based decides at the root and propagates, so it is cheap and consistent but discards errors at the same rate as successes. Tail-based buffers the whole trace in the collector and decides after the fact, so you keep every error and every slow request plus a small percentage of normal ones. Whatever you pick must be consistent across services, or traces arrive broken, and any metric derived from sampled traces must be scaled by the sampling rate.

Intermediate How do you correlate a metric spike with the specific requests that caused it?

Exemplars. A histogram bucket carries an attached trace id for an example observation, so you click a latency spike in Grafana and jump straight into a trace that landed in that bucket. Complete the loop by injecting trace and span ids into every log line, so a log search pivots to the trace and a trace pivots to the logs. That correlation chain — metric to trace to log — is what makes three separate stores behave like one dataset.

Pro Critique the "three pillars" framing.

It describes three storage products, not three engineering capabilities, and it institutionalises the split: one request's story lands in three systems with three query languages, three retention policies and three bills, so debugging becomes manual correlation. The alternative position is one arbitrarily wide, structured event per unit of work carrying every dimension you might later filter or group by, from which metrics and traces are derived. In practice you inherit three pillars, so the pragmatic move is to force them together — trace ids in logs, exemplars on histograms, shared resource attributes and semantic conventions.

Pro Your observability bill tripled in six months. Walk through what you do.

Measure before cutting: attribute spend across metrics, logs and traces, then per service. For metrics, find the top series-count contributors and hunt for unbounded labels — untemplated routes and leaked ids are the usual culprits. For logs, look at verbosity (a DEBUG line per request) and at hot retention that nobody ever decided on; move older data to warm and cold tiers. For traces, move to tail-based sampling and drop most successful, fast traces while keeping all errors. Then audit usage: dashboards, saved queries and series that have not been read in a quarter are pure cost. Finally set an explicit telemetry budget per service with an owner and a review cadence, so the correction is continuous instead of a panicked indiscriminate cut.

Pro Everything is green and users are complaining. What does that tell you about your telemetry?

That you are monitoring causes rather than symptoms, and instrumenting infrastructure rather than user outcomes. Every service returning HTTP 200 within its latency budget is compatible with a broken checkout — an empty search result set, a silently failing payment provider, a client-side error after a successful API response. The fix is symptom-based signals derived from user outcomes (checkout success rate, search result rate, login success rate) sliced by build, client version, tenant and region, plus enough dimensional context to segment when only one slice is affected. Aggregate health is the classic place a real incident hides.

Pro How would you roll out observability across forty existing microservices?

Platform-first and centrally owned. Deploy the OpenTelemetry Java agent through the base image or the deployment template so no team writes code to get baseline coverage; standardise service names, resource attributes and semantic conventions so cross-service queries work; route everything through a collector so sampling, redaction and backend choice are central policy rather than forty independent decisions. Ship structured logs with trace ids and a shared RED dashboard template in the same wave. Only then ask teams for manual instrumentation, justified by specific unanswerable questions. Set the telemetry budget and the retention tiers up front, because retrofitting cost control after adoption is far harder politically than agreeing it before.

Pro Would you ever say a system is fully observable? How do you measure progress?

No — observability is not binary, because the space of possible states is effectively unbounded. Measure it by outcomes instead: what proportion of incidents were diagnosed from existing telemetry versus needing a new deploy to investigate; time to detect and time to identify the failing component; how many novel questions engineers successfully answered from production data last month. A useful team exercise is to take a past incident and ask whether today's telemetry would have answered it without a code change — that converts an abstract property into a concrete backlog item.
