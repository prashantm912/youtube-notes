Module: Health Checks

Two lines of YAML and a one-line endpoint — health checks look like the most trivial thing in the deployment manifest, and they are one of the most reliable ways to turn a small degradation into a fleet-wide outage. Get the semantics right and everything else follows.

Knowledge Library → Courses → Observability track → Health Checks

What this module covers

A health check is a machine-readable answer to a question an orchestrator is about to act on. The whole module turns on that word which question: liveness asks "is this process wedged beyond recovery — should I restart it?", readiness asks "can this instance serve a request right now — should I keep it in the load balancer?", and startup asks "is it still booting — should I hold off the liveness clock?" Three questions, three completely different consequences, and pointing all three at the same endpoint is the classic self-inflicted outage.

We start with those semantics because the rest of the module depends on them: the Kubernetes probe knobs and their failure modes, the graceful-shutdown interaction where readiness must fail before the process stops, then Spring Boot Actuator concretely — the health endpoint, dependency indicators, health groups, ApplicationAvailability, custom HealthIndicator beans, and management-endpoint security. We close on the limit of all of it: an internal endpoint returning UP proves your components are alive, not that a user can log in. Versions here are Spring Boot 3.x/4.x and current Kubernetes.

Topics

Liveness, readiness and startup: three questions with three different consequences

The distinction is not academic — the two probes trigger different actions. A failed liveness probe makes the kubelet kill and restart the container. A failed readiness probe does nothing to the container at all; it removes the pod's address from the Service endpoints, so the load balancer stops sending it traffic and resumes the moment the probe passes again. A failed startup probe also kills the container, but its job is to suppress the liveness and readiness probes entirely while a slow application boots, so a JVM that needs ninety seconds to warm its caches is not shot at second thirty by a liveness probe with an optimistic initialDelaySeconds.

Because the consequences differ, the checks must differ. Liveness should be the cheapest possible in-process signal — the event loop is turning, the HTTP server accepts a connection, no deadlock — and it must have no external dependencies whatsoever. Readiness may legitimately check the dependencies you genuinely cannot serve a request without: the primary datastore, a mandatory downstream, a warmed cache. The rule to memorise and to say out loud in an interview: restart-worthy failures go in liveness, traffic-worthy failures go in readiness, and anything a restart cannot fix does not belong in liveness. Wiring the same /health to both is how a readiness concern (a slow database) acquires the power to kill containers.

livenessProbe:                 # cheap, in-process only — never touches a dependency
  httpGet: { path: /actuator/health/liveness, port: 8081 }
  periodSeconds: 10
  failureThreshold: 3          # restart only after sustained failure

readinessProbe:                # may check dependencies you cannot serve without
  httpGet: { path: /actuator/health/readiness, port: 8081 }
  periodSeconds: 5
  failureThreshold: 1          # shed traffic fast; it is a cheap, reversible action

startupProbe:                  # suppresses the other two until boot completes
  httpGet: { path: /actuator/health/liveness, port: 8081 }
  periodSeconds: 5
  failureThreshold: 60         # up to ~5 minutes of boot before giving up

Probe mechanics: the knobs, and HTTP vs exec vs TCP vs gRPC

Every probe is defined by the same six fields and every one of them has bitten somebody. initialDelaySeconds delays the first check (largely obsoleted by a startup probe, which is the better tool). periodSeconds is the interval between checks. timeoutSeconds is how long the kubelet waits for a response before calling it a failure — it defaults to 1 second, which is shorter than a stop-the-world garbage-collection pause on a busy JVM, and that single default is behind a lot of "random restarts under load" tickets. failureThreshold is how many consecutive failures count as a verdict; successThreshold (which must be 1 for liveness and startup) is how many consecutive passes restore a readiness verdict. Your real detection time is periodSeconds × failureThreshold plus one timeoutSeconds, so tune the pair, not either alone.

Four probe mechanisms exist. httpGet is the default choice: any status from 200 to 399 is a pass, and it exercises the HTTP stack the way a real client does. exec runs a command inside the container and is by far the most expensive — it forks a process on every period, on every pod, forever, and a command that hangs leaves zombie processes behind. tcpSocket only proves a listener accepted a connection, which a completely deadlocked application will happily do, so it is a weak liveness signal. grpc, stable since Kubernetes 1.24, speaks the standard gRPC health checking protocol natively and removes the old grpc-health-probe sidecar binary. Note also that terminationGracePeriodSeconds can be set per-probe, so a liveness failure can be given a shorter grace period than a normal delete.

The disasters: probes that cause the outage they were meant to prevent

Walk these three concretely, because interviewers ask for them by name. One: a liveness probe that checks a downstream database. The database has a thirty-second blip. Every pod's liveness probe fails simultaneously, the kubelet restarts every container in the fleet at once, all of them come up cold with empty connection pools and caches, they stampede the recovering database, and a partial degradation that would have healed itself becomes a total outage with a slow, self-inflicted recovery. Restarting a process never fixes someone else's database — so that check has no business being in liveness.

Two: a readiness probe that can never fail — the hardcoded return "OK", or a check of something unrelated to serving. Traffic keeps flowing to an instance whose connection pool is exhausted or whose migration failed, and every request routed there errors. This is the mirror-image sin: readiness that is too generous silently keeps broken instances in rotation, and because nothing restarts, nothing alerts. Three: a liveness timeoutSeconds shorter than a garbage-collection pause. Under peak load the JVM pauses for 1.5 seconds, the 1-second probe times out, three periods later the container is killed — so the pods die precisely when traffic is highest, which is the worst possible moment and looks nothing like a probe bug in the logs.

The defensive posture that falls out of this: liveness checks in-process health only and is deliberately hard to fail (generous timeout, failureThreshold of 3 or more); readiness is allowed to check genuine hard dependencies and is deliberately easy to fail, because shedding traffic is cheap and reversible; and an optional dependency — a recommendations service, an analytics sink — belongs in neither, because degrading gracefully is not the same as being unable to serve.

Graceful shutdown: readiness must fail before the process stops

Pod deletion is not a single event and the ordering matters. When a pod is deleted, Kubernetes does two things concurrently: it sends SIGTERM to the container and it removes the pod from the Service endpoints. Endpoint removal has to propagate to every kube-proxy and every ingress controller in the cluster, which takes a moment; the signal arrives instantly. So an application that exits promptly on SIGTERM will kill in-flight requests and will keep receiving new ones from load balancers that have not yet caught up — visible to users as a burst of 502s on every deploy.

The fix is to make readiness fail first and then linger. A preStop hook that simply sleeps for a few seconds (or an application that flips its readiness state to DOWN on SIGTERM and only then begins draining) gives endpoint removal time to propagate before the server stops accepting. Then drain: finish in-flight requests within a bounded window that must be shorter than terminationGracePeriodSeconds, or the kubelet's SIGKILL lands mid-request anyway. Spring Boot has first-class support — server.shutdown=graceful plus spring.lifecycle.timeout-per-shutdown-phase — and Boot's Kubernetes probe support moves ReadinessState to REFUSING_TRAFFIC as soon as shutdown begins, which is exactly the behaviour you want.

# Kubernetes side: let endpoint removal propagate before the server stops.
lifecycle:
  preStop:
    exec: { command: ["sh", "-c", "sleep 8"] }
terminationGracePeriodSeconds: 45   # must exceed preStop sleep + drain window

# Spring Boot side (application.yml):
server.shutdown: graceful
spring.lifecycle.timeout-per-shutdown-phase: 30s

Spring Boot Actuator: the health endpoint, indicators and show-details

Add spring-boot-starter-actuator and you get /actuator/health, which aggregates every HealthIndicator bean on the classpath into a single status. Boot auto-configures indicators for what it can see: DataSourceHealthIndicator (runs a validation query), DiskSpaceHealthIndicator (free space above a threshold), plus Redis, MongoDB, Elasticsearch, Kafka, RabbitMQ, Cassandra, mail and more. Statuses aggregate by severity through StatusAggregator — one DOWN contributor makes the whole endpoint DOWN — and HttpCodeStatusMapper decides the HTTP status, which by default is 200 for UP and 503 for DOWN. That 503 is what makes an HTTP probe work without any extra glue.

The setting to be deliberate about is management.endpoint.health.show-details. It defaults to never, and that default exists for a reason: the detailed body names your dependencies, their versions, database product strings, cluster node counts and disk paths. Exposing it publicly hands an attacker a free reconnaissance report on your infrastructure. Set it to when-authorized for humans behind authentication, or always only on a management port that is not routable from outside the cluster. The probe itself only needs the aggregate status code — it never reads the body — so there is no operational reason to expose details to Kubernetes.

management:
  endpoints.web.exposure.include: health,info,prometheus
  endpoint.health:
    show-details: when-authorized     # never leak dependency detail publicly
    show-components: when-authorized
    probes.enabled: true              # adds /health/liveness and /health/readiness
  health:
    diskspace.threshold: 500MB
    db.enabled: true                  # datasource indicator: readiness, not liveness

Health groups, ApplicationAvailability and Kubernetes probe auto-configuration

A single aggregate status cannot answer two different questions, so Boot lets you slice the indicators into health groups. management.endpoint.health.group.liveness.include and ...group.readiness.include define which contributors feed each group, and they surface at /actuator/health/liveness and /actuator/health/readiness — the two URLs your probes should point at. Set management.endpoint.health.probes.enabled=true to create them explicitly; Boot enables them automatically when it detects a Kubernetes environment or a Cloud Foundry deployment. Each group takes its own show-details and its own status aggregation, so the liveness group can stay minimal while readiness carries real dependency detail.

Underneath, Boot models this as first-class application state rather than as endpoint plumbing. ApplicationAvailability is an injectable bean exposing LivenessState (CORRECT or BROKEN) and ReadinessState (ACCEPTING_TRAFFIC or REFUSING_TRAFFIC). The framework publishes an AvailabilityChangeEvent on every transition, and any bean can both listen for those events and publish its own — which is how you say "my Kafka consumer group has been rebalancing for two minutes, stop sending me HTTP traffic" without touching a controller. Boot moves readiness to ACCEPTING_TRAFFIC after ApplicationReadyEvent and to REFUSING_TRAFFIC when graceful shutdown starts, and the default liveness group deliberately contains only the livenessState indicator — no datasource, no Redis, no downstream. Boot's own default is the rule this module opened with.

management.endpoint.health:
  probes.enabled: true
  group:
    liveness:
      include: livenessState          # in-process only — nothing external, ever
    readiness:
      include: readinessState,db,redis
      show-details: always            # safe: management port is cluster-internal
      additional-path: "server:/readyz"   # also serve it on the main port if needed

Writing a custom HealthIndicator that is fast and does not cascade

Implement HealthIndicator (or extend AbstractHealthIndicator) and register it as a bean; the bean name minus the healthIndicator suffix becomes the key in the response, so paymentGatewayHealthIndicator appears as paymentGateway. Return Health.up(), Health.down(), Health.outOfService() or a custom Status, optionally with withDetail(...) entries. For a hierarchy of related checks, CompositeHealthContributor groups several indicators under one key.

Two rules govern the implementation and both come from the same insight: this method runs on every probe period, on every pod, forever. It must be fast and hard-bounded. No unbounded remote call, no query without a timeout — a health check that blocks for thirty seconds turns the probe timeout into a container restart, which means your health check caused the outage. Cache expensive results for a few seconds and use a timeout strictly shorter than the probe's. It must not cascade. If your indicator pings a downstream, and that downstream's indicator pings its downstream, one leaf failure marks an entire dependency tree DOWN — and if any of that is wired into liveness, it restarts the tree too. Check what you own; report a failing optional dependency as degraded detail rather than DOWN, or exclude it from the readiness group entirely.

@Component                                     // key in the response: "paymentGateway"
class PaymentGatewayHealthIndicator implements HealthIndicator {

    private final PaymentGatewayClient client;  // configured with a hard 500ms timeout

    @Override
    public Health health() {
        try {
            var probe = client.ping();          // bounded, local, no fan-out
            return Health.up().withDetail("region", probe.region()).build();
        } catch (Exception e) {
            // DOWN here removes this pod from traffic — never wire it into liveness
            return Health.down().withDetail("reason", e.getClass().getSimpleName()).build();
        }
    }
}

Securing the endpoints: separate the management port, expose only what you need

Actuator's health endpoint is exposed over HTTP by default, and everything else is not — management.endpoints.web.exposure.include is an allow-list precisely so that env, heapdump, threaddump, loggers and shutdown stay off unless you deliberately turn them on. A leaked /actuator/env dumps your entire resolved configuration, including property names an attacker can use to fingerprint the stack; /actuator/heapdump hands over live memory. Never answer "expose all" in an interview.

The strongest control is topological: set management.server.port to a port distinct from the application port and bind it to the internal interface. Kubernetes probes and your Prometheus scraper reach it inside the cluster; the ingress only ever publishes the application port, so the management surface is simply not reachable from the internet regardless of what is exposed on it. Layer authentication on top with Spring Security using EndpointRequest.toAnyEndpoint() to match the actuator paths, and keep the probe endpoints themselves unauthenticated — the kubelet cannot present credentials — which is safe precisely because they return only a status code and, in the liveness group, no detail at all.

management:
  server:
    port: 8081                        # separate port; ingress publishes only 8080
    address: 127.0.0.1                # or a cluster-internal interface
  endpoints.web:
    base-path: /actuator
    exposure.include: health,prometheus   # allow-list; never "*"
    exposure.exclude: env,heapdump,threaddump,shutdown

Synthetic checks and blackbox monitoring: UP is not the same as working

Here is the honest limit of everything above. /actuator/health returning UP means every component that bothered to register an indicator believes itself fine. It does not mean a user can log in. A misconfigured OAuth redirect, an expired signing certificate, a broken CDN path, a feature flag stuck off, a downstream returning 200 with an empty body — none of those move a single health indicator, and all of them are total outages from the customer's point of view. Whitebox health checks are self-assessment; you also need somebody outside the system trying the thing customers actually do.

That is synthetic monitoring, or blackbox probing: a scheduled transaction executed from outside your cluster — often from several regions — that exercises a real user journey end to end (log in, search, add to cart, checkout with a test account) and alerts when the journey breaks or slows, regardless of what the internal dashboards say. The Prometheus Blackbox exporter covers the simple end (HTTP, TCP, DNS, ICMP, certificate expiry); Grafana Synthetic Monitoring and k6 scripts cover scripted multi-step journeys. Run them against production on a schedule, keep the test accounts and their data isolated, and make sure the synthetic traffic is tagged so it never pollutes your business metrics. The deeper point, which module 08 picks up: health checks tell you about components, SLOs tell you about users — and it is entirely possible for every component to be UP while your error budget burns.

Interview questions

Health checks are asked in almost every Indian backend and DevOps round that touches Kubernetes — the liveness-versus-readiness question is near-universal, and the "why not check the database in liveness" follow-up is the one that separates candidates who have configured probes from candidates who have copied them:

Beginner What is the difference between a liveness probe and a readiness probe?

They trigger different actions. A failed liveness probe makes the kubelet kill and restart the container — it answers "is this process wedged beyond recovery?" A failed readiness probe does not touch the container; it removes the pod from the Service endpoints so the load balancer stops sending traffic, and puts it back when the probe passes again. Liveness is destructive and irreversible, readiness is cheap and reversible.

Beginner What is a startup probe and what problem does it solve?

It handles slow-starting applications. While a startup probe is failing, Kubernetes disables the liveness and readiness probes entirely, so a JVM that needs two minutes to boot is not restarted by an impatient liveness probe. Once it succeeds it never runs again and the other probes take over. It is the correct replacement for piling seconds onto initialDelaySeconds, because you can give a generous failureThreshold for boot while keeping a tight liveness period afterwards.

Beginner Which endpoints does Spring Boot Actuator expose for Kubernetes probes?

/actuator/health/liveness and /actuator/health/readiness, backed by health groups. They appear when management.endpoint.health.probes.enabled=true, and Boot enables them automatically when it detects it is running on Kubernetes. Point livenessProbe at the first and readinessProbe at the second — not both at plain /actuator/health.

Beginner Name the probe configuration fields and what each controls.

initialDelaySeconds (wait before the first check), periodSeconds (interval between checks), timeoutSeconds (how long to wait for a response — default 1), failureThreshold (consecutive failures before acting), successThreshold (consecutive passes to recover; must be 1 for liveness and startup), and terminationGracePeriodSeconds (drain window, settable per probe). Detection time is roughly periodSeconds × failureThreshold plus one timeout.

Intermediate Why should a liveness probe never check the database?

Because restarting your process cannot fix someone else's database, and the action is fleet-wide. One database blip fails the liveness probe on every pod at the same instant, so the kubelet restarts the entire fleet simultaneously. They all come back cold with empty pools and caches and stampede the recovering database, turning a partial, self-healing degradation into a full outage with a slow recovery. Database health belongs in readiness, where the consequence is only "stop sending me traffic".

Intermediate Your pods restart randomly under peak load but the logs show nothing. What do you check?

Suspect the liveness probe first: check kubectl describe pod for a "Liveness probe failed" event and a Reason of OOMKilled versus Error. The classic cause is a timeoutSeconds of 1 (the default) being shorter than a stop-the-world garbage-collection pause under load, so the probe times out exactly when traffic is highest. Fix by raising timeoutSeconds and failureThreshold, making the liveness endpoint cheaper, and separating the management port so probe traffic does not queue behind application requests. Also rule out memory limits and CPU throttling.

Intermediate httpGet vs exec vs tcpSocket vs grpc probes — when do you use each?

httpGet is the default and best choice: 200–399 is a pass and it exercises the real HTTP stack. exec runs a command inside the container and is the most expensive — a fork on every period on every pod, and hanging commands leave zombies. tcpSocket only proves a listener accepted a connection, which a deadlocked app still does, so it is a weak liveness signal, useful for non-HTTP services. grpc, stable since Kubernetes 1.24, speaks the standard gRPC health protocol natively and removes the old grpc-health-probe sidecar.

Intermediate Why is show-details set to never by default, and when would you change it?

The detailed body enumerates your dependencies — database product and version, Redis cluster size, disk paths, mail hosts — which is free reconnaissance for an attacker. Probes never read the body, only the status code, so there is no operational need to expose it. Change it to when-authorized behind Spring Security for humans, or always only on a management port that is not routable from outside the cluster.

Intermediate How do you write a custom HealthIndicator, and what are the constraints?

Implement HealthIndicator (or extend AbstractHealthIndicator) as a bean; the bean name minus the healthIndicator suffix becomes the response key. Return Health.up()/down()/outOfService() with optional details. Constraints: it runs on every probe period on every pod, so it must be fast and hard-bounded — a timeout strictly shorter than the probe's, results cached for a few seconds if the check is expensive — and it must not fan out to downstream health checks, or one leaf failure marks a whole dependency tree DOWN.

Pro Walk through what happens when a pod is deleted, and why users see 502s on deploy.

Kubernetes concurrently sends SIGTERM to the container and removes the pod from the Service endpoints. The signal is instant; endpoint removal has to propagate to every kube-proxy and ingress controller, which lags. An app that exits promptly on SIGTERM therefore kills in-flight requests and keeps receiving new ones from load balancers that have not caught up — that is the 502 burst. Fix: a preStop hook that sleeps a few seconds (or flipping readiness to DOWN first) so endpoint removal propagates, then a bounded drain, with terminationGracePeriodSeconds larger than preStop plus drain. In Spring Boot that is server.shutdown=graceful with spring.lifecycle.timeout-per-shutdown-phase, and Boot moves ReadinessState to REFUSING_TRAFFIC when shutdown starts.

Pro Explain ApplicationAvailability, LivenessState and AvailabilityChangeEvent.

Boot models availability as application state rather than endpoint plumbing. ApplicationAvailability is an injectable bean exposing LivenessState (CORRECT or BROKEN) and ReadinessState (ACCEPTING_TRAFFIC or REFUSING_TRAFFIC). Every transition publishes an AvailabilityChangeEvent, and any bean can publish one too — so a Kafka consumer stuck rebalancing can push REFUSING_TRAFFIC and drop out of the load balancer without touching a controller. Boot sets ACCEPTING_TRAFFIC after ApplicationReadyEvent and REFUSING_TRAFFIC when graceful shutdown begins. The default liveness group contains only livenessState — no external dependency — which is the framework encoding the rule for you.

Pro A dependency your service can degrade without is failing. Which probe should reflect it?

Neither. Liveness is out because a restart cannot fix a downstream. Readiness is out because you can still serve — marking the pod not-ready removes capacity for no benefit, and if every replica depends on the same optional service you take yourself fully offline over a degraded feature. Report it as a detail on a non-probe health group or as a metric and alert, and let the circuit breaker degrade the feature. Only a dependency you genuinely cannot serve a request without belongs in the readiness group.

Pro All your health checks report UP but customers cannot log in. How is that possible, and what would have caught it?

Health checks are self-assessment of components. An expired signing certificate, a broken OAuth redirect URI, a feature flag stuck off, a CDN path returning the wrong asset, or a downstream answering 200 with an empty body move no health indicator at all. What catches it is blackbox monitoring: a synthetic transaction run from outside the cluster that performs the real journey — log in, search, checkout with a test account — on a schedule, from multiple regions. The Prometheus Blackbox exporter covers simple HTTP/TCP/DNS/certificate checks; Grafana Synthetic Monitoring or k6 scripts cover multi-step journeys. Tag the synthetic traffic so it does not pollute business metrics.

Pro How would you design health checks and probes for a service with a two-minute warm-up and a hard Postgres dependency?

Startup probe on the liveness path with periodSeconds 5 and failureThreshold around 40–60, so boot gets up to five minutes while liveness stays tight afterwards. Liveness on /actuator/health/liveness with the group limited to livenessState, timeoutSeconds around 3–5 to survive garbage-collection pauses, failureThreshold 3. Readiness on /actuator/health/readiness with the group including readinessState and the datasource indicator, short period and failureThreshold 1 so traffic sheds immediately. Graceful shutdown with a preStop sleep covering endpoint propagation and terminationGracePeriodSeconds above preStop plus drain. Management port separated from the application port, show-details restricted, and a synthetic check exercising a real transaction from outside to catch what the internal endpoints cannot see.
